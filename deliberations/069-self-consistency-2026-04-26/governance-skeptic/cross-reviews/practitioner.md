# Cross-Review of Practitioner — by Governance-Skeptic

**Phase 2 cross-review.** I am evaluating practitioner's review of the v2.4.0 Constitutional Inclusion Criteria gate against my own governance-skeptic review of the same target. The two reviews substantially overlap on intent — both find the gate "directionally correct, operationally fragile" — but they differ in where the operational fragility actually lives, and in a few places practitioner's recommendations would create governance soundness problems that the practitioner lens does not surface. Below I separate the dangerous contradictions (places where adopting practitioner's recommendation would violate constitutional integrity), the live tensions (where reasonable people disagree about scope or mechanism), and the safe agreements (where both reviews converge and the constitution should adopt the consensus).

---

### Dangerous Contradictions

1. **PATCH carve-out for the self-assessment (practitioner Recommendation #4) collides with the Versioning bullet and creates an exploitable bypass.** Practitioner argues PATCH amendments — "clarifications, cross-reference updates, wording refinements" — should be exempt from the three-criterion self-assessment. This is dangerous because the constitution's Versioning rule already permits "material expansions" only at MINOR; the boundary between "clarification" and "material expansion" is itself contested (the v2.3.1 PATCH for Principle XV is arguably a material expansion of the registry-as-extension-interface concept that was added in v2.3.0). If PATCH amendments are exempt from the gate, an amendment author with a borderline expansion has every incentive to classify it as PATCH to skip the self-assessment — exactly the loophole my own review #8 (Versioning classification clarification) was trying to close. Practitioner's recommendation makes that loophole worse rather than better. The correct response to "throat-clearing on typo fixes" is a *lightweight* self-assessment template ("N/A — typo fix" is one valid answer), not a class-wide carve-out. The gate should fire on every amendment; the *cost* of firing should scale with materiality.

2. **Recommendation #5 (mandatory verification deliberation as acceptance bar) over-promotes a process artifact into the constitution and conflicts with Principle V's "warnings, not blocks" stance.** Practitioner proposes lifting "zero disputes from the verification deliberation is the acceptance bar before merge" from spec 066 §7 into Governance. This is dangerous on two axes. First, Principle V (Observable Deliberation) explicitly says output validation "emits warnings for malformed output but does NOT block file writes" — the constitution's stance on automated gates is advisory, not blocking. Codifying "zero disputes blocks merge" reverses that stance specifically for amendments without addressing the inconsistency. Second, "zero disputes" is a high bar that depends on agent panel composition, prompt seeding, and round count — all of which are tunable. An amendment author who controls deliberation configuration can engineer "zero disputes" by selecting agreeable agents, defeating the gate. The verification deliberation belongs in operational guidance (CONTRIBUTING.md or a governance spec), not in the constitution itself, *until* the deliberation harness has a tamper-resistance story. Practitioner's own review §3 critiques the gate for being a "self-assessment with no second pair of eyes mechanically required" — but a tamper-able verification deliberation is not a mechanical second pair of eyes, it's a second self-assessment with more steps.

3. **Recommendation #9 (expedited security/regulatory amendment path) is correct in motivation but the wording weakens the gate's MUST language.** Practitioner proposes that "amendments responding to security disclosures, license-compliance issues, or regulatory changes MAY merge without the verification deliberation step. They MUST still satisfy the three inclusion criteria." This is dangerous as drafted because "license-compliance issues" and "regulatory changes" are open categories that an amendment author defines. There is no neutral arbiter for "is this regulatory?" — the author's own judgment governs. Combined with practitioner's #4 PATCH carve-out, an amendment author has two parallel bypass paths. The fix is not to remove the expedited path but to require *post-hoc* verification (which practitioner does include — "MUST trigger a verification deliberation within 14 days of merge") *with rollback authority* if the post-hoc deliberation finds material issues. The current draft of #9 does not say "with rollback authority" — it only says findings "land as a follow-up amendment," which is exactly what would happen anyway under normal amendment process. Without rollback authority, the expedited path is a one-way door.

4. **Recommendation #10 (cross-link gate from Principle XVII) duplicates classification logic in two places, violating Principle XI which the gate itself dogfoods.** Practitioner notes the symmetry between the v2.4.0 gate (constitutional inclusion vs. operational guidance) and Principle XVII (execution logic vs. contribution guidelines), and proposes a cross-reference. My own review #10 made the same observation but reached a different conclusion: the cross-reference should go *from* the gate *to* XVII (the gate inherits XVII's classification vocabulary), not the other way around. Practitioner's framing — "adding a one-line cross-reference in XVII" — would create a forward reference from a Core Principle (XVII) to a Governance subsection, inverting the constitution's reference topology (Governance references principles, principles do not reference Governance). This matters because XVII is grandfathered while the gate is new; a forward reference would mean the next revision of XVII has to re-justify the gate's existence. Cross-references in this constitution flow newer → older for exactly this reason. Practitioner's recommendation gets the direction backward.

### Tensions

1. **Self-assessment template scope (practitioner #1, #2 vs. my #2).** Both reviews want a template; we disagree on *where it lives*. Practitioner wants three named sections embedded in "the amendment spec template" with worked examples. I argued the template belongs as an "Inclusion Criteria Self-Assessment" section *inside the Sync Impact Report* of each amendment PR, because the Sync Impact Report is the existing audit-trail surface and lives in git history. Practitioner's location (a separate spec template) creates a second authoritative document; mine reuses an existing one. Practitioner's worked examples are valuable; my Sync Impact Report integration is more enforceable. The synthesis is "Sync Impact Report adds the self-assessment section, with worked examples maintained in CONTRIBUTING.md" — but practitioner's review does not name the Sync Impact Report as the host, and that omission is meaningful.

2. **Criterion 2 wording fix (practitioner #7 vs. my "Off-Base Assumptions" entry on coordination).** Practitioner's proposed rewrite ("the principle's wording MUST define its own scope and terms explicitly. A reviewer applying the principle to a hypothetical PR MUST be able to determine *whether the principle applies* without consulting external definitions. Application within scope MAY require judgment; scope determination MUST NOT.") is a real improvement over the current "without requiring 'interpretation'" language. But it does not address the coordination-vs-duplication problem my review flagged: Principles XV and XXVII coordinate explicitly via cross-references, and practitioner's rewrite would still arguably reject XV/XXVII if they were proposed today (each defines its scope by reference to the other). The wording needs both fixes, not one. Practitioner's version is necessary but not sufficient.

3. **Distinctness criterion's tie-breaker (my #5 80/20 burden-of-proof rule vs. practitioner #5's "no discriminator" critique).** Practitioner correctly identifies that the gate provides no way to distinguish "extension of XXVII" from "new principle" for a hypothetical "Operator Audit Logging" amendment. I proposed a quantitative threshold (≥80% existing coverage means extend, ≥20% residual means potentially new). Practitioner does not propose a discriminator at all — they only flag the gap. Quantitative thresholds in governance text are themselves contested (what counts as "20% residual"? lines of text? semantic distance?). Practitioner's silence may be wisdom: any specific threshold creates new litigation surface. My proposal may be over-specified. The honest answer is probably "criterion 3 needs an arbiter escalation path, not a numeric rule" — and neither review fully articulates that.

4. **Precedent log (practitioner #8) vs. my Sync Impact Report extension (my #2).** Practitioner proposes `deliberations/governance-decisions.md` as a precedent registry indexed by criterion. I proposed extending the Sync Impact Report to include the self-assessment in each amendment PR. These are not mutually exclusive but they are partially redundant — both create an audit trail of how the gate was applied. The Sync Impact Report integration is per-amendment and lives in git history attached to the constitution itself; the precedent log is cross-amendment and lives outside the constitution. The cross-amendment view is genuinely useful for "how has criterion 1 been interpreted across the last five amendments" queries, which a per-amendment Sync Impact Report cannot answer without manual aggregation. But maintaining two sources of truth for the same decisions risks Principle XI violations. The synthesis is "Sync Impact Report is authoritative; the precedent log is a derived index" — which neither review specifies as the relationship.

5. **Extensions semantics (my #3 P1 recommendation vs. practitioner's silence on this surface).** Practitioner does not address whether extensions to grandfathered principles (Principle IX's behavior-over-shape, Principle XI's Registry-First Declaration, Principle XV's v2.3.1 clarification) are subject to the gate. This is the single most exploitable surface in my review and practitioner does not engage with it at all. The closest practitioner gets is #5's observation that "the boundary between refining/extending an existing principle and new principle is fuzzy" — but this frames extensions as a discrimination problem (when do I extend vs. when do I add?), not as a gate-evasion problem (can I append to an existing principle to bypass the gate entirely?). Practitioner's blind spot here is meaningful: a future amendment author reading practitioner's review would see no warning about appending to an existing principle as a bypass.

### Safe Agreements

1. **The gate needs an enforcement hook, and self-assessment alone is insufficient.** Both reviews independently identify this as a P1 issue. Practitioner #2 ("No CI hook is named, even speculatively") and my #2 ("Wire the gate into the amendment workflow explicitly") arrive at the same conclusion through different framings. The constitution should require *some* mechanical forcing function on amendment PRs — minimally, a grep that fails the PR if the self-assessment section is missing. This is the highest-confidence finding from both reviews.

2. **The v2.4.0 sync impact report is missing from the candidate file and should be added.** Practitioner's #6 ("Add a v2.4.0 sync impact report to the top of the document") is correct and uncontroversial: the file's top-level Sync Impact Report describes v2.3.0 → 2.3.1 (the XV clarification), not v2.3.1 → 2.4.0 (this amendment). Adding the v2.4.0 report is a self-consistency fix that the constitution's own change-tracking discipline already requires. My review did not flag this — practitioner's catch is a clean win.

3. **Operational guidance routing needs to be a decision tree, not a flat list.** Both reviews note that "`CONTRIBUTING.md`, the relevant spec, `SKILL.md`, or domain-specific reference documents" is a four-way choice without a decision rule. Practitioner #6 proposes a routing table; my #9 disambiguates `SKILL.md` from the others (it's runtime-enforced, not advisory). Both improvements are compatible and both should land. Practitioner's routing table is the more user-facing improvement; my `SKILL.md` disambiguation prevents misclassification at the tail end of the routing table. The synthesis is straightforward: build the routing table, mark `SKILL.md` distinctly within it.

4. **Criterion 1's "concrete enough... in one paragraph" is itself a vague test that fails its own criterion 2.** Both reviews identify this self-referential weakness independently (practitioner §3 in Missed Opportunities, my P2 #4). Both propose roughly the same fix: require the amendment PR description to actually contain the one-paragraph sketch, identifying the check type. This is a clean dogfooding improvement and there is no reason not to adopt it.
