### New Recommendations

- **Specify GapFiller.fill() atomicity requirement for stage-2 pinning** (Priority: P1)
  - **Triggered by**: Mathematical's cross-review (Missed Opportunities, fourth item) and Rec 3: "if `fill()` fails partway through, subsequent retries may see a partially-pinned state... re-invoking the gap-filler mid-deliberation in the letter of the prohibition." My own cross-review of mathematical (Tensions, "GapFiller.fill() partial failure: unaddressed by both but framed differently") acknowledged this as a distinct gap that my XVI/XV resolution does not cover: "gap-filling is core execution, not plugin execution... the two fixes address different components and must not be collapsed into one."
  - **Proposed change**: Add to XVI's stage-2 description or to the Clarification v2.3.2 enforcement block: "The `GapFiller.fill()` call MUST be treated as atomic for pinning purposes: either all gap identifiers resolved in a single `fill()` invocation are written together to `objective.yml`, or none are and the call is retried from scratch. A partial result that leaves some identifiers pinned and others unresolved is an invalid state. The run orchestrator MUST detect this state — by comparing the set of gap identifiers produced in stage-1 against the set of keys present in `objective.yml` after `fill()` returns — and either retry `fill()` from scratch (re-resolving all identifiers) or abort with an error. Proceeding with a partially-pinned `objective.yml` is prohibited."
  - **Rationale**: The existing prohibition ("The LLM MUST NOT be re-invoked for parameter resolution within the same run") addresses deliberate re-invocation but leaves the partial-failure scenario unspecified. If `fill()` fails after writing three of seven identifiers to `objective.yml`, a retry that invokes `fill()` only for the remaining four identifiers is structurally "re-invocation for parameter resolution within the same run" — prohibited by the letter of the existing text — yet the alternative (aborting with a partially usable artifact) is also unspecified. Implementations will diverge. The atomicity requirement resolves this cleanly, is mechanically verifiable (a contract test can inject a partial-fill failure and assert the orchestrator rejects or retries rather than proceeding), and is not covered by any other principle.

- **Add template registry stability requirement to XVI enforcement block** (Priority: P2)
  - **Triggered by**: Mathematical's cross-review Rec 6 ("Add explicit template registry stability requirement") and Tensions section ("Template registry stability: explicit prohibition vs. implicit dependency"): "The byte-identity guarantee has an implicit dependency on template registry stability... unstated dependencies in constitutional text create exactly the silent failures Principle X warns against." My own cross-review of mathematical (Tensions, "Template registry stability") acknowledged: "Mathematical's rec 6 (template registry stability) is a precondition for the behavioral guarantees cross-principle's contract test recommendations are designed to verify. Synthesis should adopt mathematical's rec 6 early in the implementation ordering."
  - **Proposed change**: Add to XVI's Clarification v2.3.2 enforcement block: "The template registry MUST be treated as immutable for the duration of a deliberation run. A template modification or registry update between stage-1 symbolic parsing and stage-3 deterministic assembly within the same run violates requirement (2)'s byte-identity guarantee and constitutes a silent failure under Principle X: the assembled objective function would differ from what stage-1's gap-identifier set implies without any error signal. Principle V's phase-report emission is meaningful only when the template registry is byte-identical between the parse and assembly phases of a single run; a mid-run registry change makes the emission misleading. The existing Clarification already notes this scoping condition for cross-run scenarios ('a registry change between runs makes the emission misleading rather than auditable'); this requirement extends the same constraint to within-run scenarios."
  - **Rationale**: My Rec 2 (stage-3 verification artifact) and Rec 7 (IX cross-reference for stage-2 contract tests) both implicitly depend on template registry stability. A contract test for stage-3 bit-identical assembly can be circumvented by a hot-reload between parse and assembly; the test passes but the guarantee is violated. Making the implicit constraint explicit satisfies Principle X's anti-silent-failure requirement, is directly verifiable (a contract test can inject a registry modification between stage-1 and stage-3 and assert the orchestrator detects and errors), and closes a gap that neither my original recommendations nor mathematical's directly addressed, though mathematical's Rec 6 identified it.

### Position Summary

I am withdrawing zero recommendations, modifying three (Recommendations 1, 2, and 5), maintaining four (Recommendations 3, 4, 6, and 7), and adding two new recommendations from the cross-review process.

The most significant change in my thinking concerns the plain-language pairing requirement. My original position (Rec 1) was to keep the requirement in XVI and resolve the XVI/XV composition gap through in-place patching. Mathematical's cross-review exposed that schema enforcement addresses presence but not adequacy, and that a requirement whose adequacy is interpretation-dependent cannot satisfy Governance Criterion 2 regardless of how the enforcement tier is specified. I pre-committed in my cross-review of mathematical to the threshold: "the in-place patch is acceptable IF AND ONLY IF a minimum-sufficiency test can be written; absent that test, the excision wins." I cannot write that test. The excision path is therefore more constitutionally sound, and I have modified Recs 1 and 5 accordingly. The XVI/XV composition concern I originally raised is real but migrates to the receiving document: wherever the requirement lives, the XV failure semantics must be explicitly stated.

My highest-priority surviving recommendation is the newly added atomicity requirement for GapFiller.fill() (New Recommendation 1, P1). The existing prohibition on within-run re-invocation does not specify what happens when `fill()` partially succeeds before failing — a scenario where retrying the remaining gaps is structurally "re-invocation" under the current text yet the only alternative to aborting entirely. Without an explicit atomicity requirement, implementations will diverge on this edge case, and the partial-pinned-state scenario can produce a subtle violation of the pinning discipline that the current prohibition does not cover. The fix is precise, the verification path is concrete, and the gap is not addressed by any existing principle or by my original seven recommendations.
