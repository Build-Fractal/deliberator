### Executive Summary

Principle XVI governs how conversus handles mathematical optimization — specifically, how objective functions are assembled, how parameters are pinned against re-resolution, and how numerical plugin outputs are paired with plain-language explanations. The principle attempts to accomplish three things simultaneously: enforce within-run reproducibility of the assembled objective function, discipline the stochastic LLM gap-filling stage through pinning, and require interpretable output from optimization plugins. These are three distinct concerns with different verification mechanisms, different stakeholders (orchestration code, provider protocol, plugin authors), and different failure modes.

The overall assessment is mixed. The pinning discipline (requirement 1) and shape determinism (requirement 2) are logically coherent, mutually supporting, and mechanically verifiable — the CI lint sketched in the Enforcement sub-bullet is feasible and specific. The third requirement (plain-language output pairing) fails the constitution's own falsifiable-scope gate: what the principle provides is a worked example, not a verifiable criterion. This means requirement 3 is indistinguishable from operational guidance dressed in constitutional language. Additionally, the headline's "byte-identical on every assembly" framing overpromises: it does not acknowledge that byte-identity is scoped to within-run, fully-pinned-parameter executions — the Clarification carves this back, but a reader of the headline alone is misled. Finally, the principle's present-tense MUST language is structurally inconsistent with the Origin note's admission that the enforcement infrastructure is "partly under construction."

The single most important recommendation: split requirement 3 (plain-language output pairing) out of Principle XVI entirely, relocate it to operational guidance, and narrow the principle to the two mechanically verifiable claims — pinning discipline and shape determinism — which can both be CI-enforced with feasible contract tests.

### Alignment

- **Pinning discipline anchored to a concrete artifact** (Principle XVI, 3-stage pipeline block, stage 2): The principle requires resolved parameter values to be persisted to `objective.yml` and explicitly prohibits re-invoking the LLM for parameter resolution within a deliberation run. This is structurally specific and enforceable: a contract test can confirm that invoking the assembly path twice within the same run artifact reads from `objective.yml` rather than calling `GapFiller.fill()` a second time. The Enforcement sub-bullet explicitly anticipates a CI lint detecting "re-entrant `GapFiller.fill()` calls," making the verification path concrete.

- **Deliberation run defined with meaningful precision** (Principle XVI, Clarification block, "deliberation run" definition): The definition — "the lifetime of one `objective.yml` artifact; retries that reuse the same artifact are part of the same run, separate `/conversus run` invocations producing new artifacts are different runs" — is precise enough to flag a hypothetical violating PR. A PR that re-invokes gap-filling mid-run while reusing the same `objective.yml` path is structurally detectable as a violation. This level of precision is exactly what the Governance section's falsifiable-scope criterion requires.

- **Cross-run vs. within-run variance explicitly partitioned** (Principle XVI, Clarification, items b and c): The principle correctly separates "cross-run variance in resolved parameter *values* is acceptable" from "cross-run variance in the assembled objective function's *shape*... is prohibited." This partitioning is logically sound and aligns with how deterministic assembly actually behaves: the template and gap-identifier set should be stable; the user-supplied numeric values need not be. Conflating these two variance types is a common design error, and the principle avoids it.

- **Observability obligation linked to reproducibility precondition** (Principle XVI, Observability sub-bullet): The requirement that Stage 2 emit a Principle V phase-report line is correctly conditioned on Principle VII's reproducibility preconditions holding. The note that "a registry change between runs makes the emission misleading rather than auditable" shows that the principle's authors understood the dependency. This is appropriate defensive scoping.

### Missed Opportunities

- **"Plain-language explanation" has no minimum-sufficiency test**: The principle requires that every plugin recommendation include a plain-language explanation alongside numerical outputs. The worked example ("87% of agents are at their best possible position...") illustrates the intent, but what makes it sufficient is unstated. Is "Equilibrium quality: 0.87 (high)" a violation? Is "above average convergence" sufficient? A reviewer cannot answer these questions without "interpretation" — which the Governance section's Criterion 2 explicitly says means the principle is too vague for constitutional inclusion. The principle needs either a minimum-sufficiency test (e.g., "must be expressible in terms that do not require knowledge of the underlying model") or honest relocation to operational guidance. Impact: **high** — this is the only requirement in the principle that fails the constitution's own inclusion gate.

- **Byte-identical claim in headline is unscoped**: The headline states "the assembled objective function is byte-identical on every assembly" as a structural claim. This is true only given a fully-pinned parameter set within the same deliberation run. The Clarification correctly carves this back, but the headline does not acknowledge the scoping condition. A reader who only reads the headline walks away believing the claim is stronger than it is. The fix is minimal: "given a fully-pinned parameter set, the assembled objective function is byte-identical on every assembly within a deliberation run." Impact: **medium** — this creates a misleading headline, which is a real problem in a specification that agents consume as execution truth.

- **Stage 1 has no headline structural requirement**: The principle's headline enumerates three structural requirements: parameter pinning (maps to Stage 2), shape determinism (maps to Stage 3), and plain-language output pairing (maps to neither stage — it's a plugin output requirement). Stage 1 (symbolic parsing) has no corresponding headline claim. The body correctly says Stage 1 is deterministic, but the headline's three-requirement framework creates a false impression that the three requirements correspond to the three pipeline stages. This dual-framework structure (three requirements vs. three stages) is an organizational incoherence that forces readers to mentally reconcile two competing taxonomies. Impact: **medium** — it does not create a logical error, but it does create comprehension overhead in a principle that already has significant density.

- **Partial failure during GapFiller.fill() is unaddressed**: Stage 2 is stochastic "at the `GapFiller.fill()` boundary." The principle says "all resulting parameter values MUST be pinned together once `fill()` returns." But what happens if `fill()` fails partway through? If partial results have been committed to `objective.yml` before the failure, subsequent retries may see a partially-pinned state. If partial results are not committed, the retry invokes `fill()` fresh — which is correct behavior but amounts to "re-invoking the gap-filler mid-deliberation" in the letter of the prohibition. The principle is silent on this edge case. A contract test would immediately expose the gap. Impact: **medium** — the failure mode is real; the principle should state whether partial results are atomic-commit or invalid-state.

- **Enforcement sub-bullet describes future work as present-tense obligation**: The Enforcement sub-bullet says "Principle XXIV applies — a contract test reproducing the re-resolution failure pattern is required, filed as a follow-up to spec 014 FR-012/SC-004." The word "required" is present-tense obligation; the phrase "filed as a follow-up" is future work. These are in tension. Either the test exists (and the enforcement is real) or it does not (and the enforcement is aspirational). The principle should distinguish between "enforcement mechanism exists now" and "enforcement mechanism is planned." Impact: **medium** — without this distinction, agents reading the principle as execution truth may behave differently than a reader who knows the distinction.

- **"Deliberation run" definition creates an ambiguity at version boundaries**: The Clarification defines a deliberation run as "the lifetime of one `objective.yml` artifact" and explicitly says "Cross-version replay (re-running after a `conversus` upgrade) is out of scope of this principle." However, it does not address what happens when `conversus` is upgraded mid-run — i.e., a run begins, the system is upgraded, and the run resumes. Is the resumed run a continuation (same artifact) or a new run (new version context)? This is an edge case, but for a principle that governs invariants, silent edge cases are constitutionally inconsistent with Principle X (errors should never pass silently). Impact: **low** — the edge case is rare; acknowledging it in-scope or explicitly out-of-scope is the fix.

- **No requirement for template registry stability between assemblies**: The principle requires byte-identical assembly given a fully-pinned parameter set, but the template registry that Stage 1 parses is not required to be stable between assemblies within a run. If the template registry changes between the first and second assembly of the same objective function (e.g., due to a plugin reload), byte-identity would fail without any parameter re-resolution occurring. The Observability sub-bullet notes that registry changes make phase-report emissions misleading, but does not prohibit registry mutation during a run. The byte-identity guarantee implicitly requires registry stability; the principle should make this explicit. Impact: **low** — the implicit dependency is likely honored by the runtime in practice, but unstated dependencies in constitutional text are exactly what creates "silent failures" (Principle X).

### Off-Base Assumptions

- **Assumption: three headline structural requirements map to three pipeline stages**: The headline presents three structural requirements in order: parameter pinning, shape determinism, plain-language output pairing. The body presents a three-stage pipeline: symbolic parsing, LLM gap-filling, deterministic assembly. A reader naturally assumes these are in correspondence (requirement N ↔ stage N). They are not. Requirement 1 (pinning) maps to Stage 2. Requirement 2 (determinism) maps to Stage 3. Requirement 3 (plain-language) maps to no stage — it concerns plugin output, which is downstream of assembly. Stage 1 has no corresponding headline requirement. The two frameworks create different organizational structures for what is ostensibly the same content. This is not an error in the underlying discipline; it is a structural mismatch in how the principle is presented that will cause agent misreading.

- **Assumption: the plain-language output requirement is constitutionally verifiable**: The Governance section's Constitutional Inclusion Criteria (v2.4.0) require that a principle satisfy mechanical verification capability (Criterion 1) and falsifiable scope (Criterion 2). The plain-language output requirement fails Criterion 2: determining whether "Equilibrium quality: 0.87" satisfies or violates the requirement demands reviewer interpretation. The worked example helps calibrate intuition but is not a test. If this requirement were proposed as a new standalone principle post-v2.4.0, it would fail the gate. It is in the constitution only because it arrived bundled with the mechanically verifiable pinning and shape-determinism requirements, and the bundling obscured the problem. The assumption that bundling three requirements into one principle sidesteps per-requirement gate evaluation is incorrect: each normative claim must satisfy the gate independently.

### Actionable Recommendations

1. **Unbundle plain-language requirement from Principle XVI** (Priority: P1)
   - **Current state**: Requirement 3 (plain-language output pairing) is enumerated as a headline structural requirement alongside parameter pinning and shape determinism.
   - **Proposed change**: Remove requirement 3 from the Principle XVI headline and body. Relocate it to a dedicated section in AGENTS.md or an operational guidance document as a plugin authoring guideline. Amend the Principle XVI headline to read: "When optimization drives decisions, conversus MUST satisfy two structural requirements: (1) **parameter pinning** and (2) **shape determinism**." Add a non-normative note: "Plugin authors SHOULD accompany numerical outputs with plain-language explanations; see operational guidance for plugin authoring standards."
   - **Rationale**: The Governance section's Criterion 2 (falsifiable scope) states that a principle's wording must flag a violating PR "without requiring 'interpretation.'" The plain-language requirement cannot be evaluated without interpretation. The Governance section explicitly says such requirements "belong in operational guidance."
   - **Risk if ignored**: The plain-language requirement will be cited in code reviews as justification for subjective stylistic edits to plugin output, creating reviewer friction. More seriously, an agent enforcing the constitution by its text will be unable to make a consistent determination about compliance — exactly the failure mode the falsifiable-scope criterion exists to prevent.

2. **Scope headline "byte-identical" claim explicitly** (Priority: P1)
   - **Current state**: Headline reads "the assembled objective function is byte-identical on every assembly" without scoping conditions.
   - **Proposed change**: Amend to: "the assembled objective function is byte-identical on every assembly **within a deliberation run, given a fully-pinned parameter set**."
   - **Rationale**: The Clarification already makes this scoping explicit, but constitutional principles are consumed as headlines by agents skimming for enforcement criteria. A misleading headline is a functional bug in a prompt-orchestrated system where "SKILL.md edits carry the same weight as code changes" (Principle IV).
   - **Risk if ignored**: Agents reading the headline as the enforcement criterion will flag cross-run parameter variation as a violation, producing false positives. The Clarification carve-out will be missed by agents that do not load the full principle text.

3. **Add atomicity requirement for GapFiller.fill() partial failures** (Priority: P2)
   - **Current state**: The principle says "all resulting parameter values MUST be pinned together once `fill()` returns" but does not address what happens if `fill()` fails before returning.
   - **Proposed change**: Add to the Stage 2 block: "If `GapFiller.fill()` fails before returning, any partial results MUST NOT be persisted to `objective.yml`. The run orchestrator MUST treat a `fill()` failure as requiring a fresh invocation of `fill()` (not a mid-run parameter resolution), which is permitted because no `objective.yml` artifact exists from the failed call."
   - **Rationale**: The pin-once discipline depends on `fill()` being atomic. Without an explicit atomicity requirement, a retry after partial failure re-invokes `fill()`, which is correct behavior but reads as a prohibition violation under the current text. The contract test sketched in the Enforcement sub-bullet would immediately expose this gap.
   - **Risk if ignored**: Implementors handling `fill()` failures will either (a) violate the no-re-invocation rule to be correct, or (b) honor the no-re-invocation rule and ship a broken retry path. Both outcomes are worse than an explicit atomicity clause.

4. **Reconcile two organizational frameworks** (Priority: P2)
   - **Current state**: The headline presents three structural requirements. The body presents a three-stage pipeline. These map as: requirement 1 → stage 2, requirement 2 → stage 3, requirement 3 → no stage. Stage 1 has no corresponding requirement.
   - **Proposed change**: After removing requirement 3 (per recommendation 1), restructure the headline to explicitly reference the pipeline: "conversus's optimization pipeline MUST satisfy two invariants across its three stages: (1) **parameter pinning** — the LLM gap-filling stage (stage 2) produces values that are persisted and not re-resolved within a deliberation run; (2) **shape determinism** — the deterministic assembly stage (stage 3) produces byte-identical output given a fully-pinned parameter set." This makes the stage-to-requirement mapping explicit.
   - **Rationale**: Dual taxonomies in a principle that agents consume as execution logic create systematic misreading. Agents will either apply the three-requirement framework (missing stage 1's determinism) or the three-stage framework (finding no corresponding requirement for stages 1 and 3), depending on which they encounter first.
   - **Risk if ignored**: Agent misreading of the principle will produce enforcement that is inconsistent with the principle's intent — precisely the failure mode Principle IV warns against when SKILL.md text is ambiguous.

5. **Distinguish shipped enforcement from planned enforcement** (Priority: P2)
   - **Current state**: Enforcement sub-bullet says "a contract test... is required, filed as a follow-up to spec 014 FR-012/SC-004." The MUST language is present-tense; the "filed as a follow-up" is future work.
   - **Proposed change**: Replace "is required" with "is pending (tracked in spec 014 follow-up)." Add an explicit notice: "Until the contract test ships, this principle's enforcement depends on code review and manual verification." Add a cross-reference to the Governance note about partial enforcement acknowledgment in the Origin.
   - **Rationale**: Constitutional principles are consumed as executable truth. Present-tense MUSTs with future-tense enforcement create a false impression that the safeguard is operational. The origin note already acknowledges "partly under construction" — the enforcement block should be consistent with that admission.
   - **Risk if ignored**: Agents and engineers will assume the contract test exists, skip the manual verification step, and miss the re-resolution failure mode that the principle was created to prevent.

6. **Add explicit template registry stability requirement** (Priority: P2)
   - **Current state**: Byte-identical assembly is required "given a template and a fully-pinned parameter set." Template registry stability during a deliberation run is not required.
   - **Proposed change**: Add to the Stage 3 block or the Clarification: "The template registry MUST be treated as immutable for the duration of a deliberation run. Plugin reloads or registry updates that occur during a run MUST NOT take effect until a new run artifact is created. Template registry changes between the first and second assembly of the same objective function are a violation of the byte-identity guarantee."
   - **Rationale**: The byte-identity guarantee has an implicit dependency on template registry stability. Unstated dependencies in constitutional text create exactly the "silent failures" Principle X (and Principle V's "agents MUST NOT silently swallow errors") warn against.
   - **Risk if ignored**: A plugin hot-reload feature (plausible given Principle XV's plugin isolation framework) could violate byte-identity without violating any stated prohibition. The template registry stability requirement closes this gap.

7. **Address the version-boundary edge case for deliberation run definition** (Priority: P3)
   - **Current state**: Cross-version replay is declared out of scope. Mid-run upgrades are not mentioned.
   - **Proposed change**: Add to the "deliberation run" definition: "A `conversus` upgrade that occurs after a deliberation run has begun constitutes a new version context. The run orchestrator MUST either (a) complete the run using the pre-upgrade binary, or (b) abort the run and require a fresh invocation that creates a new `objective.yml` artifact. Resuming a run from a pre-upgrade `objective.yml` using a post-upgrade binary is prohibited — it creates an ambiguous version context in which neither the old nor new enforcement rules cleanly apply."
   - **Rationale**: The principle goes to lengths to define "deliberation run" precisely. A definition that is silent on in-progress upgrades leaves a real operational edge case unaddressed. This is a falsifiability gap: a PR implementing mid-run upgrade recovery would be neither clearly permitted nor clearly prohibited.
   - **Risk if ignored**: Low probability, but the failure mode (mid-run upgrade corrupting pinned state) is difficult to debug because the version context ambiguity is not flagged by any existing constraint.
