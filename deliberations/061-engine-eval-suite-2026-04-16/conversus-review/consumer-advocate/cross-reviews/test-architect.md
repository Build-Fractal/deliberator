# Cross-Review: consumer-advocate reviewing test-architect's review

---

### Dangerous Contradictions

- **Mock provider: fix it vs. accept it as a distinct test tier**
  - **test-architect claims**: The mock provider's canned output does not exercise the synthesis parser's production path. The smoke tier built on mock is "testing the fallback path rather than the production path." The single highest-leverage change is fixing mock to return parseable synthesis markdown (P0 recommendation #2).
  - **consumer-advocate claims**: Mock provider is fine for structural smoke tests (section 8, endorsing the layered eval architecture). The real consumer concern is not whether mock output is parseable but whether the *consumer surfaces* handle both success and failure gracefully -- schema mapping across surfaces (section 1.3), SDK parity (section 1.4), and error paths producing valid JSON (section 3.3 point 4).
  - **Why this is dangerous**: If test-architect's position is adopted without qualification, the team invests significant effort building a "realistic response mode" for mock that generates well-structured markdown per phase and mode. This is a test infrastructure project masquerading as a bug fix. Meanwhile, the deepeval quality tier already tests with a real provider (anthropic). If the mock provider is upgraded to return realistic output, the smoke tier starts to overlap with the quality tier, and the clean separation between "structural on every commit" and "semantic on release" blurs. Conversely, if consumer-advocate's position is adopted and mock remains as-is, the test-architect is correct that the smoke tier cannot catch synthesis parser regressions -- the `from_events()` bare except means mock always succeeds trivially.
  - **Suggested resolution**: Do not build a general-purpose "realistic response mode" for mock. Instead, add a single targeted test: one smoke test that calls `parse_synthesis()` directly with a known-good markdown string (a fixture, not mock-generated output) and asserts the five output fields are populated. This catches parser regressions without entangling mock provider behavior with synthesis format expectations. The mock provider stays cheap; the parser gets its own test. Both reviewers' concerns are addressed without the mock provider becoming a shadow LLM.

- **SDK surface priority: P2 (test-architect) vs. P0 (consumer-advocate)**
  - **test-architect claims**: "Add SDK surface to cross-surface parity tests" is recommendation #12, priority P2 ("should fix before declaring the suite complete"). The test-architect's P0 list focuses on multi-round pipeline tests, mock provider fix, adhoc red-blue through parse_config, and provider test levels.
  - **consumer-advocate claims**: "Add SDK surface to cross-surface parity tests" is the first item in the summary table, priority P0. The rationale is that `engine.sdk.Deliberation` is the primary consumer surface for CI/CD pipelines and any programmatic Python integration, and omitting it means the most composable surface is untested.
  - **Why this is dangerous**: The SDK is how external Python code calls the engine. CI/CD pipelines using conversus as a library (not a subprocess) depend on this surface. If SDK parity is deferred to P2, the suite can declare "cross-surface parity validated" while the SDK returns `engine.sdk.Result` (5 fields: headline, summary, full_analysis, quality_indicators, debate_transcript) and MCP returns `engine.results.DecideResult` (5 different fields: sufficient, classification, output, cost_estimate, errors). These are structurally incompatible types. A consumer migrating from CLI to SDK will discover this mismatch only at runtime. Meanwhile, if multi-round pipeline tests (test-architect's P0 #1) are prioritized over SDK parity, the suite validates an advanced engine feature before validating the basic consumer contract. Multi-round deliberations are an edge case for most consumers; SDK type correctness affects every programmatic consumer.
  - **Suggested resolution**: SDK cross-surface parity belongs at P1, not P0 or P2. It should be implemented after the P0 bugs are fixed (G1, G2) and alongside the settings cascade and SKILL.md parity tests. The specific test: `Deliberation(question="Q", provider="mock").run()` returns a `Result` whose field set matches the CLI JSON output field set. This is a single test, not a test infrastructure project, and it closes the most visible consumer-facing gap.

### Tensions

- **Multi-round and arbiter coverage vs. consumer surface coverage**
  - **test-architect's position**: Sections 2.2 (multi-round), 2.3 (arbiter), and 2.4 (iterations) collectively argue that the highest-complexity engine code paths have zero dedicated eval tests. The test-architect calls multi-round pipeline tests a P0 and arbiter tests a P1. The argument is technically sound: rounds, stagnation detection, inter-round arbitration, and iteration loops are the most complex code paths in phases.py and the most likely to harbor bugs.
  - **consumer-advocate's position**: Sections 1-3 and 5 focus on consumer surfaces (SDK, Desktop Extension, Claude Code, CI/CD, OpenCode, Codex, Cowork, claude.ai) and the composability contract across those surfaces. Multi-round and arbiter are not mentioned because most consumers use single-round ad-hoc deliberations (the `decide` command with defaults).
  - **Nature of tension**: The test-architect is optimizing for "test the code that is most likely to break," which is the complex engine internals. The consumer-advocate is optimizing for "test what consumers actually use," which is the surfaces and their contracts. Both are valid testing philosophies, but resource allocation forces a choice. The spec cannot test everything at once. The test-architect's multi-round tests catch engine bugs that affect power users running config-based deliberations. The consumer-advocate's surface tests catch integration bugs that affect every user, including those who never touch a config file.
  - **Coordination needed**: The implementation order should interleave engine-depth tests and surface-breadth tests rather than completing one before the other. Concretely: after the P0 bug fixes (G1, G2), alternate between adding one multi-round smoke test (test-architect) and one cross-surface parity test (consumer-advocate). This prevents either dimension from being fully deferred.

- **Desktop Extension divergence: two codebases vs. one test target**
  - **test-architect's position**: Section 2.5 identifies that `desktop-extension/server/lib/engine/` is a separate copy of the engine with its own inline type definitions. The test-architect asks whether the two copies are byte-identical and whether evals should run against both. This is framed as a structural concern about the spec's "cross-surface parity" claim.
  - **consumer-advocate's position**: Section 3.1 identifies Desktop-specific failure modes (content scanner rejection, claude-desktop provider fallback, sensitive field handling, darwin-only compatibility) but does not flag the two-codebase problem explicitly. The consumer-advocate treats the Desktop Extension as a consumer surface with its own behavioral requirements, not as a second copy of the engine.
  - **Nature of tension**: The test-architect sees a code duplication problem that undermines the entire eval strategy. If the Desktop Extension has its own engine copy, testing the main engine says nothing about Desktop behavior. The consumer-advocate sees a consumer behavior problem that exists regardless of whether the code is duplicated or shared. Both are right: the duplication is structurally dangerous (test-architect) AND the consumer-facing behaviors need their own tests regardless of the duplication (consumer-advocate). The test-architect's concern is more fundamental -- if the engine is forked, surface-level tests on the main engine do not protect Desktop users at all.
  - **Coordination needed**: The spec must first answer the test-architect's question: which copy is canonical? If `desktop-extension/server/lib/engine/` is a build artifact (generated from the main engine), add a build-parity test. If it is independently maintained, the entire eval suite must run against both copies. Only after this is resolved do the consumer-advocate's Desktop-specific behavioral tests become meaningful, because only then do we know which codebase they should target.

- **Provider test depth: instantiation ladder vs. consumer-facing error messages**
  - **test-architect's position**: Section 4.4 defines a four-level provider test ladder: import, instantiate, auth-resolve, dispatch. The argument is that instantiation alone is "trivially insufficient" and that only the dispatch level is meaningful for catching bugs like G3.
  - **consumer-advocate's position**: Section 3.1 point 2 (claude-desktop provider fallback) and section 3.4 (OpenCode/Codex specifics) focus on what consumers see when a provider fails -- clear error messages, graceful fallbacks, not crashes. Section 1.2 focuses on what consumers see when a mode is unsupported.
  - **Nature of tension**: The test-architect wants to validate that providers work end-to-end (can dispatch and get results). The consumer-advocate wants to validate that when providers fail, the failure is consumer-comprehensible. These are different test dimensions: the test-architect tests the happy path depth, the consumer-advocate tests the failure path presentation. Both matter, but they require different test designs. A provider that dispatches successfully but returns a cryptic error message on auth failure is a test-architect pass and a consumer-advocate fail.
  - **Coordination needed**: The provider test ladder should include a fifth level: **error-message quality**. For each provider that lacks auth wiring (the 9 providers in G3), the test should verify that calling `resolve_execution_provider(name)` produces an error message that names the provider, states what is missing, and suggests a remediation step. This addresses both the test-architect's "instantiation is not enough" concern and the consumer-advocate's "error messages must be actionable" concern.

- **Quality threshold calibration: deferred vs. foundational**
  - **test-architect's position**: Section 4.3 calls the thresholds "arbitrary" and recommends either calibrating after the first baseline run or declaring them aspirational.
  - **consumer-advocate's position**: Section 6.3 recommends calibrating thresholds from baselines rather than setting them a priori, with a regression margin of 0.1 below baseline.
  - **Nature of tension**: Both reviewers agree the thresholds are not grounded. The tension is minor: the test-architect is willing to accept aspirational thresholds as a starting point, while the consumer-advocate wants a specific calibration methodology (baseline minus margin). The consumer-advocate's position is more prescriptive but both converge on "run once, observe, then set."
  - **Coordination needed**: Adopt the consumer-advocate's calibration methodology (baseline minus 0.1 margin) but apply it after the first baseline run, as both reviews recommend. This is a safe agreement disguised as a tension.

### Safe Agreements

- **The SKILL.md divergence is a real, high-priority problem**
  - **Shared position**: The test-architect (section 1, paragraph 3) identifies the SKILL.md masking engine bugs as an "important architectural insight that deserves to be an explicit test dimension." The consumer-advocate (section 3.2 point 1) provides the specific divergence: SKILL.md advertises 10 providers while auth.py resolves 4, and recommends moving SKILL.md parity from step 9 to step 4-5 in the implementation order.
  - **Combined evidence**: The test-architect provides the architectural framing (the SKILL.md reimplements the pipeline as prompt instructions, creating a parallel universe). The consumer-advocate provides the concrete test (parse SKILL.md examples, run each via CLI, verify each SKILL.md-advertised provider resolves). Together, these establish both the why (architectural divergence is structurally dangerous) and the how (specific provider-list mismatch test).
  - **Confidence level**: High. SKILL.md parity should be elevated in the implementation order per the consumer-advocate's recommendation, using the test-architect's framing as the architectural justification.

- **The spec tests the simple center and misses the complex edges**
  - **Shared position**: The test-architect's summary states: "it tests the 'simple center' of the configuration space (mock provider, cooperative mode, single round, no arbiter, CLI surface) while leaving the 'complex edges' untested." The consumer-advocate's summary states: "The spec is a solid 70% of what consumers need. The remaining 30% is the SDK surface, the env var cascade layer, CI/CD-specific failure modes, SKILL.md parity, and paid tier groundwork."
  - **Combined evidence**: The reviewers define "complex edges" differently but reach the same conclusion. The test-architect's edges are engine-internal (multi-round, mixed providers, arbitration, all 8 modes through all surfaces). The consumer-advocate's edges are consumer-external (SDK surface, env var cascade, CI/CD exit codes, paid tier placeholders). Both sets of edges are underspecified. The union of both reviewers' missing dimensions is larger than either reviewer identified alone.
  - **Confidence level**: High. The spec needs a second pass that systematically addresses both engine-depth edges (test-architect) and consumer-surface edges (consumer-advocate).

- **The known gaps table (section 5) is a strength**
  - **Shared position**: The test-architect calls it "unusually candid for a spec" (section 1). The consumer-advocate calls it "honest and specific" (section 8). Both reviewers build their gap analyses on top of the existing G1-G10 table rather than discovering the gaps independently.
  - **Combined evidence**: The gaps table enabled both reviewers to focus on what is missing from the table rather than rediscovering what is already known. This is evidence that the table is doing its job. The test-architect extends it with engine-specific gaps (multi-round, arbiter, cancellation). The consumer-advocate extends it with consumer-specific gaps (SDK surface, CI/CD exit codes, Desktop content scanner). The table should grow to incorporate both extensions.
  - **Confidence level**: High. The gaps table format should be preserved and expanded with findings from both reviews.

- **Pydantic schema stability needs testing**
  - **Shared position**: The test-architect (section 5.2) recommends snapshot tests for Pydantic schemas to catch breaking changes. The consumer-advocate (section 1.3) recommends a schema mapping test to verify CLI JSON output is derivable from MCP Pydantic models, and (section 6.2) recommends using `ConversusOutput` as the canonical model both surfaces validate against.
  - **Combined evidence**: The test-architect is concerned about schema drift over time (field additions, removals, renames breaking consumers). The consumer-advocate is concerned about schema inconsistency across surfaces right now (CLI returns `ConversusOutput` fields, MCP returns `DecideResult` wrapping `ConversusOutput`). Both point to the same underlying need: a canonical schema definition that all surfaces are tested against. The test-architect's snapshot test catches regressions; the consumer-advocate's mapping test catches cross-surface inconsistencies. Both are needed.
  - **Confidence level**: High. Implement both: a schema snapshot test (test-architect) and a cross-surface schema mapping test (consumer-advocate) using `ConversusOutput` as the canonical model.

### What the test-architect caught that I missed

1. **Multi-round pipeline tests (section 2.2)**: I did not mention rounds, stagnation detection, or convergence termination at all. These are real code paths that real users will exercise through config files. The test-architect is correct that the most complex orchestration logic has zero test coverage in the spec.

2. **Arbiter interaction tests (section 2.3)**: I did not mention arbiter testing. The arbiter is a conditional Phase 6 with multiple trigger modes and influence levels. The test-architect's enumeration of arbiter test cases (trigger=disputes_remain with/without disputes, influence=binding vs advisory, timing=inter-round with rounds=1) is thorough and identifies real edge cases.

3. **Cancellation testing (section 2.7)**: I did not mention `CancellationFlag` or mid-pipeline cancellation at all. For CI/CD consumers that need to abort long-running deliberations, this is a real gap.

4. **The G1 regression test is not meaningful (section 5.3)**: I noted that G1 exists but did not examine whether the existing test (`test_adhoc.py`) actually catches the bug. The test-architect's observation that the test checks raw YAML rather than calling `parse_config` on the generated config is a precise, actionable finding that I missed entirely.

5. **`VALID_PROVIDERS` hardcoded to two (section 6.1)**: I noted the provider-auth wiring gap (G3) but did not identify that `config.py` line 82 rejects any provider except anthropic and openai in YAML configs. This means even after auth wiring is fixed, config-file-based runs cannot use most providers. This is a more fundamental issue than the auth resolver gap.

6. **The `is-json` assertion is too weak (section 4.2)**: I noted the promptfoo shell-quoting issue (section 6.1) but did not examine the assertion strength. The test-architect is right that checking `headline !== undefined` while ignoring the other 4 required fields is insufficient.

### What I caught that the test-architect missed

1. **CI/CD governance exit codes (section 3.3 point 1)**: The engine has two exit code schemes (interactive and governance). CI/CD pipelines using conversus as a quality gate need governance exit codes (0=PASS, 1=BLOCK, 2=ERROR, 3=META_DISPUTE). The test-architect does not mention exit code semantics at all.

2. **Desktop Extension content scanner rejection (section 3.1 point 1)**: The MCP prompts use a role-split pattern to work around Claude Desktop's content scanner. The test-architect does not test MCP prompts at all -- only MCP tools.

3. **Env var type coercion edge cases (section 2.4)**: `CONVERSUS_MAX_LAUNCHES=abc` should fall through gracefully. The test-architect mentions the settings cascade but does not identify the type coercion path as a distinct failure mode.

4. **Paid tier groundwork (section 4)**: HTTP surface shape, PAID_TIER_REQUIRED error testing, cost telemetry verification, persistence round-trip tests for the paid tier foundation. The test-architect mentions persistence (section 2.6) but does not connect it to the paid tier strategy or test cost telemetry.

5. **Cowork and claude.ai web skills as planned consumers (section 3.5)**: The test-architect does not mention Cowork's HTTP+OAuth transport requirement or claude.ai web skills at all.

6. **MCP tool count assertion for Cursor's 40-tool limit (section 5.1)**: The test-architect does not consider editor-specific constraints. If conversus exposes too many MCP tools, Cursor users cannot use it.

7. **The .mcpb bundle build test (section 5.3)**: The test-architect identifies the desktop extension as a separate engine copy but does not suggest testing the bundle build process itself.

8. **Sensitive field handling (section 3.1 point 3)**: `ANTHROPIC_API_KEY` marked as `sensitive: true` in the manifest should never appear in logs or error output. The test-architect does not mention secret leakage testing.
