### Systemic Contradictions

- **"Verified once" culture produces cascading false assurance across both artifacts**
  - **Manifests in**: Contradiction 3 ("core pipeline works" vs. unverified), Contradiction 4 (backward-compatibility claim without test), sub-step-skeptic's critique of PR #103's "only unit-tested it on a sample" claim, spec-061-completeness-auditor's identification that "DONE" markers in spec 061 §7 are overclaimed at steps 10 and 13.
  - **Root cause**: The project's development practice treats manual verification ("I traced through it once") as equivalent to automated verification ("a test would fail if I broke it"). This works at low complexity but fails when the artifact is safety-critical infrastructure (the strip script gates blind verification validity) or when format hazards accumulate across amendment cycles.
  - **Implication for spec**: Both `specs/067-verification-methodology/spec.md` (if it exists) and `scripts/strip-constitution-for-blind.py` require explicit documentation of what "verified" means: manual trace is insufficient; automated tests that would catch a regression are required. Spec 061's §7 DONE markers should adopt the same standard that spec-061-completeness-auditor applied during this deliberation — "what test would fail if this behavior regressed?"

- **CI smoke tier has no authoritative scope definition, producing opposite repairs from different observers**
  - **Manifests in**: sub-step-skeptic (Rec 2): smoke runs too many things — integration tests violate §4.3 taxonomy. script-end-to-end-tester (Rec 7): smoke runs too few things — strip script is absent entirely. Disputes §1 (Stage B timing) and §2 (test file location).
  - **Root cause**: The smoke tier is labeled in evals.yml but nowhere is its authoritative scope documented — what belongs there, what doesn't, and whether bash steps and pytest tests are equivalent or distinct mechanisms. Each reviewer repaired the aspect they observed without a shared target definition.
  - **Implication for spec**: Spec 061 §4.3's marker taxonomy must be extended with an explicit smoke tier definition that specifies: (a) permitted mechanisms (pytest tests and/or bash steps); (b) marker governance for each; (c) constraints (mock provider only, no API credits, deterministic). This definition must precede any further additions to evals.yml's smoke job. New Rec 30 and Rec 26 both address this symptom; the root fix is the §4.3 definition.

- **Spec-implementation parity violations accumulate across both artifacts and go uncorrected until audited**
  - **Manifests in**: Node 18 vs. Node 22 in evals.yml (spec 061 step 10), PR attribution miscount (step 10 DONE note), XIX sub-headings not documented in strip script (Rec 6), prior SIR preservation undocumented in strip script docstring (Rec 4), dead code at L68–78 asserting a compatibility guarantee not covered by any test (Rec 3).
  - **Root cause**: Principle XIV (Spec-Implementation Parity) is ratified but has no mechanical enforcement. Parity violations accumulate silently because neither the implementation path nor the spec amendment path requires cross-referencing. The violations are discovered only when an auditor specifically looks.
  - **Implication for spec**: Principle XIV needs a mechanical enforcement artifact — either a CI step that diffs authoritative doc against implementation facts (e.g., grep the spec for "Node 18" and fail if evals.yml says "22"), or a structured DONE annotation template that requires explicit parity attestation. The current DONE marker pattern (free-form text) enables the PR #101 attribution error and Node version gap to persist undetected across multiple PRs.

- **False completion signals emerge when per-step DONE markers don't communicate cross-step sequencing dependencies**
  - **Manifests in**: Step 14 MATCH verdict (sub-step-skeptic, spec-061-completeness-auditor New Rec 1), §7 progress header misrepresentation (sub-step-skeptic Rec 1), step 13's DONE annotation silently leaving two §3.1.9 P1 rows unclosed (spec-061-completeness-auditor Recs 1/2/4, sub-step-skeptic New Rec A), step 11 declined without tracking issue (sub-step-skeptic Rec 3).
  - **Root cause**: Spec 061's §7 was designed as a sequential implementation queue. Non-sequential execution (steps 9, 10, 13, 14a before 5, 6, 7, 8) is not inherently wrong, but the DONE annotation format does not record which steps were prerequisites for the step being marked done, or which upstream P1 bugs (G2, G12) remain open. A DONE marker conveys "this step is complete" without conveying "this step was done out of sequence with these open prerequisites."
  - **Implication for spec**: Spec 061 §7 needs a structured DONE annotation format that requires: (1) prerequisite status (which earlier steps were complete or intentionally skipped); (2) open gap list (P1 gaps that were known at DONE time); (3) downstream dependencies (what this step unblocks or blocks). The free-form DONE annotation pattern enabled sub-step-skeptic's "false health signal" diagnosis across multiple steps.

- **Priority labels diverge in meaning across artifacts and reviewers, creating false ordering equivalences in synthesis**
  - **Manifests in**: script-end-to-end-tester's P1 = operational blocker (tool can't produce output). spec-061-completeness-auditor's P1 = coverage gap for a §3.1.9-specified behavior. sub-step-skeptic's P1 = execution order constraint. Disputes §5 (load-bearing fix framing) arises directly from this asymmetry.
  - **Root cause**: Deliberation specs do not define what P1, P2, P3 mean. Each agent imported their own semantic for these labels based on their analytical domain. When a synthesizer reads P1 from both agents simultaneously, there is no way to know whether "P1 from script-end-to-end-tester" and "P1 from spec-061-completeness-auditor" are commensurate.
  - **Implication for spec**: Future deliberation prompts over multi-artifact scopes should define priority labels explicitly: "P1 = blocks the next user-visible workflow step; P2 = should land before next release; P3 = improvement that does not block release." This calibration prevents disputes that are actually semantic mismatches from being treated as substantive disagreements.
