### Dangerous Contradictions

- **Integration test placement creates a double-bind on the marker taxonomy**
  - **sub-step-skeptic claims**: The smoke CI job violates §4.3's marker taxonomy because `TestPersistListShowRoundTrip` carries `@pytest.mark.integration` and runs on every push with no marker filter. Rec 2 (P1) demands adding `-m "not integration and not live and not eval"` to the pytest invocation. (Missed Opportunities item 2, Rec 2)
  - **script-end-to-end-tester claims**: The new `test_strip_constitution.py` should include "Integration test: run `strip_constitution` on a fixture derived from the actual `CONSTITUTION.md`" (Rec 2 item 10), and the strip script should run in the CI smoke job on every push (Rec 7). Both recommendations target the same every-push tier.
  - **Why this is dangerous**: Applying both recommendations forces a choice between two broken states. If the strip-script integration test (Rec 2 item 10) uses `@pytest.mark.integration`, sub-step-skeptic's marker filter excludes it from smoke — defeating Rec 7's stated purpose of catching regressions on every push. If the integration test carries no marker (or a non-integration marker), it violates the very taxonomy sub-step-skeptic is enforcing. A developer implementing both recommendations independently will produce either a coverage gap (test filtered out) or a new taxonomy violation (unmarked integration test in smoke). Neither reviewer surfaces this collision.
  - **Suggested resolution**: script-end-to-end-tester should clarify that Rec 7's CI step is a standalone shell step in evals.yml, not a pytest test. The Rec 2 item 10 integration test should carry `@pytest.mark.integration` and run only pre-release per the taxonomy. This separates the every-push shell step (Rec 7) from the pytest taxonomy (Rec 2), allowing both recommendations to coexist without forcing the double-bind.

- **Adding CI coverage before repairing existing CI violations deepens the false-health problem**
  - **sub-step-skeptic claims**: The smoke CI tier has active violations — G12 causes 11/13 YAML-configured providers to silently fail parse-time validation while smoke reports green; `@pytest.mark.integration` tests run in the wrong tier; the §7 progress header misrepresents completion state. All four P1 fixes must land before additional coverage expansion. (Executive Summary, Recs 1–4)
  - **script-end-to-end-tester claims**: Add the strip script to the CI smoke job immediately as an independent improvement that does not depend on engine correctness. (Rec 7, P2)
  - **Why this is dangerous**: If Rec 7 lands before sub-step-skeptic's P1 fixes, the smoke job now shows four passing steps — strip script plus the three existing steps — while G12 is still open and integration tests still run in the wrong tier. The apparent comprehensiveness of CI increases while the structural violations persist. Future contributors reading a four-step green smoke job will calibrate their trust upward, making sub-step-skeptic's "false health signal" diagnosis harder to act on, not easier. The strip-script step itself passes regardless of G12 — it has no dependency on VALID_PROVIDERS — which means the misleading green signal acquires a new, unrelated passing indicator.
  - **Suggested resolution**: Sub-step-skeptic's four P1 CI repairs (restate §7 header, add marker filter, file step 11 issue, block steps 7–8) should be sequenced before Rec 7's P2 addition. Alternatively, both sets of changes can be bundled in a single evals.yml PR that applies the marker filter, adds the strip-script step, and updates the pytest invocation atomically, so the smoke job grows and is repaired in one commit.

- **`verify_zero_leakage` remediation: behavioral fix vs. docstring update as parallel-but-not-equivalent paths**
  - **sub-step-skeptic claims**: Not addressed — the strip script is outside sub-step-skeptic's scope entirely. However, sub-step-skeptic cites Principle XIV ("After implementing an FR, re-read the FR text. If the implementation deviates, update the spec to match reality") when flagging the Node 18/Node 22 version drift, establishing the principle that the docstring IS the spec. (Rec 7)
  - **script-end-to-end-tester claims**: The `verify_zero_leakage` date check is broken for any `--date 2026-05-01` invocation because prior SIR blocks contain that date. Rec 1 (P1) proposes fixing the behavior. Rec 4 (P2) proposes updating the docstring to document the prior-SIR preservation behavior. Both are listed as separate, individually completable items. (Recs 1, 4)
  - **Why this is dangerous**: If Principle XIV is applied strictly to the strip script — which sub-step-skeptic's citation implies is the correct posture — then the docstring's promise ("The `--date` are the leakage-check anchors — the script greps for these strings") IS the specification, and the prior-SIR date behavior is a spec violation, not a feature to document. Rec 4 (documentation update) landing without Rec 1 (behavioral fix) produces a Principle XIV-compliant docstring that accurately describes a still-broken workflow. The two recommendations are not alternatives; treating them as parallelizable discrete deliverables creates a state where a developer closes Rec 4 as done and considers the strip script compliant while the `--date 2026-05-01` exit code 1 problem persists.
  - **Suggested resolution**: Rec 1 (behavioral fix: exclude HTML comment blocks from date needle scan) is the load-bearing change and must land first. Rec 4 (docstring update) is the follow-on documentation complement. Any PR checklist or issue tracking these recommendations should make the sequencing explicit.

  - **sub-step-skeptic's position**: When implementation diverges from spec text, the spec should be updated to reflect reality. Node 22 is what runs; Node 18 is what the spec claims. Principle XIV requires correction. (Rec 7)
