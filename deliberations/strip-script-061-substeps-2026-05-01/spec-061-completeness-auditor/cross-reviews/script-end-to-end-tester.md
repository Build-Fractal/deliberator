### Dangerous Contradictions

- **CI green-light without date-path validation**
  - **script-end-to-end-tester claims**: Recommendation 7 proposes adding a smoke-tier CI step that runs `strip-constitution-for-blind.py --input CONSTITUTION.md --output /tmp/CONSTITUTION-blind.md --version v...` and asserts exit code 0. The step does not pass `--date`. The recommendation describes this as giving maintainers early detection of "strip-script regressions" on the push that introduces a CONSTITUTION.md format change.
  - **spec-061-completeness-auditor claims**: Recommendation 3 (P1) applies Principle XIV to establish that when "spec says X when implementation does Y," that is a bug in the spec. The existing CI workflow has exactly this problem: spec step 10 says "Node 18" but evals.yml uses `node-version: '22'`. The Missed Opportunities section explicitly predicts the failure mode: "A future CI maintainer sees 'Node 18' in the spec, pins `node-version: '18'`... and breaks the pipeline silently."
  - **Why this is dangerous**: Script-end-to-end-tester's Executive Summary identifies the `--date 2026-05-01` leakage check failure as its first substantive gap: "operators following the docstring usage example... cannot produce a stripped output file at all." The script's docstring explicitly documents `--date` as a standard invocation parameter. A CI step that runs without `--date` exits code 0 even when the documented usage path is completely blocked. Applying spec-061-completeness-auditor's Principle XIV standard: adding a CI step that doesn't exercise the documented `--date` feature creates the same false-assurance problem as the Node 18 documentation gap — maintainers see green CI and have no signal that the script's primary documented workflow fails. Both recommendations implemented simultaneously produce an inconsistent state: CI claims the strip script is verified; the P1 date-path remains broken with no CI detection.
  - **Suggested resolution**: Script-end-to-end-tester's Rec 1 (fix `verify_zero_leakage` HTML exclusion) must precede Rec 7 (add CI step). Once the fix lands, the CI step should include `--date` to exercise the corrected path. If Rec 7 must ship before Rec 1, it should carry an explicit comment following spec-061-completeness-auditor's DONE annotation pattern: `# date-path not validated here — see scripts/tests/test_strip_constitution.py test case 9`.

- **Dead code retention vs. coverage-completeness standard**
  - **script-end-to-end-tester claims**: Recommendation 3 proposes retaining the arbiter-ruling substitutions at script L68-78 "for compatibility with older constitution versions" and adding a comment. The Missed Opportunities section rates the impact as "low — no functional impact," characterizing the substitutions as "no-ops on v3.1.x+ constitutions but retained for compatibility."
  - **spec-061-completeness-auditor claims**: The Missed Opportunities section rates the absent arbiter influence output heading test as "high" impact specifically because "an influence-level heading regression is invisible to all existing tests." The Off-Base Assumptions section distinguishes "template context tests verify the variable is in scope" from "pipeline-level test runs with `influence='advisory'` and asserts heading-level output differences" — code reachable only through a specific path that no existing test exercises constitutes a high-priority coverage gap.
  - **Why this is dangerous**: Script-end-to-end-tester's Recommendation 2 proposes tests using "a fixture derived from the actual `CONSTITUTION.md`" (test case 10: "Integration test: run `strip_constitution` on a fixture derived from the actual `CONSTITUTION.md`..."). Because CONSTITUTION.md v3.1.3 contains no sentences matching L68-78's patterns — those sentences were moved to Amendment record blocks in cycle 2B (v3.1.0), which the earlier Amendment record regex already consumes — the L68-78 substitutions will never execute against any test using v3.1.3 as the fixture. Applying spec-061-completeness-auditor's coverage standard: L68-78 is permanently untested code carrying an unverifiable backward-compatibility claim. Both Recs 2 and 3 are implemented simultaneously; the resulting test suite is green while the dead code claim is unsubstantiated. Any mutation to L68-78 (accidental regex corruption, unintended scope change) silently passes all tests.
  - **Suggested resolution**: Script-end-to-end-tester's current "retain and comment" position is internally inconsistent with its own Rec 2 test plan. The choice should be made explicit: (a) add a synthetic pre-v3.1.0 constitution fixture to the test suite that exercises L68-78, converting the backward-compatibility claim into a tested guarantee; or (b) remove L68-78 and document in the strip script docstring that pre-v3.1.0 constitutions are out of scope for this version of the script. Spec-061-completeness-auditor's coverage standard provides the criterion for choosing: untested backward-compatibility guarantees in safety-critical infrastructure (the strip script gates blind verification validity) warrant a fixture, not a comment.

- **Additions to a documented-gap CI job without sequencing**
  - **script-end-to-end-tester claims**: Recommendation 7 targets adding "a step to the `smoke` job in `evals.yml`" as a P2 addition that "runs on every push."
  - **spec-061-completeness-auditor claims**: Recommendation 3 (P1) identifies the smoke job as having an existing documentation gap: "spec says Node 18; evals.yml uses Node 22; no inline comment, no SIR entry, no spec annotation acknowledging the change." This gap is rated P1 because "a future CI maintainer sees 'Node 18' in the spec, pins `node-version: '18'`... and breaks the pipeline silently."
  - **Why this is dangerous**: Adding a new step to the smoke job before the existing P1 documentation gap is resolved means the job accumulates undocumented state. After both recommendations are implemented, the smoke job has: (a) Node 22 behavior with no documentation, (b) the new strip-script step with no `--date` coverage, and (c) no annotation inventory of what is and is not exercised. A future CI maintainer auditing the smoke job encounters multiple undocumented assumptions compounded across changes. Spec-061-completeness-auditor's Recommendation 3 rationale establishes that each undocumented assumption is independently capable of causing silent pipeline failures; combining two in the same job without sequencing multiplies that risk.
  - **Suggested resolution**: Spec-061-completeness-auditor's Rec 3 is P1 and should be resolved — updating the spec and adding the inline `node-version` comment to evals.yml — before script-end-to-end-tester's Rec 7 adds a new step to the same job. ### Tensions

- **Immediate code fix vs. issue-tracked escalation**
  - **script-end-to-end-tester's position**: P1 recommendations (Recs 1 and 2) propose direct code changes — modify `verify_zero_leakage` and create `scripts/tests/test_strip_constitution.py`. No explicit GitHub issue filing precedes or accompanies the proposed fixes.

The rationale is explicit in Rec 4: "the §3.1.9 influence P1 row has no owner and no issue, making it easy to miss in the next release gate."
  - **Nature of tension**: Direct fixes are faster and reduce time-to-resolution. Issue tracking creates accountability, audit trail, and release-gate signal. Neither is wrong, but they are operationally incompatible without coordination: a direct fix without issue tracking satisfies the code change but leaves no signal for future release-gate reviews of the same system.
  - **Coordination needed**: P1 items with immediate user-visible impact — script-end-to-end-tester's date leakage blocking behavior — can be fast-tracked to direct code change. However, the accompanying test (Rec 2) should be filed as an issue first (adopting spec-061-completeness-auditor's pattern) so that if the test file is incomplete at the time of the code change, the gap is tracked. P2 and below recommendations in both reviews can follow the issue-first pattern without sacrificing P1 urgency.

- **"Core pipeline works" vs. module-API vs. CLI-surface as completeness standards**
  - **script-end-to-end-tester's position**: The Alignment section concludes that "the core stripping pipeline works" for v3.1.3 — all four substantive strip steps (SIR removal, Amendment records, Origins, footer anonymization) function correctly. This is the review's positive baseline claim.
