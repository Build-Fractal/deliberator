### Dangerous Contradictions

- **Q2 Migration Eagerness: Eager vs. Lazy**
  - **skeptical-reviewer claims**: "Adopt Position A (eager, on first conversus invocation). Lazy migration creates permanent split-state where untouched providers never migrate" (Recommendation #7, Priority P2). The reasoning is that eager migration is "one-shot and deterministic."
  - **pragmatist-reviewer claims**: "Adopt lazy (Position B). Migration triggers per-provider on first read of that provider's credentials" (Recommendation #4, Priority P1). The three-provider scenario (Anthropic OAuth + OpenAI env + Gemini OAuth) is the grounding case: lazy scopes each migration to the moment a credential is actually needed.
  - **Why this is dangerous**: These cannot both be implemented. Eager migration fires all-providers at startup; lazy fires per-provider on first read. If the implementation tries to honor both (e.g., eager at startup plus per-provider re-migration on read), the migration may run twice for some providers, potentially triggering the concurrent-save race that skeptical-reviewer independently identifies. The resolution logic for "has this provider already been migrated" also diverges: eager requires a migration-complete flag or directory scan; lazy derives the same answer from `credentials/{provider}.json` existence.
  - **Suggested resolution**: This is the single highest-stakes decision in the cross-review. The pragmatist position is grounded in blast-radius minimization per operation; the skeptical position is grounded in state-consistency guarantees. A cooperative resolution: adopt **lazy** migration (smaller failure blast radius, consistent with the read-path fallback already in place) but add a **one-time startup sweep** that logs which providers remain unmigrated, without acting on them. This gives skeptical-reviewer's observability concern without eager migration's all-or-nothing failure mode.

- **Q3 Fallback Duration: Time-Bounded vs. Permanent**
  - **skeptical-reviewer claims**: "Adopt Position B. Emit a deprecation warning after 3 releases; remove fallback in the 4th. Provide `conversus migrate-credentials` as an explicit migration command" (Recommendation #8, Priority P2). The concern is that permanent fallback means "migration is never truly complete; operational state stays ambiguous indefinitely."
  - **pragmatist-reviewer claims**: "Adopt permanent fallback (Position A). The cost of the permanent fallback is essentially zero. The cost of a time-bounded fallback breaking a user who upgraded after six months and never ran a migration command is high" (Recommendation #5, Priority P2).
  - **Why this is dangerous**: If both positions were partially adopted — e.g., permanent fallback in the implementation but a deprecation warning added — the warning creates a user expectation of eventual fallback removal that the code never enforces. Conversely, if the fallback is genuinely time-bounded but the `conversus migrate-credentials` command is not shipped in the same PR, there is a release window where the fallback will expire before users have a migration escape hatch. This is a concrete regression risk.
  - **Suggested resolution**: Pragmatist should yield partially: permanent fallback in the implementation, but add the `conversus migrate-credentials` command as a future spec item (not in SC-004). This closes skeptical-reviewer's operational-ambiguity concern via tooling rather than expiry. The fallback remains permanent; the migration path becomes explicit and user-triggered rather than time-forced.

- **`os.rename` vs. `os.replace`**
  - **skeptical-reviewer claims**: "Replace all migration rename calls with `os.replace(tmp, final)`" as Priority P1, citing that `os.rename` raises `FileExistsError` on Windows when the destination already exists (Recommendation #1).
  - **pragmatist-reviewer claims**: "then `os.rename(tmp_path, final_path)`" in the implementation description for Recommendation #6 (confirm same-directory `.tmp`). The pragmatist review does not flag `os.rename` as incorrect.
  - **Why this is dangerous**: `os.rename` on Windows fails on second migration attempt (destination `credentials/anthropic.json` already exists from a previous partial run). `os.replace` has POSIX-like semantics on Windows. If pragmatist's recommendation is adopted verbatim, the Windows failure mode is baked in. The pragmatist's focus on `os.makedirs` and permissions — both correct and important — may have caused this Windows correctness issue to be missed.
  - **Suggested resolution**: Pragmatist should yield entirely here. `os.replace` is the correct primitive; it subsumes `os.rename` on POSIX and fixes Windows. This is a one-word change with no trade-off. All `os.rename` calls in the implementation should become `os.replace`.

- **Concurrency Lock (fcntl.flock): P1 Critical vs. Not Mentioned**
  - **skeptical-reviewer claims**: "Use `fcntl.flock` (POSIX) / `msvcrt.locking` (Windows) on the per-provider file during migration" to prevent the concurrent-save race where a fresh token is overwritten by a migrating stale token (Recommendation #3, Priority P1). The failure scenario: Process A migrating stale credentials overwrites Process B's freshly saved token.
  - **pragmatist-reviewer claims**: Not mentioned. The pragmatist review defines migration failure behavior (Recommendation #3) and directory/permission setup (Recommendations #1, #2), but has no concurrency guard.
  - **Why this is dangerous**: If the pragmatist's recommendations are adopted without skeptical-reviewer's locking, the concurrent-save race exists. For a CLI tool, concurrent processes are uncommon but not impossible (background token refresh daemon + foreground invocation, two terminal sessions). The failure mode — silently overwriting a fresh token with a stale migrating one — is the kind of corruption that produces a "my credentials stopped working after the upgrade" bug report with no clear cause. This is not a hypothetical: token refresh daemons and backgrounded conversus processes are real.
  - **Suggested resolution**: Adopt skeptical-reviewer's locking recommendation, but with a pragmatist caveat: the lock must be **advisory and non-blocking with a short timeout** (e.g., 200ms), not a hard block. A CLI should not hang indefinitely waiting for a file lock from another conversus process. If the lock cannot be acquired, skip migration (fall back to legacy), log a warning, and retry on next invocation. This preserves the safety guarantee without introducing UX regression.

### Tensions

- **Post-Migration Verification vs. No Over-Engineering**
  - **skeptical-reviewer's position**: "After `os.replace()`, immediately `_read_all()` the new per-provider file and compare provider key count/token field to source" (Recommendation #9, Priority P3). Surfaces NFS/SMB partial-write corruption before authentication breaks.
  - **pragmatist-reviewer's position**: "No transaction log" and "the atomic-rename pattern is sufficient" (Recommendation #7, Priority P2). The pragmatist's entire model depends on the idempotent fallback handling partial state without additional verification machinery.
  - **Nature of tension**: Post-migration verification adds a read immediately after write on every migration event. On a local POSIX filesystem, this is redundant — if `os.replace` succeeded, the file is consistent. On NFS, it catches a real (if rare) failure. The tension is: does the verification cost (one extra read per provider migration) justify the NFS protection, given that NFS home directories are a niche scenario for a developer CLI?
  - **Coordination needed**: If verification is adopted, it must be fail-open: a verification failure should trigger fallback-and-warn, not crash. The pragmatist's failure-behavior model (Recommendation #3) already defines this path. Verification becomes an optional check before declaring migration complete, not a hard gate.

- **`conversus status` Credential-Source Reporting vs. SC-004 Scope**
  - **skeptical-reviewer's position**: "`conversus status` should report credential source per-provider" as part of resolving the "invisible orphan providers" concern from lazy migration + permanent fallback (Missed Opportunities, "Lazy migration + permanent fallback = invisible orphan providers").
  - **pragmatist-reviewer's position**: No mention of `conversus status` changes. SC-004's contract is bounded to the credential storage format change; the pragmatist review does not recommend scope expansion.
  - **Nature of tension**: Skeptical-reviewer's concern is real — in lazy + permanent-fallback mode, a user cannot tell from `conversus status` whether their Gemini credentials came from `credentials/gemini.json` or from the legacy `auth.json` fallback. This is an observability gap. But adding per-provider credential-source reporting to SC-004 risks scope creep into the final spec needed to close 057.
  - **Coordination needed**: Defer credential-source reporting to a follow-on spec. Add a single-line deprecation log message per pragmatist's Recommendation #5 ("Note: credentials for {provider} loaded from legacy auth.json") to cover the observability gap without a `conversus status` schema change. Log emission is in-scope for SC-004; display changes to `conversus status` are not.

- **`O_EXCL` vs. `O_TRUNC` in `os.open`**
  - **skeptical-reviewer's position**: Create `.tmp` via `os.open(..., os.O_WRONLY|os.O_CREAT|os.O_EXCL, 0o600)` (Recommendation #2). `O_EXCL` ensures exclusive creation — if `.tmp` already exists (orphaned from a previous crash), the open fails rather than silently overwriting.
  - **pragmatist-reviewer's position**: Create `.tmp` via `os.open(tmp_path, os.O_WRONLY | os.O_CREAT | os.O_TRUNC, 0o600)` (Recommendation #2). `O_TRUNC` overwrites any existing `.tmp`.
  - **Nature of tension**: `O_EXCL` treats an orphaned `.tmp` as an error; `O_TRUNC` treats it as a cleanup opportunity. In practice, an orphaned `.tmp` from a previous crash is stale data that should be overwritten — it has no integrity guarantee. `O_EXCL` would require explicit orphan handling (detect, delete, retry) on each migration attempt. `O_TRUNC` is simpler and correct for this use case.
  - **Coordination needed**: Adopt `O_TRUNC`. The `O_EXCL` behavior provides no safety advantage here since the `.tmp` is always discarded or overwritten — it is never read as a recovery path. Skeptical-reviewer's security intent (mode 0o600) is fully preserved with `O_TRUNC`.

- **`PermissionError` Re-Raising vs. Graceful Degradation**
  - **skeptical-reviewer's position**: "Catch `json.JSONDecodeError` and `FileNotFoundError` silently; let `PermissionError` propagate" from `_read_all()` (Recommendation #5, Priority P2). Rationale: unreadable credential files should surface immediately.
  - **pragmatist-reviewer's position**: Migration failure should "catch, log a single-line warning... and fall back to reading from `auth.json[provider]` directly. Do not propagate the exception" (Recommendation #3). The pragmatist model treats all I/O failures during migration as warn-and-degrade.
  - **Nature of tension**: These positions conflict on whether `PermissionError` is a migration failure (pragmatist: log + degrade gracefully) or a hard error (skeptical: propagate). The scenarios differ: `PermissionError` reading `credentials/anthropic.json` that was created with wrong permissions is different from `PermissionError` reading `auth.json` (the fallback). If the per-provider file exists but is unreadable, failing silently into the legacy fallback could mask a real problem; but propagating to the user's terminal is also harsh for a credential read.
  - **Coordination needed**: A middle path: log `PermissionError` at WARNING level (not silent, not crash), skip the per-provider file, fall back to legacy for this session, and surface a user-visible message: "credentials/{provider}.json exists but is not readable (permission denied); check file permissions." This satisfies skeptical-reviewer's "don't silently degrade on PermissionError" without propagating an unhandled exception to the CLI user.

### Safe Agreements

- **Directory creation with mode 0o700**
  - **Shared position**: Both reviews independently identify the absence of `credentials/` directory creation as the most impactful missing item. Pragmatist: "`os.makedirs(Path.home() / '.conversus' / 'credentials', mode=0o700, exist_ok=True)`" rated P1 and called out as "the most likely failure mode in practice" (Executive Summary, Recommendation #1). Skeptical: "Create `credentials/` directory with mode 0o700" (Recommendation #4, Priority P2).
  - **Combined evidence**: Both reviews reach this finding from different analytical approaches — pragmatist from first-run failure analysis ("runtime crash in a common scenario"), skeptical from information-disclosure analysis ("directory is world-listable"). The fact that two reviewers with different threat models independently converge on the same missing implementation detail with the same proposed mode (0o700) is strong signal. The QUESTION.md proposal does not mention directory creation at all.
  - **Confidence level**: High. This should be a non-negotiable P1 implementation requirement regardless of which positions are adopted on Q1–Q4.

- **Q1: Preserve legacy auth.json, never delete**
  - **Shared position**: Both reviews agree on Position B for Q1. Pragmatist: "Preserving `auth.json` is the right call for a local-only CLI tool. The blast radius of a deletion bug dwarfs the blast radius of stale-file confusion" (Alignment section). Skeptical: "Add a post-migration log line: 'Legacy auth.json preserved...'" (Recommendation #6, Priority P2, citing SC-001 precedent).
  - **Combined evidence**: Pragmatist grounds the decision in risk asymmetry (deletion bug impact vs. stale-file impact). Skeptical grounds it in prior art (SC-001's `settings.json` preservation pattern). Both independently invoke the same user-safety principle from different directions. The SC-001 precedent argument from skeptical adds an important consistency dimension that the pragmatist review does not surface: users who already trust that conversus doesn't delete their config files should continue to be able to trust this.
  - **Confidence level**: High. Position B (preserve) is the correct call and both reviews provide complementary justification.

- **File permissions 0o600 on credential files via `os.open`**
  - **Shared position**: Both reviews identify credential file permissions as a missing requirement and recommend the same implementation mechanism. Pragmatist: "Write `.tmp` using `os.open(tmp_path, os.O_WRONLY | os.O_CREAT | os.O_TRUNC, 0o600)`" (Recommendation #2, Priority P1). Skeptical: "open `.tmp` with `os.open(..., flags=os.O_WRONLY|os.O_CREAT|os.O_EXCL, mode=0o600)`" (Recommendation #2, Priority P1).
  - **Combined evidence**: Both reviews independently arrive at `os.open` with mode 0o600 as the correct primitive — not `open()` followed by `chmod`, which has a world-readable window. The mechanism agreement is substantive, not cosmetic. The only variation is `O_TRUNC` vs. `O_EXCL` (addressed in Tensions), which does not affect the security property. The QUESTION.md proposal mentions nothing about file permissions, making this a shared catch with high implementation specificity.
  - **Confidence level**: High. The `os.open(mode=0o600)` approach should be mandated regardless of other decisions.

- **No transaction log for Q4**
  - **Shared position**: Neither review recommends a transaction log. Pragmatist explicitly: "No transaction log... A transaction log would need to track which providers were migrated successfully, handle its own crash during write, and add complexity to the read path. The cost is not justified" (Recommendation #7, Priority P2). Skeptical implicitly: Recommendation #9 (post-rename verification) is the proposed safety measure, not a transaction log. Skeptical notes NFS risk in Missed Opportunities but proposes "checking for orphaned `.tmp` files on startup and logging a warning" as the lightweight alternative.
  - **Combined evidence**: Pragmatist argues transaction log cost > benefit given idempotent fallback. Skeptical proposes a lightweight substitute (orphan `.tmp` detection) that addresses NFS risk without full transaction semantics. Together they establish that `.tmp` + `os.replace` is sufficient with one cheap addition: startup scan for orphaned `.tmp` files, logging a warning if found. This is a jointly-derivable position that neither review states explicitly but both reviews support.
  - **Confidence level**: Medium. Agreement is clear on "no transaction log"; the orphaned-`.tmp` startup scan as a substitute is a synthesis neither review explicitly proposes but both reviews' reasoning supports.
