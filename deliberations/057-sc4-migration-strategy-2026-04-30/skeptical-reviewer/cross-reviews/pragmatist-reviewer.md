### Dangerous Contradictions

- **Q2 verdict: Lazy vs. Eager migration**
  - **pragmatist-reviewer claims**: "Adopt lazy (Position B). Migration triggers per-provider on first read of that provider's credentials." Rationale: smaller per-operation failure blast radius; the failure handler is already in context on the hot path. (pragmatist-reviewer/review.md, Recommendation 4)
  - **skeptical-reviewer claims**: "Adopt Position A (eager, on first conversus invocation). Lazy migration creates permanent split-state where untouched providers never migrate; combined with a time-bounded fallback (Q3), this silently breaks them." (skeptical-reviewer/review.md, Recommendation 7)
  - **Why this is dangerous**: My review identifies a concurrent-save race condition (auth.py:102–106) where process B's freshly-refreshed token is overwritten by process A's lazy migration of the stale pre-migration token. Under lazy migration, this race can fire at any moment during a provider read, at arbitrary runtime points throughout a session. Under eager migration, the race window is confined to startup before any user command executes — a narrower, more predictable window where a startup lock is easier to scope. If lazy is adopted without the concurrency fix my review describes, and the concurrency fix is not implemented, token corruption is a real production failure mode for any user running concurrent conversus processes (e.g., a long-running process plus a CLI invocation). The pragmatist's recommendation for lazy migration does not mention the concurrent-save race at all, which means the two reviews in combination would produce lazy migration code with an unaddressed race condition.
  - **Suggested resolution**: The concurrency issue is load-bearing here. If a file lock (fcntl.flock/msvcrt.locking) is added around the read-migrate-write path, the failure blast radius argument for lazy collapses — the lock already scopes each migration atomically. With a lock, eager becomes strictly safer because it runs once at startup under a single lock scope rather than acquiring and releasing per-provider locks throughout the session. Skeptical-reviewer should yield on blast radius framing; pragmatist-reviewer should yield on the lazy verdict once the concurrency implication is made explicit. Resolution: eager migration with a per-provider file lock during the migration write.

- **Q3 verdict: Permanent vs. Time-bounded fallback**
  - **pragmatist-reviewer claims**: "Adopt permanent fallback (Position A). The fallback is a read-only JSON lookup. Its maintenance burden is a single `if path.exists()` check plus a dict key access." (pragmatist-reviewer/review.md, Recommendation 5)
  - **skeptical-reviewer claims**: "Adopt Position B. Emit a deprecation warning after 3 releases; remove fallback in the 4th. Provide `conversus migrate-credentials` as an explicit migration command." (skeptical-reviewer/review.md, Recommendation 8)
  - **Why this is dangerous**: My review's concern about permanent fallback is operational: `conversus status` (which reports settings cascade per SC-003) would display inconsistent credential sources with no indication of which providers came from legacy vs. new storage. With lazy migration (pragmatist's Q2 position) combined with permanent fallback, providers that are never accessed continue to read from auth.json indefinitely — which means the migration is never complete by definition and the per-provider file layer never becomes the sole source of truth. This is not a hypothetical: any conversus user with Anthropic + Gemini credentials who primarily uses Anthropic would migrate Anthropic and never migrate Gemini. Under lazy + permanent fallback, Gemini silently reads from auth.json forever, and any tooling that assumes "credentials are in credentials/" will miss it. The integration failure is that these two recommendations compound each other in a way that makes the migration semantically incomplete.
  - **Suggested resolution**: The disagreement is resolvable without full time-bounding. Adopt permanent fallback (pragmatist's position) but require conversus status to report credential source per-provider (skeptical's observability concern). This satisfies both: permanent fallback prevents silent breakage for dormant users; per-provider reporting in status prevents the invisible split-state. The explicit `conversus migrate-credentials` command (skeptical's recommendation) becomes a convenience rather than a hard deadline.

- **`os.rename` vs. `os.replace`**
  - **pragmatist-reviewer claims**: "Confirm atomic rename uses same-directory `.tmp`" with the implicit endorsement that `os.rename` is the correct primitive, citing "os.rename is atomic on POSIX filesystems within the same directory." (pragmatist-reviewer/review.md, Recommendation 6 and Alignment section)
  - **skeptical-reviewer claims**: "Replace all migration rename calls with `os.replace(tmp, final)`. `os.rename` raises `FileExistsError` on Windows when destination exists; `os.replace` is atomic and cross-platform." (skeptical-reviewer/review.md, Recommendation 1)
  - **Why this is dangerous**: On Windows, `os.rename` raises `FileExistsError` if the destination already exists. The migration code will attempt to overwrite `credentials/{provider}.json` every time a credential is saved (the `.tmp` → final pattern is not just for migration but for all writes per QUESTION.md L21). This means every second save for any provider silently raises `FileExistsError` on Windows. Pragmatist's review does not address Windows at all. If the implementation follows pragmatist's recommendation and uses `os.rename`, it ships a broken save path on Windows. This is not a rare edge case — it is every Windows user on every credential save after the first.
  - **Suggested resolution**: This is a factual correctness question, not a design trade-off. `os.replace` is a strict superset of `os.rename` behavior and available in Python 3.3+. Skeptical-reviewer's position should prevail here unconditionally. Pragmatist-reviewer's same-directory `.tmp` requirement remains correct and complementary — both should be adopted together.

### Tensions

- **chmod timing: before write vs. after rename**
  - **pragmatist-reviewer's position**: "Write credential files with 0o600 permissions... os.chmod immediately after the rename." This allows the `.tmp` file to be created with default permissions and chmoded post-write, with the rename as the final step. (pragmatist-reviewer/review.md, Recommendation 2)
  - **skeptical-reviewer's position**: "Create `.tmp` via `os.open(..., os.O_WRONLY|os.O_CREAT|os.O_EXCL, 0o600)`, write, then rename." Chmod must precede content write to eliminate the world-readable window between file creation and permission set. (skeptical-reviewer/review.md, Recommendation 2 and Missed Opportunities: "chmod race on the `.tmp` file")
  - **Nature of tension**: Both reviews agree on the goal (0o600 on credential files) but disagree on when in the write sequence permissions are set. Pragmatist's "chmod after rename" approach leaves the `.tmp` file world-readable from creation until chmod fires. On a shared system, co-resident processes that watch for new file creation (inotify watchers, backup agents) could read the `.tmp` before chmod. This is a real window even though it is brief. The tension is between implementation simplicity (chmod after, which is standard `write_text` + `chmod` pattern) and strict security (os.open with mode at creation, which requires lower-level file API).
  - **Coordination needed**: Both can be satisfied with a single implementation choice: use `os.open(path, os.O_WRONLY|os.O_CREAT|os.O_TRUNC, 0o600)` for the `.tmp` file, write content via the resulting fd, then `os.replace`. This satisfies pragmatist's requirement (0o600 is set) and skeptical's requirement (0o600 is set at creation time, not after). The `O_EXCL` flag skeptical recommends should be dropped for the `.tmp` file (since it will be retried on next invocation and `O_EXCL` would fail if a previous `.tmp` was left behind); `O_TRUNC` is correct instead.

- **Migration failure behavior vs. concurrent write safety**
  - **pragmatist-reviewer's position**: Defines explicit failure behavior: "catch, log a single-line warning, fall back to reading from auth.json[provider] directly, clean up `.tmp` with unlink(missing_ok=True)." Treats failure as I/O errors during copy or rename. (pragmatist-reviewer/review.md, Recommendation 3)
  - **skeptical-reviewer's position**: Identifies a silent data-corruption scenario that is not an I/O error: "Process A's `os.replace(tmp, final)` overwrites B's fresh token with the stale pre-migration token." This is not caught by pragmatist's try/except pattern because no exception is raised — it is a logical race, not a system error. (skeptical-reviewer/review.md, Missed Opportunities: "Concurrent save() + migration race")
  - **Nature of tension**: Pragmatist's failure spec handles exceptions correctly but is silent on the non-exceptional corruption case. These are not contradictory — exception handling and concurrency control are orthogonal — but shipping pragmatist's Recommendation 3 without adding skeptical's locking recommendation would produce code that handles I/O errors but silently corrupts tokens under concurrent access. The two recommendations need to be implemented together, not as alternatives.
  - **Coordination needed**: Pragmatist's Recommendation 3 should be treated as the exception-handling spec; skeptical's Recommendation 3 (file lock) is the concurrency spec. Both are required. The lock must be acquired before the migration read and released after the rename — pragmatist's failure cleanup (unlink of `.tmp`) must happen inside the lock's finally block.

- **Observability: log line vs. status command**
  - **pragmatist-reviewer's position**: "A single-line log message — 'Note: credentials for {provider} loaded from legacy auth.json; they will be migrated to credentials/{provider}.json' — emitted once per provider per migration event." Scoped to the logging layer. (pragmatist-reviewer/review.md, Missed Opportunities: "One-time deprecation warning on fallback trigger")
  - **skeptical-reviewer's position**: "`conversus status` should report credential source per-provider." Scoped to the status command UI. (skeptical-reviewer/review.md, Missed Opportunities: "Lazy migration + permanent fallback = invisible orphan providers")
  - **Nature of tension**: These are not contradictory but they target different audiences and different tooling surfaces. A log line during migration is visible only when migration fires (once per provider). A status command report is visible on demand at any time. Under lazy + permanent fallback, a provider that was never accessed has no log line because migration never fired — skeptical's status report is the only surface that would reveal it. Under eager migration (skeptical's Q2 position), all providers migrate at startup so a log line is sufficient. This tension compounds with the Q2 disagreement.
  - **Coordination needed**: The correct scope depends on which Q2 verdict is adopted. Under eager migration, pragmatist's log line suffices. Under lazy migration, skeptical's per-provider status report is needed because the log line may never have fired for some providers. Resolution: agree on Q2 first, then select the observability mechanism that matches the migration trigger.

- **Migration verification post-write**
  - **pragmatist-reviewer's position**: No post-write verification recommended. Atomic rename + permanent fallback is treated as sufficient. (pragmatist-reviewer/review.md, Recommendation 7: "no transaction log. The atomic-rename pattern is sufficient.")
  - **skeptical-reviewer's position**: "After `os.replace()`, immediately `_read_all()` the new per-provider file and compare provider key count/token field to source. If mismatch, log error and fall back to legacy without marking migration complete." (skeptical-reviewer/review.md, Recommendation 9)
  - **Nature of tension**: Pragmatist's position is correct for local POSIX filesystems. Skeptical's verification is defensive against NFS partial writes where the rename is not atomic. The tension is risk appetite: pragmatist considers NFS failure mode "beyond spec scope" implicitly; skeptical considers it worth one read-back. These are not mutually exclusive — verification adds two lines of code and one read call.
  - **Coordination needed**: If permanent fallback is adopted (pragmatist's Q3 position), a failed verification falls back to auth.json gracefully and the risk is low. If time-bounded fallback is adopted, a missed NFS failure breaks the user after cutover. Adopting permanent fallback resolves this tension by making verification optional rather than required.

### Safe Agreements

- **Directory creation with 0o700 mode**
  - **Shared position**: Both reviews independently identify missing directory creation as a P1 gap. Pragmatist: "`os.makedirs(credentials_dir, mode=0o700, exist_ok=True)` before the first write... this is a runtime crash in a common scenario." (pragmatist-reviewer/review.md, Recommendation 1). Skeptical: "`credentials_dir.mkdir(parents=True, exist_ok=True, mode=0o700)`. Prevents enumeration of credential providers by co-resident users." (skeptical-reviewer/review.md, Recommendation 4)
  - **Combined evidence**: Pragmatist identifies the failure mode (FileNotFoundError on clean install), skeptical identifies the information-disclosure vector (world-listable directory on shared hosts). Together they establish that the omission has two independent failure modes — a crash path and a security path — not just one. Neither review arrived at these findings by reading the other; they converged from different analytical approaches.
  - **Confidence level**: High. This is the single strongest finding from the deliberation. It is not mentioned anywhere in QUESTION.md, it is trivial to fix, and both reviews agree on the exact fix. It should appear as P0 in the final synthesis.

- **0o600 permissions on credential files**
  - **Shared position**: Both reviews identify unspecified file permissions as a P1 security gap. Pragmatist: "OAuth tokens stored in `{provider}.json` are sensitive credentials... credential files should be written with 0o600." (pragmatist-reviewer/review.md, Recommendation 2). Skeptical: "credentials exposed in a window that exists on every write" (skeptical-reviewer/review.md, Missed Opportunities: "chmod race on the `.tmp` file").
  - **Combined evidence**: Pragmatist establishes the baseline requirement (0o600 on final files). Skeptical tightens it (0o600 must be set at `.tmp` creation, not post-rename). The two together establish the complete requirement: the file must never appear on disk in any path with permissions wider than 0o600, including during the write sequence. The combination closes a gap that either review alone would leave open.
  - **Confidence level**: High. The implementation detail (os.open vs. chmod-after) remains a tension, but the goal is agreed.

- **Legacy auth.json preservation (Q1: Position B)**
  - **Shared position**: Both reviews endorse preserving auth.json without deletion. Pragmatist: "Preserving auth.json is the right call for a local-only CLI tool. The blast radius of a deletion bug... dwarfs the blast radius of stale-file confusion." (pragmatist-reviewer/review.md, Alignment section). Skeptical: "Adopt Position B. Add a post-migration log line: 'Legacy auth.json preserved...'" (skeptical-reviewer/review.md, Recommendation 6). Both explicitly cite the SC-001 pattern as a precedent.
  - **Combined evidence**: Pragmatist grounds the decision in asymmetric blast radius. Skeptical grounds it in consistency with established SC-001 behavior. Both note that the SC-001 PR set precedent by preserving orphan settings.json. The two rationales are complementary: one is forward-looking risk management, one is backward-looking consistency with existing user trust expectations.
  - **Confidence level**: High. This is the one Q1/Q2/Q3/Q4 decision point where both reviews agree on the same position with independent supporting rationale.

- **Atomic rename as the correct primitive (with caveats)**
  - **Shared position**: Both reviews endorse the `.tmp` → rename pattern as the correct crash-safety primitive. Pragmatist: "Using `.tmp` + `os.rename` is the correct primitive for crash-safe single-file writes." (pragmatist-reviewer/review.md, Alignment section). Skeptical: "the atomic-rename pattern is the right intent" (skeptical-reviewer/review.md, Off-Base Assumptions, which critiques the scope of the safety claim, not the primitive itself).
  - **Combined evidence**: Where the reviews diverge (os.rename vs. os.replace) is on the implementation of the primitive, not the pattern. Both agree that a `.tmp` + atomic rename is superior to direct overwrite, and both agree it handles single-process crash correctly. Skeptical adds the NFS caveat; pragmatist adds the same-directory requirement. Neither review suggests an alternative pattern (e.g., journal-based, copy-on-write). The convergence on the pattern is substantive.
  - **Confidence level**: Medium. The agreement is on the pattern; the implementation detail (os.rename vs. os.replace) is a real contradiction that must be resolved before coding begins.
