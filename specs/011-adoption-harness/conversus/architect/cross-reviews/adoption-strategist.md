# Architect Cross-Review of Adoption Strategist's Review

**Reviewer**: architect
**Cross-reviewing**: adoption-strategist
**Target**: Spec 011 — Conversus Adoption Harness

---

### Dangerous Contradictions

- **Build order inversion: "ship Just Ask first" vs "define engine interfaces first"**
  - **adoption-strategist claims**: "Move 'Just Ask' to step 1. Implement it as a new `/conversus decide` skill command within the existing SKILL.md runtime. ... No Python extraction needed." (Actionable Recommendations, item 1). The entire review is organized around the principle that user-facing validation must precede any infrastructure work, with the proposal to "ship 'Just Ask' mode as a Claude Code skill within the existing runtime in two weeks" (Executive Summary).
  - **architect claims**: "Add a 'Phase 0: Interface Definition' step before engine extraction. Define `DeliberationState`, `AgentState`, `RoundState`, `PluginResult`, and the lifecycle hook enum from spec 007 ... as Python dataclasses/protocols. The engine extraction then targets these interfaces." (Actionable Recommendations, item 1). My review prioritizes getting the foundational data model right before building anything on top of it.
  - **Why this is dangerous**: If both recommendations are adopted simultaneously without coordination, the team ships a Just Ask wrapper inside SKILL.md that produces unstructured output (because the output contract was never defined), while a separate effort defines `DeliberationState` interfaces that Just Ask does not conform to. When the Python engine eventually ships, Just Ask output cannot participate in the plugin ecosystem (no equilibrium scoring, no convergence prediction, no scenario replay) because it was built against no contract. The adoption-strategist's recommendation to "add 'see the debate' to Just Ask output" (Recommendations, item 3) compounds this: if the debate transcript format is ad hoc rather than following the mode-specific template structure, the dispute parsing subsystem (`SKILL.md, L670-697`) cannot operate on it, and plugins that consume `DeliberationState` cannot ingest Just Ask results.
  - **Suggested resolution**: Both positions have merit. The resolution is sequencing, not yielding. Define the Just Ask output contract as a subset of `DeliberationState` (my interface-first concern) before implementing Just Ask in the SKILL.md runtime (the strategist's speed-to-users concern). This is days of work, not months. The output contract ensures Just Ask results can feed into `prior:` context for deeper follow-ups (which my review identifies in Recommendation 8: "Specify-output-contract-for-Just-Ask") and can be consumed by spec 007 plugins when they ship. The adoption-strategist should yield on "no infrastructure before users" to the extent that a 2-day output format definition is infrastructure. I should yield on insisting that the full `DeliberationState` model be finalized before any user-facing work ships.

- **SKILL.md as living distribution format vs frozen legacy**
  - **adoption-strategist claims**: "Ship 'Just Ask' as a Claude Code skill first" (Recommendations, item 1) and the entire review presupposes that the SKILL.md runtime is the primary vehicle for initial adoption. The strategist wants to build new features (the `/conversus decide` command) inside SKILL.md, treating it as an active, evolving distribution channel.
  - **architect claims**: "SKILL.md becomes a thin adapter that invokes the Python engine via subprocess or MCP, OR SKILL.md is frozen as a legacy distribution format that receives no new features. Do not maintain two independent implementations of the same orchestration logic -- they will diverge." (Actionable Recommendations, item 7: "Resolve-SKILL.md-vs-engine-coexistence").
  - **Why this is dangerous**: If the adoption-strategist's plan is implemented, Just Ask mode gets built as new SKILL.md orchestration logic. If my recommendation is also implemented, SKILL.md is then frozen or converted to a thin adapter. This means the Just Ask feature either (a) gets rewritten for the Python engine, doubling the work, or (b) remains SKILL.md-only, creating the exact feature drift I warn about -- Just Ask works in Claude Code but not in the CLI, MCP, or SDK. The adoption-strategist explicitly wants to validate with "100 real decisions" before building infrastructure, but if those 100 decisions all run on SKILL.md-only logic, the validation data applies to a runtime that will be deprecated.
  - **Suggested resolution**: Build Just Ask as a thin orchestration layer that delegates to existing SKILL.md execution (specifically: auto-generate a `conversus.yml` and call `/conversus run`), rather than as new orchestration logic within SKILL.md. The adoption-strategist's own recommendation already hints at this: "auto-generates a `conversus.yml` using the heuristics from spec 003, runs `/conversus run`, and returns a plain-language synthesis" (Recommendations, item 1). If Just Ask is purely a config-generation layer plus output formatting, it is portable to any runtime. The orchestration logic remains in one place. Both positions are satisfied: users get fast validation (strategist), no new orchestration logic gets added to SKILL.md (architect).

- **MCP prioritization disagreement**
  - **adoption-strategist claims**: "MCP is the primary integration path" is premature because "the majority of developers using AI coding tools are not yet on MCP-compatible setups" (Off-Base Assumptions, item 1). The strategist recommends the existing Claude Code skill as the primary channel for the first 100 users, with MCP as the second channel, and further recommends "reorder build sequence: MCP before CLI" (Recommendations, item 4) -- making MCP step 2 after Claude Code validation but still not the primary path.
  - **architect claims**: "v1 ships CLI + MCP server + Python SDK. Web app is a separate proposal." (Actionable Recommendations, item 4: "Defer-web-app-to-v2"). My review treats the Python engine as the canonical implementation and implicitly positions MCP and CLI as co-equal distribution channels built on that engine, with no strong ordering preference between them.
  - **Why this is dangerous**: The strategist's position delays MCP behind Claude Code validation, while my position delays everything behind engine extraction. If both are adopted, the MCP server is blocked twice: first by "validate Just Ask in Claude Code" (strategist's gate), then by "extract the engine to Python first" (my prerequisite). MCP could be delayed indefinitely while both prerequisites chain. Meanwhile, the proposal's open question #5 (`L135`) about MCP maturity goes unanswered with no concrete timeline.
  - **Suggested resolution**: The strategist is right that Claude Code validation should come first (it is the lowest-friction channel). I am right that the MCP server requires a Python engine to exist. The resolution is parallel work: validate Just Ask in Claude Code (weeks 1-4) while defining engine interfaces and beginning extraction (weeks 1-4). MCP server ships as soon as the engine core is functional, gated by engine readiness, not by a specific user-count threshold. The strategist's adoption gates (Recommendations, item 2) should apply to the web app decision, not to MCP.

### Tensions

- **Validation-first vs architecture-first sequencing philosophy**
  - **adoption-strategist's position**: The entire review is organized around the principle that "usage data -- not architectural ambition -- drive the subsequent build order" (Executive Summary). Every recommendation includes adoption gates: "After 50 'Just Ask' runs, review" (Recommendations, item 2). Infrastructure that does not produce users is deprioritized.
  - **architect's position**: My review is organized around the principle that getting foundational abstractions right prevents costly rewrites. "Building the engine without this model means retrofitting it later when plugins need it" (Missed Opportunities, item 1). My recommended minimum viable extraction (Recommendation 9) is architecture-scoped, not user-scoped.
  - **Nature of tension**: These are genuinely different optimization targets. The strategist optimizes for time-to-first-user; I optimize for cost-of-rework. Neither is wrong. The danger is not that they contradict but that they pull resource allocation in opposite directions -- the strategist wants a product person shipping a Claude Code skill next week, I want an engineer defining Python interfaces next week. On a small team, these may be the same person.
  - **Coordination needed**: Explicit resource allocation. If only one engineer is available, the Just Ask wrapper (strategist's priority) and the interface definition (my priority) must be sequenced, and the sequencing decision needs to be made deliberately rather than by default. The Just Ask wrapper is lower effort if scoped as config-generation-plus-formatting (see Dangerous Contradictions, item 2 resolution). The interface definition is lower effort if scoped to `DeliberationState` and `PluginResult` only (not the full plugin system). Both could plausibly be done in the same two-week sprint.

- **Scope of "Just Ask" output: concise answer vs visible debate**
  - **adoption-strategist's position**: "The output should have two layers: (1) a concise recommendation (2-3 sentences), and (2) a full 'debate transcript' showing the agent positions, cross-review attacks, and how the synthesis resolved disagreements" (Recommendations, item 3). The strategist frames this as essential for differentiation: "Without this, conversus is indistinguishable from asking ChatGPT" (Missed Opportunities, item 4).
  - **architect's position**: "'Just Ask' should produce a subset of the standard conversus output: at minimum, a synthesis file following the same mode-specific template structure" (Recommendations, item 8). My concern is that the output must be machine-parseable for follow-up rounds and plugin consumption, not just human-readable.
  - **Nature of tension**: The strategist wants the output optimized for first-impression impact (differentiation, shareability, word-of-mouth). I want the output optimized for system integration (parseable by dispute detection, consumable by plugins, feedable into `prior:` context). These pull the format in different directions: the strategist's "collapsible 'see the debate' section" is a presentation concern that may not map to the structured markdown format that the dispute parsing subsystem requires.
  - **Coordination needed**: Design the Just Ask output as a standard conversus synthesis file (my requirement) with a presentation layer that formats it for human consumption (the strategist's requirement). The structured file is the canonical artifact; the "two-layer" display is a rendering choice made by the distribution channel (Claude Code shows a summary + expandable detail, web app shows tabs, CLI shows full output with a `--brief` flag). This satisfies both concerns without creating two different output formats.

- **Community presets: growth flywheel vs engineering complexity**
  - **adoption-strategist's position**: "Seed 20 community presets before launching the preset system" (Recommendations, item 5). Presets are positioned as a critical adoption mechanism: "Empty marketplaces do not grow" (Recommendations, item 5). The strategist wants presets covering framework selection, database choice, architecture patterns, and more.
  - **architect's position**: My review does not address community presets directly, but my concern about scope is relevant: the proposal already has 8 build phases, and I argue for deferring the web app to reduce scope (Recommendations, item 4). Adding a 20-preset seeding effort increases scope further. Additionally, the existing preset system in SKILL.md (`SKILL.md, L93-169`) already handles preset resolution, composition, and validation -- the preset infrastructure exists, but porting it to the Python engine is additional extraction work.
  - **Nature of tension**: The strategist sees presets as an adoption accelerant that should be built early. I see them as additional scope in an already overloaded proposal. Both are right: presets are high-value for adoption, and each new commitment increases the risk that the core engine extraction gets rushed.
  - **Coordination needed**: Presets are a content problem, not an engineering problem, if the preset system already works in SKILL.md. The 20 seed presets can be written as YAML files for the existing system while the engine extraction proceeds in parallel. They become available in the Python engine automatically when preset resolution is ported. The strategist should own the preset content creation; the architect should own the preset infrastructure porting. These can proceed independently.

- **Web app: "cut it entirely" vs "defer to v2"**
  - **adoption-strategist's position**: "Remove the web app from this proposal entirely" (Recommendations, item 8). The strategist frames this as avoiding the "build the product before finding the market" mistake and recommends revisiting only if demand is validated through other channels.
  - **architect's position**: "Move the web app out of the v1 scope entirely. ... Web app is a separate proposal." (Recommendations, item 4). I frame this as a scope management concern: the web app "adds 5+ new technology layers" that create scope pressure on the engine work.
  - **Nature of tension**: The positions are nearly identical in outcome (no web app in this proposal) but differ in framing. The strategist says "cut it because we haven't validated demand." I say "defer it because it adds too much engineering complexity." These framings lead to different re-entry conditions: the strategist would re-introduce the web app when user demand data supports it; I would re-introduce it when the engine is stable enough to support a real-time streaming UI without shortcuts. If demand appears before the engine is stable, the two positions diverge on whether to build the web app.
  - **Coordination needed**: Agree on re-entry criteria that satisfy both: the web app proposal is drafted when (a) adoption data from CLI/MCP/Claude Code validates demand for a browser-based interface AND (b) the Python engine's async dispatch architecture is stable enough to support WebSocket streaming without architectural compromises. Both gates must pass, not just one.

- **Differentiation strategy: structural vs experiential**
  - **adoption-strategist's position**: "Answer 'Why not just ask ChatGPT?' in the first user interaction" (Recommendations, item 9). The strategist wants visible differentiation at the moment of value delivery: "This recommendation was produced by N agents with [cooperative/adversarial] incentives. [X] arguments were challenged and [Y] survived cross-review."
  - **architect's position**: My review does not address user-facing differentiation directly. My focus is on ensuring the engine correctly implements the multi-agent rules (`SKILL.md, L286-298`) that produce the differentiated outcomes. If the engine works correctly, the outputs are structurally different from single-model responses.
  - **Nature of tension**: The strategist is concerned that correct engine behavior is invisible and therefore valueless for adoption. I am concerned that visible differentiation without correct engine behavior is misleading. Both are valid: a perfectly implemented engine that looks like ChatGPT will not be adopted; a visually differentiated wrapper that runs a shallow single-round deliberation may not actually produce better decisions.
  - **Coordination needed**: The adoption-strategist's "see the debate" feature should expose real engine artifacts (cross-reviews, disputes, concessions) rather than generating a summary of the process. This ensures that differentiation is truthful -- users see actual agent disagreement, not a description of disagreement. The engine must produce these artifacts correctly (my concern); the presentation layer must surface them effectively (the strategist's concern).

### Safe Agreements

- **Defer the web app from v1 scope**
  - **Shared position**: Both reviews independently conclude that the web app should not be built as part of this proposal. The adoption-strategist recommends "Remove the web app from this proposal entirely" (Recommendations, item 8), citing the risk of "months of development on a web app that may attract zero non-technical users." The architect recommends "Move the web app out of the v1 scope entirely. ... Replace with: 'v1 ships CLI + MCP server + Python SDK. Web app is a separate proposal.'" (Recommendations, item 4), citing that the web app "adds 5+ new technology layers" that create scope pressure on the engine.
  - **Combined evidence**: The strategist provides the demand-side argument (no validated user need for a browser interface), while the architect provides the supply-side argument (engineering complexity diverts resources from the core engine). Together, these make a comprehensive case: the web app is both unvalidated in demand and disproportionately expensive to build. The proposal's own build order places it at step 7 of 8 (`L127`), suggesting even the original author considered it low priority.
  - **Confidence level**: High. This is the strongest point of agreement and should be treated as a settled recommendation in the synthesis.

- **The proposal underestimates engine extraction complexity**
  - **Shared position**: Both reviews identify that "Python engine extraction (SKILL.md logic to Python package)" as a single build phase (`L120`) dramatically underestimates the scope. The adoption-strategist frames this as an off-base assumption: "The proposal assumes the engine must be extracted to Python before any adoption work can happen. This is an engineering-first assumption that delays all user-facing work" (Off-Base Assumptions, item 2). The architect frames it as a decomposition problem: "SKILL.md is not a script to be transliterated; it is an agent orchestration specification that relies on the host runtime" and identifies 6 distinct subsystems that each require module-scale work (Off-Base Assumptions, item 2).
  - **Combined evidence**: The strategist demonstrates that extraction is not a prerequisite for initial adoption (Just Ask can run in the existing runtime). The architect demonstrates that extraction, when it does happen, is 5-6 modules of work, not one phase. These perspectives reinforce each other: the extraction is both not-urgent (strategist) and larger-than-estimated (architect). This means the proposal's build order is wrong in two ways -- it starts with extraction when it should start with validation, and it treats extraction as one step when it is five.
  - **Confidence level**: High. The evidence from both perspectives is concrete and specific. The synthesis should recommend both deferring extraction behind initial validation and decomposing it into sub-phases when it does begin.

- **Parallel dispatch outside Claude Code is a hard engineering problem**
  - **Shared position**: Both reviews flag the proposal's characterization of parallel agent dispatch as "already built" (`L111`) as misleading. The adoption-strategist identifies that MCP as the "primary integration path" is premature given current adoption levels (Off-Base Assumptions, item 1). The architect directly challenges the "already built" framing: "Parallel dispatch is built for Claude Code's Agent tool. ... In a standalone Python runtime, 'parallel dispatch' means implementing an async task manager" with five specific requirements listed (Off-Base Assumptions, item 1). The architect further recommends a dedicated architecture section for the async dispatch engine (Recommendations, item 3).
  - **Combined evidence**: The strategist's evidence shows that even the distribution channel (MCP) through which the new dispatch would be used is not yet mature. The architect's evidence shows that the dispatch engine itself requires substantial new infrastructure: concurrent API calls, context isolation, output collection, partial failure handling, and phase barriers. Together, these mean the proposal simultaneously overestimates the readiness of the execution infrastructure and the distribution infrastructure. The gap between "works in Claude Code" and "works anywhere" is larger than the proposal acknowledges from both the engineering and adoption perspectives.
  - **Confidence level**: High. This agreement strengthens the case for the architect's minimum viable extraction recommendation (single provider, cooperative mode only) and the strategist's recommendation to validate in the existing Claude Code runtime first.

- **The three-tier user model is the right framework**
  - **Shared position**: Both reviews endorse the Just Ask / Guided / Power tiering as the correct approach to user segmentation. The adoption-strategist states it "correctly recognizes that different users need different entry points" and maps it to the spec 003 guided workflow (Alignment, item 1). The architect states it "correctly maps to three distinct user populations with different config effort tolerances" and connects it to the existing SKILL.md separation of config parsing from orchestration (Alignment, item 1).
  - **Combined evidence**: The strategist validates the model from the user perspective (different users have different needs), while the architect validates it from the architecture perspective (the existing codebase already separates concerns in a way that supports wrapping different front-ends). The tier model is sound from both angles, which means it can serve as a stable organizing principle for the rest of the proposal even as build order and scope are adjusted.
  - **Confidence level**: Medium. The agreement is genuine but the tiering is relatively uncontroversial -- it is hard to argue against offering different complexity levels. The value of this agreement is less about its strength and more about its stability as a design anchor.
