# Architect — Final Disputes and Convergence

---

### Remaining Disputes

- **Dispute: Engine extraction timing relative to Just Ask prototype**
  - **My claim**: Phase 0 interface definition (both internal engine interfaces and external SDK types) must precede any shipping, including the Just Ask prototype. The interfaces are approach-agnostic and cost 1 week. (Architect revision, Recommendation 1, modified position; Recommendation 9, MV1/MV2 milestone definition.)
  - **Opposing position(s)**: The adoption-strategist's revised position (Recommendation 1) argues that the Just Ask Claude Code skill should ship first with only a lightweight output contract (2-3 days of work), and that Phase 0 interface definition is premature before usage data exists. The devil's advocate's revised position (Recommendation 5) allows a "time-boxed prototype" before extraction begins, with extraction starting "once the prototype validates the concept or after a defined time limit."
  - **Why I will not concede**: The adoption-strategist's "output contract" (recommendation, confidence metadata, debate transcript fields) is a subset of the Phase 0 interface work I propose. If the output contract is worth defining (and the adoption-strategist now agrees it is), then defining the full `DeliberationState` and `Result` types costs only marginally more and prevents the exact divergence the devex-advocate warned about in their cross-review. The difference between "2-3 days of output contract" and "1 week of Phase 0" is 2-4 days. The cost of getting the interfaces wrong and retrofitting is months. Spec 007's plugin system (sections 3 and 6) requires `DeliberationState` with mode, round, agents, synthesis, and history fields. If the Just Ask prototype's output contract does not align with this shape, the prototype's output is incompatible with the plugin ecosystem from day one. The adoption-strategist is optimizing for days; I am optimizing against months of rework.
  - **Counter-argument to their position**: The adoption-strategist frames the choice as "ship in days vs. design for weeks." This is a false dichotomy. Phase 0 is not a design-in-a-vacuum exercise -- it codifies the interfaces that already exist implicitly in SKILL.md's orchestration (the phase loop, agent context isolation, output directory structure) and spec 007's plugin API (`DeliberationState`, `AgentState`, `PluginResult`). The types are already designed; Phase 0 writes them down as Python protocols. The adoption-strategist's output contract will discover these same constraints piecemeal as the prototype evolves. The devil's advocate's "time-boxed prototype with sunset" is better than the adoption-strategist's framing but still risks the prototype accreting logic that diverges from the eventual engine, because without the full interface definition, there is no target to converge toward.
  - **Proposed resolution path**: Compromise on sequencing: Phase 0 interface definition (1 week, time-boxed) runs in parallel with the adoption-strategist's Just Ask config-generation design work. The output contract the adoption-strategist wants is a deliverable of Phase 0, not a separate artifact. The Just Ask prototype ships immediately after Phase 0, inheriting the interface definitions rather than inventing its own. Total delay to first user: 1 week. Total risk reduction: the prototype's output is ecosystem-compatible from launch.

- **Dispute: Single-agent failure semantics as a design decision vs. an open question**
  - **My claim**: The single-agent failure question -- does a failed agent abort the phase or does the phase continue with N-1 agents? -- must be resolved as a design decision in the spec, not left as an implementation choice. (Architect revision, Recommendation 3, modified position, layer (b): "The single-agent failure question... must be resolved as a design decision, not left as an open question.")
  - **Opposing position(s)**: The devil's advocate's revised position (Recommendation 6) proposes designing the failure isolation contract for the single-provider case and documenting multi-provider failure modes as "known future requirements," but frames the single-agent failure semantics as a "key design question to resolve" without committing to a specific answer. The devex-advocate's revised position (Recommendation 8) places failure handling in the `AgentRuntime` layer that "checks whether the model's output meets structural requirements after generation" -- this addresses output validation but does not address mid-execution agent crashes during parallel dispatch. Neither revision commits to continue-with-N-1 or abort-phase as the answer.
  - **Why I will not concede**: SKILL.md's current orchestration (Step 4, "NON-NEGOTIABLE MULTI-AGENT RULES," rule 5) enforces hard phase barriers: "Wait for ALL agents in the current phase to complete before launching ANY agent in the next phase." In Claude Code's Agent tool runtime, a failed agent returns an error result but does not crash the orchestrator -- the phase completes with N-1 successful outputs. The extracted Python engine must replicate this behavior explicitly. If the spec does not commit to a failure semantics, different implementations (CLI, MCP server, SDK) will make different choices, producing inconsistent behavior across distribution channels. The dispatch engine is the single piece of shared infrastructure; its failure contract must be specified once.
  - **Counter-argument to their position**: The devil's advocate and devex-advocate both treat this as a question that can be deferred to implementation. But implementation-time decisions on failure semantics produce the worst kind of inconsistency -- the kind that surfaces only in production when an agent actually fails. The devex-advocate's `AgentRuntime` handles post-generation validation (was the output structurally valid?) but does not address the dispatch-level question (the API call timed out, the model returned a 500, the connection dropped). These are different failure modes requiring different handling. Leaving the dispatch-level failure semantics unspecified means the CLI might retry, the MCP server might abort, and the SDK might silently continue -- all defensible individually, all producing inconsistent user experience.
  - **Proposed resolution path**: The spec should commit to continue-with-N-1 as the default, with a configurable `on_agent_failure: continue | abort` option in `conversus.yml`. This matches SKILL.md's current implicit behavior (Claude Code's Agent tool continues if one subagent fails), provides a safety valve for users who want strict mode (abort on any failure), and gives the dispatch engine a single, testable contract. The synthesizer should include this as a specified behavior, not an open question.

- **Dispute: Model tiering as architectural requirement vs. optimization**
  - **My claim**: Per-phase model configuration (`models: { default: ..., synthesis: ..., cross-review: ... }`) is an architectural decision that must be designed into the engine's provider abstraction from Phase 0, not a performance optimization added later. Each per-phase model assignment must pass a capability validation gate for that specific phase's requirements. (Architect revision, Recommendation 10, modified position.)
  - **Opposing position(s)**: The devex-advocate's revised position (Recommendation 8) places capability validation in the `AgentRuntime` layer as post-generation structural checking, not as a pre-dispatch gate. The adoption-strategist's revised position does not address model tiering directly, implicitly treating it as a later concern. The consumer-advocate's revised position (Recommendation 5) addresses confidence scoring but not model tiering.
  - **Why I will not concede**: The proposal lists "model tiering: cheap model for cross-reviews, expensive for synthesis" under Performance Optimizations (proposal section "Performance Optimizations," item 5). This classification is wrong. Model tiering determines the quality ceiling of each phase's output. A cheap model assigned to cross-reviews may not produce structurally valid cross-review output -- it may miss required template sections, fail to identify contradictions, or produce surface-level agreement. This is not a performance concern; it is a correctness concern. If the engine ships with single-model-only and model tiering is added later, the `ModelProvider` interface must change to accept per-phase model routing, which is a breaking API change for every distribution channel. The devex-advocate's post-generation validation catches bad output but does not prevent the wasted API call or the latency of generating output that will be rejected.
  - **Counter-argument to their position**: The devex-advocate's approach -- validate output after generation -- is correct as a safety net but insufficient as a design strategy. Post-generation validation means the system generates output, inspects it, finds it structurally invalid, and then... what? Retries with the same cheap model? Falls back to a more capable model? Fails the phase? These are design decisions that cascade from the model tiering architecture. If model tiering is not part of the Phase 0 interface definition, the `ModelProvider` interface will be designed for single-model dispatch and will need to be refactored when tiering is added. The adoption-strategist's implicit deferral is understandable given their focus on speed-to-users, but the MV2 engine extraction (my revised Recommendation 9) will need model tiering immediately to validate cost-performance trade-offs.
  - **Proposed resolution path**: Include per-phase model configuration in the `ModelProvider` interface definition during Phase 0. The initial implementation uses a single model for all phases (the `default` key), making model tiering opt-in without adding implementation complexity. But the interface supports it from day one, preventing the breaking change. The synthesizer should classify model tiering as an architectural concern in the provider interface section, not a performance optimization to be added later.

### Convergence

- **Converged: Engine extraction requires sub-phase decomposition**
  - **Shared position**: The proposal's treatment of engine extraction (step 1) as a single build phase is a planning failure. It must be decomposed into independently testable sub-phases: config parser, template engine, async dispatch, dispute parsing, and output manager. Each sub-phase has distinct input/output contracts and can be tested in isolation.
  - **Agreeing agents**: Architect (revision, Recommendation 2), consumer-advocate (revision, note in Recommendation 1 modifications), devex-advocate (revision, Recommendation 1 discussion), adoption-strategist (revision, Recommendation 1 cross-review acknowledgment), devil's advocate (revision, Recommendation 5 discussion).
  - **Strength**: Unanimous
  - **Path to convergence**: Agreed from Phase 1. Every cross-review independently confirmed this position. No agent challenged the decomposition itself. This is the strongest consensus finding in the entire deliberation.

- **Converged: Just Ask output quality gate before shipping**
  - **Shared position**: Before shipping Just Ask in any form (Claude Code skill, CLI, MCP), define minimum quality criteria that distinguish conversus output from a single-model response. At minimum: (1) the synthesis must surface at least one substantive disagreement between agents, and (2) agent attributions must be present showing which perspective generated which argument. These criteria are testable in a single session against sample questions.
  - **Agreeing agents**: Devil's advocate (revision, Recommendation 1 and new recommendation "Gate Just Ask prototype on minimum quality bar"), consumer-advocate (revision, new recommendation "Adopt deliberation quality criteria for Just Ask mode"), devex-advocate (revision, new recommendation "Define Just Ask quality model before output schema"), adoption-strategist (revision, new recommendation "Define-Just-Ask-quality-floor"), architect (revision, Recommendation 8, quality gate as priority 1 constraint on output).
  - **Strength**: Unanimous
  - **Path to convergence**: This emerged through the cross-review process. In Phase 1, only the devil's advocate raised this concern. By Phase 3 revision, every agent independently adopted it as a P1 requirement. The devil's advocate's original challenge -- that a 2-agent, 1-round deliberation without cross-reviews is structurally identical to asking two models the same question and having a third summarize -- was the catalyst that shifted every other agent's position.

- **Converged: Web app removed from v1 scope, gated behind adoption metrics**
  - **Shared position**: The full-featured web app (Next.js, PostgreSQL, auth, WebSocket streaming, decision history) is removed from this proposal's scope. It is either deferred to a separate spec (012) or gated behind a quantitative adoption metric from developer channels. The engine must be designed with web-compatible constraints (streaming events, structured output, no filesystem-only assumptions) to prevent painting the architecture into a CLI-only corner.
  - **Agreeing agents**: Architect (revision, Recommendation 4), devil's advocate (revision, Recommendation 7), adoption-strategist (revision, Recommendation 8), devex-advocate (revision, new recommendation "Gate web app behind adoption metric"), consumer-advocate (revision, Recommendation 1 -- modified to accept minimal web artifact instead of full web app at step 4-5).
  - **Strength**: Unanimous
  - **Path to convergence**: In Phase 1, positions ranged from "elevate to step 4-5" (consumer-advocate) to "cut entirely" (adoption-strategist) to "defer to v2" (architect) to "separate spec" (devil's advocate). The consumer-advocate's self-fulfilling-prophecy argument -- that validating only through developer channels produces developer-representative data -- shifted the adoption-strategist from "cut entirely" to "minimal web form for consumer validation." The architect accepted that the engine must emit phase-lifecycle events for future streaming consumers. By Phase 3, all agents converged on: full web app out of v1 scope, but engine designed with web consumption as a forward-compatibility constraint.

- **Converged: MCP server ships before CLI in the build order**
  - **Shared position**: The proposal's build order (CLI at step 3, MCP at step 5) should be reversed. MCP reaches developers at the point of decision-making inside their editors. CLI is a convenience wrapper that can ship after MCP. The MCP server should ship after the SDK API is designed and quality criteria are defined, but before the web app.
  - **Agreeing agents**: Adoption-strategist (revision, Recommendation 4), devex-advocate (revision, Recommendation 3), devil's advocate (revision, Recommendation 10 cross-review acknowledgment), architect (revision, Recommendation 9 -- MV2 engine extraction implicitly supports MCP as a primary consumer).
  - **Strength**: Majority (no agent argued CLI should precede MCP; the consumer-advocate did not contest)
  - **Path to convergence**: Agreed from Phase 1 between adoption-strategist and devex-advocate. No agent produced a counter-argument for CLI-before-MCP. The only tension was about prerequisites (architect: SDK must be stable first; devil's advocate: quality criteria must be defined first), not about the relative ordering of MCP and CLI.

- **Converged: Python extraction is the target architecture**
  - **Shared position**: The engine extraction should target Python as the canonical runtime. Spec 007's plugin system (lifecycle hooks, `DeliberationState`, feature extraction) requires a Python runtime. The adapter approach is a dead end for features that depend on plugins. SKILL.md remains the initial execution runtime for user validation, but new orchestration logic is not added to it. The commitment to Python is directional; timing is informed by prototype validation.
  - **Agreeing agents**: Architect (revision, Recommendation 7), devil's advocate (revision, Recommendation 5 -- "Explicitly commit to Python extraction as the target architecture"), devex-advocate (revision, Recommendation 1 -- "Resolve the engine extraction question first -- commit to Python extraction"), adoption-strategist (revision, Recommendation 1 -- accepts config-generation-only constraint that keeps SKILL.md as execution runtime without adding new orchestration logic).
  - **Strength**: Majority (the consumer-advocate's revision does not address extraction architecture directly)
  - **Path to convergence**: The architect and devex-advocate advocated for Python extraction from Phase 1. The devil's advocate initially treated it as an unresolved blocking question. The adoption-strategist initially resisted by prioritizing SKILL.md-first shipping. The architect's cross-review argument -- that spec 007's plugin API (`DeliberationState`, lifecycle hooks, `PluginResult`) is defined in Python and the adapter approach cannot support it -- convinced the devil's advocate to commit directionally. The adoption-strategist's concession to "config-generation-only" (no new orchestration logic in SKILL.md) resolved the coexistence tension without blocking speed-to-users.

### Final Position Statement

**Non-Negotiables** (3 items):

1. **Engine extraction must be decomposed into independently testable sub-phases.** Treating engine extraction as a single build phase makes it unestimable, untestable, and unparallelizable. The 5-sub-phase decomposition (config parser, template engine, async dispatch, dispute parsing, output manager) maps directly to distinct SKILL.md subsystems with clear input/output contracts. This is the only recommendation that received zero challenges across all cross-reviews from all agents. (Architect revision, Recommendation 2; SKILL.md Steps 1, 3, 4, and 5 demonstrate the distinct subsystems.)

2. **The async dispatch engine must specify failure semantics, not defer them.** The dispatch engine is the single shared infrastructure layer that CLI, MCP, SDK, and future web app all depend on. Its contract must specify: parallel execution via `asyncio.TaskGroup`, hard phase barriers matching SKILL.md's current rule 5, per-agent error isolation with configurable continue-with-N-1 or abort-phase behavior, and phase-lifecycle event emission for streaming consumers. Without a specified failure contract, each distribution channel will implement its own failure handling, producing inconsistent behavior across surfaces. (Architect revision, Recommendation 3; SKILL.md Step 4 "NON-NEGOTIABLE MULTI-AGENT RULES" rules 2 and 5; spec 007 section 3 lifecycle hooks.)

3. **Phase 0 must define both internal engine interfaces and external SDK types together.** Designing internal interfaces (`DeliberationState`, `AgentState`, lifecycle hooks) without the external SDK types (`Problem`, `Config`, `Result`), or vice versa, produces impedance mismatch that requires costly refactoring. The two interface layers and the mapping between them must be designed in a single time-boxed phase before implementation begins. The Just Ask output contract is a deliverable of this phase, not a separate artifact. (Architect revision, Recommendation 1; devex-advocate revision, Recommendation 1; spec 007 section 3 Plugin API defines `DeliberationState` fields.)

**Flexibility** (3 items):

1. **Phase 0 may run in parallel with Just Ask design work rather than strictly preceding it.** I am flexible on whether Phase 0 is a hard prerequisite or a parallel workstream, as long as the Just Ask prototype does not ship before the output contract (a Phase 0 deliverable) is defined. The core intent to preserve: no prototype ships with an output format that is incompatible with the broader conversus ecosystem.

2. **The specific model tiering interface shape is negotiable; the principle that it belongs in the provider interface from day one is not.** I proposed `models: { default: ..., synthesis: ..., cross-review: ... }` in the config and a corresponding dispatch routing in `ModelProvider`. The exact schema can differ. What must be preserved: the `ModelProvider` interface is designed from the start to accept per-phase model routing, even if the initial implementation uses a single model for all phases. This prevents a breaking API change when tiering is enabled.

3. **The consumer-facing path in v1 may be a minimal web form, a Slack bot, or another lightweight surface.** I originally proposed deferring all consumer surfaces. The consumer-advocate's product-identity argument and the adoption-strategist's self-fulfilling-prophecy argument convinced me that some consumer validation channel is necessary. I am flexible on which channel (minimal web form, hosted share page, Slack integration, or similar). What must be preserved: the engine's dispatch events and structured output are designed to support non-CLI consumers, regardless of which specific consumer surface ships first.
