### Dangerous Contradictions

- **MCP maturity assessment and build order priority**
  - **devils-advocate claims**: MCP is listed as "primary integration path" but open question 5 (L135) acknowledges MCP may not be mature enough. The proposal provides "no fallback integration strategy" if MCP adoption stalls. devils-advocate labels this impact as medium and does not challenge the current build order placement at step 5. (Missed Opportunities, "MCP as 'primary integration path' without fallback")
  - **devex-advocate claims**: MCP maturity concern is overstated — MCP is already supported by Claude Code, Cursor, Windsurf, Zed, and VS Code. The real risk is not protocol maturity but conversus's MCP server design quality. The MCP server should be moved from build step 5 to build step 3, shipping alongside or immediately after the CLI. (Off-Base Assumptions, "MCP maturity concern is overstated"; Actionable Recommendations #3, "Move MCP server to build step 3")
  - **Why this is dangerous**: If both positions influence the final spec, they pull in opposite directions on the same component. devils-advocate's framing — that MCP might not be ready and needs a fallback — would justify keeping MCP at step 5 or later, while also adding work to design fallback native plugins. My position demands MCP move to step 3 precisely because the protocol is mature enough. If the spec adopts both the fallback requirement and the earlier build step, the team spends engineering effort on fallback strategies for a protocol that does not need them, delaying the MCP server anyway. If the spec adopts only the fallback requirement, the highest-value developer integration ships last. The failure mode is either wasted effort or missed adoption window.
  - **Suggested resolution**: devils-advocate should yield on maturity — the evidence supports MCP readiness. However, their underlying concern about fallback is worth preserving in a narrower form: the MCP tool contract should be designed so that the same tool signatures can be exposed via a REST API if needed, which is cheap insurance without requiring a separate fallback engineering track. Move MCP to step 3, design tool contracts that are transport-agnostic, skip the native plugin fallback.

- **"Just ask" mode: gutting value vs. shipping value**
  - **devils-advocate claims**: A 2-agent, 1-round deliberation "is structurally identical to asking two models the same question and having a third summarize — which is not what makes conversus valuable." The cross-review/revision cycle is the core mechanism, and skipping it removes the value proposition. They recommend designing a "mini-cross-review" or explicitly documenting what replaces adversarial pressure if cross-reviews are skipped. (Off-Base Assumptions, "2-3 agents, 1 round implies adequate deliberation"; Actionable Recommendations #3, "Design the cross-review bypass for lightweight mode")
  - **devex-advocate claims**: "Just ask" mode needs structured output (JSON with recommendation, confidence, arguments_for, arguments_against, dissent), a non-interactive execution path for CI/CD, and a dry-run/validate step. The review accepts the lightweight configuration as a reasonable starting point and focuses on making its output programmatically useful. (Actionable Recommendations #2, "Add structured output mode"; #4, "Design CI/CD non-interactive mode"; #6, "Add dry-run/validate command")
  - **Why this is dangerous**: I implicitly accepted that "just ask" with 2-3 agents and 1 round is a valid mode and focused on improving its output format and programmatic ergonomics. devils-advocate argues that this mode may not produce meaningfully better results than a single LLM call — in which case, making its output beautifully structured is polishing something that has no value. If both positions are adopted without resolution, the spec would ship a well-typed, CI-friendly "just ask" mode that developers integrate into pipelines, only to discover it produces results indistinguishable from single-model prompting. The failure mode is developer trust destruction: engineers who wire conversus into CI based on my recommendations will churn when they realize the output has no adversarial depth, validating devils-advocate's concern.
  - **Suggested resolution**: devils-advocate is correct that the quality question must be answered before the output format question. I should yield on sequencing: define minimum quality criteria for "just ask" mode first (devils-advocate's recommendation #1), then design the structured output format around those criteria. The structured output should include a `quality_indicators` field that exposes whether genuine disagreement occurred — making quality measurable is where both positions converge. The mini-cross-review proposal deserves serious consideration as a middle ground between "full 5-phase" and "no adversarial pressure."

- **Engine extraction: commit vs. defer**
  - **devils-advocate claims**: Open question 1 (engine extraction approach) is "not an open question — it is a blocking architectural decision" that must be resolved before any implementation begins. The team should "either commit to Python extraction with a concrete migration plan... or commit to the adapter approach with a concrete interface definition." (Actionable Recommendations #5, "Resolve the engine extraction question before proceeding")
  - **devex-advocate claims**: The SDK public API must be designed first because "CLI is click wrapping SDK methods. MCP server is MCP handlers wrapping SDK methods. Web app is FastAPI wrapping SDK methods." The review prescribes the SDK as the foundational layer and specifies concrete classes, methods, and patterns — implicitly assuming Python extraction has already been decided. (Actionable Recommendations #1, "Define SDK public API")
  - **Why this is dangerous**: My recommendation presupposes the answer to the question devils-advocate says must be explicitly resolved first. If the spec adopts my SDK API design but the team later decides on the SKILL.md-with-adapters approach (keeping orchestration in the agent runtime rather than extracting to Python), the SDK design is wrong — it assumes a Python engine that does not exist. If the spec adopts devils-advocate's "resolve first" stance but not my "design the API first" stance, the team may commit to Python extraction without having designed the API, producing the leaky abstraction I warn about. The failure mode is either building an SDK for a nonexistent engine or building an engine without an SDK contract.
  - **Suggested resolution**: Both positions are correct but need sequencing. The resolution is: (1) commit to Python extraction (devils-advocate's point — this is a blocking decision, not an open question), (2) design the SDK public API before implementing the engine (my point — the API is the contract the engine must satisfy). These are not contradictory; they are two steps that both reviews demand but neither review sequences correctly relative to the other. The spec should present this as: "Decision: Python extraction. First deliverable: SDK interface definition (types, methods, async contract). Second deliverable: engine implementation satisfying that interface."

- No additional contradictions identified.

### Tensions

- **Cost controls: who pays vs. how much**
  - **devils-advocate's position**: A retiree who asks "what stocks should I buy?" and gets a $15 API bill will not become a repeat user. Cost estimation, budget caps, and per-tier cost ranges are P1 requirements. The concern is framed around protecting non-technical consumers from surprise bills. (Missed Opportunities, "No cost estimation or budget controls"; Actionable Recommendations #4)
  - **devex-advocate's position**: A dry-run/validate command should "estimate agent launches and token cost" without executing. The concern is framed around developer workflow efficiency — fail fast in CI, not waste money on misconfigured deliberations. (Actionable Recommendations #6, "Add dry-run/validate command")
  - **Nature of tension**: Both reviews want cost visibility, but for different users and at different points in the workflow. devils-advocate wants runtime budget caps and pre-execution cost consent for consumers. I want pre-execution validation for developers and CI pipelines. These are not the same feature: a budget cap is a runtime enforcement mechanism; a dry-run estimate is a pre-execution check. The consumer version needs a confirmation dialog ("This will cost approximately $3. Proceed?"); the developer version needs a machine-readable estimate that a CI script can evaluate against a threshold.
  - **Coordination needed**: The spec should define cost estimation as a core engine capability (shared infrastructure), then expose it differently per surface: the web app shows a consent dialog (devils-advocate's consumer concern), the CLI/SDK returns a structured estimate (my developer concern), and the MCP tool includes cost_estimate in its response metadata. One engine capability, three presentation layers.

- **Web app: separate spec vs. deprioritize**
  - **devils-advocate's position**: The web app should be "removed from this spec's build order" and created as a separate spec (012 or later) because it introduces authentication, hosting, state management, real-time streaming, and database design. "The web app scope creep delays delivery of the CLI, SDK, and MCP server." (Actionable Recommendations #7, "Separate the web app into its own spec")
  - **devex-advocate's position**: The build order correctly sequences CLI before web app. The review does not recommend removing the web app from the spec but implicitly deprioritizes it by focusing all 10 recommendations on CLI, SDK, and MCP concerns. No recommendation addresses the web app at all.
  - **Nature of tension**: devils-advocate wants the web app formally excluded from this spec's scope. I want it deprioritized but present — having it in the build order at step 7 communicates intent and ensures the engine is designed with web app requirements in mind (e.g., WebSocket streaming, session management). Removing it entirely risks designing an engine that is CLI-first in ways that make the web app harder to build later (e.g., assuming filesystem-based artifact storage that does not translate to a database-backed web context).
  - **Coordination needed**: Keep the web app in this spec as a vision item with explicit scope boundaries: "The web app is in scope for architectural consideration (the engine must not assume filesystem-only storage) but out of scope for detailed design. Detailed web app design is deferred to a follow-on spec." This satisfies devils-advocate's concern about scope creep while preserving forward compatibility.

- **Model agnosticism: capability matrix vs. provider interface**
  - **devils-advocate's position**: The spec needs a "capability matrix or minimum model requirements per mode/tier" and runtime validation that warns or blocks when the selected model cannot support the requested deliberation depth. Focus is on model quality and output fidelity. (Missed Opportunities, "No degradation model across providers"; Actionable Recommendations #2, "Add model capability requirements per mode")
  - **devex-advocate's position**: Commit to a thin provider interface (`class ModelProvider: async def complete(...)`) with LiteLLM as the default implementation. Focus is on extensibility and avoiding vendor lock-in at the abstraction layer. (Actionable Recommendations #8, "Resolve LiteLLM vs custom provider decisively")
  - **Nature of tension**: Both reviews address model agnosticism but from different angles. devils-advocate cares about preventing bad output when weak models are used. I care about preventing architectural lock-in to a specific abstraction library. These pull in different directions: a capability matrix implies the engine must know about specific models and their capabilities (coupling), while a thin provider interface implies the engine should be model-ignorant (decoupling). A runtime validator that blocks certain models from certain modes requires model-specific knowledge that a thin interface deliberately avoids.
  - **Coordination needed**: Layer the solution. The thin provider interface handles routing and extensibility (my concern). A separate capability assessment layer sits above it and evaluates whether a given model's outputs meet structural requirements — not by knowing model names, but by validating output structure after generation (e.g., "did the agent produce all required review sections?"). This turns devils-advocate's capability matrix from a static lookup table into a dynamic quality gate, which is more robust and does not require maintaining a catalog of model capabilities.

- **Failure modes: multi-provider vs. single-provider**
  - **devils-advocate's position**: Moving from a single provider to arbitrary providers "multiplies the failure surface by the number of providers times the number of agents." The spec needs failure mode analysis covering agent failure in parallel batches, rate limiting, output validation, and mid-deliberation outages. (Missed Opportunities, "No failure mode analysis"; Actionable Recommendations #6, "Add failure mode analysis for multi-provider execution")
  - **devex-advocate's position**: The MCP tools need machine-readable error contracts — invalid input, model failure, rate limit, missing dependencies. Errors should be structured, not conversational. (Missed Opportunities, "No error contract for MCP tools"; Actionable Recommendations #5, "Specify MCP tool input/output schemas")
  - **Nature of tension**: devils-advocate addresses failure at the engine level (what does the orchestrator do when an agent call fails mid-deliberation?). I address failure at the interface level (what does the MCP/SDK client receive when something goes wrong?). These are complementary but require coordination: the engine's failure handling strategy determines what errors the interface can surface. If the engine silently retries a failed agent, the interface cannot report a partial failure. If the engine aborts the full deliberation on any single agent failure, the interface must communicate total failure even when 4 of 5 agents succeeded.
  - **Coordination needed**: Design the failure taxonomy at the engine level first (devils-advocate's scope), then map each engine failure mode to a structured error type at the interface level (my scope). The engine should expose failure events, not just final status, so that streaming MCP/SDK clients can report partial progress before failure.

- **Auto-generated agents: algorithm vs. API**
  - **devils-advocate's position**: The spec must "define the agent generation algorithm" — classification model, prompt-based generation, or rule-based heuristics — because poorly generated agents with nearly identical perspectives produce no adversarial pressure. (Actionable Recommendations #8, "Define what 'auto-generates 2-4 appropriate agents' means concretely")
  - **devex-advocate's position**: The preset system should be exposed programmatically: `conversus.presets.list()`, `conversus.presets.compose(["mechanist", "security"])`. The focus is on giving developers control over agent composition, not on defining the auto-generation algorithm. (Actionable Recommendations #7, "Expose preset system programmatically")
  - **Nature of tension**: devils-advocate wants the "just ask" auto-generation to be well-defined so it produces quality output without user intervention. I want the preset system to be programmable so developers can compose agents explicitly. These serve different tiers — auto-generation is for "just ask" consumers, programmatic presets are for power users and SDK consumers. The tension is in resource allocation: specifying the auto-generation algorithm is design work that benefits the consumer tier; exposing presets programmatically is engineering work that benefits the developer tier. Both are important, but they compete for priority in a constrained build order.
  - **Coordination needed**: The auto-generation algorithm should use the preset system internally — mapping question classification to preset composition. This means the programmatic preset API (my concern) is infrastructure that the auto-generation algorithm (devils-advocate's concern) depends on. Build the preset API first (step 2, as part of the SDK), then build auto-generation on top of it (step 4, as part of "just ask" mode). This sequencing satisfies both reviews.

### Safe Agreements

- **Structured output is non-negotiable**
  - **Shared position**: Both reviews identify the absence of structured output as a significant gap. devils-advocate frames it as the missing "quality metric" — without structured criteria, there is no way to measure whether a deliberation produced value (Missed Opportunities, "No quality metric for 'just ask' mode"; Actionable Recommendations #1). I frame it as the missing "developer contract" — without structured output (JSON with typed fields), developers cannot compose conversus programmatically (Missed Opportunities, "No structured output format"; Actionable Recommendations #2).
  - **Combined evidence**: devils-advocate provides the quality argument: structured output with explicit disagreement, evidence grounding, and trade-off acknowledgment is what distinguishes conversus from a single-model call. I provide the integration argument: structured output with typed fields (recommendation, confidence, arguments, dissent) is what makes conversus usable in CI/CD, agent pipelines, and MCP tool chains. Together, these establish that structured output serves both quality assurance and developer adoption — it is the intersection point where "is the output good?" and "can the output be consumed programmatically?" are answered by the same design.
  - **Confidence level**: High. This is the single strongest convergence point between the two reviews. Both reviews flag it as high-impact, both provide distinct supporting evidence, and the combined position is strictly stronger than either alone. The spec should add structured output as a P1 requirement.

- **MCP tool contracts must be specified before implementation**
  - **Shared position**: Both reviews identify the six MCP tool names as underspecified. devils-advocate notes that the tools have "one-line descriptions" and need "input schema, output schema, error contract, and execution model" for each (Actionable Recommendations #10, "Define the MCP tool contract more precisely"). I make the same demand with specific examples: input schemas with typed parameters, output schemas with structured JSON, error types, and progress/streaming behavior (Actionable Recommendations #5, "Specify MCP tool input/output schemas").
  - **Combined evidence**: devils-advocate grounds this in stability: "MCP tool contracts are the API surface that third-party integrations depend on. Underspecifying them leads to integration breakage when implementation details change." I ground it in developer experience: "MCP clients need schemas to render tool descriptions, validate inputs, and parse outputs." The combined position is that underspecified MCP tools fail on two fronts simultaneously — they break when internals change (stability) and they are unusable before they break (DX). devils-advocate's warning about the current single entry point (`/conversus run`) expanding to six separate tools reinforces why explicit contracts matter: the surface area is multiplying.
  - **Confidence level**: High. Both reviews independently arrive at the same recommendation with complementary rationale. The spec should include full tool schemas as part of the MCP server design, not defer them to implementation.

- **Web app must not delay developer-facing distribution**
  - **Shared position**: Both reviews agree that the web app should not block CLI, SDK, or MCP server delivery. devils-advocate recommends removing the web app from this spec entirely and creating a separate spec for it (Actionable Recommendations #7, "Separate the web app into its own spec"). I implicitly agree by focusing all 10 recommendations on CLI/SDK/MCP and offering zero web app recommendations, while explicitly endorsing the build order that sequences CLI before web app (Alignment, "Build order: CLI before web app").
  - **Combined evidence**: devils-advocate provides the scope argument: the web app introduces authentication, hosting, state management, streaming, and database design — "each of which is a significant design surface that is not addressed here." I provide the adoption argument: developer adoption always precedes web app usage for developer tools, and delaying MCP "means the highest-value developer integration ships last." The combined position is that the web app is both under-designed (devils-advocate) and lower-priority for the target adopters (my position). Shipping it before the developer-facing tools are stable serves neither quality nor adoption.
  - **Confidence level**: High. The disagreement between our reviews is tactical (remove from spec vs. deprioritize within spec), not strategic. Both reviews strongly agree on the underlying principle: developer distribution formats must ship first.

- **The proposal's constraints are well-designed and must be enforced**
  - **Shared position**: Both reviews commend the proposal's constraint list (L140-146). devils-advocate notes that the constraints are "well-chosen and mutually reinforcing" and that "if enforced, would catch many of the problems I identify below" (Alignment, "Constraint list"). I note that the proposal "explicitly preserves `/conversus run` for hand-crafted YAML" and that backward compatibility aligns with the decision framework's constraints (Alignment, "Power-user YAML preserved").
  - **Combined evidence**: The convergence is specifically on the enforcement question. devils-advocate's review demonstrates that the proposal violates its own constraints in practice — e.g., the constraint "Must not require any specific model or provider" is undermined by the absence of a degradation model across providers. My review demonstrates that the constraint "Must work for both trivial decisions and high-stakes decisions" is undermined by the absence of a CI/CD non-interactive mode. Both reviews use the proposal's constraints as the standard against which the proposal's design is measured and found incomplete. The constraints are sound; the design has not fully satisfied them yet.
  - **Confidence level**: Medium. The agreement is substantive — both reviews use the same analytical approach of "your constraints are correct, now here is where the design falls short of them." However, the specific gaps we identify are different (model capability gaps vs. programmatic execution gaps), so the combined confidence is about the analytical framework, not about any single gap.
