# Cross-Review of Architect's Review

**Cross-reviewer**: devex-advocate
**Reviewing**: architect's review of spec 011 (Adoption Harness)
**Date**: 2026-03-21

---

### Dangerous Contradictions

- **SDK API design vs. engine-interfaces-first**
  - **architect claims**: The extraction should target spec 007's `DeliberationState`, `AgentState`, `RoundState`, `PluginResult`, and lifecycle hook enum as Python dataclasses/protocols. "Add a 'Phase 0: Interface Definition' step before engine extraction" (Actionable Recommendations, item 1). These interfaces are internal engine state representations designed for plugin consumption.
  - **devex-advocate claims**: "Define the Python SDK's public API surface (classes, methods, types, async support) before any implementation begins -- it is the contract that CLI, MCP server, and web app all depend on" (Actionable Recommendations, item 1). The SDK's public API -- `Problem`, `Interests`, `Config`, `Deliberation`, `Result` -- is the primary interface contract, and all distribution surfaces are thin wrappers around it.
  - **Why this is dangerous**: Both reviews demand a "Phase 0: define interfaces first" step, but they are specifying *different* interfaces. Architect wants internal engine state models (`DeliberationState`, lifecycle hooks) drawn from spec 007's plugin architecture. devex-advocate wants external-facing SDK types (`Deliberation.run()`, `Config.from_yaml()`, structured `Result` dataclasses) drawn from the user-facing artifact chain. If both are adopted independently, the engine's internal state model and its public API will be designed in isolation, then forced together. The result is either a leaky abstraction where SDK users must understand plugin lifecycle internals, or a translation layer that adds complexity and drift between the two interface sets. This is particularly dangerous because architect's `DeliberationState` tracks `mode`, `round`, `agents` (positions/concessions), `synthesis`, and `history` -- while devex-advocate's `Result` needs `recommendation`, `confidence`, `arguments_for`, `arguments_against`, `dissent`. These are related but structurally different views of the same data, and designing one without the other produces impedance mismatch.
  - **Suggested resolution**: Both interface sets are necessary -- one internal, one external. The resolution is to design them together in the same Phase 0, with an explicit mapping layer. Architect's `DeliberationState` is the engine's runtime model; devex-advocate's `Result` is the public projection of that model. Define both, plus the `to_result()` method that bridges them. Neither reviewer should yield; the gap is that neither review acknowledges the other interface set exists.

- **Build order: plugin system early vs. MCP server early**
  - **architect claims**: "Invert the build order so that spec 007's plugin interface and `DeliberationState` model are defined first, then extract the engine to target those interfaces" (Executive Summary). Plugins are "architecturally foundational" and should move from last (phase 8) to effectively first (phase 0).
  - **devex-advocate claims**: "Move MCP server to build step 3" because it "reaches the largest developer audience... with zero behavior change" (Actionable Recommendations, item 3). The MCP server should ship alongside or immediately after the CLI, ahead of "Just Ask" mode.
  - **Why this is dangerous**: Both reviews propose reordering the build phases, but in conflicting directions. Architect pulls the plugin system forward (from phase 8 toward phase 0-1), which adds interface definition work before any shippable artifact. devex-advocate pulls the MCP server forward (from phase 5 to phase 3), which prioritizes shipping to the largest developer audience fast. If both are adopted without coordination, Phase 0 becomes interface definition (architect), Phase 1 becomes engine extraction targeting those interfaces (architect), Phase 2 becomes LiteLLM (unchanged), Phase 3 becomes MCP server (devex-advocate) -- but the MCP server needs the SDK to wrap, and the SDK design has been deferred in favor of internal plugin interfaces. The MCP server ships early but wrapping an undesigned public API, producing tool signatures that later break when the SDK is properly designed.
  - **Suggested resolution**: Architect's Phase 0 interface definition should include both the internal `DeliberationState` model and the external SDK public API. This satisfies architect's concern (engine targets the right interfaces) and devex-advocate's concern (SDK contract exists before MCP wraps it). The MCP server then moves to phase 3 as devex-advocate requests, but it wraps a designed SDK rather than an ad-hoc engine surface. Architect yields on making plugin *implementation* early; devex-advocate yields on accepting interface *definition* as a prerequisite step.

- **Web app deferral: hard cut vs. build-order preservation**
  - **architect claims**: "Move the web app out of the v1 scope entirely... Replace with: 'v1 ships CLI + MCP server + Python SDK. Web app is a separate proposal.'" (Actionable Recommendations, item 4). This is a hard architectural boundary -- the web app is explicitly excluded from the adoption harness scope.
  - **devex-advocate claims**: The review's build-order recommendation (Actionable Recommendations, item 3) reorders phases 3-5 but does not remove the web app. The Alignment section endorses "CLI before web app" (L120-127) as the correct sequencing, implicitly accepting the web app as in-scope but lower priority.
  - **Why this is dangerous**: Architect's position removes the web app from the proposal entirely. devex-advocate's position keeps it in the proposal but sequences it after developer-facing surfaces. If the synthesis adopts architect's hard cut, the proposal loses its story for non-technical users (the "Just Ask" consumer audience that the web app serves). If the synthesis adopts devex-advocate's implicit acceptance, architect's concern about scope pressure on the engine layer goes unaddressed. The contradiction matters because the proposal's three-tier user model (L25-31) includes "Anyone -- no technical knowledge" as the first tier, and the web app is the only distribution format that serves that tier without requiring a terminal.
  - **Suggested resolution**: Architect's concern is fundamentally about scope pressure on the engine, not about whether a web app should ever exist. The resolution is to keep the web app in the *vision* section of the proposal but explicitly defer it to a separate spec or v2 milestone, as architect recommends. This preserves the narrative for non-technical users while removing the engineering scope pressure. devex-advocate should support this -- developer tools that try to ship a web app alongside CLI/SDK/MCP in a single effort invariably shortchange the developer surfaces.

### Tensions

- **Minimum viable extraction scope**
  - **architect's position**: "The MVE is: Python CLI that reads `conversus.yml`, makes concurrent API calls to one provider (Anthropic), writes output files, and supports cooperative mode only" (Actionable Recommendations, item 9). Single mode, single provider, CLI only.
  - **devex-advocate's position**: The review does not define an MVE explicitly, but item 1 (Define SDK public API) and item 2 (structured output mode) both implicitly assume the full type system and all modes are designed before anything ships. The SDK's `Result` dataclass with `recommendation`, `confidence`, `mode_used`, `agents`, `arguments`, `dissent` presupposes multi-mode support.
  - **Nature of tension**: Architect wants to ship something minimal and validate the extraction quickly. devex-advocate wants to design the full type contract before shipping, which delays the first shippable artifact. These are not contradictory -- you can define a broad type contract and implement a narrow subset -- but they pull in different directions on what "ready to ship" means.
  - **Coordination needed**: Agree that the SDK types are designed for all modes (devex-advocate's concern) but the initial implementation only executes cooperative mode (architect's concern). The `Result` dataclass exists with all fields; `mode_used` is always `"cooperative"` in v0.1. This gives developers a stable type contract to code against while the engine fills in modes incrementally.

- **LiteLLM adequacy assessment**
  - **architect's position**: LiteLLM "does not normalize tool use, structured output, or long-context handling" (Off-Base Assumptions, item 3). Recommends evaluating whether a custom `ConversusAgent` abstraction is needed on top of LiteLLM (Actionable Recommendations, item 5).
  - **devex-advocate's position**: Recommends committing to "a thin provider interface (`class ModelProvider: async def complete(messages, **kwargs) -> str`) with LiteLLM as the default implementation" (Actionable Recommendations, item 8). Frames this as a standard pattern (cites LangChain's BaseModel, LlamaIndex's LLM class).
  - **Nature of tension**: Architect's concern is deeper than devex-advocate's solution addresses. devex-advocate proposes a clean interface with LiteLLM as the default backend -- a sound API pattern. But architect points out that conversus agents are not simple `complete(messages) -> str` calls -- they read files, write structured output, and follow template formats. The thin provider interface solves provider routing but does not solve the agent capability abstraction that architect identifies. These are two different layers: model provider (which model to call) vs. agent runtime (what an agent can do).
  - **Coordination needed**: Both layers need to exist. devex-advocate's `ModelProvider` interface handles model routing (which LLM to call, with what credentials). Architect's `ConversusAgent` abstraction sits above it, handling tool registration, output validation, and template enforcement. The two reviews are describing different parts of the same stack without acknowledging it. The spec should define both: `ModelProvider` (simple, LiteLLM-backed) and `AgentRuntime` (complex, handles the tool-use and structured-output concerns architect raises).

- **Parallel dispatch complexity framing**
  - **architect's position**: The proposal's claim that parallel dispatch is "already built" is "misleading" (Off-Base Assumptions, item 1). Lists five specific requirements for the async dispatch engine: concurrent API calls, context isolation, output collection/validation, partial failure handling, and phase barriers. Calls this "a substantial piece of infrastructure that does not exist and must be built from scratch."
  - **devex-advocate's position**: The review does not challenge the "already built" claim directly. Instead, it focuses on the *streaming* aspect of parallel dispatch: "The SKILL.md execution model already has phase-by-phase reporting... These natural phase boundaries should be exposed as progress events" (Missed Opportunities, item 5). Implicitly treats the dispatch problem as solvable and focuses on the developer-facing observation points.
  - **Nature of tension**: Architect is raising an alarm about the engineering difficulty of replicating Claude Code's Agent tool dispatch semantics in pure Python. devex-advocate is already designing the developer experience of that dispatch (progress events, streaming). These are not contradictory, but devex-advocate's streaming design depends on architect's dispatch engine existing and having the right internal hooks. If the dispatch engine is harder than devex-advocate assumes, the streaming/progress design may need to be simplified.
  - **Coordination needed**: Architect's dispatch engine design (Actionable Recommendations, item 3: `asyncio.TaskGroup`, `PhaseBarrier`, per-agent error isolation) should be adopted as the engineering specification. devex-advocate's streaming/progress design should be layered on top of it. The `PhaseBarrier` abstraction naturally emits the phase-boundary events that devex-advocate wants to expose via MCP progress notifications.

- **"Just Ask" output format**
  - **architect's position**: "Just Ask" output should "produce a subset of the standard conversus output: at minimum, a synthesis file following the same mode-specific template structure" so it can feed back into `prior:` context and the dispute parsing subsystem (Actionable Recommendations, item 8).
  - **devex-advocate's position**: "Just Ask" should return structured data -- "a Python dataclass / JSON object with fields: `recommendation`, `confidence`, `mode_used`, `agents`, `arguments`, `dissent`, `raw_synthesis`" (Actionable Recommendations, item 2). Plain English is "a rendering of this structure, not the primary output."
  - **Nature of tension**: Architect wants the output to be template-conformant markdown (for ecosystem compatibility -- prior rounds, dispute parsing, plugins). devex-advocate wants the output to be structured data (for programmatic consumption -- CI/CD, SDK chaining, MCP tool responses). These are not mutually exclusive but they imply different "primary" representations. If the template-conformant markdown is primary, parsing it into structured data is lossy and fragile. If the structured data is primary, rendering it to template-conformant markdown may not produce output that the dispute parsing subsystem can reliably parse.
  - **Coordination needed**: The engine should produce structured data internally (devex-advocate's position) and render it to template-conformant markdown as a serialization step (architect's position). The `Result` dataclass includes `raw_synthesis: str` which is the rendered markdown. This way both consumers -- programmatic (read the dataclass) and ecosystem (read the markdown) -- get what they need. The key design constraint is that the markdown renderer must produce output that passes the dispute parsing subsystem's structural checks.

### Safe Agreements

- **Engine extraction before distribution surfaces**
  - **Shared position**: Both reviews agree that the Python engine extraction is the foundational step that must precede all distribution formats. Architect: "invert the build order so that spec 007's plugin interface and `DeliberationState` model are defined first, then extract the engine to target those interfaces" (Executive Summary). devex-advocate: "The SDK is the foundational layer. CLI is `click` wrapping SDK methods. MCP server is MCP handlers wrapping SDK methods. Web app is FastAPI wrapping SDK methods" (Actionable Recommendations, item 1).
  - **Combined evidence**: Architect provides the engineering argument: the SKILL.md contains 734 lines across 6 distinct subsystems that must be decomposed into independently testable modules (Actionable Recommendations, item 2). devex-advocate provides the developer experience argument: without a designed SDK, three separate implementations of core logic will diverge across CLI, MCP, and web, tripling maintenance cost (Actionable Recommendations, item 1, Risk). Both lines of reasoning converge on the same conclusion: the engine/SDK is the single dependency that every surface shares, and getting it wrong propagates errors everywhere.
  - **Confidence level**: High. This is the structural insight of the entire review process, and both reviewers arrived at it independently from different analytical frameworks.

- **SKILL.md and Python engine cannot remain independent implementations**
  - **Shared position**: Both reviews identify that maintaining two independent implementations of the orchestration logic will produce divergence and bugs. Architect: "Do not maintain two independent implementations of the same orchestration logic -- they will diverge" and recommends either making SKILL.md a thin adapter or freezing it as legacy (Actionable Recommendations, item 7). devex-advocate: identifies the proposal's framing of the Claude Code lock-in as mischaracterized -- "The lock-in is to the Agent tool pattern, not to Claude Code specifically" (Off-Base Assumptions) -- which implies the SKILL.md's value is its orchestration spec, not its runtime coupling, and that spec should live in exactly one place.
  - **Combined evidence**: Architect cites the concrete risk: "Feature drift between SKILL.md and Python engine produces two subtly different deliberation behaviors, making bug reports unresolvable." devex-advocate identifies the architectural reason: the SKILL.md is really an agent runtime specification, and the Python extraction is a re-implementation of that specification in a portable form. Maintaining both means maintaining two codebases that encode the same five non-negotiable rules (`SKILL.md, L286-298`), which is a synchronization problem that scales with every feature addition.
  - **Confidence level**: High. Dual-implementation maintenance is a well-understood antipattern. Both reviews flag it as a risk, and both recommend explicit resolution rather than leaving open question 1 (L131) unanswered.

- **MCP maturity is not the real concern**
  - **Shared position**: Both reviews agree that the proposal's open question 5 ("Is MCP mature enough to be the primary integration strategy?" at L135) misidentifies the risk. Architect implicitly agrees by designing MCP tool additions (Actionable Recommendations, item 6: `conversus_replay`) without questioning MCP's readiness. devex-advocate explicitly states: "MCP coverage is sufficient... The correct concern is not MCP's maturity but conversus's MCP server design quality" (Off-Base Assumptions, item 2).
  - **Combined evidence**: Architect's review treats MCP as a stable platform -- recommending additional tools, endorsing the existing six-tool surface, and focusing critique on what the tools expose rather than whether MCP can support them. devex-advocate lists the MCP-supporting editors (Claude Code, Cursor, Windsurf, Zed, VS Code) as evidence of maturity and redirects the concern to input/output schema quality. Both reviews treat MCP as ready and focus on conversus's design quality as the real adoption risk.
  - **Confidence level**: Medium. The agreement is substantive but the underlying claim (MCP is mature enough) is an external dependency assessment that could change. The combined position is strong enough to resolve open question 5 in the proposal -- replace it with a design quality concern rather than a platform maturity concern.

- **Decomposition of the engine extraction**
  - **Shared position**: Both reviews identify that treating engine extraction as a single build phase (L120) undersells the scope. Architect: explicitly calls for 5 sub-phases -- config parser, template engine, async dispatch, dispute parsing, output manager (Actionable Recommendations, item 2). devex-advocate: implicitly requires decomposition by demanding that the SDK's public API be designed first (Actionable Recommendations, item 1), that structured output parsing exist (item 2), that validation/dry-run be a separate capability (item 6), and that preset management be independently accessible (item 7) -- each of which maps to a distinct engine module.
  - **Combined evidence**: Architect provides the internal decomposition (6 subsystems identified from SKILL.md line references). devex-advocate provides the external decomposition (each SDK capability implies a distinct engine module behind it). The two decompositions are complementary: architect's modules are implementation-oriented (what the code does), devex-advocate's are API-oriented (what the developer sees). Together they define both the internal architecture and the public surface of a well-factored engine.
  - **Confidence level**: High. Both reviews independently conclude that a monolithic extraction will fail, and their respective decompositions are compatible and reinforcing.
