# Cross-Review: consumer-advocate's Review

**Reviewer**: devex-advocate
**Reviewing**: consumer-advocate's Phase 1 review of spec 011 (Adoption Harness)

---

### Dangerous Contradictions

- **Build order inversion: Web app vs. MCP server priority**
  - **consumer-advocate claims**: "Move the web app and 'Just Ask' mode into a single deliverable and prioritize it above the MCP server and CLI, because non-technical users are the largest addressable market and they will never use a terminal." (Executive Summary). Their Recommendation 1 proposes moving the web app to build step 4 or 5, immediately after "Just Ask" engine work (Actionable Recommendations, item 1).
  - **devex-advocate claims**: "Move MCP server to build step 3" (Actionable Recommendations, item 3). The MCP server should ship alongside or immediately after the CLI because it reaches the largest developer audience with zero behavior change. Delaying it to step 5 means the highest-value developer integration ships last.
  - **Why this is dangerous**: Both reviews demand their preferred distribution format be elevated to approximately the same build position (step 3-5). If both are adopted literally, either the MCP server or the web app gets deprioritized again, or the team attempts to ship both simultaneously and delivers neither well. The build order is a zero-sum resource allocation: engineering time spent on Next.js/FastAPI/WebSocket/PostgreSQL is time not spent on MCP tool schemas, and vice versa. Attempting parallel delivery of two complex distribution formats with different tech stacks (Python MCP server vs. Next.js + FastAPI) will split focus and produce two half-finished surfaces.
  - **Suggested resolution**: Sequence them back-to-back rather than fighting for the same slot. The SDK and engine extraction (steps 1-2) are prerequisites for both. Ship the MCP server at step 3 (it is a thin wrapper over the SDK -- consumer-advocate does not contest this). Ship the web app at step 4-5 (consumer-advocate's recommendation). This gives developers the MCP integration within weeks of the SDK, while consumers get the web app one sprint later -- not months later as the original proposal has it. The key concession from the devex side: do not block the web app behind the guided workflow (step 6). The key concession from the consumer side: accept that MCP ships first because it is a thinner layer with less engineering surface area.

- **"Just Ask" output format: Structured JSON vs. plain English**
  - **consumer-advocate claims**: Results should use "progressive disclosure" with three layers: "(1) headline recommendation in one sentence, (2) summary paragraph with key trade-offs, (3) full agent arguments and dissent expandable on demand" (Actionable Recommendations, item 4). The emphasis throughout their review is on plain-English, human-readable output.
  - **devex-advocate claims**: "All SDK methods and MCP tools should return structured data by default -- a Python dataclass / JSON object with fields: `recommendation`, `confidence`, `arguments_for`, `arguments_against`, `dissent`." (Actionable Recommendations, item 2). "Plain-English is a rendering of this structure, not the primary output."
  - **Why this is dangerous**: If the "Just Ask" engine is built to emit prose (as consumer-advocate's layered disclosure model implies), developers will be forced to parse markdown to extract structured fields. If it is built to emit JSON (as devex-advocate proposes), the web app will need a rendering layer that the proposal does not currently scope. These are not just different presentations of the same data -- they imply different engine architectures. A prose-first engine loses structure; a structure-first engine requires a presentation layer. Building both paths doubles the output pipeline.
  - **Suggested resolution**: Build structure-first, render-second. The engine should return a structured object (JSON/dataclass) with fields that map to consumer-advocate's three layers: `headline` (layer 1), `summary` (layer 2), `full_analysis` (layer 3), plus machine-readable fields like `confidence`, `mode_used`, and `agents`. The web app renders this structure into consumer-advocate's progressive disclosure UI. The SDK and MCP return the raw structure. Both reviews get what they need from the same engine output. Consumer-advocate should yield on the engine design; devex-advocate should yield on the web app rendering -- it must not dump raw JSON on consumers.

- **"Just Ask" as CLI-first vs. web-native**
  - **consumer-advocate claims**: "Building 'Just Ask' as a headless engine and then bolting a web UI onto it will produce a developer tool with a web skin, not a consumer product. The correct approach is to design 'Just Ask' as a web-native experience from the start, with the engine as its backend." (Off-Base Assumptions, item 1).
  - **devex-advocate claims**: The SDK is the foundational layer: "CLI is `click` wrapping SDK methods. MCP server is MCP handlers wrapping SDK methods. Web app is FastAPI wrapping SDK methods." (Actionable Recommendations, item 1). The engine must be headless and distribution-agnostic.
  - **Why this is dangerous**: Consumer-advocate's "web-native from the start" framing risks coupling the "Just Ask" engine to HTTP/WebSocket semantics, making it unusable from CLI, SDK, or MCP contexts. Devex-advocate's "headless engine" framing risks producing a "Just Ask" mode that feels like a CLI command rendered in a browser. If the team interprets "web-native" as "build the web app first and extract the engine later," the SDK will be an afterthought. If the team interprets "headless engine" as "ignore UX concerns until the web app sprint," the consumer experience will suffer.
  - **Suggested resolution**: These positions are reconcilable if "web-native" is understood as a UX design constraint, not an architecture constraint. The engine should be headless (devex-advocate's position) but its API surface must be designed with the web app's UX requirements as first-class inputs (consumer-advocate's concern). Concretely: the engine's streaming events, clarification flow, and result structure should be co-designed with the web app wireframes, even if the engine ships before the web app. Consumer-advocate should accept a headless engine. Devex-advocate should accept that the engine's API must be shaped by consumer UX requirements, not just SDK ergonomics.

### Tensions

- **Clarification flow: Conversational vs. non-interactive**
  - **consumer-advocate's position**: "The system should ask one clarifying question (not five), offer to reframe the question, or explain what kinds of questions work best. Model this on the decision framework's `[CLARIFY: ...]` behavior but make it conversational, not tag-based." (Actionable Recommendations, item 2).
  - **devex-advocate's position**: "Add `--non-interactive` / `--ci` flag to all CLI commands that: (a) accepts all auto-generated defaults without prompting, (b) fails with a non-zero exit code and structured error on missing required inputs instead of prompting." (Actionable Recommendations, item 4).
  - **Nature of tension**: Consumer-advocate wants the system to be more interactive when input is vague -- ask a follow-up, guide the user. Devex-advocate wants the system to be less interactive -- accept defaults or fail fast. These pull in opposite directions on the same feature (vague input handling). A conversational clarification loop is exactly what breaks CI/CD pipelines.
  - **Coordination needed**: The engine must support both paths through a mode flag, not by being fundamentally interactive or fundamentally non-interactive. When `interactive=True` (web app, CLI default), vague input triggers consumer-advocate's clarification flow. When `interactive=False` (SDK default, CLI with `--ci`), vague input triggers devex-advocate's fail-fast behavior with a structured error explaining what was ambiguous. The clarification logic exists in both paths; only the response mechanism differs.

- **Scope of "Just Ask" auto-generation: Domain-aware vs. domain-agnostic**
  - **consumer-advocate's position**: "Add a secondary classification layer for consumer domains: personal finance, career, travel, shopping, health, entertainment. Use domain to adjust agent personas, set appropriate disclaimers, and tune output tone." (Actionable Recommendations, item 9).
  - **devex-advocate's position**: The proposal's existing problem-type classification (selection, integration, scoping, stress-test) maps to the decision framework's taxonomy, and the SDK should expose this classification programmatically. The devex review does not propose domain-specific routing -- it focuses on the structural classification and mode selection. (Alignment section, reference to decision framework heuristics).
  - **Nature of tension**: Consumer-advocate wants the system to know about domains (finance, health, travel) and behave differently for each. Devex-advocate wants the system to remain domain-agnostic, with the structural problem-type classification as the only built-in taxonomy. Domain-specific behavior risks hardcoding assumptions that do not generalize and creates a maintenance burden for every new domain. But domain-agnostic treatment makes consumer results feel generic.
  - **Coordination needed**: Implement domain awareness as a preset layer, not as core engine logic. Consumer-advocate's domain routing maps naturally to the preset system that devex-advocate's review highlights (Alignment section, "Preset and template extensibility"). A "personal-finance" preset would include risk-averse agent templates, disclaimer text, and formal output tone -- without requiring the engine to know about finance. The web app applies presets automatically based on domain classification; the SDK lets developers apply them explicitly. This gives consumers domain-aware behavior and developers domain-agnostic composability.

- **Confidence indicators: Consumer-facing vs. machine-readable**
  - **consumer-advocate's position**: "Add a confidence signal to every result: 'Strong recommendation' (agents converged), 'Moderate recommendation' (majority agreement with notable dissent), or 'Close call' (significant disagreement)." (Actionable Recommendations, item 5). These are human-readable labels.
  - **devex-advocate's position**: The structured output should include `confidence` as a float 0-1 (Actionable Recommendations, item 2). This is a machine-readable value.
  - **Nature of tension**: Consumer-advocate wants three discrete buckets with plain-language labels. Devex-advocate wants a continuous numeric score. These are not contradictory, but they require coordination: the mapping from float to label must be defined, consistent, and documented. If the web app maps 0.6 to "Moderate recommendation" but a developer's CI pipeline treats 0.6 as high confidence, the system sends mixed signals about the same deliberation.
  - **Coordination needed**: Define the confidence value as a float in the engine (devex-advocate's position) and define the bucket boundaries as a documented, configurable mapping: 0.0-0.4 = "Close call," 0.4-0.7 = "Moderate recommendation," 0.7-1.0 = "Strong recommendation." The web app uses the labels; the SDK returns the float and the label. The thresholds are configurable so developers can adjust for their use case.

- **Share links: Viral growth mechanism vs. API endpoint**
  - **consumer-advocate's position**: "Share links are the primary viral growth mechanism for consumer products. If the shared page confuses the recipient, the viral loop breaks." Detailed requirements for standalone, no-login, no-context share pages with CTAs. (Actionable Recommendations, item 8).
  - **devex-advocate's position**: The devex review does not mention share links at all. The focus is on programmatic access -- SDK methods, MCP tools, CLI output. The closest analog is the structured output recommendation, where results are JSON objects that can be serialized and passed between systems.
  - **Nature of tension**: Consumer-advocate sees share links as a critical growth vector requiring significant frontend investment (standalone pages, CTAs, social optimization). Devex-advocate's silence on share links reflects a different growth model: developers adopt tools through package registries, MCP directories, and word-of-mouth in engineering communities -- not through shared result pages. The tension is not about whether share links should exist, but about how much engineering effort they deserve relative to SDK/MCP polish.
  - **Coordination needed**: Share links should be scoped as a web-app-only feature that does not affect the engine, SDK, or MCP server. The engine produces structured results; the web app renders shareable pages from those results. This keeps the devex surface clean while giving consumer-advocate the viral mechanism they need. The share page is a read-only rendering concern, not an engine concern.

### Safe Agreements

- **The three-tier user model is correct**
  - **Shared position**: Both reviews endorse the Just Ask / Guided / Power tier structure. Consumer-advocate: "The tiered approach correctly segments users by technical ability. The 'Just Ask' tier with 'Zero -- system infers everything' config effort directly matches what consumer users need." (Alignment section). Devex-advocate: "The three-tier user model (Just Ask, Guided, Power) is a sound abstraction that maps cleanly to how developers actually adopt tools: try it in one command, use the guided workflow when they need more control, then drop to raw YAML when they own the domain." (Executive Summary).
  - **Combined evidence**: Consumer-advocate grounds this in the decision framework's non-expert usability constraint (SC-1, spec.md L481-483). Devex-advocate grounds it in developer adoption patterns (progressive complexity). Both perspectives arrive at the same conclusion from different directions: consumers need the tiers because they cannot handle YAML; developers need the tiers because they want to start simple and escalate. The model serves both audiences simultaneously.
  - **Confidence level**: High. This is the proposal's central architectural decision and both reviews validate it independently from their respective user bases.

- **The proposal underspecifies what it claims to prioritize**
  - **Shared position**: Both reviews identify that the proposal names distribution formats and features but fails to specify their interfaces, contracts, or behaviors. Consumer-advocate: vague question handling is unspecified (Missed Opportunities, item 1), progressive result disclosure is absent (item 3), share link recipient experience is undefined (item 7). Devex-advocate: SDK API surface is undefined (Missed Opportunities, item 1), MCP tool schemas are missing (item 4), CI/CD non-interactive mode is undesigned (item 3).
  - **Combined evidence**: Consumer-advocate finds underspecification in the consumer-facing features (web app UX, "Just Ask" edge cases). Devex-advocate finds underspecification in the developer-facing features (SDK types, MCP schemas, error contracts). Together, these reviews reveal that the proposal is underspecified across every distribution format, not just one. The proposal reads as a vision document, not a technical specification -- it names what to build but not how any of it works. This pattern is consistent: the proposal is 147 lines covering 8 build steps, 5 distribution formats, and 3 user tiers. Nothing at that ratio can be adequately specified.
  - **Confidence level**: High. Both reviews independently reach this conclusion from opposite ends of the user spectrum, which makes it a systemic issue rather than a perspective-specific complaint.

- **Backward compatibility with existing power-user workflows is non-negotiable**
  - **Shared position**: Both reviews confirm that preserving `/conversus run` with hand-crafted YAML is essential. Consumer-advocate does not contest this (the review focuses on consumer additions, not power-user removals). Devex-advocate explicitly endorses it: "The proposal explicitly preserves `/conversus run` for hand-crafted YAML, which means existing power-user workflows are not broken. This aligns with the backward compatibility constraint in the decision framework." (Alignment section, item 3).
  - **Combined evidence**: Consumer-advocate's entire review is about adding consumer-facing capabilities on top of the existing system -- none of the 10 recommendations propose changing or removing power-user features. Devex-advocate cites the decision framework's backward compatibility constraint (spec.md L439-446). The absence of conflict here is itself evidence: neither reviewer sees the adoption harness as requiring trade-offs against the power-user tier.
  - **Confidence level**: High. This agreement is load-bearing: it means the adoption harness can be designed as a purely additive layer, which reduces risk for both audiences.
