# Cross-Review: adoption-strategist's Review

**Reviewer**: consumer-advocate
**Reviewing**: adoption-strategist's Phase 1 review of Spec 011 (Adoption Harness)

---

### Dangerous Contradictions

- **Web app: cut it vs. elevate it**
  - **adoption-strategist claims**: "Cut the web app from the initial roadmap" (Actionable Recommendations, #8). The web app is "the highest-cost, highest-risk item in the proposal" and should be removed entirely, revisited only if demand is validated through Claude Code, MCP, and CLI channels.
  - **consumer-advocate claims**: "Elevate web-app priority" (Actionable Recommendations, #1). The web app should move to step 4 or 5 in the build order, delivered as a single milestone with "Just Ask" mode, because "non-experts will not use a CLI. The web app is the only path that satisfies SC-1 for the consumer tier."
  - **Why this is dangerous**: These are mutually exclusive positions on the single largest deliverable in the proposal. If both recommendations are adopted without resolution, the web app is simultaneously removed from the roadmap and elevated to a top-five priority. More concretely: adoption-strategist's approach validates demand exclusively through developer-facing channels (Claude Code skill, CLI, MCP). If non-technical users never encounter conversus through those channels -- and they will not, because none of those channels are accessible to a retiree or a parent -- the validation will show zero non-technical demand, and the web app will never be built. The absence of demand becomes a self-fulfilling prophecy created by the channel selection, not by actual market disinterest.
  - **Suggested resolution**: Both positions share a valid concern -- the web app is expensive and should not be built speculatively. The compromise is a scoped consumer validation step that does not require the full Next.js + FastAPI + PostgreSQL stack. A single-page "Just Ask" web interface (static frontend, API backend, no history, no accounts) could validate consumer demand at a fraction of the cost. If adoption-strategist's validation gates (their Recommendation #2) show consumer interest through this lightweight channel, the full web app investment is justified. If not, it is cut. The key concession: adoption-strategist should yield on "cut the web app entirely" and accept a minimal web validation artifact; consumer-advocate should yield on "full web app at step 4" and accept a scoped proof-of-concept first.

- **Primary integration path: MCP-skepticism vs. dual-primary**
  - **adoption-strategist claims**: "MCP is not mature enough to be the 'primary' integration path" (Off-Base Assumptions, first item). "The primary path for the first 100 users should be the channel with the lowest friction -- which is the existing Claude Code skill."
  - **consumer-advocate claims**: "Declare dual-primary integration paths" (Actionable Recommendations, #6). The MCP server should be "Primary Developer Integration Path" and the web app should be "Primary Consumer Integration Path." Both are primary for different audiences.
  - **Why this is dangerous**: Adoption-strategist wants a single primary path (Claude Code skill) validated first, then expansion. Consumer-advocate wants two declared primaries from the start (MCP for developers, web for consumers). If both positions stand, the team receives conflicting signals about where to focus. Adoption-strategist's single-primary approach risks starving the consumer path of investment. Consumer-advocate's dual-primary approach risks splitting focus before either channel reaches critical mass.
  - **Suggested resolution**: Adoption-strategist's phased validation logic is sound: prove one channel before expanding. Consumer-advocate's audience segmentation is also correct: developers and consumers need fundamentally different paths. The resolution is sequential dual-primary: validate the Claude Code skill first (adoption-strategist's recommendation), then validate a lightweight consumer web experience second -- but commit to the consumer validation as a defined next step with a timeline, not an open-ended "revisit later." Consumer-advocate should accept sequencing; adoption-strategist should accept that the consumer channel is a committed phase, not an optional future.

- **Where "Just Ask" lives: CLI-engine vs. web-native**
  - **adoption-strategist claims**: Ship "Just Ask" as a Claude Code skill first (Actionable Recommendations, #1). Implement it as a `/conversus decide` command within the existing SKILL.md runtime. "No Python extraction needed." The emphasis is on speed to validation within the developer ecosystem.
  - **consumer-advocate claims**: Building "Just Ask" as "a headless engine and then bolting a web UI onto it will produce a developer tool with a web skin, not a consumer product" (Off-Base Assumptions, first item). "Just Ask" should be designed as "a web-native experience from the start, with the engine as its backend."
  - **Why this is dangerous**: If "Just Ask" is designed as a Claude Code skill first and a web experience second, the interaction model will be shaped by terminal constraints: text-in, text-out, no progressive disclosure, no visual confidence indicators, no example prompts on a landing page. When the web app eventually wraps this, it inherits a CLI-shaped API that makes consumer features (progressive result layers, mobile layout, clickable examples) feel bolted on. Conversely, if "Just Ask" is designed web-native first, it delays the earliest possible validation by weeks or months.
  - **Suggested resolution**: Both sides should accept a design-first, implement-twice approach. Design the "Just Ask" output format with the consumer web experience in mind -- structured JSON with headline, summary, full-analysis, and confidence fields -- even when the first implementation is a Claude Code skill that renders those fields as plain text. This lets adoption-strategist get the fast validation they want while ensuring consumer-advocate's web experience does not inherit a flat-text output model. The key constraint: the output schema must be defined before the Claude Code skill ships, not after.

### Tensions

- **Validation speed vs. consumer representation in validation**
  - **adoption-strategist's position**: "Ship 'Just Ask' as a Claude Code skill first" and "define adoption gates before committing to build order" (Recommendations #1 and #2). Validate with 50-100 real decisions, then let data drive expansion.
  - **consumer-advocate's position**: Consumer users "will never use a terminal" (Executive Summary). The proposal's named consumer users -- retirees, students, parents, small business owners (citing proposal L18-20) -- cannot participate in a Claude Code validation.
  - **Nature of tension**: Adoption-strategist optimizes for speed-to-learning. Consumer-advocate notes that learning from the wrong population teaches the wrong lessons. A Claude Code validation will tell you what developers want from conversus. It will tell you nothing about what a parent planning a vacation wants, because that parent is not in Claude Code. Both priorities are valid: fast feedback is essential, but feedback from a non-representative sample can be worse than no feedback.
  - **Coordination needed**: The validation gates (adoption-strategist's Recommendation #2) must include a consumer-specific gate. After the Claude Code validation, there must be a separate consumer validation using a channel consumers can access (even if lightweight). The gates should explicitly define what "consumer validation" looks like: different users, different metrics (task completion rate, not retention-in-IDE), different questions.

- **"See the debate" vs. progressive disclosure**
  - **adoption-strategist's position**: "Add 'see the debate' to Just Ask output" (Recommendation #3). The full debate transcript -- agent positions, cross-review attacks, resolution of disagreements -- is what makes conversus "visibly different from ChatGPT." Without it, "conversus is just another wrapper."
  - **consumer-advocate's position**: "Design progressive result disclosure" (Recommendation #4). Results should be layered: one-sentence answer, one-paragraph explanation, full analysis behind a toggle. "Dumping the full synthesis on a non-technical user is overwhelming."
  - **Nature of tension**: Both reviews want the debate visible, but they pull in opposite directions on default behavior. Adoption-strategist wants the debate front-and-center to differentiate. Consumer-advocate wants the recommendation front-and-center to serve the user. Showing everything by default serves differentiation but hurts usability. Hiding the debate by default serves usability but makes conversus look like any other chatbot.
  - **Coordination needed**: The resolution is a layered default: headline recommendation visible, debate collapsed but prominently indicated. The key design constraint is that the "see the debate" affordance must be visually prominent -- not a buried link, but a clear indicator like "3 agents debated, 2 attacks survived cross-review -- see the full debate." This satisfies adoption-strategist's differentiation requirement (the multi-agent process is visible in the summary metadata) and consumer-advocate's usability requirement (the recommendation is not buried under agent arguments).

- **Preset seeding scope: developer decisions vs. consumer decisions**
  - **adoption-strategist's position**: "Seed 20 community presets" (Recommendation #5). Examples are developer-focused: "React vs Vue vs Svelte," "Postgres vs MySQL vs Mongo," "monolith vs microservices," "AWS vs GCP vs Azure."
  - **consumer-advocate's position**: "Add consumer domain routing" (Recommendation #9) and "Add example questions to web app landing page" (Recommendation #3). Examples are consumer-focused: "Should I lease or buy my next car?", "Which major should I choose?", "Where should my family vacation?"
  - **Nature of tension**: The initial preset library and example set signal what conversus is for. If the first 20 presets are all developer decisions, conversus is positioned as a developer tool. If examples include consumer decisions, it is positioned as a general-purpose decision tool. Preset development effort is finite; every developer preset is a consumer preset not built.
  - **Coordination needed**: The initial 20 presets should include both audiences: 12-15 developer/professional presets (adoption-strategist's list) plus 5-8 consumer presets (personal finance, career choice, major purchase, vacation planning). The developer presets validate the power-user path; the consumer presets validate the "Just Ask" path and serve as landing page examples. Both reviews should agree on a mixed preset allocation.

- **Sharing mechanism priority**
  - **adoption-strategist's position**: "Build a sharing mechanism as a first-class feature" (Recommendation #7). Every deliberation should produce a shareable artifact -- markdown or HTML report. Sharing is "the highest-leverage growth mechanic."
  - **consumer-advocate's position**: "Specify self-contained share page experience" (Recommendation #8). Shared links must render standalone pages requiring no login, no account, and no knowledge of conversus. Must include a CTA: "Ask your own question."
  - **Nature of tension**: Both agree sharing matters, but adoption-strategist frames it as a developer-to-developer growth channel (markdown in Slack, forwarded to colleagues), while consumer-advocate frames it as a viral consumer loop (standalone web page with conversion CTA). A markdown file shared in Slack does not convert a non-technical recipient. A web share page does not exist if the web app is cut. These are different sharing mechanisms for different audiences.
  - **Coordination needed**: If the web app is scoped down per the resolution above (lightweight validation artifact), the share page must be included in that minimal scope. A shareable deliberation result that renders as a standalone web page is both a sharing mechanism and a consumer acquisition channel. Both reviews should converge on: share pages are in-scope even for the minimal web artifact.

### Safe Agreements

- **Build order must be resequenced away from infrastructure-first**
  - **Shared position**: Adoption-strategist's Executive Summary states the proposal "sequences build order by technical dependency rather than by adoption velocity" and that Python engine extraction as step 1 is an "engineering-first assumption that delays all user-facing work" (Off-Base Assumptions, second item). Consumer-advocate's Executive Summary states the build order "buries the consumer-facing product at step 7 of 8" and "every step before it serves developers." Both reviews identify the current build order (L119-127) as the proposal's most significant structural flaw.
  - **Combined evidence**: Adoption-strategist grounds this in the decision framework spec's Phase A having "zero dependencies on engine changes" (`spec.md, L547-559`). Consumer-advocate grounds it in the decision framework's SC-1 (Non-Expert Usability) requiring that non-experts complete a deliberation without YAML (`spec.md, L481-483`). The infrastructure-first sequence delays validation from both perspectives: developers cannot test "Just Ask" until step 4 (adoption-strategist's concern), and consumers cannot access the product until step 7 (consumer-advocate's concern).
  - **Confidence level**: **High**. This is the strongest agreement between both reviews. Both independently arrived at the same core critique -- the build order optimizes for architectural elegance rather than user-facing value -- using different evidence and different user populations. The final synthesis should treat build-order resequencing as a settled recommendation, with the remaining question being the exact new sequence.

- **"Just Ask" mode is the highest-priority feature**
  - **Shared position**: Adoption-strategist's Executive Summary calls "Just Ask" mode the "single fastest path to initial adoption" and recommends shipping it in two weeks. Consumer-advocate's Alignment section calls the "Just Ask" tier's "Zero -- system infers everything" config effort "directly what consumer users need" (citing proposal L29). Both reviews independently elevate "Just Ask" to P1 priority above all infrastructure work.
  - **Combined evidence**: Adoption-strategist cites the decision framework's heuristic detection system (`spec.md, L322-343`) as already providing the underlying capability. Consumer-advocate cites the decision framework's constraint that coding knowledge must not be required (`spec.md, L518-519`) and SC-8 plain-language output (`spec.md, L509-511`). Together, these establish that the spec 003 foundation already exists for "Just Ask," it serves both developer and consumer audiences, and it should be the first deliverable.
  - **Confidence level**: **High**. When the adoption strategist and the consumer advocate both independently identify the same feature as the single most important priority, the synthesis should treat this as near-certain.

- **Conversus must visibly differentiate from single-LLM answers**
  - **Shared position**: Adoption-strategist asks "Why not just ask ChatGPT?" and states conversus must "answer this in the first user interaction" (Recommendation #9). Consumer-advocate notes that results must include a "confidence indicator" (Recommendation #5) derived from agent agreement levels and that progressive disclosure must surface the multi-agent process. Both reviews independently identify invisible differentiation as an existential risk.
  - **Combined evidence**: Adoption-strategist proposes showing "N agents with [cooperative/adversarial] incentives" and "[X] arguments challenged, [Y] survived." Consumer-advocate proposes "Strong recommendation" / "Moderate recommendation" / "Close call" labels derived from dispute counts and cross-review alignment. Together, these form a complete differentiation strategy: quantitative process metadata (adoption-strategist) plus qualitative confidence signals (consumer-advocate). Neither alone is sufficient -- the metadata without the confidence label is developer jargon; the confidence label without the metadata is unsupported assertion.
  - **Confidence level**: **High**. Both reviews identify this as a risk that, if unaddressed, makes conversus indistinguishable from a chatbot and eliminates any reason for users to return. The combined approach (metadata + confidence label) is stronger than either review's individual recommendation.
