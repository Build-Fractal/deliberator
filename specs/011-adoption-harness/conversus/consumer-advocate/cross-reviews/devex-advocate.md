# Cross-Review: consumer-advocate reviewing devex-advocate

**Spec under review:** `specs/011-adoption-harness/proposal.md`
**Cross-reviewer:** consumer-advocate
**Reviewing:** devex-advocate's Phase 1 review

---

### Dangerous Contradictions

- **Build order: web app vs. MCP server priority**
  - **devex-advocate claims**: "Reorder to: (1) Python engine extraction, (2) SDK with types, (3) MCP server wrapping SDK, (4) CLI wrapping SDK, (5) 'Just Ask' mode." The MCP server should move from step 5 to step 3 because it "reaches the largest developer audience" and "delaying it to step 5 means the highest-value developer integration ships last." [Actionable Recommendations, item 3]
  - **consumer-advocate claims**: "Move web app to step 4 or 5, immediately after 'Just Ask' engine work. Deliver 'Just Ask' and web app as a single milestone." The web app should move from step 7 to step 4-5 because "non-technical users are the largest addressable market and they will never use a terminal." [Actionable Recommendations, item 1]
  - **Why this is dangerous**: Both reviews propose pulling their priority integration forward, but into the same build slots. devex-advocate's proposed order explicitly pushes "Just Ask" mode to step 5 and does not mention the web app at all -- implying it stays at step 7 or later. consumer-advocate's proposed order pushes the web app to step 4-5, which would collide with the MCP server at step 3-4 in devex-advocate's plan. If the synthesis adopts both recommendations without resolving the conflict, the build order becomes incoherent: everything is "step 3" and nothing is actually prioritized.
  - **Suggested resolution**: Acknowledge that these serve different audiences and sequence them in parallel tracks or as interleaved milestones. After engine extraction (step 1) and SDK (step 2), the MCP server and "Just Ask" web app could be built concurrently by different teams or interleaved as steps 3 and 4. The critical move is that neither should be step 7. Both reviews agree the current build order buries their highest-value feature -- the resolution is to compress the middle of the plan, not to fight over who gets step 3.

- **Structured output vs. plain-English output as the default**
  - **devex-advocate claims**: "All SDK methods and MCP tools should return structured data by default -- a Python dataclass / JSON object with fields: `recommendation` (string), `confidence` (float 0-1), `mode_used` (string), `agents` (list of agent summaries)... Plain-English is a rendering of this structure, not the primary output." [Actionable Recommendations, item 2]
  - **consumer-advocate claims**: The "Just Ask" mode's plain-English synthesis (L41) is correctly designed for consumer users. The review's progressive disclosure recommendation [Actionable Recommendations, item 4] asks for results layered as "(1) headline recommendation in one sentence, (2) summary paragraph with key trade-offs, (3) full agent arguments and dissent expandable on demand." The emphasis is on human-readable prose as the primary experience, not structured data.
  - **Why this is dangerous**: If structured JSON is the default output and plain-English is a "rendering," the development team will optimize for the structured format and treat the prose rendering as a second-class serialization layer. Consumer-facing language will be generated from field labels rather than written for human comprehension. "Recommendation: string" rendered into prose is not the same as a synthesis written to communicate with a non-technical reader. Conversely, if plain-English prose is the primary output, developers will parse it with regex -- the exact failure mode devex-advocate warns about.
  - **Suggested resolution**: Both outputs need to be first-class, not one derived from the other. The engine should produce a rich internal representation that is then rendered through two separate formatters: a structured-data formatter for SDK/MCP/CI consumers and a prose formatter for web app/consumer consumers. Neither is a "rendering" of the other; both are renderings of the deliberation result. This requires the synthesis step to produce structured data AND write human-quality prose, not to produce one and derive the other.

- **"Just Ask" as engine feature vs. web-native experience**
  - **devex-advocate claims**: The build order should be "(1) Python engine extraction, (2) SDK with types, (3) MCP server wrapping SDK, (4) CLI wrapping SDK, (5) 'Just Ask' mode" -- treating "Just Ask" as a feature of the engine/SDK layer. The review's entire framing positions "Just Ask" as an API endpoint: `conversus_decide` returning structured JSON. [Actionable Recommendations, items 2 and 3]
  - **consumer-advocate claims**: "Building 'Just Ask' as a headless engine and then bolting a web UI onto it will produce a developer tool with a web skin, not a consumer product. The correct approach is to design 'Just Ask' as a web-native experience from the start, with the engine as its backend." [Off-Base Assumptions, item 1]
  - **Why this is dangerous**: If "Just Ask" is designed engine-first (devex-advocate's position), the web experience inherits API-shaped constraints: single-request/single-response flow, no clarification step, no progressive disclosure, no example-driven onboarding. If "Just Ask" is designed web-first (consumer-advocate's position), the API/MCP surface may not get the structured input/output contracts developers need. Building both independently produces two "Just Ask" implementations that diverge in behavior.
  - **Suggested resolution**: Design "Just Ask" as a shared interaction protocol with two renderers. The protocol must include: question intake, optional clarification, deliberation execution, and result delivery. The web renderer adds UI elements (examples, progressive disclosure, mobile layout). The API renderer adds structured schemas (JSON input/output, error codes). Both share the same engine logic, but neither constrains the other's presentation layer. This requires the spec to define the protocol before either surface is built.

- No additional contradictions identified.

### Tensions

- **SDK-first architecture vs. consumer-first design**
  - **devex-advocate's position**: "Define the Python SDK's public API surface (classes, methods, types, async support) before any implementation begins -- it is the contract that CLI, MCP server, and web app all depend on." The SDK is the foundational layer; everything else wraps it. [Executive Summary, most important recommendation; Actionable Recommendations, item 1]
  - **consumer-advocate's position**: The web app and "Just Ask" mode should be designed as a consumer product first, with the engine as its backend. Consumer experience requirements (vague question handling, progressive disclosure, example onboarding) should shape the system's behavior. [Off-Base Assumptions, item 1; Actionable Recommendations, items 1-4]
  - **Nature of tension**: These positions are not contradictory -- you can have an SDK that is designed to support consumer experiences. But they pull in different directions on what drives design decisions. SDK-first means the consumer experience is constrained by what the API exposes. Consumer-first means the API is shaped by what the web app needs. The tension is about which set of requirements gets first-mover advantage in shaping the abstractions.
  - **Coordination needed**: The SDK design (devex-advocate's item 1) must be informed by consumer experience requirements (consumer-advocate's items 2-4) before it is locked down. This means the consumer UX requirements -- clarification flow, progressive result disclosure, confidence indicators -- must be captured as SDK-level capabilities, not web-app-only features. Joint design session where both perspectives contribute to the SDK spec.

- **CI/CD non-interactive mode vs. conversational clarification**
  - **devex-advocate's position**: "Add `--non-interactive` / `--ci` flag to all CLI commands that: (a) accepts all auto-generated defaults without prompting, (b) fails with a non-zero exit code and structured error on missing required inputs." SDK methods should be non-interactive by default. [Actionable Recommendations, item 4]
  - **consumer-advocate's position**: Vague question handling is the highest-priority missed opportunity. The system must ask clarifying questions when consumers provide vague input, not fail or produce shallow results. [Missed Opportunities, item 1; Actionable Recommendations, item 2]
  - **Nature of tension**: Non-interactive mode wants the system to never prompt; consumer mode wants the system to always prompt when input is unclear. These serve different audiences, but the underlying question classification and "is this input sufficient?" logic is shared. If the non-interactive path is built first, the clarification logic may never be designed. If the conversational path is built first, the fail-fast path may be an afterthought.
  - **Coordination needed**: The question intake layer needs a shared "sufficiency check" that determines whether the input is clear enough to proceed. In interactive/web mode, insufficient input triggers clarification. In non-interactive/CI mode, insufficient input triggers a structured error with a description of what is missing. Same detection logic, different response strategy. Design the sufficiency check as a first-class concept in the SDK.

- **Model agnosticism priority**
  - **devex-advocate's position**: LiteLLM integration should be resolved decisively with a thin provider interface and LiteLLM as default implementation. This is framed as a P2 recommendation but is described as blocking the entire extraction. [Actionable Recommendations, item 8]
  - **consumer-advocate's position**: Model agnosticism is not mentioned in the consumer review because consumers do not care which model runs their deliberation. They care about result quality, speed, and cost -- none of which are directly addressed by a provider abstraction.
  - **Nature of tension**: devex-advocate sees model agnosticism as architecturally critical for developer adoption. consumer-advocate sees it as irrelevant to consumer adoption. Both are correct for their audience. The tension is in resource allocation: engineering effort spent on the provider interface is effort not spent on the web app, clarification flow, or progressive disclosure.
  - **Coordination needed**: Model agnosticism belongs in the engine extraction phase (step 1-2), where it is an architectural decision, not a user-facing feature. It should not delay consumer-facing work. The resolution is sequencing: do the provider interface early as part of engine extraction, then move on to consumer features without blocking on multi-provider testing.

- **Preset system: programmatic API vs. consumer invisibility**
  - **devex-advocate's position**: The preset system should be exposed programmatically with `conversus.presets.list()`, `conversus.presets.get()`, `conversus.presets.compose()`, and corresponding MCP tools and CLI commands. [Missed Opportunities, item 6; Actionable Recommendations, item 7]
  - **consumer-advocate's position**: Consumer users should never see or interact with presets. The "Just Ask" mode should auto-select appropriate agent personas based on domain classification (personal finance, career, travel, etc.) without exposing the underlying preset machinery. [Actionable Recommendations, item 9]
  - **Nature of tension**: devex-advocate wants presets surfaced as a composable developer primitive. consumer-advocate wants presets hidden behind domain-aware auto-selection. Both can coexist, but the auto-selection layer that consumer-advocate needs is not addressed in devex-advocate's programmatic API design. If presets are exposed only programmatically, consumer users get generic agents. If presets are only auto-selected, developers lose composability.
  - **Coordination needed**: Build the programmatic preset API (devex-advocate's recommendation) AND a domain-routing layer on top of it (consumer-advocate's recommendation). The domain router is a consumer-facing feature that uses the programmatic preset API internally. The domain router maps "stock picking question" to `presets.compose(["bull-analyst", "bear-analyst", "risk-assessor"])` automatically. This makes presets useful to both audiences without compromise.

- **Dry-run/validate vs. consumer trust signals**
  - **devex-advocate's position**: Add `conversus validate` and `Deliberation.dry_run()` that check config, resolve presets, validate templates, and estimate cost/tokens without launching agents. [Missed Opportunities, item 8; Actionable Recommendations, item 6]
  - **consumer-advocate's position**: Add a confidence indicator to results showing "Strong recommendation," "Moderate recommendation," or "Close call" so consumers can calibrate trust. [Missed Opportunities, item 4; Actionable Recommendations, item 5]
  - **Nature of tension**: Both are asking for the system to communicate meta-information -- but to different audiences and at different stages. Developers want pre-execution validation (before spending money). Consumers want post-execution confidence (after getting results). The underlying need is the same: "how much should I trust this?" but the timing and framing differ entirely.
  - **Coordination needed**: The confidence/trust signal should be a property of the deliberation result (computed post-execution from agent agreement levels), exposed in both structured output (for developers) and prose output (for consumers). The dry-run/validate is a separate pre-execution check. Both should exist; neither substitutes for the other. Ensure the result data model includes a confidence field that both the structured and prose renderers can use.

### Safe Agreements

- **The current build order buries critical features**
  - **Shared position**: Both reviews identify the proposal's build order (L120-127) as fundamentally misordered. devex-advocate argues the MCP server should move from step 5 to step 3 [Actionable Recommendations, item 3]. consumer-advocate argues the web app should move from step 7 to step 4-5 [Actionable Recommendations, item 1]. Both reviews agree that the current ordering is driven by technical dependencies rather than user adoption value.
  - **Combined evidence**: devex-advocate provides the developer adoption argument: "the highest-value developer integration ships last" and "missing the window where AI-native engineers are actively looking for MCP tools." consumer-advocate provides the consumer adoption argument: "the product ships as a developer tool with a web app bolted on months later" and "the web app inherits CLI-shaped abstractions that feel wrong in a browser." Together, these establish that the current build order delays adoption for both primary audiences simultaneously. The proposal's own language supports the critique: it calls MCP the "Primary Integration Path" (L74) and names consumer users as a target audience (L18-20), yet both of their primary interfaces are in the back half of the plan.
  - **Confidence level**: High. This is the strongest shared finding. The synthesis should restructure the build order to deliver consumer and developer integration surfaces earlier, whether through parallel tracks or compressed sequencing.

- **The proposal correctly identifies the three-tier user model**
  - **Shared position**: Both reviews endorse the Just Ask / Guided / Power tiering (L25-31) as a sound segmentation. devex-advocate writes that it "maps cleanly to how developers actually adopt tools: try it in one command, use the guided workflow when they need more control, then drop to raw YAML when they own the domain" [Alignment, item 1]. consumer-advocate writes that the tiered approach "correctly segments users by technical ability" and that the "Just Ask" tier with zero config effort "directly matches what consumer users need" [Alignment, item 1].
  - **Combined evidence**: The developer perspective validates the tiers as matching real adoption patterns (try, guided, power). The consumer perspective validates that the "Just Ask" tier genuinely serves non-technical users. The decision framework's SC-1 (Non-Expert Usability) and the backward compatibility table [spec.md, L443-446] already embody this tiering, meaning the proposal aligns with an established design principle, not just reviewer preference.
  - **Confidence level**: High. The three-tier model should be treated as settled architecture. Both reviews agree on what it is and why it works; they differ only on which tier to build first.

- **"Just Ask" mode needs better handling of imperfect input**
  - **Shared position**: Both reviews identify that the proposal underspecifies what happens when "Just Ask" receives unclear, vague, or insufficient input. consumer-advocate calls vague question handling "the highest-priority missed opportunity" and recommends the system "ask one clarifying question (not five), offer to reframe the question, or explain what kinds of questions work best" [Missed Opportunities, item 1; Actionable Recommendations, item 2]. devex-advocate calls out the lack of a CI/CD non-interactive mode where the system must "fail with a non-zero exit code and structured error on missing required inputs instead of prompting" [Actionable Recommendations, item 4]. Both identify that the proposal's "Just Ask" description (L35-42) assumes clean input and provides no error handling design.
  - **Combined evidence**: The consumer perspective establishes that non-technical users are the most likely to provide vague input and the least equipped to fix it. The developer perspective establishes that programmatic consumers cannot prompt for clarification and need structured failure signals. The decision framework already has the `[CLARIFY: ...]` mechanism [spec.md, L44] for vague input in the guided workflow, proving the need is recognized but not carried through to "Just Ask" mode. Together, these perspectives demand a shared input-sufficiency layer with audience-appropriate responses.
  - **Confidence level**: High. The synthesis should require the "Just Ask" specification to include explicit behavior for vague, ambiguous, and insufficient input, with different response strategies for interactive (clarify) and non-interactive (structured error) contexts.

- **MCP "Primary Integration Path" label needs qualification**
  - **Shared position**: Both reviews take issue with the unqualified "Primary Integration Path" label for the MCP server (L74). devex-advocate argues the label is correct for developers but critiques the proposal for not backing it up with the build order -- "the build order should reflect that priority" [Actionable Recommendations, item 3]. consumer-advocate argues the label is misleading because it implies the web app is secondary: "For the non-technical users the proposal explicitly names (L18-20), the web app is the only integration path that exists" [Off-Base Assumptions, item 2]. consumer-advocate recommends "dual-primary integration paths" [Actionable Recommendations, item 6].
  - **Combined evidence**: devex-advocate accepts the MCP-as-primary framing but demands the build order match it. consumer-advocate challenges the framing itself as incomplete. Both agree the current presentation creates a hierarchy that does not serve the proposal's stated goal of reaching "everyone" (L12). The convergent recommendation is that the proposal should explicitly name both the MCP server (for developers) and the web app (for consumers) as primary paths for their respective audiences.
  - **Confidence level**: Medium. The labeling matters because it signals internal priorities. The synthesis should adopt the dual-primary framing, but the practical impact depends on whether the build order is also restructured (where both reviews agree it must be).
