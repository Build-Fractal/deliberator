# Cross-Review: devex-advocate's Review

**Cross-reviewer**: adoption-strategist
**Reviewing**: devex-advocate's initial review of spec 011 (Adoption Harness)
**Date**: 2026-03-21

---

### Dangerous Contradictions

- **Build order: infrastructure-first vs. validation-first**
  - **devex-advocate claims**: The SDK public API must be designed before any implementation begins — "it is the contract that CLI, MCP server, and web app all depend on" (Actionable Recommendations, item 1). Their recommended build order is: (1) Python engine extraction, (2) SDK with types, (3) MCP server wrapping SDK, (4) CLI wrapping SDK, (5) "Just Ask" mode (Actionable Recommendations, item 3).
  - **adoption-strategist claims**: Ship "Just Ask" as a Claude Code skill first, within the existing runtime, before any Python extraction or SDK work. "The existing runtime already supports everything needed" (Actionable Recommendations, item 1). The recommended sequence is: (1) "Just Ask" in Claude Code, (2) validate with real usage data, (3) let usage data drive subsequent build order.
  - **Why this is dangerous**: These two build orders are mutually exclusive in their first step. devex-advocate's order produces zero users until step 5 (months of SDK/engine work first). adoption-strategist's order produces users immediately but without the typed SDK foundation, risking the "leaky abstraction" devex-advocate warns about. If both positions are adopted, the team either stalls (trying to design a perfect SDK while also shipping a quick skill) or ships a quick skill that becomes technical debt the SDK must awkwardly wrap. The failure mode is classic: ship fast, then discover the quick implementation's contracts are incompatible with the SDK design, requiring a rewrite that invalidates early user integrations.
  - **Suggested resolution**: Sequence, not compromise. Ship "Just Ask" as a Claude Code skill (adoption-strategist's step 1) with the explicit constraint that it is a validation prototype, not the SDK's interface. Set a gate: after N validated uses, freeze the learnings and design the SDK API (devex-advocate's recommendation) informed by real usage patterns. devex-advocate is right that the SDK is the foundational layer; adoption-strategist is right that designing it without usage data produces the wrong API. The resolution is: validate first, then design the SDK. Neither should yield entirely — the question is sequencing, not substance.

- **MCP as primary channel vs. MCP as premature bet**
  - **devex-advocate claims**: MCP is already mature enough — "MCP is already supported by Claude Code, Cursor, Windsurf, Zed, and VS Code (via extensions). For a developer tool targeting AI-native engineers, MCP coverage is sufficient" (Off-Base Assumptions, item 2). They recommend moving MCP server to build step 3, immediately after the SDK (Actionable Recommendations, item 3).
  - **adoption-strategist claims**: "The proposal assumes MCP is mature enough and widely adopted enough to be the primary integration strategy. This is premature" (Off-Base Assumptions, item 1). The primary path for the first 100 users should be the existing Claude Code skill. MCP should be the second distribution channel, validated by user demand.
  - **Why this is dangerous**: If devex-advocate's position drives investment and MCP is indeed too niche, significant engineering effort ships to a channel with insufficient audience for validation. If adoption-strategist's position prevails and MCP is actually the right channel, delaying it misses the window when AI-native engineers are actively adding MCP tools. The two reviews make incompatible bets on the same factual question — MCP's current reach — and the build order diverges accordingly.
  - **Suggested resolution**: This is an empirical question that can be answered with data, not debate. Measure: how many active Claude Code / Cursor / Windsurf users configure custom MCP servers today? If the number is in the tens of thousands, devex-advocate is right and MCP should be prioritized. If it is in the hundreds, adoption-strategist is right and the Claude Code skill is the faster path. In the absence of data, a reasonable compromise is: ship the Claude Code skill first (days of work), then build the MCP server next (not step 5, as the proposal suggests, but not before validation either). Both reviews agree MCP should ship before the CLI — the disagreement is only about whether it ships before or after initial validation.

- **Structured output as default vs. "show the debate" as differentiator**
  - **devex-advocate claims**: All SDK methods and MCP tools should return structured JSON by default — "a Python dataclass / JSON object with fields: `recommendation`, `confidence`, `arguments_for`, `arguments_against`, `dissent`" (Actionable Recommendations, item 2). Plain-English is "a rendering of this structure, not the primary output."
  - **adoption-strategist claims**: The output must include a visible "debate transcript" showing agent positions, cross-review attacks, and resolution — "The transcript is what makes conversus visibly different from ChatGPT" (Actionable Recommendations, item 3). The differentiator is not structured data but visible multi-agent dynamics.
  - **Why this is dangerous**: These are not the same output. devex-advocate's structured JSON distills the debate into summary fields (`arguments_for`, `dissent`), which is useful for programmatic consumption but strips the adversarial process that adoption-strategist identifies as the core differentiator. If structured JSON becomes the default and the debate transcript is an afterthought, conversus loses its visible differentiation. If the verbose debate transcript is the default and structured data is secondary, programmatic integrations (CI/CD, MCP tool chaining) receive unwieldy output. The failure mode: the output is either too compressed to differentiate or too verbose to integrate.
  - **Suggested resolution**: Both are right for different audiences. The output should be layered: (1) a concise recommendation (2-3 sentences), (2) structured metadata (JSON with the fields devex-advocate specifies), and (3) the full debate transcript (the "show your work" that adoption-strategist requires). SDKs and MCP tools return structured data with a `debate_transcript` field. CLI and web outputs render the transcript by default. The structured fields and the transcript are complementary, not competing — the danger is only if one is treated as optional.

### Tensions

- **SDK-first design vs. usage-driven design**
  - **devex-advocate's position**: The SDK's public API (classes, methods, types, async support) must be specified before implementation — "designing it after the fact will produce a leaky abstraction" (Missed Opportunities, item 1; Actionable Recommendations, item 1).
  - **adoption-strategist's position**: "Let usage data — not architectural ambition — drive the subsequent build order" (Executive Summary). The API should emerge from validated usage patterns, not be designed in a vacuum.
  - **Nature of tension**: devex-advocate optimizes for long-term architectural soundness. adoption-strategist optimizes for speed to first users. Both are legitimate: premature API design locks in assumptions that usage data would have corrected, but shipping without an API design creates contracts that are expensive to change once users depend on them. This is the classic "plan vs. iterate" tension in product development.
  - **Coordination needed**: Define the boundary between "validated prototype" and "public API." The Claude Code skill can ship without a public API because it is an internal interface. The moment the Python SDK or MCP server ships to external users, devex-advocate's API design discipline becomes mandatory. The coordination rule: no external-facing surface ships without the typed API design. Internal surfaces can iterate freely.

- **CI/CD as first-class concern vs. CI/CD as premature optimization**
  - **devex-advocate's position**: CI/CD non-interactive mode is a P1 priority. The CLI needs `--non-interactive` / `--ci` flags, and SDK methods should be non-interactive by default (Actionable Recommendations, item 4). "CI/CD is a primary use case for developer tools — it must be designed in, not bolted on."
  - **adoption-strategist's position**: The review does not mention CI/CD as a priority at all. The focus is entirely on interactive, human-facing use cases — "Just Ask" mode, visible debate transcripts, shareable artifacts (Actionable Recommendations, items 1, 3, 7). The implicit position is that CI/CD adoption follows human adoption, not the reverse.
  - **Nature of tension**: devex-advocate sees conversus as a developer tool where CI/CD integration is table stakes. adoption-strategist sees it as a decision-making tool where human trust and visible differentiation matter more than automation. These are not contradictory — both will be needed eventually — but they pull the immediate build priority in different directions. Designing for CI/CD first may produce a tool optimized for headless execution that feels mechanical to interactive users. Designing for interactive use first may produce a tool that requires significant rework for CI/CD.
  - **Coordination needed**: Agree that the interactive "Just Ask" skill ships first (adoption-strategist's priority), but that when the CLI is built, it includes `--non-interactive` from day one (devex-advocate's requirement). The CI/CD mode is not a separate phase — it is a flag on the CLI that ships alongside the interactive mode. This avoids both premature CI/CD investment and the cost of retrofitting non-interactive execution later.

- **Breadth of SDK surface vs. minimal viable distribution**
  - **devex-advocate's position**: The SDK should include programmatic preset management (`conversus.presets.list()`, `.get()`, `.compose()`, `.install()`), a config builder pattern (`Config.builder().problem(...).agent(...).build()`), a dry-run/validate command, and a plugin/extension hook for custom modes (Actionable Recommendations, items 6, 7, 9, 10).
  - **adoption-strategist's position**: "Every successful developer tool (Homebrew, npm, Docker) grew by validating one channel before expanding" (Actionable Recommendations, item 2). The recommendation is to cut the web app entirely and focus on the narrowest possible surface that produces engaged users.
  - **Nature of tension**: devex-advocate's SDK vision is comprehensive and well-designed, but it describes a mature product's API, not a launch product's API. adoption-strategist would argue that building preset management, builder patterns, dry-run, and plugin systems before validating that anyone uses the core `decide` function is premature investment. devex-advocate would counter that without these features, developer adoption stalls because the tool lacks the composability engineers expect.
  - **Coordination needed**: Tier the SDK surface explicitly. Tier 1 (ships at launch): `Deliberation.run()`, `Config.from_yaml()`, structured result types. Tier 2 (ships after N users): preset management, builder pattern, validate/dry-run. Tier 3 (ships after community demand): plugin system, custom modes. devex-advocate designs the full API surface up front (types and interfaces), but only Tier 1 is implemented initially. This satisfies devex-advocate's "design before implementation" principle while respecting adoption-strategist's "validate before expanding" principle.

- **LiteLLM resolution urgency**
  - **devex-advocate's position**: The LiteLLM vs. custom provider question must be resolved decisively — commit to a thin provider interface with LiteLLM as the default implementation (Actionable Recommendations, item 8, Priority P2). "Indecision on the model layer blocks the entire extraction."
  - **adoption-strategist's position**: The review does not prioritize resolving the LiteLLM question. Instead, it recommends shipping within the existing Claude Code runtime first (Actionable Recommendations, item 1), which sidesteps the model abstraction question entirely because the current runtime uses Claude via the Agent tool.
  - **Nature of tension**: devex-advocate is solving for the Python extraction path, where model agnosticism is an architectural prerequisite. adoption-strategist is solving for immediate adoption, where model agnosticism is irrelevant because the first users are Claude Code users who already have Claude. Both are correct for their time horizon. The tension is about when this decision must be made, not what the decision should be.
  - **Coordination needed**: Agree that the LiteLLM question does not block step 1 (Claude Code skill) but must be resolved before step 2 (Python extraction). devex-advocate's thin-interface recommendation is sound and should be adopted when the extraction begins. The two reviews are actually compatible here — they just disagree on urgency because they disagree on what step 1 is.

### Safe Agreements

- **MCP server should ship before CLI**
  - **Shared position**: Both reviews agree that the proposal's build order (CLI at step 3, MCP at step 5) is wrong and should be reversed. devex-advocate: "Move MCP server to build step 3... it reaches the largest developer audience with zero behavior change — they stay in their editor" (Actionable Recommendations, item 3). adoption-strategist: "After validating 'Just Ask' in Claude Code, build the MCP server next (step 2). The CLI can come later as a convenience wrapper" (Actionable Recommendations, item 4).
  - **Combined evidence**: devex-advocate grounds this in developer behavior (editors are the natural habitat; context-switching to CLI is friction). adoption-strategist grounds this in distribution strategy (MCP puts conversus where decisions happen; CLI requires users to remember to invoke it). The decision framework's commands (`999-decision-framework/spec.md, L448-458`) map 1:1 to MCP tool signatures, making the MCP server a thin wrapper rather than a large engineering effort — a point both reviews make independently.
  - **Confidence level**: High. Both perspectives converge on the same recommendation with complementary evidence. The proposal should reorder MCP before CLI.

- **The web app is premature and should be deferred or cut**
  - **Shared position**: Both reviews argue against building the web app as part of the initial roadmap. devex-advocate: "CLI and SDK adoption always precedes web app usage for developer tools" and endorses the proposal's sequencing of CLI before web app (Alignment, item 5). adoption-strategist goes further: "Remove the web app from this proposal entirely. If adoption via Claude Code skill, MCP, and CLI validates demand from non-technical users, revisit a web app as a separate spec" (Actionable Recommendations, item 8). devex-advocate does not explicitly recommend cutting the web app but sequences it last and focuses all P1 priorities on SDK, MCP, and CLI — implicitly deprioritizing the web app.
  - **Combined evidence**: devex-advocate's evidence is that developer tools follow a CLI-then-web adoption pattern. adoption-strategist's evidence is that the web app's tech stack (Next.js + FastAPI + WebSocket + PostgreSQL) represents the highest-cost, highest-risk item with unvalidated demand. Both cite the decision framework's phased delivery model (`999-decision-framework/spec.md, L547-566`) as evidence that independent phases with clear gates produce better outcomes. Combined, the case is strong: do not invest in the web app until developer-channel adoption validates the core value proposition.
  - **Confidence level**: High. The agreement is substantive and well-evidenced from both perspectives. The web app should either be cut from this proposal or gated behind a clear adoption milestone.

- **Community presets need a seeding strategy**
  - **Shared position**: Both reviews identify that the proposal mentions community presets as a growth mechanism but provides no plan for initial content. devex-advocate: "No programmatic preset management... A developer building a CI pipeline needs `conversus.presets.list()`, `conversus.presets.get('devils-advocate')`" (Missed Opportunities, item 6). adoption-strategist: "The first 20 presets need to be built by the conversus team and cover high-value, high-frequency decisions" (Actionable Recommendations, item 5). Both cite the existing preset system in SKILL.md as the foundation.
  - **Combined evidence**: devex-advocate focuses on the API surface needed to make presets discoverable and composable programmatically. adoption-strategist focuses on the content strategy needed to bootstrap the library with useful presets before launch. These are complementary — the API without content is an empty shelf; the content without an API is hidden value. Combined, the recommendation is: seed 20 presets (adoption-strategist) and expose them through a programmatic interface (devex-advocate). The existing preset composition system (`SKILL.md, L93-168`) provides the structural foundation for both.
  - **Confidence level**: Medium. The agreement is genuine but the two reviews emphasize different aspects (API vs. content). The combined recommendation is stronger than either alone, but the prioritization within the build order is unresolved — seeding presets is a content task that can happen in parallel with engineering, while the programmatic API depends on the SDK timeline.
