# Capability Declaration: template-owner

## Core Competencies

**Mode-specific agent behavior definition.** template-owner defines how agents behave differently across cooperative, red-blue, winner-take-all, and prisoners-dilemma modes through the `templates/{mode}/` directory structure. Each mode has six to seven template files (review.md, cross-review.md, revision.md, disputes.md, synthesis.md, arbitration.md, cross-round-synthesis.md) that encode the game-theoretic framing, scoring rules, required output sections, and constraints for that mode. Evidence: the seven templates under `templates/prisoners-dilemma/` (review.md lines 7-13 define PD scoring; cross-review.md lines 8-14 define audit incentives; synthesis.md lines 43-72 define the Trust Scorecard methodology). No other component in the system defines what agents produce or how they frame their arguments.

**Output format definition.** template-owner specifies the exact section headings, ordering, and content requirements for every phase's output in every mode. Evidence: `templates/prisoners-dilemma/review.md` lines 38-89 define required sections (Core Competencies, Unique Capabilities, Shared Territory, Deferrals, Integration Surface) with precise rules for each. `templates/prisoners-dilemma/disputes.md` lines 39-95 define the Phase 4 structure (Accepted Boundaries, Disputed Boundaries, Proposed Responsibility Summary). These structured output requirements are the mechanism through which the Dispute-Parsing Subsystem can reliably extract dispute counts -- the templates produce the headings the parser expects.

**Dispute heading conventions (the stable interface contract).** template-owner produces the headings that constitute the stable interface contract described in SKILL.md line 683. The synthesis templates contain the `<!-- CONVERSUS:DISPUTES_BEGIN -->` and `<!-- CONVERSUS:DISPUTES_END -->` structural markers (e.g., `templates/prisoners-dilemma/synthesis.md` lines 97-117) and the mode-specific dispute headings (`## Disputed Boundaries` for PD, `### Disputed Risks` for red-blue, `### Remaining Disputes` for cooperative, `## Runner-Up` for winner-take-all). These markers and headings are produced by the templates -- if a template changes them, the Dispute-Parsing Subsystem breaks. template-owner is the source of truth for what these markers are and where they appear.

**Cross-round narrative framing.** template-owner defines how multi-round deliberations are synthesized through mode-specific `cross-round-synthesis.md` templates. Evidence: `templates/prisoners-dilemma/cross-round-synthesis.md` defines the complete cross-round narrative structure including Cooperation Dynamics (lines 46-60), Boundary Trajectory (lines 62-76), Final Boundary Map (lines 78-99), Disputed Boundaries (lines 101-111), and Termination Assessment (lines 113-121). This is the template created by spec 004 (FR-005, confirmed in `work_done.md` line 35). The engine merely fills variables and dispatches agents; the cross-round narrative logic is entirely template-owned.

**Phase 6 required headings.** template-owner's arbitration templates define the section headings that the engine validates after Phase 6 execution. The SKILL.md validation table (lines 587-592) explicitly states at line 594: "The headings correspond to those instructed by each mode's `templates/{mode}/arbitration.md` -- if a template's heading instructions change, update this table." This establishes a directional dependency: the templates define the headings, and the engine's validation table follows. template-owner is the authority on what headings are correct; the engine validation table is a derived artifact.

## Unique Capabilities

**Game-theoretic prompt engineering.** Only template-owner encodes the specific game theory dynamics that differentiate modes. The prisoners-dilemma review template (lines 9-13) defines the Accuracy/Value/Trust scoring model. The red-blue review template defines attacker/defender role framing. The winner-take-all synthesis template defines the ADR selection process. No other system component contains game-theoretic reasoning -- the engine is mode-agnostic, and the Dispute-Parsing Subsystem only knows headings, not game dynamics.

**Template variable contracts.** template-owner defines which `{VARIABLES}` each phase expects and how they are used in context. While the engine populates these variables (SKILL.md lines 336-377 enumerate them), only the templates define the semantic contract for how variables are consumed. For example, `{PRIOR_ROUND_SECTION}` is defined by the engine but its integration into the agent's prompt flow is a template concern (it appears in review.md templates at a specific narrative position).

**Agent constraint specification.** Only template-owner defines the behavioral constraints each agent operates under (e.g., "Write in third person", "Do not introduce new capability claims", length guidelines). These constraints shape agent behavior independent of the engine's orchestration logic.

## Shared Territory

**Phase 6 heading validation.** template-owner defines the authoritative headings in the arbitration templates. The engine (SKILL.md lines 583-594) maintains a validation table that mirrors these headings. This is shared territory where template-owner is upstream (defines) and engine-owner is downstream (validates). Relative strength: template-owner is the source of truth per SKILL.md line 594. However, a spec-level mismatch exists between the spec's FR-009 (spec.md lines 173-178) and the actual SKILL.md implementation (lines 587-592). The spec proposed `Boundary Framework, Binding Boundary Decisions, Cooperation Assessment` for PD mode; the implementation uses `Decision Framework, Binding Decisions, Revised Responsibility Map`. template-owner's actual templates (`templates/prisoners-dilemma/arbitration.md`) use `Decision Framework`, `Binding Decisions`, `Revised Responsibility Map`, and `Confidence Assessment`. The implementation followed the templates, not the spec -- which is correct behavior given the directional dependency.

**Dispute-Parsing Subsystem interface.** template-owner produces the headings and markers that the Dispute-Parsing Subsystem consumes. The engine defines the parsing rules (SKILL.md lines 656-683). This is a producer-consumer boundary: template-owner owns what is produced, engine-owner owns how it is consumed. Both must coordinate on changes -- the stable interface contract (SKILL.md line 683) exists precisely to formalize this shared boundary. Relative strength: roughly equal. Breaking changes require coordination from both sides.

**Template variable population.** The engine populates variables; templates consume them. template-owner depends on the engine providing the correct variables at the right time. The engine depends on templates using variables that it actually defines. Evidence: SKILL.md lines 336-377 (engine defines), templates use `{AGENT_NAME}`, `{TARGET_FILES}`, `{OUTPUT_PATH}`, `{ROUND}`, `{MAX_ROUNDS}`, etc. Relative strength: engine-owner is stronger here because the engine defines the available variable set. template-owner can only use what the engine provides.

## Deferrals

**Phase sequencing and round loop mechanics.** template-owner defers entirely to engine-owner. The round loop (SKILL.md lines 294-312), termination conditions (lines 461-498), lazy directory creation (lines 218-224), retroactive Round 1 move (lines 222-223), and iteration loop (lines 317-327) are pure engine concerns. Templates do not and should not encode execution order or loop logic. template-owner provides the prompts; the engine decides when and how to dispatch them.

**Config validation and parsing.** template-owner defers entirely to engine-owner. Validation rules (SKILL.md lines 170-195), preset resolution (lines 92-168), target resolution (lines 79-91), and error message formatting are engine responsibilities. The two validation rules removed by FR-001 (rounds mode restriction and arbiter mode restriction) were engine-level gates, and their removal was correctly an engine concern.

**Agent dispatch mechanics.** template-owner defers to engine-owner on how agents are launched (background vs. foreground, parallelism rules, one-agent-per-file constraint). SKILL.md lines 272-284 define the non-negotiable multi-agent rules. Templates are agnostic to dispatch mechanics.

**Dispute count computation.** While template-owner produces the headings and markers, the actual counting logic (primary: structural markers, fallback: heading-based parsing, default: return true) is engine-owned. template-owner defers to engine-owner on how dispute counts are computed from the headings template-owner produces.

## Integration Surface

**Template-to-engine interface:** Templates produce `.md` files containing `{VARIABLE}` placeholders. The engine reads these files at `templates/{mode}/{phase}.md`, substitutes all variables, and uses the result as agent prompts. The interface is the file path convention (`templates/{mode}/{phase}.md`) and the variable substitution syntax (`{VARIABLE_NAME}`).

**Template-to-Dispute-Parsing interface:** Synthesis templates produce `<!-- CONVERSUS:DISPUTES_BEGIN -->` / `<!-- CONVERSUS:DISPUTES_END -->` markers and mode-specific dispute headings. The Dispute-Parsing Subsystem reads synthesized output files and extracts dispute information using these markers. The interface is the marker syntax and heading text (the stable interface contract at SKILL.md line 683).

**Template-to-Phase-6-validation interface:** Arbitration templates instruct agents to produce specific section headings. The engine validates that the output contains these headings. The interface is the heading text, and the flow is template-defines -> engine-validates (SKILL.md line 594).

**Spec-to-template feedback loop:** Spec 004 defined functional requirements (FR-003 through FR-008) for new templates. The templates were created to satisfy those FRs. Where the spec's proposed headings (FR-009) diverged from the template implementation, the templates were treated as authoritative and the SKILL.md validation table was updated to match the templates rather than the spec. This is the correct resolution -- the spec proposes, the template implements, and the engine validates what the template actually produces.
