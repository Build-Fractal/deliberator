### Remaining Disputes

- **Dispute: Effort field enrichment depth — compact four-dimension inline vs. selective parenthetical**
  - **My claim**: My revision (New Recommendations, "Acknowledge FR-017 effort field incompleteness") adopted compliance's position that the current Effort fields are incomplete against FR-017's literal four-dimension requirement. I did not, however, endorse a specific remediation format. The scope-boundary concern is that the remedy must not degrade STATUS.md's scanability function, which is core to SC-003's "zero ambiguity about what is safe to build on" standard.
  - **Opposing position(s)**: compliance (revision, Recommendation 1 modified) proposes a compact inline format covering all four FR-017 dimensions per spec, plus a one-sentence scale definition as a secondary P2 improvement. integration (revision, Recommendation 4 modified) proposes a global scale definition plus a single parenthetical per spec covering only the most decision-relevant dimensions, explicitly rejecting the mechanical four-line breakdown. compliance assigns the four-dimension enrichment P1; integration also elevated to P1 but with a different format. The two agents agree on the gap but disagree on the remedy format.
  - **Why I will not concede**: My mandate does not extend to dictating effort field content depth — I acknowledged this in my revision (New Recommendations rationale: "effort field content depth is not a scope-boundary concern"). However, the format question has scope implications. STATUS.md is a Phase 3 deliverable. T011 (tasks.md L66) specified the effort field content that Phase 3 was required to produce. FR-017 (spec.md L242) specifies the full four-dimension requirement. There is a gap between the task description and the FR. Whether Phase 3 is obligated to close that gap, or whether it correctly implemented its task and the FR shortfall is an upstream decomposition issue, determines whether this is a Phase 3 remediation or a spec-level errata. I cannot concede a format without clarity on which obligation Phase 3 is satisfying.
  - **Counter-argument to their position**: compliance's compact inline format is a reasonable attempt to satisfy FR-017's literal text, but compliance's own revision acknowledges that the FR-017 interpretation is the crux: "The colon-and-list construction in FR-017 is enumerative." This is compliance's reading, not a settled fact. The acceptance scenario for US9 (spec.md L151) says "an estimate covers: new files, logic complexity, testing surface, and relative effort" — the same text as FR-017. But US9's verification criterion (spec.md L153) says only: "STATUS.md contains an 'Effort' field for each of the 5 specs." The verification criterion is structural presence, not dimensional completeness. The gap between US9's acceptance scenario and its verification criterion creates genuine ambiguity about whether FR-017's enumeration is a mandatory checklist or an illustrative scope. integration's selective-parenthetical approach addresses the most decision-relevant dimensions without mechanically satisfying all four, which may be the pragmatically correct reading.
  - **Proposed resolution path**: The synthesizer should decide the FR-017 interpretation question first (enumerative requirement vs. illustrative scope), then apply the format that matches. If enumerative, compliance's compact inline format satisfies the requirement while preserving scanability. If illustrative, integration's selective parenthetical is sufficient. Either way, the global scale definition (proposed by both compliance and integration) should be adopted as a P2 addition — it is uncontested and improves interpretability regardless of the per-spec format.

- **Dispute: Spec 002 Phase 4 post-condition placement — STATUS.md entry vs. gate summary**
  - **My claim**: My revision (Recommendation 1, modified) accepted P1 priority for transition criteria and framed all Phase 2 binding commitments as carrying forward into Phase 3. However, I did not address integration's Recommendation 2 (spec 002 Phase 4 re-evaluation note) in my revision because it was not raised in my cross-reviews. The question is whether STATUS.md per-spec entries should contain forward references to Phase 4 post-conditions. My mandate requires me to flag content that imports Phase 4 scope into a Phase 3 deliverable.
  - **Opposing position(s)**: integration (revision, Recommendation 2 modified) proposes adding a parenthetical to spec 002's Notes field: "(Phase 4 post-condition: re-evaluate Spec-complete label after T019 modifies Round Termination Check cross-references.)" integration assigns P1, arguing the obligation is inherited from Phase 2's binding commitments (final.md L214, P3 item 4). compliance (revision) does not address spec 002's Notes field directly but raised a concern in cross-review (Tensions, "Scope of Phase 4 cross-references in STATUS.md") that Phase 4 forward references could violate the principle that each phase produces a deliverable accurate as of its completion date.
  - **Why I will not concede**: The Phase 2 synthesis (final.md L116) established a principle: "each phase produces a deliverable accurate as of its completion date." Adding Phase 4 post-conditions to STATUS.md entries embeds temporal predicates about future work into a current-state document. The Phase 2 synthesis did record the re-evaluation obligation (final.md L214), but it recorded it in the gate summary document, not in STATUS.md itself. The re-evaluation note should live in the gate summary or a post-conditions register — not in the per-spec Notes field of STATUS.md, where it would require maintenance when T019's scope changes. This is a scope-boundary concern: Phase 3's deliverable should describe what is true now, not what Phase 4 might change.
  - **Counter-argument to their position**: integration argues the cross-reference is "informational context about the current state of the subsystem" (revision, Recommendation 1 explanation), analogous to a "Depends On" field noting a dependency. But "Depends On" describes a current structural relationship. A Phase 4 post-condition describes a future temporal event. The analogy breaks down. compliance's own cross-review raised the same concern about phase-scoped deliverables but then retreated from it. The Phase 2 synthesis principle is explicit and should apply consistently. If Phase 4 post-conditions belong in STATUS.md entries, then the principle was wrong, and every future phase's deliverables could be annotated with obligations from subsequent phases. That is a maintenance burden that scales poorly.
  - **Proposed resolution path**: Record the spec 002 re-evaluation obligation in the Phase 3 gate summary (this deliberation's synthesis output), not in STATUS.md itself. If the synthesizer determines that STATUS.md entries must contain Phase 4 cross-references, limit the convention to integration's Recommendation 1 (Dispute-Parsing heading-match cross-reference), which describes a current deficiency with a scheduled fix, and exclude the spec 002 re-evaluation note, which describes a future event that may or may not change the current label.

### Final Position Statement

**Non-Negotiables** (3 items):

1. **Phase 2 binding commitments must be implemented before the Phase 3 checkpoint can pass.** This covers transition criteria (Recommendation 1), the "Not assessed" label and spec 003 relabeling (Recommendation 2), and the compound-label permission rule (Recommendation 5). All three are recorded in the Phase 2 synthesis (final.md L186-192, L202) as P1 or binding items. Leaving any unimplemented means STATUS.md contains undefined labels, undefined label formats, or implicit transition boundaries — each of which falsifies SC-003's "zero ambiguity" standard (spec.md L265). This position is non-negotiable because I accepted the logical consequence of treating the Phase 2 synthesis as binding in my revision (Position Summary), and reversing that acceptance would re-introduce the selective-authority inconsistency that cross-review correctly identified.

2. **Phase 3 changes must be limited to STATUS.md content within the T008-T012a task scope.** My mandate is to flag modifications that fall outside the Phase 3 task descriptions or that modify content belonging to other phases. The Phase 2 binding commitments are exceptions because they are explicitly inherited obligations with documented provenance. Any other taxonomy modifications, SKILL.md changes, or spec.md edits proposed in this deliberation are out of scope for Phase 3 and should be deferred to the appropriate phase. This is non-negotiable because it is the core function of the scope-boundary role (my mandate document).

3. **STATUS.md per-spec entries must describe current state, not future-phase obligations.** Phase 4 post-conditions (such as spec 002's label re-evaluation) belong in gate summaries or post-condition registers, not in STATUS.md's per-spec Notes fields. The Phase 2 synthesis established the principle that each phase produces a deliverable accurate as of its completion date (final.md L116). Embedding temporal predicates about future phases in the current deliverable undermines this principle and creates a maintenance burden. This is non-negotiable because it is a direct application of a Phase 2 synthesis principle that all three agents accepted.

**Flexibility** (2 items):

1. **Effort field enrichment format.** I am flexible on whether the per-spec effort fields use compliance's compact four-dimension inline format or integration's selective-parenthetical format. What must be preserved: the synthesizer must decide the FR-017 interpretation question (enumerative requirement vs. illustrative scope) before mandating a format, and the chosen format must not degrade STATUS.md's quick-reference function. I will accept either format if it is grounded in a principled reading of FR-017 rather than an ad-hoc compromise.

2. **Dispute-Parsing heading-match Phase 4 cross-reference.** I am flexible on whether integration's Recommendation 1 (add T013 cross-reference to STATUS.md L93) is adopted. Integration makes a strong case that the cross-reference describes a current deficiency with a scheduled remediation, which is different from a future-phase post-condition. If the synthesizer distinguishes between "current deficiency with scheduled fix" (acceptable in STATUS.md) and "future event that may change a label" (not acceptable in STATUS.md), I can accept the heading-match cross-reference while still opposing the spec 002 re-evaluation parenthetical. What must be preserved: a clear principle distinguishing the two categories, applied consistently.
