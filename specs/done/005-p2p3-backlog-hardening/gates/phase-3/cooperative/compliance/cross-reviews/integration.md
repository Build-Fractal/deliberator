### Dangerous Contradictions

- **Effort field sufficiency standard**
  - **integration claims**: Effort estimates need a "comparative anchor" -- a one-sentence scale definition (e.g., "Small = targeted edits to existing files; Medium = new sections or modest new functionality; Large = multiple new components with cross-cutting integration") to make labels meaningful (Actionable Recommendations, item 4, Priority P2). integration's concern is that identical "Small" labels for dissimilar work (spec 001 template text vs. spec 004 CLI commands) reduce discriminating value.
  - **compliance claims**: Effort fields fail FR-017 compliance because they omit the four-dimension breakdown the FR explicitly requires: "new files, logic complexity, testing surface, and relative effort (small/medium/large)" (Missed Opportunities, item 1; Actionable Recommendations, item 1, Priority P1). The issue is not label ambiguity but structural incompleteness against the FR's "covering" clause.
  - **Why this is dangerous**: If both recommendations are implemented without coordination, one implementor adds a comparative-anchor sentence to the taxonomy section (integration's fix) while another restructures each Effort field into four sub-dimensions (compliance's fix). These are different interventions targeting different problems. Integration's fix treats effort as a relative-priority label needing calibration; compliance's fix treats effort as a multi-dimensional assessment needing structural completeness. An implementor following integration's recommendation alone would produce calibrated but still structurally incomplete fields, leaving FR-017 partially unsatisfied. An implementor following compliance's recommendation alone would produce structurally complete fields that still lack the comparative anchor. The priority gap (P2 vs. P1) compounds this: if the synthesis adopts integration's P2 framing, the four-dimension breakdown may be deprioritized, leaving a material FR-017 compliance gap.
  - **Suggested resolution**: Compliance should yield on the comparative anchor (it is a useful addition) while integration should yield on priority. The combined fix is: add the four-dimension breakdown per FR-017's explicit requirement (P1), and include a comparative-anchor sentence in the taxonomy section as a secondary improvement (P2). The four-dimension breakdown is the FR-required structure; the comparative anchor is an additional usability enhancement.

- **Phase 2 binding commitments: inherited obligation vs. informational context**
  - **integration claims**: Transition criteria should be added as a "deferred Phase 3 obligation" (Actionable Recommendations, item 6, Priority P2). integration frames this as something that the Phase 2 synthesis directed Phase 3 to do, citing final.md L200-202 and L171 ("binding commitment, not an optional suggestion"). The recommendation uses language of obligation: "T008's scope includes the taxonomy section's maintenance obligation."
  - **compliance claims**: Transition criteria are absent from the taxonomy section, and this constitutes a Phase 3 compliance gap because the Phase 2 synthesis recorded the obligation as binding for T008 (Missed Opportunities, item 6; Off-Base Assumptions, item 2). Compliance goes further, stating that the Phase 2 synthesis's "binding commitments" framing is either authoritative (in which case several Phase 2 P1 changes are outstanding obligations Phase 3 inherited) or advisory (in which case its "binding" framing is misleading).
  - **Why this is dangerous**: Both reviews agree transition criteria should be added, but they frame the obligation differently. integration treats it as a P2 recommendation -- something that "should" happen. compliance treats it as a compliance gap -- something that "must" happen because Phase 2 declared it binding. If the synthesis adopts integration's P2 framing, the transition criteria become a nice-to-have that could be deferred again. If it adopts compliance's framing, the absence is a gate-blocking deficiency. The same logic applies to the compound-label permission rule and the "Not assessed" acceptance label, both of which compliance flags as Phase 2 binding commitments that Phase 3 inherited (Actionable Recommendations, items 2 and 3, both P1). integration's review does not address these two items at all, meaning the synthesis could silently drop them if it relies solely on integration's recommendation set.
  - **Suggested resolution**: The synthesis should take an explicit position on whether Phase 2's "binding commitments" (final.md L171) carry forward as Phase 3 obligations. If they do, transition criteria are P1 (compliance's position) and the compound-label rule and "Not assessed" label are also required. If they do not, the synthesis should explain why the Phase 2 synthesis's "binding" language was incorrect or non-operative. The worst outcome is silent ambiguity where some binding commitments are honored and others are ignored without stated rationale.

- **Spec 005 risk-of-gap: tautology vs. forward reference**
  - **integration claims**: The risk-of-gap statement is "tautological" because it "describes the spec's deliverables rather than the cost of their absence" (Missed Opportunities, item 4; Off-Base Assumptions, item 1). integration also flags that the "STATUS.md lacks complete cross-spec reference information" clause is outdated because Phase 3 has already added that information (Off-Base Assumptions, item 1). Proposed fix: rewrite as a cost-of-absence statement following the pattern of specs 001-004 (Actionable Recommendations, item 3, Priority P2).
  - **compliance claims**: The risk-of-gap field is present and populated for all five specs, satisfying FR-016 and T010 at the structural level (Alignment, item 3). Compliance does not flag the spec 005 risk-of-gap content as deficient.
  - **Why this is dangerous**: integration identifies a genuine content quality issue that compliance missed. The spec 005 risk-of-gap at STATUS.md L63 says "STATUS.md lacks complete cross-spec reference information" -- but Phase 3 just added that information, making the statement factually outdated within the same document. If the synthesis follows compliance's structural-only assessment, this stale text persists, undermining the document's reliability. But integration's proposed rewrite introduces a different risk: the replacement text ("Implementors lack a single reference for cross-spec status, shared subsystem stability, and dependency ordering") describes the pre-spec-005 state, not the current state where Phase 3 has partially delivered. A risk-of-gap statement should describe what happens if the spec is never implemented, but spec 005 is already partially implemented. The correct framing needs to account for the remaining-work scope, not the full-spec scope.
  - **Suggested resolution**: Adopt integration's recommendation to rewrite the risk-of-gap as a cost-of-absence statement, but scope it to the remaining unimplemented FRs rather than the full spec. Something like: "SKILL.md Phase 6 edge cases (heading match semantics, missing document handling, overwrite behavior) remain undocumented, and the dispute-parsing subsystem lacks explicit cross-references from its consumers, increasing the risk of divergent implementations." This satisfies integration's pattern-consistency concern while avoiding the factual staleness that both the current text and integration's proposed replacement share.

### Tensions

- **Granularity of SKILL.md Structure Plan for spec 003**
  - **integration's position**: The structure plan for spec 003 (STATUS.md L76-80) lists only new sections needed but does not identify which existing sections would be modified. FR-019 requires identifying "which existing sections change and what new sections are needed." integration proposes adding explicit existing-section modification targets: Step 1, Step 4, Step 5 (Actionable Recommendations, item 5, Priority P2).
  - **compliance's position**: The SKILL.md Structure Plan covers specs 002, 003, and 004 and satisfies FR-019 and T012 at the section-existence level (Alignment, item 5). Compliance does not flag the missing existing-section analysis for spec 003.
  - **Nature of tension**: integration applies a higher fidelity standard to FR-019 than compliance does. Compliance checks that the structure plan exists with entries for all three specs; integration checks that each entry covers both halves of FR-019's requirement ("which existing sections change and what new sections are needed"). Neither is wrong -- compliance assesses structural presence, integration assesses content completeness. The tension is about what constitutes "satisfies FR-019": having an entry, or having an entry that addresses both clauses.
  - **Coordination needed**: The synthesis should establish whether FR-019 compliance requires both clauses to be addressed per spec. If so, spec 003's entry needs the existing-section analysis integration proposes. If structural presence is sufficient for Phase 3 (with detail deferred to implementation time), the current entry passes. The decision should be consistent with how the synthesis resolves the Effort field sufficiency question (same pattern: structural presence vs. content completeness).

- **Scope of Phase 4 cross-references in STATUS.md**
  - **integration's position**: STATUS.md should cross-reference Phase 4 tasks in multiple places: the Dispute-Parsing heading-match note should reference T013 (Actionable Recommendations, item 1, P1), spec 002's entry should reference T019's re-evaluation post-condition (item 2, P1), and spec 002's Effort field should note T019's planned modification (item 8, P3).
  - **compliance's position**: Compliance does not recommend any Phase 4 cross-references in STATUS.md. The review focuses on whether Phase 3's own deliverables are structurally present and FR-compliant, without assessing forward references to Phase 4.
  - **Nature of tension**: integration treats STATUS.md as a living planning document that should surface upcoming dependencies and scheduled remediations. compliance treats STATUS.md as a snapshot of Phase 3 deliverables that should be assessed against Phase 3's FR requirements. These are different document-purpose models. Integration's model makes STATUS.md more useful for implementors but introduces Phase 4 content into Phase 3's deliverable -- exactly the pattern that Phase 2's scope-boundary agent argued against (final.md L116, systemic contradiction 4). Compliance's model keeps Phase 3's deliverable self-contained but leaves implementors without forward-looking context.
  - **Coordination needed**: The synthesis should decide whether Phase 4 cross-references in STATUS.md are (a) required for SC-003's "zero ambiguity about what is safe to build on" standard, (b) helpful but optional enhancements, or (c) scope violations that import Phase 4 content into Phase 3. The Phase 2 synthesis established a principle that "each phase produces a deliverable accurate as of its completion date" with "forward-facing risks recorded as post-conditions for the relevant future phase" (final.md L116). Under that principle, integration's cross-references would be recorded in the Phase 3 gate summary rather than in STATUS.md itself.

- **Treatment of Phase 2 residuals**
  - **integration's position**: integration's review does not address the "Not assessed" label absence, the compound-label permission rule absence, or spec 003's cross-tier label reuse. These Phase 2 binding commitments are outside integration's scope as an integration checker focused on content accuracy and implementor usability.
  - **compliance's position**: The absence of "Not assessed" in the Acceptance Tier taxonomy (Actionable Recommendations, item 2, P1), the absent compound-label permission rule (item 3, P1), and spec 003's use of an undefined label (Missed Opportunities, item 5) are compliance gaps that Phase 3 inherited from Phase 2. Compliance treats these as high-impact issues.
  - **Nature of tension**: These are not contradictions -- integration simply does not address them. But the absence creates a coverage gap in the combined review set. If the synthesis weights integration's review heavily (due to its detailed content-accuracy analysis), it may not surface the Phase 2 residuals that compliance considers P1 blockers. The tension is between two legitimate review scopes: content accuracy/usability (integration) vs. FR/commitment compliance (compliance).
  - **Coordination needed**: The synthesis must ensure Phase 2 residuals are evaluated on their merits, not dropped because only one reviewer flagged them. The compound-label rule and "Not assessed" label are either (a) Phase 2 obligations that Phase 3 should have inherited, requiring immediate action, or (b) Phase 2 items that were never implemented and whose absence should be tracked but not attributed to Phase 3. The synthesis should take an explicit position.

- **Spec 001 "Depends On" field absence**
  - **integration's position**: integration does not flag the missing "Depends On" field for spec 001.
  - **compliance's position**: Spec 001 lacks a "Depends On" field, creating ambiguity about whether the dependency was assessed or simply omitted. The cross-spec dependency section shows 001 has no dependencies, but the per-spec entry -- which STATUS.md L129 calls "authoritative" -- is silent (Missed Opportunities, item 3; Actionable Recommendations, item 5, P2).
  - **Nature of tension**: This is a completeness-vs-signal-to-noise trade-off. Adding "Depends On: None (foundational)" to spec 001 eliminates ambiguity but adds a field that conveys no actionable information. Omitting it keeps the entry lean but creates the interpretive gap compliance identifies. The tension matters because it sets a precedent: must every field template be populated for every spec, or can fields be omitted when they have null values?
  - **Coordination needed**: The synthesis should decide whether STATUS.md follows a strict template (every spec has every field, even if null) or a sparse template (fields omitted when not applicable). If strict, spec 001 needs the "Depends On" line. If sparse, the convention should be documented so readers know omission means "not applicable" rather than "not assessed."
