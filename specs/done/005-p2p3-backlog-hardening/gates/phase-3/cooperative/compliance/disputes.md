### Remaining Disputes

- **Dispute: Effort field four-dimension coverage — compact inline vs. most-decision-relevant parenthetical**
  - **My claim**: Each spec's Effort field must address all four FR-017 dimensions (new files, logic complexity, testing surface, relative effort) in a compact inline format. The current fields provide only relative effort labels and summary sentences, omitting three of four required dimensions. (Revision, Recommendation 1, modified recommendation.)
  - **Opposing position(s)**: Integration (revision, Recommendation 4, modified) proposes a concise parenthetical covering "the most decision-relevant FR-017 dimensions" per spec rather than all four. Integration's example for spec 004 — "Small (discovery only) -- 3 new CLI commands, no new parsing logic, testing: command output verification" — addresses three dimensions but frames them as selective highlights, not a systematic coverage requirement. Integration elevated priority to P1 to align with my assessment but maintained that a "mechanical four-line breakdown" degrades scanability.
  - **Why I will not concede**: FR-017 (spec.md L242) uses an enumerative construction: "covering: new files, logic complexity, testing surface, and relative effort (small/medium/large)." The colon followed by a comma-separated list is a requirements enumeration, not a menu of options. An effort field that addresses "the most decision-relevant" dimensions satisfies the FR only when the most decision-relevant dimensions happen to be all four. The FR does not grant implementor discretion to select a subset. Scope-boundary's new recommendation (revision, "Acknowledge FR-017 effort field incompleteness") independently confirmed this reading: "The colon-and-list construction in FR-017 is enumerative."
  - **Counter-argument to their position**: Integration's concern about scanability is real, which is why my modified recommendation uses compact inline format rather than four separate lines. The example I provided (revision, Recommendation 1) — "Small -- New files: none; logic complexity: low (template-level instructions); testing surface: behavioral verification of template output. 2 FRs remain." — covers all four dimensions in a single line. Integration's "most decision-relevant" approach would produce effort fields of similar length but with unpredictable dimension coverage across specs. Spec 001 might mention testing surface but omit logic complexity; spec 004 might mention new files but omit testing surface. The result is that a reader comparing effort across specs cannot make apples-to-apples comparisons because each field addresses a different subset. Systematic coverage is cheaper to maintain than per-spec editorial judgment about relevance.
  - **Proposed resolution path**: Adopt the compact inline format with all four dimensions. Integration's comparative-anchor sentence (scale definition in the taxonomy section) is a complementary improvement that both agents agree on. The synthesizer should require all four dimensions in the inline format and include the scale definition. If the synthesizer judges that strict four-dimension coverage is too rigid, a minimum of three dimensions with the fourth addressed when non-obvious would be an acceptable fallback — but the default should be full coverage.

- **Dispute: Phase 2 remediation framing — prerequisite for Phase 3 checkpoint vs. Phase 3 task output**
  - **My claim**: Phase 2 binding commitments (transition criteria, "Not assessed" label, compound-label rule) must be framed as Phase 2 remediation prerequisites for Phase 3 checkpoint passage, not as Phase 3 task outputs. The obligation belongs to Phase 2; the execution happens during Phase 3 because the Phase 3 checkpoint ("complete cross-spec reference") cannot pass with undefined labels or missing transition criteria. (Revision, Recommendations 2, 3, 4, all modified with this framing.)
  - **Opposing position(s)**: Integration (revision, Recommendation 6, modified) and scope-boundary (revision, Recommendation 1, modified) both elevate transition criteria to P1 and agree the fix must happen, but neither consistently adopts the "Phase 2 remediation prerequisite" framing. Integration frames it as a "P1 priority" obligation without distinguishing between Phase 2 and Phase 3 ownership. Scope-boundary's modified recommendation says "Frame this as a Phase 2 binding commitment executed in Phase 3, categorized separately from Phase 3's own content improvements in the final synthesis priority stack" — which is close to my position but adds the "categorized separately" qualifier that could result in the Phase 2 items being listed in a separate section of the synthesis rather than integrated into the Phase 3 remediation priority list.
  - **Why I will not concede**: The framing matters for process integrity. If Phase 2 binding commitments are treated as Phase 3 task outputs, then Phase 2's synthesis authority is retroactively weakened: any binding commitment from a prior phase can be re-scoped to a later phase's task list, where it competes with that phase's own priorities and may be deprioritized. The "Phase 2 remediation prerequisite" framing preserves the binding nature of inter-phase obligations while acknowledging that the execution timing is Phase 3. This is not merely a labeling preference — it determines whether Phase 3 can claim its checkpoint is met while these items remain unimplemented.
  - **Counter-argument to their position**: Scope-boundary's "categorized separately" qualifier risks creating a two-track priority system where Phase 2 remediation items and Phase 3 content improvements are assessed independently. If the synthesis produces a single priority-ordered remediation list (which is what an implementor needs), the Phase 2 items must be interleaved with Phase 3 items at their appropriate priority level, not segregated into a separate section. The framing should be: "These are Phase 2 obligations executed during Phase 3, at the priority level the Phase 2 synthesis assigned them." Integration's simpler "P1" framing achieves the right outcome in practice but loses the attribution that ensures future phases respect prior-phase binding commitments.
  - **Proposed resolution path**: The synthesizer should adopt the "Phase 2 remediation prerequisite" framing for the three items (transition criteria, "Not assessed" label, compound-label rule) while integrating them into a single priority-ordered remediation list alongside Phase 3 content improvements. Each Phase 2 item should carry a parenthetical noting its Phase 2 origin — e.g., "(Phase 2 binding commitment, final.md L186)" — without being relegated to a separate section. This preserves both process integrity and implementor usability.

### Final Position Statement

**Non-Negotiables** (3 items):

1. **Effort fields must cover all four FR-017 dimensions.** FR-017's "covering: new files, logic complexity, testing surface, and relative effort" is an enumerative requirement, confirmed independently by compliance and scope-boundary. The compact inline format accommodates scanability without sacrificing coverage. Without this fix, SC-006(d) ("effort estimates present") is nominally satisfied but the estimates are structurally incomplete against their source FR.

2. **Phase 2 binding commitments must be implemented before Phase 3 checkpoint passage.** The three items — transition criteria (final.md L171), "Not assessed" label (final.md L186-188), and compound-label rule (final.md L192) — were unanimously or bilaterally agreed in Phase 2 and recorded as binding. A "complete cross-spec reference" (SC-003) cannot contain undefined labels, undocumented label formats, or implicit transition boundaries. All three agents now agree on the substance; the remaining question is framing, which affects process integrity for future phases.

3. **The FR-008a identifier must be retained in the maintenance note.** Integration demonstrated (revision, Recommendation 7 cross-reference) that "FR-008a" is the established identifier in tasks.md T008 (L63), T017 (L101). My withdrawal of Recommendation 7 was based on this evidence and must be respected. Scope-boundary's combined edit should adopt the trigger-scope broadening while preserving "(FR-008a)."

**Flexibility** (3 items):

1. **Effort field format details.** I am committed to four-dimension coverage but flexible on the exact inline format. If the synthesizer prefers integration's example format (e.g., "Small (discovery only) -- 3 new CLI commands, no new parsing logic, testing: command output verification") extended to systematically cover all four dimensions, that achieves the same outcome. The non-negotiable is coverage, not formatting.

2. **Spec 005 risk-of-gap exact wording.** My proposed text and integration's proposed text are substantively equivalent. Either formulation satisfies the requirement that the statement be scoped to remaining work and follow the consequence-oriented pattern of specs 001-004. The synthesizer can choose either or blend them.

3. **Maintenance note trigger-scope wording.** I proposed broadening the maintenance note to cover three trigger categories (status changes, subsystem changes, structure plan changes). Scope-boundary proposed similar but slightly different wording. Either formulation achieves the goal of covering Phase 3's living-content sections. The non-negotiable is that the trigger scope must be broader than the current "implementation or acceptance status changes" — the exact wording is flexible.
