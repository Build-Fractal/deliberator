### Dangerous Contradictions

- **Effort field remediation scope**
  - **compliance claims**: Effort fields must be expanded to include all four FR-017 dimensions ("new files, logic complexity, testing surface, and relative effort") as separate line items within each spec entry. Their Recommendation 1 proposes inline expansion: "Small -- New files: none. Logic complexity: low (template-level instructions only). Testing surface: behavioral verification of template output. 2 FRs remain..." (Actionable Recommendations, item 1).
  - **integration claims**: Effort fields need a comparative anchor -- a one-sentence preamble defining the scale (e.g., "Small = targeted edits to existing files; Medium = new sections or modest new functionality; Large = multiple new components with cross-cutting integration") rather than per-spec dimension breakdowns. My Recommendation 4 proposes adding scale definitions, not expanding each field into four sub-lines (Actionable Recommendations, item 4).
  - **Why this is dangerous**: If both are adopted, each spec's effort field would carry both a four-dimension breakdown and a reference to a global scale definition. The four-dimension breakdown per spec adds significant textual weight to STATUS.md (five specs times four dimensions = twenty additional data points in a document meant to be scannable). Meanwhile, the global scale definition makes the individual dimension breakdowns partially redundant because the scale implicitly communicates the nature of "Small" vs. "Large" work. An implementor reading the result gets two different effort signals that may conflict -- the scale says "Small = targeted edits" while the per-spec breakdown says "Logic complexity: low" which is a different axis of simplicity. The document's scan-ability degrades without a proportional gain in decision-making utility.
  - **Suggested resolution**: Compliance is correct that FR-017 textually requires four dimensions. Integration is correct that the document must remain scannable. The compromise is: add the global scale definition (integration's recommendation) and add a single parenthetical clarification to each effort field that addresses the most decision-relevant non-obvious dimension, rather than mechanically listing all four. For example, spec 004's "Small (discovery only)" could become "Small (discovery only) -- 3 new CLI commands, no new parsing logic, testing: command output verification." This satisfies FR-017's coverage requirement without inflating every entry to four lines. Compliance should yield on the mechanical four-line-per-spec format; integration should yield on adding more than just the scale definition.

- **Priority assignment of transition criteria**
  - **compliance claims**: Adding transition criteria to the taxonomy section is Priority P2, framed as a Phase 2 residual that Phase 3 inherited (Actionable Recommendations, item 4). Compliance explicitly calls this a "Phase 3 compliance gap" in Missed Opportunities (item 6), citing final.md L202-203 as a "binding commitment" for T008.
  - **integration claims**: Adding transition criteria is Priority P2, but framed as a "deferred Phase 3 obligation" rather than a compliance gap (Actionable Recommendations, item 6). My review acknowledges the Phase 2 synthesis language but does not classify the absence as a compliance failure of Phase 3 -- instead treating it as a gap that Phase 3 should close for completeness.
  - **Why this is dangerous**: The classification matters for gate passage. If transition criteria absence is a "compliance gap" (compliance's view), Phase 3 arguably fails the checkpoint. If it is a "deferred obligation" (integration's view), Phase 3 passes with a noted follow-up. An implementor receiving both signals cannot determine whether to block Phase 3 completion on this item or proceed to Phase 4.
  - **Suggested resolution**: The factual question is: does the Phase 3 checkpoint ("STATUS.md is the complete cross-spec reference with status for all 5 specs, subsystems, dependencies, risk, effort, and structure plan") explicitly require transition criteria? It does not mention transition criteria. The Phase 2 synthesis assigned this to T008, and T008's task description in tasks.md L63 does not mention transition criteria either -- it covers shared subsystems and the maintenance note. Compliance's traceability from final.md is valid but the obligation was not carried into the task decomposition. Integration should acknowledge the Phase 2 binding commitment is real; compliance should acknowledge the task decomposition did not include it, making it a spec-level gap rather than a Phase 3 execution failure. The resolution is to add it as a P1 follow-up before Phase 5 verification, without classifying Phase 3 as non-compliant.

- **FR-008a identifier treatment**
  - **compliance claims**: The "(FR-008a)" reference in STATUS.md L138 is an informal convention not traceable to the spec's FR list. Compliance recommends normalizing it to "(FR-008)" (Actionable Recommendations, item 7, Priority P3). Compliance's Missed Opportunities (item 4) flags this as an untraceable reference.
  - **integration claims**: My Alignment section (item 5) states the maintenance note "cites the correct FR" -- explicitly endorsing "FR-008a" as correct. This is because tasks.md L63 uses "FR-008a" as the task-level identifier for the maintenance obligation sub-requirement.
  - **Why this is dangerous**: If compliance's recommendation is adopted, the maintenance note changes from "(FR-008a)" to "(FR-008)". But tasks.md L63 uses "FR-008a" as a distinct identifier. An implementor searching for "FR-008a" in STATUS.md after the normalization would find nothing, breaking traceability between tasks.md and STATUS.md. Conversely, if integration's position stands, a reader searching spec.md for "FR-008a" finds nothing, breaking traceability in the other direction.
  - **Suggested resolution**: This is a minor formatting issue with a clear resolution: keep "(FR-008a)" in STATUS.md because it matches tasks.md's convention, but add a parenthetical in the taxonomy section or a footnote: "FR-008a refers to the maintenance sub-requirement within FR-008 (spec.md L215)." This preserves both traceability chains. Compliance should yield on the normalization; both agents should agree on adding a traceability note.

### Tensions

- **Phase 2 synthesis authority**
  - **compliance's position**: The Phase 2 synthesis is authoritative, and items labeled "binding commitments" are outstanding obligations that Phase 3 inherited. Compliance's Off-Base Assumptions section (item 2) explicitly interrogates whether the synthesis is authoritative or advisory, and concludes that if it is authoritative, several Phase 2 items (compound-label rule, transition criteria, "Not assessed" label) are unaddressed compliance gaps.
  - **integration's position**: My review references the Phase 2 synthesis for specific items (transition criteria in Recommendation 6, spec 002 re-evaluation in Recommendation 2) but treats each on its merits rather than asserting blanket authority of the synthesis document. I do not classify unimplemented Phase 2 items as Phase 3 compliance gaps.
  - **Nature of tension**: These positions pull in different directions on how strictly to enforce inter-phase continuity. Compliance's approach creates a strict chain of accountability where any unfulfilled Phase 2 commitment automatically becomes a Phase 3 failure. Integration's approach evaluates each phase against its own checkpoint and task list, treating inter-phase commitments as context rather than binding constraints.
  - **Coordination needed**: The deliberation framework needs a clear rule: do phase gate reviews evaluate against (a) the phase's own task list and checkpoint, or (b) all accumulated obligations from prior phases? If (a), compliance's Phase 2 residual items should be logged as spec-level debt but not block Phase 3. If (b), the Phase 3 task list was itself incomplete for not incorporating Phase 2 commitments, and the corrective action is updating tasks.md, not failing Phase 3.

- **Spec 003 "Not assessed" label**
  - **compliance's position**: This is a high-impact compliance issue -- spec 003 uses "Not started" in the Acceptance Tier, which is an Implementation Tier label, violating FR-009. Compliance recommends adding "Not assessed" to the Acceptance Tier taxonomy and relabeling spec 003 (Actionable Recommendations, item 2, Priority P1).
  - **integration's position**: My review does not flag the spec 003 acceptance label at all. The Two-tier taxonomy section in my Alignment (item 1) notes the taxonomy "cleanly separates Implementation Tier and Acceptance Tier with three labels each" without identifying the cross-tier label reuse for spec 003.
  - **Nature of tension**: Compliance identified a genuine inconsistency that integration missed. This is not a disagreement -- it is an asymmetry in coverage. The tension is whether this is a Phase 3 issue or a Phase 2 residual. Compliance classifies it as a Phase 2 residual with ongoing compliance impact. If it is a Phase 2 issue, then Phase 3's review scope does not naturally cover it, which explains why integration's review did not flag it.
  - **Coordination needed**: Integration should incorporate compliance's finding. The "Not assessed" label should be added to the taxonomy and spec 003 relabeled. The question of which phase owns the fix is secondary to getting it done -- it should be added to the Phase 3 follow-up actions regardless of whether Phase 3 is "blamed" for the gap.

- **Shared subsystem entry consistency**
  - **compliance's position**: The Structural Markers subsystem entry lacks a Location field, creating inconsistency with the other two entries (Missed Opportunities, item 2). Compliance recommends adding a Location field pointing to specific SKILL.md sections (Actionable Recommendations, item 6, Priority P3).
  - **integration's position**: My Alignment section (item 2) states the three entries "each specify Location, Stability, Consumers, Interface, and Notes -- the exact fields T008 requires." This is factually inaccurate for Structural Markers, which has Stability and sub-entries but no Location, Interface (as a labeled field), or Notes field. My review over-generalized the structure.
  - **Nature of tension**: Integration's review has a factual error that compliance's review correctly identifies. The tension is not in recommendations but in the accuracy of the baseline assessment. If integration's review is taken at face value, the subsystem entries appear uniform and complete. If compliance's review is taken at face value, there is a consistency gap that should be addressed.
  - **Coordination needed**: Integration should correct its Alignment claim. The three entries do not share identical field structures -- Dispute-Parsing has Location/Stability/Consumers/Interface/Notes; Structural Markers has Stability plus sub-entries; Template Conventions has Stability/Consumers/Interface. Compliance's recommendation to add a Location field to Structural Markers is reasonable, though the broader issue is that no formal field schema was specified for subsystem entries, making "inconsistency" a judgment call rather than a compliance failure.

- **Spec 005 risk-of-gap characterization**
  - **compliance's position**: Not explicitly flagged as an issue. Compliance's Alignment section (item 3) lists spec 005's risk-of-gap as satisfying FR-016 alongside the other four specs, without noting the tautological nature of spec 005's statement.
  - **integration's position**: My Missed Opportunities (item 4) flags spec 005's risk-of-gap as "self-referential without actionable consequence" -- it describes what spec 005 delivers rather than the cost of its absence. I recommend rewriting it to follow the consequence pattern used by specs 001-004 (Actionable Recommendations, item 3, Priority P2).
  - **Nature of tension**: Compliance and integration disagree on whether spec 005's risk-of-gap statement is adequate. Compliance considers it sufficient for FR-016 compliance ("What happens if this spec is never implemented?" -- "Documentation gaps persist" is technically an answer). Integration considers it inadequate because it does not follow the consequence-oriented pattern of the other four entries, reducing its comparative value for prioritization.
  - **Coordination needed**: This is a quality-versus-compliance trade-off. FR-016 does not prescribe a format for risk-of-gap statements, so compliance's "technically satisfies" reading is defensible. Integration's "the field loses its comparative value" reading is also defensible from a SC-003 perspective (the document should enable prioritization decisions). The resolution should be to rewrite the field because SC-003's "zero ambiguity" standard is best served by consistent formatting across entries, even if FR-016 is technically satisfied.

### Safe Agreements

- **Transition criteria are missing and needed**
  - **Shared position**: Both reviews identify that STATUS.md's taxonomy section lacks transition criteria for when a spec moves between acceptance tiers. Compliance flags this in Missed Opportunities (item 6) and Actionable Recommendations (item 4). Integration flags this in Actionable Recommendations (item 6). Both cite the Phase 2 final synthesis (final.md L152-156, L200-203) as the source of this obligation, and both propose the same dual-condition formulation: (a) all documented gaps resolved and (b) all acceptance scenarios verified.
  - **Combined evidence**: Compliance traces the obligation through the Phase 2 synthesis's "binding commitment" language and T008's scope. Integration traces it through the Phase 2 convergence point and the practical need for an explicit boundary between Feature-complete and Spec-complete. The convergence from different analytical angles (compliance traceability vs. integration practicality) strengthens the case that this is not a nice-to-have but a structural requirement for the taxonomy to function.
  - **Confidence level**: High. Both reviews independently arrived at the same proposed text, the same source citations, and the same rationale. This should be implemented.

- **Phase 4 cross-references needed in shared subsystem entries**
  - **Shared position**: Both reviews identify that the Dispute-Parsing Subsystem entry's heading-match gap note (STATUS.md L93) is incomplete without a forward reference to Phase 4's remediation. Compliance does not raise this specific cross-reference issue but does flag the heading-match semantics as part of the broader FR-017 context. Integration raises this as the highest-priority recommendation (Actionable Recommendations, item 1) and also flags the spec 002 re-evaluation post-condition (Actionable Recommendations, item 2). Compliance's Alignment section (item 1) notes the stagnation-detection limitation is present but does not flag the missing forward reference.
  - **Combined evidence**: Integration provides the stronger evidence here: the heading-match gap has a scheduled fix (T013 in Phase 4), but STATUS.md does not mention it, so an implementor encountering the gap has no way to know whether to wait or work around it. Compliance's observation that the note exists and satisfies T008's specification confirms the structural requirement is met -- the gap is in actionability, not compliance. Together, the evidence shows the entry is compliant but not sufficient for SC-003's "zero ambiguity" standard regarding what is safe to build on.
  - **Confidence level**: High. The cross-reference is a small textual addition with high information value. The only question is whether it belongs in the shared subsystem entry or in the spec 005 gaps field -- both reviews implicitly place it in the subsystem entry, which is correct because that is where an implementor looking at the subsystem will read it.

- **Effort estimates need more structure**
  - **Shared position**: Both reviews identify that the current effort fields are insufficient. Compliance flags the missing four-dimension breakdown required by FR-017 (Missed Opportunities, item 1; Actionable Recommendations, item 1). Integration flags the lack of comparative anchoring and the identical "Small" labels for dissimilar work (Missed Opportunities, item 3; Actionable Recommendations, item 4). Both agree the current fields are populated but inadequately structured for their purpose.
  - **Combined evidence**: Compliance provides the FR-compliance argument (FR-017 says "covering" four dimensions, the current fields cover only one). Integration provides the practical argument (identical labels for different work types reduce discriminating value). These are complementary: the FR requires more dimensions, and the practical need confirms those dimensions would actually improve the document's utility rather than just satisfying a checkbox. The combined evidence is stronger than either alone because it shows the gap matters both formally and functionally.
  - **Confidence level**: High. The disagreement (noted in Dangerous Contradictions above) is about the format of the fix, not whether a fix is needed. Both reviews agree the current state is inadequate.

- **Spec 005 gap field accuracy concern**
  - **Shared position**: Both reviews raise concerns about the accuracy of spec 005's entry. Compliance questions whether the four gaps listed (FR-007, FR-011, FR-014, FR-015) are complete, noting that tasks.md shows additional remaining FRs (Actionable Recommendations, item 9). Integration's Off-Base Assumptions (item 1) flags the risk-of-gap statement as outdated -- written before Phase 3 work was done and not updated afterward. Both are concerned that spec 005's self-entry does not accurately reflect its own state at the time of reading.
  - **Combined evidence**: Compliance's concern is about gap completeness (are all unimplemented FRs listed?). Integration's concern is about temporal accuracy (does the risk statement reflect the post-Phase-3 state?). Together, these suggest the T012a entry was written as a point-in-time snapshot that was not revisited after the Phase 3 tasks it was part of were completed. This is a process issue -- T012a should have been the last task in Phase 3, executed after T008-T012, so it could reflect the enriched state.
  - **Confidence level**: Medium. The gap list may be intentionally scoped to SKILL.md-targeted FRs (as compliance notes), in which case the incompleteness is a design choice, not an error. But the risk-of-gap staleness (integration's finding) is more clearly incorrect. The combined finding warrants verification but not necessarily a P1 fix.
