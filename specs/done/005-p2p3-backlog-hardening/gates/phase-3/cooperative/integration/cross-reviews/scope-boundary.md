# Cross-Review of scope-boundary's Phase 3 Review

**Reviewed agent**: scope-boundary

### Dangerous Contradictions

- **Transition criteria priority versus Phase 4 cross-reference priority**
  - **scope-boundary claims**: Transition criteria are the highest-priority missing item (Recommendation 1, P1): "Add transition criteria to STATUS.md... Phase 2's synthesis recorded this as a binding commitment for T008 implementation" (Actionable Recommendations, item 1). scope-boundary assigns this P1 and frames it as a Phase 2 binding obligation that Phase 3 failed to deliver.
  - **integration claims**: Transition criteria are important but ranked P2 (Recommendation 6): "Add transition criteria as deferred Phase 3 obligation... Priority: P2." Meanwhile, integration assigns P1 to the Dispute-Parsing heading-match Phase 4 cross-reference (Recommendation 1): "Add Phase 4 cross-reference to Dispute-Parsing heading-match note (Priority: P1)."
  - **Why this is dangerous**: If both priority schemes are adopted without resolution, the implementor receives conflicting signals about what to fix first. scope-boundary's framing treats transition criteria as a blocking obligation inherited from Phase 2 that gates Phase 3's checkpoint claim. integration's framing treats the Dispute-Parsing cross-reference as the highest-risk content gap because it affects implementors building on the subsystem right now. If an implementor can only address one item before shipping Phase 3, these reviews point in opposite directions. More concretely: adopting scope-boundary's P1 for transition criteria could delay the Dispute-Parsing cross-reference that integration considers the most operationally urgent fix for preventing divergent parsing implementations (integration Recommendation 1, Risk if ignored).
  - **Suggested resolution**: Both items should be P1, but the justifications differ. scope-boundary's case for transition criteria rests on procedural obligation (Phase 2 binding commitment). integration's case for the Dispute-Parsing cross-reference rests on operational risk (implementors building on an unspecified foundation). The resolution is to accept both as P1 with a clarifying note: transition criteria are P1 because of the binding commitment; the Dispute-Parsing cross-reference is P1 because of the implementor-facing risk. Neither review's P1 item should be demoted to accommodate the other.

- **Spec 003 acceptance label — Phase 2 inheritance versus Phase 3 scope**
  - **scope-boundary claims**: The spec 003 "Not started" label is a P1 issue that Phase 3 should fix (Recommendation 2, P1; Recommendation 8, P1): "Two options: (a) add 'Not assessed' to the Acceptance Tier taxonomy at L20 and update L45, or (b) flag as a Phase 2 incomplete that blocks Phase 3's checkpoint claim. I recommend option (a)." scope-boundary explicitly recommends Phase 3 make this change.
  - **integration claims**: integration's review does not identify the spec 003 label as a Phase 3 issue at all. The "Not started" label at STATUS.md L45 is not mentioned in integration's Missed Opportunities or Actionable Recommendations. integration's review implicitly treats the taxonomy as Phase 2's deliverable and evaluates Phase 3's additions (risk, effort, subsystems, dependencies, structure plan) against it.
  - **Why this is dangerous**: scope-boundary recommends Phase 3 modify the taxonomy section by adding a third acceptance label. integration's review operates on the assumption that the taxonomy section is Phase 2's output and Phase 3 should not modify it. If scope-boundary's recommendation is adopted, Phase 3 would be retroactively fixing Phase 2 deliverables, which changes the boundary between phases. If integration's silence is taken as implicit approval of the current taxonomy, the undefined "Not started" label persists and undermines SC-003's "zero ambiguity" requirement. The contradiction is not about whether the fix is needed (both would likely agree it is) but about whether Phase 3 is the right phase to make it, and whether it is in-scope for the Phase 3 gate review at all.
  - **Suggested resolution**: Acknowledge this as a Phase 2 implementation gap that Phase 3 inherited. The most practical path is scope-boundary's option (a) — fix it now — but frame it explicitly as a Phase 2 remediation being executed during Phase 3, not as Phase 3 expanding its own scope. This preserves the phase boundary principle while fixing the real problem.

- **Maintenance note scope — narrow is correct versus narrow is incomplete**
  - **scope-boundary claims**: The maintenance note at L138 is too narrow (Missed Opportunities, item 6; Recommendation 6, P3): "Phase 3 added sections (Shared Subsystems, Structure Plan) that are also living content... none of these would trigger the maintenance obligation as currently worded." scope-boundary recommends broadening the note to cover subsystem stability changes, consumer changes, and structure plan updates.
  - **integration claims**: integration's review marks the maintenance note as aligned (Alignment, item 5): "The maintenance note... is present and cites the correct FR. This is a direct implementation of the FR-008a requirement from T008." integration does not flag the scope of the maintenance note as a problem.
  - **Why this is dangerous**: If scope-boundary's recommendation to broaden the maintenance note is adopted, the obligation expands beyond what FR-008a specifies. If integration's assessment stands, the maintenance note remains narrow and sections added by Phase 3 (subsystems, structure plan) have no formal maintenance trigger. The specific failure mode: an implementor changes a subsystem's stability (e.g., Dispute-Parsing moves from "Stable" to "Evolving" after Phase 4's T013) but does not update STATUS.md because the maintenance note only references "implementation or acceptance status changes." The document becomes stale in exactly the sections Phase 3 was designed to add.
  - **Suggested resolution**: scope-boundary's observation is correct — the maintenance note's scope does not cover Phase 3's additions. integration's assessment is technically accurate — the note does implement FR-008a as written. The resolution is to broaden the note as scope-boundary recommends (Recommendation 6), but at P3 priority rather than P1, since the risk of subsystem-level staleness is lower than the risk of label-level staleness. FR-008a's language is narrower than the document's needs, and the maintenance note should exceed the minimum FR requirement.

### Tensions

- **Depth of Phase 2 accountability versus Phase 3 forward focus**
  - **scope-boundary's position**: scope-boundary dedicates significant attention to Phase 2 deliverables that were not completed: the "Not assessed" label (Missed Opportunities, items 3-4; Off-Base Assumptions, item 1; Recommendations 2 and 8), the compound-label permission rule (Missed Opportunities, item 5; Recommendation 5), and the transition criteria (Missed Opportunities, item 1; Recommendation 1). Four of eight recommendations address Phase 2 gaps.
  - **integration's position**: integration focuses almost entirely on Phase 3's own content quality: whether risk-of-gap statements describe consequences (Missed Opportunities, item 4), whether effort estimates have comparative anchors (Missed Opportunities, item 3), whether the structure plan identifies existing sections that change (Missed Opportunities, item 5). Only one of eight recommendations (Recommendation 6, transition criteria) addresses a Phase 2 gap.
  - **Nature of tension**: scope-boundary reviews Phase 3 partly as an audit of whether Phase 2's obligations were carried forward. integration reviews Phase 3 as a standalone content quality assessment. Both are legitimate: scope-boundary's mandate includes flagging acceptance label and taxonomy changes, which naturally extends to checking whether Phase 2's taxonomy changes were actually implemented. integration's mandate is content accuracy and actionability. The tension is that scope-boundary's Phase 2 accountability items could dominate the remediation effort, leaving integration's content quality items under-resourced.
  - **Coordination needed**: The final synthesis should separate Phase 2 remediation items (taxonomy label, compound-label rule, transition criteria) from Phase 3 content improvements (risk-of-gap rewording, effort anchors, structure plan specificity, cross-references). Each category should have its own priority stack. This prevents Phase 2 debt from crowding out Phase 3 quality work, and prevents Phase 3 quality work from being used as an excuse to defer Phase 2 obligations.

- **Spec 005 SKILL.md Structure Plan — completeness versus task fidelity**
  - **scope-boundary's position**: The SKILL.md Structure Plan should include spec 005 (Missed Opportunities, item 6; Recommendation 7, P3): "Spec 005 has more pending SKILL.md work than any other spec... An implementor consulting the Structure Plan for guidance before Phase 4 would not see spec 005's SKILL.md changes listed."
  - **integration's position**: integration does not flag the absence of spec 005 from the structure plan. integration's review assesses the structure plan entries that exist (Missed Opportunities, item 5 focuses on spec 003's specificity) but does not question which specs are included.
  - **Nature of tension**: scope-boundary argues from completeness — the structure plan should cover all specs with pending SKILL.md work. integration's silence implicitly accepts that T012 (tasks.md L67) specifies "specs 002, 003, 004" and the plan is faithful to its task definition. These pull in different directions: scope-boundary wants the document to serve the implementor's full needs, even if that exceeds the task spec; integration accepts the task scope as given and assesses quality within it.
  - **Coordination needed**: The synthesis should decide whether T012's scope ("specs 002, 003, 004") is a deliberate boundary or an oversight. If deliberate (spec 005's SKILL.md changes are already detailed in tasks.md L86-90), note that the structure plan defers to the task list for spec 005. If an oversight, add spec 005 as scope-boundary recommends. The resolution depends on whether the structure plan is meant to be exhaustive (all pending SKILL.md work) or scoped (only specs whose SKILL.md integration requires advance planning for structural changes).

- **"Depends On" field consistency — structural completeness versus information value**
  - **scope-boundary's position**: Specs 001 and 004 should have explicit "Depends On" fields with "(none -- foundational)" and "(none -- self-contained engine)" respectively (Missed Opportunities, items 2-3; Recommendations 3-4, P2).
  - **integration's position**: integration notes that the dependency graph at L106-129 correctly includes all specs and their dependencies (Alignment, item 3) but does not flag the missing "Depends On" fields in the per-spec entries for 001 and 004.
  - **Nature of tension**: scope-boundary prioritizes structural completeness — every per-spec entry should have the same fields, even when the value is "none." integration prioritizes information value — the dependency graph provides the cross-cutting view and the per-spec entries are authoritative (STATUS.md L129). The tension is between form (uniform field presence) and function (information is already accessible). Adding "(none -- foundational)" to spec 001 adds no new information; it just makes the entry structurally parallel with the others.
  - **Coordination needed**: This is a low-stakes tension. If the implementor-orientation test (SC-003) is applied strictly — "can an implementor determine dependencies by reading a single spec entry" — then scope-boundary's recommendation improves the document. If the test is applied practically — "can an implementor determine dependencies from STATUS.md" — the dependency graph already satisfies it. The synthesis should decide which standard to apply and document it for future entries.

- **Spec 002 effort "None" versus Phase 4 T019 dependency — explicit caveat versus cross-phase purity**
  - **scope-boundary's position**: scope-boundary does not flag the spec 002 effort field's "No remaining work" statement as problematic. The review mentions spec 002's "Spec-complete" label in the context of Phase 2 inheritance (Missed Opportunities, items 3-4) but does not connect the effort field to Phase 4's T019.
  - **integration's position**: integration explicitly flags this (Off-Base Assumptions, item 2; Recommendation 8, P3): "The effort field's 'None' is accurate only if T019 is considered a spec 005 task, not a spec 002 task. This distinction should be made explicit."
  - **Nature of tension**: integration wants the effort field to carry a caveat about T019's cross-spec impact. scope-boundary's implicit position (by not flagging it) is that spec 002's effort is correctly "None" because T019 is a spec 005 task. Both are defensible, but they create different expectations for an implementor reading spec 002's entry. integration's caveat preserves cross-spec awareness; scope-boundary's silence preserves the principle that each spec's effort field reflects only its own remaining work.
  - **Coordination needed**: The synthesis should establish whether effort fields are spec-scoped (only the spec's own remaining work) or impact-scoped (including cross-spec modifications). The convention choice determines whether integration's Recommendation 8 applies or not. If spec-scoped, "None" is correct and no caveat is needed. If impact-scoped, caveats are needed for any spec that Phase 4 modifies.

### Safe Agreements

- **Dispute-Parsing Subsystem heading-match gap is the most significant content issue**
  - **Shared position**: Both reviews identify the Dispute-Parsing Subsystem's unspecified heading-match semantics as a material content gap. scope-boundary notes it under Missed Opportunities (item 1 is the transition criteria, but the heading-match issue surfaces in Recommendations 1 and 7 as dependencies). integration makes it the lead finding (Executive Summary, most important recommendation; Missed Opportunities, item 1; Recommendation 1, P1).
  - **Combined evidence**: scope-boundary's evidence comes from the Phase 2 synthesis obligation path — the heading-match gap is connected to what Phase 2 recorded and Phase 3 should carry forward. integration's evidence comes from the implementor-facing risk path — an implementor building on the subsystem has no way to know whether to wait for the fix or work around it (integration Missed Opportunities, item 1). The two perspectives converge: the gap is both procedurally significant (unmet obligation) and operationally dangerous (divergent implementations).
  - **Confidence level**: High. The gap is factually present in STATUS.md L93, the remediation path is clear (cross-reference T013), and both reviews independently identify it as material. The Phase 2 synthesis (final.md L212-213) also records a related post-condition for Phase 4.

- **Spec 005 risk-of-gap statement is not actionable in its current form**
  - **Shared position**: Both reviews identify a problem with spec 005's risk-of-gap statement at STATUS.md L63. scope-boundary flags that the statement contains a forward reference to STATUS.md itself that "warrants scrutiny" (Executive Summary) and notes the self-referential nature throughout. integration identifies the statement as "self-referential without actionable consequence" (Missed Opportunities, item 4) and "tautological... it describes the spec's deliverables rather than the cost of their absence." integration's Recommendation 3 (P2) proposes a rewrite.
  - **Combined evidence**: scope-boundary approaches this from a scope-boundary lens — the risk-of-gap statement references STATUS.md, which is the document it lives in, creating a self-referential quality that undermines its value as an external reference. integration approaches from a content quality lens — the statement does not follow the consequence-based pattern established by specs 001-004 (compare spec 003's "Users must manually configure conversus.yml" at STATUS.md L48 with spec 005's deliverable-listing at L63). Both lines of reasoning reach the same conclusion: the statement needs rewriting.
  - **Confidence level**: High. The gap is clear, both reviews identify it through independent reasoning, and integration provides a concrete rewrite (Recommendation 3) that scope-boundary's analysis supports.

- **STATUS.md achieves its primary orientation goal for implementors**
  - **Shared position**: Both reviews affirm that STATUS.md, despite its gaps, functions as a useful cross-spec reference. scope-boundary states "the current STATUS.md is mostly well-bounded. The additions stay within their designated file, do not redefine Phase 2's taxonomy, and do not touch SKILL.md" (Executive Summary). integration states "the current STATUS.md is well-structured and largely achieves its goal... An implementor new to conversus could orient themselves from STATUS.md alone for most purposes, satisfying SC-003" (Executive Summary).
  - **Combined evidence**: scope-boundary validates the structural discipline — Phase 3 stayed in its lane, editing only STATUS.md and not encroaching on SKILL.md or the taxonomy. integration validates the content quality — the taxonomy section, shared subsystem entries, dependency graph, and structure plan are all present and substantively correct (Alignment, items 1-5). Together, these assessments confirm that the document is both structurally sound (scope-boundary) and substantively useful (integration). The identified gaps are improvements to an already-functional document, not indictments of a broken one.
  - **Confidence level**: Medium. Both reviews qualify their approval with significant gap lists. scope-boundary has 8 recommendations; integration has 8 recommendations. The agreement is that the document works, not that it is finished. The confidence is medium rather than high because both reviews identify gaps that affect SC-003 — notably the Dispute-Parsing cross-reference and the spec 005 risk-of-gap statement — meaning the "zero ambiguity" standard is not yet met even though the practical orientation standard is.
