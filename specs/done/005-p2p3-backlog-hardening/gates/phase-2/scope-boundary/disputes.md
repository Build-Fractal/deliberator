### Remaining Disputes

- **Dispute: Compound implementation labels vs. normalization to "Partially-complete"**
  - **My claim**: Spec 004's compound implementation label ("Implementation-complete (core) / Not started (discovery)") should be normalized to "Partially-complete" with subsystem detail moved into the notes/gaps field. This preserves the three-value controlled vocabulary defined at STATUS.md L9-13 (Revision, New Recommendation).
  - **Opposing position(s)**: taxonomy-reviewer (Revision, Recommendation 5) and consistency-checker (Revision, Recommendation 2) both converged on explicitly permitting compound labels in the taxonomy section, constrained to use only existing tier values as components. taxonomy-reviewer proposed adding a rule: "Specs with independently-implementable subsystems may use compound labels composed of existing tier values." consistency-checker adopted the same position, calling it the "cooperative resolution."
  - **Why I will not concede**: The taxonomy section at STATUS.md L9-13 defines exactly three implementation-tier values. A compound label is not one of those three values — it is an ad-hoc formatting convention that happens to reference them. Permitting compound labels in Phase 2 adds a structural extension to the taxonomy that FR-012 does not specify. FR-012 (spec.md L225) requires establishing and documenting a two-tier status convention with two acceptance labels; it says nothing about extending the implementation tier's vocabulary format. Phase 2's scope is T006 (define the acceptance convention) and T007 (apply labels). Adding a compound-label permission rule to the Implementation Tier section is taxonomy enrichment — it changes what the taxonomy permits, which is a definitional expansion, not a label application. This expansion is defensible but belongs in Phase 3 alongside other STATUS.md structural enrichment (T008-T012), not in Phase 2's minimal taxonomy definition.
  - **Counter-argument to their position**: taxonomy-reviewer and consistency-checker argue compound labels "preserve information" that "Partially-complete" loses. This is true but mislocated. The information is not lost — it moves to the notes field, exactly where spec 001 already places its gap details (STATUS.md L33). The notes field exists precisely to carry detail that the label alone cannot. Furthermore, adding a compound-label rule in Phase 2 creates a precedent that Phase 3's T012a (adding spec 005) must follow. If spec 005 also has subsystem variance, should it also use a compound label? The rule, once introduced, requires enforcement guidance that Phase 2 is not scoped to provide. "Partially-complete" requires no new rules — it uses the existing vocabulary as-is.
  - **Proposed resolution path**: The synthesizer should normalize spec 004 to "Partially-complete" for Phase 2, ensuring the taxonomy's controlled vocabulary is consistently applied in the same pass that adds the acceptance tier. If the project wants compound labels, the compound-label permission rule should be introduced in Phase 3 (T008 or T012a), where it can be designed alongside subsystem documentation and applied with full knowledge of spec 005's structure. This sequences the change correctly: define vocabulary first (Phase 2), extend vocabulary format second (Phase 3).

- **Dispute: Transition criteria belong in Phase 3, not Phase 2**
  - **My claim**: Transition criteria ("A spec transitions from feature-complete to spec-complete when...") are operational process rules that define when labels change, not what labels mean. They belong alongside FR-008's maintenance obligation in Phase 3's T008, not in the Phase 2 taxonomy section (Revision, Recommendation 4 disposition — scope-boundary's cross-review argument accepted by taxonomy-reviewer).
  - **Opposing position(s)**: consistency-checker (Revision, Recommendation 5) maintains that transition criteria should be added to the taxonomy section in Phase 2, arguing they are "definitional, not enrichment" and citing scope-boundary's cross-review concession that "A one-sentence transition rule that clarifies when labels change is defensibly part of defining those labels." consistency-checker proposes the dual-condition formulation: "A spec transitions from feature-complete to spec-complete when (a) all documented gaps in its Gaps field are resolved and (b) all acceptance scenarios defined in its spec.md are verified as satisfied."
  - **Why I will not concede**: My cross-review concession was that a one-sentence transition rule is "defensible" — not that it is correct for Phase 2. taxonomy-reviewer (Revision, Recommendation 4) explicitly accepted my phase-boundary argument and refiled transition criteria as a Phase 3 input for T008: "Phase 2's task descriptions (tasks.md L44-45) focus on 'add two-tier acceptance convention' (T006) and 'apply acceptance labels' (T007). Neither task mentions transition rules." taxonomy-reviewer further stated: "The phase placement changes; the substance does not." If the taxonomy-reviewer — the agent whose mandate most naturally covers definitional completeness — agrees that transition criteria belong in Phase 3, the scope-boundary argument is reinforced, not weakened. The tasks.md checkpoint at L47 says "Two-tier convention defined and applied to all 4 specs." Transition criteria are neither a definition of a label nor an application of a label to a spec. They are a process rule governing label changes over time.
  - **Counter-argument to their position**: consistency-checker argues that transition criteria are "definitional." But the distinction between "what a label means" (definitional) and "when a label changes" (operational) is real and consequential. The acceptance tier definitions at STATUS.md L19-20 are static descriptions of states. A transition rule is a temporal predicate about when one state becomes another. Static state descriptions are Phase 2 scope (T006). Temporal transition rules are Phase 3 scope (T008, which explicitly operationalizes FR-008's maintenance obligation). Conflating them expands Phase 2's footprint beyond what tasks.md specifies. The substance of the dual-condition rule is sound — the dispute is purely about phase placement.
  - **Proposed resolution path**: The synthesizer should defer transition criteria to Phase 3, recording consistency-checker's dual-condition formulation as the agreed substance to be added during T008. This preserves the content while respecting the phase boundary. If the synthesizer places it in Phase 2, the rule must be limited to exactly the one-sentence dual-condition formulation with no additional elaboration — and it should be noted that this is a scope expansion beyond what T006/T007 specify.

- **Dispute: FR-023 gap characterization revision in Phase 2**
  - **My claim**: The current STATUS.md L32 characterization of FR-023 ("output validation — SKILL.md validation logic exists but template-level heading instructions pending") is adequate for Phase 2. Revising the parenthetical to add Phase 4 cross-references (T013, heading match semantics) imports Phase 4 awareness into Phase 2's deliverable (Revision, original position on FR-023 scope).
  - **Opposing position(s)**: consistency-checker (Revision, Recommendation 4) proposes revising STATUS.md L32's FR-023 parenthetical to: "FR-023 (output validation — SKILL.md validation check exists; heading match semantics and template-level instructions pending; see T013)." consistency-checker assigns P2 priority and argues "If Phase 2 wrote the text, Phase 2 should fix it."
  - **Why I will not concede**: The text at STATUS.md L32 was written to satisfy FR-013 (spec.md L226), which says: "FR-023 (output validation — SKILL.md validation logic exists but template-level heading instructions are pending)." The current STATUS.md text is a near-verbatim implementation of FR-013. Revising it to add "heading match semantics" and "see T013" goes beyond what FR-013 specifies and introduces forward references to Phase 4 tasks. Phase 2's mandate is to define and apply labels per FR-012 and FR-013 — not to prospectively enrich gap descriptions with cross-phase dependency information. The enrichment is useful but belongs in Phase 4 when T013 actually implements FR-007, at which point the gap characterization should be updated to reflect the completed work.
  - **Counter-argument to their position**: consistency-checker's argument that "Phase 2 wrote the text, Phase 2 should fix it" assumes the text is wrong. But the text implements FR-013 as specified. The "fix" consistency-checker proposes is not correcting an error — it is adding information that FR-013 does not require. Adding Phase 4 task cross-references to a Phase 2 deliverable creates a maintenance burden: if T013's scope changes, the Phase 2 text must be retroactively updated. This is exactly the kind of forward-looking enrichment that taxonomy-reviewer (Revision, Recommendation 3) correctly deferred: "defer this to Phase 4 when T013 actually implements FR-007."
  - **Proposed resolution path**: The synthesizer should leave STATUS.md L32 as-is for Phase 2, consistent with FR-013's specification. Record that the FR-023 parenthetical should be updated as a Phase 4 post-condition after T013 completes. taxonomy-reviewer's revised Recommendation 3 already supports this deferral.

### Final Position Statement

**Non-Negotiables** (3 items):

1. **The "Not assessed" label must be added to the acceptance tier and applied to spec 003 in Phase 2.** This is the single most consequential finding across all three reviews. Without it, the Phase 2 checkpoint claim that "STATUS.md taxonomy is authoritative" (tasks.md L47) is false — the taxonomy uses an undefined label for spec 003 (STATUS.md L41). All three reviewers agree unanimously. (spec.md FR-012; STATUS.md L41; tasks.md L47.)

2. **Spec 004 must have enumerated acceptance gaps added in Phase 2.** The taxonomy definition of "Feature-complete" (STATUS.md L19) explicitly states "acceptance criteria gaps remain," and spec 001 sets the enumerated-gaps precedent at STATUS.md L32. Spec 004 using the same label without enumerated gaps means the convention is defined but not uniformly applied. The Phase 2 checkpoint requires application "to all 4 specs." (tasks.md L47; STATUS.md L19, L32, L46-48.)

3. **Phase 2 must not modify SKILL.md.** SKILL.md changes belong to Phase 4 (T013-T015, T019). Any SKILL.md modification during Phase 2 would violate the phase boundary and invalidate Phase 4's assumptions about the file's starting state. This is a structural verification, not a content judgment. (tasks.md L44-45 scope T006 and T007 to STATUS.md; tasks.md L74-91 scope SKILL.md edits to Phase 4.)

**Flexibility** (3 items):

1. **Compound implementation labels vs. normalization.** I recommend normalizing spec 004 to "Partially-complete" in Phase 2 and deferring the compound-label permission rule to Phase 3. However, if the synthesizer judges that permitting compound labels in Phase 2 is more practical, I can accept that outcome provided: (a) the rule constrains compound labels to use only existing tier values as components, and (b) the rule is kept to a single sentence without elaboration that would constitute enrichment beyond taxonomy definition.

2. **Transition criteria phase placement.** I recommend deferring transition criteria to Phase 3 (T008). If the synthesizer places them in Phase 2, I can accept the dual-condition formulation from consistency-checker's revision, provided it is limited to exactly one sentence and does not expand into process guidance that belongs with FR-008's maintenance obligation.

3. **FR-023 gap characterization.** I recommend leaving STATUS.md L32 as-is for Phase 2, consistent with FR-013's specification. If the synthesizer judges that adding "heading match semantics" and a T013 cross-reference is warranted, I can accept it provided the addition is factual (not speculative about Phase 4 outcomes) and is recorded as requiring update after T013 completes.
