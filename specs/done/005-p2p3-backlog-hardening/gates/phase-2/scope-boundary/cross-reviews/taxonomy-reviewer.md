### Dangerous Contradictions

- **Priority divergence on spec 004 gap documentation**
  - **taxonomy-reviewer claims**: Recommendation 2 (Priority: P1) states that adding explicit acceptance gaps to spec 004 is critical: "If gaps remain, they must be documented for the label to be meaningful. Spec 001 sets the precedent." (Actionable Recommendations, item 2)
  - **scope-boundary claims**: Recommendation 2 (Priority: P2) identifies the same issue but at lower priority: "Consistency across specs prevents the convention from being applied rigorously to some specs and loosely to others." (Actionable Recommendations, item 2)
  - **Why this is dangerous**: If the synthesis adopts taxonomy-reviewer's P1, the spec 004 gap documentation becomes a blocking issue for Phase 2 gate passage. If it adopts scope-boundary's P2, it is deferred or treated as non-blocking. The implementor receives conflicting signals about whether Phase 2 can close without this fix. A P1 label implies the gate should not pass; a P2 label implies it can pass with the issue noted.
  - **Suggested resolution**: scope-boundary should yield to P1 here. The reasoning is straightforward: the taxonomy definition of "Feature-complete" explicitly states "acceptance criteria gaps remain," and spec 001 sets an enumerated-gaps precedent at STATUS.md L32. Spec 004 using the same label without enumerated gaps is an internal inconsistency within the very file Phase 2 produces. This is a taxonomy-completeness issue, not a STATUS.md-enrichment issue, so it belongs in Phase 2 scope.

- **Scope classification of transition rules**
  - **taxonomy-reviewer claims**: Recommendation 4 (Priority: P2) proposes adding transition criteria to the taxonomy section: "A spec transitions from feature-complete to spec-complete when all documented gaps are resolved and all acceptance scenarios in the spec pass." (Actionable Recommendations, item 4). This is presented as a taxonomy gap that Phase 2 should address.
  - **scope-boundary claims**: The review does not raise transition rules at all. The scope-boundary mandate defines Phase 2 as "taxonomy definitions and per-spec acceptance labels" (Executive Summary) and flags anything beyond that as Phase 3 leakage. Transition criteria define when labels change, which is an operational process rule, not a taxonomy definition.
  - **Why this is dangerous**: If taxonomy-reviewer's recommendation is adopted, Phase 2's scope expands to include operational process rules (when to change labels), not just static definitions (what the labels mean). This sets a precedent that the taxonomy section can grow to include governance rules, which blurs the Phase 2/Phase 3 boundary. Phase 3's T008 already includes a maintenance obligation ("STATUS.md MUST be updated when any spec's implementation or acceptance status changes" per FR-008). Adding transition criteria in Phase 2 partially duplicates Phase 3 content.
  - **Suggested resolution**: taxonomy-reviewer should yield on placing this in Phase 2. Transition criteria are valuable but belong in Phase 3 alongside FR-008's maintenance obligation (T008 in `tasks.md` L63). The taxonomy section should define labels, not the process for moving between them. taxonomy-reviewer could refile this as a Phase 3 recommendation without losing the substance of the observation.

- **Recommendation to verify spec 002's "Spec-complete" label**
  - **taxonomy-reviewer claims**: Recommendation 6 (Priority: P2) suggests verifying that spec 002's "Spec-complete" label is justified, citing T019's future behavioral changes: "If T019 (Phase 4) changes parsing behavior and this invalidates one of spec 002's acceptance criteria, the 'spec-complete' label becomes false."   - **scope-boundary claims**: The review accepts spec 002's "Spec-complete" label without challenge (Alignment, bullet 3): "Spec 002 is labeled 'Spec-complete,' which is correct — all 36 FRs are represented in SKILL.md and the spec's acceptance criteria are met."
  - **Why this is dangerous**: If the synthesis follows taxonomy-reviewer, Phase 2 must now audit spec 002's acceptance scenarios against Phase 4's planned changes (T019) before passing the gate. This pulls Phase 4 analysis into Phase 2, violating the phase boundary. If the synthesis follows scope-boundary, the label stands unchallenged, but taxonomy-reviewer has identified a real risk: T019 could invalidate the label. The contradiction is about whether Phase 2 must account for future phase impacts on current labels.
  - **Suggested resolution**: Compromise. Phase 2 should not block on this, but the observation should be recorded as a risk note for Phase 4. When T019 executes, the implementor should re-evaluate spec 002's acceptance status. scope-boundary's position (label is correct now) and taxonomy-reviewer's position (label may become incorrect after T019) are both valid for their respective time horizons. The synthesis should note this as a Phase 4 post-condition check, not a Phase 2 blocking issue.

### Tensions

- **Scope of "Interpreting the Two Tiers" section — dependency sentence**
  - **taxonomy-reviewer's position**: Recommendation 8 (Priority: P3) explicitly addresses the dependency sentence in STATUS.md L24, acknowledges the scope-boundary agent may flag it, and recommends retaining it: "it is a natural part of explaining orthogonality and does not encroach on Phase 3's structural content." (Actionable Recommendations, item 8)
  - **scope-boundary's position**: Recommendation 6 (Priority: P3) confirms the section is "minimal and necessary" and explicitly approves retention: "No change needed. The section is minimal and necessary." (Actionable Recommendations, item 6). However, the review also notes: "expansion belongs in a separate document, not in this section."
  - **Nature of tension**: Both reviews approve the current content, but from different frames. taxonomy-reviewer proactively defends the dependency sentence as taxonomy-clarifying. scope-boundary approves the section as-is but establishes a boundary against future expansion. The tension is about the principle, not the current state: taxonomy-reviewer sees the dependency sentence as part of the taxonomy's explanatory core, while scope-boundary sees it as at the outer edge of what Phase 2 should contain.
  - **Coordination needed**: The synthesis should adopt both positions: retain the dependency sentence (both agree), and establish a marker that any future additions to this section require scope-boundary justification (scope-boundary's defensive recommendation). No conflict in practice, but the principle should be recorded so Phase 3 does not silently expand the section.

- **"Not started" label — definition wording**
  - **taxonomy-reviewer's position**: Recommendation 1 proposes: "Not started: No acceptance criteria have been evaluated. The spec has no implementation to assess." (Actionable Recommendations, item 1)
  - **scope-boundary's position**: Recommendation 1 proposes: "Not started: No acceptance criteria have been evaluated. The spec's features are not yet implemented." (Actionable Recommendations, item 1)
  - **Nature of tension**: The difference is subtle but meaningful. "The spec has no implementation to assess" implies the label is contingent on implementation status (no implementation = nothing to evaluate). "The spec's features are not yet implemented" describes the cause but does not make the label contingent on the implementation tier. taxonomy-reviewer's framing creates a dependency between the acceptance label and the implementation label — if a spec has partial implementation, "Not started" might not apply even if no acceptance criteria have been evaluated. scope-boundary's framing is more independent, consistent with the taxonomy's orthogonality principle (STATUS.md L22-24).
  - **Coordination needed**: Adopt scope-boundary's wording or a neutral variant: "No acceptance criteria have been evaluated." The second sentence can be dropped entirely since it introduces an unnecessary causal explanation. The orthogonality section already establishes that the tiers are independent — the "Not started" definition should not reintroduce coupling.

- **Whether to add "In progress" / "Partially feature-complete" acceptance label**
  - **taxonomy-reviewer's position**: Recommendation 7 (Priority: P3) proposes adding a third operational label: "In progress" or "Partially feature-complete" to handle spec 005's eventual state when it has some implementation but an unstable gap list. (Actionable Recommendations, item 7)
  - **scope-boundary's position**: The review does not raise this. The scope-boundary mandate restricts Phase 2 to the labels defined in FR-012, which specifies exactly "feature-complete" and "spec-complete." Adding a label that FR-012 does not define would be an embellishment.
  - **Nature of tension**: taxonomy-reviewer is forward-looking (Phase 3 will need this label for spec 005), while scope-boundary is strict-present (Phase 2 implements FR-012 as written). Both are valid perspectives. The tension is between taxonomy completeness (covering all future states) and specification fidelity (implementing exactly what the FR defines).
  - **Coordination needed**: Defer to Phase 3. When T012a adds spec 005 to STATUS.md, the implementor will face this labeling question. At that point, the taxonomy can be extended if needed. Adding it now in Phase 2 is premature — it solves a problem that Phase 3 has not yet encountered, and it introduces a label that FR-012 does not define.
