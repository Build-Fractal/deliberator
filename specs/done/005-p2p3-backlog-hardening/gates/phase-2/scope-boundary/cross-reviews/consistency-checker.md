### Dangerous Contradictions

- **Acceptance tier label for unimplemented specs: "not-assessed" vs. "Not started"**
  - **consistency-checker claims**: "Add a third acceptance-tier label ('not-assessed') ... Apply this to spec 003 and to spec 004's discovery component. Alternatively, add a scoping rule: 'Acceptance labels apply only to specs with at least Partially-complete implementation status.'" (Actionable Recommendations #1, and Missed Opportunities #1: "The acceptance tier needs either a third value ... or an explicit rule that acceptance-tier labels do not apply.")
  - **scope-boundary claims**: "Add 'Not started' to acceptance tier taxonomy ... Add `- **Not started**: No acceptance criteria have been evaluated. The spec's features are not yet implemented.` to the Acceptance Tier list (after 'Spec-complete,' L20)." (Actionable Recommendations #1)
  - **Why this is dangerous**: Both reviews agree the problem is real — STATUS.md L41 uses an undocumented label in the acceptance tier. But the proposed solutions are incompatible. consistency-checker proposes either a new label named "not-assessed" or a scoping rule that removes acceptance labels entirely from unimplemented specs. scope-boundary proposes legitimizing the existing "Not started" label by adding it to the taxonomy. If the synthesis adopts "not-assessed" while STATUS.md already says "Not started" for spec 003, the label mismatch persists. If the synthesis adopts the scoping rule (no acceptance label when implementation is "Not started"), then spec 003's acceptance column must be blank or marked "N/A," which contradicts scope-boundary's recommendation to define "Not started" as a valid acceptance value. The failure mode is that one reviewer's fix is adopted in the taxonomy definition while the other's is adopted in the per-spec entries, leaving the taxonomy and its application inconsistent.
  - **Suggested resolution**: The core agreement is strong: an undocumented label is in use and must be resolved. The simplest cooperative resolution is to adopt "Not assessed" as the label name (consistency-checker's terminology is more precise — "Not started" risks confusion with the implementation tier's identical label) and apply it to spec 003 and spec 004's discovery component (both reviews agree these are the affected entries). scope-boundary should yield on the label name; consistency-checker should yield on the scoping-rule alternative, which adds complexity by making the acceptance tier conditionally applicable rather than universally applicable.

- **Scope of spec 004's compound implementation label**
  - **consistency-checker claims**: "Normalize spec 004's compound implementation label" as a P1 recommendation — either relabel spec 004 as "Partially-complete" or explicitly permit compound labels in the taxonomy. (Actionable Recommendations #2; Missed Opportunities #5: "This inconsistency undermines the taxonomy's value — if compound labels are permitted, the tier is no longer a controlled vocabulary.")
  - **scope-boundary claims**: scope-boundary's review does not flag the compound implementation label as a problem. The review notes spec 004's acceptance label ambiguity (Missed Opportunities #2) and recommends gap documentation for spec 004 (Actionable Recommendations #2), but does not address the implementation tier's "Implementation-complete (core) / Not started (discovery)" format as a taxonomy violation.
  - **Why this is dangerous**: consistency-checker identifies a genuine taxonomy consistency issue that scope-boundary missed entirely. If the synthesis does not address this, the implementation tier taxonomy (STATUS.md L9-13) claims three values while the actual entries use a fourth format. This is exactly the kind of controlled-vocabulary violation that scope-boundary's own mandate is designed to catch — the convention must match the spec exactly. The failure mode is that Phase 3 inherits an implementation tier that is already inconsistent, and T012a (adding spec 005) has no guidance on whether compound labels are permitted.
  - **Suggested resolution**: scope-boundary should acknowledge this as a valid finding that falls within its enforcement mandate. The resolution should follow consistency-checker's Option (a): relabel spec 004's implementation tier as "Partially-complete" and move the core/discovery split into the gaps or notes field. This preserves the three-value controlled vocabulary without information loss.

- **No additional contradictions identified.** The remaining differences between the two reviews are tensions rather than direct contradictions.

### Tensions

- **Priority assignment for spec 004 acceptance gap documentation**
  - **consistency-checker's position**: Labels the spec 004 acceptance gap documentation as P2 (Actionable Recommendations #3), noting that "an implementor reading STATUS.md gets precise guidance for spec 001 and vague guidance for spec 004."
  - **scope-boundary's position**: Also labels spec 004 acceptance gap documentation as P2 (Actionable Recommendations #2), with nearly identical rationale: "Consistency across specs prevents the convention from being applied rigorously to some specs and loosely to others."
  - **Nature of tension**: While both reviews agree on priority and the problem, they disagree on what content the gap documentation should contain. consistency-checker recommends referencing user stories and acceptance scenarios ("US-3 through US-6 acceptance scenarios are not testable"), while scope-boundary recommends referencing FRs ("discovery commands (FR-022-024) represent the acceptance criteria gap"). The acceptance tier is defined in terms of acceptance criteria, not FRs — but FR-013 sets the precedent of using FRs as gap identifiers. This tension reflects a deeper ambiguity that consistency-checker explicitly calls out (Actionable Recommendations #8: "FRs and acceptance scenarios are different constructs") but scope-boundary does not address.
  - **Coordination needed**: The synthesis must decide whether gap documentation references FRs, acceptance scenarios, or both. consistency-checker's Recommendation #8 (document the relationship between FRs and acceptance scenarios) would resolve this by making the convention explicit. scope-boundary should support this recommendation even though it did not originate it.

- **Depth of FR-023 gap characterization**
  - **consistency-checker's position**: Recommends revising STATUS.md L32 to distinguish between (a) the validation logic check (exists), (b) heading match semantics per FR-007 (not yet in SKILL.md), and (c) template-level heading instructions (pending). This is Actionable Recommendations #4, priority P2.
  - **scope-boundary's position**: scope-boundary's review does not flag the FR-023 characterization as imprecise. The Alignment section (item 2) notes that "The gaps text matches the spec nearly verbatim" and treats FR-023's current description as adequate.
  - **Nature of tension**: consistency-checker is applying a higher precision standard to gap documentation than scope-boundary. consistency-checker cross-references SKILL.md L581-582 and spec 005 FR-007 to identify a sub-gap that scope-boundary's review does not surface. From scope-boundary's perspective, this level of detail risks exceeding Phase 2's scope — FR-007 is a Phase 4 task (T013), and enriching gap documentation with Phase 4 cross-references could be seen as Phase 3 content leaking backward. But from consistency-checker's perspective, the gap characterization is already in STATUS.md and is simply imprecise.
  - **Coordination needed**: The synthesis should determine whether improving FR-023's gap text is a Phase 2 correction (fixing an imprecise label that Phase 2 created) or a Phase 3 enrichment (adding cross-spec dependency detail that T009 or T010 would naturally provide). If Phase 2 wrote the text, Phase 2 should fix it. scope-boundary should not block this correction on scope grounds as long as the fix does not introduce Phase 3 structural elements (subsystem tracking, dependency maps).

- **Scope of Phase 2 review: SKILL.md cross-verification depth**
  - **consistency-checker's position**: Extensively cross-references SKILL.md content (L34-35, L186-193, L249, L286-305, L453-475, L496-521, L581-582, L641-668, L692-704) to verify that STATUS.md labels are justified. Recommends spot-checking spec 002's 18 acceptance scenarios against SKILL.md implementation (Actionable Recommendations #6).
  - **scope-boundary's position**: Confirms "No SKILL.md modifications" occurred (Alignment item 4) and recommends verifying via git diff that SKILL.md was not modified (Actionable Recommendations #7). Does not cross-verify label accuracy by reading SKILL.md content in depth.
  - **Nature of tension**: consistency-checker treats Phase 2 review as requiring substantive verification that labels are correct (reading SKILL.md to check whether "Spec-complete" is truly justified). scope-boundary treats Phase 2 review as requiring structural verification that no unauthorized changes occurred and that labels use defined taxonomy values. These are different review depths. consistency-checker's approach is more thorough but risks pulling Phase 3 verification work (T008's subsystem tracking, T009's dependency map) into Phase 2. scope-boundary's approach is cleaner on boundaries but could pass a gate where labels are formally correct but substantively wrong.
  - **Coordination needed**: The synthesis should establish the verification standard for Phase 2: does the gate check that labels are (a) syntactically valid (defined in taxonomy) and (b) applied to all specs, or does it also check (c) substantively accurate? consistency-checker's Recommendation #6 (verify spec 002's "Spec-complete" label) is a reasonable ask but may need to be flagged as a Phase 3 prerequisite rather than a Phase 2 blocker.

- **Acceptance label transition criteria**
  - **consistency-checker's position**: Recommends defining transition criteria ("A spec transitions from feature-complete to spec-complete when all acceptance scenarios defined in its spec.md are verified as satisfied"), rated P2 (Actionable Recommendations #5).
  - **scope-boundary's position**: Does not address transition criteria. The review focuses on whether the current labels are defined and applied, not on when they change.
  - **Nature of tension**: consistency-checker is proposing that Phase 2's taxonomy include lifecycle rules (when labels change), while scope-boundary's mandate focuses on static correctness (are the labels defined and applied correctly right now). Transition criteria are arguably Phase 3 content — they are process guidance that informs how STATUS.md is maintained over time, which aligns with FR-008's "MUST be updated when any spec's implementation or acceptance status changes." But consistency-checker places this in Phase 2 because the taxonomy section is Phase 2's deliverable.
  - **Coordination needed**: If transition criteria are added to the taxonomy section, they must be minimal (one sentence, as consistency-checker proposes) to avoid expanding the taxonomy section beyond its Phase 2 scope. scope-boundary should evaluate whether the proposed sentence fits within "taxonomy definitions" or is "STATUS.md enrichment" that belongs in Phase 3. A one-sentence transition rule that clarifies when labels change is defensibly part of defining those labels.

### Safe Agreements

- **Undocumented acceptance label is the highest-priority issue**
  - **Shared position**: Both reviews identify the "Not started" acceptance label for spec 003 (STATUS.md L41) as the most critical finding. consistency-checker calls it "the single most consequential definitional gap" (Off-Base Assumptions #1) and rates the fix as P1 (Actionable Recommendations #1). scope-boundary calls it the "most important recommendation" (Executive Summary) and also rates it P1 (Actionable Recommendations #1).
  - **Combined evidence**: consistency-checker provides the theoretical argument — the tiers are described as orthogonal (STATUS.md L5), so labels from one tier should not transfer to the other without explicit definition. scope-boundary provides the practical argument — "Any future reviewer applying the convention strictly will flag this as a gap, recreating the 'labeling disagreement' FR-012 was designed to resolve" (Actionable Recommendations #1, Risk if ignored). Together, these establish both that the gap violates the taxonomy's design principles and that it will cause real problems downstream.
  - **Confidence level**: High. This is the strongest agreement in the cross-review. The only coordination needed is on the label name ("not-assessed" vs. "Not started"), which is addressed in Dangerous Contradictions #1.

Together, these provide both the mandate (scope-boundary) and the content (consistency-checker) for the fix.
