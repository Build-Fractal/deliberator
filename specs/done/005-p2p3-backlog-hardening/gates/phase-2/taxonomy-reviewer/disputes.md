### Remaining Disputes

- **Dispute: Spec 004 compound implementation label — permit vs. normalize**
  - **My claim**: Permit compound labels in the Implementation Tier section of the taxonomy, constrained to use only existing tier values as components. The taxonomy note would read: "Specs with independently-implementable subsystems may use compound labels composed of existing tier values to distinguish subsystem status (e.g., 'Implementation-complete (core) / Not started (discovery)'). Each component must use a defined implementation-tier label." (Revision, Recommendation 5.)
  - **Opposing position(s)**: scope-boundary's revision (New Recommendations, "Normalize spec 004's compound implementation label") proposes the opposite: relabel spec 004 to "Partially-complete" and move the core/discovery detail into a notes field. scope-boundary argues that "an authoritative taxonomy whose own entries violate its controlled vocabulary is not authoritative." consistency-checker's revision (Recommendation 2) agrees with my position — explicitly permit compound labels, constrained to existing tier values.
  - **Why I will not concede**: Normalizing to "Partially-complete" destroys information that the taxonomy exists to provide. STATUS.md is the single document an implementor reads to determine what is safe to build on (SC-003, spec.md L265). If spec 004's entry says "Partially-complete" and the reader must then find the notes field to learn that core is complete and discovery is not started, the status label no longer answers the implementor's question at a glance. The whole point of the implementation tier is to communicate implementation state — a compound label using defined tier values does this more precisely than a lossy summary. The "Partially-complete" label already exists for specs where subsystems are not independently implementable; compound labels serve the distinct case where they are. Furthermore, STATUS.md L46 already uses this compound format — scope-boundary's proposal would change a working entry to satisfy a formalism that the taxonomy can instead accommodate with a one-sentence rule.
  - **Counter-argument to their position**: scope-boundary frames this as a "controlled-vocabulary violation," but the proposed rule does not violate the controlled vocabulary — it extends it through composition of existing terms. Each component of the compound label ("Implementation-complete," "Not started") is a defined tier value. The rule explicitly constrains compounds to use only defined values, preventing ad-hoc terms. scope-boundary's analogy to the acceptance tier is also misplaced: the acceptance tier had an undefined label ("Not started" used without a taxonomy definition), which is a genuine vocabulary violation. Spec 004's compound label uses two defined values in a structured format — it is a formatting question, not a vocabulary question. Normalizing to "Partially-complete" also creates a problem for Phase 3's T012a: spec 005 will likely have subsystem-level variance (STATUS.md work may be further along than SKILL.md work), and without compound-label guidance, T012a has no precedent to follow.
  - **Proposed resolution path**: The synthesizer should adopt the compound-label permission rule with the constraint that only defined tier values may appear as components. This is the position shared by taxonomy-reviewer and consistency-checker (bilateral agreement). If scope-boundary's concern is that the taxonomy must explicitly define what it permits, the compound-label rule satisfies that concern — it makes the format explicit rather than implicit. The one-sentence addition to the Implementation Tier section closes the gap without information loss.

- **Dispute: Transition criteria placement — Phase 2 taxonomy section vs. Phase 3 maintenance note**
  - **My claim**: Transition criteria belong in Phase 3, alongside T008's maintenance obligation (FR-008). The criteria should read: "A spec transitions from feature-complete to spec-complete when all documented gaps are resolved. Gaps are considered resolved when their corresponding acceptance scenarios pass." This is a Phase 3 input, not a Phase 2 deliverable. (Revision, Recommendation 4.)
  - **Opposing position(s)**: consistency-checker's revision (Recommendation 5) places the transition criteria in the Phase 2 taxonomy section itself, at P2 priority. consistency-checker argues: "A one-sentence transition rule that clarifies when labels change is defensibly part of defining those labels," citing scope-boundary's concession on this point. consistency-checker's formulation is: "A spec transitions from feature-complete to spec-complete when (a) all documented gaps in its Gaps field are resolved and (b) all acceptance scenarios defined in its spec.md are verified as satisfied."
  - **Why I will not concede**: Phase 2's task descriptions (tasks.md L44-45) scope T006 as "add two-tier acceptance convention" and T007 as "apply acceptance labels." Neither task mentions transition rules. The Phase 2 checkpoint (tasks.md L47) says "Two-tier convention defined and applied to all 4 specs." Defining when labels change is operationally distinct from defining what labels mean. The taxonomy section in its current form (STATUS.md L15-20) defines two static states; adding a transition rule changes the section's character from definitions to process guidance. Phase 3's T008 explicitly adds a maintenance note (tasks.md L63: "This document MUST be updated when any spec's implementation or acceptance status changes"), which is the natural anchor for transition criteria. Placing transition criteria in Phase 2 would add content to a phase whose tasks are already marked complete (T006 and T007 are checked off in tasks.md L44-45), requiring reopening completed work.
  - **Counter-argument to their position**: consistency-checker cites scope-boundary's concession that a transition rule is "defensibly part of defining those labels." But scope-boundary's actual revision text (Recommendation dispositions) does not include transition criteria in any surviving or new recommendation — scope-boundary neither endorsed nor adopted consistency-checker's placement. The concession was that it is defensible, not that it is correct. The substance of the dual-condition formulation is agreed upon by all three agents; only the placement is in dispute. Placing it in Phase 3 costs nothing — T008 has not been implemented yet — while placing it in Phase 2 reopens completed tasks.
  - **Proposed resolution path**: The synthesizer should record the agreed dual-condition formulation as a Phase 3 input for T008. If the synthesizer judges that the taxonomy section must include transition criteria for the Phase 2 checkpoint to be "authoritative," then consistency-checker's formulation should be used, but tasks.md should note that T006 was reopened for this addition. The substance is not in dispute; only the phase boundary is.

- **Dispute: FR-023 gap characterization enrichment — Phase 2 fix vs. Phase 4 deferral**
  - **My claim**: The FR-023 parenthetical in STATUS.md L32 is adequate for Phase 2. The heading-match semantics dependency (FR-007, implemented in T013) should be reflected in the FR-023 gap characterization only when T013 is complete in Phase 4. Filing this as a Phase 4 post-condition avoids editing STATUS.md for a dependency that has not been implemented. (Revision, Recommendation 3.)
  - **Opposing position(s)**: consistency-checker's revision (Recommendation 4) proposes revising the FR-023 parenthetical now to: "FR-023 (output validation — SKILL.md validation check exists; heading match semantics and template-level instructions pending; see T013)." consistency-checker argues this is a within-document precision issue: "If Phase 2 wrote the text, Phase 2 should fix it."
  - **Why I will not concede**: The current parenthetical — "output validation — SKILL.md validation logic exists but template-level heading instructions pending" — accurately describes the gap as of Phase 2. Adding "heading match semantics" and a cross-reference to T013 introduces a forward reference to Phase 4 work that does not yet exist. FR-013 (spec.md L226) defines the gap as "FR-023 (output validation — SKILL.md validation logic exists but template-level heading instructions are pending)." STATUS.md L32 matches this definition verbatim. The parenthetical is not imprecise — it is correctly scoped to what FR-013 specifies. Enriching it with Phase 4 context is useful but not a Phase 2 obligation.
  - **Counter-argument to their position**: consistency-checker's "if Phase 2 wrote the text, Phase 2 should fix it" principle is reasonable in general but proves too much here. Phase 2 wrote the text to match FR-013. FR-013 does not mention heading match semantics or T013. Fixing the text to include information beyond FR-013's scope is enrichment, not correction. The P2 priority consistency-checker assigns is also disproportionate — this is a parenthetical refinement, not a gate-blocking issue.
  - **Proposed resolution path**: Accept consistency-checker's proposed wording as a Phase 4 post-condition — when T013 implements FR-007, the FR-023 gap characterization should be updated in the same pass. If the synthesizer prefers to apply the enrichment now, consistency-checker's wording is acceptable, but priority should be P3 (documentation improvement), not P2.

### Final Position Statement

**Non-Negotiables** (3 items):

1. **The "Not assessed" label must be added to the acceptance tier and applied to spec 003.** Without this, the taxonomy uses an undefined label ("Not started" in the acceptance tier at STATUS.md L41), and the Phase 2 checkpoint's claim that "STATUS.md taxonomy is authoritative" is false. All three agents agree; this is unanimous convergence with no residual dispute. (STATUS.md L15-20; FR-012; tasks.md L47.)

2. **Spec 004 must have explicit gap documentation at P1 priority.** The taxonomy defines "feature-complete" as having "acceptance criteria gaps remain" (STATUS.md L19). Spec 001 demonstrates the expected format: label plus enumerated gaps (STATUS.md L32). Spec 004 uses the same label without enumerated gaps (STATUS.md L46-48). The Phase 2 checkpoint requires the convention to be "applied to all 4 specs" (tasks.md L47), and incomplete application to spec 004 means the checkpoint is not met. All three agents agree on the need and the P1 priority. (FR-013; FR-009; tasks.md L47.)

3. **Compound implementation labels must be permitted with a constraining rule, not normalized away.** Normalizing spec 004 to "Partially-complete" loses information that implementors need. The compound format using defined tier values is both more informative and more precise than a lossy summary label. This is the one dispute where I will not accept the alternative formulation. taxonomy-reviewer and consistency-checker agree on this position; scope-boundary disagrees. (Revision, Recommendation 5; STATUS.md L46; SC-003.)

**Flexibility** (3 items):

1. **Transition criteria placement (Phase 2 vs. Phase 3).** I prefer Phase 3 (alongside T008's maintenance note), but if the synthesizer judges that the Phase 2 taxonomy section must include transition criteria to be "authoritative," I will accept consistency-checker's formulation placed in the taxonomy section. What must be preserved: the dual-condition structure (gaps resolved AND scenarios satisfied). What I am flexible on: which phase it lands in.

2. **FR-023 gap characterization enrichment.** I prefer deferring the heading-match-semantics addition to Phase 4 when T013 implements FR-007. But if the synthesizer prefers to apply consistency-checker's enriched wording now, I accept it at P3 priority. What must be preserved: the parenthetical must not contradict FR-013's definition. What I am flexible on: timing and priority of the enrichment.

3. **Gap documentation format for spec 004 — FR-only vs. FR-with-parenthetical-scenarios.** I prefer FR-based identifiers only, matching spec 001's format. But consistency-checker's proposal to add parenthetical acceptance-scenario references ("US-3 through US-6 not testable") is a useful enrichment I do not oppose. What must be preserved: FR-based identifiers as the primary reference. What I am flexible on: whether the parenthetical scenario references are included.
