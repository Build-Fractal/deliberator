### Dangerous Contradictions

- **Parenthetical examples in Feature-complete definition: embellishment vs. useful grounding**
  - **scope-boundary claims**: The "(e.g., missing template instructions, incomplete edge case documentation)" in STATUS.md L19 is an embellishment beyond FR-012's exact wording. "The scope-boundary mandate states 'The convention must match the spec exactly — no embellishments.' The examples are not in the spec." (Missed Opportunities, third bullet; Actionable Recommendations #3, Priority P3)
  - **taxonomy-reviewer claims**: The same parenthetical is "a useful, non-distorting addition that grounds the abstraction in a concrete case." (Alignment, second bullet — FR-012 definition fidelity)
  - **Why this is dangerous**: If both positions are adopted without resolution, the synthesis would contain contradictory guidance: one directive saying to remove or caveat the examples and another affirming them as correctly aligned. A Phase 2 implementor receiving both directives would not know whether to edit STATUS.md L19 or leave it alone. More importantly, if the examples are removed per scope-boundary's recommendation, Phase 3 implementors lose the grounding that makes "feature-complete" concrete — but if they are retained without the "illustrative, not exhaustive" marker scope-boundary suggests, a strict reader could treat them as an exhaustive list.
  - **Suggested resolution**: Adopt scope-boundary's fallback option: retain the examples but rephrase to make them clearly illustrative. Change "(e.g., missing template instructions, incomplete edge case documentation)" to something like "(examples: missing template instructions, incomplete edge case documentation — not exhaustive)." This preserves the grounding taxonomy-reviewer values while satisfying scope-boundary's precision concern. scope-boundary already offers this compromise in Recommendation #3's proposed change. taxonomy-reviewer should yield on calling the current form "faithful" and accept the minor rewording.

- **Whether spec 002's "Spec-complete" label requires qualification**
  - **scope-boundary claims**: Spec 002's "Spec-complete" label is "correct — all 36 FRs are represented in SKILL.md and the spec's acceptance criteria are met." (Alignment, third bullet) The review does not question the label's validity.
  - **taxonomy-reviewer claims**: Spec 002's "Spec-complete" label should be verified against acceptance scenarios, not just FR presence. "If the dependency on spec 001's parsing subsystem means some acceptance scenarios cannot be fully validated until spec 001's gaps are resolved, note this qualification." The label "may be premature" given T019's planned behavioral expansion in Phase 4. (Actionable Recommendations #6, Priority P2)
  - **Why this is dangerous**: These positions directly conflict on whether spec 002's label passes Phase 2 review. If scope-boundary's position is adopted, the label stands unqualified and Phase 4's T019 changes could silently invalidate a "spec-complete" designation without anyone flagging the regression. If taxonomy-reviewer's position is adopted, the label gets a qualification that scope-boundary's analysis determined is unnecessary given the current state. The danger is concrete: "spec-complete" is the highest-confidence label in the taxonomy, and if it can be silently invalidated by a downstream phase, the taxonomy's credibility collapses — which is exactly the concern taxonomy-reviewer raises. But adding qualifications to labels that currently satisfy their criteria adds noise that scope-boundary's analysis correctly identifies as outside Phase 2's scope.
  - **Suggested resolution**: Compromise by scope. The label "Spec-complete" is accurate for Phase 2's purposes — all acceptance criteria are met as of now. taxonomy-reviewer's concern is valid but is a Phase 4 concern (T019 changes stagnation detection behavior). Add a note in the Phase 4 gate review checklist: "Verify spec 002's Spec-complete label remains valid after T019 changes to dispute-parsing cross-references." This satisfies taxonomy-reviewer's forward-looking concern without adding Phase 4 content to Phase 2's STATUS.md, which scope-boundary would correctly flag as scope leakage.

- **No additional contradictions identified.** The remaining differences between the two reviews are tensions or agreements, not positions that would produce conflicting implementation directives.

### Tensions

- **Scope of "taxonomy completeness" — enumeration depth**
  - **scope-boundary's position**: The taxonomy should define every label actually used in STATUS.md, but no more. The recommendation to add "Not started" to the acceptance tier (Recommendation #1) is motivated by the principle that "an authoritative taxonomy cannot have labels in use that it does not define" (Recommendation #5). scope-boundary does not recommend additional labels beyond the three that would result (Not started, Feature-complete, Spec-complete).
  - **taxonomy-reviewer's position**: The taxonomy should anticipate labels that Phase 3 will need. Recommendation #7 (Priority P3) proposes adding "In progress" or "Partially feature-complete" because spec 005 will need a label that is neither "not started" nor "feature-complete" when T012a adds it to STATUS.md.
  - **Nature of tension**: scope-boundary optimizes for Phase 2 minimalism — define what is used, nothing more. taxonomy-reviewer optimizes for Phase 3 readiness — define what will be used soon. Both are defensible principles, but they pull the taxonomy in opposite directions. A minimal taxonomy risks ad-hoc label invention in Phase 3. A forward-looking taxonomy risks defining labels for states that may not materialize or may look different than anticipated.
  - **Coordination needed**: The synthesis should decide whether Phase 2's taxonomy is "complete for Phase 2" (scope-boundary's standard) or "complete for Phases 2-3" (taxonomy-reviewer's standard). If the former, taxonomy-reviewer's Recommendation #7 is explicitly deferred to Phase 3 with a note that the taxonomy may need extension. If the latter, scope-boundary would need to accept that Phase 2 defines a label not currently in use — which their scope-boundary mandate would typically reject.

- **Transition criteria: Phase 2 scope or Phase 3 scope**
  - **scope-boundary's position**: The review does not mention transition criteria at all. The "Interpreting the Two Tiers" section is assessed as "appropriately minimal" (Alignment, sixth bullet) and "minimal and necessary" (Recommendation #6). By omission, scope-boundary treats transition criteria as outside Phase 2's scope.
  - **taxonomy-reviewer's position**: Recommendation #4 (Priority P2) argues that the taxonomy should include transition criteria — "A spec transitions from feature-complete to spec-complete when all documented gaps are resolved and all acceptance scenarios in the spec pass." The rationale cites FR-008's update obligation and Phase 3's upcoming additions as reasons this is needed now.
  - **Nature of tension**: scope-boundary's silence on transition criteria is consistent with their mandate to keep Phase 2 minimal. taxonomy-reviewer sees the absence of transition criteria as a gap that will cause inconsistent label updates in Phase 3. The tension is about where the taxonomy's explanatory responsibility ends. scope-boundary draws the line at "define labels + orthogonality." taxonomy-reviewer draws it at "define labels + orthogonality + transition rules."
  - **Coordination needed**: The synthesis should rule on whether transition criteria are part of "defining the convention" (T006's scope) or part of "maintaining the convention" (closer to FR-008's ongoing update obligation, which Phase 3 operationalizes). If they are Phase 2 scope, scope-boundary's review missed them. If they are Phase 3 scope, taxonomy-reviewer's Recommendation #4 should be retagged as a Phase 3 input.

- **Compound-label convention: documentation needed vs. readable-as-is**
  - **scope-boundary's position**: Does not flag spec 004's compound implementation label ("Implementation-complete (core) / Not started (discovery)") as a taxonomy issue. The only concern about spec 004 is the missing acceptance gap documentation (Missed Opportunities, second bullet; Recommendation #2).
  - **taxonomy-reviewer's position**: Recommendation #5 (Priority P2) argues that compound labels are "a convention-by-example rather than a taxonomy-defined format" and should be documented in the Implementation Tier section. The Missed Opportunities section (sixth bullet) also flags that "Partially-complete" does not convey subsystem-level granularity.
  - **Nature of tension**: scope-boundary implicitly treats compound labels as a presentation detail — the taxonomy defines the primitive labels, and compound usage is self-explanatory. taxonomy-reviewer treats them as a taxonomy gap — if the taxonomy is authoritative, all label formats must be defined, not just primitive ones.
  - **Coordination needed**: Minimal. This is a P2 recommendation from taxonomy-reviewer and scope-boundary simply did not address it. The synthesis should decide whether compound-label conventions are taxonomy scope (define them) or presentation scope (leave them as self-documenting). If the former, a brief note in the taxonomy suffices. If the latter, no action needed but the decision should be explicit.

- **FR-023 gap characterization: three full gaps vs. two-plus-partial**
  - **scope-boundary's position**: The review does not flag any inconsistency between US5 AS3 and FR-013 regarding the gap count. It affirms that spec 001's gap list "matches the spec nearly verbatim" (Alignment, second bullet) and treats three gaps as correct.
  - **taxonomy-reviewer's position**: Recommendation #3 (Priority P2) identifies that US5 AS3 (spec.md L89) frames FR-023 as a partial gap ("implemented in SKILL.md; template instructions pending") while FR-013 (spec.md L226) lists it as a full gap. STATUS.md follows FR-013's three-gap formulation. The inconsistency could cause different verification conclusions depending on which reference is consulted.
  - **Nature of tension**: scope-boundary's analysis is satisfied that STATUS.md matches FR-013, which is the authoritative FR. taxonomy-reviewer's analysis looks at the acceptance scenario (US5 AS3) that would be used to verify Phase 2 completion and finds it tells a slightly different story. Both are correct in their framing — FR-013 is the requirement, US5 AS3 is the verification scenario. The tension is about which document a Phase 2 verifier would consult.
  - **Coordination needed**: The synthesis should decide whether aligning US5 AS3 with FR-013 is in scope for Phase 2 (a spec.md edit) or whether it is a minor documentation inconsistency to note and defer. scope-boundary's silence suggests it is not a Phase 2 concern. taxonomy-reviewer's P2 priority suggests it is. If the spec is not edited in Phase 2 (and it should not be — Phase 2 edits STATUS.md only), this becomes a deferred note.

### Safe Agreements

- **"Not started" must be added to the acceptance tier taxonomy (P1)**
  - **Shared position**: Both reviews independently identify the undefined "Not started" acceptance label as the most important issue in Phase 2. scope-boundary: "my most important recommendation: the 'Not started' acceptance label used for spec 003 (L41) is not defined in the taxonomy section" (Executive Summary, final sentence; Missed Opportunities, first bullet; Recommendation #1, Priority P1). taxonomy-reviewer: "the acceptance tier has only two labels but STATUS.md uses 'Not started' for spec 003, creating a three-state system that is not defined in the taxonomy" (Executive Summary, item 1; Missed Opportunities, first bullet; Recommendation #1, Priority P1).
  - **Combined evidence**: Both reviews cite the same root cause — FR-012 defines two labels, STATUS.md L41 uses a third that is not in L17-20. scope-boundary adds the orthogonality argument: "If they are truly orthogonal, labels from one tier do not automatically transfer to the other" (Off-Base Assumptions, first bullet). taxonomy-reviewer adds the forward-looking argument: Phase 3 will add spec 005 (T012a) and the implementor "faces the same ambiguity" (Recommendation #1, Risk if ignored). Both reviews propose nearly identical definitions for the missing label. The convergence from two different analytical lenses (scope purity vs. taxonomy completeness) makes this finding robust.
  - **Confidence level**: High. This should be treated as a blocking P1 item. The taxonomy cannot be called "authoritative" (Phase 2 checkpoint language, tasks.md L47) while using an undefined label.

- **Spec 004 needs explicit acceptance gap documentation (P1/P2)**

  - **Confidence level**: High. The inconsistency between spec 001's treatment (gaps listed) and spec 004's treatment (gaps implied from narrative) is unambiguous. The fix is straightforward.
