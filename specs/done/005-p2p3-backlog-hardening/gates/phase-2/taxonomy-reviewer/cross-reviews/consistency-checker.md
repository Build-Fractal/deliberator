### Dangerous Contradictions

- **Acceptance tier label naming: "not-assessed" vs. "Not started"**
  - **consistency-checker claims**: The acceptance tier needs a third value, and recommends "not-assessed" as the label name: "Add 'not-assessed' to the acceptance tier... Not assessed -- No implementation exists to evaluate against acceptance criteria." (Actionable Recommendations, item 1). They frame the problem as one of mutual exclusivity, arguing that "Not started" is "borrowed from the implementation tier's vocabulary and applied to the acceptance tier, which breaks the taxonomy's stated design" (Missed Opportunities, item 1).
  - **taxonomy-reviewer claims**: The acceptance tier needs a third value, but recommends formalizing the existing "Not started" label rather than introducing a new term: "Add 'Not started' to acceptance tier... Not started: No acceptance criteria have been evaluated. The spec has no implementation to assess." (Actionable Recommendations, item 1). The rationale is that STATUS.md already uses "Not started" at L41, and formalization of existing usage is simpler than introducing new vocabulary.
  - **Why this is dangerous**: If both recommendations are adopted without resolution, Phase 3 inherits two competing names for the same concept. The consistency-checker's "not-assessed" label implies a deliberate choice not to evaluate; taxonomy-reviewer's "Not started" implies no work has begun. These carry different semantic connotations. A Phase 3 implementor applying labels to spec 005 (T012a) could interpret "not-assessed" as "we chose not to assess yet" vs. "Not started" as "nothing exists to assess." Worse, if spec 005 has partial implementation at the time of T012a, "not-assessed" might still apply (it hasn't been formally assessed) while "Not started" would be factually wrong (work has started). The label choice directly affects whether Phase 3 can correctly label spec 005.
  - **Suggested resolution**: consistency-checker's "not-assessed" is semantically more precise because it describes the evaluation state rather than the implementation state, which is the acceptance tier's domain. However, taxonomy-reviewer's approach of formalizing existing usage has lower adoption friction. The compromise is to use "not-assessed" as the label (consistency-checker's recommendation) but define it in terms that cover both "no implementation exists" and "implementation exists but acceptance has not been formally evaluated" -- this handles spec 005's Phase 3 state as well. taxonomy-reviewer should yield on the label name; consistency-checker should accept a broader definition.

- **Spec 004 compound label: normalize to "Partially-complete" vs. document compound format**
  - **consistency-checker claims**: Spec 004's compound implementation label should be normalized to "Partially-complete" with the core/discovery split documented in the gaps field: "Either (a) label spec 004 as 'Partially-complete' with the core/discovery split documented in the gaps field, or (b) explicitly permit compound labels... Option (a) is simpler and consistent with the three-value taxonomy." (Actionable Recommendations, item 2). They frame compound labels as undermining the controlled vocabulary.
  - **taxonomy-reviewer claims**: The compound label format should be documented as a permitted convention: "Add a note to the Implementation Tier section: 'Specs with independently-implementable subsystems may use compound labels...'" (Actionable Recommendations, item 5). The rationale is that "Partially-complete" loses information about which subsystem is complete, and compound labels are pragmatically useful.
  - **Why this is dangerous**: These recommendations pull the taxonomy in opposite directions. consistency-checker's approach preserves a strict three-value controlled vocabulary but loses granularity. taxonomy-reviewer's approach preserves granularity but weakens the taxonomy's role as a controlled vocabulary. If both are partially adopted -- e.g., relabeling spec 004 as "Partially-complete" (per consistency-checker) while also documenting compound labels as permitted (per taxonomy-reviewer) -- the result is contradictory: the taxonomy permits a format that the spec entries do not use, or spec entries use a format the taxonomy does not endorse. Phase 3's T012a (adding spec 005) would face ambiguity about which format to follow.
  - **Suggested resolution**: The key question is whether the taxonomy section is a controlled vocabulary with exactly three labels or a convention guide that permits structured extensions. Given that spec 004 genuinely has two independently-implementable subsystems, and future specs may also, the pragmatic answer is consistency-checker's option (b): explicitly permit compound labels in the taxonomy with a clear rule for when they apply. This gives taxonomy-reviewer the granularity they want while addressing consistency-checker's concern about undocumented formats. consistency-checker's option (a) loses real information and would force a reader to dig into the gaps field to understand that "core" is complete.

- **No additional contradictions identified.** Both reviews converge on most structural observations. The remaining differences are tensions (below), not contradictions that would break integration.

### Tensions

- **Scope of FR-023 gap characterization**
  - **consistency-checker's position**: FR-023's gap description in STATUS.md should be expanded to explicitly mention spec 005 FR-007's heading match semantics as a separate pending item: "Revise to: 'FR-023 (output validation -- SKILL.md validation check exists; heading match semantics (case-insensitive, level-agnostic) pending per spec 005 FR-007; template-level heading instructions pending).'" (Actionable Recommendations, item 4). This adds cross-spec traceability.
  - **taxonomy-reviewer's position**: The gap inconsistency is between US5 AS3 and FR-013 -- US5 AS3 treats FR-023 as a partial gap while FR-013 lists it as a full gap. The recommended fix is reconciliation between these two references, not expansion of the STATUS.md entry: "Either (a) align US5 AS3 to list all three gaps consistently with FR-013, or (b) add a parenthetical to FR-013..." (Actionable Recommendations, item 3).
  - **Nature of tension**: consistency-checker wants STATUS.md to carry more detail about FR-023's sub-components, adding cross-spec references (FR-007 from spec 005). taxonomy-reviewer wants the spec's own internal references (US5 AS3 vs. FR-013) to be consistent with each other. These are not contradictory -- both could be done -- but they pull in different directions on where precision should live. consistency-checker pushes precision into STATUS.md (the tracking document); taxonomy-reviewer pushes precision into spec.md (the specification document). The question is whether STATUS.md gap entries should be exhaustive cross-spec references or concise summaries.
  - **Coordination needed**: Decide on a convention: STATUS.md gap entries are either (a) concise with cross-references to spec.md for detail, or (b) exhaustive with all sub-component breakdowns inline. Phase 3 will add more content to STATUS.md (T008-T012a), and the convention affects how detailed those entries should be. Both recommendations can coexist if STATUS.md uses a brief note with a pointer: "FR-023 (output validation -- validation check exists; template instructions and heading match semantics pending; see spec 005 FR-007 for match semantics)."

- **Spec 002 "Spec-complete" verification depth**
  - **consistency-checker's position**: Recommends either spot-checking spec 002's 18 acceptance scenarios against SKILL.md or adding a caveat that "Spec-complete" is based on FR coverage rather than acceptance scenario verification: "verify all 18 acceptance scenarios are satisfied... or add a note acknowledging that 'Spec-complete' is based on FR coverage and the dependency note serves as a caveat." (Actionable Recommendations, item 6).
  - **taxonomy-reviewer's position**: Recommends verifying that the parsing subsystem dependency does not invalidate acceptance scenarios: "If the dependency on spec 001's parsing subsystem means some acceptance scenarios cannot be fully validated until spec 001's gaps are resolved, note this qualification." (Actionable Recommendations, item 6). Frames the concern through the T019 behavioral expansion lens from the Phase 1 summary.
  - **Nature of tension**: Both reviews question whether "Spec-complete" is justified for spec 002, but they propose different verification approaches. consistency-checker wants scenario-level spot-checking (test-oriented); taxonomy-reviewer wants dependency-based qualification (risk-oriented). The scenario-level approach is more thorough but is arguably Phase 3 scope (enrichment and deeper analysis). The dependency-based approach is lighter but could miss non-dependency-related gaps.
  - **Coordination needed**: These approaches are complementary, not competing. The dependency qualification (taxonomy-reviewer) should be done in Phase 2 because it affects the label's accuracy. The scenario-level spot-check (consistency-checker) could be deferred to Phase 3 (T010/T011 risk-of-gap and effort analysis) since it is enrichment rather than taxonomy correctness. If the dependency check reveals that acceptance scenarios depend on unresolved spec 001 parsing behavior, the "Spec-complete" label should be downgraded to "Feature-complete" with a gap note -- both reviews agree on this outcome.

- **Transition criteria specificity**
  - **consistency-checker's position**: Recommends adding transition criteria: "A spec transitions from feature-complete to spec-complete when all acceptance scenarios defined in its spec.md are verified as satisfied. The spec entry's 'Gaps' field tracks what remains." (Actionable Recommendations, item 5). Uses acceptance scenarios as the transition gate.
  - **taxonomy-reviewer's position**: Recommends similar transition criteria but uses a different formulation: "A spec transitions from feature-complete to spec-complete when all documented gaps are resolved and all acceptance scenarios in the spec pass." (Actionable Recommendations, item 4). Adds "all documented gaps are resolved" as a separate condition alongside acceptance scenarios.
  - **Nature of tension**: consistency-checker's formulation uses acceptance scenarios as the sole gate. taxonomy-reviewer's formulation adds gap resolution as an independent condition. These differ when gaps exist that are not tied to acceptance scenarios (e.g., documentation gaps, or gaps in FRs that do not map to a specific acceptance scenario). Under consistency-checker's rule, resolving all acceptance scenarios would suffice even if documented gaps remain in the gaps field. Under taxonomy-reviewer's rule, both conditions must be met.
  - **Coordination needed**: taxonomy-reviewer's dual-condition formulation is more conservative and prevents a scenario where a spec is relabeled "spec-complete" while its Gaps field still lists items. The simpler resolution is to adopt taxonomy-reviewer's formulation, since it is strictly stronger (acceptance scenarios passing AND gaps resolved) and prevents the awkward state of "spec-complete with documented gaps." consistency-checker's acceptance-scenario-only gate is not wrong but is less robust when gap documentation and acceptance scenarios diverge.

- **Priority assignment for acceptance gap documentation on spec 004**
  - **consistency-checker's position**: Rates adding acceptance gap documentation for spec 004 as P2: "Add acceptance gap documentation for spec 004 (Priority: P2)" (Actionable Recommendations, item 3).
  - **taxonomy-reviewer's position**: Rates the same item as P1: "Add explicit acceptance gaps to spec 004 (Priority: P1)" (Actionable Recommendations, item 2).
  - **Nature of tension**: This is not a disagreement about what to do but about urgency. taxonomy-reviewer's P1 rating is based on the argument that "feature-complete" without documented gaps defeats the label's purpose and creates an inconsistency with spec 001. consistency-checker's P2 rating treats it as important but not blocking for Phase 2's checkpoint criteria.
  - **Coordination needed**: The Phase 2 checkpoint is "Two-tier convention defined and applied to all 4 specs. STATUS.md taxonomy is authoritative" (tasks.md L47). If "authoritative" means every feature-complete label has accompanying gap documentation (as spec 001 demonstrates), then spec 004's missing gaps violate the checkpoint, supporting P1. If "authoritative" means the taxonomy section itself is correct and labels are assigned, then gap completeness is enrichment and can wait, supporting P2. The checkpoint definition should be clarified to resolve this.

### Safe Agreements

- **The acceptance tier needs a third label for unassessed/unstarted specs**
  - **Shared position**: Both reviews identify the same structural deficiency: the acceptance tier defines only two labels ("feature-complete" and "spec-complete") but STATUS.md L41 uses "Not started" for spec 003, which is not a defined acceptance-tier label. consistency-checker: "The two-value acceptance tier cannot represent the full state space" (Missed Opportunities, item 1; Off-Base Assumptions, item 1). taxonomy-reviewer: "'Not started' is not a defined acceptance-tier label... FR-012 only establishes two labels" (Missed Opportunities, item 1; Off-Base Assumptions, item 1).
  - **Combined evidence**: consistency-checker cross-references spec.md L276 ("the two-tier status convention applies to all four existing specs") against STATUS.md L41 to show the assumption is violated on first application. taxonomy-reviewer cross-references FR-009 (spec.md L216) to argue that using an undefined label violates the requirement that labels "use the two-tier convention defined in FR-012/FR-013." Both reviews also independently identify that Phase 3's T012a will face the same problem when labeling spec 005, confirming the issue is not a one-time anomaly but a recurring gap. The convergence from two different angles -- one definitional (consistency-checker: "breaks mutual exclusivity") and one regulatory (taxonomy-reviewer: "violates FR-009") -- makes this finding robust.
  - **Confidence level**: High. This is the single most important finding in both reviews and should be addressed before Phase 2 is considered complete.

- **Spec 004's implementation label deviates from the taxonomy's controlled vocabulary**
  - **Shared position**: Both reviews identify that spec 004's "Implementation-complete (core) / Not started (discovery)" label at STATUS.md L46 does not match any of the three defined implementation-tier values at L9-13. consistency-checker: "This is a compound label that does not fit the three-value implementation tier taxonomy... the tier is no longer a controlled vocabulary" (Missed Opportunities, item 5). taxonomy-reviewer: "The taxonomy (L11-13) does not account for this. 'Partially-complete' is the closest match, yet that label does not convey that one entire subsystem is complete while another is untouched" (Missed Opportunities, item 6).
  - **Combined evidence**: Both reviews agree the deviation exists and that it undermines the taxonomy's claim to being a controlled vocabulary. They diverge on the remedy (normalize vs. document -- see Tensions above), but the factual observation is shared and uncontested. consistency-checker adds the forward-looking argument that "spec 005's own entry (T012a) could use any ad-hoc format" if the deviation is not addressed, which reinforces taxonomy-reviewer's observation about compound labels setting a precedent.
  - **Confidence level**: High. The deviation is factual and both reviews agree it must be resolved. The direction of resolution (normalize vs. formalize) is a tension, but the need for resolution is a safe agreement.

- **Transition criteria are missing and needed before Phase 3**
  - **Shared position**: Both reviews identify that the taxonomy defines static labels but provides no rules for when a spec moves between them. consistency-checker: "does not define the transition criteria. When does a spec move from feature-complete to spec-complete?" (Missed Opportunities, item 3). taxonomy-reviewer: "The taxonomy defines static labels but says nothing about when or how a spec transitions between them" (Missed Opportunities, item 3). Both rate this as medium impact and P2 priority.
  - **Combined evidence**: consistency-checker grounds the concern in auditability ("Explicit criteria make the label change auditable") and gives a concrete disagreement scenario involving T013 and FR-023. taxonomy-reviewer grounds it in FR-008's update obligation and the risk of ad-hoc relabeling during Phase 3. The complementary rationales -- one focused on audit trail, one focused on process discipline -- strengthen the case that transition criteria serve multiple governance functions.
  - **Confidence level**: Medium. Both reviews agree the criteria are needed, but both also rate it P2, suggesting it is important for Phase 3 readiness rather than Phase 2 completeness. The agreement is real but the urgency is moderate.
