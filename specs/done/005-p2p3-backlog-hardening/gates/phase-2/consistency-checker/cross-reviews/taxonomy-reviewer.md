### Dangerous Contradictions

- **[Naming of the missing acceptance-tier label]**
  - **taxonomy-reviewer claims**: "Add 'Not started' to acceptance tier" (Recommendation 1, Priority P1). Proposes adding the literal label "Not started" with definition: "No acceptance criteria have been evaluated. The spec has no implementation to assess." This reuses the implementation tier's vocabulary intentionally.
  - **consistency-checker claims**: "Add 'not-assessed' to the acceptance tier" (Recommendation 1, Priority P1). Proposes either a distinct label ("not-assessed") or a scoping rule that acceptance labels only apply when implementation > 0. Explicitly frames "Not started" as "borrowed from the implementation tier's vocabulary" in the Missed Opportunities section, treating this borrowing as the problem rather than the solution.
  - **Why this is dangerous**: Both reviews agree a third acceptance-tier value is needed (this is a Safe Agreement below). But they propose incompatible label names. If taxonomy-reviewer's "Not started" is adopted, the same label appears in both tiers with different definitions (implementation: "No SKILL.md representation exists"; acceptance: "No acceptance criteria have been evaluated"). If consistency-checker's "not-assessed" is adopted, it introduces a term that does not exist anywhere in the current STATUS.md or spec.md. Phase 3 (T012a) must assign an acceptance label to spec 005 — if the label name is unresolved, the implementor will pick one ad hoc, exactly defeating SC-005 ("zero labeling disagreements").
  - **Suggested resolution**: Adopt "not-assessed" as the acceptance-tier label. The tiers are defined as orthogonal (STATUS.md L22-24); sharing a label name across tiers undermines that orthogonality by creating parsing ambiguity when a reader sees "Not started" and must determine which tier it belongs to. "Not-assessed" is semantically precise — it communicates that no evaluation has occurred, distinct from "no implementation exists." taxonomy-reviewer should yield on the label name while retaining the definition they proposed, which is accurate.

- **[Whether spec 004's compound implementation label should be normalized or formalized]**
  - **taxonomy-reviewer claims**: "Document compound-label conventions for multi-subsystem specs" (Recommendation 5, Priority P2). Proposes adding a note to the Implementation Tier section permitting compound labels and defining their format: "Specs with independently-implementable subsystems may use compound labels."
  - **consistency-checker claims**: "Normalize spec 004's compound implementation label" (Recommendation 2, Priority P1). Proposes either relabeling spec 004 as "Partially-complete" with subsystem details in the gaps field, or explicitly permitting compound labels — but recommends option (a) as "simpler and consistent with the three-value taxonomy."
  - **Why this is dangerous**: These are opposite approaches to the same problem. taxonomy-reviewer would expand the taxonomy to accommodate the deviation. consistency-checker would constrain the deviation to fit the existing taxonomy. If both are partially adopted — say, the taxonomy is expanded to permit compound labels AND spec 004 is relabeled as "Partially-complete" — the result is a taxonomy that permits compound labels with no entries that use them, which is confusing. If taxonomy-reviewer's formalization is adopted, every future spec with subsystem variance will use compound labels, making the three-value implementation tier effectively unbounded. If consistency-checker's normalization is adopted, compound labels are prohibited and subsystem detail moves to the gaps field.
  - **Suggested resolution**: This is a genuine design trade-off. taxonomy-reviewer's approach is more expressive but less constrained; consistency-checker's is more constrained but loses information in the label itself. The cooperative resolution is consistency-checker's option (b): explicitly permit compound labels in the taxonomy, but require them to use only the existing three values as components (e.g., "Implementation-complete (core) / Not started (discovery)" is valid because both "Implementation-complete" and "Not started" are defined labels). This preserves the controlled vocabulary while accommodating multi-subsystem specs. taxonomy-reviewer should refine their recommendation to constrain compound labels to existing tier values; consistency-checker should accept that compound labels have legitimate use cases.

- **[Priority assigned to spec 004 acceptance gap documentation]**
  - **taxonomy-reviewer claims**: "Add explicit acceptance gaps to spec 004" (Recommendation 2, Priority P1). Frames the missing gap documentation as a first-tier issue that blocks consistency.
  - **consistency-checker claims**: "Add acceptance gap documentation for spec 004" (Recommendation 3, Priority P2). Frames the same issue as important but secondary to the definitional problems (missing acceptance-tier label, compound label normalization).
  - **Why this is dangerous**: Priority labels drive implementation order. If both reviews are synthesized and the priorities conflict, the synthesizer must decide which to use. If P2 is adopted and Phase 2 is gated before Phase 3 begins, the gap documentation might be deferred to Phase 3 — but Phase 3 tasks (T010, T011) add risk-of-gap and effort fields that depend on understanding each spec's acceptance status. If the gap documentation is missing for spec 004 when T010 runs, the risk-of-gap assessment will be imprecise.
  - **Suggested resolution**: taxonomy-reviewer's P1 is more defensible. The inconsistency between spec 001 (gaps documented) and spec 004 (gaps absent) is a Phase 2 problem because Phase 2's goal is applying the taxonomy correctly to all specs (tasks.md L42: "Two-tier convention defined and applied to all 4 specs"). If spec 004's feature-complete label lacks gap documentation, the taxonomy is not fully applied. consistency-checker should yield to P1.

### Tensions

- **[Granularity of FR-023 gap characterization]**
  - **taxonomy-reviewer's position**: "Reconcile US5 AS3 gap list with FR-013 gap list" (Recommendation 3, Priority P2). Focuses on the discrepancy between US5 AS3 (which treats FR-023 as partially implemented, listing only two full gaps) and FR-013/STATUS.md (which lists three gaps including FR-023). Proposes aligning the two framings.
  - **consistency-checker's position**: "Clarify FR-023 gap characterization in STATUS.md" (Recommendation 4, Priority P2). Focuses on the STATUS.md parenthetical being imprecise — it mentions template instructions but omits heading match semantics (spec 005 FR-007, planned for T013). Proposes expanding the parenthetical to include both sub-issues.
  - **Nature of tension**: Both reviews identify FR-023's characterization as problematic, but they diagnose different symptoms. taxonomy-reviewer sees a cross-document consistency issue (US5 AS3 vs. FR-013). consistency-checker sees a within-document precision issue (STATUS.md parenthetical is incomplete). Fixing one does not fix the other. A more precise STATUS.md parenthetical (consistency-checker's fix) does not resolve the US5 AS3 vs. FR-013 discrepancy. Aligning US5 AS3 with FR-013 (taxonomy-reviewer's fix) does not add the missing FR-007 dependency.
  - **Coordination needed**: Both fixes should be applied. taxonomy-reviewer's reconciliation addresses spec-level consistency. consistency-checker's parenthetical expansion addresses gap precision. The synthesizer should combine them: align the gap count across documents AND expand the FR-023 parenthetical to mention both template instructions and heading match semantics.

- **[Scope of spec 002 "Spec-complete" verification]**
  - **taxonomy-reviewer's position**: "Verify spec 002's 'Spec-complete' label is justified" (Recommendation 6, Priority P2). Raises the concern that T019 (Phase 4) may change parsing behavior and invalidate spec 002's acceptance label. Frames the risk as temporal — the label may be correct now but false after Phase 4.
  - **consistency-checker's position**: "Verify spec 002 'Spec-complete' label against acceptance scenarios" (Recommendation 6, Priority P2). Raises the concern that the label is based on FR coverage rather than acceptance scenario verification. Proposes spot-checking the most complex acceptance scenarios (US-1 AS5, US-2 AS3).
  - **Nature of tension**: taxonomy-reviewer frames the risk as a future-facing temporal problem (T019 could invalidate the label). consistency-checker frames it as a present-facing verification problem (the label may never have been properly verified against acceptance scenarios). These pull in different directions: taxonomy-reviewer's concern suggests deferring verification until after T019; consistency-checker's concern suggests verifying now. Acting on both simultaneously is contradictory — you cannot verify the label now AND acknowledge it may be invalidated by T019.
  - **Coordination needed**: The synthesizer should separate the two concerns. Present-facing verification (consistency-checker) should be addressed in Phase 2 — even a cursory check strengthens the label. Future-facing staleness (taxonomy-reviewer) should be addressed by adding a note to spec 002's entry: "Acceptance label subject to re-evaluation after T019 modifies dispute-parsing cross-references." This acknowledges the temporal risk without blocking current verification.

- **[Whether the taxonomy needs an "in progress" acceptance label]**
  - **taxonomy-reviewer's position**: "Add a 'Partially feature-complete' or 'In progress' acceptance label" (Recommendation 7, Priority P3). Argues that when spec 005 is added to STATUS.md in Phase 3 (T012a), neither "feature-complete" nor "not-started" will accurately describe a spec under active development with an unstable gap list.
  - **consistency-checker's position**: "Add explicit guidance for Phase 3 on labeling spec 005 itself" (Recommendation 7, Priority P3). Proposes adding a note to T012a with explicit instructions: "Label acceptance status as 'feature-complete' with gaps listing the remaining Phase 4 FRs."
  - **Nature of tension**: taxonomy-reviewer wants to expand the taxonomy to accommodate in-progress specs. consistency-checker wants to use the existing "feature-complete" label with explicit guidance on how to apply it. Expanding the taxonomy adds a fourth acceptance-tier label, increasing complexity. Using "feature-complete" for in-progress specs stretches the definition ("all major capabilities present" may not be true for a spec mid-implementation).
  - **Coordination needed**: The pragmatic resolution is consistency-checker's approach — use "feature-complete" with explicit gap documentation — because adding a fourth acceptance label for a single known case (spec 005) increases taxonomy complexity disproportionately. However, taxonomy-reviewer's concern is legitimate: if the gap list is unstable, "feature-complete" with gaps is misleading because "feature-complete" implies all major capabilities ARE present. The synthesizer should adopt consistency-checker's approach but add a qualifier to the guidance: "If major capabilities are still pending, label as 'not-assessed' (or the chosen third label) until gap list stabilizes."

- **[Whether transition criteria belong in Phase 2 or are Phase 3 scope]**
  - **taxonomy-reviewer's position**: "Add transition criteria to taxonomy section" (Recommendation 4, Priority P2). Proposes a specific paragraph: "A spec transitions from feature-complete to spec-complete when all documented gaps are resolved and all acceptance scenarios in the spec pass."
  - **consistency-checker's position**: "Define acceptance label transition criteria" (Recommendation 5, Priority P2). Proposes a similar rule: "A spec transitions from feature-complete to spec-complete when all acceptance scenarios defined in its spec.md are verified as satisfied."
  - **Nature of tension**: Both reviews agree transition criteria are needed and propose nearly identical content. The tension is subtle: taxonomy-reviewer anchors the transition to "documented gaps resolved AND acceptance scenarios pass" (two conditions). consistency-checker anchors it to "acceptance scenarios verified as satisfied" (one condition, with gap tracking as a supporting mechanism). The two-condition formulation could create a situation where all gaps are resolved but an acceptance scenario still fails (or vice versa), leaving the transition criteria ambiguous.
  - **Coordination needed**: The synthesizer should use taxonomy-reviewer's two-condition formulation but clarify the relationship: "A spec transitions from feature-complete to spec-complete when all documented gaps are resolved. Gaps are considered resolved when their corresponding acceptance scenarios pass." This makes gap resolution the primary trigger and scenario verification the evidence.

### Safe Agreements

- **[A third acceptance-tier value is required]**
  - **Shared position**: Both reviews identify that the acceptance tier's two-value system (feature-complete, spec-complete) is insufficient. taxonomy-reviewer states: "The assumption that two labels are sufficient is contradicted by the first application of the convention" (Off-Base Assumptions, first item). consistency-checker states: "The two-value acceptance tier cannot represent the full state space" (Recommendation 1, Rationale).
  - **Combined evidence**: taxonomy-reviewer provides the concrete example of spec 003 (STATUS.md L41) using "Not started" in the acceptance column — a label not defined in the acceptance tier. consistency-checker provides the forward-looking evidence: Phase 3 task T012a must assign an acceptance label to spec 005, and the current tier cannot represent an in-progress spec. Together, these establish both a present deficiency (spec 003) and a future deficiency (spec 005), making the case for a third value overwhelming.
  - **Confidence level**: High. This is the most important finding across both reviews and must be addressed before Phase 3 begins.

- **[Spec 004 needs acceptance gap documentation]**
  - **Shared position**: Both reviews identify that spec 004's "Feature-complete" acceptance label lacks the gap documentation that spec 001's entry provides. taxonomy-reviewer states: "Spec 004 is labeled 'Feature-complete' but has no explicit Gaps field listing which acceptance criteria are unmet" (Missed Opportunities, fifth item). consistency-checker states: "Spec 004's entry lists the core/discovery split but does not state which acceptance criteria gaps prevent it from being 'spec-complete'" (Missed Opportunities, second item).
  - **Combined evidence**: taxonomy-reviewer frames this as an inconsistency with spec 001's treatment ("If gaps remain, they should be listed, as they are for spec 001"). consistency-checker provides the specific acceptance scenarios that are untestable: "US-3 through US-6 acceptance scenarios are not testable (discovery features not implemented)." Together, this identifies both the problem (inconsistency) and the solution (which scenarios to document as gaps).
  - **Confidence level**: High. The asymmetry between spec 001 and spec 004 is unambiguous and easily remedied.

- **[The taxonomy's orthogonality design is sound]**
  - **Shared position**: Both reviews affirm that the two-tier design — separating implementation completeness from acceptance completeness — is well-conceived. taxonomy-reviewer states: "The taxonomy section cleanly separates implementation tier and acceptance tier under distinct headings" and calls the orthogonality paragraph "the right level of explanation" (Alignment, first and fourth items). consistency-checker states: "The two tiers measure genuinely orthogonal dimensions" and "This correctly models the real situation — implementation status and acceptance status are genuinely independent dimensions" (Executive Summary; Alignment, first item).
  - **Combined evidence**: taxonomy-reviewer validates the tier definitions against FR-012 and confirms definitional fidelity. consistency-checker validates the implementation tier's three-value system as mutually exclusive and exhaustive. Neither review finds a case where the tiers overlap or where a spec could be correctly classified under both acceptance labels simultaneously (the core mutual-exclusivity check). The problems both reviews identify are about coverage (missing third value) and application (inconsistent gap documentation), not about the fundamental design.
  - **Confidence level**: High. Phase 3 can build on the orthogonal two-tier structure with confidence that the design is sound. The issues identified in both reviews are about extending and consistently applying the taxonomy, not redesigning it.

- **[Transition criteria must be added to the taxonomy]**
  - **Shared position**: Both reviews independently recommend adding transition criteria — rules for when a spec moves between acceptance labels. taxonomy-reviewer states: "The taxonomy defines static labels but says nothing about when or how a spec transitions between them" (Missed Opportunities, third item). consistency-checker states: "The taxonomy defines what 'feature-complete' and 'spec-complete' mean but does not define the transition criteria" (Missed Opportunities, third item).
  - **Combined evidence**: taxonomy-reviewer grounds the need in FR-008 ("STATUS.md MUST be updated when any spec's implementation or acceptance status changes") and notes that without transition criteria, two reviewers could disagree about whether partial gap closure warrants relabeling. consistency-checker grounds the need in the distinction between FRs and acceptance scenarios — gap documentation uses FRs as proxies, but the acceptance tier's definition references "acceptance criteria," creating ambiguity about what must be satisfied for a transition. Both perspectives converge on the same conclusion: static definitions without transition rules leave the taxonomy incomplete.
  - **Confidence level**: Medium. Both reviews agree on the need, but the exact formulation differs (see Tensions above). The synthesizer must resolve the two-condition vs. one-condition tension before this can be implemented.
