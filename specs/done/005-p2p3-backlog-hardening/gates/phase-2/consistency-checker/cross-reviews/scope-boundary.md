### Dangerous Contradictions

- **Label name for the missing acceptance-tier value**
  - **scope-boundary claims**: Recommends adding "Not started" to the acceptance tier taxonomy, defined as "No acceptance criteria have been evaluated. The spec's features are not yet implemented." (Actionable Recommendations, item 1: "Add 'Not started' to acceptance tier taxonomy")
  - **consistency-checker claims**: Recommends adding "not-assessed" as a distinct label, or alternatively a scoping rule that acceptance labels only apply when implementation > 0. Explicitly argues against borrowing "Not started" from the implementation tier because it "breaks mutual exclusivity" between tiers. (Missed Opportunities, item 1: "Acceptance tier for specs with zero implementation"; Actionable Recommendations, item 1: "Add 'not-assessed' to the acceptance tier")
  - **Why this is dangerous**: Both reviews agree a third acceptance-tier value is needed, but they propose different labels with different semantics. scope-boundary's "Not started" reuses the implementation-tier's label name, creating cross-tier terminological overlap in the very taxonomy designed to be orthogonal. If Phase 3 adopts scope-boundary's recommendation, the same label ("Not started") appears in both tiers with different definitions — implementation-tier "Not started" means "No SKILL.md representation exists" (STATUS.md L13), while acceptance-tier "Not started" would mean "No acceptance criteria have been evaluated." A contributor reading STATUS.md L41 ("Implementation: Not started | Acceptance: Not started") would see identical labels and might assume they mean the same thing, undermining the orthogonality the taxonomy exists to establish. If Phase 3 adopts consistency-checker's recommendation ("not-assessed"), the labels are distinct but the name sounds passive and clinical rather than action-oriented. Both approaches solve the coverage gap differently, and implementing both would produce contradictory taxonomy entries.
  - **Suggested resolution**: Adopt a label name that is (a) distinct from implementation-tier vocabulary and (b) semantically clear. "Not assessed" or "Pending implementation" would satisfy both constraints. scope-boundary should yield on reusing "Not started" because the orthogonality principle — which scope-boundary's own review endorses (Alignment section, "Interpreting the Two Tiers" confirmation) — is violated by cross-tier label reuse. consistency-checker should yield on the alternative scoping rule ("acceptance labels only apply when implementation > 0") because it creates a special case that complicates Phase 3's T012a labeling of spec 005 (which will be partially implemented).

- **Scope of gap documentation obligation**
  - **scope-boundary claims**: Gap documentation for spec 004 is a "missed opportunity" at medium impact. The recommendation is to "add a `**Gaps**:` line to spec 004's entry identifying that discovery commands (FR-022-024) represent the acceptance criteria gap." Frames this as a consistency issue driven by FR-013's precedent for spec 001. (Missed Opportunities, item 2: "Spec 004 acceptance label ambiguity")
  - **consistency-checker claims**: Gap documentation for spec 004 is also flagged (Actionable Recommendations, item 3), but goes further: the gaps should reference US-3 through US-6 acceptance scenarios, not just FR-022-024 implementation requirements. Separately argues that the taxonomy conflates FRs and acceptance scenarios in gap documentation (Actionable Recommendations, item 8: "Document the relationship between FRs and acceptance scenarios in the taxonomy"), and that this conflation is itself a consistency problem.
  - **Why this is dangerous**: If Phase 3 follows scope-boundary's recommendation, spec 004 gaps will be documented in FR terms (FR-022-024). If Phase 3 follows consistency-checker's recommendation, spec 004 gaps will be documented in acceptance-scenario terms (US-3 through US-6). These are not interchangeable — FRs are implementation requirements, acceptance scenarios are testable behaviors. A STATUS.md where spec 001 gaps use FRs and spec 004 gaps use acceptance scenarios would be internally inconsistent in a different way. But a STATUS.md where all gaps use FRs would mask the acceptance-level assessment that the acceptance tier is supposed to measure. Phase 3 contributors would not know which convention to follow.
  - **Suggested resolution**: Establish a single gap documentation convention before Phase 3 begins. The pragmatic choice is FR-based gaps (consistent with spec 001's existing documentation and with how FR-013 is written), with a parenthetical noting which acceptance scenarios are affected. This satisfies scope-boundary's consistency requirement and consistency-checker's concern about the FR/acceptance-scenario distinction. Add this convention as a brief note in the taxonomy section.

- **Whether spec 002's "Spec-complete" label is safe to accept at face value**
  - **scope-boundary claims**: Spec 002's "Spec-complete" label is correct. States: "Spec 002 is labeled 'Spec-complete,' which is correct — all 36 FRs are represented in SKILL.md and the spec's acceptance criteria are met." (Alignment, item 3: "Spec 002 acceptance label")
  - **consistency-checker claims**: Spec 002's "Spec-complete" label should be verified against its 18 acceptance scenarios, not assumed from FR coverage. Notes that the dependency on spec 001's parsing subsystem may mean some acceptance scenarios "cannot be verified in isolation," potentially making "Spec-complete" premature. (Actionable Recommendations, item 6: "Verify spec 002 'Spec-complete' label against acceptance scenarios")
  - **Why this is dangerous**: "Spec-complete" is the strongest label in the taxonomy. If scope-boundary's position is adopted without verification, the label stands on FR coverage alone. If consistency-checker's position is adopted and verification reveals a gap, the label must be downgraded to "Feature-complete" with documented gaps — which would change the STATUS.md content that Phase 3 builds on. The danger is timing: if Phase 3 enriches spec 002's entry (adding risk-of-gap, effort, etc.) assuming "Spec-complete," and Phase 5 verification reveals it should be "Feature-complete," Phase 3's enrichment work may need revision.
  - **Suggested resolution**: Perform a lightweight spot-check of spec 002's most dependency-sensitive acceptance scenarios (e.g., US-2 AS3 — stagnation with arbiter configured) before Phase 3 begins. If the spot-check confirms "Spec-complete," both positions are satisfied. If it reveals a gap, downgrade to "Feature-complete" in Phase 2 so Phase 3 builds on the corrected label. scope-boundary should acknowledge this verification need; consistency-checker should accept that a spot-check (not full verification of all 18 scenarios) is proportionate.

### Tensions

- **Strictness of "match the spec exactly" vs. helpful elaboration**
  - **scope-boundary's position**: The "(e.g., ...)" examples in the Feature-complete definition (STATUS.md L19) are flagged as an embellishment that should either be removed or explicitly marked as illustrative. Cites the scope-boundary mandate: "convention must match the spec exactly — no embellishments." (Missed Opportunities, item 3: "No explicit mapping from FR-012 terms to taxonomy text")
  - **consistency-checker's position**: Does not flag the examples as a problem. Instead, flags the absence of transition criteria and the absence of guidance on FR vs. acceptance-scenario gap documentation as problems — both of which would require adding content beyond what FR-012 literally specifies. (Actionable Recommendations, items 5 and 8)
  - **Nature of tension**: scope-boundary applies a strict "nothing beyond the spec" standard to the taxonomy text, while consistency-checker applies a "the taxonomy must be complete enough to prevent ambiguity" standard that requires additions the spec does not literally mandate. Both standards are valid but they pull in opposite directions: strict fidelity vs. operational completeness.
  - **Coordination needed**: Agree on a principle: the taxonomy section must contain everything needed for unambiguous label assignment, but nothing that constrains or elaborates beyond what is needed. The examples in L19 fail scope-boundary's test (they elaborate). The missing transition criteria fail consistency-checker's test (they leave ambiguity). Resolve by removing the examples and adding the transition criteria — the former is decorative, the latter is structural.

- **Spec 005 self-tracking: boundary clarity vs. forward guidance**
  - **scope-boundary's position**: T007's description should explicitly exclude spec 005 with a deferral note to T012a. Frames this as a Phase 2/Phase 3 boundary issue. Recommends appending "(Spec 005 entry deferred to T012a, Phase 3)" to T007's description. (Actionable Recommendations, item 4: "Add explicit T007 exclusion note for spec 005")
  - **consistency-checker's position**: T012a should include explicit guidance on what labels to assign spec 005, since the taxonomy has no guidance for labeling a spec that is actively being implemented. Recommends adding labeling instructions to T012a itself. (Actionable Recommendations, item 7: "Add explicit guidance for Phase 3 on labeling spec 005 itself")
  - **Nature of tension**: scope-boundary wants the Phase 2 boundary to be cleaner (annotate what is excluded). consistency-checker wants the Phase 3 task to be more prescriptive (specify how to include it). Both are valid but address different sides of the same gap — the handoff between Phase 2 and Phase 3 for spec 005 is under-specified on both the "out" side and the "in" side.
  - **Coordination needed**: Adopt both recommendations. They are complementary, not competing: annotate T007 with the deferral note (scope-boundary's recommendation) AND annotate T012a with labeling instructions (consistency-checker's recommendation). This closes the gap from both ends.

- **Spec 004's compound implementation label**
  - **scope-boundary's position**: Does not flag the compound implementation label ("Implementation-complete (core) / Not started (discovery)" at STATUS.md L46) as a problem. The review discusses spec 004's acceptance label ambiguity but treats the implementation label as given.
  - **consistency-checker's position**: Flags the compound label as a P1 issue. Argues it does not fit the three-value implementation tier taxonomy and should be normalized to "Partially-complete" with the core/discovery split in the gaps field. (Actionable Recommendations, item 2: "Normalize spec 004's compound implementation label")
  - **Nature of tension**: scope-boundary is focused on Phase 2's acceptance-tier additions and treats the pre-existing implementation-tier labels as out of scope. consistency-checker treats the entire taxonomy (both tiers) as within scope because Phase 2's checkpoint claims "STATUS.md taxonomy is authoritative" (tasks.md L47) — and an authoritative taxonomy must be consistently applied across both tiers.
  - **Coordination needed**: Clarify whether Phase 2's scope includes normalizing pre-existing implementation labels or only adding the new acceptance tier. If Phase 2's checkpoint claim of "authoritative" taxonomy extends to the implementation tier, the compound label must be normalized (consistency-checker's position is correct). If Phase 2 only defines the acceptance tier and inherits implementation labels as-is, the compound label is a pre-existing condition to address in Phase 3 or separately (scope-boundary's implicit position). The checkpoint language ("STATUS.md taxonomy is authoritative") suggests the broader reading.

### Safe Agreements

- **The "Not started" acceptance label is undefined and must be addressed before Phase 3**
  - **Shared position**: Both reviews identify that STATUS.md L41 uses "Not started" in the acceptance tier for spec 003, but the acceptance tier taxonomy (STATUS.md L17-20) only defines "Feature-complete" and "Spec-complete." Both flag this as the highest-priority issue. scope-boundary: "my most important recommendation" (Executive Summary); "the 'Not started' acceptance label used for spec 003 (L41) is not defined in the taxonomy section and is not part of FR-012's two-tier convention" (Missed Opportunities, item 1). consistency-checker: "the single most consequential definitional gap" (Off-Base Assumptions, item 1); "the most critical issue" (Executive Summary).
  - **Combined evidence**: scope-boundary approaches this from the scope-boundary perspective: the label is used but not defined, which contradicts the purpose of a documented convention. consistency-checker approaches from the consistency perspective: the two-value acceptance tier cannot represent the full state space, and Phase 3 tasks (T010, T011, T012a) will inherit this ambiguity. Both arrive at the same conclusion through independent reasoning paths — scope-boundary via "a taxonomy cannot use undefined labels" and consistency-checker via "the state space is larger than the label set." The convergence from different analytical frames makes this finding highly reliable.
  - **Confidence level**: High. This must be resolved before Phase 3 begins. Both reviews agree on the problem, the impact, and the urgency. The only disagreement is the label name (addressed in Dangerous Contradictions above).

- **Spec 004 needs explicit acceptance gap documentation**
  - **Shared position**: Both reviews identify that spec 004's "Feature-complete" acceptance label lacks the gap documentation that spec 001 has. scope-boundary: "spec 004's entry does not state which acceptance criteria are unmet" and recommends adding a `**Gaps**:` line identifying FR-022-024 (Missed Opportunities, item 2; Actionable Recommendations, item 2). consistency-checker: "spec 004's entry lists the core/discovery split but does not state which acceptance criteria gaps prevent it from being 'spec-complete'" and recommends adding acceptance gaps referencing US-3 through US-6 (Missed Opportunities, item 2; Actionable Recommendations, item 3).
  - **Combined evidence**: scope-boundary's evidence is internal consistency: FR-013 sets the precedent that "feature-complete" labels come with documented gaps, and spec 004 does not follow this precedent. consistency-checker's evidence is operational: an implementor reading STATUS.md gets precise guidance for spec 001 but must infer spec 004's gaps from narrative text. Both perspectives reinforce the same conclusion — the gap documentation is necessary for the taxonomy to be useful — through complementary lenses (precedent-consistency and operational-utility).
  - **Confidence level**: High. The disagreement on whether to document gaps as FRs or acceptance scenarios (see Dangerous Contradictions) does not affect the shared conclusion that some gap documentation is required.

- **Phase boundaries are intact — no Phase 3 content has leaked into Phase 2**
  - **Shared position**: Both reviews confirm that Phase 2 only modified STATUS.md with taxonomy and labeling content, and that no Phase 3 content (subsystems, dependencies, risk, effort, structure plan) is present. scope-boundary: "No Phase 3 content leakage" — "no risk-of-gap statements (FR-016, Phase 3 T010), no effort estimates (FR-017, Phase 3 T011), no shared subsystem section (FR-008, Phase 3 T008), and no structure plan (FR-019, Phase 3 T012). Phase 3 content is absent, as it should be." (Alignment, item 5). consistency-checker: "Phase 2 dependency chain is sound" — Phase 2 is correctly foundational and Phase 3's enrichment tasks depend on the taxonomy being defined first (Alignment, item 5).
  - **Combined evidence**: scope-boundary performed an explicit negative check (verified absence of Phase 3 content types). consistency-checker verified the dependency chain (Phase 1 passed, Phase 2 precondition met, Phase 3 prerequisites satisfied). Together, these confirm both that Phase 2 did not include Phase 3 material and that Phase 3 can proceed with confidence that its foundation is in place.
  - **Confidence level**: High. This is a structural finding — the files either contain Phase 3 content or they do not. Both reviews independently confirmed they do not.

- **The "Interpreting the Two Tiers" section is appropriately scoped**
  - **Shared position**: Both reviews accept the one-paragraph orthogonality explanation (STATUS.md L22-24) as necessary and minimal. scope-boundary: "one paragraph of necessary clarification — it explains orthogonality, which is the single non-obvious property of a two-dimensional status system, and does not bloat into a tutorial or guide" (Executive Summary); "The section is minimal and necessary. Both found it satisfactory. The section passes both tests — it is minimal enough to not be scope creep and complete enough to not be ambiguous.

If the taxonomy is extended (e.g., adding a third acceptance label), this section may need a corresponding update, which neither review addresses.
