# Consistency Checker Review — Phase 2: Two-Tier Status Convention

**Reviewer**: consistency-checker
**Date**: 2026-03-20
**Spec**: 005-p2p3-backlog-hardening
**Gate**: Phase 2 (Foundational — Two-Tier Status Convention)
**Target files**: STATUS.md, spec.md, tasks.md

---

### Executive Summary

Spec 005 Phase 2 establishes a two-tier status convention that separates "implementation completeness" (are the FRs in SKILL.md?) from "acceptance completeness" (are the spec's own acceptance criteria met?). This is the foundational taxonomy upon which Phase 3's STATUS.md enrichment depends. The taxonomy is documented in STATUS.md L3-24 and codified in spec.md FR-012/FR-013. My job is to determine whether these definitions are mutually exclusive, whether the labels assigned to specs 001-004 are justified, whether the existing implementation-tier labels are undisturbed, and whether Phase 3 can safely build on this taxonomy without ambiguity.

The taxonomy is well-designed in principle: the two tiers measure genuinely orthogonal dimensions. However, there are real consistency problems in how labels are applied to specific specs, incomplete gap documentation for specs other than 001, and one definition-level ambiguity in the acceptance tier that will cause Phase 3 to apply labels inconsistently if not addressed. The most critical issue is that spec 003's acceptance tier is labeled "Not started" in STATUS.md L41, but the acceptance tier as defined only has two values ("feature-complete" and "spec-complete") — "Not started" is an implementation-tier concept being used in the acceptance tier, which breaks mutual exclusivity.

My single most important recommendation: add a third acceptance-tier label ("not-assessed") or explicitly define when acceptance-tier labels do not apply, because the current two-value acceptance tier cannot cleanly represent specs that have no implementation to assess.

### Alignment

- **[Orthogonal tier design]** (STATUS.md L22-24): The "Interpreting the Two Tiers" section explicitly states that the tiers are orthogonal, with a concrete example of how a spec can be implementation-complete but only feature-complete. This correctly models the real situation — implementation status and acceptance status are genuinely independent dimensions. [tasks.md L36-47, where Phase 2 is scoped to defining exactly this convention]

- **[Spec 001 gap documentation]** (STATUS.md L31-33): Spec 001's acceptance label ("feature-complete") is accompanied by specific FR gap references (FR-023, FR-025, FR-026). This is the correct level of specificity — it names the exact functional requirements that are incomplete and provides a parenthetical explaining the nature of each gap. Cross-referencing with spec 001 spec.md L159-161 and L173, these FRs do exist and describe template-level behavioral instructions, confirming the gaps are real. [spec.md L226, FR-013, which mandates this exact gap documentation]

- **[Implementation-tier definitions are clean]** (STATUS.md L7-13): The three implementation-tier values ("Implementation-complete", "Partially-complete", "Not started") are mutually exclusive and exhaustively partition the space. A spec's FRs are either all in SKILL.md, some in SKILL.md, or none in SKILL.md. No spec can occupy two categories simultaneously. [spec.md L225, FR-012, which only touches acceptance tier and does not modify the existing implementation tier]

- **[Spec 002 labels are justified]** (STATUS.md L36-38): Spec 002 is labeled "Implementation-complete" and "Spec-complete". Cross-referencing with SKILL.md, all 36 spec 002 FRs (FR-001 through FR-036) are represented: rounds config (L34-35, L186-193), round loop (L286-305), stagnation detection (L453-475), cross-round synthesis (L496-521), output directories (L201-232), template variables (L328-334), and reporting (L609-632). The "Spec-complete" acceptance label is justified because there are no documented acceptance criteria gaps. The dependency note on spec 001's dispute-parsing subsystem is appropriate — it flags a runtime correctness dependency, not an implementation gap.

- **[Phase 2 dependency chain is sound]** (tasks.md L38, L111-112): Phase 2 is correctly identified as foundational — Phase 3's STATUS.md enrichment tasks (T008-T012a) depend on the taxonomy being defined first. The Phase 1 summary (final.md L262) confirms Phase 1 passed, so the Phase 2 precondition is met.

### Missed Opportunities

- **[Acceptance tier for specs with zero implementation]**: The acceptance tier defines only two values: "feature-complete" and "spec-complete" (STATUS.md L19-20, spec.md FR-012 L225). Both presuppose that some implementation exists to assess. But spec 003 has "Implementation: Not started" and "Acceptance: Not started" (STATUS.md L41). "Not started" is borrowed from the implementation tier's vocabulary and applied to the acceptance tier, which breaks the taxonomy's stated design. The acceptance tier needs either a third value (e.g., "not-assessed" or "not-applicable") or an explicit rule that acceptance labels only apply when implementation > 0. Without this, Phase 3 tasks (especially T010, T011, T012a) will face ambiguity when assigning acceptance labels to new or unstarted specs. Impact: **high**. [tasks.md L44-46, T006/T007 which define the acceptance labels; STATUS.md L15-20 which define the acceptance tier]

- **[Spec 004 acceptance label justification is absent]**: Spec 004 is labeled "Feature-complete" in STATUS.md L46, but there is no gap documentation explaining why it is feature-complete rather than spec-complete. Spec 001 has explicit gap FRs listed (FR-023, FR-025, FR-026). Spec 004's entry lists the core/discovery split but does not state which acceptance criteria gaps prevent it from being "spec-complete". Looking at spec 004's acceptance criteria: US-1 through US-2 (core) are implemented, but US-3 through US-6 (discovery, custom presets, guided workflow, arbiter integration) are "Not started" per STATUS.md L48. If discovery FRs are not started, the acceptance tier should specify what gaps remain — the current entry only documents implementation gaps, not acceptance gaps. Impact: **medium**. [STATUS.md L46-48; spec 004 spec.md L86-143, US-3 through US-6]

- **[No explicit rule for when a spec transitions between acceptance labels]**: The taxonomy defines what "feature-complete" and "spec-complete" mean (STATUS.md L19-20), but does not define the transition criteria. When does a spec move from feature-complete to spec-complete? The definition says "all acceptance criteria are met," but acceptance criteria live in the spec's "Acceptance Scenarios" sections — there is no mechanism to enumerate which scenarios are met and which are not. For spec 001, the gap FRs (FR-023, FR-025, FR-026) serve as a proxy, but FRs and acceptance scenarios are different constructs. Phase 3 will add risk-of-gap and effort fields (T010, T011) but will not add acceptance-scenario tracking, leaving the transition criteria implicit. Impact: **medium**. [spec.md L225-226, FR-012/FR-013; STATUS.md L19-20]

- **[Spec 005 self-tracking is not addressed in Phase 2]**: Spec.md L279 states "Spec 005 must track itself in STATUS.md to satisfy SC-003." Tasks.md L68 assigns this to T012a in Phase 3. But Phase 2 (T006/T007) only applies acceptance labels to specs 001-004. When T012a runs in Phase 3, it will need to assign both tiers to spec 005 using the taxonomy defined in Phase 2, but there is no guidance in Phase 2's task descriptions about how to classify a spec-in-progress. This is a consistency gap that Phase 3 will inherit. Impact: **low**. [tasks.md L68, T012a; spec.md L279]

- **[Implementation tier label for spec 004 is imprecise]**: STATUS.md L46 labels spec 004 as "Implementation-complete (core) / Not started (discovery)". This is a compound label that does not fit the three-value implementation tier taxonomy defined at STATUS.md L9-13. The closest match is "Partially-complete", but the entry uses a custom format. This inconsistency undermines the taxonomy's value — if compound labels are permitted, the tier is no longer a controlled vocabulary. Impact: **medium**. [STATUS.md L9-13 tier definitions vs. L46 actual label]

- **[Heading match semantics for dispute parsing not in scope for Phase 2 but affects taxonomy application]**: The Phase 1 summary (final.md L107-108) identifies that T019 introduces behavioral expansion to dispute parsing — structural-marker support and case-insensitive heading matching. STATUS.md L63 (T008, Phase 3) plans to note that "stagnation detection does not support structural-marker parsing." But if T019 in Phase 4 changes this, the taxonomy-defined labels in Phase 2 will be technically correct at time of writing but stale immediately after Phase 4. The Phase 1 summary's P2-4 recommendation (final.md L197-203) addresses this with T019-post, but the timing dependency between Phase 2 taxonomy and Phase 4 behavioral changes is not explicit in Phase 2's task descriptions. Impact: **low**. [final.md L197-203; tasks.md L86-87, T019]

### Off-Base Assumptions

- **[Assumption: The two-value acceptance tier is sufficient for all spec states]**: STATUS.md L15-20 defines only "feature-complete" and "spec-complete" in the acceptance tier. But STATUS.md L41 (spec 003) and L48 (spec 004 discovery) use "Not started" — a label from the implementation tier — in the acceptance column. The spec assumes (spec.md L276) that "the two-tier status convention applies to all four existing specs," but the convention as defined cannot represent specs with zero implementation. The correct understanding is that the acceptance tier needs either a third value or an explicit scope restriction (e.g., "acceptance tier applies only to specs with at least partial implementation"). This is the single most consequential definitional gap.

- **[Assumption: Gap documentation for spec 001 is complete]**: Spec.md FR-013 (L226) lists three gaps: FR-023, FR-025, FR-026. STATUS.md L32 documents these same three. But FR-023's parenthetical says "SKILL.md validation logic exists but template-level heading instructions pending." Cross-checking SKILL.md L581-582, the output validation logic does exist and checks the four required headings. However, spec 005 FR-007 (spec.md L211) adds heading match semantics (case-insensitive, heading-level agnostic) that are NOT yet in SKILL.md — they are planned for T013 in Phase 4. So FR-023 is more nuanced than "template-level heading instructions pending": part of it is implemented (the validation check) and part is pending (match semantics per FR-007). The gap documentation is accurate but incomplete in its characterization of what exactly is pending.

### Actionable Recommendations

1. **Add "not-assessed" to the acceptance tier** (Priority: P1)
   - **Current state**: STATUS.md L19-20 defines two acceptance values: "feature-complete" and "spec-complete". STATUS.md L41 uses "Not started" in the acceptance column for spec 003, borrowing from the implementation tier's vocabulary.
   - **Proposed change**: Add a third acceptance-tier value: "Not assessed — No implementation exists to evaluate against acceptance criteria. Acceptance status is pending implementation." Apply this to spec 003 and to spec 004's discovery component. Alternatively, add a scoping rule: "Acceptance labels apply only to specs with at least Partially-complete implementation status. Specs with 'Not started' implementation have no acceptance label."
   - **Rationale**: The two-value acceptance tier cannot represent the full state space. Phase 3 tasks (T010, T011, T012a) will need to assign acceptance labels to spec 005, which is in-progress — the taxonomy must handle this case cleanly. [STATUS.md L15-20 definitions vs. L41 usage]
   - **Risk if ignored**: Phase 3 will apply labels inconsistently. Different contributors will handle unstarted specs differently — some will use "Not started" (borrowing from implementation tier), some will omit the label, some will use "feature-complete" prematurely. SC-005 ("zero labeling disagreements") will fail.

2. **Normalize spec 004's compound implementation label** (Priority: P1)
   - **Current state**: STATUS.md L46 uses "Implementation-complete (core) / Not started (discovery)" — a compound label that does not match any of the three defined implementation-tier values (L9-13).
   - **Proposed change**: Either (a) label spec 004 as "Partially-complete" with the core/discovery split documented in the gaps field, or (b) explicitly permit compound labels in the taxonomy section with a rule like "When a spec has independently-scoped subsections with different implementation statuses, both are listed." Option (a) is simpler and consistent with the three-value taxonomy.
   - **Rationale**: The taxonomy's value comes from being a controlled vocabulary. Compound labels that bypass the taxonomy undermine consistency. [STATUS.md L9-13 vs. L46]
   - **Risk if ignored**: The taxonomy is not actually enforced. Spec 005's own entry (T012a) could use any ad-hoc format, and future specs will follow the precedent of inventing custom labels rather than using the defined values.

3. **Add acceptance gap documentation for spec 004** (Priority: P2)
   - **Current state**: STATUS.md L46-48 documents spec 004's implementation split (core complete, discovery not started) but provides no acceptance-tier gap analysis comparable to spec 001's FR-023/FR-025/FR-026 documentation.
   - **Proposed change**: Add acceptance gaps for spec 004. Based on the spec, the core (FR-001-021) is implemented but acceptance scenarios from US-3 (discovery), US-4 (custom presets), US-5 (guided workflow integration), and US-6 (arbiter preset interaction) are not testable because their features are not implemented. State this explicitly: "Acceptance gaps: US-3 through US-6 acceptance scenarios are not testable (discovery features not implemented)."
   - **Rationale**: Spec 001 has exemplary gap documentation. Spec 004 does not. This asymmetry makes the acceptance tier less useful for spec 004 than for spec 001 — an implementor can determine spec 001's exact remaining work but not spec 004's. [STATUS.md L31-33 vs. L46-48]
   - **Risk if ignored**: An implementor reading STATUS.md gets precise guidance for spec 001 and vague guidance for spec 004. SC-003 ("zero ambiguity about what is safe to build on") is weakened.

4. **Clarify FR-023 gap characterization in STATUS.md** (Priority: P2)
   - **Current state**: STATUS.md L32 says "FR-023 (output validation — SKILL.md validation logic exists but template-level heading instructions pending)". This conflates two distinct sub-issues: (a) the validation logic check (exists at SKILL.md L581-582) and (b) heading match semantics per spec 005 FR-007 (not yet in SKILL.md, planned for T013).
   - **Proposed change**: Revise to: "FR-023 (output validation — SKILL.md validation check exists; heading match semantics (case-insensitive, level-agnostic) pending per spec 005 FR-007; template-level heading instructions pending)."
   - **Rationale**: Precision in gap documentation enables implementors to understand exactly what remains. The current characterization is not wrong but is imprecise enough that an implementor could believe FR-023 is entirely about template instructions, missing the heading match semantics gap. [SKILL.md L581-582; spec.md L211, FR-007; tasks.md L88, T013]
   - **Risk if ignored**: An implementor working on spec 001's remaining gaps may not realize that spec 005 FR-007 contributes to closing FR-023. The cross-spec dependency is hidden.

5. **Define acceptance label transition criteria** (Priority: P2)
   - **Current state**: STATUS.md L19-20 defines what "feature-complete" and "spec-complete" mean but does not define when a spec transitions from one to the other. The definitions are static snapshots, not transition rules.
   - **Proposed change**: Add a brief transition rule to the taxonomy section: "A spec transitions from feature-complete to spec-complete when all acceptance scenarios defined in its spec.md are verified as satisfied. The spec entry's 'Gaps' field tracks what remains."
   - **Rationale**: Without transition criteria, Phase 3 contributors (and future maintainers) must infer when to change a label. Explicit criteria make the label change auditable. [STATUS.md L15-24]
   - **Risk if ignored**: Labels become opinions rather than facts. Two maintainers could disagree about whether spec 001 is still "feature-complete" after T013 adds heading match semantics — one might argue it closes FR-023 and qualifies as spec-complete, another might argue template instructions are still pending.

6. **Verify spec 002 "Spec-complete" label against acceptance scenarios** (Priority: P2)
   - **Current state**: STATUS.md L37 labels spec 002 as "Spec-complete" — meaning all acceptance criteria are met. Spec 002 defines acceptance scenarios in US-1 (7 scenarios), US-2 (4 scenarios), US-3 (3 scenarios), and US-4 (4 scenarios) = 18 total acceptance scenarios across 4 user stories.
   - **Proposed change**: Either (a) verify all 18 acceptance scenarios are satisfied by the current SKILL.md implementation by spot-checking at least the most complex ones (e.g., US-1 AS5 — arbiter runs after final round, US-2 AS3 — stagnation with arbiter configured), or (b) add a note acknowledging that "Spec-complete" is based on FR coverage and the dependency note serves as a caveat. Currently the dependency note mentions "runtime correctness of stagnation detection depends on spec 001's parsing subsystem" — if that dependency means some acceptance scenarios cannot be verified in isolation, "Spec-complete" may be premature.
   - **Rationale**: "Spec-complete" is the strongest label in the taxonomy. It should be defensible. The dependency on spec 001's parsing subsystem is acknowledged but its impact on acceptance completeness is not assessed. [STATUS.md L36-38; spec 002 spec.md US-2 AS3]
   - **Risk if ignored**: The strongest label is applied without verification. If a future audit finds an acceptance gap, the taxonomy's credibility is undermined — if spec 002's "Spec-complete" was wrong, can any label be trusted?

7. **Add explicit guidance for Phase 3 on labeling spec 005 itself** (Priority: P3)
   - **Current state**: T012a (tasks.md L68) instructs adding spec 005 to STATUS.md but does not specify what acceptance label to use. Spec 005 will be partially implemented when T012a runs (Phase 3 will be complete, Phase 4 will not). The taxonomy has no guidance for labeling a spec that is actively being implemented.
   - **Proposed change**: Add a note to T012a: "Label spec 005 implementation status based on FRs completed at time of writing. Label acceptance status as 'feature-complete' with gaps listing the remaining Phase 4 FRs. Update both labels in Phase 5 (T016/T017) to reflect final state."
   - **Rationale**: Without guidance, T012a becomes a judgment call. Explicit instructions prevent inconsistency. [tasks.md L68; spec.md L279]
   - **Risk if ignored**: Minor — the label can be corrected in Phase 5. But it sets a precedent that in-progress specs get ad-hoc treatment rather than principled labeling.

8. **Document the relationship between FRs and acceptance scenarios in the taxonomy** (Priority: P3)
   - **Current state**: The taxonomy tracks implementation via FRs (STATUS.md L9-13, "FRs represented in SKILL.md") and acceptance via acceptance criteria (L15-20, "spec's own acceptance criteria are met"). But gap documentation uses FRs (e.g., spec 001 gaps: FR-023, FR-025, FR-026) as proxies for acceptance gaps. FRs and acceptance scenarios are different constructs — FRs are implementation requirements, acceptance scenarios are testable behaviors.
   - **Proposed change**: Add a clarifying note: "Gap documentation may reference FRs (implementation requirements) or acceptance scenarios (testable behaviors). FRs are used when the gap is at the implementation level. Acceptance scenarios are referenced when the gap is behavioral or testing-related."
   - **Rationale**: Prevents confusion about whether gap documentation tracks implementation gaps, acceptance gaps, or both. Currently the answer is "both, implicitly." [STATUS.md L19-20 acceptance definition vs. L32 FR-based gap documentation]
   - **Risk if ignored**: Low. The current approach works for the four existing specs. But as more specs are added, the conflation of FRs and acceptance scenarios in gap documentation could cause misclassification.
