### Remaining Disputes

- **Dispute: Compound implementation labels vs. normalization to "Partially-complete"**
  - **My claim**: Permit compound labels in the Implementation Tier section, constrained to existing tier values. Retain spec 004's current label format: "Implementation-complete (core) / Not started (discovery)." Add a rule documenting when compound labels are permitted and how they must be structured. (Revision, Recommendation 2, Modified recommendation.)
  - **Opposing position(s)**: scope-boundary's revision (New Recommendations, "Normalize spec 004's compound implementation label") recommends relabeling spec 004 to "Partially-complete" and moving the core/discovery detail into the notes field. scope-boundary argues that an authoritative taxonomy whose entries violate its controlled vocabulary is not authoritative, and that the three-value system should be strictly enforced.
  - **Why I will not concede**: The normalization loses information at the label level. "Partially-complete" tells the reader that something is incomplete but not *what* is complete and what is not. For spec 004, the core engine (FR-001-021) is fully implemented and safe to depend on; the discovery CLI (FR-022-024) is entirely absent. This distinction is operationally critical for spec 003 Phase A development, which depends on the core engine being complete but does not depend on discovery commands. Pushing this information into a notes field means a reader scanning the status table for "can I build on spec 004's core?" must read narrative prose rather than the label itself. The taxonomy's purpose is to enable quick status assessment (STATUS.md L5: "Status uses two tiers measuring different dimensions"). A label that forces readers into the notes field to understand what it means fails that purpose.
  - **Counter-argument to their position**: scope-boundary's argument rests on controlled-vocabulary purity — that a three-value taxonomy must use exactly three values. But the compound label format I propose does not introduce new values; it composes existing ones. "Implementation-complete (core) / Not started (discovery)" uses exactly two of the three defined labels. The controlled vocabulary is preserved at the component level. scope-boundary's analogy to the acceptance tier ("fixing the acceptance tier but leaving the implementation tier's compound label uncorrected") is a false equivalence: the acceptance tier had an *undefined* label ("Not started" used without a taxonomy definition), while spec 004's compound label uses only *defined* labels in a documented structure. taxonomy-reviewer independently reached the same conclusion in their revision (Recommendation 5, Modified recommendation): "compound labels composed of existing tier values preserve the vocabulary while retaining subsystem-level information."
  - **Proposed resolution path**: The synthesizer should adopt compound labels with the constraint that each component must use a defined tier value. This is the position held by both consistency-checker and taxonomy-reviewer. If the synthesizer prefers scope-boundary's normalization approach, it must also specify how spec 005 (which will have its own subsystem variance in T012a) should be labeled — "Partially-complete" without subsystem detail, or with a note. The compound-label convention answers this question proactively; normalization defers it.

- **Dispute: Transition criteria phase placement**
  - **My claim**: Add transition criteria to the Phase 2 taxonomy section as a definitional companion to the label definitions: "A spec transitions from feature-complete to spec-complete when (a) all documented gaps in its Gaps field are resolved and (b) all acceptance scenarios defined in its spec.md are verified as satisfied." (Revision, Recommendation 5, Modified recommendation.)
  - **Opposing position(s)**: taxonomy-reviewer's revision (Recommendation 4, Modified recommendation) refiled transition criteria to Phase 3, arguing they are "operational rules" that belong alongside T008's maintenance obligation rather than alongside label definitions. taxonomy-reviewer explicitly accepted scope-boundary's argument that "Phase 2's task descriptions (tasks.md L44-45) focus on 'add two-tier acceptance convention' (T006) and 'apply acceptance labels' (T007). Neither task mentions transition rules."
  - **Why I will not concede**: Transition criteria are not operational rules — they are the completion condition for a label definition. The taxonomy defines "Feature-complete" (acceptance criteria gaps remain) and "Spec-complete" (all acceptance criteria met). Without a transition rule, the boundary between these two labels is implicit: a reader must infer that "all gaps resolved + all scenarios pass = Spec-complete" from the definitions alone. The dual-condition formulation makes this inference explicit and adds the critical constraint that gap resolution and scenario verification must *both* hold — which is not derivable from the definitions alone (a reader could reasonably argue that scenario verification alone suffices, since gaps are merely documentary). Furthermore, scope-boundary's own revision (Recommendation 5) conceded that "A one-sentence transition rule that clarifies when labels change is defensibly part of defining those labels." That concession supports Phase 2 placement.
  - **Counter-argument to their position**: taxonomy-reviewer's argument that tasks.md L44-45 do not mention transition rules is a weak basis for phase placement. tasks.md is a task decomposition, not a scope definition — it describes *how* to implement the spec, not *what* the spec requires. The spec itself (FR-012) requires establishing the two-tier convention. A convention that defines two labels but not the boundary between them is incomplete. The Phase 3 placement taxonomy-reviewer proposes is also structurally awkward: T008 adds a maintenance note ("this document MUST be updated when status changes") — a process rule about *when to update the file*. Transition criteria define *when a label changes* — a semantic rule about the taxonomy itself. These are different concerns that happen to share the word "when."
  - **Proposed resolution path**: Compromise: add the transition criteria in Phase 2 as part of the taxonomy section but mark them as a "Note" subordinate to the label definitions rather than a peer definition. This preserves Phase 2's scope as definitional while separating the transition rule from the label entries themselves. If the synthesizer prefers Phase 3 placement, the dual-condition formulation (gaps resolved AND scenarios pass) must be preserved — taxonomy-reviewer and I agree on the substance; only the phase is in dispute.

- **Dispute: "Not assessed" definition breadth**
  - **My claim**: The "Not assessed" definition should cover two distinct states: "No acceptance evaluation has been performed. Either no implementation exists to evaluate, or implementation exists but acceptance criteria have not been formally verified." (Revision, Recommendation 1, Modified recommendation.)
  - **Opposing position(s)**: taxonomy-reviewer's revision (Recommendation 1, Modified recommendation) and scope-boundary's revision (Recommendation 1, Modified recommendation) both converge on a shorter single-sentence definition: "No acceptance criteria have been evaluated." Both explicitly dropped the second sentence to preserve orthogonality — taxonomy-reviewer citing scope-boundary's argument that causal explanations reintroduce coupling between tiers.
  - **Why I will not concede**: The single-sentence definition is sufficient for spec 003 (no implementation, no evaluation — the simple case). But it provides no guidance for the ambiguous case that Phase 3 will encounter in T012a: spec 005 will have *partial* implementation with *no formal acceptance evaluation*. An implementor reading "No acceptance criteria have been evaluated" might hesitate to apply this label to a spec with substantial implementation, because the label sounds like it describes the absence of something to evaluate rather than the absence of evaluation itself. My two-clause definition ("Either no implementation exists to evaluate, or implementation exists but acceptance criteria have not been formally verified") explicitly covers the T012a case and prevents the hesitation. This is not coupling — it is disambiguation. The definition does not reference the implementation *tier*; it references the state of the world that an evaluator observes.
  - **Counter-argument to their position**: taxonomy-reviewer and scope-boundary argue that including implementation state in the acceptance-tier definition violates orthogonality. But the short definition has its own problem: it is under-specified for the case it was partly designed to handle. My Recommendation 7 (which I withdrew) would have added a fourth label for this case. Since I withdrew it in favor of the three-label system, the "Not assessed" definition must carry the weight of covering both "nothing to evaluate" and "something to evaluate but not yet evaluated." A single sentence cannot do both without ambiguity.
  - **Proposed resolution path**: If the synthesizer prefers the short definition, add a usage note (not part of the definition itself) in T012a's task description or in the taxonomy section: "This label applies regardless of implementation state — a spec with partial implementation that has not undergone formal acceptance evaluation is 'Not assessed.'" This preserves the short definition's orthogonality while providing the disambiguation Phase 3 needs. I am flexible on whether the disambiguation lives in the definition or in a usage note, but it must exist somewhere before T012a executes.

### Convergence

- **Converged: A third acceptance-tier label named "Not assessed" is required**
  - **Shared position**: Add a third acceptance-tier value named "Not assessed" to STATUS.md's taxonomy section and apply it to spec 003's acceptance tier (replacing the current undefined "Not started" usage). The label name must be distinct from the implementation tier's "Not started" to preserve cross-tier orthogonality.
  - **Agreeing agents**: All three — consistency-checker (Revision, Recommendation 1), taxonomy-reviewer (Revision, Recommendation 1), scope-boundary (Revision, Recommendation 1).
  - **Strength**: Unanimous
  - **Path to convergence**: The problem was identified independently in Phase 1 by all three reviewers. The label *name* was disputed in cross-review (consistency-checker proposed "not-assessed," taxonomy-reviewer and scope-boundary initially proposed "Not started"). Both cross-reviewers conceded on semantic precision grounds during their own cross-reviews, and all three revisions converge on "Not assessed." This is the highest-confidence finding of the entire deliberation.

- **Converged: Spec 004 requires explicit acceptance gap documentation at P1**
  - **Shared position**: Add a `**Gaps**:` line to spec 004's entry in STATUS.md identifying FR-022, FR-023, and FR-024 (discovery commands) as the acceptance criteria gap. This is a P1 item because the Phase 2 checkpoint requires the two-tier convention to be "applied to all 4 specs" (tasks.md L47), and a "Feature-complete" label without enumerated gaps is incomplete application given the precedent set by spec 001 (STATUS.md L32).
  - **Agreeing agents**: All three — consistency-checker (Revision, Recommendation 3), taxonomy-reviewer (Revision, Recommendation 2), scope-boundary (Revision, Recommendation 2).
  - **Strength**: Unanimous
  - **Path to convergence**: All three reviewers identified the need in Phase 1. Priority was disputed: scope-boundary originally assigned P2, taxonomy-reviewer and consistency-checker assigned P1. scope-boundary conceded P1 in their revision, citing the spec 001 precedent argument. The gap *content* (FR-based vs. acceptance-scenario-based) was disputed but resolved toward FR-based references with optional acceptance-scenario parentheticals, consistent with spec 001's existing format.

- **Converged: The "Interpreting the Two Tiers" paragraph is correctly scoped and should not be modified**
  - **Shared position**: STATUS.md L22-24 (the "Interpreting the Two Tiers" section) is minimal and necessary. The dependency sentence is a natural part of explaining orthogonality. No changes are needed, and future expansion should be resisted.
  - **Agreeing agents**: All three — consistency-checker (implicitly, no recommendation to change), taxonomy-reviewer (Revision, Recommendation 8), scope-boundary (Revision, Recommendation 6).
  - **Strength**: Unanimous
  - **Path to convergence**: Agreed from Phase 1. taxonomy-reviewer proactively defended the section; scope-boundary confirmed it as within scope; consistency-checker found no consistency issues with it. No cross-review disputed it. This is a status-quo convergence — all three reviewers evaluated the same content from different perspectives and independently concluded it requires no action.

- **Converged: Spec 005 self-tracking requires both a T007 exclusion note and T012a labeling guidance**
  - **Shared position**: Annotate T007 with "(Spec 005 entry deferred to T012a, Phase 3)" and add labeling guidance to T012a specifying how to assign implementation and acceptance labels to spec 005 based on its state at the time of writing. This closes the Phase 2/Phase 3 handoff from both ends.
  - **Agreeing agents**: All three — consistency-checker (Revision, Recommendation 7), scope-boundary (Revision, Recommendation 4), taxonomy-reviewer (Revision, Recommendation 7, withdrawn but replaced by endorsement of existing labels covering spec 005's state).
  - **Strength**: Unanimous
  - **Path to convergence**: scope-boundary proposed the T007 exclusion note; consistency-checker proposed the T012a labeling guidance; both recognized the complementary nature during cross-review. taxonomy-reviewer withdrew Recommendation 7 (fourth acceptance label) after accepting that the three-label system with "Not assessed" sufficiently covers spec 005's future state, which implicitly endorses the T012a guidance approach.

- **Converged: Transition criteria must use the dual-condition formulation**
  - **Shared position**: When transition criteria are added (whether in Phase 2 or Phase 3), they must require both (a) all documented gaps resolved AND (b) all acceptance scenarios verified as satisfied. The single-condition formulation (scenarios only) is insufficient because it permits "Spec-complete" with unresolved gaps in the Gaps field.
  - **Agreeing agents**: consistency-checker (Revision, Recommendation 5) and taxonomy-reviewer (Revision, Recommendation 4). scope-boundary did not take a position on formulation specifics.
  - **Strength**: Bilateral (consistency-checker + taxonomy-reviewer)
  - **Path to convergence**: consistency-checker originally proposed a single-condition formulation. taxonomy-reviewer's cross-review identified the gap: scenarios could pass while documented gaps remain, creating an inconsistent state. consistency-checker adopted the dual-condition formulation in the revision. The *substance* is agreed; only the *phase placement* remains disputed (see Remaining Disputes above).

### Final Position Statement

**Non-Negotiables** (3 items):

1. **The "Not assessed" label must be added to the acceptance tier and applied to spec 003 before the Phase 2 gate passes.**
   This is non-negotiable because the Phase 2 checkpoint claims "STATUS.md taxonomy is authoritative" (tasks.md L47). A taxonomy that uses an undefined label (STATUS.md L41: "Acceptance: Not started" with no corresponding taxonomy definition) is not authoritative. All three reviewers agree. (Revision, Recommendation 1; STATUS.md L41; tasks.md L47.)

2. **Spec 004 must have explicit acceptance gap documentation using FR-based identifiers before the Phase 2 gate passes.**
   This is non-negotiable because the Phase 2 checkpoint requires the convention to be "applied to all 4 specs." Spec 001 demonstrates the expected format (STATUS.md L32: enumerated FR gaps). Spec 004 uses the same "Feature-complete" label without gap enumeration (STATUS.md L46-48). The taxonomy definition of "Feature-complete" states "acceptance criteria gaps remain" — if gaps remain, they must be listed. All three reviewers agree on substance and P1 priority. (Revision, Recommendation 3; STATUS.md L32, L46-48; tasks.md L47.)

3. **Compound implementation labels must be permitted (not normalized away) if the taxonomy is to accurately represent multi-subsystem specs.**
   This is non-negotiable because normalization to "Partially-complete" destroys operationally critical information. Spec 004's core engine is safe to build on; its discovery CLI is not started. "Partially-complete" erases this distinction. taxonomy-reviewer and consistency-checker agree on this position. (Revision, Recommendation 2; STATUS.md L46; taxonomy-reviewer Revision, Recommendation 5.)

**Flexibility** (3 items):

1. **Transition criteria phase placement (Phase 2 vs. Phase 3).**
   I prefer Phase 2 placement as part of the taxonomy section. However, I will accept Phase 3 placement alongside T008's maintenance note if the dual-condition formulation is preserved and the criteria are explicitly designated as a taxonomy definition (not a process rule). What must be preserved: the dual-condition formulation (gaps resolved AND scenarios pass) and the framing as definitional, not operational.

2. **"Not assessed" definition breadth (two-clause vs. single-sentence).**
   I prefer the two-clause definition that explicitly covers both "no implementation to evaluate" and "implementation exists but not formally evaluated." However, I will accept the single-sentence definition ("No acceptance criteria have been evaluated") if a usage note or T012a annotation makes clear that the label applies regardless of implementation state. What must be preserved: Phase 3 implementors must not be left to infer that "Not assessed" only applies when implementation is zero.

3. **FR-023 gap characterization revision in STATUS.md (Phase 2 fix vs. Phase 4 deferral).**
   I proposed revising the FR-023 parenthetical to mention heading match semantics and T013 (Revision, Recommendation 4). taxonomy-reviewer deferred this to Phase 4 when T013 actually implements FR-007. I will accept Phase 4 deferral if the current parenthetical is acknowledged as incomplete in the synthesis record — so that when T013 executes, the implementor knows to update the FR-023 gap description. What must be preserved: the observation that the current FR-023 characterization in STATUS.md L32 omits the heading-match-semantics dependency is recorded somewhere, even if the fix is deferred.
