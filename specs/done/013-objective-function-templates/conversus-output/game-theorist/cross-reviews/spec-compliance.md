## Dangerous Contradictions

### DC-1. The import-path deviation (FR-011) is flagged as CRITICAL but its risk ranking conflicts with the mathematical correctness failures my review identifies as more severe

spec-compliance labels the `conversus.schemas` vs. `conversus_schemas` import path mismatch as "CRITICAL: Reconcile Import Path (FR-011)" (spec-compliance §Actionable Recommendations, item 1). This framing implies the import path is the most urgent defect in the implementation. My review identifies four structural defects that break the mathematical contract of the templates — the sign-convention inversion in `budget-constrained` and `time-constrained` (O4), the reversed signs in `boundary-negotiation` (O4/R1), the incomplete `form` field in `risk-adversarial` that omits `false_positive_penalty` (O3/R3), and the red-blue/Stackelberg vs. GNEP contradiction in `mode-mapping.yml` (O1/R2). These are not stylistic inconsistencies; they alter equilibrium structures and make templates produce the wrong optimization behavior when consumed programmatically. A consumer who resolves the import path alias and uses the templates as written will still silently maximize cost in `budget-constrained` and maximize boundary violations in `boundary-negotiation`. The contradiction: spec-compliance elevates a naming convention issue to CRITICAL while treating mathematical correctness issues as outside its remit. Those mathematical issues deserve CRITICAL classification before the import path. The two reviews must not coexist as if the import path is the primary risk.

### DC-2. spec-compliance accepts the `example` block format for cross-mode templates as a "missed opportunity," but my review shows those blocks encode the wrong optimization convention

spec-compliance identifies the `example` block inconsistency in cross-mode templates (§Missed Opportunities, item 3: "Off-Base Assumption 3" and Recommendation 3) and frames it as a formatting/uniformity problem — redundant keys like `name`, `form`, `game_form` should be removed from example blocks. My review (O4) identifies that those same cross-mode templates (`budget-constrained`, `time-constrained`) use a maximization convention (`J = quality - beta * cost`) while all mode-specific templates use a minimization convention (`J = -benefit + penalty`). These two observations point at the same YAML blocks but reach incompatible conclusions about what the fix is. spec-compliance's fix (remove redundant keys, standardize format) would leave behind the wrong sign convention. My fix (R1) changes the mathematical expression. If spec-compliance's recommendation is implemented first without correcting the signs, the "cleaned up" examples would still encode the wrong objective. Any team implementing spec-compliance's Recommendation 3 without also implementing my R1 will have neatly formatted templates that produce incorrect optimization behavior. This is a dangerous sequencing contradiction.

### DC-3. spec-compliance's SC-001/SC-002/SC-003 test recommendations would validate templates with known mathematical errors and create a false confidence signal

spec-compliance's Recommendation 2 calls for creating `tests/test_objectives.py` that loads every YAML file and validates it against `ObjectiveTemplate`, asserts invalid modes raise `ValidationError`, and verifies filtering by mode (§Actionable Recommendations, item 2). This is the correct approach for spec compliance testing. However, my review documents that `risk-adversarial.yml` has an incorrect `form` field (O3), `budget-constrained.yml` and `time-constrained.yml` encode the wrong optimization direction (O4), `boundary-negotiation.yml` has reversed signs (O4/R1), and `mode-mapping.yml` assigns the wrong game form to red-blue (O1). spec-compliance's proposed tests would pass on all of these templates because `ObjectiveTemplate` validates schema structure, not mathematical correctness. The tests would pass and signal "templates are valid" while the templates contain correctness errors. This creates a dangerous false positive: a green test suite masks mathematical defects. The two reviews conflict on what "validated" means — spec-compliance means schema-valid, game-theorist means mathematically correct. A test suite that only addresses spec-compliance's criteria is actively misleading about the templates' fitness for use.

### DC-4. spec-compliance does not flag the mode-mapping.yml red-blue contradiction; this gap means its "FR-003 through FR-015 — MET" conclusion is incomplete

spec-compliance's alignment section (§Alignment, item 3: "Constraint Template Schema — MET" and item 2: "Parameter Definitions — MET") reviews implementation compliance at the template-file level and concludes the implementation meets its requirements. My review (O1) documents that `mode-mapping.yml` declares `red-blue: form: gnep` while all three red-blue templates use `game_form: stackelberg`. spec-compliance does not reference `mode-mapping.yml` at all — it does not appear in the Referenced Documentation table. This means spec-compliance's overall "solid and well-structured" verdict (§Executive Summary) is rendered on an incomplete evidence set. The mapping file is not a cosmetic artifact: it is the machine-readable document that guided construction (spec 014) will consult when selecting a game form for a red-blue deliberation. If mode-mapping.yml is wrong, spec 014's pipeline will assign GNEP to red-blue sessions and produce structurally incorrect games. spec-compliance's "MET" verdicts for template-level requirements do not extend to this cross-file consistency question, and the two reviews' combined view of the implementation's status is therefore inconsistent: spec-compliance says "solid," game-theorist says "has a silent GNEP/Stackelberg contradiction in the file that spec 014 will consume."

## Tensions

### T-1. spec-compliance flags the `click` dependency as a potential Section 5 violation; game-theorist did not examine `pyproject.toml`

spec-compliance (§Off-Base Assumptions, item 1) argues that `click>=8.3.1` in `pyproject.toml` potentially violates Section 5's "no library beyond pydantic and pyyaml" constraint and recommends moving it to an optional dependency group. My review did not examine package configuration at all — I focused on game form correctness and mathematical structure. I cannot confirm or contradict this finding from my evidence base. However, the tension is real: if Section 5 is read strictly, the violation applies regardless of whether `click` is "only used by the CLI." The spec says the package must not depend on additional libraries; the package's `pyproject.toml` lists the dependency at the project level. spec-compliance's reading is plausible. The unresolved tension is whether "the package" means the schema module specifically or the conversus project as a whole. A game-theorist lens has no strong prior here, but I would note that if the linter CLI (`conversus-lint`) is itself a deliverable of spec 013, then `click` is a legitimate dependency; if the CLI is out of scope, spec-compliance is correct to flag it.

### T-2. spec-compliance and game-theorist agree the `cooperative-fairness` template is undocumented but disagree on its mathematical quality

spec-compliance (§Missed Opportunities, item 6) flags `cooperative-fairness` as an undocumented addition not in the spec catalog and recommends updating the spec to include it. My review (M8/R8) accepts the template's legitimacy but identifies a dimensional inconsistency: the form `J = -min_i(allocation_i) + phi * variance(allocation)` mixes allocation units with allocation-squared units, making phi's interpretation scale-dependent. spec-compliance's recommendation is "add it to the spec catalog." My recommendation is "fix the dimensional inconsistency before canonizing it." These are not mutually exclusive, but they have different urgency orderings: spec-compliance would add the template to the spec as-is; I would require a mathematical fix first. Adding a dimensionally inconsistent formula to the spec catalog creates a spec-level mathematical error that is harder to correct later. The tension is about whether spec correctness (the formula in the spec should be dimensionally sound) is a precondition for updating the spec catalog, or whether the catalog update and the formula fix are independent tracks. I hold the former: fix first, then canonize.

### T-3. spec-compliance raises the `type: string` overloading problem for structured data; game-theorist identified the same underlying tension via the type-example mismatch in parameter definitions

spec-compliance (§Off-Base Assumptions, item 2) observes that parameters like `Q` in `general-quadratic` are declared `type: string` but represented as YAML native lists in examples. The recommendation (Recommendation 7) is to add an `array` type to the FR-003 vocabulary. My review touches this implicitly through O3 and O4 (the gap between declared forms and actual parameter usage), and through R9's `form_complete` validator recommendation which would surface this mismatch. However, my review did not address the type vocabulary gap directly. The tension here is not contradiction but coverage asymmetry: spec-compliance identifies the type system limitation clearly; I identify the form-completeness gap that is a consequence of the same structural looseness. Both findings point at the same root cause — the schema does not enforce a contract between parameter types, form expressions, and example blocks — but they propose different fixes (add `array` type vs. add a form completeness validator). Both fixes are needed; implementing only one leaves the other gap open.

### T-4. spec-compliance recommends adding `description` to `ConstraintTemplate`; game-theorist's O1 finding implies constraint templates also need a `game_form` field for the red-blue/GNEP contradiction to be resolvable at the constraint level

spec-compliance (§Missed Opportunities, items 7 and 9) recommends adding an optional `description` field to `ConstraintTemplate` for self-documentation and forward compatibility. My review (O1/R2) identifies that the GNEP/Stackelberg contradiction in mode-mapping.yml will cause spec 014's guided construction to misassign game forms. Resolving this contradiction cleanly would benefit from constraint templates also carrying a `game_form_compatibility` field — so that constraints designed for GNEP (coupled constraints) are distinguishable from constraints designed for Stackelberg (hierarchical constraints). spec-compliance's `description` recommendation and my game-form-awareness recommendation are not in tension per se, but they represent different maturity targets for constraint templates. The tension arises if only spec-compliance's recommendation is implemented: constraint templates gain human-readable descriptions but remain game-form-agnostic, meaning the guided construction pipeline still cannot distinguish "this constraint is appropriate for GNEP" from "this constraint is appropriate for Stackelberg." The two recommendations should be sequenced together rather than treated as independent LOW-priority items.

### T-5. spec-compliance's Recommendation 9 (template registry) and game-theorist's R4 (Nash bargaining template) both depend on spec 014 but in different ways — and their coordination matters

spec-compliance (§Missed Opportunities, item 8 and Recommendation 9) recommends a `load_all_templates()` registry function to make SC-003 testable. My review (M1/R4) recommends adding a `cooperative-nash-bargaining` template. Both are correct in isolation. The tension is that adding new templates (my R4, R5, R10) before the registry exists means the registry's initial discovery will pick up mathematically correct but currently unvalidated templates. Conversely, building the registry before fixing the mathematical errors (my R1, R2, R3) means the registry will surface incorrect templates with equal authority as correct ones. spec-compliance's registry recommendation implicitly assumes the template library is in a stable, correct state. My review documents that it is not yet stable. The sequencing should be: (1) fix mathematical errors, (2) build registry, (3) add new templates.

## Safe Agreements

### SA-1. Both reviews agree that `SC-001`, `SC-002`, `SC-003` are untested and that a `tests/test_objectives.py` file is needed

spec-compliance (§Missed Opportunities, items 4 and 5; Recommendation 2) and my review (implicitly, through the form-correctness validators in R9) both conclude that the absence of objective template tests is a significant gap. spec-compliance identifies that the Pydantic model logic for SC-002 and SC-003 is present but unverified; I identify that even passing tests would not catch mathematical errors unless the test suite includes property-based checks. The shared conclusion is unambiguous: no test file for objective templates exists, and the spec's primary success criteria are unverifiable in CI. This is the most immediately actionable shared finding.

### SA-2. Both reviews agree that `cooperative-fairness` is an undocumented addition that requires spec reconciliation

spec-compliance (§Missed Opportunities, item 6; Recommendation 5) and my review (M8) both document that `cooperative-fairness` is not listed in the spec's Section 2 catalog. Both reviews agree the template should be reconciled with the spec — either by updating Section 2 to include it or by marking it as an extension. The disagreement (see T-2) is about whether the dimensional inconsistency must be resolved before the spec update, not about whether the reconciliation is needed. On the core finding — undocumented addition, spec drift, action required — both reviews agree without qualification.

### SA-3. Both reviews agree that the `example` blocks in cross-mode templates are inconsistent with mode-specific templates and require standardization

spec-compliance (§Missed Opportunities, item 3; §Off-Base Assumptions, item 3) identifies that cross-mode template examples include non-parameter keys (`name`, `form`, `game_form`, `computed_objective`) absent from mode-specific examples, and that the `ObjectiveTemplate` model accepts this because `example` is typed as `dict[str, Any]`. My review (O4) arrives at the same cross-mode templates from a different angle — the sign convention mismatch — and agrees that the cross-mode template `example` blocks are structurally inconsistent. Both reviews recommend that the `example` format be standardized across all templates. The specific fixes differ (spec-compliance: remove redundant keys; game-theorist: also fix signs), but the diagnosis that cross-mode templates are the locus of inconsistency is shared and well-supported by evidence from both perspectives.

### SA-4. Both reviews agree that the `form` field lacks enforcement — the Pydantic model does not validate that form expressions are internally consistent with parameter definitions

spec-compliance (§Off-Base Assumptions, items 2 and 3) and my review (O3, R9) both identify that the `ObjectiveTemplate` model validates the presence of fields but not the semantic consistency between `form` and `parameters`. spec-compliance observes this through the type-example mismatch (`type: string` vs. YAML-native list in examples). My review observes this through the missing `false_positive_penalty` term in `risk-adversarial`'s declared form. Both findings point at the same structural weakness: the `form` field is a free-text string and the `parameters` list is a separate collection, with no machine-enforced contract between them. My R9 (add a `form_complete` validator that checks parameter names appear in the form string) directly addresses this gap. spec-compliance does not propose an equivalent validator but agrees the loose typing creates ambiguity. The shared recommendation is that the schema should enforce tighter form-parameter consistency.
