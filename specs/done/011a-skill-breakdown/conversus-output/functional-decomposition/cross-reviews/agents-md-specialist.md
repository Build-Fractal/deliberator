# Cross-Review of agents-md-specialist — by functional-decomposition

## Dangerous Contradictions

### 1. Contribution guidance extraction will not meaningfully reduce SKILL.md

agents-md-specialist estimates "200-400 tokens" of savings from moving contribution-oriented content out of SKILL.md into AGENTS.md files (agents-md-specialist review, Actionable Recommendation 8). My review identifies that the real decomposition opportunity is in the *execution* specification — extracting subcommand handlers, multi-round orchestration, and the gate specification to `references/` files, yielding a 60-75% reduction in per-invocation context load (functional-decomposition review, Executive Summary; Recommendations 1-4). These two analyses are not additive — they address the same file from opposite ends — and the danger is that pursuing the AGENTS.md strategy *first* creates a false sense of progress. A 200-400 token reduction against a 31,000-token file is a rounding error. If the team ships nested AGENTS.md files and declares the decomposition "done," the actual problem — every `/conversus define` invocation paying 31k tokens for 2k tokens of relevant content — remains untouched. The spec's goal (011a, line 1: "our conversus/SKILL.md has grown quite large") is about SKILL.md size, not AGENTS.md coverage. The AGENTS.md work is valuable on its own merits but must not be conflated with the SKILL.md decomposition.

### 2. Nested AGENTS.md files risk duplicating rather than replacing SKILL.md content

agents-md-specialist recommends creating four nested AGENTS.md files (`templates/`, `presets/`, `schema/`, `linter/`) that document template naming conventions, preset validation rules, schema contribution workflows, and linter invocation (agents-md-specialist review, Recommendations 1-4). My review identifies the same content blocks in SKILL.md (template naming at L283-289, preset validation at L139-145, linter invocation at L309) as extraction candidates — but into `references/` files loaded conditionally by the skill runtime (functional-decomposition review, Missed Opportunities: validation logic duplication). The contradiction: if template naming rules exist in both `templates/AGENTS.md` (for cross-agent contribution) and in `references/validation-contract.md` (for runtime enforcement), the same rules are maintained in two places with no synchronization mechanism. agents-md-specialist explicitly warns against moving execution logic into AGENTS.md (review, Off-Base Assumption 1), but does not address the reverse problem — that contribution rules documented in AGENTS.md will drift from the runtime specification in SKILL.md or its `references/` extracts. One canonical source must own each rule, with the other referencing it. Neither review proposes this cross-referencing mechanism.

### 3. The "100 lines per AGENTS.md" guideline conflicts with the prescribed content scope

agents-md-specialist recommends keeping each nested AGENTS.md under 100 lines (Recommendation 9) while also prescribing substantial content for each: `templates/AGENTS.md` should cover 7 required files per mode, variable syntax, structural markers, heading-change coordination rules, and validation commands (Recommendation 1, estimated at 40-60 lines); `presets/AGENTS.md` should cover directory structure, naming invariants, required/optional fields, composition rules, and examples (Recommendation 2, estimated at 30-50 lines). My review's analysis of the validation logic alone (functional-decomposition review, Recommendation 6) identifies five distinct validation patterns (heading checks, name patterns, path existence, post-write validation, schema validation) that would need to be documented in the relevant AGENTS.md files. The agentskills best practices warn against exactly this scenario: "Overly comprehensive skills can hurt more than they help — the agent struggles to extract what's relevant" (agentskills-best-practices.md, L150-152). The same principle applies to AGENTS.md files. If each nested file approaches 100 lines of dense contribution rules, and an agent opens a template file in the `templates/` directory, it receives 100 lines of AGENTS.md context that competes for attention with the actual editing task. The per-file line estimates are optimistic given the prescribed scope.

### 4. Treating AGENTS.md as the primary cross-agent compatibility mechanism ignores the spec's other options

agents-md-specialist frames the review around AGENTS.md as the key mechanism for cross-agent compatibility (Executive Summary, paragraph 3; Missed Opportunity on cross-agent testing). The spec (011a) lists four options: agentskills.io, agents.md, APM, and openspec.dev. My review focuses on agentskills.io `references/` as the primary decomposition mechanism because it addresses the core problem (SKILL.md size) while preserving execution fidelity (functional-decomposition review, Recommendations 1-5). agents-md-specialist correctly notes that "other agents cannot execute `/conversus run`" (Off-Base Assumption 2) — so the cross-agent benefit is limited to contribution, not usage. Yet the review devotes the majority of its recommendations to the cross-agent contribution use case (8 of 10 recommendations involve AGENTS.md) rather than the SKILL.md decomposition that the spec actually requests. This is a scope mismatch: the spec asks how to make SKILL.md smaller; agents-md-specialist answers how to make contribution more accessible.

## Tensions

### 1. Where contribution rules should live: AGENTS.md vs. SKILL.md references

agents-md-specialist argues that contribution rules (template naming, preset validation, linter invocation) belong in AGENTS.md because they are "contribution guidelines, not execution rules" (Recommendation 8). My review argues that validation logic should be centralized in `references/validation-contract.md` because the same rules are enforced at runtime (functional-decomposition review, Recommendation 6). The tension is real: some rules *are* both contribution guidelines and runtime enforcement. The template naming convention is enforced by the linter at contribution time and by the template-loading subsystem at runtime. Neither review addresses how to handle rules that span both audiences. A resolution might be: the `references/` file owns the canonical definition, and AGENTS.md files reference it with a pointer ("See `references/validation-contract.md` for the authoritative naming rules") rather than restating it.

### 2. Whether the SKILL.md size problem is about absolute tokens or conditional relevance

agents-md-specialist treats the size problem as partly about cross-agent accessibility: "an agent editing a preset in Cursor or Copilot has no way to discover these constraints — they are locked inside a Claude Code-specific SKILL.md" (Missed Opportunity 2). My review treats the size problem as primarily about conditional relevance: "The metric that matters is the ratio of relevant tokens to loaded tokens per subcommand, not the absolute size" (Off-Base Assumption 3). Both framings are valid, but they lead to different solutions. The conditional relevance framing prioritizes `references/` extraction with load triggers. The cross-agent accessibility framing prioritizes AGENTS.md proliferation. The spec (011a) does not disambiguate — it says "grown quite large" without specifying whether the concern is runtime cost or developer experience. This tension cannot be resolved without clarifying the spec's intent, but both approaches can proceed in parallel since they target different file types.

### 3. Whether root AGENTS.md should grow or stay lean

agents-md-specialist recommends adding multiple new sections to the root AGENTS.md: testing, commit conventions, file relationship documentation, antipattern catalog references, and CLAUDE.md cross-references (Recommendations 5, 7). This would expand the current 51-line file significantly. My review does not address AGENTS.md content directly, but the underlying principle of my analysis — that loaded content should be proportional to immediate need — applies equally. The agentskills best practices state that "concise, stepwise guidance with a working example tends to outperform exhaustive documentation" (agentskills-best-practices.md, L152). A root AGENTS.md that grows from 51 lines to 120+ lines starts to become the kind of "documentation dump" that agents-md-specialist's own Recommendation 9 warns against. The tension is between comprehensiveness (everything an agent contributing to conversus needs) and conciseness (agents read the nearest AGENTS.md and need it to be digestible).

### 4. Whether the linter is a contribution tool or a runtime tool

agents-md-specialist categorizes the linter exclusively as a contribution workflow tool and recommends documenting it in `linter/AGENTS.md` (Recommendation 4). My review identifies validation logic as a cross-cutting concern used by both the linter and the runtime (functional-decomposition review, Recommendation 6: five handlers implement overlapping validation). If the linter's validation rules are the same rules the SKILL.md runtime enforces, then `linter/AGENTS.md` and `references/validation-contract.md` describe overlapping territory. The linter is both a contribution tool (run before committing) and a runtime dependency (the SKILL.md validation steps mirror its checks). This dual nature means the linter documentation belongs partly in AGENTS.md (how to run it) and partly in `references/` (what it validates), but neither review draws this boundary explicitly.

### 5. Scope of the spec itself

agents-md-specialist interprets the spec broadly — as an opportunity to improve the entire conversus developer experience across multiple agent platforms (Executive Summary, paragraph 3). My review interprets the spec narrowly — as a directive to reduce SKILL.md's token footprint through structural decomposition (Executive Summary, paragraph 2). The spec's single-sentence prompt ("look at for opportunities to offload some of the work") is genuinely ambiguous. The broad interpretation leads to the AGENTS.md recommendations; the narrow interpretation leads to the `references/` extraction plan. Both are legitimate responses, but they require different levels of effort, produce different deliverables, and should be prioritized independently.

## Safe Agreements

### 1. SKILL.md execution logic must not move to AGENTS.md

Both reviews explicitly agree on this boundary. agents-md-specialist states: "AGENTS.md cannot replace any part of SKILL.md's execution specification" and "Do not move execution logic from SKILL.md to AGENTS.md" (Off-Base Assumption 1; Recommendation 6). My review treats the entire SKILL.md as an execution specification amenable only to `references/` extraction, not AGENTS.md migration (functional-decomposition review, Recommendations 1-7). The agentskills best practices support this: `references/` files are first-class execution context loaded on demand, while AGENTS.md is a contribution guide read at edit time (agentskills-best-practices.md, L154-156). This agreement establishes a clear constraint for the implementation: any SKILL.md decomposition must use `references/` (or equivalent agentskills mechanisms), not AGENTS.md.

### 2. The existing AGENTS.md is stale and needs updating regardless of decomposition strategy

agents-md-specialist identifies that the structure section lists `tasks/` (no longer present) and omits `schema/`, `linter/`, `presets/`, `antipatterns/`, and `.specify/` (Alignment, point 6). My review does not address AGENTS.md content directly, but the staleness is independently verifiable by comparing the AGENTS.md structure section (AGENTS.md lines 16-30) with the actual directory listing. Both reviews agree the file needs updating. This is a low-risk, high-value change that can proceed immediately regardless of which decomposition strategy is adopted.

### 3. The conversus SKILL.md contains natural decomposition seams

agents-md-specialist identifies that contribution-oriented content is "buried in the monolithic SKILL.md" at specific, extractable locations (Executive Summary, paragraph 3: template naming on line ~283, preset validation on line ~139). My review identifies the same sections plus larger structural units (gate handler at L1881-2178, guided handlers at L781-1879, multi-round orchestration at L248-610) as having clean extraction boundaries with well-defined inputs and outputs (functional-decomposition review, Recommendations 1-4). Both reviews agree the file is decomposable — the seams exist and are well-defined. The disagreement is about *where* to extract the content to (AGENTS.md vs. `references/`), not about *whether* extraction is feasible.

### 4. Progressive disclosure is the correct architectural pattern for this decomposition

agents-md-specialist's recommendation structure implicitly follows progressive disclosure: root AGENTS.md for orientation, nested AGENTS.md files for directory-specific rules (Recommendations 1-5). My review explicitly invokes the agentskills progressive disclosure pattern: "Keep your main SKILL.md under 500 lines. Move detailed reference material to separate files" (functional-decomposition review, Missed Opportunity 1, citing agentskills-spec.md L384-387). Both reviews apply the same principle — load detailed content only when the agent is in the relevant context — through different mechanisms (directory-scoped AGENTS.md vs. conditional `references/` loading). The shared architectural pattern means the two strategies are structurally compatible and can coexist.
