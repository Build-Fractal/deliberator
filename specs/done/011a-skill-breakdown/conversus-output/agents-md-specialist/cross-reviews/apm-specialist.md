# Cross-Review of apm-specialist — by agents-md-specialist

## Dangerous Contradictions

### 1. Mode specifications as APM context files vs. runtime execution requirements

apm-specialist recommends moving mode specifications into `.apm/context/modes/cooperative.context.md` etc. (Recommendation 2), framing these as reference documentation that APM's context linking can manage. My review explicitly warns that "moving template variable contracts, phase orchestration rules, or dispute-parsing logic into AGENTS.md would make them invisible to the conversus runtime" (agents-md-specialist, Off-Base Assumptions). The same danger applies to APM context files. Mode specifications are not reference documentation — they are runtime execution logic that the orchestrating agent must follow during active deliberation phases. APM context files are discovered at compile/install time and placed for agent awareness, but they have no guaranteed loading mechanism during a skill's runtime execution. If mode specs are extracted from SKILL.md into context primitives, the conversus engine loses the guarantee that the executing agent has the active mode's rules in its working context. The SKILL.md monolith is large precisely because all mode rules must be available to the executing agent at runtime. Moving them to context files trades a context-window problem for a correctness problem.

### 2. The Dispute-Parsing Subsystem cannot be a context file

apm-specialist recommends extracting the Dispute-Parsing Subsystem into `.apm/context/dispute-parsing.context.md` (Recommendation 4), describing it as a "stable interface" with "defined inputs, outputs, parsing rules." My review identifies the same subsystem as important but notes that execution logic belongs in SKILL.md: "The subcommand dispatch table, phase orchestration, template variable expansion, dispute-parsing subsystem, and agent isolation rules are all runtime specifications" (agents-md-specialist, Recommendation 6). The dispute-parsing subsystem is not background knowledge for agent awareness — it is an algorithm the executing agent must follow step-by-step when processing synthesis outputs. Converting it to a context file downgrades it from "instructions the agent must execute" to "information the agent should be aware of." APM's context primitive model does not carry execution authority. If an agent reads a `.context.md` file about dispute parsing, there is no contract that it will follow the parsing rules with the same fidelity as when those rules are embedded in the active skill specification. This is the most dangerous recommendation in the apm-specialist review because dispute parsing directly determines whether rounds continue or terminate.

### 3. PostToolUse hook for template validation conflates contribution-time and execution-time

apm-specialist proposes a PostToolUse hook (Recommendation 6) that triggers `linter/validate.py` when files in `templates/` are modified. My review recommends the same validation be surfaced via `templates/AGENTS.md` and `linter/AGENTS.md` (Recommendations 1 and 4) as contribution guidance. The contradiction is in the mechanism: APM hooks fire during agent tool execution inside a Claude Code session, but template editing may happen in any agent (Cursor, Copilot, Codex, Junie). A PostToolUse hook only protects Claude Code users. Worse, it fires on every template write during normal conversus operation — when the engine itself generates output files in the output directory. If the hook's glob pattern is not carefully scoped to source templates (not output), it would interrupt deliberation runs with linter invocations on generated content. The AGENTS.md approach surfaces the validation requirement to all agents at edit-time without the risk of runtime interference. The hook is not wrong in principle, but deploying it without acknowledging its scope limitation (Claude Code only) and its runtime collision risk (firing during deliberation) is dangerous.

### 4. Sub-skill promotion assumes runtime selectivity that does not exist

apm-specialist's central recommendation (Recommendation 1) proposes three sub-skills: conversus-engine, conversus-wizard, and conversus-gate, arguing that "agent runtimes can load only the relevant subcommand's specification." The apm-specialist review itself notes in Off-Base Assumptions that "skills are copied whole to `.github/skills/`" and that the benefit is "load-time selectivity." But the review does not address who performs this selection. When a user invokes `/conversus run`, the Claude Code runtime loads the skill matching the invocation. If sub-skills are deployed to `.github/skills/conversus-engine/`, `.github/skills/conversus-wizard/`, and `.github/skills/conversus-gate/`, the user must know to invoke `/conversus-engine run` or `/conversus-wizard define` — breaking the unified `/conversus` dispatch interface documented in SKILL.md lines 22-44. My review notes that "SKILL.md has features AGENTS.md cannot replicate: YAML frontmatter, tool permissions, activation triggers" (Alignment point 4). The root SKILL.md's dispatch table is itself an activation mechanism. Splitting into sub-skills either requires a root dispatcher skill that re-invokes sub-skills (adding indirection and context overhead) or requires users to learn a new invocation model. Neither option is addressed.

## Tensions

### 1. Scope of "contribution guidelines" extraction from SKILL.md

Both reviews agree that SKILL.md contains contribution-oriented content that does not belong in an execution specification. My review identifies specific lines: antipattern check (line 239), template naming (line 283), preset validation (lines 139-145), linter invocation (line 309), and recommends moving them to AGENTS.md files (Recommendation 8, estimating 200-400 token savings). apm-specialist takes a broader view, proposing that presets, mode specs, the dispute-parsing subsystem, the antipattern catalog, and the schema directory all be extracted into APM primitives (Recommendations 2-5, 7). The tension is quantitative: my approach yields modest SKILL.md reduction (~200-400 tokens) with zero execution risk, while the apm-specialist approach promises dramatic reduction (~1000+ lines moved to context files and sub-skills) but requires the executing agent to reassemble information from multiple files. Both are valid strategies, but they pull in opposite directions on the tradeoff between context-window relief and execution integrity. The resolution likely requires a hybrid: move contribution rules to AGENTS.md (safe, agent-universal), keep execution logic in SKILL.md but refactor internally using agentskills.io reference files (safe, runtime-aware), and use APM sub-skills only for genuinely independent subcommands (gate).

### 2. Preset system as APM sub-skill vs. AGENTS.md contribution target

apm-specialist recommends registering presets as an APM sub-skill (`.apm/skills/conversus-presets/SKILL.md`, Recommendation 3) while correctly noting that "presets are tightly coupled to conversus's composition template system" and should not be independent packages (Off-Base Assumptions). My review recommends a `presets/AGENTS.md` (Recommendation 2) documenting naming invariants, required fields, and composition rules. These are not contradictory — both could exist — but they serve different purposes and there is tension about which is primary. The APM sub-skill makes presets "discoverable via APM's skill system," but presets are discovered by the conversus engine at runtime, not by APM at install time. The AGENTS.md makes preset contribution rules visible to any editing agent, which is the actual need (agents creating or modifying preset files). The risk is duplicating preset documentation in two places (APM sub-skill SKILL.md and presets/AGENTS.md) with inevitable drift.

### 3. Timing of structural changes vs. spec stability

apm-specialist explicitly recommends deferring full APM distribution (Recommendation 8) but proceeding immediately with sub-skill creation (Recommendation 1: "Create `.apm/skills/` directory with three sub-skills immediately"). My review does not address timing directly but implicitly assumes a lighter-touch approach (creating AGENTS.md files is low-overhead and reversible). The tension is that creating three sub-skills with context files, hooks, and schema primitives during active spec development (specs 001-011a and counting) creates structural commitments that constrain future spec evolution. If spec 012 adds a new subcommand, it must be assigned to a sub-skill. If spec 013 restructures the dispute-parsing subsystem, the context file must be updated alongside the sub-skill SKILL.md. AGENTS.md files, by contrast, are lightweight and can be updated or deleted without affecting the package structure. The apm-specialist acknowledges this risk in the executive summary ("premature packaging creates maintenance drag") but then proceeds to recommend substantial packaging work.

### 4. Antipattern catalog placement

apm-specialist recommends converting the antipattern catalog to an APM context primitive (`.apm/context/antipatterns.context.md`, Recommendation 5). My review recommends mentioning it in the root AGENTS.md and possibly creating an `antipatterns/AGENTS.md` if the catalog grows (Recommendations 5 and 10). The tension: APM context primitives are compiled and distributed by APM's machinery, making them available to consuming projects. AGENTS.md files are read by agents at edit-time in the local directory. If the antipattern catalog is meant to guide agents *contributing to conversus* (do not introduce these patterns), AGENTS.md is the right vehicle. If it is meant to be *consumed by the conversus engine at runtime* (check the target for these patterns), it belongs in SKILL.md or a reference file. apm-specialist frames it as a discovery problem ("discoverable by APM's compilation system and linkable from other primitives"), which assumes the antipatterns have value beyond the conversus project. Currently, they are conversus-specific deliberation antipatterns, making AGENTS.md the simpler and more appropriate home.

### 5. Root SKILL.md size after decomposition

apm-specialist envisions a root SKILL.md of ~100-150 lines containing a dispatch table, dependency graph, and shared interfaces (Recommendation 10). My review envisions SKILL.md remaining the primary execution specification, reduced by ~200-400 tokens from contribution-guideline extraction. These lead to very different end states: apm-specialist's approach produces a thin dispatcher with three substantial sub-skills; my approach produces a slightly slimmer but still monolithic execution spec with companion AGENTS.md files. The tension is about what the "right size" for SKILL.md is. A 100-150 line dispatcher requires agents to load sub-skills on demand, adding file reads and context switches during execution. A ~2000 line monolith wastes context on irrelevant modes and subcommands. Neither review proposes the middle ground that the spec's other references (agentskills.io) might enable: a ~800-1000 line SKILL.md with mode-specific details offloaded to reference files that the skill itself links to.

## Safe Agreements

### 1. The SKILL.md at 2200+ lines is too large and must be decomposed

apm-specialist opens with: "At 119KB / 2200+ lines, this exceeds any reasonable context window budget for a single skill" (Alignment). My review states the same problem from the AGENTS.md perspective: the monolithic SKILL.md buries contribution guidelines inside execution logic, making both less effective. Both reviews agree that the status quo is unsustainable and that structural decomposition is needed. The disagreement is on mechanism and boundary, not on the diagnosis.

### 2. The gate subcommand is the cleanest extraction boundary

apm-specialist identifies gate as "architecturally independent" with "its only dependency on the rest of SKILL.md [being] the run engine and the Dispute-Parsing Subsystem" (Alignment). My review does not specifically call out gate, but the recommendation to keep execution logic in SKILL.md (Recommendation 6) implicitly carves out gate as the exception — it has a distinct input (gates.yml), output (gate-result.md), and use case (CI/CD integration) that separates it from the interactive deliberation workflow. Both reviews converge on gate as the lowest-risk, highest-value extraction target, regardless of whether the extraction uses APM sub-skills or a simpler file split.

### 3. Contribution guidelines are currently invisible to non-Claude-Code agents

apm-specialist notes the lack of a `.apm/skills/` directory despite the `type: skill` declaration (Missed Opportunities). My review identifies the same gap from the AGENTS.md angle: "An agent editing a preset in Cursor or Copilot has no way to discover these constraints — they are locked inside a Claude Code-specific SKILL.md" (Missed Opportunities). Both reviews agree that the current structure serves only Claude Code users and that contribution rules must be surfaced through agent-universal mechanisms. The reviews differ on whether APM context files or AGENTS.md files are the right mechanism, but the underlying diagnosis is shared.

### 4. Full APM distribution should be deferred

apm-specialist explicitly recommends deferring full distribution: "do not publish it to a package registry until the spec development cadence slows" (Recommendation 8). My review implicitly supports this by recommending lightweight AGENTS.md additions rather than structural packaging changes. Both reviews recognize that conversus is a single-project, actively-evolving framework where the overhead of version management, dependency resolution, and multi-target deployment is not yet justified. Internal structural improvements (whether sub-skills or nested AGENTS.md files) provide the immediate benefits without the distribution tax.
