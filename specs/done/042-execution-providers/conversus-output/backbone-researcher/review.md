# Backbone Researcher: Ground Truth on Production Agent Tool Runtimes

**Role**: Tooling archaeologist for spec 042 (execution provider architecture).
**Date**: 2026-04-03
**Goal**: Establish FACTUAL ground truth about how shipping agent tools actually dispatch work, so other deliberation agents can argue from evidence rather than assumption.

This report avoids advocacy. Where I could not verify a claim, I say so explicitly.

---

## 0. TL;DR — What's actually under the hood

1. **Claude Code** does not expose its in-session `Agent`/`Task` tool to external programs. The only public primitive is `@anthropic-ai/claude-agent-sdk` (TS) / `claude-agent-sdk` (Python), and **both SDKs are thin wrappers that spawn the `claude` CLI binary as a subprocess and speak JSON-RPC over stdio**. The CLI binary is bundled into the PyPI/npm package. There is no direct-to-API mode.
2. **OpenCode** is the only mainstream coding agent with a genuine, first-class HTTP REST API: `opencode serve` exposes an OpenAPI 3.1 spec at `/doc`, and there are official TypeScript (`@opencode-ai/sdk`) and Go (`github.com/sst/opencode-sdk-go`) SDKs generated by Stainless. **There is no official Python SDK**. It also supports the Zed/JetBrains ACP over stdio via `opencode acp`.
3. **Aider** has no official Python SDK. There is an **unofficial, unsupported** Python API (`from aider.coders import Coder`) that the docs explicitly warn "could change in future releases without providing backwards compatibility." Primary interface is CLI + subprocess.
4. **Cursor / Windsurf** are closed-source VS Code forks. No public agent-dispatch primitive, no SDK. Both consume MCP for tool access but expose nothing.
5. **Continue.dev / Cline** are open-source VS Code/JetBrains extensions. Continue ships an open-source CLI (`@continuedev/cli`, the `cn` command). Cline is a VS Code extension with no headless mode.
6. **"ACP"** is an ambiguous term in the current (2026-04) landscape. **Two different protocols share the name**:
   - **IBM ACP → merged into Google A2A** (Aug 2025, Linux Foundation governance): agent-to-agent dispatch, JSON-RPC 2.0 over HTTP(S). Python SDK `a2a-sdk` on PyPI (0.3.25 stable, 1.0.0a0 pre-release as of 2026-03).
   - **Zed/JetBrains Agent Client Protocol (agentclientprotocol.com)**: IDE-to-coding-agent, "LSP for agents", JSON-RPC over stdio (with experimental HTTP/WebSocket). Official SDKs in Rust, TypeScript, Python, Kotlin, Java. v0.11.4 (March 2026) — not 1.0 yet.
   - **Spec 042 currently conflates these two.** See §6 below — this is a correctness issue in the spec and other deliberation agents must not assume either protocol alone covers both layers.
7. **GitHub Agentic Workflows (gh-aw)** is a Go CLI that compiles natural-language markdown workflows into hardened `.github/workflows/*.lock.yml` files. Supported "engines" are Claude Code, GitHub Copilot CLI, and OpenAI Codex. It is not a runtime — it is a code generator that emits GitHub Actions YAML which then runs one of those CLIs inside Actions runners.
8. **There is no common programmatic primitive shared across these tools.** MCP is shared for tool exposure (model → tool), but MCP does not define agent dispatch. A2A is a shared protocol for agent-to-agent dispatch but is very early (1.0.0a0); only Google/IBM/BeeAI reference implementations are visible. Every shipping tool has its own bespoke dispatch mechanism at the boundary — subprocess + CLI flags, or HTTP.

## 1. Claude Code / Claude Agent SDK

### 1.1 Package identity
- **Python**: `claude-agent-sdk` on PyPI. Current version **0.1.56** (2026-04-04). MIT license. Requires Python ≥3.10. Marked "Alpha" development status.
- **TypeScript**: `@anthropic-ai/claude-agent-sdk` on npm. Same author (Anthropic), Node ≥18.
- **Repos**: `github.com/anthropics/claude-agent-sdk-python`, `github.com/anthropics/claude-agent-sdk-typescript`.
- The SDK was formerly called "Claude Code SDK"; renamed to "Claude Agent SDK". Docs explicitly cover this rename.

### 1.2 Architecture — subprocess, not API
From the Python SDK README and Anthropic's own docs (code.claude.com/docs/en/headless and platform.claude.com/docs/en/agent-sdk/overview):

> "The Claude Code CLI is automatically bundled with the package - no separate installation required! The SDK will use the bundled CLI by default."

Concrete architectural facts:

- The SDK **spawns a subprocess** running the bundled `claude` CLI binary. It does not call the Anthropic `/v1/messages` API directly.
- Platform-specific wheels ship prebuilt CLI binaries for macOS arm64/x86_64, Linux x86_64/arm64, and Windows x86_64.
- You can override with `ClaudeAgentOptions(cli_path="/path/to/claude")`.
- Exposed error classes `CLINotFoundError`, `CLIConnectionError`, `ProcessError`, `CLIJSONDecodeError` confirm subprocess + stdio-JSON architecture.
- The TypeScript SDK exposes a `spawnClaudeCodeProcess` customization hook, further confirming subprocess dispatch.
- Anthropic's own comparison docs call out: "Client SDK: direct API access, you implement the tool loop. **Agent SDK**: Claude handles tools autonomously" — the differentiator IS the agent loop, which lives inside the CLI binary.

**Corollary**: Using the Agent SDK gives you the entire Claude Code agent loop as a library, but you are paying the subprocess-spawn cost per call and depending on a bundled prebuilt binary.

### 1.3 Public primitive: `query()` + `ClaudeSDKClient`

Two entry points, both async:

```python
# One-shot (stateless)
async for message in query(prompt="...", options=ClaudeAgentOptions(...)):
    ...

# Bidirectional / multi-turn
async with ClaudeSDKClient(options=options) as client:
    await client.query("...")
    async for msg in client.receive_response():
        ...
```

`ClaudeAgentOptions` fields of note: `allowed_tools`, `disallowed_tools`, `permission_mode`, `cwd`, `system_prompt`, `mcp_servers`, `agents` (AgentDefinition map), `hooks`, `setting_sources`, `resume` (session id).

### 1.4 The `Agent` tool — is it exposed externally?

**This is the precise question the caller asked.** The answer is nuanced:

- Inside a Claude Code session (including the SDK), there is a tool named `Agent` (formerly `Task`, renamed in Claude Code v2.1.63). It spawns a subagent in an isolated context window. This is what conversus SKILL.md uses when it "dispatches" agent work via `run_in_background=True`.
- This tool is **only usable from within a Claude session** — it is invoked by the model via tool_use blocks. It is not a standalone API endpoint.
- You can programmatically access it from outside Claude Code by (a) starting a `query()` or `ClaudeSDKClient`, (b) defining custom `agents={...}` in options, (c) including `"Agent"` in `allowed_tools`, and (d) prompting the outer Claude to invoke your named subagent. You are still going through a Claude conversation.
- Subagents **cannot spawn their own subagents**. The docs explicitly forbid putting `Agent` in a subagent's tools array.
- Messages from within a subagent are tagged with `parent_tool_use_id`.
- Subagent transcripts persist to disk; they can be resumed via `resume=session_id` + capturing `agentId`.

**What this means for conversus**: The current SKILL.md "backbone" (Claude's built-in Agent tool with `run_in_background=True`) is NOT a protocol. It is a Claude Code–internal tool that only exists inside a live Claude session and can only be triggered by Claude's own tool-use machinery. You cannot POST to it. Any "Claude Code provider" for conversus that wants to preserve that exact dispatch model must either:
1. Run inside a Claude Code session (current setup), OR
2. Use the Agent SDK's `query()` with a custom `agents` dict — which still runs the full Claude loop in a subprocess per phase dispatch, OR
3. Shell out to `claude -p "prompt" --bare --output-format json --allowedTools ...` per task — the CLI headless path. This is what Anthropic recommends for "CI and scripted calls" and is what `--bare` mode is explicitly designed for.

The CLI headless flag surface (verified from code.claude.com/docs/en/headless):
- `claude -p "prompt"` — non-interactive, prints result and exits
- `--bare` — skips auto-discovery of hooks/skills/plugins/MCP/CLAUDE.md (recommended for scripts; will become default for `-p` in a future release)
- `--output-format text|json|stream-json`
- `--json-schema` for structured output
- `--allowedTools`, `--permission-mode`, `--settings`, `--mcp-config`, `--agents`, `--append-system-prompt`
- `--continue`, `--resume <session_id>`

This is the most primitive, most stable, and most portable way to invoke Claude Code from any language: `subprocess.run(["claude", "-p", prompt, "--bare", "--output-format", "json", ...])`.

## 2. OpenCode (sst/opencode)

### 2.1 Package identity
- **Repo**: `github.com/sst/opencode`. MIT license.
- **Language composition**: Primarily TypeScript (business logic, running on Bun) with a Go TUI (Bubble Tea). The project is an SST v3 monorepo. Claims that OpenCode was "rewritten to Go" are inaccurate — the TUI is Go, the core server/logic is TypeScript/Bun. There IS also an `opencode` Go package (`pkg.go.dev/github.com/sst/opencode`) which is a thin CLI launcher.
- **Binaries**: shipped for Linux x64/arm64, macOS x64/arm64, Windows x64.
- **SDKs**:
  - TypeScript: `@opencode-ai/sdk` (npm, first-class)
  - Go: `github.com/sst/opencode-sdk-go` v0.19.2, Stainless-generated from OpenAPI
  - **Python: none published** (the conversus spec/research doc references `opencode-ai` on PyPI — this could not be verified and appears to be wishful thinking. The only `opencode-ai` package I can confirm is the npm one.)

### 2.2 Architecture — real client/server HTTP

This is the key differentiator: OpenCode is a **proper HTTP server** by design. From opencode.ai/docs/server/:

```
opencode serve [--port <number>] [--hostname <string>] [--cors <origin>]
```

Default port 4096. Exposes OpenAPI 3.1 spec at `http://<host>:<port>/doc`. Even when you run plain `opencode` (the TUI), it starts both a client and a server internally and the TUI communicates with the server over the same HTTP API.

Endpoint surface:
- `/project` — list/manage projects
- `/session` — create / list / delete / get sessions
- `/session/:id/message` — send a message / prompt
- `/file/content` — read files
- `/provider` — list LLM providers
- `/command` — list commands
- Plus SSE subscription endpoints

Session flow (from Go SDK docs):
```go
client := opencode.NewClient()
session, _ := client.Session.New(ctx, opencode.SessionNewParams{...})
response, _ := client.Session.Prompt(ctx, session.ID, opencode.SessionPromptParams{
    Model: opencode.F(...),
    Parts: opencode.F([]opencode.SessionPromptParamsPartUnion{...TextPart, FilePart, ...}),
})
```

TypeScript equivalent from `@opencode-ai/sdk`:
```js
const session = await client.session.create({ body: { title: "..." }})
const result = await client.session.prompt({
  path: { id: session.id },
  body: { parts: [{ type: "text", text: "..." }] }
})
```

Part types supported: `TextPart`, `FilePart`, `ToolPart`, `ReasoningPart`, `SnapshotPart`.

### 2.3 ACP (Zed/JetBrains) bridge

OpenCode also ships `opencode acp`, which runs OpenCode as an **Agent Client Protocol** subprocess, speaking JSON-RPC over stdio. This is what lets Zed, JetBrains, and Neovim users drive OpenCode from their editor. It's a separate transport from the HTTP server.

### 2.4 Concrete answer to the caller's question

**"Can conversus just HTTP POST to a locally-running OpenCode server?"** Yes, literally. `opencode serve` → POST `/session` → POST `/session/:id/message` → poll or SSE-subscribe. There's a published OpenAPI 3.1 spec and generated SDKs in TS and Go.

**The bottleneck** is that there's no Python SDK. Conversus would either (a) use `httpx` + the OpenAPI spec directly, (b) auto-generate a Python client from the OpenAPI spec with openapi-python-client or Stainless, or (c) subprocess to `opencode` CLI. Option (a) is ~100 lines of code.

## 3. Aider

### 3.1 Package identity
- **Repo**: `github.com/Aider-AI/aider`. Apache 2.0. ~12k stars.
- **PyPI**: `aider-chat` (and the `aider` command).
- **Primary interface**: CLI. `aider --message "..." file.py` runs a single-shot task and exits.

### 3.2 Python API — unofficial

From `aider.chat/docs/scripting.html`:

```python
from aider.coders import Coder
from aider.models import Model
from aider.io import InputOutput

model = Model("gpt-4-turbo")
io = InputOutput(yes=True)  # suppress confirmations
coder = Coder.create(main_model=model, fnames=["greeting.py"], io=io)
coder.run("make a script that prints hello world")
```

**The docs explicitly caveat**: "The python scripting API is not officially supported or documented, and could change in future releases without providing backwards compatibility."

`aider.main.main(argv=None, input=None, output=None, force_git_root=None, return_coder=False)` is also callable; with `return_coder=True` you get a configured `Coder` instance back instead of running the interactive loop.

### 3.3 Practical implications
- No subprocess required if you accept the unsupported API risk.
- No async support; `coder.run()` is blocking.
- Single model per Coder; not designed for per-task model switching.
- Any conversus provider would need to either (a) use the unsupported `Coder.create` API and pin aider version tightly, or (b) subprocess `aider --message "..." --yes`.

## 4. GitHub Agentic Workflows (gh-aw)

### 4.1 Identity
- **Repo**: `github.com/githubnext/gh-aw` (also mirrored as `github.com/github/gh-aw`).
- **Language**: Go (confirmed via `go.mod`, `go.sum`, `tools.go`).
- **Installation**: GitHub CLI extension (`gh extension install githubnext/gh-aw`).
- **Status**: Technical preview (announced 2026-02-13 on github.blog/changelog).

### 4.2 What it actually is

`gh-aw` is **not a runtime**. It is a **compiler**. Workflow authors write natural-language markdown with YAML frontmatter; `gh aw compile` converts each into a hardened `.github/workflows/*.lock.yml` file that GitHub Actions then runs. The `lock.yml` is the real runtime artifact.

The lock file embeds the frontmatter and loads the markdown body at runtime. Inside the workflow, an AI "engine" is invoked with the markdown as its prompt.

### 4.3 Supported engines

From docs and blog posts, the engines are:
- **GitHub Copilot CLI** (default)
- **Claude Code**
- **OpenAI Codex** (the CLI)

Each engine is invoked inside a containerized Actions job. `gh-aw` does not define its own wire protocol to these engines — it shells out to their CLIs inside the compiled GitHub Actions job.

### 4.4 Security model
From GitHub's blog posts: agents receive a read-only GitHub token and cannot write directly. Output is a "structured artifact describing intended actions", which a separate scoped-permission job reads and applies. Agent requests; gated job decides.

### 4.5 Implication for conversus

gh-aw is a legitimate execution surface — a `gh-aw` provider for conversus would emit lock.yml files and dispatch workflow runs. But it is **not** an agent runtime conversus can embed. It is a GitHub-Actions-shaped compiler around Copilot / Claude Code / Codex CLIs. The actual backbone in every case is still a subprocess of one of those three CLIs.

## 6. MCP vs A2A vs "Agent Client Protocol" — the three-protocol tangle

Spec 042 currently claims: *"ACP (Agent Communication Protocol) — IBM/Linux Foundation standard for agent-to-agent dispatch, merged with Google's A2A protocol (2025). ACP Task Requests map to conversus phase dispatch."* It also mentions *"JetBrains ACP (Agent Client Protocol) — different from IBM ACP"*.

**The terminology in the spec is partially correct but the implementation story needs tightening.** Verified facts:

### 6.1 MCP (Model Context Protocol)
- **Owner**: Anthropic, with a modelcontextprotocol.io org.
- **Scope**: How a **model** calls **tools**. Server exposes tools/resources/prompts; client (a model runtime like Claude Code, Cursor, VS Code) invokes them.
- **Python SDK**: `mcp` — stable, 1.0 released.
- **Transports**: stdio, SSE, HTTP streaming.
- **What MCP does NOT do**: It does not define agent-to-agent dispatch, task delegation, or "here is a task, go work on it asynchronously and report back." MCP servers are passive tool surfaces. Anthropic's own docs and the MCP spec are clear about this.
- **Implication for conversus**: MCP is **orthogonal** to spec 042's question. Conversus agents USE MCP internally to access tools. MCP is not a candidate for the execution provider layer.

### 6.2 A2A / IBM ACP (merged)
- **History**: IBM Research launched ACP in March 2025 to power BeeAI. Google launched A2A at Cloud Next 2025 (April). In August 2025, IBM's ACP was merged into A2A under Linux Foundation AI & Data (`lfaidata.foundation/communityblog/2025/08/29/acp-joins-forces-with-a2a-...`). Kate Blair (IBM) joined the A2A TSC.
- **Current identity**: The protocol is now called **A2A** (Agent2Agent). "ACP" as a standalone brand effectively retired; "ACP" as a term still appears in legacy docs and in the Zed/JetBrains context (see §6.3).
- **Wire format**: JSON-RPC 2.0 over HTTP(S). Supports sync request/response, SSE streaming, and async push notifications.
- **Repo**: `github.com/a2aproject/A2A`. 1.0.0 released 2026-03-12. ~23k stars, 151 contributors.
- **Python SDK**: `a2a-sdk` on PyPI. **0.3.25 stable (2026-03-10); 1.0.0a0 pre-release available**. Maintained by Google LLC. Apache 2.0. Requires Python ≥3.10. Supports JSON-RPC, HTTP+JSON/REST, gRPC. Optional FastAPI/Starlette server, DB backends, OpenTelemetry.
- **Other SDKs**: `a2a-go`, `@a2a-js/sdk` (npm), Java Maven, .NET NuGet.
- **Adoption**: Framework integrations in Google ADK, LangGraph, BeeAI. No major agent SDK has shipped an A2A server wrapper for itself yet. No canonical reference implementation of "wrap Claude Code as an A2A server" exists.
- **Maturity warning**: The 1.0.0 protocol release is a month old. The Python SDK is still 0.3.x stable / 1.0.0a0 alpha. This is early.

### 6.3 Agent Client Protocol (Zed/JetBrains)
- **This is a completely separate protocol** from A2A/IBM-ACP.
- **Scope**: IDE ↔ coding agent. Literally "LSP for AI agents." Local agents run as subprocesses of the editor over JSON-RPC on stdio; remote agents over HTTP/WebSocket (WIP).
- **Repo**: `github.com/zed-industries/agent-client-protocol` (mirrored at `agentclientprotocol.com`). v0.11.4 as of March 2026. **Not 1.0 yet.**
- **SDKs**: Rust (`agent-client-protocol` on crates.io), TypeScript (`@agentclientprotocol/sdk` on npm), Python, Kotlin, Java.
- **Supported agents in the JetBrains/Zed ACP Agent Registry**: Claude Code, Codex CLI, GitHub Copilot CLI, OpenCode, Gemini CLI, plus others.
- **How it works for editor integration**: The editor spawns the agent as a subprocess (e.g. `opencode acp`). JSON-RPC messages flow: editor sends `initialize` → `session/new` → `session/prompt`; agent streams back `session/update` events; editor applies edits/tool calls with user approval.
- **It is NOT a general-purpose agent dispatch protocol for headless pipelines.** Its threat model and UX assume a live IDE with a human in the loop approving tool calls. Spec 042's "autonomous governance" use case (spec 048) does not fit Zed/JetBrains ACP cleanly — it fits A2A.

### 6.4 Spec 042 terminology correction

Spec 042 says *"ACP (Agent Communication Protocol) — IBM/Linux Foundation standard, merged with Google's A2A (2025)"*. This is **directionally correct but the naming has moved on**: the merged protocol is now universally called **A2A**. "ACP" in 2026-04 usage most commonly refers to the Zed/JetBrains **Agent Client Protocol**. To avoid confusion, any spec-042 follow-up should:

- Rename the "ACP provider" to **"A2A provider"** (or more explicitly, `a2a` using `a2a-sdk`).
- Explicitly distinguish from the **Agent Client Protocol** (Zed/JetBrains) — which is a *different* integration vector, potentially useful for a future "run conversus inside an IDE" story but not for headless CI dispatch.
- Treat A2A as the long-term unification target but recognize the Python SDK is still 0.3.x stable.

## 7. Is there a common pattern?

I looked for any shared primitive across the tools above. Results:

| Layer | Shared standard? | Reality |
|---|---|---|
| Model API | Yes (LiteLLM, OpenAI-compatible endpoints) | 100+ providers via a single OpenAI-shaped interface |
| Tool exposure (model → tool) | Yes (MCP) | Nearly every shipping coding agent is an MCP client |
| IDE ↔ agent | Emerging (Zed/JetBrains ACP) | Claude Code, Codex CLI, Copilot CLI, OpenCode, Gemini CLI all in the Registry |
| Agent ↔ agent (task dispatch) | Emerging (A2A, 1.0.0 as of 2026-03) | Framework integrations only; no major SDK ships an A2A server wrapper of itself yet |
| Headless CLI invocation | **De facto** (subprocess + flags + JSON output) | **Every shipping agentic coding tool supports this**: `claude -p --output-format json`, `aider --message`, `opencode` CLI, `copilot` CLI, `codex` CLI, `gemini` CLI, `cn` for Continue |

**The de facto backbone across all agentic coding tools today is: subprocess-spawn a CLI, pass a prompt via `-p`/`--message`/stdin, collect JSON output.** Every one of them ships this. None of them ship a shared Python library. None of them ship a shared HTTP protocol (OpenCode has one, nobody else does). A2A is the closest thing to a future unification but is not yet widely adopted by the tools conversus would dispatch to.

## 8. Is MCP the right abstraction for conversus's execution layer?

**No, and this is unambiguous.** Evidence:

- MCP's specification (`modelcontextprotocol/specification`) defines servers that expose tools/resources/prompts and clients that consume them. The verbs are `tools/list`, `tools/call`, `resources/read`, `prompts/get` — there is no `tasks/dispatch`, `agent/invoke`, or equivalent.
- MCP clients are model runtimes (Claude Code, Cursor, VS Code Copilot). They use MCP to *enrich the context window of a model*. They do not use MCP to delegate work to another agent.
- Anthropic's own Agent SDK docs cleanly separate: "Built-in tools" (Read/Write/Edit/Bash/Glob/Grep — the subagent uses these), "Subagents" (spawned via the `Agent` tool, an SDK primitive), and "MCP" (external tool integration). The subagent dispatch path is **not** an MCP call.
- There is no shipping tool that uses MCP to dispatch agent tasks to another agent.

**Conversus phase dispatch is agent-to-agent, not model-to-tool.** That puts it in A2A's scope, not MCP's.

## 9. Is A2A mature enough to bet on in 2026-04?

**Partially.** Concrete facts:

- **Protocol spec**: v1.0.0 released 2026-03-12. Less than a month old.
- **Python SDK (`a2a-sdk`)**: 0.3.25 stable, 1.0.0a0 alpha. The stable version is pre-1.0.
- **Governance**: Linux Foundation LF AI & Data; Google + IBM + Microsoft + AWS + Cisco + Salesforce + ServiceNow + SAP on the TSC.
- **Reference implementations**: Google ADK, IBM BeeAI, LangGraph integration. No Anthropic/Claude Code reference. No GitHub/Copilot reference. No Aider reference. No OpenCode reference.
- **Ecosystem fact**: As of 2026-04, **there is no off-the-shelf A2A server that wraps any of the coding agents conversus would actually dispatch to**. If conversus ships an A2A provider today, it will have nothing on the other end of the wire that speaks A2A natively — someone (probably conversus maintainers) has to build the wrapper.

**What this means for the deliberation**: A2A is a bet on a future that will probably arrive, but it has not arrived yet for coding agents. Any "A2A provider" the conversus team ships in 042 will be betting on the assumption that A2A wrappers of Claude Code / Copilot / Aider / OpenCode will exist within the relevant horizon. That is a bet, not a given.

## 11. What this means for spec 042 (kept terse, non-advocacy)

Neutral observations the other agents can argue from:

1. **The SKILL.md's current dispatch primitive (Claude's `Agent` tool with `run_in_background`) is not portable.** It only exists inside a live Claude Code session. Any execution-provider abstraction that claims to support "running headless" must replace it with one of: (a) `claude -p --bare` subprocess, (b) `claude-agent-sdk.query()` (which itself subprocesses), or (c) something else entirely.

2. **The most portable, lowest-risk backbone today is "spawn a CLI and read JSON output."** Every shipping agentic coding tool supports this. It's ugly, it's per-task process overhead, but it is the one thing that actually works across Claude Code, Aider, OpenCode, Copilot, Codex, Gemini, and Continue **today**. It requires zero protocol agreement and zero wrapper code on the tool side.

3. **OpenCode is the one exception** that offers a first-class HTTP API with an OpenAPI 3.1 spec. If conversus wants to build a provider that doesn't fork-exec per task and supports native streaming, OpenCode is the only option at present.

4. **A2A exists and is technically the right abstraction** for agent-to-agent dispatch (which conversus phase dispatch is). But in 2026-04, no one has wrapped Claude Code / Aider / Copilot / Codex / Gemini as A2A servers yet. If conversus ships an A2A provider, it will initially have no counterparties unless conversus maintainers build the wrappers themselves.

5. **MCP is not the right layer.** It is for tools-in-context, not agent-dispatch. Dismiss it as a candidate for the execution layer (not as a candidate for tool access within an agent — that's separate and already in use).

6. **Zed/JetBrains ACP is also not the right layer** for headless CI dispatch. It is for IDE integration. It is potentially interesting for a future "run conversus inside an IDE" story (spec 042 §12 open question 8), but not for spec 048 autonomous governance.

7. **The gh-aw provider is real and valuable but limited**: it doesn't execute agents, it emits GitHub Actions YAML that executes Copilot/Claude/Codex CLIs. Useful for CI/CD conversus, useless for programmatic in-process dispatch.

8. **Spec 042's `claude-code` provider via "Node bridge" is misleading**: the `@anthropic-ai/claude-agent-sdk` is itself a subprocess wrapper around the `claude` CLI binary. From Python you are not avoiding subprocess by calling the TS SDK — you are adding a Node layer between your Python and a CLI subprocess. Go straight to `claude -p --bare` from Python.

9. **The spec-042 "ACP provider" name is ambiguous** given the two-ACP problem in the current landscape. Rename to `a2a` or `a2a-client` if that's the intent; clarify if Zed/JetBrains ACP is separately in-scope.

10. **Pricing/runtime fact spec 042 doesn't cover**: subprocess-spawning Claude Code has a cold-start cost (typically ~1–3 seconds for the CLI to boot, load plugins/hooks/MCP servers). `--bare` exists specifically to cut this. For a conversus run with 10–30 parallel agent phases, this adds up. An HTTP-server-based backbone (OpenCode or A2A) avoids the cold start entirely by reusing a long-lived process.

## 13. One-paragraph summary for the other agents

The current Claude-Code-dependent SKILL.md backbone is not a protocol, it's an in-session tool that only works inside a Claude Code conversation. Every production agentic coding tool that conversus might want to dispatch to (Claude Code, Aider, Copilot CLI, Codex CLI, Gemini CLI, Continue's `cn`) ships a CLI with headless/script mode and JSON output; this is the de facto interop layer today and the only one that uniformly exists. OpenCode is the one exception with a proper HTTP/OpenAPI server — it is uniquely positioned for an API-based provider but has no Python SDK. Google+IBM's A2A protocol (formerly IBM ACP, merged Aug 2025) is the right long-term abstraction for agent-to-agent dispatch and shipped protocol v1.0.0 last month with `a2a-sdk` Python 0.3.25 stable / 1.0.0a0 alpha, but no shipping coding agent has been wrapped as an A2A server yet, so the wire is there but there's nothing on the other end. MCP is not the right layer — it is for model-to-tool, not agent-to-agent. Zed/JetBrains Agent Client Protocol (the "other ACP") is for IDE-to-agent integration, also not the right layer for headless CI. Spec 042 currently blurs these three protocols and should separate them. The realistic 2026-04 options for conversus are: (1) CLI-subprocess providers as the portable baseline, (2) OpenCode HTTP provider for the one tool that supports it natively, (3) an A2A provider as a speculative future path conversus would have to bootstrap itself since no counterparties exist yet.
