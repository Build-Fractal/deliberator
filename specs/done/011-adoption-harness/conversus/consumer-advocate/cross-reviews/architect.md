# Cross-Review: consumer-advocate reviewing architect's review

---

### Dangerous Contradictions

- **Web app priority: defer vs. elevate**
  - **architect claims**: "Defer-web-app-to-v2" (Actionable Recommendation #4): "Move the web app out of the v1 scope entirely... v1 ships CLI + MCP server + Python SDK. Web app is a separate proposal." The rationale cites engine-layer scope pressure and the complexity of Next.js, WebSocket, PostgreSQL, auth, and hosting.
  - **consumer-advocate claims**: "Elevate web-app priority" (Actionable Recommendation #1): "Move web app to step 4 or 5, immediately after 'Just Ask' engine work. Deliver 'Just Ask' and web app as a single milestone." The rationale cites the decision framework's SC-1 (Non-Expert Usability) and the fact that non-experts will never use a CLI.
  - **Why this is dangerous**: These are diametrically opposed recommendations for the same deliverable. If architect's position is adopted, the product ships as a developer tool with no consumer-facing surface at all in v1 -- CLI, MCP server, and SDK are invisible to the retiree, student, and parent named in the proposal (L18-20). If consumer-advocate's position is adopted, the web app competes with engine extraction for engineering bandwidth, risking the fragile foundation architect warns about. Implementing both positions is impossible: the web app cannot simultaneously be "out of v1 scope entirely" and "step 4 or 5." The real failure mode is strategic: if v1 has no consumer path, the product establishes its identity as a developer tool, and the web app (whenever it ships) inherits developer-shaped abstractions that feel wrong to consumers.
  - **Suggested resolution**: Neither full deferral nor full elevation. Define a "v1.1" milestone that ships a minimal web app (landing page + "Just Ask" + results page, no auth, no history, no PostgreSQL) within weeks of v1, not months. This gives architect the room to get the engine extraction right without the full web stack, while giving consumer-advocate a consumer-facing surface before the product's identity calcifies. The web app's scope in v1.1 is deliberately limited: static hosting, no accounts, no persistence. The heavy web features (history, sharing, auth) move to v2. Both parties should yield partially: architect accepts that some consumer surface must ship near v1; consumer-advocate accepts that the full-featured web app described at L89-98 cannot ship simultaneously with the engine extraction.

- **"Just Ask" output format: structured vs. plain-English**
  - **architect claims**: "Specify-output-contract-for-Just-Ask" (Actionable Recommendation #8): "'Just Ask' should produce a subset of the standard conversus output: at minimum, a synthesis file following the same mode-specific template structure." The rationale is that unstructured prose cannot participate in the conversus ecosystem -- no follow-up rounds, no arbitration, no plugin analysis via the dispute parsing subsystem (SKILL.md, L670-697).
  - **consumer-advocate claims**: "Design progressive result disclosure" (Actionable Recommendation #4): Results must be structured in three layers -- "(1) headline recommendation in one sentence, (2) summary paragraph with key trade-offs, (3) full agent arguments and dissent expandable on demand." The emphasis is on consumers getting the answer first and the reasoning second, not on system-interoperable output.
  - **Why this is dangerous**: If architect's structured-template output is adopted without consumer layering, "Just Ask" outputs look like every other conversus synthesis -- a dense markdown document that satisfies the dispute parsing subsystem but overwhelms a parent choosing a vacation. If consumer-advocate's progressive disclosure is adopted without architect's structural contract, the output is consumer-friendly but cannot feed back into the conversus ecosystem (`prior:` context, arbitration, plugin analysis), making "Just Ask" a dead end. Both reviews identify real requirements, but implementing one without the other produces either a bad consumer experience or a disconnected product.
  - **Suggested resolution**: The output should be generated using architect's mode-specific template structure (ensuring ecosystem compatibility), then rendered through consumer-advocate's progressive disclosure layers (ensuring consumer readability). The underlying file can follow the standard synthesis format; the web app and CLI presentation layer adds the three-tier progressive reveal on top. Architect's concern is about the data model; consumer-advocate's concern is about the presentation. These are different layers and can coexist if both are designed together from the start. The key design constraint: the structured template must include machine-parseable markers (e.g., a `## Recommendation` section) that the presentation layer uses to extract the headline.

- **MCP server as primary integration path**
  - **architect claims**: The architect's review does not challenge the MCP server's "Primary Integration Path" label (L74). In the Alignment section, the architect endorses the MCP tool surface as "well-chosen" and discusses adding a seventh tool (`conversus_replay`). The MCP server's primacy is accepted without qualification.
  - **consumer-advocate claims**: "Declare dual-primary integration paths" (Actionable Recommendation #6): "Replace 'Primary Integration Path' with 'Primary Developer Integration Path' for MCP. Add 'Primary Consumer Integration Path' heading for the Web App section." The Off-Base Assumptions section explicitly calls out the "Primary" label as sending the wrong signal about product priorities.
  - **Why this is dangerous**: If architect's unchallenged acceptance of MCP-as-primary is combined with architect's recommendation to defer the web app to v2, the product's entire v1 identity is developer-focused. The "primary" label drives internal prioritization, staffing, and feature triage. Consumer features will consistently lose to MCP/CLI features in v1 because they are not "primary." This is not a technical integration failure but a product strategy failure: the proposal names consumer users (L18-20) but architect's recommendations systematically deprioritize every consumer-facing surface.
  - **Suggested resolution**: Architect should acknowledge that "primary" needs qualification by audience. The proposal should adopt dual-primary language. This costs nothing technically but reframes how the team thinks about prioritization. Architect's deep concern about engine quality is valid and should not be undermined, but it can coexist with explicit acknowledgment that the consumer path is equally important strategically, even if it ships slightly later.

### Tensions

- **Engine purity vs. consumer-first design**
  - **architect's position**: The architect's core thesis is that the engine extraction is the hardest and most important work. Recommendations #1-4 all focus on getting the engine right: define interfaces first, decompose the extraction, design the async dispatch engine, defer the web app. The architect's build order is interfaces -> engine -> CLI -> MCP -> plugins, with the web app explicitly removed from v1 scope (Recommendation #4).
  - **consumer-advocate's position**: The consumer-advocate's core thesis is that the consumer experience defines the product. Recommendations #1, #3, #4, and #7 all focus on consumer-facing features: web app priority, example questions, progressive disclosure, mobile-first design. The consumer-advocate's build order is "Just Ask" + web app as a single milestone, with the engine as a backend concern.
  - **Nature of tension**: Both positions are correct within their domains. A poorly extracted engine will produce bugs in every distribution format. A product with no consumer surface will never reach the majority of potential users. The tension is about sequencing and resource allocation, not about whether both things matter. The architect sees the engine as load-bearing infrastructure that must be right first; the consumer-advocate sees the consumer experience as the product's reason to exist.
  - **Coordination needed**: A shared milestone plan that sequences engine extraction and consumer surface in parallel tracks, with explicit handoff points. The engine team builds to architect's interface-first approach; a separate (even small) effort builds a minimal consumer surface that can absorb the engine as it matures. The key constraint: the "Just Ask" engine work (proposal step 4) must be designed with both CLI and web consumption in mind from the start, not as a CLI feature that later gets a web wrapper.

- **Plugin system timing: foundational vs. final**
  - **architect's position**: The architect argues forcefully that spec 007's plugin interfaces should be defined first ("Phase 0: Interface Definition"), before engine extraction begins (Recommendation #1). The rationale is that `DeliberationState`, lifecycle hooks, and the plugin API are architecturally foundational -- building without them means a retrofit (Missed Opportunities, "DeliberationState as the extraction target").
  - **consumer-advocate's position**: The consumer-advocate does not discuss plugins at all. The consumer-advocate's review implicitly treats plugins as a developer concern that does not affect consumer users. No consumer-advocate recommendation references spec 007 or the plugin system.
  - **Nature of tension**: Architect's Phase 0 interface definition adds work before any user-facing feature ships. From the consumer-advocate's perspective, this is exactly the kind of developer-serving infrastructure that delays the consumer product. From the architect's perspective, skipping it means the engine will need a disruptive refactor later, which delays everything. The tension is not about whether plugins matter (they do for the platform's long-term health) but about whether defining their interfaces is a prerequisite for shipping a consumer experience.
  - **Coordination needed**: Architect's Phase 0 should be time-boxed. The interface definitions (dataclasses, protocols, lifecycle hook enum) are small artifacts -- they can be defined in days, not weeks. If Phase 0 is scoped tightly to "define the types, not implement the system," it does not meaningfully delay consumer-facing work. Consumer-advocate should accept this small upfront investment; architect should accept that Phase 0 is a type-definition sprint, not a design exploration.

- **Vague question handling: system concern vs. consumer concern**
  - **architect's position**: The architect does not mention vague question handling anywhere in the review. The review's focus is on engine architecture, dispatch semantics, and interface design. The "Just Ask" mode is discussed only in terms of its output contract (Recommendation #8) and its connection to spec 007's config optimizer (Missed Opportunities, "Config optimizer for 'Just Ask' defaults"), not in terms of what happens when the input is bad.
  - **consumer-advocate's position**: "Specify vague-question handling for Just Ask" is the consumer-advocate's P1 Recommendation #2. The review identifies this as the most common consumer scenario and warns that without it, "consumers type vague questions, get shallow or confused results, and conclude the tool is useless."
  - **Nature of tension**: Architect's silence on this topic does not mean disagreement -- it means the architect does not view input quality as an architectural concern. But for the consumer path, input quality is THE architectural concern. If the engine is beautifully extracted but cannot handle "help me decide," the consumer product fails at the front door. The tension is about what counts as "the engine": architect scopes it to orchestration and dispatch; consumer-advocate scopes it to include input classification and clarification.
  - **Coordination needed**: Vague question handling must be part of the "Just Ask" engine, not bolted on by the web app. Architect's engine extraction should include a "question classifier" module (or at minimum, a hook point where classification logic can be injected). This aligns with architect's own interface-first approach: define a `QuestionClassifier` protocol alongside `DeliberationState`, and the "Just Ask" mode has a clean place to handle vague input.

- **Model tiering scope: optimization vs. architecture**
  - **architect's position**: "Align-model-tiering-with-provider-abstraction" (Recommendation #10): Model tiering is "an architectural decision, not an optimization." It requires per-invocation model selection designed into the engine from the start, with explicit per-phase configuration in `conversus.yml` (e.g., `models: { default: claude-sonnet-4-6, synthesis: claude-opus-4, cross-review: gpt-4o-mini }`).
  - **consumer-advocate's position**: The consumer-advocate does not mention model tiering. However, the consumer-advocate's P1 concern for "2-3 agents, 1 round -- fast and cheap" (Alignment section, "Lightweight deliberation default") implicitly depends on model tiering: "cheap" requires using less expensive models for some phases. The consumer-advocate also does not engage with the SKILL.md constraint that "All subagents use the orchestrator's model" (SKILL.md, L716), which architect identifies as a barrier.
  - **Nature of tension**: If model tiering is deferred (treated as optimization), "Just Ask" mode cannot deliver on "fast and cheap" without using a cheap model for everything, which degrades synthesis quality. If model tiering is prioritized (treated as architecture), it adds complexity to Phase 0 and Phase 1, potentially delaying consumer-facing delivery. The consumer-advocate's "fast and cheap" goal depends on the architect's model tiering architecture, but neither review makes this dependency explicit.
  - **Coordination needed**: Define model tiering as a Phase 1 capability with a simple default: one model for everything (current behavior), with per-phase override as an optional config extension. This gives "Just Ask" a path to cheapness without requiring the full multi-model architecture to ship in v1. The consumer-advocate should explicitly acknowledge that "fast and cheap" has architectural prerequisites.

### Safe Agreements

- **Engine extraction is necessary and the SKILL.md cannot be the sole runtime**
  - **Shared position**: Architect's Executive Summary states: "conversus's current SKILL.md + Agent tool architecture locks it to a single runtime, a single model provider, and users who can hand-write YAML. Opening it up is the right strategic move." Consumer-advocate's Executive Summary states: "conversus has real value for non-technical decision-makers, but only if they can actually reach it." Both reviews agree that the current Claude Code-only architecture is a distribution bottleneck that must be resolved.
  - **Combined evidence**: Architect provides technical evidence: the SKILL.md relies on Claude Code's Agent tool for parallel dispatch, output isolation, and error handling (Off-Base Assumptions, "Parallel agent dispatch"). Consumer-advocate provides market evidence: the proposal's named users (retirees, students, parents) will never open a terminal (Off-Base Assumptions, "Just Ask as CLI-first feature"). Together, these establish that extraction is necessary for both technical and market reasons -- the engine cannot scale to new runtimes AND cannot reach new users without it.
  - **Confidence level**: High. This agreement is the foundational premise of the entire proposal, and both reviews reinforce it from orthogonal perspectives.

- **The three-tier user model is the right segmentation**
  - **Shared position**: Architect's Alignment section endorses the three-tier model: "The Just Ask / Guided / Power tiering correctly maps to three distinct user populations with different config effort tolerances." Consumer-advocate's Alignment section agrees: "The tiered approach correctly segments users by technical ability. The 'Just Ask' tier with 'Zero -- system infers everything' config effort directly matches what consumer users need."
  - **Combined evidence**: Architect validates the tiers from an architectural perspective: the SKILL.md already separates config parsing from orchestration, making multiple front-ends feasible. Consumer-advocate validates the tiers from a usability perspective: the decision framework's SC-1 (Non-Expert Usability) and the constraint that the system "Must NOT require coding knowledge to use" (spec.md, L518-519) demand at least the "Just Ask" tier. The agreement is not just "both reviews mention tiers" -- both provide independent evidence that the segmentation maps to real, distinct user populations with different needs.
  - **Confidence level**: High. The three-tier model should be treated as settled architecture in the final synthesis.

- **"Just Ask" mode must handle the full lifecycle from question to recommendation without user configuration**
  - **Shared position**: Architect's Alignment section endorses auto-generated agents, optimal mode selection, and lightweight deliberation as components of "Just Ask" (citing L37-42). Consumer-advocate's Alignment section makes the same endorsement: "The 'Just Ask' mode auto-generates 2-4 agents, picks the optimal competition mode, and returns a plain-English synthesis. This eliminates the three hardest steps for consumers: writing agent prompts, understanding game theory, and configuring YAML."
  - **Combined evidence**: Architect connects "Just Ask" to spec 007's config optimizer and feature extraction pipeline (Missed Opportunities), providing the technical mechanism for auto-configuration. Consumer-advocate connects "Just Ask" to the decision framework's heuristic detection system (spec.md, L322-343) and SC-8 plain-language output requirement (spec.md, L509-511), providing the usability mandate. Both reviews agree the mode must be zero-configuration AND produce useful output -- the disagreements are about output format and delivery priority, not about whether the mode should exist or what it fundamentally does.
  - **Confidence level**: High. The "Just Ask" mode's zero-configuration promise is endorsed by both reviews and should be treated as a non-negotiable requirement.

- **The proposal underestimates the complexity of engine extraction**
  - **Shared position**: Architect's Off-Base Assumptions section identifies "Python engine extraction as a single build phase (L120)" as underselling scope, decomposing it into six module-scale pieces of work. Consumer-advocate's Off-Base Assumptions section identifies "'Just Ask' as CLI-first feature (L123-124)" as architecturally backwards, noting that building "Just Ask" as a headless engine and then bolting a web UI onto it "will produce a developer tool with a web skin, not a consumer product."
  - **Combined evidence**: Both reviews independently conclude that the proposal's build order underestimates complexity, though they identify different dimensions: architect sees technical complexity (six subsystems, not one phase), consumer-advocate sees design complexity (CLI-shaped abstractions that will not transfer to web). Together, these reinforce that the build plan needs significant revision -- not just reordering, but decomposition and parallel tracking. The proposal's linear 8-phase plan is too coarse for both the technical and product challenges it faces.
  - **Confidence level**: Medium. Both reviews agree the plan is underspecified, but they disagree on what should replace it (architect wants decomposed engine-first; consumer-advocate wants consumer-first). The agreement is on the diagnosis, not the prescription.
