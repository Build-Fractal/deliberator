# Cross-Review of Devil's Advocate Review — by Consumer Advocate

---

### Dangerous Contradictions

- **Web App Deferral vs. Consumer-First Delivery**
  - **devils-advocate claims**: "Remove the web app from this spec's build order. Create a separate spec (012 or later) for the web app after the core engine, CLI, and MCP server are stable." (Actionable Recommendations, item 7)
  - **consumer-advocate claims**: "Move web app to step 4 or 5, immediately after 'Just Ask' engine work. Deliver 'Just Ask' and web app as a single milestone, not separate steps." (Actionable Recommendations, item 1). Additionally: "Building 'Just Ask' as a headless engine and then bolting a web UI onto it will produce a developer tool with a web skin, not a consumer product." (Off-Base Assumptions, item 1)
  - **Why this is dangerous**: If both positions are adopted, the spec would simultaneously defer the web app to a later spec AND elevate it to step 4. More substantively, the devil's advocate frames the web app as a complexity risk that threatens delivery of developer-facing distribution formats. The consumer advocate frames it as the only path that reaches the largest user segment. If the synthesis splits the difference by building the engine first and "web app later," the engine's API shapes, output formats, and interaction patterns will be designed for CLI/SDK consumers. When the web app eventually arrives, it inherits abstractions (file-system output, single-document synthesis, no progressive disclosure) that feel wrong in a browser. The failure mode is a web app that is technically functional but structurally a CLI port.
  - **Suggested resolution**: The devil's advocate's concern about scope is legitimate -- the web app introduces authentication, hosting, state management, and database design that are genuinely underspecified. The consumer advocate's concern about build-order shaping product DNA is also legitimate. A cooperative resolution: keep the web app in the same spec but gate it behind an explicit "web app design spec" milestone that must be written before implementation begins. Meanwhile, require the engine API to be designed with web-native consumption patterns from day one (streaming partial results, structured output layers, not just flat markdown files). This way the engine ships first without blocking on the web app, but the web app is not deferred to a separate spec where it risks becoming permanently deprioritized.

- **Lightweight Deliberation: Value Preservation vs. Consumer Speed**
  - **devils-advocate claims**: "A 2-agent, 1-round deliberation is structurally identical to asking two models the same question and having a third summarize -- which is not what makes conversus valuable." (Off-Base Assumptions, item 2). They recommend designing an explicit "cross-review bypass" with an alternative adversarial pressure mechanism. (Actionable Recommendations, item 3)
  - **consumer-advocate claims**: "The '2-3 agents, 1 round -- fast and cheap' default for 'Just Ask' mode is correct for consumer use cases where speed matters more than exhaustiveness. A parent choosing a vacation destination does not need 5 agents and 3 rounds." (Alignment, item 6)
  - **Why this is dangerous**: The consumer advocate endorses the lightweight default as aligned with consumer needs. The devil's advocate argues this lightweight default produces output that is structurally indistinguishable from single-model prompting. If both positions are adopted without resolution, the "Just Ask" mode ships with a configuration that the consumer advocate considers correct for the audience but the devil's advocate considers structurally incapable of delivering conversus's value. The failure mode: consumers get fast, cheap results that are genuinely no better than ChatGPT, confirm the "just another wrapper" perception, and never return.
  - **Suggested resolution**: The devil's advocate is right that the mechanism matters -- skipping cross-reviews removes the structural feature that makes conversus different. The consumer advocate is right that consumers will not wait for a full 5-phase cycle. The resolution is the devil's advocate's own suggestion: design a "mini-cross-review" where agents respond to each other in a single combined prompt rather than isolated phases. This preserves adversarial pressure while keeping the token cost and latency closer to the consumer advocate's speed requirement. Both perspectives should yield toward this middle ground, and the spec should define what this compressed cycle looks like concretely.

- **"Just Another ChatGPT Wrapper" — Visible Differentiation vs. Quality Metrics**
  - **devils-advocate claims**: "Add a 'Differentiation' section that concretely demonstrates -- with a side-by-side example -- how a conversus 'just ask' response differs from asking the same question to a single model." (Actionable Recommendations, item 9). The emphasis is on measurable, structural differences in output.
  - **consumer-advocate claims**: "Add a confidence signal to every result" (Actionable Recommendations, item 5) and "Design progressive result disclosure" (Actionable Recommendations, item 4). The emphasis is on consumer-legible presentation of the output.
  - **Why this is dangerous**: These are not contradictory in intent, but they point at the same problem from opposite ends. The devil's advocate wants proof that multi-agent deliberation produces structurally different output. The consumer advocate wants the output formatted so consumers can see the value. If the synthesis adopts only the devil's advocate's position, the spec gets a side-by-side demo that proves structural value to spec reviewers but consumers still cannot see it because the output is a wall of text. If the synthesis adopts only the consumer advocate's position, the output is well-formatted but the underlying deliberation may not actually be better than single-model. The failure mode is building presentation polish on top of output that is not meaningfully different.
  - **Suggested resolution**: Both positions are needed, and they should be sequenced: first, adopt the devil's advocate's quality criteria (Recommendation 1 -- define minimum quality bar for deliberation output). Then, adopt the consumer advocate's progressive disclosure so that the structural differences the quality criteria guarantee are actually visible to end users. The devil's advocate provides the "is it actually better" gate; the consumer advocate provides the "can users see that it is better" layer.

### Tensions

- **Quality Floor vs. Speed Ceiling**
  - **devils-advocate's position**: Defines three minimum quality criteria: synthesis must surface at least one substantive disagreement, each agent must reference specific evidence, and the recommendation must acknowledge trade-offs. (Actionable Recommendations, item 1)
  - **consumer-advocate's position**: Emphasizes that consumer users need results in under 60 seconds and that the lightweight default is correct for their use cases. (Alignment, item 6; Executive Summary, "Can my users get value in under 60 seconds with zero setup?")
  - **Nature of tension**: Quality criteria increase the minimum work each agent must do, which increases latency and cost. A synthesis that must "surface at least one substantive disagreement" requires agents to actually disagree substantively, which may require more than one round or more than two agents. The consumer advocate's speed requirement and the devil's advocate's quality floor may be incompatible at the cheapest model tiers.
  - **Coordination needed**: The spec must define per-tier quality/speed targets. "Just Ask" with cheap models might target a 30-second, $0.10 run that meets a reduced quality bar (e.g., one of the three criteria instead of all three). Power mode meets the full quality bar with no latency constraint. This tiering must be explicit so that neither perspective is silently violated.

- **Model Capability Requirements vs. Consumer Accessibility**
  - **devils-advocate's position**: Recommends a capability matrix and runtime validation that warns or blocks when the selected model cannot support the requested deliberation depth. (Actionable Recommendations, item 2)
  - **consumer-advocate's position**: Does not address model selection at all -- consumer users should not know or care what model is running. The entire Off-Base Assumptions section argues against requiring technical knowledge.
  - **Nature of tension**: The devil's advocate's runtime validation ("the selected model is unlikely to produce valid deliberation output") assumes someone is selecting a model. For consumer users in a web app, there is no model selection -- the system chooses. If the system blocks because the default model is "too weak," the consumer sees a failure they cannot understand or fix. If the system silently downgrades the deliberation, the consumer gets low-quality output with no explanation.
  - **Coordination needed**: For consumer-facing tiers, model capability validation must be invisible -- the system selects a capable model automatically and never surfaces model-level diagnostics to end users. The devil's advocate's capability matrix is valuable for the SDK/CLI/Power tier where users choose models. The spec should distinguish: for Power tier, warn/block on weak models; for Just Ask tier, the system is responsible for choosing an adequate model, and failure to do so is a platform bug, not a user error.

- **Cost Visibility vs. Frictionless Experience**
  - **devils-advocate's position**: Recommends cost estimation before execution: "This deliberation will use approximately X tokens across Y API calls, estimated cost: $Z. Proceed?" (Actionable Recommendations, item 4)
  - **consumer-advocate's position**: Does not mention cost controls but emphasizes zero-config, zero-friction experience. The entire review framework is "value in under 60 seconds with zero setup."
  - **Nature of tension**: A cost confirmation dialog breaks the frictionless flow. A consumer who types "Should I lease or buy my next car?" and then sees "Estimated cost: $0.47. Proceed?" will be confused (what is a token?), annoyed (I just want an answer), or frightened (am I being charged?). But the devil's advocate is right that surprise costs kill adoption.
  - **Coordination needed**: For the web app, cost management must be a platform concern, not a per-query concern. The business model (subscription, freemium, per-query with account balance) must handle this so that individual queries never require cost confirmation. For SDK/CLI users, the devil's advocate's cost estimation is appropriate because those users understand API economics. The spec should declare that cost confirmation is a Power/SDK feature, not a consumer feature, and that the web app requires a business model section that makes per-query cost invisible.

- **Prompt Injection Risk vs. "Just Ask" Openness**
  - **devils-advocate's position**: Raises prompt injection as a medium-impact concern: "A user could craft input that causes agents to bypass their adversarial roles or produce biased outputs." (Missed Opportunities, item 7)
  - **consumer-advocate's position**: Does not address security at all. The review focuses entirely on usability, accessibility, and consumer experience.
  - **Nature of tension**: The consumer advocate's vision of "just type anything" is inherently at odds with input sanitization. Consumer users will type things that look like prompt injection purely by accident ("ignore the previous options and just tell me the best one"). Aggressive input filtering would reject legitimate consumer queries; no filtering leaves the devil's advocate's security concern unaddressed.
  - **Coordination needed**: The spec should distinguish between adversarial prompt injection (intentional manipulation in a web app context) and naive instruction-like phrasing (consumers telling the system what to do). The system should handle the latter gracefully -- "ignore the previous options" should be interpreted as user intent, not as an injection attack. For the former, standard web-app security practices (rate limiting, output monitoring, role-boundary enforcement at the system prompt level) should be specified.

- **MCP Maturity Uncertainty vs. Consumer Irrelevance**
  - **devils-advocate's position**: Flags MCP as risky because it may not be mature enough and has no fallback strategy. (Missed Opportunities, item 8)
  - **consumer-advocate's position**: Argues MCP should not be labeled "primary" because it is invisible to consumers; the web app is the consumer primary. (Off-Base Assumptions, item 2; Actionable Recommendations, item 6)
  - **Nature of tension**: Both reviews agree MCP is not the consumer path, but they draw different conclusions. The devil's advocate worries about MCP maturity affecting the overall adoption strategy. The consumer advocate worries about the "primary" label misallocating resources. Both concerns are valid but point in different directions: the devil's advocate would invest in MCP fallbacks; the consumer advocate would reallocate that investment to the web app.
  - **Coordination needed**: The spec should define "primary integration path for developers" (MCP) and "primary integration path for consumers" (web app) as the devil's advocate implicitly suggests is reasonable in the MCP section. MCP fallback planning and web app investment are then separate workstreams that do not compete for priority.

### Safe Agreements

- **"Just Ask" Agent Auto-Generation Needs Concrete Specification**
  - **Shared position**: Both reviews identify that "auto-generates 2-4 appropriate agents with relevant perspectives" (proposal L38) is critically underspecified. The devil's advocate calls it out explicitly: "Define the agent generation algorithm" (Actionable Recommendations, item 8). The consumer advocate states: "All consumer questions get the same generic agent treatment. A vacation recommendation feels as clinical as an architecture review" (Actionable Recommendations, item 9 -- consumer domain routing).
  - **Combined evidence**: The devil's advocate frames this as a mechanism design problem -- without a specified algorithm, there is no way to evaluate whether auto-generated agents will produce adversarial pressure. The consumer advocate frames it as a relevance problem -- without domain-aware routing, agents feel generic and unhelpful. Both perspectives converge on the same conclusion: the spec cannot defer agent generation as an implementation detail. It is the core UX mechanism of "Just Ask" mode and its quality determines whether the mode delivers value.
  - **Confidence level**: High. Both reviews independently identify this as a critical gap, from different angles (mechanism quality vs. consumer relevance), and both argue it must be resolved in the spec rather than deferred to implementation.

- **Vague Question Handling Is a Critical Gap**
  - **Shared position**: Both reviews identify that the proposal does not specify what happens when users ask vague, ambiguous, or malformed questions. The consumer advocate raises this as the top missed opportunity: "Consumer users ask bad questions constantly. The system must handle this gracefully or it will feel broken." (Missed Opportunities, item 1). The devil's advocate's quality criteria implicitly require this: if the synthesis must "surface at least one substantive disagreement," a vague question that produces no real disagreement would fail the quality bar (Actionable Recommendations, item 1).
  - **Combined evidence**: The consumer advocate provides the user behavior evidence -- non-technical users will type "help me decide" and "what should I do" -- and identifies the decision framework's existing `[CLARIFY: ...]` mechanism as a solution template. The devil's advocate provides the structural argument: without quality criteria, there is no way to detect when a vague question has produced a degenerate deliberation. Together, these perspectives define both the problem (users will ask bad questions) and the detection mechanism (quality criteria that flag degenerate output), which is stronger than either alone.
  - **Confidence level**: High. Both reviews independently identify this gap, provide complementary evidence, and both rate the impact as high. The decision framework spec already has a partial solution (`[CLARIFY: ...]` tags) that the adoption harness needs to adapt for the "Just Ask" context.

- **The Proposal's Open Questions Are Load-Bearing, Not Cosmetic**
  - **Shared position**: Both reviews treat the proposal's eight open questions (L129-138) as unresolved decisions that affect the viability of the architecture, not as optional items for later consideration. The devil's advocate states: "several of them, if answered differently than the proposal implicitly assumes, would invalidate entire sections of the architecture" (Executive Summary). The consumer advocate's entire Off-Base Assumptions section is built on the premise that the proposal has already implicitly answered open questions in ways that disadvantage consumers (e.g., "Just Ask" as CLI-first, MCP as primary).
  - **Combined evidence**: The devil's advocate identifies open question 1 (engine extraction) as a blocking architectural decision that cannot be deferred (Actionable Recommendations, item 5). The consumer advocate identifies the implicit answer to the MCP-vs-web-app priority question as setting the wrong default for the consumer audience (Off-Base Assumptions, item 2). Together, both reviews demonstrate that the proposal's open questions are not independent -- answering them one way produces a developer tool, answering them another way produces a consumer product, and the proposal's build order has already implicitly chosen the developer-tool path.
  - **Confidence level**: High. Both reviews independently reach the same structural critique: the open questions are not deferrable, and the proposal's implicit answers to them create a developer-first trajectory that must be made explicit and deliberate rather than accidental.
