# Consumer Advocate — Final Disputes and Convergence

---

### Remaining Disputes

- **Dispute: Minimal web artifact must be in-scope for this spec, not conditionally gated**
  - **My claim**: A minimal web artifact — a single-page "Just Ask" interface with no auth, no history, no PostgreSQL — ships as the step immediately after "Just Ask" engine work, within this spec's scope (revision, Modified Recommendation 1). The engine API must be designed with web-app consumption as a first-class requirement from step 1 (revision, New Recommendation 2). Every deliberation output should produce a shareable artifact including a standalone share page with CTA (revision, Modified Recommendation 8).
  - **Opposing position(s)**: The architect's revised position removes the web app from v1 scope entirely and proposes evaluating "lightweight alternatives (Slack bot, simple hosted form) alongside the engine work, rather than committing to a full web app prematurely" — leaving the consumer surface as an open question with no commitment (architect revision, Modified Recommendation 4). The devil's advocate's revised position does not preemptively create a separate web app spec and instead defines "a quantitative adoption gate (e.g., measurable demand from non-technical users via CLI/MCP channels) that triggers a dedicated web app spec" (devil's advocate revision, Modified Recommendation 7) — but CLI/MCP channels are inaccessible to non-technical users, making this gate structurally unpassable for the consumer audience.
  - **Why I will not concede**: The adoption-strategist's revision already conceded on this point: "I was wrong to propose 'cut entirely' because it eliminated the possibility of consumer validation, not just the full-stack investment" (adoption-strategist revision, Modified Recommendation 8). The minimal web form is the compromise position — it is not the full Next.js + PostgreSQL stack the architect objects to. The architect's and devil's advocate's positions require measuring "demand from non-technical users via CLI/MCP channels," but non-technical users do not use CLI or MCP. This is the self-fulfilling prophecy the adoption-strategist acknowledged: testing only through developer channels guarantees the absence of consumer data, which is then interpreted as the absence of consumer demand. The proposal's own vision statement declares conversus a "general-purpose decision-making tool" for "personal decisions (stock picking, career choices, vacation planning)" — users who will never touch a terminal. If the spec does not commit to at least a minimal consumer-accessible surface, it contradicts its own vision.
  - **Counter-argument to their position**: The architect argues the consumer surface should remain an open question — "evaluate lightweight alternatives (Slack bot, simple hosted form)" — but this framing treats consumer access as optional exploration rather than a product requirement. A Slack bot requires the user to have a Slack workspace, which is a workplace tool, not a consumer channel. The devil's advocate's adoption gate — "measurable demand from non-technical users via CLI/MCP channels" — is logically incoherent: it asks non-technical users to demonstrate demand through channels they cannot access. The adoption-strategist has already shown that a minimal hosted web form is "days of work, not weeks" (adoption-strategist revision, Modified Recommendation 8). The cost is trivially small relative to the information value. The architect's scope concern applies to the full-featured web app, which I agree should be a separate spec — but a single-page form with a text input is not a "5+ new technology layers" addition.
  - **Proposed resolution path**: The synthesizer should adopt the adoption-strategist's compromise: remove the full-featured web app from this spec, but include a minimal hosted web form as part of the consumer validation gate. The form is a single page, no auth, no history, no PostgreSQL — it calls the same engine API as CLI/MCP. The share page (a standalone rendered deliberation with CTA) is included in this minimal scope. The full web app is triggered by a separate spec (012) if the minimal form demonstrates consumer traction. This is the position the adoption-strategist, the devex-advocate, and I converge on. The architect and devil's advocate should accept it because it addresses their scope concern (no full stack) while preserving the ability to validate consumer demand through a consumer-accessible channel.

- **Dispute: Dual-primary integration path labels must appear in the spec**
  - **My claim**: Replace "Primary Integration Path" (currently labeling only MCP) with audience-qualified labels: "Primary Developer Integration Path" for MCP, "Primary Consumer Integration Path" for the web artifact (revision, Surviving Recommendation 6). Labels shape internal prioritization and prevent the consumer path from being permanently deprioritized.
  - **Opposing position(s)**: The architect's revised position does not address labeling and treats MCP as the primary integration path without qualification (architect revision, Modified Recommendation 4 discusses web deferral but does not address the label). The devil's advocate's revised position is silent on the dual-primary label. The adoption-strategist's revised position proposed "sequential validation — prove one channel first, then expand" (adoption-strategist revision, Recommendation 2), which is compatible with dual-primary labeling but does not explicitly endorse it.
  - **Why I will not concede**: The proposal currently states "MCP Server (Primary Integration Path)" as a section heading. This label signals that MCP is the product's primary channel and everything else is secondary. For a product whose vision includes non-technical users, this is a design-level commitment to developer primacy. Labels are cheap — changing a heading costs nothing — but they shape how every subsequent design decision is framed. If MCP is "primary" and the web app is unlabeled, every scope cut will deprioritize the consumer path because it is not "primary." The devex-advocate's revision agreed that "the dual-primary framing is correct" (referenced in my revision, Surviving Recommendation 6). The decision framework (spec 003, Section 9, Constraints) states the system "Must NOT require coding knowledge to use" — if the primary integration path requires coding knowledge, this constraint is violated at the architectural level.
  - **Counter-argument to their position**: Silence on labeling is not neutrality — it is acceptance of the status quo label, which privileges developers. The adoption-strategist's "sequential validation" approach is about build order, not about which paths are primary. You can build developer surfaces first while still declaring that the consumer surface is equally primary in importance. The sequencing question (what ships first) and the priority question (what matters most) are independent. The architect's scope concern is about the full web app's engineering cost, not about whether consumers matter. Accepting the dual-primary label costs zero engineering effort and commits only to the principle that both audiences are first-class.
  - **Proposed resolution path**: The synthesizer should change the heading from "MCP Server (Primary Integration Path)" to "MCP Server (Primary Developer Integration Path)" and add "Web App / Hosted Form (Primary Consumer Integration Path)" with a note that the consumer path ships after initial developer validation but is architecturally primary, not secondary. This is a wording change, not a scope change. If the architect or devil's advocate object, the synthesizer must choose — but the objection would be to a label, not to engineering cost.

- **Dispute: Vague-question handling must be specified as a required engine behavior, not deferred to distribution channels**
  - **My claim**: The "Just Ask" pipeline must handle vague input gracefully — including a conversational clarification step (one focused question, not five) for interactive channels and a structured error for non-interactive channels (revision, Surviving Recommendation 2). This should be implemented as a `QuestionClassifier` protocol or `NEEDS_CLARIFICATION` state in the engine's execution flow, not left to each distribution channel to implement independently (revision, New Recommendation 2, referencing the architect's proposed `QuestionClassifier` protocol).
  - **Opposing position(s)**: The architect proposed a `QuestionClassifier` protocol at P2 priority (architect revision, New Recommendation 1). The devil's advocate and devex-advocate do not prioritize vague-question handling — neither lists it as a P1 concern. The adoption-strategist endorses the concept but focuses on shipping speed, implying clarification is a refinement after initial validation (adoption-strategist revision, Modified Recommendation 1 focuses on output contract and config-generation, not input handling).
  - **Why I will not concede**: Vague-question handling is where consumer adoption succeeds or fails. Non-technical users are the most likely to provide unclear input ("help me decide," "what should I do about my career," "is this a good investment") and the least equipped to know what the system needs. If "Just Ask" receives vague input and silently produces shallow output, the user concludes conversus is no better than ChatGPT — and they are right, because the system did not engage with the real decision. The decision framework (spec 003, US-1, AC-5) already specifies `[CLARIFY: ...]` tags for vague input. The adoption harness must adapt this into a conversational, cost-controlled clarification step. The architect agrees on the mechanism (the `QuestionClassifier` protocol) but rates it P2. For consumer users, it is P1 — a "Just Ask" mode that cannot handle "help me decide" is not a "Just Ask" mode.
  - **Counter-argument to their position**: The architect's P2 rating reflects an infrastructure perspective — the engine works correctly on well-formed input, so clarification is an enhancement. But from the consumer perspective, most input will not be well-formed. Rating clarification as P2 means the first consumer-facing release will handle well-formed questions (which consumers rarely ask) and fail on vague questions (which consumers usually ask). The adoption-strategist's focus on shipping speed is valid, but the devil's advocate's own argument about first impressions applies here: if the first 100 consumer users ask vague questions and get shallow output, the validation data says "consumers don't value conversus" when the real lesson is "consumers couldn't use it." The cost of a single cheap-model clarification call is trivially small compared to the cost of a false-negative validation.
  - **Proposed resolution path**: The synthesizer should elevate the `QuestionClassifier` / `NEEDS_CLARIFICATION` state to P1 for the "Just Ask" mode specifically. It can remain P2 for power-user and guided modes where input is already structured. The implementation can be lightweight — a single cheap-model call that classifies input sufficiency and generates one clarification question if needed. This is the architect's proposed mechanism at the consumer advocate's proposed priority. The adoption-strategist's speed concern is addressed because a single classification call adds seconds, not weeks, to the pipeline.

### Convergence

- **Converged: Deliberation quality criteria must be defined before shipping "Just Ask"**
  - **Shared position**: Before the "Just Ask" prototype ships (even as a Claude Code skill), define minimum quality criteria that distinguish conversus output from a single-model response. At minimum: (1) the synthesis must surface at least one substantive disagreement between agents, (2) each agent must reference specific evidence or reasoning, and (3) the recommendation must acknowledge trade-offs. If the 2-agent, 1-round configuration cannot meet these criteria, design a "mini-cross-review" (agents respond to each other in a single combined prompt) to preserve adversarial pressure.
  - **Agreeing agents**: Devil's advocate (revision, Surviving Recommendation 1 and New Recommendation 1), consumer advocate (revision, New Recommendation 1), devex-advocate (revision, New Recommendation 1), adoption-strategist (revision, New Recommendation 1), architect (revision, Modified Recommendation 8 — quality gate as priority 1 constraint on Just Ask output).
  - **Strength**: Unanimous
  - **Path to convergence**: The devil's advocate identified this gap in Phase 1. In Phase 2 (cross-reviews), every agent acknowledged the blind spot. The consumer advocate, devex-advocate, and adoption-strategist all added new P1 recommendations on quality criteria in their revisions. The architect elevated quality to the first constraint on Just Ask output format. This is the single strongest consensus finding in the entire deliberation — five agents independently arrived at the same conclusion through different reasoning paths (the devil's advocate from the "ChatGPT wrapper" risk, the consumer advocate from the UX quality concern, the devex-advocate from the output schema design concern, the adoption-strategist from the first-impression risk, the architect from the output contract integrity concern).

- **Converged: The full-featured web app should be removed from this spec and addressed in a separate spec**
  - **Shared position**: The full Next.js + FastAPI + WebSocket + PostgreSQL + auth + history web app described in the proposal is too large and underspecified to be part of this spec's build order. It should be addressed in a separate spec (012 or later) with proper architectural depth. The engine should be designed with web-compatible requirements (streaming events, structured output, no filesystem-only assumptions) from day one to prevent CLI-shaped abstractions from calcifying.
  - **Agreeing agents**: Architect (revision, Modified Recommendation 4), devil's advocate (revision, Modified Recommendation 7), adoption-strategist (revision, Modified Recommendation 8), devex-advocate (revision, New Recommendation 2 — gated behind adoption metric), consumer advocate (revision, Modified Recommendation 1 — agrees on removing the full web app, disagrees only on whether a minimal form is in-scope).
  - **Strength**: Unanimous
  - **Path to convergence**: The architect proposed this in Phase 1 and it was initially contested by the consumer advocate (who wanted to elevate the web app). Through cross-reviews, the consumer advocate accepted that the full web app's scope is too large for this spec, modifying the position to advocate for a minimal artifact instead. All five agents now agree the full web app leaves this spec. The remaining dispute (above) is about whether a minimal form stays in-scope, not about the full web app.

- **Converged: Engine extraction should be decomposed into independently testable sub-phases**
  - **Shared position**: Treating engine extraction as a single build phase is a planning failure. The extraction should be decomposed into at least five sub-phases: config parser, template engine, async dispatch, dispute parsing, and output manager. Each sub-phase has distinct inputs, outputs, and testability criteria.
  - **Agreeing agents**: Architect (revision, Surviving Recommendation 2), devex-advocate (revision, endorsement in Safe Agreements context), adoption-strategist (revision, endorsement from adoption-timeline perspective), devil's advocate (revision, endorsement with extraction approach addendum), consumer advocate (revision, endorsement from product perspective, referenced in original review Safe Agreements).
  - **Strength**: Unanimous
  - **Path to convergence**: This was agreed from Phase 1. The architect proposed it, and no cross-review challenged it. All four cross-reviews endorsed it independently. It is the only recommendation that received zero challenges across the entire deliberation.

- **Converged: Structured output with progressive disclosure rendering per distribution channel**
  - **Shared position**: The engine produces structured, template-conformant output as the canonical artifact. This structured output includes machine-extractable fields (headline/recommendation, summary/trade-offs, full analysis/debate transcript, confidence/quality indicators). Each distribution channel renders these fields according to its audience: progressive disclosure layers for web, concise + expandable for CLI, typed `Result` dataclass for SDK, structured JSON for MCP. Neither structured data nor prose rendering is derived from the other — both are first-class projections of the canonical output.
  - **Agreeing agents**: Consumer advocate (revision, Modified Recommendation 4), devex-advocate (revision, Modified Recommendation 2), architect (revision, Modified Recommendation 8), adoption-strategist (revision, New Recommendation 2 — "same data, different renderings").
  - **Strength**: Majority (four agents). The devil's advocate does not contest the structure but prioritizes quality criteria over format design.
  - **Path to convergence**: In Phase 1, the consumer advocate proposed progressive disclosure, the devex-advocate proposed structured output, and the architect proposed template-conformant markdown. These initially appeared as competing requirements. Through cross-reviews, all three agents recognized these are complementary layers, not alternatives. The architect's template-conformant markdown is the canonical artifact; the devex-advocate's structured types and the consumer advocate's progressive disclosure are both renderings. The adoption-strategist's revision explicitly adopted "same data, different renderings" as the unifying principle.

- **Converged: Confidence indicators combining quantitative metadata and qualitative labels**
  - **Shared position**: Deliberation results should include both quantitative metadata (agent count, mode used, disagreements surfaced, disagreements surviving) and qualitative confidence labels ("Strong recommendation" / "Moderate recommendation" / "Close call"). The quantitative metadata serves developers and programmatic consumers; the qualitative labels serve non-technical users. Documented bucket boundaries map between them. The confidence value is derived from deliberation dynamics (dispute convergence, cross-review agreement), not from model self-assessment.
  - **Agreeing agents**: Consumer advocate (revision, Modified Recommendation 5), devex-advocate (revision, Modified Recommendation 2 — quality_indicators replacing raw confidence float), adoption-strategist (revision, Modified Recommendation 9 — combined quantitative metadata with qualitative labels).
  - **Strength**: Bilateral expanding to majority. The consumer advocate and adoption-strategist converged on this in Phase 2. The devex-advocate's revision replaced the raw confidence float with quality indicators, which is compatible. The devil's advocate's concern about meaningless confidence values from shallow deliberations is addressed by the quality criteria convergence above — confidence is only reported when deliberation quality meets the minimum bar.
  - **Path to convergence**: The consumer advocate proposed qualitative labels in Phase 1. The devex-advocate proposed a confidence float. Through cross-reviews, both recognized these serve different audiences and proposed documented mappings between them. The devil's advocate's challenge — that confidence from a 2-agent run is meaningless — was resolved by the unanimous quality criteria convergence: if the deliberation meets quality criteria, the confidence value is grounded; if it does not, the output should honestly reflect that rather than displaying a false confidence score.

### Final Position Statement

**Non-Negotiables** (3 items):

1. **A consumer-accessible surface must exist in the initial release cycle, even if minimal.** A single-page hosted web form with a text input, calling the same engine as CLI/MCP, is the minimum viable consumer channel. Without it, the product cannot validate whether non-technical users find value in conversus, and every adoption decision will be based on developer-only data. (Revision, Modified Recommendation 1; adoption-strategist revision, Modified Recommendation 8, acknowledging the self-fulfilling prophecy risk.)

2. **Vague-question handling must be a P1 engine behavior for "Just Ask" mode, not deferred or left to channels.** Non-technical users will ask vague questions — "help me decide," "what should I do" — and if the system silently produces shallow output, they will conclude it adds no value. A single cheap-model classification call that generates one clarification question when input is insufficient is the minimum viable implementation. (Revision, Surviving Recommendation 2; spec 003, US-1, AC-5 establishing the `[CLARIFY: ...]` precedent.)

3. **The spec must use dual-primary integration path labels.** "Primary Developer Integration Path" for MCP, "Primary Consumer Integration Path" for the web artifact. This is a zero-cost labeling change that prevents the consumer path from being treated as permanently secondary. (Revision, Surviving Recommendation 6; proposal Section "MCP Server (Primary Integration Path)" currently labeling only MCP.)

**Flexibility** (3 items):

1. **The timing of the minimal web form relative to MCP/CLI is flexible; the commitment to building it is not.** I accept that the minimal web form can ship after the Claude Code skill, MCP server, and CLI — the adoption-strategist's sequential validation is a sound build order. What must be preserved: the minimal web form is committed to in this spec with a defined timeline, not left as an open question that depends on developer-channel data to trigger.

2. **The specific implementation of vague-question handling is flexible; the requirement that it exists is not.** Whether clarification uses the architect's `QuestionClassifier` protocol, a simpler prompt-based sufficiency check, or a `NEEDS_CLARIFICATION` state in the execution flow is an implementation choice. What must be preserved: the "Just Ask" pipeline has an explicit behavior for insufficient input that produces a clarification response rather than silently degrading output quality.

3. **The confidence label thresholds are flexible; the existence of qualitative labels alongside quantitative metadata is not.** The specific bucket boundaries (0.0-0.4 = "Close call," 0.4-0.7 = "Moderate recommendation," 0.7-1.0 = "Strong recommendation") can be adjusted based on calibration data. What must be preserved: non-technical users see a plain-language confidence signal, not a raw float or developer-oriented metadata.
