# Devil's Advocate — Revised Position (Iteration 1)

---

## Recommendation Dispositions

#### Recommendation 1: Define deliberation quality criteria

- **Original position**: Add a "Quality Model" section defining minimum criteria for valid deliberation output — the synthesis must surface at least one substantive disagreement, each agent must reference specific evidence, and the recommendation must acknowledge trade-offs — with a mechanism to detect when "just ask" output has degenerated to single-model-equivalent quality.
- **Disposition**: Surviving
- **Explanation**: This recommendation received the broadest cross-review support of any position in my review. The devex-advocate's cross-review explicitly endorsed it as the prerequisite for structured output design: "define minimum quality criteria for 'just ask' mode first, then design the structured output format around those criteria" (devex-advocate cross-review, Dangerous Contradictions, "'Just ask' mode: gutting value vs. shipping value"). The consumer-advocate's cross-review agreed the quality floor should come before the progressive disclosure layer: "first, adopt the devil's advocate's quality criteria... Then, adopt the consumer advocate's progressive disclosure" (consumer-advocate cross-review, Dangerous Contradictions, "'Just Another ChatGPT Wrapper'"). The adoption-strategist's cross-review challenged the recommendation as a potential shipping gate that could create a "specification loop," but then conceded: "The devil's advocate is right that some quality floor must exist before shipping" (adoption-strategist cross-review, Dangerous Contradictions, "Quality criteria as a gate vs. quality criteria as an iteration target"). Even the adoption-strategist's suggested compromise — two heuristic quality checks testable in 30 minutes — is entirely compatible with my recommendation; it is a scoping refinement, not a refutation. No cross-review argued this recommendation is unnecessary. It remains my highest-priority recommendation.

#### Recommendation 2: Add model capability requirements per mode

- **Original position**: Define a capability matrix specifying which modes require which model features, with runtime validation that warns or blocks when the selected model cannot support the requested deliberation depth.
- **Disposition**: Modified
- **Explanation**: The architect's cross-review surfaced a genuine tension between a static capability matrix (my proposal) and runtime output validation via a `ConversusAgent` abstraction (architect cross-review, Tensions, "Model capability gates vs. model agnosticism"). The devex-advocate's cross-review made this tension sharper: a thin provider interface deliberately avoids model-specific knowledge, while a capability matrix requires it (devex-advocate cross-review, Tensions, "Model agnosticism: capability matrix vs. provider interface"). The consumer-advocate's cross-review added a crucial user-segmentation point: for consumer-facing tiers, model capability validation must be invisible — the system selects a capable model, and failure to do so is a platform bug, not a user error (consumer-advocate cross-review, Tensions, "Model Capability Requirements vs. Consumer Accessibility").

  **Modified recommendation**: Replace the static capability matrix with a dynamic quality validation layer. Instead of maintaining a catalog of model capabilities (which is brittle and requires constant updates), the engine should validate agent output structure after generation — checking whether required review sections, dispute markers, and template headings are present and substantive. For consumer-facing tiers, model selection is a platform responsibility and capability failures are handled by automatic fallback to a known-good model, never surfaced to the user. For power-user tiers, output validation failures produce warnings with diagnostic information. This preserves the core concern (preventing garbage output from weak models) while adopting the devex-advocate's and architect's insight that runtime validation is more robust than static lookup.

#### Recommendation 3: Design the cross-review bypass for lightweight mode

- **Original position**: Explicitly design the phase subset for "just ask" mode, including what adversarial pressure mechanism replaces cross-reviews if they are skipped. Consider a "mini-cross-review" where agents respond to each other in a single combined prompt.
- **Disposition**: Surviving
- **Explanation**: This recommendation was the most contested across all cross-reviews, but the challenges reinforced rather than undermined it. The consumer-advocate's cross-review acknowledged the structural concern while advocating for consumer speed, then converged on my own suggestion: "design a 'mini-cross-review' where agents respond to each other in a single combined prompt rather than isolated phases" (consumer-advocate cross-review, Dangerous Contradictions, "Lightweight Deliberation: Value Preservation vs. Consumer Speed"). The adoption-strategist's cross-review endorsed the same compromise: "The devil's advocate's 'mini-cross-review' suggestion is the right compromise — a single combined prompt where agents respond to each other's initial positions within one additional round" and proposed a concrete budget of "2 agents + 1 mini-cross-review + 1 synthesis = 4 launches" (adoption-strategist cross-review, Dangerous Contradictions, "'Just Ask' lightweight mode: value-preserving or value-destroying?"). The architect's cross-review raised a valid compatibility concern — the mini-cross-review output must conform to template structure for ecosystem composability (architect cross-review, Dangerous Contradictions, "'Just Ask' quality: structural redesign vs. quality metric") — which I accept as a design constraint on the mini-cross-review, not an argument against it. Four of four cross-reviews either endorsed or refined this recommendation. The adoption-strategist's "4 launches" budget is a useful concrete target that I adopt as part of this recommendation.

#### Recommendation 4: Add cost estimation and budget controls

- **Original position**: Add a "Cost Model" section with per-tier API cost estimates, pre-execution cost estimation with user confirmation for consumer-facing modes, and budget caps for programmatic use.
- **Disposition**: Modified
- **Explanation**: The consumer-advocate's cross-review raised a legitimate UX concern: a cost confirmation dialog breaks the frictionless consumer flow. "A consumer who types 'Should I lease or buy my next car?' and then sees 'Estimated cost: $0.47. Proceed?' will be confused, annoyed, or frightened" (consumer-advocate cross-review, Tensions, "Cost Visibility vs. Frictionless Experience"). The devex-advocate's cross-review reframed cost visibility as a per-surface concern: the web app shows a consent dialog, the CLI/SDK returns a structured estimate, and MCP includes cost in response metadata (devex-advocate cross-review, Tensions, "Cost controls: who pays vs. how much"). The adoption-strategist's cross-review noted that if the web app is deferred, cost controls are less urgent for the initial release since CLI/MCP/SDK users are developers who understand API costs (adoption-strategist cross-review, Tensions, "Cost awareness: when to surface it"). The architect's cross-review added that per-phase model selection must be designed into the engine from the start for cost estimation to work at all (architect cross-review, Tensions, "Cost as an adoption concern vs. cost as an architecture concern").

  **Modified recommendation**: Cost estimation should be a core engine capability (shared infrastructure) exposed differently per surface. For the SDK/CLI/MCP (the initial distribution surfaces), expose a `dry-run` or `estimate` mode that returns structured cost data — token count, API call count, estimated dollar range — so developers and CI pipelines can evaluate cost before execution. Per-run cost confirmation dialogs are a consumer-tier feature that belongs in the web app spec, not the engine spec. For the engine itself, per-phase model configuration (enabling model tiering) must be designed in from the start so that cost estimation has the data it needs. This preserves the core concern (users must not be surprised by costs) while accepting that the presentation layer is surface-specific and the consumer dialog belongs in a later spec.

#### Recommendation 5: Resolve the engine extraction question before proceeding

- **Original position**: Open question 1 is a blocking architectural decision, not an open question. The proposal should commit to Python extraction with a concrete migration plan or commit to the adapter approach with a concrete interface definition.
- **Disposition**: Modified
- **Explanation**: The architect's cross-review agreed this is blocking but went further — arguing the answer is already determined: "the Python engine is the canonical implementation" because spec 007's plugin system only works in Python (architect cross-review, Dangerous Contradictions, "Engine extraction framing: blocking decision vs. blocking architecture"). The adoption-strategist's cross-review challenged the timing, arguing that "Just Ask" can and should ship as a Claude Code skill first, before engine extraction (adoption-strategist cross-review, Dangerous Contradictions, "Build order sequencing: infrastructure-first vs. adoption-first"). The devex-advocate's cross-review noted that their SDK API design implicitly presupposes Python extraction, creating a dependency that must be acknowledged (devex-advocate cross-review, Dangerous Contradictions, "Engine extraction: commit vs. defer").

  The adoption-strategist's challenge forced the most significant change in my thinking. The strategist is correct that shipping "Just Ask" within the existing SKILL.md runtime provides real user validation before committing to the expensive extraction. My original position treated this as a pure architectural decision that must precede all work. The strategist demonstrated it is also a product validation question that can be answered in parallel.

  **Modified recommendation**: Explicitly commit to Python extraction as the target architecture (the architect's evidence about spec 007 compatibility makes the adapter approach a dead end for features that depend on plugins). However, allow a time-boxed prototype of "Just Ask" within the existing SKILL.md runtime to validate the product concept before beginning extraction. The prototype has a defined sunset: it informs the extraction, it does not replace it. Engine extraction begins once the prototype validates the concept or after a defined time limit (whichever comes first), and the prototype is retired once the Python engine ships. This prevents the adoption-strategist's concern about "waiting for extraction before any user validation" while preventing the indefinite deferral of extraction that would leave the project stuck on a single-runtime architecture.

#### Recommendation 6: Add failure mode analysis for multi-provider execution

- **Original position**: Add a "Failure Modes" section addressing agent failure in parallel batches, provider-specific rate limits, output validation, and mid-deliberation outages.
- **Disposition**: Modified
- **Explanation**: The architect's cross-review created a useful tension: the architect wants to start with a single-provider minimum viable extraction (MVE) where failure modes are simpler, while I want comprehensive failure mode analysis for multi-provider execution (architect cross-review, Tensions, "Failure mode scope: multi-provider vs. single-provider"). The devex-advocate's cross-review added that failure handling at the engine level determines what errors the interface can surface — these are complementary layers that must be designed together (devex-advocate cross-review, Tensions, "Failure modes: multi-provider vs. single-provider").

  **Modified recommendation**: Design the failure isolation contract for the single-provider case first, as part of the minimum viable extraction. The key design question to resolve now — applicable to both single and multi-provider scenarios — is: does a single agent failure abort the phase or continue with N-1 agents? Define this semantics in the engine's dispatch contract. Document multi-provider failure modes (provider-specific rate limits, API incompatibilities, mixed-provider consistency) as known future requirements that the dispatch engine's error contract must be extensible enough to handle, but do not require full multi-provider failure analysis before shipping the single-provider engine. This scoping change does not reduce rigor — it sequences it appropriately.

#### Recommendation 7: Separate the web app into its own spec

- **Original position**: Remove the web app from this spec's build order and create a separate spec (012 or later) after the core engine, CLI, and MCP server are stable.
- **Disposition**: Modified
- **Explanation**: All four cross-reviews agreed the web app should leave this spec, making this the strongest consensus finding in the entire deliberation. However, the cross-reviews diverged on framing in ways that matter. The consumer-advocate's cross-review warned that deferring the web app entirely risks designing engine abstractions that feel wrong in a browser — "Building 'Just Ask' as a headless engine and then bolting a web UI onto it will produce a developer tool with a web skin" (consumer-advocate cross-review, Dangerous Contradictions, "Web App Deferral vs. Consumer-First Delivery"). The architect's cross-review recommended removing the web app from v1 scope entirely but adding a minimum engine constraint: "the dispatch engine must emit phase-lifecycle events that a future streaming consumer could subscribe to" (architect cross-review, Dangerous Contradictions, "Web app scope: separate spec vs. v2 deferral"). The adoption-strategist's cross-review argued the web app should only be built if demand is validated by earlier channels (adoption-strategist cross-review, Tensions, "Scope of web app critique: defer vs. separate").

  **Modified recommendation**: Remove the web app from this spec's build order and scope. Do not create a separate web app spec preemptively. Instead, define a quantitative adoption gate (e.g., measurable demand from non-technical users via CLI/MCP channels) that triggers a dedicated web app spec. However — and this is the critical addition prompted by the consumer-advocate and architect — the engine's API contract must include web-app-compatible design requirements from day one: streaming phase-lifecycle events, structured output suitable for progressive rendering, and no assumption of filesystem-only storage. These requirements are engine constraints, not web app features, and they belong in this spec. This addresses the consumer-advocate's concern about CLI-shaped abstractions calcifying while accepting the adoption-strategist's demand-validation gate.

#### Recommendation 8: Define what "auto-generates 2-4 appropriate agents" means concretely

- **Original position**: Define the agent generation algorithm by evaluating at least two approaches (classification model, prompt-based generation, rule-based heuristics) and selecting one with rationale.
- **Disposition**: Modified
- **Explanation**: The adoption-strategist's cross-review implicitly answered this question by pointing to spec 003's existing heuristics as the foundation for auto-generation — classify the problem type, map to interest patterns, generate agents accordingly (adoption-strategist cross-review, Tensions, "Agent auto-generation: specify the algorithm vs. ship and iterate"). The devex-advocate's cross-review proposed that the auto-generation algorithm should use the preset system internally, with programmatic preset composition as the underlying infrastructure (devex-advocate cross-review, Tensions, "Auto-generated agents: algorithm vs. API").

  **Modified recommendation**: Use spec 003's existing classification heuristics as the initial agent generation algorithm (the adoption-strategist's implicit answer), built on top of the programmatic preset API (the devex-advocate's infrastructure recommendation). The spec should document this as the chosen approach — classification-based mapping to preset compositions — rather than requiring evaluation of multiple alternatives before implementation. However, the quality criteria from Recommendation 1 serve as the acceptance test: if the heuristic-to-preset pipeline produces agents with nearly identical perspectives or perspectives irrelevant to the question domain, the quality gate catches it, and the algorithm is iterated. This satisfies my concern about poorly generated agents without requiring the upfront comparative evaluation I originally demanded.

#### Recommendation 9: Address the "just another ChatGPT wrapper" risk head-on

- **Original position**: Add a "Differentiation" section with a concrete side-by-side example demonstrating how conversus "just ask" output differs structurally from single-model output.
- **Disposition**: Surviving
- **Explanation**: The adoption-strategist's cross-review endorsed the need for differentiation but framed it as a product feature ("see the debate" output) rather than a spec-level demonstration (adoption-strategist cross-review, Tensions, "Competitive differentiation: structural vs. visible"). The consumer-advocate's cross-review agreed both approaches are needed and sequenced them: "Both positions are needed... the devil's advocate provides the 'is it actually better' gate; the consumer advocate provides the 'can users see that it is better' layer" (consumer-advocate cross-review, Dangerous Contradictions, "'Just Another ChatGPT Wrapper'"). No cross-review argued this recommendation is unnecessary. The adoption-strategist's cross-review explicitly stated: "Do both. The spec should include a side-by-side example to validate that the differentiation is real, and the product should surface the debate in every output" (adoption-strategist cross-review, Tensions, "Competitive differentiation: structural vs. visible"). The side-by-side example serves as a design validation artifact that proves the value exists before the "see the debate" feature is built to communicate it. If the side-by-side comparison fails to show a meaningful difference, the product has a foundational problem that no UX feature can fix.

#### Recommendation 10: Define the MCP tool contract more precisely

- **Original position**: For each of the six MCP tools, define input schema, output schema, error contract, and execution model.
- **Disposition**: Modified
- **Explanation**: The devex-advocate's cross-review strongly endorsed this recommendation as a consensus finding: "Both reviews independently arrive at the same recommendation with complementary rationale" (devex-advocate cross-review, Safe Agreements, "MCP tool contracts must be specified before implementation"). The adoption-strategist's cross-review challenged the timing, arguing MCP should ship after Claude Code skill validation (adoption-strategist cross-review, Dangerous Contradictions, "MCP positioning"). My own cross-review of the adoption-strategist proposed a compromise: "define MCP contracts at a directional level now, and specify them precisely when MCP moves to the top of the build queue" (devils-advocate cross-review of adoption-strategist, Dangerous Contradictions, "MCP positioning"). The devex-advocate's cross-review also raised a valid point about MCP maturity being less of a concern than I originally framed — MCP is already supported by multiple IDEs (devex-advocate cross-review, Dangerous Contradictions, "MCP maturity assessment and build order priority").

  **Modified recommendation**: Define MCP tool contracts at two levels of specificity. Now: establish the directional contract for each tool — blocking vs. streaming execution, rough input/output shapes, and the error taxonomy. This is cheap and prevents integration-breaking surprises later. When MCP implementation begins: specify full input schemas, output schemas, and error contracts with the precision the devex-advocate demands. Additionally, I withdraw my characterization of MCP maturity as a medium-impact risk — the devex-advocate's evidence that MCP is already deployed across multiple IDEs is persuasive. The risk is not protocol maturity but conversus's MCP server design quality, which the two-level contract approach addresses.

## New Recommendations

- **Gate "Just Ask" prototype on minimum quality bar** (Priority: P1)
  - **Triggered by**: The adoption-strategist's cross-review of my Recommendation 1, which proposed a compromise between quality-as-gate and quality-as-iteration-target: "define two heuristic quality checks before shipping — (1) the synthesis must contain at least one point of genuine disagreement between agents, and (2) the output must structurally differ from a single-model response (i.e., show agent attributions)" (adoption-strategist cross-review, Dangerous Contradictions, "Quality criteria as a gate vs. quality criteria as an iteration target").
  - **Proposed change**: Before the "Just Ask" prototype ships (even as a Claude Code skill), validate that its output passes two binary tests: (a) the synthesis contains at least one substantive disagreement between agents (not just cosmetic differences in phrasing), and (b) the output includes agent attributions showing which perspective generated which argument. These two checks are testable in a single afternoon against 10-20 sample questions. If the prototype fails either test, it is not ready to ship — but these checks are lightweight enough to not delay shipping by more than days.
  - **Rationale**: The adoption-strategist correctly argued that exhaustive quality criteria should not block shipping. But shipping output that is literally indistinguishable from a single-model response would be worse than not shipping at all — it would create a negative first impression that poisons the adoption funnel. This recommendation threads the needle: a minimal, fast quality gate that prevents the worst failure mode without requiring months of quality model design.

- **Design engine API with streaming phase-lifecycle events** (Priority: P2)
  - **Triggered by**: The architect's cross-review of my web app deferral recommendation, which proposed: "the dispatch engine must emit phase-lifecycle events that a future streaming consumer could subscribe to" as the minimum hook to prevent painting the engine into a corner (architect cross-review, Dangerous Contradictions, "Web app scope: separate spec vs. v2 deferral"). The consumer-advocate's cross-review reinforced this: "require the engine API to be designed with web-native consumption patterns from day one" (consumer-advocate cross-review, Dangerous Contradictions, "Web App Deferral vs. Consumer-First Delivery").
  - **Proposed change**: The engine's dispatch contract should include a streaming event model — phase-started, agent-dispatched, agent-completed, phase-completed, synthesis-started, synthesis-completed — that any consumer (CLI progress bar, MCP streaming response, future web app) can subscribe to. This is an engine design requirement, not a web app feature.
  - **Rationale**: My original recommendation to separate the web app into its own spec was correct on scope but incomplete on forward-compatibility. The architect and consumer-advocate both identified that engine API decisions made now will constrain what distribution surfaces are possible later. Adding a streaming event model is low-cost during initial engine design but high-cost to retrofit. This recommendation ensures the web app deferral does not become a web app impediment.

## Position Summary

Of my 10 original recommendations, I maintained 3 (Recommendations 1, 3, and 9), modified 6 (Recommendations 2, 4, 5, 6, 8, and 10), and withdrew 0. I added 2 new recommendations that emerged from the cross-review process. The modifications were substantive — not cosmetic softening but genuine changes in mechanism, timing, or scope prompted by cross-review evidence.

The most significant change in my thinking was on Recommendation 5 (engine extraction). My original position treated engine extraction as a pure blocking architectural decision that must be resolved before any other work begins. The adoption-strategist's challenge — that "Just Ask" can ship as a Claude Code skill prototype before extraction — was the strongest argument I encountered in the cross-review process. The strategist is right that waiting for full Python extraction before any user validation is wasteful, and that a time-boxed prototype provides exactly the learning the extraction decision needs. I modified my recommendation to commit to Python extraction as the target architecture (the architect's spec 007 compatibility evidence settled the directional question) while allowing a prototype phase that the adoption-strategist's approach enables. This is not a retreat from my position that the extraction question must be resolved — it is a recognition that "resolved" can mean "committed direction with informed timing" rather than "fully implemented before anything else ships."

My remaining highest-priority recommendation is Recommendation 1: define deliberation quality criteria. It should survive into the final synthesis because it is the single recommendation that every other agent either explicitly endorsed or implicitly depends on. The devex-advocate needs quality criteria to ground the structured output schema. The consumer-advocate needs quality criteria to ensure progressive disclosure has something worth disclosing. The architect needs quality criteria to define what the "Just Ask" output contract guarantees. The adoption-strategist needs quality criteria to distinguish the prototype from "ChatGPT with extra steps." Without a quality model — even a minimal one — every other recommendation in this deliberation is building on an assumption that conversus output is better than single-model output, an assumption that no one has validated and that the proposal never specifies how to validate. That is the unchallenged assumption I exist to challenge, and it has survived every cross-review.
