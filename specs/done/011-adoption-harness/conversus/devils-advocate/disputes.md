# Devil's Advocate — Final Disputes and Convergence

---

### Remaining Disputes

- **Dispute: The side-by-side differentiation example must be a spec-level artifact, not a deferred product feature**
  - **My claim**: The spec should include a concrete side-by-side comparison demonstrating how conversus "Just Ask" output differs structurally from a single-model response for the same question. This example serves as a design validation artifact that proves the value exists before any shipping decision is made. (Revision, Recommendation 9, Surviving.)
  - **Opposing position(s)**: The adoption-strategist's revised position frames differentiation primarily as a product output feature — visible metadata ("3 agents debated this using cooperative mode. 2 disagreements were surfaced; 1 survived cross-review") and qualitative confidence labels — rather than as a spec-level validation artifact. The adoption-strategist's modified Recommendation 9 adds a side-by-side example as a secondary addition ("the spec itself should include a side-by-side example") but treats it as a "marketing asset" rather than as a design gate. The consumer-advocate's revised position does not include a side-by-side example requirement. The architect's revised position does not address differentiation demonstration at the spec level. The devex-advocate's revised position does not include this requirement.
  - **Why I will not concede**: The entire deliberation rests on an unvalidated assumption — that conversus's multi-agent output is meaningfully better than a single-model response for the "Just Ask" use case. Every agent has built recommendations on top of this assumption (the consumer-advocate's progressive disclosure assumes there is something worth disclosing; the devex-advocate's structured output schema assumes the fields contain substantive data; the architect's ecosystem compatibility assumes the output feeds value into downstream uses; the adoption-strategist's "see the debate" assumes the debate contains genuine disagreement). If the assumption is false — if a 2-agent, 1-round deliberation produces output that is functionally equivalent to asking Claude directly — then every other recommendation in this deliberation is building on sand. The side-by-side example is the cheapest possible way to test this assumption before committing any engineering effort. It is an afternoon of work. Not including it is choosing to spend months building on an unvalidated premise.
  - **Counter-argument to their position**: The adoption-strategist treats the side-by-side example as a "marketing asset" — useful but optional. This fundamentally mischaracterizes its purpose. A marketing asset communicates a known advantage. A design validation artifact tests whether the advantage exists. These are different activities with different stakes. If the side-by-side comparison reveals that "Just Ask" output is not meaningfully different from a single-model response, the correct action is to redesign the deliberation pipeline (perhaps requiring the mini-cross-review as a minimum, or increasing the default agent count), not to ship the product and hope users do not notice. An example that fails is more valuable than an example that is never attempted, because it identifies the problem before users do.
  - **Proposed resolution path**: The synthesis should require the spec to include at least one worked example: a specific question answered by both a single LLM call and a conversus "Just Ask" deliberation, with structural annotations showing where the outputs diverge (explicit disagreement, trade-off acknowledgment, evidence-grounded positions, surviving dissent). If the worked example fails to show meaningful differentiation, the spec must document what pipeline changes are required to achieve it. This is a gate on spec completion, not on shipping.

- **Dispute: The quality floor must gate the Just Ask prototype, not merely accompany it**
  - **My claim**: Before the "Just Ask" prototype ships (even as a Claude Code skill), it must pass two binary quality tests: (a) the synthesis contains at least one substantive disagreement between agents, and (b) the output includes agent attributions showing which perspective generated which argument. These are pre-ship gates, not post-ship iteration targets. (Revision, New Recommendations, "Gate 'Just Ask' prototype on minimum quality bar.")
  - **Opposing position(s)**: The adoption-strategist's revised position defines a quality floor (New Recommendations, "Define-Just-Ask-quality-floor") that is structurally similar to mine — same two checks, same fast-testable format — but frames the timing ambiguously. The strategist's language says "before shipping the Just Ask Claude Code skill, define two minimal quality checks" but then says "they are not a comprehensive quality model — that comes from the 100-decision validation." The distinction between "define the checks" and "gate shipping on the checks passing" is critical. The consumer-advocate's revised position (New Recommendations, "Adopt deliberation quality criteria for 'Just Ask' mode") includes a conditional that weakens the gate: "If the 2-agent, 1-round configuration cannot meet these criteria, design a 'mini-cross-review'... that preserves adversarial pressure while keeping latency and cost within consumer tolerance." This treats the quality failure as a design trigger rather than a shipping blocker — the prototype could ship while the mini-cross-review is being designed.
  - **Why I will not concede**: The distinction between "define checks" and "gate on checks" is the difference between a quality commitment and a quality aspiration. Defining checks without gating on them means the checks can be documented, acknowledged, and then shipped past because the team is under pressure to validate quickly. I have seen this pattern in every production system I have challenged: quality criteria are written, acknowledged as important, and then deprioritized because "we need user data first." The adoption-strategist's own argument makes this risk explicit — their entire framework is speed-to-users, and any gate that adds even days of delay will face pressure to be reclassified as an "iteration target." The quality floor must be a gate because the failure mode it prevents — negative first impressions from output indistinguishable from ChatGPT — is irreversible. Users who try conversus once and see no difference will not return for a second try after the team iterates. The adoption-strategist acknowledged this exact risk in their revision: "if the first 100 users' experience is indistinguishable from ChatGPT, the validation data does not say 'the product needs iteration' — it says 'users tried it once and left.'" This concession validates the gate framing, not the iteration-target framing.
  - **Counter-argument to their position**: The consumer-advocate's conditional — "if the 2-agent, 1-round configuration cannot meet these criteria, design a mini-cross-review" — introduces a temporal gap between discovering the quality failure and resolving it. During that gap, what happens? Either the prototype ships with known-substandard quality (defeating the purpose of the check), or shipping is blocked until the mini-cross-review is designed (which is the gate I am advocating for, just with extra steps). The conditional framing creates an illusion of flexibility that resolves to the same binary choice: ship with quality or do not ship. I am stating this binary explicitly rather than hiding it behind a conditional.
  - **Proposed resolution path**: The synthesis should adopt the two quality checks as pre-ship gates. The adoption-strategist's "testable in 30 minutes" framing is exactly right — these checks are fast enough to not delay shipping by more than a day. If the checks fail, the mini-cross-review is designed and implemented before shipping (not after). This sequencing costs at most a few additional days and prevents the irreversible first-impression damage that all agents acknowledged as the highest-risk failure mode.

- **Dispute: Engine extraction must be committed as target architecture in this spec, not deferred to Phase 0 evaluation**
  - **My claim**: The spec should explicitly commit to Python extraction as the target architecture, with a time-boxed SKILL.md prototype phase that validates the product concept before extraction begins. The extraction direction is already determined by spec 007's Python-only plugin system. (Revision, Recommendation 5, Modified.)
  - **Opposing position(s)**: The architect's revised position (Recommendation 7, Modified) defers the commitment: "The commitment to Python-as-canonical is made *after* the Phase 0 interface definition demonstrates that spec 007's plugin system requires a Python runtime." The architect treats this as an open evaluation to be resolved in Phase 0 rather than a decision to be recorded in this spec. The adoption-strategist's revised position (Recommendation 1, Modified) is compatible with my position on timing (prototype first, then extract) but does not explicitly commit to Python extraction as the target — the strategist is focused on the SKILL.md prototype and treats extraction as a later concern.
  - **Why I will not concede**: The architect's deferred-evaluation framing creates a risk that I identified in my original review and that the revision process did not resolve: if the extraction direction is left as an open question, every implementation decision between now and Phase 0 completion is made without architectural commitment. The SKILL.md prototype will accrete logic. The SDK types will be designed in a vacuum. The MCP tool contracts will be specified without knowing what engine they wrap. The architect's own evidence — that spec 007's lifecycle hooks, feature extraction, and `DeliberationState` are Python constructs — already answers the evaluation. Phase 0 will not discover new information that changes this conclusion. Framing a decided question as an open evaluation wastes the evaluation period and creates ambiguity that slows every dependent decision.
  - **Counter-argument to their position**: The architect argues that Phase 0 interface definitions are "approach-agnostic" — valid whether the implementation is Python extraction or SKILL.md adapters. This is technically true for the type definitions themselves but false for the design decisions they inform. If the target is Python extraction, the SDK types should be designed for direct in-process integration. If the target is SKILL.md adapters, the SDK types should be designed for subprocess communication with serialization boundaries. These are different design constraints that produce different type signatures. "Approach-agnostic" interface design that works for both approaches works optimally for neither. The architect's own modified Recommendation 1 acknowledges this implicitly by designing internal engine interfaces (`DeliberationState`, `AgentState`) and external SDK types (`Problem`, `Config`, `Result`) together — a design that only makes sense if both live in the same Python process.
  - **Proposed resolution path**: The synthesis should record: "The target architecture is Python extraction. The evidence is spec 007's Python-only plugin system (lifecycle hooks, `DeliberationState`, feature extraction). A time-boxed SKILL.md prototype validates the product concept before extraction begins. The prototype informs the extraction but does not replace it." This is a statement of direction, not a commitment to a timeline. The architect's Phase 0 interface work proceeds with the extraction commitment as context, not as a conclusion to be re-derived.

### Convergence

- **Converged: Deliberation quality criteria are a prerequisite for shipping Just Ask**
  - **Shared position**: The "Just Ask" mode must meet minimum quality criteria — at minimum, the synthesis must contain at least one substantive disagreement between agents, and the output must structurally differ from a single-model response — before any distribution surface ships it. Quality criteria inform the output schema, the MCP tool contracts, and the progressive disclosure design.
  - **Agreeing agents**: Devil's advocate (Revision, Recommendation 1 and New Recommendation "Gate Just Ask prototype on minimum quality bar"), devex-advocate (Revision, New Recommendation "Define 'Just Ask' quality model before output schema"), consumer-advocate (Revision, New Recommendation "Adopt deliberation quality criteria for 'Just Ask' mode"), architect (Revision, Recommendation 8, quality gate as priority 1 constraint), adoption-strategist (Revision, New Recommendation "Define-Just-Ask-quality-floor").
  - **Strength**: Unanimous
  - **Path to convergence**: This was not agreed in Phase 1. My original Recommendation 1 proposed quality criteria. Cross-reviews from the devex-advocate and consumer-advocate explicitly endorsed it. The adoption-strategist initially resisted it as a potential shipping gate but conceded in their cross-review that "some quality floor must exist before shipping" and proposed two fast-testable heuristic checks. By revision, all five agents independently included quality criteria as a P1 requirement. This is the strongest consensus finding in the entire deliberation.

- **Converged: The mini-cross-review is the right design for lightweight mode**
  - **Shared position**: The "Just Ask" lightweight mode should include a mini-cross-review — a single combined prompt where agents respond to each other's initial positions — to ensure adversarial pressure even in the fastest mode. The adoption-strategist's budget of "2 agents + 1 mini-cross-review + 1 synthesis = 4 launches" is the concrete implementation target.
  - **Agreeing agents**: Devil's advocate (Revision, Recommendation 3, Surviving), consumer-advocate (Revision, New Recommendation "Adopt deliberation quality criteria for 'Just Ask' mode" — endorses mini-cross-review if 2-agent config fails quality criteria), adoption-strategist (Revision, Recommendation 3, Modified — adopts "the devil's advocate's suggestion of a mini-cross-review"), architect (Revision, Recommendation 8, Modified — does not oppose, requires template compatibility).
  - **Strength**: Majority (four of five agents; devex-advocate does not address mini-cross-review directly but endorses quality criteria that likely require it)
  - **Path to convergence**: I proposed the mini-cross-review in my original review as a compromise between full cross-reviews (too expensive for lightweight mode) and no cross-reviews (structurally degraded output). The consumer-advocate's and adoption-strategist's cross-reviews both endorsed it. By revision, three agents explicitly adopted it and the architect required only that it produce template-compatible output. This emerged through Phase 2 cross-review, not Phase 1.

- **Converged: The full web app is out of this spec's scope; the engine must include web-compatible design constraints**
  - **Shared position**: The full-featured web app (Next.js, PostgreSQL, auth, WebSocket streaming, decision history) is removed from this spec's build order. A separate spec or conditional milestone governs its development. However, the engine API must include web-app-compatible design requirements from day one: streaming phase-lifecycle events, structured output suitable for progressive rendering, and no assumption of filesystem-only storage. These are engine constraints, not web app features.
  - **Agreeing agents**: Devil's advocate (Revision, Recommendation 7, Modified and New Recommendation "Design engine API with streaming phase-lifecycle events"), architect (Revision, Recommendation 4, Modified — "the dispatch engine must emit phase-lifecycle events"), consumer-advocate (Revision, Recommendation 1, Modified — "engine API must be designed with web-app consumption as a first-class requirement"), devex-advocate (Revision, New Recommendation "Gate web app behind adoption metric, do not cut entirely"), adoption-strategist (Revision, Recommendation 8, Modified — removes full web app, adds minimal hosted web form for consumer validation).
  - **Strength**: Unanimous
  - **Path to convergence**: In Phase 1, the consumer-advocate wanted the web app at step 4-5, the architect wanted it cut entirely from v1, I wanted it in a separate spec, and the adoption-strategist wanted it cut from the initial roadmap. By Phase 2 cross-review, all agents converged on: remove the full web app from scope, but require the engine to be designed with web consumption in mind. By revision, all five agents include engine-level web-compatibility constraints. The specific mechanism (streaming events, structured output, no filesystem assumption) emerged through the architect's and consumer-advocate's cross-reviews and was adopted by all agents in revision.

- **Converged: The SKILL.md prototype is the right first step, implemented as config-generation-plus-formatting**
  - **Shared position**: "Just Ask" ships first as a Claude Code skill within the existing SKILL.md runtime. It is implemented as a config-generation layer — auto-generates a `conversus.yml`, delegates to existing `/conversus run` orchestration, and reformats the output — rather than as new orchestration logic within SKILL.md. This preserves portability to the future Python engine.
  - **Agreeing agents**: Adoption-strategist (Revision, Recommendation 1, Modified — config-generation-plus-output-formatting), architect (Revision, Recommendation 7, Modified — "new features are built as config-generation layers on top of existing SKILL.md orchestration"), devil's advocate (Revision, Recommendation 5, Modified — "allow a time-boxed prototype of Just Ask within the existing SKILL.md runtime").
  - **Strength**: Majority (three agents explicitly agree; devex-advocate accepts the prototype as validation mechanism but focuses on SDK design; consumer-advocate does not directly address SKILL.md implementation approach)
  - **Path to convergence**: In Phase 1, the adoption-strategist proposed shipping within SKILL.md, I argued for resolving the extraction question first, and the architect argued for Python extraction as step 1. Cross-reviews produced the compromise: prototype in SKILL.md (adoption-strategist's speed), but as config-generation only (architect's portability), with extraction committed as the target (my architectural concern). This is a genuine three-way convergence that emerged through deliberation, not initial agreement.

- **Converged: Engine extraction is decomposed into 5 independently testable sub-phases**
  - **Shared position**: Engine extraction is broken into 5 sub-phases: config parser, template engine, async dispatch, dispute parsing, and output manager. Each sub-phase has distinct inputs and outputs and can be tested independently. Treating extraction as a single build phase is a planning failure.
  - **Agreeing agents**: Architect (Revision, Recommendation 2, Surviving — zero challenges across all cross-reviews), devil's advocate (cross-review endorsement), devex-advocate (Revision, Safe Agreements — complementary decomposition from API perspective), consumer-advocate (cross-review endorsement), adoption-strategist (cross-review endorsement).
  - **Strength**: Unanimous
  - **Path to convergence**: This was agreed from Phase 1. The architect proposed it, and every cross-review independently confirmed it without challenge. It is the only recommendation in the entire deliberation that received zero objections.

### Final Position Statement

**Non-Negotiables** (3 items):

1. **The spec must include a side-by-side differentiation example proving that "Just Ask" output differs structurally from a single-model response.** This is the cheapest possible validation of the assumption on which every other recommendation depends. Without it, the deliberation has produced a detailed plan for a product whose core value proposition has never been tested. (Revision, Recommendation 9; proposal, "Just Ask" mode description — claims the system "returns a plain-English synthesis with the recommendation, supporting arguments, and dissenting views" but never demonstrates that this output is different from what a single model produces.)

2. **The quality floor must be a pre-ship gate, not a post-ship iteration target.** Two binary quality checks — substantive disagreement present, agent attributions present — must pass before the prototype ships to any users. The checks are testable in 30 minutes. The cost of gating is trivial. The cost of shipping without gating is a poisoned first impression that no iteration can recover from. (Revision, New Recommendation "Gate Just Ask prototype on minimum quality bar"; adoption-strategist Revision, New Recommendation "Define-Just-Ask-quality-floor" — the strategist conceded the irreversibility of first-impression damage.)

3. **Python extraction must be committed as the target architecture in this spec, not deferred to Phase 0 re-evaluation.** Spec 007's plugin system is Python-only. Lifecycle hooks, `DeliberationState`, and feature extraction are Python constructs. The directional question is already answered. Leaving it as an open question creates ambiguity that slows every dependent design decision. The SKILL.md prototype validates the product concept; it does not re-open the architecture question. (Revision, Recommendation 5; architect Revision, Recommendation 7 — the architect's own evidence about spec 007 compatibility supports this commitment.)

**Flexibility** (3 items):

1. **The specific quality checks can be refined.** I proposed "substantive disagreement present" and "agent attributions present" as the two gate checks. If the synthesis identifies better or additional binary checks that are equally fast to test, I am flexible on the specific checks. What must be preserved: the checks are binary (pass/fail), fast (testable in under an hour), and gating (shipping is blocked if they fail).

2. **The timing of MCP tool contract specification can follow the two-level approach.** I modified my position to accept directional contracts now and full schemas when MCP implementation begins. I am flexible on exactly how much detail the directional contracts contain, as long as they specify blocking vs. streaming execution and rough input/output shapes. What must be preserved: MCP tool contracts are designed before implementation, not discovered during it.

3. **The format of the side-by-side differentiation example is open.** I proposed a worked example in the spec document itself. It could alternatively be a companion artifact (a test case, a validation script, a documented experiment). What must be preserved: the example exists as a reviewable artifact before engineering work begins, and it compares the same question answered by both approaches with structural annotations showing where the outputs diverge.
