# Cross-Review of Architect's Review — by Devil's Advocate

---

### Dangerous Contradictions

- **Engine extraction scope: monolithic phase vs. blocking architectural question**
  - **architect claims**: Engine extraction should be decomposed into 5 sub-phases (config parser, template engine, async dispatch, dispute parsing, output manager) and should target spec 007's `DeliberationState` interfaces defined in a new "Phase 0" (Actionable Recommendations #1 and #2). The architect treats extraction as a well-scoped engineering task with a clear decomposition.
  - **devils-advocate claims**: Open question 1 (L131) — whether to extract to Python at all or keep SKILL.md with adapters — is "not an open question" but "a blocking architectural decision that determines the shape of everything downstream" (Actionable Recommendation #5). The build order is "not a plan — it is a wish list" until this question is resolved.
  - **Why this is dangerous**: The architect's review provides a detailed decomposition of an approach (Python extraction) that the devil's advocate argues has not yet been validated as the correct approach. If the synthesis adopts the architect's 5-sub-phase decomposition and Phase 0 interface work, it commits substantial design effort to Python extraction before resolving whether that path is viable. But if the synthesis adopts the devil's advocate's position that this is a blocking decision requiring formal evaluation of both approaches, the architect's detailed decomposition becomes premature. Implementing both — the decomposition and the decision process — wastes effort if the decision goes toward the adapter approach.
  - **Suggested resolution**: The architect should yield on sequencing. The blocking decision (Python extraction vs. SKILL.md adapters) must be resolved first. However, the architect's decomposition and Phase 0 interface definition are valuable regardless of outcome — if the adapter approach wins, those same interfaces define the adapter contract. Reframe the architect's recommendations as "conditional on Python extraction being chosen" and use the devil's advocate's insistence on a formal decision as the gating mechanism.

- **LiteLLM assessment: solvable engineering vs. fundamental capability gap**
  - **architect claims**: LiteLLM's limitation is primarily about tool-use normalization — it "does not normalize tool use, structured output, or long-context handling" (Off-Base Assumptions, third item). The fix is a thin `ConversusAgent` abstraction on top of LiteLLM that handles tool registration and output validation (Actionable Recommendation #5).
  - **devils-advocate claims**: The problem is deeper than API normalization. Different models have "wildly different capabilities for the kind of structured argumentation conversus requires" (Off-Base Assumptions, first item). A Llama-7B cannot produce the same quality cross-review as Claude Opus. The spec needs "a capability matrix or minimum model requirements per mode/tier, and a graceful degradation strategy" (Actionable Recommendation #2).
  - **Why this is dangerous**: The architect's fix (a `ConversusAgent` wrapper) solves the API surface problem but not the capability problem. If the synthesis adopts the architect's abstraction layer without the devil's advocate's capability matrix, conversus will successfully route API calls to weak models and produce garbage output that technically conforms to the tool contract but is semantically empty. The system will "work" in a way that destroys trust. Conversely, if only the capability matrix is adopted without the abstraction layer, the system will correctly reject weak models but fail on API incompatibilities with strong ones.
  - **Suggested resolution**: Both positions are needed and non-overlapping. The architect's `ConversusAgent` abstraction handles the how (API normalization), while the devil's advocate's capability matrix handles the whether (model qualification). The synthesis should adopt both: a `ConversusAgent` wrapper for provider normalization, and a capability validation gate that runs before dispatching agents to check that the selected model meets minimum requirements for the requested mode. Neither reviewer should yield — these are complementary, not competing.

- **"Just Ask" output format: structured subset vs. quality-defined**
  - **architect claims**: "Just Ask" output should produce "a subset of the standard conversus output: at minimum, a synthesis file following the same mode-specific template structure" so that it can participate in the conversus ecosystem — feeding into `prior:` context and being parseable by the dispute parsing subsystem (Actionable Recommendation #8).
  - **devils-advocate claims**: The problem with "Just Ask" is not output format but output quality. The spec must "define how to tell if it worked" with criteria like "the synthesis must contain at least one substantive disagreement that was resolved through evidence" (Missed Opportunities, first item). A 2-agent, 1-round deliberation is "structurally identical to asking two models the same question and having a third summarize" (Off-Base Assumptions, second item).
  - **Why this is dangerous**: These pull in genuinely different directions. The architect's position optimizes for ecosystem composability — "Just Ask" output flows into deeper workflows. The devil's advocate's position optimizes for standalone value — "Just Ask" output must be provably better than a single-model response. If the synthesis prioritizes structured format (architect) but the content does not meet quality criteria (devil's advocate), you get a well-formatted document that is no better than ChatGPT output but now takes 3x longer. If the synthesis prioritizes quality criteria but allows freeform output, the result cannot feed into `prior:` or arbitration workflows.
  - **Suggested resolution**: The architect should yield partially. Quality criteria (devil's advocate) are the primary constraint — there is no point in producing composable output if the output is not worth composing with. But the output format (architect) should be adopted as a secondary constraint: once quality criteria are met, the output should use the standard template structure so it remains ecosystem-compatible. The synthesis should frame this as: quality is the acceptance criterion, format is the implementation constraint.

### Tensions

- **Build order philosophy: interface-first (top-down) vs. decision-first (resolve unknowns)**
  - **architect's position**: Invert the build order so spec 007's plugin interfaces are defined first ("Phase 0: Interface Definition"), then extract the engine targeting those interfaces. The plugin system becomes "expose what already exists" (Actionable Recommendations #1, Executive Summary).
  - **devils-advocate's position**: The build order is secondary to resolving the open questions. "Every subsequent build step depends on this decision. Leaving it open means the build order is not a plan" (Actionable Recommendation #5). The open questions (L129-138) are "more dangerous than they appear — several of them, if answered differently than the proposal implicitly assumes, would invalidate entire sections of the architecture" (Executive Summary).
  - **Nature of tension**: The architect wants to restructure the plan around a technical insight (interfaces-first enables clean plugin integration). The devil's advocate wants to restructure the plan around risk reduction (resolve unknowns before committing to any build order). These are not contradictory — you could do both — but they compete for what gets prioritized when resources are finite. If the team spends its first sprint defining `DeliberationState` interfaces, it has not yet resolved whether Python extraction is the right path. If the team spends its first sprint evaluating extraction approaches, it has not yet defined the interfaces that would make extraction clean.
  - **Coordination needed**: Define a time-boxed "Phase 0" that does both: evaluate the extraction vs. adapter decision using the spec 007 interfaces as the evaluation framework. If the interfaces can be cleanly targeted by both approaches, the decision is less consequential. If one approach cannot target the interfaces, that is evidence for the other. This turns the tension into a combined activity.

- **Web app: defer to v2 vs. separate spec**
  - **architect's position**: "Move the web app out of the v1 scope entirely" and replace with "v1 ships CLI + MCP server + Python SDK. Web app is a separate proposal" (Actionable Recommendation #4).
  - **devils-advocate's position**: "Remove the web app from this spec's build order. Create a separate spec (012 or later) for the web app after the core engine, CLI, and MCP server are stable" (Actionable Recommendation #7).
  - **Nature of tension**: Both agree the web app should be removed from this spec. The difference is subtle but consequential: the architect frames it as a scope decision (not in v1), while the devil's advocate frames it as a specification decision (needs its own spec). The architect's framing leaves the web app as an acknowledged future item with no design commitment. The devil's advocate's framing requires that the web app receive the same rigorous specification treatment as the core engine, which has implications for how the core engine's interfaces are designed — they need to be web-app-ready even if the web app is deferred.
  - **Coordination needed**: Adopt the devil's advocate's framing (separate spec) but with the architect's timeline (after v1 ships). This means the current spec should identify the interface requirements that a future web app would need (streaming state, session persistence, auth hooks) without designing the web app itself. These requirements become constraints on the engine's API surface.

- **Spec 007 integration timing: foundational vs. final**
  - **architect's position**: Spec 007's `DeliberationState` model and lifecycle hooks are "architecturally foundational" and should be defined before engine extraction. "The plugin system becomes 'expose what already exists' rather than a separate integration project" (Missed Opportunities, second item; Actionable Recommendation #1).
  - **devils-advocate's position**: Does not directly address spec 007 timing but raises the related concern that the proposal "proceeds as if [the open questions] have already been answered" (Alignment, second item) and that the build order "contains hidden parallelism assumptions and scope risks that are not acknowledged" (Executive Summary).
  - **Nature of tension**: The architect sees spec 007 as a source of proven interfaces that reduce risk if adopted early. The devil's advocate sees the build order's implicit assumptions as a source of risk that increases if the plan becomes more elaborate before unknowns are resolved. Moving spec 007 interfaces earlier (architect) makes the plan more technically sound but also more committed to a specific architecture before the open questions are resolved (devil's advocate concern). If the open questions reveal that, say, the adapter approach is better than Python extraction, the spec 007 interfaces designed for a Python engine may not apply cleanly.
  - **Coordination needed**: The architect should demonstrate that spec 007's interfaces are approach-agnostic — that `DeliberationState` and the lifecycle hooks are valid contracts regardless of whether the implementation is Python extraction or SKILL.md adapters. If this can be shown, early interface definition reduces risk rather than increasing it, and the devil's advocate's concern is satisfied.

- **Scope of "model agnosticism" ambition**
  - **architect's position**: Model agnosticism is achievable with the right abstractions. The `ConversusAgent` wrapper on top of LiteLLM, combined with per-phase model configuration (`models: { default: claude-sonnet-4-6, synthesis: claude-opus-4, cross-review: gpt-4o-mini }`), makes the system genuinely multi-provider (Actionable Recommendations #5 and #10).
  - **devils-advocate's position**: Model agnosticism is "not 'use any model' — it is 'use any model that meets minimum capability thresholds for the requested mode'" (Off-Base Assumptions, first item). The spec should define these thresholds and "warn or block when the selected model is unlikely to produce valid deliberation output" (Actionable Recommendation #2).
  - **Nature of tension**: The architect's per-phase model tiering actually increases the capability problem the devil's advocate identifies. If the system supports mixing providers within a single deliberation (`gpt-4o-mini` for cross-reviews, `claude-opus-4` for synthesis), the capability matrix becomes a per-phase validation problem, not just a per-deliberation one. The cheap model used for cross-reviews might not meet the minimum threshold for producing structurally valid cross-review output, even if the expensive model used for synthesis is excellent.
  - **Coordination needed**: Model tiering (architect) must be constrained by the capability matrix (devil's advocate). The per-phase model configuration should validate each model against the requirements of its assigned phase, not just check that a model is "supported by LiteLLM." This means the capability matrix must be granular enough to specify per-phase requirements, which is a design task that should be part of the architect's proposed Phase 0.

### Safe Agreements

- **Web app must be removed from the v1 scope of this spec**
  - **Shared position**: Both reviews independently conclude that the web app does not belong in this spec's build order. The architect states it "dwarfs the core engine work" and recommends "v1 ships CLI + MCP server + Python SDK" (Executive Summary; Actionable Recommendation #4). The devil's advocate states it is "the highest-complexity, lowest-certainty item in the proposal" and recommends creating "a separate spec (012 or later)" (Actionable Recommendation #7).
  - **Combined evidence**: The architect provides a concrete inventory of what the web app adds: "Next.js frontend, FastAPI backend, WebSocket streaming, PostgreSQL, authentication, session management, deployment infrastructure, and a real-time deliberation viewer" — six technology layers orthogonal to the core engine. The devil's advocate adds a risk dimension: "The web app scope creep delays delivery of the CLI, SDK, and MCP server — the distribution formats that serve the users most likely to adopt conversus first." Together, these establish both the technical case (too much scope) and the strategic case (wrong sequencing for adoption).
  - **Confidence level**: High. Both reviewers reach this conclusion from different analytical frameworks (architectural complexity vs. adoption risk) and arrive at the same recommendation. This convergence strongly suggests the synthesis should defer the web app.

- **Parallel dispatch outside Claude Code is a substantial unsolved engineering problem**
  - **Shared position**: Both reviews flag the proposal's claim that "parallel agent dispatch (already built)" (L111) as misleading. The architect identifies this as an "Off-Base Assumption," noting that "parallel dispatch is built for Claude Code's Agent tool" and lists five specific capabilities (concurrent API calls, context isolation, output collection, partial failure handling, phase barriers) that must be built from scratch (Off-Base Assumptions, first item). The devil's advocate raises the same concern through the lens of failure modes: "What happens when one agent in a parallel dispatch fails?" and notes the proposal "does not discuss how these invariants survive extraction to a Python engine" (Missed Opportunities, fourth item; Actionable Recommendation #6).
  - **Combined evidence**: The architect's analysis is implementation-focused — what must be built (asyncio task manager, phase barriers, error isolation). The devil's advocate's analysis is failure-focused — what can go wrong (partial failures, provider rate limits, malformed output, mid-deliberation outages). Together, they define both the positive requirements (what the dispatch engine must do) and the negative requirements (what failure modes it must handle). The architect's Recommendation #3 provides a concrete design direction (asyncio.TaskGroup, PhaseBarrier abstraction) while the devil's advocate's Recommendation #6 provides the failure mode taxonomy that the design must address.
  - **Confidence level**: High. This is the most technically grounded agreement across both reviews, with complementary evidence from implementation and failure-mode perspectives.

- **The engine extraction question must be resolved before meaningful progress can occur**
  - **Shared position**: Both reviews identify open question 1 (L131) — Python extraction vs. SKILL.md adapters — as a decision that cannot remain open. The architect states: "Commit to a clear answer: the Python engine is the canonical implementation. SKILL.md becomes a thin adapter... or SKILL.md is frozen as a legacy distribution format. Do not maintain two independent implementations" (Actionable Recommendation #7). The devil's advocate states: "This is not an open question — it is a blocking architectural decision that determines the shape of everything downstream" (Actionable Recommendation #5).
  - **Combined evidence**: The architect provides the technical argument: maintaining two implementations means "feature drift... produces two subtly different deliberation behaviors, making bug reports unresolvable." The devil's advocate provides the planning argument: "Every subsequent build step (CLI, MCP server, SDK, web app) depends on this decision. Leaving it open means the build order is not a plan." The architect also notes that spec 007's plugin system "is designed for the Python engine; it cannot run in SKILL.md," adding a compatibility constraint that tips the decision toward Python extraction.
  - **Confidence level**: High. Both reviewers agree this is blocking and both provide distinct reasons why. The architect's evidence about spec 007 compatibility adds a constraint the devil's advocate did not raise, strengthening the combined case.
