# Cross-Review of devex-advocate's Review

**Cross-reviewer:** devils-advocate
**Review under examination:** devex-advocate's review of spec 011 (Adoption Harness)
**Date:** 2026-03-21

---

### Dangerous Contradictions

- **Build order priority: MCP server vs. quality foundations**
  - **devex-advocate claims**: The MCP server should be moved from build step 5 to build step 3, shipping "alongside or immediately after the CLI" because it "reaches the largest developer audience" and is "a thin wrapper, not a large engineering effort" (Actionable Recommendations, item 3).
  - **devils-advocate claims**: The proposal's build order contains "hidden parallelism assumptions and scope risks that are not acknowledged" (Executive Summary), and the spec must first "define what 'good enough' deliberation quality means for 'just ask' mode" before building any distribution surface (Executive Summary, Actionable Recommendations item 1). Additionally, MCP tool contracts require significant design work that the proposal has not done (Actionable Recommendations item 10).
  - **Why this is dangerous**: If the MCP server ships at step 3 as devex-advocate recommends, it ships before "just ask" mode (step 4 in the original order), before quality criteria are defined, and before failure modes for multi-provider execution are analyzed. The MCP server would expose `conversus_decide` — the "just ask" tool — before anyone has defined what a good output looks like or what happens when an agent fails mid-deliberation. Early adopters of the MCP server would hit undesigned failure modes and undefined quality bars, forming a negative first impression that is extremely difficult to reverse in developer communities.
  - **Suggested resolution**: Both positions have merit. The resolution is to define the MCP tool contracts and quality criteria (as both reviews independently recommend) first, then ship the MCP server early — but with only the fully-designed tools initially. Ship `conversus_run` (the power-user tool with known behavior) as the first MCP tool at step 3, and add `conversus_decide` only after quality criteria and failure modes are specified. This satisfies devex-advocate's urgency on MCP availability while respecting the quality concerns.

- **Structured output as default vs. quality verification gap**
  - **devex-advocate claims**: "All SDK methods and MCP tools should return structured data by default" with fields including `confidence` (float 0-1), `arguments_for`, `arguments_against`, and `dissent` (Actionable Recommendations, item 2). Plain-English should be "a rendering of this structure, not the primary output."
  - **devils-advocate claims**: There is "no quality metric for 'just ask' mode" (Missed Opportunities, item 1), and the proposal never defines "how to tell if it worked" or what distinguishes a good deliberation from "asking ChatGPT the same question." A 2-agent, 1-round deliberation is "structurally identical to asking two models the same question and having a third summarize" (Off-Base Assumptions, item 2).
  - **Why this is dangerous**: Structured output with a `confidence` float creates an illusion of rigor. If a 2-agent, 1-round deliberation without cross-reviews produces a `confidence: 0.82` value, what does that number mean? It is not calibrated against any quality model. Developers building on the SDK will treat structured fields as reliable signals — branching CI pipelines on `confidence > 0.7`, filtering recommendations by `dissent` length — when the underlying deliberation may not have produced genuinely adversarial pressure. The structured format makes low-quality output look authoritative instead of obviously shallow.
  - **Suggested resolution**: Devex-advocate is right that structured output is necessary for programmatic consumption. But the structure must include a `deliberation_depth` or `quality_indicators` field that honestly reports what phases were run (e.g., "reviews only, no cross-reviews"), how many agents participated, and whether genuine disagreement surfaced. The `confidence` field should either be removed or accompanied by a clear caveat that it reflects the synthesis model's self-assessment, not a calibrated probability. Define the quality model (my recommendation) before defining the output schema (devex-advocate's recommendation) so that the schema reflects reality rather than aspirations.

- **SDK-first design vs. unresolved engine extraction**
  - **devex-advocate claims**: "Define the Python SDK's public API surface (classes, methods, types, async support) before any implementation begins" because "it is the contract that CLI, MCP server, and web app all depend on" (Executive Summary, Actionable Recommendations item 1). Proposes specific classes: `Problem`, `Interests`, `Config`, `Deliberation`, `Result`.
  - **devils-advocate claims**: Open question 1 ("Should the engine be extracted to Python or kept as a SKILL.md with adapters?") is "not an open question — it is a blocking architectural decision that determines the shape of everything downstream" and must be resolved before proceeding (Actionable Recommendations, item 5).
  - **Why this is dangerous**: Devex-advocate's recommendation to design the SDK API first implicitly assumes the answer to open question 1 is "extract to Python." If the decision goes the other way — keep SKILL.md with adapters — then the SDK classes devex-advocate proposes (dataclass pipeline, asyncio-native, builder pattern) would be wrappers around a fundamentally different execution model (Agent tool dispatch in Claude Code). The API surface would be a lie: `Deliberation.run_async()` would not actually use asyncio, it would shell out to an agent runtime. Designing the SDK before resolving the extraction question means either the API constrains the architectural decision (putting the cart before the horse) or the API gets redesigned after the decision is made (wasted work that devex-advocate is explicitly trying to avoid).
  - **Suggested resolution**: Resolve the engine extraction question first (my position), then immediately design the SDK API (devex-advocate's position). These are sequential, not competing. The disagreement is about ordering, and the correct order is: architectural decision, then API design. Devex-advocate should yield on timing but is correct that the SDK API must be designed before implementation begins.

### Tensions

- **Completeness of specification vs. speed of delivery**
  - **devex-advocate's position**: Recommends 10 specific additions to the proposal — SDK API, structured output, MCP schemas, CI/CD mode, dry-run, preset API, provider interface, config builder, plugin model — each with detailed specifications (Actionable Recommendations, items 1-10).
  - **devils-advocate's position**: Recommends separating the web app into its own spec (Actionable Recommendations, item 7), resolving blocking architectural questions before proceeding (Actionable Recommendations, item 5), and defining quality criteria before building (Actionable Recommendations, item 1).
  - **Nature of tension**: Devex-advocate wants to add more design to this spec to make it implementation-ready. I want to subtract scope from this spec and resolve foundational questions first. Both impulses are valid — underspecified APIs and unresolved architectural questions are both real problems. But if all 10 of devex-advocate's additions are incorporated alongside my recommendations, this proposal balloons from 147 lines to potentially 500+ lines and tries to be simultaneously a vision document, an API specification, an architecture decision record, and a quality framework. That is four documents wearing one spec's clothing.
  - **Coordination needed**: Agree on what this spec is. If it is a proposal (as titled), it should resolve the blocking questions and defer detailed API design to child specs. If it is a technical design, it should incorporate devex-advocate's API specifications but scope down to the engine + SDK + CLI, deferring MCP/web/plugins. The two reviews are both correct but assume different document purposes.

- **Model agnosticism as opportunity vs. model agnosticism as risk**
  - **devex-advocate's position**: Model agnosticism is "essential for developer adoption" and the LiteLLM concern should be resolved by committing to "a thin provider interface with LiteLLM as the default implementation" (Alignment item 4, Actionable Recommendations item 8). Frames the concern around MCP maturity as "overstated" (Off-Base Assumptions, item 2).
  - **devils-advocate's position**: The proposal "treats model agnosticism as a routing problem" when it is actually a capability problem — "a Llama-7B agent cannot produce the same quality adversarial cross-review as Claude Opus" (Off-Base Assumptions, item 1). Recommends a capability matrix and minimum model requirements per mode (Actionable Recommendations, item 2).
  - **Nature of tension**: Devex-advocate sees model agnosticism primarily through the lens of developer freedom and vendor lock-in avoidance. I see it primarily through the lens of output quality degradation. These are not contradictory — both are real concerns — but they pull the design in different directions. Devex-advocate's thin provider interface makes it easy to plug in any model. My capability matrix makes it hard to use the wrong model. The developer who plugs in Llama-7B through the clean provider interface and gets garbage output experiences the tension between these two positions directly.
  - **Coordination needed**: The provider interface (devex-advocate's recommendation) should include the capability validation layer (my recommendation) as a built-in component, not an afterthought. When `ModelProvider.complete()` is called, the provider should first check whether the model meets the minimum capability threshold for the requested deliberation mode. This means the capability matrix must be designed alongside the provider interface, not separately.

- **MCP tool granularity: developer convenience vs. contract complexity**
  - **devex-advocate's position**: Recommends adding more MCP tools beyond the six listed — `conversus_presets_list`, `conversus_presets_search` — and specifying full input/output schemas for each (Actionable Recommendations, items 5 and 7).
  - **devils-advocate's position**: Notes that "the current SKILL.md is invoked via a single entry point (`/conversus run`); six separate tools need six separate contracts" and each tool needs its own error contract, execution model, and timeout behavior (Actionable Recommendations, item 10).
  - **Nature of tension**: More MCP tools provide finer-grained developer control (devex-advocate's goal) but multiply the contract surface that must be specified, tested, versioned, and maintained (my concern about underspecification). Adding preset management tools on top of the six already-listed tools pushes toward 8-10 MCP tools, each needing schemas, error contracts, and streaming semantics. The proposal already has zero of this design work done for the existing six tools.
  - **Coordination needed**: Start with fewer, well-specified tools rather than more underspecified ones. Ship `conversus_run` and `conversus_decide` with full contracts first. Add `conversus_define`, `conversus_interests`, `conversus_mode`, and `conversus_converge` as the guided workflow matures. Defer preset management tools until the preset API itself is designed. Quality of contracts over quantity of tools.

- **Preset system: programmatic API vs. quality governance**
  - **devex-advocate's position**: Recommends exposing the preset system programmatically with `conversus.presets.list()`, `get()`, `compose()`, and `install()` methods, and calls the preset composition system "one of conversus's most differentiating features" (Actionable Recommendations, item 7).
  - **devils-advocate's position**: Warns that scaling to a community registry "without defining quality gates, versioning, or deprecation policies creates a npm-left-pad risk for deliberation quality" (Missed Opportunities, item 6).
  - **Nature of tension**: Devex-advocate wants to make presets maximally accessible and composable. I want to ensure that accessibility does not compromise quality. A `presets.install(source)` method that can pull from an unvetted community registry, combined with `presets.compose()` that mixes arbitrary presets, could produce agent configurations that violate the structural requirements of the template system. The existing preset validation (SKILL.md L93-169) was designed for a curated, filesystem-local set — not a package manager.
  - **Coordination needed**: The programmatic API should enforce the same validation constraints that the SKILL.md preset system enforces (name matching, category matching, composability flags). The `install()` method should validate against these constraints on install, not just on use. Define the quality governance model before building the distribution mechanism.

### Safe Agreements

- **Existing power-user workflows must be preserved**
  - **Shared position**: Both reviews agree that the proposal correctly preserves `/conversus run` for hand-crafted YAML and that backward compatibility is a non-negotiable constraint. Devex-advocate cites this as an alignment point: "existing power-user workflows are not broken" (Alignment, item 3). My review lists the constraint "Must not break existing `/conversus run` behavior" as "well-chosen and mutually reinforcing" (Alignment, item 3).
  - **Combined evidence**: Devex-advocate grounds this in the decision framework's backward compatibility constraint (spec 999, L439-446). My review grounds it in the proposal's own constraint list (L140-146) and notes that these constraints, if enforced, would catch many identified problems. Both perspectives converge: the power-user path is the proven path, and any adoption-expanding changes must be additive.
  - **Confidence level**: High. This is a load-bearing constraint that both reviews independently validate from different angles (developer workflow continuity vs. architectural integrity).

- **MCP tool contracts are dangerously underspecified**
  - **Shared position**: Both reviews identify the six MCP tool listings (L79-86) as critically underspecified. Devex-advocate calls out "no input schemas, error codes, or failure semantics" (Missed Opportunities, item 4) and recommends full schema definitions (Actionable Recommendations, item 5). My review identifies the same gap: "Six MCP tools are listed with one-line descriptions" and each needs "input schema, output schema, error contract, and execution model" (Actionable Recommendations, item 10).
  - **Combined evidence**: Devex-advocate approaches this from the developer experience angle — MCP clients need schemas to render tool descriptions and validate inputs. My review approaches it from the failure mode angle — without error contracts, integration breakage is unpredictable and debugging requires understanding both conversus internals and provider-specific failure modes. Together, the evidence is stronger: underspecified MCP tools fail on both the happy path (bad developer experience) and the sad path (unpredictable errors).
  - **Confidence level**: High. Both reviews independently flag this as a significant gap, cite the same proposal lines, and recommend essentially the same fix. This should be treated as a consensus finding.

- **The web app should not be in this spec's critical path**
  - **Shared position**: Devex-advocate's build order recommendation (Actionable Recommendations, item 3) prioritizes CLI and MCP server over the web app, consistent with the proposal's existing sequencing. My review explicitly recommends separating the web app into its own spec: "Remove the web app from this spec's build order. Create a separate spec (012 or later)" (Actionable Recommendations, item 7). Both reviews treat the web app as lower priority than the developer-facing distribution formats.
  - **Combined evidence**: Devex-advocate argues from adoption patterns: "CLI and SDK adoption always precedes web app usage for developer tools" (Alignment, item 5). My review argues from scope management: the web app "introduces authentication, hosting, state management, real-time streaming, and database design — each of which is a significant design surface that is not addressed here" (Actionable Recommendations, item 7). The proposal's own architect agent (conversus.yml L57-77) independently validates both positions. Together: the web app is both lower-priority for the target audience and higher-risk for the project scope.
  - **Confidence level**: High. Both reviews converge on this from independent reasoning chains, and the proposal's own deliberation agents flagged the same concern. This is the strongest consensus finding across the two reviews.

- **The "just ask" mode requires significantly more design work**
  - **Shared position**: Both reviews identify "just ask" mode as critically underspecified despite being the proposal's headline feature. Devex-advocate flags missing structured output (Missed Opportunities, item 2), missing CI/CD non-interactive design (Missed Opportunities, item 3), and the need for the SDK to define how auto-configuration works programmatically (Actionable Recommendations, items 1-2). My review flags missing quality criteria (Missed Opportunities, item 1), the risk that 2-agent 1-round deliberation is "structurally identical to asking two models the same question" (Off-Base Assumptions, item 2), undefined agent auto-generation (Actionable Recommendations, item 8), and the "just another ChatGPT wrapper" risk (Actionable Recommendations, item 9).
  - **Combined evidence**: Devex-advocate identifies what the output interface should look like (structured data, typed fields, machine-readable). My review identifies what the quality guarantees should be (substantive disagreement, evidence grounding, trade-off acknowledgment). Together, these form a complete picture: "just ask" mode needs both a well-designed output interface AND a quality model that ensures the output is worth structuring. Neither alone is sufficient.
  - **Confidence level**: High. The two reviews attack the same gap from complementary angles (interface design vs. quality assurance), and together they demonstrate that "just ask" is the proposal's highest-risk feature — it is the most important for adoption and the least specified for implementation.
