# Cross-Review of adoption-strategist's Review — by devils-advocate

---

### Dangerous Contradictions

- **Build order priority: "Ship the skill now" vs. "Resolve the engine question first"**
  - **adoption-strategist claims**: "Ship 'Just Ask' as a Claude Code skill first" (Actionable Recommendations #1). Move "Just Ask" to step 1, implement it within the existing SKILL.md runtime, auto-generate a `conversus.yml`, and run `/conversus run`. "No Python extraction needed." The existing runtime "already supports everything needed."
  - **devils-advocate claims**: "Resolve the engine extraction question before proceeding" (Actionable Recommendations #5). Open question 1 is "not an open question — it is a blocking architectural decision that determines the shape of everything downstream." The proposal should "either commit to Python extraction with a concrete migration plan... or commit to the adapter approach with a concrete interface definition."
  - **Why this is dangerous**: adoption-strategist's recommendation implicitly answers the engine extraction question — keep SKILL.md, skip Python — but frames it as a temporary shortcut rather than an architectural decision. If the team ships "Just Ask" within SKILL.md as step 1, then later extracts to Python as step 2, the "Just Ask" implementation must be rebuilt entirely. The Claude Code skill version would use Agent tool dispatch, filesystem-relative templates, and SKILL.md's orchestration logic; the Python version would use asyncio, LiteLLM, and a different template resolution mechanism. Two implementations of the same feature, one throwaway. Alternatively, if the team treats adoption-strategist's recommendation as the permanent architecture (no Python extraction), my recommendation to resolve the engine question becomes moot — but then distribution formats 2-5 (CLI, MCP, web app, SDK) all require adapters whose design is unspecified.
  - **Suggested resolution**: Both positions have merit but need sequencing clarity. adoption-strategist is correct that waiting for Python extraction before any user validation is wasteful. I am correct that the engine extraction decision shapes everything downstream. The resolution is to explicitly frame the Claude Code skill version of "Just Ask" as a prototype with a defined sunset: ship it within SKILL.md, validate with real users, but commit to a concrete extraction path before building the second distribution format. The prototype informs the extraction decision rather than deferring it indefinitely.

- **MCP positioning: "Not the primary path" vs. "Define the MCP tool contract precisely"**
  - **adoption-strategist claims**: MCP should not be the "primary" integration path (Off-Base Assumptions, first item). "The primary path for the first 100 users should be the channel with the lowest friction — which is the existing Claude Code skill." MCP is premature because "the majority of developers using AI coding tools are not yet on MCP-compatible setups."
  - **devils-advocate claims**: "Define the MCP tool contract more precisely" (Actionable Recommendations #10). The six MCP tools need input schemas, output schemas, error contracts, and execution model definitions. MCP tool contracts are "the API surface that third-party integrations depend on."
  - **Why this is dangerous**: adoption-strategist deprioritizes MCP and pushes it behind Claude Code skill validation; I call for precise MCP contract specification. If both are adopted, the team delays MCP implementation (adoption-strategist) but also invests in detailed MCP contract specification (devils-advocate) — specifying contracts for tools that will not be built for months. Conversely, if MCP contracts are not specified early, adoption-strategist's later recommendation to "reorder build sequence: MCP before CLI" (Recommendation #4) produces an MCP server built without contract discipline, leading to the integration breakage I warn about.
  - **Suggested resolution**: adoption-strategist should yield on calling MCP "not primary" — MCP is the right long-term primary path for developer adoption, and early contract specification is cheap insurance. I should yield on the timing: MCP contracts do not need full specification until the team begins MCP implementation. The compromise is to define MCP contracts at a directional level (blocking vs. streaming, rough input/output shapes) now, and specify them precisely when MCP moves to the top of the build queue after Claude Code skill validation.

- **Web app: "Cut it entirely" vs. "Separate it into its own spec"**
  - **adoption-strategist claims**: "Cut the web app from the initial roadmap" (Actionable Recommendations #8). "Remove the web app from this proposal entirely." It is "the classic 'build the product before finding the market' mistake."
  - **devils-advocate claims**: "Separate the web app into its own spec" (Actionable Recommendations #7). "Remove the web app from this spec's build order. Create a separate spec (012 or later) for the web app after the core engine, CLI, and MCP server are stable."
  - **Why this is dangerous**: These sound similar but diverge on intent. adoption-strategist frames the web app as potentially unnecessary — "revisit a web app as a separate spec" only "if adoption via Claude Code skill, MCP, and CLI validates demand from non-technical users." I frame the web app as likely necessary but premature — it should be its own spec because it introduces authentication, hosting, state management, real-time streaming, and database design that deserve dedicated design attention. If the synthesis adopts adoption-strategist's framing, the web app is treated as speculative and may never receive serious design investment. If it adopts mine, the web app is treated as deferred-but-planned and receives eventual spec attention. The failure mode is that neither framing produces a clear decision criterion for when to build the web app.
  - **Suggested resolution**: Adopt adoption-strategist's gating mechanism (validate demand first) combined with my architectural concern (the web app needs its own spec when the time comes). Concretely: define a quantitative adoption gate (e.g., "100+ users across CLI/MCP requesting web access") that triggers a dedicated web app spec. This prevents premature investment while ensuring the web app gets proper design attention if demand materializes.

### Tensions

- **Speed of first ship vs. quality of first impression**
  - **adoption-strategist's position**: Ship "Just Ask" in two weeks within the existing Claude Code runtime (Recommendations #1). Validate with 100 real decisions. Speed to market is the priority: "This gets a usable product in front of real users in days, not months."
  - **devils-advocate's position**: Before shipping "Just Ask," define deliberation quality criteria (Recommendations #1), design the cross-review bypass for lightweight mode (Recommendations #3), and define what "auto-generates 2-4 appropriate agents" means concretely (Recommendations #8). Ship only when the output is demonstrably better than asking a single LLM.
  - **Nature of tension**: adoption-strategist optimizes for learning velocity — ship fast, measure, iterate. I optimize for first-impression quality — if early users see shallow output indistinguishable from ChatGPT, they will not return, and the learning from "100 real decisions" will be "users tried it once and left." These are not contradictory goals but they pull in opposite directions on timeline. Every quality gate I add delays adoption-strategist's two-week target.
  - **Coordination needed**: Define a minimal quality bar that can be validated before shipping but does not require months of design work. My recommendation #1 (quality criteria) is the non-negotiable minimum — it can be defined in days, not weeks. My recommendations #3 (cross-review bypass design) and #8 (agent generation algorithm) can be deferred to iteration if the quality criteria provide a way to detect when output is inadequate. adoption-strategist's two-week target becomes a three-week target with a quality bar, which is still fast.

- **"See the debate" as differentiator vs. zero-friction UX**
  - **adoption-strategist's position**: Add "see the debate" to Just Ask output (Recommendations #3). "The transcript is what makes conversus visibly different from ChatGPT." Users need to see "agents disagreeing — the cross-review attacks, the rebuttals, the concessions."
  - **devils-advocate's position**: Address the "just another ChatGPT wrapper" risk with a side-by-side example (Recommendations #9). The differentiation must be visible "in a side-by-side comparison" without requiring users to expand a collapsible section they may never open. Additionally, a 2-agent, 1-round "Just Ask" deliberation may not produce a substantive debate worth showing (Off-Base Assumptions, second item).
  - **Nature of tension**: adoption-strategist assumes the debate transcript is inherently compelling content that users will want to see. I question whether a lightweight 2-3 agent, 1-round deliberation produces a debate worth showing — if the agents do not cross-review each other, there is no real "debate," just parallel opinions and a summary. Showing shallow debate may be worse than showing no debate, because it reveals that the mechanism is less adversarial than advertised.
  - **Coordination needed**: The "see the debate" feature should be gated by deliberation depth. For full-mode deliberations (Guided/Power tiers with cross-reviews), showing the debate is a clear differentiator. For "Just Ask" lightweight mode, the transcript should only be shown if it contains genuine disagreement resolution — which requires the quality criteria from my recommendation #1 to detect. This means the quality model and the UX feature must be designed together.

- **Community presets: growth flywheel vs. quality control**
  - **adoption-strategist's position**: "Seed 20 community presets before launching the preset system" (Recommendations #5). Presets covering framework selection, database choice, architecture patterns, and 13 more categories. Presets "turn users into contributors and create network effects" (Alignment section).
  - **devils-advocate's position**: Community presets without quality control create "a npm-left-pad risk for deliberation quality" (Missed Opportunities, sixth item). The existing preset system has strict validation requirements. "Scaling this to a community registry without defining quality gates, versioning, or deprecation policies" is risky.
  - **Nature of tension**: adoption-strategist sees presets as a growth mechanism and wants to seed the ecosystem quickly. I see presets as a quality mechanism and want to gate the ecosystem carefully. Both are correct — an empty preset library produces no growth, but a low-quality preset library produces bad deliberations that damage trust. The tension is between seeding volume and maintaining quality.
  - **Coordination needed**: adoption-strategist's 20 seed presets should be treated as first-party, curated presets with the quality controls I describe. Community-contributed presets should be a later phase with defined quality gates (minimum fields, tested output examples, version pinning). The seed presets serve double duty: they provide immediate value and they establish the quality bar that community contributions must meet.

- **Cost awareness: when to surface it**
  - **adoption-strategist's position**: No explicit mention of cost controls or estimation. The focus is on reducing friction to zero — "Just Ask" should be a single natural-language question with zero configuration. Adding cost warnings before execution adds friction.
  - **devils-advocate's position**: "Add cost estimation and budget controls" (Recommendations #4). "A retiree who asks 'what stocks should I buy?' and gets a $15 API bill is not going to become a repeat user." Cost visibility is critical for non-technical users.
  - **Nature of tension**: Cost warnings are friction. Surprise bills are churn. adoption-strategist's framing of zero-friction adoption is in tension with my insistence on cost transparency. For developer users running conversus via CLI or MCP with their own API keys, cost awareness is expected. For web app users (if the web app is built), cost is a design-level concern that adoption-strategist's recommendation to cut the web app would sidestep — but only temporarily.
  - **Coordination needed**: If the web app is deferred (as both reviews recommend), cost controls are less urgent for the initial release — CLI/MCP/SDK users are developers who understand API costs. However, the cost model should still be documented in the spec so that when non-developer distribution channels are built, the cost design is ready. This is a "design now, implement later" item that both reviews can agree on.

### Safe Agreements

- **"Just Ask" mode is the highest-priority adoption feature**
  - **Shared position**: Both reviews identify "Just Ask" as the single most important feature for adoption. adoption-strategist calls it "the single most important feature for adoption" (Alignment section, second item) and makes shipping it the #1 recommendation. I agree that the three-tier model with "Just Ask" as the zero-config entry is "sound architecture" (Alignment section, first item) and structure three of my top recommendations around making "Just Ask" work correctly (quality criteria, cross-review bypass design, agent generation algorithm).
  - **Combined evidence**: adoption-strategist provides the demand-side argument — users need a zero-config entry point, the existing decision framework spec already provides the scaffolding, and the feature can ship within the current runtime. I provide the supply-side argument — the feature must meet a quality bar that distinguishes it from single-model responses, the phase subset must be explicitly designed, and the agent generation mechanism must be specified. Together, these form a complete picture: "Just Ask" is the right feature (adoption-strategist) and here is what it takes to build it well (devils-advocate).
  - **Confidence level**: High. Both reviews treat this as foundational. Any synthesis that deprioritizes "Just Ask" is misreading both reviews.

- **The web app should not be in the initial build order**
  - **Shared position**: adoption-strategist recommends cutting the web app from the initial roadmap entirely (Recommendations #8), calling it "the highest-cost, highest-risk item in the proposal." I recommend separating it into its own spec (Recommendations #7), noting it introduces "authentication, hosting, state management, real-time streaming, and database design — each of which is a significant design surface." Both reviews agree the web app should not block or delay the core engine, CLI, and MCP work.
  - **Combined evidence**: adoption-strategist argues from adoption strategy — build and validate one channel before expanding to the next, and the web app targets a user segment (non-technical users) that has not been validated. I argue from architectural scope — the web app is a different kind of system than the deliberation engine and deserves its own design process. The combination is stronger than either alone: the web app is both strategically premature (adoption-strategist) and architecturally underspecified (devils-advocate).
  - **Confidence level**: High. The proposal itself places the web app at step 7 of 8, so even the original author treats it as late-stage. Both reviews reinforce this ordering and argue for making it even more explicitly contingent.

- **The proposal's build order is wrong — it sequences by technical dependency rather than adoption signal**
  - **Shared position**: adoption-strategist states the proposal "sequences build order by technical dependency rather than by adoption velocity" (Executive Summary) and recommends reordering to start with user-facing features. I state the build order "is presented as a sequential plan but contains hidden parallelism assumptions and scope risks that are not acknowledged" (Executive Summary) and note that open question 1 means "the build order is not a plan — it is a wish list" (Recommendations #5).
  - **Combined evidence**: adoption-strategist provides a concrete alternative sequencing (Claude Code skill first, then MCP, then CLI) driven by "which channel puts conversus in front of users who are already making decisions." I provide the architectural critique — the build order assumes Python extraction is settled, treats open questions as answered, and does not include validation gates. Together: the build order is wrong both strategically (adoption-strategist) and structurally (devils-advocate), and fixing it requires both reordering by adoption signal and adding decision gates at each stage.
  - **Confidence level**: High. This is the strongest agreement between the two reviews and should be the primary structural recommendation in the synthesis.

- **Conversus must visibly differentiate from "just asking ChatGPT"**
  - **Shared position**: adoption-strategist identifies the missing "show your work" output mode as a high-impact missed opportunity (Missed Opportunities, fourth item) and makes "Answer 'Why not just ask ChatGPT?'" recommendation #9. I identify the missing competitive differentiation as a high-impact missed opportunity (Missed Opportunities, fifth item) and make addressing the "just another ChatGPT wrapper" risk recommendation #9.
  - **Combined evidence**: adoption-strategist's solution is UX-oriented — add a "see the debate" collapsible section showing agent positions, cross-review attacks, and resolution. My solution is evidence-oriented — produce a side-by-side example demonstrating structural differences (explicit disagreement, evidence-grounded positions, surviving dissent). These are complementary: the side-by-side example proves the value exists; the "see the debate" feature makes the value visible in the product. Both are needed.
  - **Confidence level**: High. If conversus cannot answer "why not just use ChatGPT?" in the product experience itself, the adoption thesis fails regardless of distribution strategy or build order.
