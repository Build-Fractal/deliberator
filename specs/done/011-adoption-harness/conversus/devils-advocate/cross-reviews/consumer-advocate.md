# Cross-Review of consumer-advocate's Review — by devils-advocate

---

### Dangerous Contradictions

- **Web app priority vs. web app readiness**
  - **consumer-advocate claims**: The web app should be elevated to build order step 4 or 5, delivered as a single milestone with "Just Ask" engine work. "Non-experts will not use a CLI. The web app is the only path that satisfies SC-1 for the consumer tier." (Actionable Recommendations, item 1)
  - **devils-advocate claims**: The web app should be separated into its own spec (012 or later), removed from this spec's build order entirely, because it "introduces authentication, hosting, state management, real-time streaming, and database design — each of which is a significant design surface that is not addressed here." (Actionable Recommendations, item 7)
  - **Why this is dangerous**: These two positions are directly incompatible. If the synthesis adopts both, the spec would simultaneously promise to deliver the web app early and defer it to a separate spec. More concretely: if the web app is elevated to step 4-5 without adequate design specification (which consumer-advocate does not provide and my review argues does not exist in the current proposal), the team builds a consumer-facing product on an underspecified foundation. If the web app is deferred per my recommendation, consumer users are locked out for an indeterminate period, and the CLI-shaped abstractions consumer-advocate warns about calcify into the engine's API surface.
  - **Suggested resolution**: The resolution is not "who yields" but sequencing clarity. The engine extraction, model agnosticism, and "Just Ask" mode logic (steps 1-4 in the proposal) must be designed with web-app consumption as a first-class use case from the start, even if the web app itself ships later. Consumer-advocate is right that designing "Just Ask" as a headless engine and bolting a web UI on later produces a developer tool with a web skin. I am right that the web app's design surface is too large for this spec. The compromise: this spec defines the engine API contract with explicit web-app requirements (streaming, progressive output, cost estimation hooks), and a follow-on spec delivers the web app against that contract. Consumer-advocate should insist on the API contract requirements; I should yield on the strict separation if those requirements are embedded in the engine spec.

- **Build order: consumer-first vs. developer-first**
  - **consumer-advocate claims**: The MCP server should not be labeled "Primary Integration Path" because "for the non-technical users the proposal explicitly names (L18-20), the web app is the only integration path that exists." The proposal should declare "dual-primary integration paths" — MCP for developers, web app for consumers. (Off-Base Assumptions, item 2; Actionable Recommendations, item 6)
  - **devils-advocate claims**: The web app is "the highest-complexity, lowest-certainty item in the proposal" and developer-facing distribution formats (CLI, SDK, MCP) serve "the users most likely to adopt conversus first." Deferring the web app prevents scope creep that delays delivery to developers. (Actionable Recommendations, item 7)
  - **Why this is dangerous**: Consumer-advocate's dual-primary framing implies equal resource allocation and priority. My developer-first framing implies sequential delivery where consumers wait. If both positions are adopted, the team tries to build two primary paths simultaneously, splitting focus and delivering neither well. Alternatively, the "dual-primary" label is adopted but developer features are still built first (because they are simpler), making the label a lie that erodes trust in the spec.
  - **Suggested resolution**: Acknowledge that "primary" is an overloaded term conflating importance with build sequence. Consumer-advocate is right about importance: the consumer market is larger and the web app is the only viable consumer path. I am right about build sequence: the engine must exist before any distribution format, and simpler formats (CLI, MCP) validate the engine faster. The spec should state: "The web app is the primary consumer distribution path and represents the largest adoption opportunity. It is built after the engine, CLI, and MCP server are stable, because it depends on a validated engine and its design surface requires a dedicated spec." This gives consumer-advocate's market reality the weight it deserves without creating the false promise of simultaneous delivery.

- **Lightweight deliberation: sufficient vs. structurally degraded**
  - **consumer-advocate claims**: "The '2-3 agents, 1 round -- fast and cheap' default for 'Just Ask' mode is correct for consumer use cases where speed matters more than exhaustiveness. A parent choosing a vacation destination does not need 5 agents and 3 rounds." (Alignment, item 6)
  - **devils-advocate claims**: "A 2-agent, 1-round deliberation is structurally identical to asking two models the same question and having a third summarize -- which is not what makes conversus valuable." The cross-review/revision cycle is "the core mechanism that makes conversus outputs better than 'ask N models and summarize.'" (Off-Base Assumptions, item 2; Actionable Recommendations, item 3)
  - **Why this is dangerous**: Consumer-advocate validates the lightweight default as "correct" without examining whether it preserves conversus's value proposition. My review argues the lightweight default actively destroys that value proposition. If consumer-advocate's position is adopted unchallenged, "Just Ask" ships as a consumer product that is structurally no better than a single-model response, users see no benefit, and adoption fails for the exact reason consumer-advocate most wants it to succeed. If my position is adopted unchallenged, "Just Ask" becomes slow and expensive, and the consumer market consumer-advocate correctly identifies as the largest opportunity is priced out.
  - **Suggested resolution**: This is the most important contradiction to resolve. The answer is not "more rounds" or "fewer rounds" but "what is the minimum adversarial structure that produces a measurably different output from single-model reasoning?" My recommendation 3 (design the cross-review bypass for lightweight mode) and recommendation 1 (define deliberation quality criteria) provide the framework. Consumer-advocate should adopt these as preconditions for the lightweight default, not oppose them. A "mini-cross-review" that preserves adversarial pressure in a single combined prompt could satisfy both positions: fast enough for consumers, structured enough to differentiate from ChatGPT.

### Tensions

- **Progressive disclosure vs. quality criteria**
  - **consumer-advocate's position**: Results should be structured in three progressive layers: (1) one-sentence recommendation, (2) summary paragraph with trade-offs, (3) full agent arguments expandable on demand. "Consumer users need the answer first and the reasoning second." (Actionable Recommendations, item 4)
  - **devils-advocate's position**: The output must meet minimum quality criteria including "the synthesis must surface at least one substantive disagreement between agents" and "the recommendation must acknowledge trade-offs, not just declare a winner." (Actionable Recommendations, item 1)
  - **Nature of tension**: Progressive disclosure is a presentation concern; quality criteria are a content concern. They are not opposed, but they pull in different directions at the implementation layer. If the one-sentence headline recommendation is designed to be a clean, simple answer (as consumer-advocate intends), it may structurally conflict with the quality requirement to acknowledge trade-offs and surface disagreement. A headline that says "Choose Postgres for your caching layer" satisfies consumer-advocate's UX goal but violates the quality criterion that trade-offs must be acknowledged. A headline that says "Postgres is recommended, but Redis has meaningful advantages for write-heavy workloads" satisfies the quality criterion but is a worse consumer UX.
  - **Coordination needed**: The progressive disclosure design must be informed by the quality criteria. Layer 1 (headline) can be a clean recommendation if layers 2-3 are guaranteed to contain the disagreement and trade-off data. The quality criteria should specify which layer must contain each required element, not require all elements in every layer.

- **Domain routing vs. competitive differentiation**
  - **consumer-advocate's position**: Add consumer domain routing (personal finance, career, travel, health, entertainment) with domain-specific agent personas, disclaimers, and tone adjustments. "Consumer users think in domains, not problem types." (Actionable Recommendations, item 9)
  - **devils-advocate's position**: The product must demonstrate concrete competitive differentiation from single-model reasoning through visible structural differences: "explicit disagreement, evidence-grounded positions, transparent reasoning chains, surviving dissent in the synthesis." (Actionable Recommendations, item 9)
  - **Nature of tension**: Domain routing makes the experience feel polished and contextual for consumers. Competitive differentiation demands that the output be structurally distinct from what a domain-aware single model would produce. These goals are not opposed, but domain routing could become a substitute for real deliberation quality — if the agents are well-named and domain-appropriate but do not actually produce adversarial pressure, the output looks good but is not better than ChatGPT with a domain-specific system prompt. Consumer-advocate's domain routing could mask the quality problem my review identifies.
  - **Coordination needed**: Domain routing should be layered on top of quality criteria, not instead of them. The domain-specific agent personas must be designed to produce genuine disagreement within the domain (a risk-averse financial agent vs. a growth-oriented one), not just thematic decoration. If domain routing is adopted, the quality criteria (minimum one substantive disagreement, evidence-grounded positions) must apply within each domain, and domain routing must be tested against the "ChatGPT with a system prompt" baseline for each domain.

- **Example-driven onboarding vs. expectation management**
  - **consumer-advocate's position**: The web app landing page should show 6-8 clickable example questions spanning consumer domains. "Without them, users stare at a blank box and leave." (Actionable Recommendations, item 3)
  - **devils-advocate's position**: The proposal never defines what distinguishes a good "just ask" result from a single-model response, and the "just another ChatGPT wrapper" risk must be addressed with a concrete side-by-side comparison. (Missed Opportunities, item 5; Actionable Recommendations, item 9)
  - **Nature of tension**: Example questions set expectations. If the examples promise consumer-grade answers ("Should I lease or buy my next car?") but the underlying deliberation engine has not been validated to produce meaningfully better answers than ChatGPT for those exact questions, the examples become a demonstration of the product's weakness rather than its strength. The examples must be curated to showcase questions where multi-agent deliberation visibly outperforms single-model reasoning — and that requires the differentiation work my review demands.
  - **Coordination needed**: Example questions should be selected after competitive differentiation testing, not before. Each example should have a validated comparison showing that conversus's output is measurably different from (and better than) asking the same question to a single model. Consumer-advocate's examples should be the output of my differentiation analysis, not an input to it.

- **Vague question handling vs. cost implications**
  - **consumer-advocate's position**: The system must handle vague questions like "help me decide" or "what should I do about my job" with conversational clarification — "ask one clarifying question (not five), offer to reframe the question, or explain what kinds of questions work best." (Missed Opportunities, item 1; Actionable Recommendations, item 2)
  - **devils-advocate's position**: Multi-agent deliberation is expensive, and the proposal lacks any cost estimation or budget controls. A non-technical user "who asks 'what stocks should I buy?' and gets a $15 API bill is not going to become a repeat user." (Missed Opportunities, item 3; Actionable Recommendations, item 4)
  - **Nature of tension**: Conversational clarification adds API calls before the deliberation even begins. If the system asks a clarifying question, the user responds, the system potentially asks another, and then runs a full deliberation, the total cost increases. Consumer-advocate's UX improvement and my cost concern are both valid, but they compound: better question handling means more interaction, which means more cost, which is exactly what my review warns will kill adoption.
  - **Coordination needed**: The clarification step must use a cheap, fast model (not the full deliberation engine). It should be a single lightweight call that classifies the question as actionable or vague, and either proceeds or asks for clarification. This is consistent with the proposal's model tiering suggestion (L115) but must be explicitly designed as a cost-controlled pre-processing step, not an open-ended conversation.

### Safe Agreements

- **"Just Ask" as the critical adoption feature**
  - **Shared position**: Both reviews identify "Just Ask" mode as the feature that will determine whether conversus achieves broad adoption. Consumer-advocate's executive summary calls it "the single most important feature for non-technical users." My review's executive summary states that the central question is whether "just ask" can deliver genuine deliberation quality, and my recommendation 1 treats its quality bar as the highest-priority item.
  - **Combined evidence**: Consumer-advocate provides the demand-side argument: non-technical users are the largest market, they will never use a CLI, and "Just Ask" is their only viable entry point. My review provides the supply-side constraint: "Just Ask" must produce outputs measurably better than single-model reasoning or the adoption thesis collapses regardless of UX quality. Together, these establish that "Just Ask" must be both accessible (consumer-advocate's contribution) and structurally sound (my contribution). Neither condition alone is sufficient.
  - **Confidence level**: High. Both reviews converge on this from opposite directions (market need vs. product integrity), making the agreement robust. The synthesis should treat "Just Ask" quality + accessibility as a joint requirement, not two separable concerns.

- **Open question 7 is under-addressed and critical**
  - **Shared position**: Both reviews identify the proposal's open question 7 ("Does 'just ask' mode risk oversimplifying?") as insufficiently addressed and potentially fatal. Consumer-advocate's Missed Opportunities flags that vague question handling is unspecified and that the proposal "never specifies what happens when a consumer asks a vague or malformed question." My review's Missed Opportunities states there is "no quality metric for 'just ask' mode" and that without one, "there is no way to know if the simplified mode is delivering conversus's value or just adding latency to a single-model response."
  - **Combined evidence**: Consumer-advocate approaches this from the input side (what happens when the question is bad?) and I approach it from the output side (what happens when the answer is indistinguishable from single-model output?). Both failure modes are real, and both are consequences of the same underspecification: the proposal describes "Just Ask" mechanics (classify, generate, run, synthesize) without defining quality at either end of the pipeline. Together, these reviews establish that the "Just Ask" pipeline needs quality gates at both ingestion (consumer-advocate's clarification handling) and output (my quality criteria).
  - **Confidence level**: High. The convergence from input-quality and output-quality perspectives makes this a well-triangulated finding. The synthesis should require both input validation and output quality criteria before "Just Ask" ships.

- **The proposal's build order needs revision**
  - **Shared position**: Both reviews argue the build order (L118-128) is wrong, though for different reasons. Consumer-advocate's executive summary and Actionable Recommendations item 1 argue the web app must be elevated because consumers are the largest market and are locked out by the current ordering. My Actionable Recommendations items 5 and 7 argue the build order is not a real plan because it assumes the engine extraction question (open question 1) is resolved and because the web app's scope is too large for this spec.
  - **Combined evidence**: Consumer-advocate demonstrates the build order fails on market priority (largest audience served last). My review demonstrates it fails on technical soundness (blocking decisions unresolved, scope unbounded). The build order is attacked from both the demand side and the supply side, and cannot survive either critique intact. The current eight-step sequence needs restructuring regardless of which perspective prevails.
  - **Confidence level**: High. Both reviews independently and forcefully argue the build order is wrong. The synthesis should treat build order revision as a prerequisite for spec approval, not an optional improvement.
