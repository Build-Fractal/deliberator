# Cross-Review: adoption-strategist's Review

**Cross-reviewer**: devex-advocate
**Reviewing**: adoption-strategist's Phase 1 review of spec 011 (Adoption Harness)

---

### Dangerous Contradictions

- **MCP server priority vs. Claude Code skill-first sequencing**
  - **adoption-strategist claims**: "The primary path for the first 100 users should be the channel with the lowest friction — which is the existing Claude Code skill, where conversus already works. The MCP server should be built as the second distribution channel." (Off-Base Assumptions, first bullet). Their recommendation 4 reorders to "MCP before CLI" but still places it after "Just Ask" as a Claude Code skill (recommendations 1 and 4).
  - **devex-advocate claims**: "Move MCP server to build step 3" — immediately after engine extraction and SDK (recommendation 3). "The MCP server should ship alongside or immediately after the CLI because it reaches the largest developer audience" and "Delaying it to step 5 means the highest-value developer integration ships last."
  - **Why this is dangerous**: These two build orders are incompatible. adoption-strategist's sequence is: (1) Claude Code skill "Just Ask," (2) validate with 100 users, (3) then MCP. devex-advocate's sequence is: (1) engine extraction, (2) SDK, (3) MCP server. If both are adopted, the MCP server either blocks on user validation gates that could take months (adoption-strategist's model) or ships before any user validation happens (devex-advocate's model). The first path starves AI-native engineers of the integration they need; the second path risks building infrastructure without signal. Neither review resolves when MCP should ship relative to a validation milestone.
  - **Suggested resolution**: Decouple the two concerns. Ship a minimal "Just Ask" Claude Code skill in week 1-2 (adoption-strategist's recommendation 1 is correct that this is low-cost). Simultaneously begin SDK and MCP server work. The validation gate applies to expanding beyond MCP (to web app, broader marketing) — not to shipping MCP itself. MCP users and Claude Code skill users are the same population (AI-native engineers in MCP-compatible runtimes), so the Claude Code skill validation directly informs MCP design. Both reviewers should yield: adoption-strategist yields the sequential gate between skill validation and MCP build; devex-advocate yields the position that engine extraction must precede any user-facing work.

- **SDK-first architecture vs. ship-before-you-design**
  - **adoption-strategist claims**: "Ship 'Just Ask' as a Claude Code skill first" — implement it "within the existing SKILL.md runtime" with "no Python extraction needed" (recommendation 1). The explicit rationale: "The existing runtime already supports everything needed... This gets a usable product in front of real users in days, not months."
  - **devex-advocate claims**: "Define SDK public API... before any implementation begins — it is the contract that CLI, MCP server, and web app all depend on" (recommendation 1). "The SDK is the foundational layer. CLI is click wrapping SDK methods. MCP server is MCP handlers wrapping SDK methods."
  - **Why this is dangerous**: adoption-strategist wants to ship a user-facing feature inside the existing Claude Code runtime before any Python extraction. devex-advocate wants to design the Python SDK API before any feature ships. If both are followed literally, either the SDK design blocks the "Just Ask" skill (killing adoption velocity) or the skill ships without SDK design (creating a second implementation path that the SDK must later reconcile or replace). The "thin wrapper" that adoption-strategist proposes will accrete logic that diverges from whatever SDK is later designed, producing the exact "three separate implementations" failure mode devex-advocate warns about.
  - **Suggested resolution**: Accept two tracks with an explicit convergence point. Track A: ship "Just Ask" as a Claude Code skill immediately (adoption-strategist's recommendation). Track B: design the SDK API concurrently (devex-advocate's recommendation). The convergence gate: when the Python engine extraction begins, the Claude Code skill's logic is refactored onto the SDK, not maintained as a parallel path. The SDK API design is informed by what was learned from the Claude Code skill. devex-advocate yields on "before any implementation" — the skill is implementation. adoption-strategist yields on treating the skill as the permanent architecture — it is a prototype that must converge.

- **"Cut the web app" vs. implicit acceptance of the web app timeline**
  - **adoption-strategist claims**: "Cut the web app from the initial roadmap" entirely (recommendation 8). "Remove the web app from this proposal entirely. If adoption via Claude Code skill, MCP, and CLI validates demand from non-technical users, revisit a web app as a separate spec."
  - **devex-advocate claims**: The web app is addressed only indirectly. The review's build order recommendation (recommendation 3) reorders steps 1-5 but does not mention cutting the web app. The executive summary notes "CLI and MCP ahead of the web app in the build order" as correct sequencing (Alignment, fifth bullet). The review implicitly accepts the web app as a later-stage deliverable.
  - **Why this is dangerous**: If the final synthesis follows adoption-strategist and cuts the web app entirely, the proposal loses its non-technical user story — and devex-advocate's structured output recommendation (recommendation 2) becomes the only way non-developers see results, which is insufficient for PMs and team leads. If the synthesis follows devex-advocate's implicit acceptance, adoption-strategist's concern about premature investment goes unaddressed. The web app question is load-bearing for resource allocation and neither review takes a conditional position.
  - **Suggested resolution**: Neither full cut nor implicit acceptance. The web app should be gated behind a specific adoption metric (adoption-strategist's recommendation 2 about "adoption gates" is the right mechanism). devex-advocate should explicitly support gating the web app behind validated demand from non-developer users, and adoption-strategist should accept that gating is different from cutting — the web app stays in the roadmap as a conditional item, not an unconditional one and not a deleted one.

### Tensions

- **Validation-first vs. design-first methodology**
  - **adoption-strategist's position**: "Let usage data — not architectural ambition — drive the subsequent build order" (Executive Summary). Defines explicit gates: "After 50 'Just Ask' runs, review: Do users trust the output?" (recommendation 2). The entire review is organized around the principle that user validation must precede infrastructure investment.
  - **devex-advocate's position**: "Define the Python SDK's public API surface... before any implementation begins" (Executive Summary, recommendation 1). Specifies detailed type contracts, async interfaces, error schemas, and builder patterns before any user touches the system.
  - **Nature of tension**: These are fundamentally different theories of product development applied to the same project. adoption-strategist follows lean startup methodology — ship fast, measure, iterate. devex-advocate follows API-first design — get the contract right, then everything built on top is consistent. Neither is wrong in isolation, but they pull in opposite directions on timeline. Every week spent designing the SDK is a week without user data; every week shipping without SDK design is a week accumulating technical debt that the SDK must absorb.
  - **Coordination needed**: Explicitly scope what must be designed before shipping vs. what can be designed after. The SDK's public API types and method signatures need an initial sketch (devex-advocate is right that the contract matters), but the internal implementation can evolve. The Claude Code skill can ship before the SDK is finalized (adoption-strategist is right that validation data is urgent). The coordination artifact: a one-page "SDK API sketch" that is treated as a draft, not a spec, and is refined after 50 "Just Ask" runs provide data on what the API actually needs to return.

- **Structured output vs. "show the debate" as the differentiation layer**
  - **adoption-strategist's position**: "Add 'see the debate' to Just Ask output" (recommendation 3). The differentiator is visibility into the multi-agent process: "a full 'debate transcript' showing the agent positions, cross-review attacks, and how the synthesis resolved disagreements." The output is narrative — designed for humans to read and be impressed by.
  - **devex-advocate's position**: "Add structured output mode" (recommendation 2). The differentiator is machine-readable data: "JSON with fields like recommendation, confidence, arguments_for, arguments_against, dissent." The output is structured — designed for programs to consume and compose.
  - **Nature of tension**: Both are asking for richer output from "Just Ask" mode, but they want different things. adoption-strategist wants an output that creates word-of-mouth (humans share interesting debates). devex-advocate wants an output that enables programmatic composition (CI pipelines parse JSON results). These are not mutually exclusive, but they compete for design attention and they imply different primary audiences for the same feature.
  - **Coordination needed**: The output should be layered: the SDK and MCP tools return structured data (devex-advocate's JSON schema), and that structured data includes a `debate_transcript` field (adoption-strategist's narrative). The human-readable rendering — whether in the Claude Code skill, CLI, or web app — surfaces the debate by default, with the structured data available for programmatic access. The structured schema must be designed to contain the narrative, not replace it.

- **MCP maturity assessment**
  - **adoption-strategist's position**: "MCP adoption is growing rapidly but as of early 2026, the majority of developers using AI coding tools are not yet on MCP-compatible setups" (Off-Base Assumptions, first bullet). Concludes MCP should not be "primary" and the first 100 users should come through the Claude Code skill.
  - **devex-advocate's position**: "MCP is already supported by Claude Code, Cursor, Windsurf, Zed, and VS Code (via extensions). For a developer tool targeting AI-native engineers, MCP coverage is sufficient" (Off-Base Assumptions, second bullet). Concludes the real risk is MCP server design quality, not MCP protocol maturity.
  - **Nature of tension**: Both reviews address the same open question (proposal L135) and reach different conclusions about MCP's readiness. adoption-strategist assesses the installed base (how many developers have MCP configured today); devex-advocate assesses the coverage (which tools support MCP). Both assessments are factually correct but lead to different strategic conclusions about where to invest first.
  - **Coordination needed**: Distinguish between MCP as a protocol (mature enough, devex-advocate is right) and MCP as a user-configured integration (not yet universal, adoption-strategist is right). The MCP server should be built early (devex-advocate's position) but should not be the sole adoption channel (adoption-strategist's position). Track MCP server installs as a separate metric from total conversus usage. adoption-strategist's recommendation 10 ("track MCP adoption metrics separately from overall adoption") is the right coordination mechanism.

- **Scope of "Just Ask" mode design**
  - **adoption-strategist's position**: "Just Ask" should include differentiation features — "a brief note: 'This recommendation was produced by N agents with [cooperative/adversarial] incentives'" (recommendation 9) and the full debate transcript (recommendation 3). The mode is optimized for demonstrating conversus's unique value.
  - **devex-advocate's position**: "Just Ask" should include structured return types, error contracts, and a non-interactive execution path (recommendations 2, 4). The mode is optimized for programmatic composability.
  - **Nature of tension**: adoption-strategist wants "Just Ask" to be a showcase. devex-advocate wants it to be an API endpoint. These design goals create different UX: a showcase mode is verbose and explanatory; an API endpoint is terse and structured. The same command cannot optimize for both without a format parameter or content negotiation.
  - **Coordination needed**: Introduce an output format option early: `--format human` (default for CLI, Claude Code skill) vs. `--format json` (default for SDK, MCP). The human format includes adoption-strategist's differentiation layer. The JSON format includes devex-advocate's structured fields. Both formats include the same underlying data; only the rendering differs. This must be in the initial design, not retrofitted.

### Safe Agreements

- **Build order must be resequenced away from the proposal's current ordering**
  - **Shared position**: Both reviews agree the proposal's build order (L120-128) is incorrectly sequenced. adoption-strategist: "it sequences build order by technical dependency rather than by adoption velocity" (Executive Summary). devex-advocate: "The build order is driven by technical dependencies rather than developer adoption milestones" (Executive Summary). Both specifically call out MCP server at step 5 as too late — adoption-strategist's recommendation 4 and devex-advocate's recommendation 3 both move it earlier.
  - **Combined evidence**: adoption-strategist provides the adoption-velocity argument: ship what produces users first, then build infrastructure to support scale. devex-advocate provides the developer-audience argument: MCP reaches the highest-value user segment (AI-native engineers) and should not wait for consumer features. Together, these constitute both a demand-side and supply-side case for reordering. The proposal itself calls MCP the "Primary Integration Path" (L74) — both reviews note this label contradicts its step-5 placement.
  - **Confidence level**: High. The resequencing recommendation is the strongest convergence point across both reviews, and the evidence from both perspectives is complementary rather than redundant.

- **"Just Ask" mode is the most important feature for adoption but needs richer output**
  - **Shared position**: Both reviews identify "Just Ask" as the critical adoption feature and both argue its output specification is insufficient. adoption-strategist: "'Just Ask' mode as zero-config entry point — this is the single most important feature for adoption" but "the proposal hides conversus's core differentiator" by returning only prose (Alignment, second bullet; Missed Opportunities, fourth bullet). devex-advocate: the mode is "overspecified for consumers and underspecified for programmatic use — developers will want conversus_decide to return structured data (JSON), not prose" (Executive Summary).
  - **Combined evidence**: adoption-strategist argues from the differentiation angle: plain prose makes conversus indistinguishable from ChatGPT. devex-advocate argues from the integration angle: plain prose cannot be consumed by CI pipelines or composed in agent workflows. Both conclude that the current specification of "plain-English synthesis" (L41) is necessary but not sufficient. The output must include both human-readable differentiation (debate visibility) and machine-readable structure (typed fields). The decision framework's artifact tree `[specs/999-decision-framework/spec.md, L277-293]` already produces rich structured output that both reviewers reference as the foundation for richer "Just Ask" returns.
  - **Confidence level**: High. Both reviewers independently identify the same gap from different angles and reference the same existing artifact structure as the solution basis.

- **Community presets need a seeding strategy, not just a system**
  - **Shared position**: Both reviews support the concept of community presets (proposal L116) but flag the absence of a concrete plan to populate them. adoption-strategist: "The proposal mentions community presets but provides no plan for initial library seeding" and recommends building the first 20 presets covering specific decision types (Missed Opportunities, fifth bullet; recommendation 5). devex-advocate: "There is no API for listing, searching, installing, or composing presets programmatically" and recommends SDK methods for preset management (Missed Opportunities, sixth bullet; recommendation 7).
  - **Combined evidence**: adoption-strategist addresses the content problem: an empty preset library has no network effects. devex-advocate addresses the access problem: even with content, presets locked behind filesystem conventions are invisible to programmatic users. Both problems must be solved for presets to function as the "growth flywheel" the proposal envisions. The existing preset system `[SKILL.md, L93-168]` provides the structural foundation — it needs both initial content (adoption-strategist) and a programmatic API (devex-advocate).
  - **Confidence level**: Medium. Both reviews identify the gap, but neither provides strong evidence on the priority relative to shipping "Just Ask" and MCP. Preset seeding and API design could be deferred to Phase 2 without blocking initial adoption, which tempers the urgency.

- **Model agnosticism requires a concrete provider interface, not just LiteLLM**
  - **Shared position**: Both reviews support model agnosticism as a goal but identify LiteLLM alone as insufficient. adoption-strategist does not deeply engage with the LiteLLM question but flags the overall open question as needing resolution (Off-Base Assumptions and recommendation 10 note MCP maturity but do not deeply contest the LiteLLM approach). devex-advocate: "Commit to a thin provider interface (class ModelProvider) with LiteLLM as the default implementation" (recommendation 8). The decision framework's constraint `[specs/999-decision-framework/spec.md, L531]` that "Must not require any specific model" is cited by devex-advocate as the grounding requirement.
  - **Combined evidence**: devex-advocate provides the stronger technical position here — a provider interface pattern avoids hard-coupling to LiteLLM while using it as the default. adoption-strategist's concern about hedging (recommendation 10, on not depending on MCP for the first 100 users) applies equally to not depending on LiteLLM for all providers. Both reviews implicitly agree that the model layer must be pluggable, not monolithic.
  - **Confidence level**: Medium. The agreement is substantive but lopsided — devex-advocate provides the concrete solution while adoption-strategist's contribution is more about the strategic principle of avoiding single-dependency risk. The resolution (thin interface + default implementation) is well-established in the ecosystem and does not require further debate.
