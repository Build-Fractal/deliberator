# Developer Experience Advocate — Final Disputes and Convergence

**Spec under review:** `specs/011-adoption-harness/proposal.md`
**Reviewer role:** devex-advocate
**Phase:** 4 — Final Disputes
**Grounding document:** `specs/999-decision-framework/spec.md`

---

### Remaining Disputes

- **Dispute: Confidence as a numeric float vs. quality indicators**
  - **My claim**: The `confidence` field should be removed from the output schema and replaced with a `quality_indicators` object that reports what the deliberation actually did — phases run, agent count, whether cross-reviews occurred, whether genuine disagreement surfaced — rather than a numeric score implying calibrated probabilistic certainty. (Revision, Recommendation 2, Modified recommendation.)
  - **Opposing position(s)**: The consumer-advocate's revision (Recommendation 5, Modified recommendation) specifies "Confidence is a float (0.0-1.0) in the engine output, derived from deliberation dynamics (dispute convergence, cross-review agreement). Documented, configurable bucket boundaries map the float to consumer labels: 0.0-0.4 = 'Close call,' 0.4-0.7 = 'Moderate recommendation,' 0.7-1.0 = 'Strong recommendation.'" The adoption-strategist's revision (Recommendation 9, New version) also endorses combining quantitative metadata with qualitative confidence labels. Both positions presuppose a calibrated numeric confidence score is achievable and desirable.
  - **Why I will not concede**: A confidence float requires calibration — the system must be validated to ensure that outcomes labeled 0.8 are correct 80% of the time, and outcomes labeled 0.4 are correct 40% of the time. No such calibration process exists in the proposal, and building one requires thousands of validated decisions with ground-truth outcomes. Without calibration, a float is a fiction that looks authoritative. The devil's advocate's revision (Recommendation 1, Surviving) independently established that the quality model must be defined before the output schema, and their core concern — that a 2-agent, 1-round deliberation without cross-reviews is "structurally identical to asking two models the same question and having a third summarize" — demonstrates that the same pipeline configuration can produce vastly different quality levels. A `confidence: 0.72` value from such a pipeline is not just unhelpful; it is actively misleading. Developers will use numeric confidence in CI/CD gates (`if result.confidence > 0.7: deploy`), making the fiction load-bearing. Quality indicators (boolean and structural facts about what the deliberation did) are honest, verifiable, and actionable without calibration.
  - **Counter-argument to their position**: The consumer-advocate argues that consumer-facing labels ("Strong recommendation," "Close call") require a numeric backing to be consistent. This is false. The labels can be derived directly from structural quality indicators: if cross-reviews occurred and genuine disagreement surfaced and was resolved through evidence, the label is "Strong recommendation"; if no genuine disagreement surfaced, the label is "Close call." No float is needed. Bucket boundaries on a float are a more complex mechanism that achieves the same result while introducing a calibration requirement the project cannot meet. The adoption-strategist's endorsement of "quantitative metadata" is already satisfied by the quality indicators object — agent count, mode, disagreements surfaced, disagreements surviving are all quantitative. They do not require synthesis into a single scalar.
  - **Proposed resolution path**: Replace the confidence float with a `quality_indicators` object containing structural facts: `{ agent_count, mode, cross_reviews_performed, genuine_disagreements_surfaced, genuine_disagreements_surviving, phases_completed }`. Derive consumer-facing labels from these indicators using documented rules, not from a numeric score. If the project later achieves sufficient validated decisions to calibrate a true confidence score, add it as an optional field at that time. This preserves the consumer-advocate's requirement for plain-language confidence signals and the adoption-strategist's requirement for visible metadata while eliminating the calibration problem.

- **Dispute: SDK API design timing — Phase 0 sketch vs. post-prototype design**
  - **My claim**: The SDK public API types (`Problem`, `Config`, `Deliberation`, `Result`) and the engine's internal interfaces (`DeliberationState`, `AgentState`, lifecycle hooks) must be designed together in a Phase 0 before the Claude Code skill prototype ships, even if those types are a "draft sketch" refined after usage data. The output contract, type definitions, and mapping layer are the foundation that prevents divergent implementations across distribution channels. (Revision, Recommendation 1, Modified recommendation.)
  - **Opposing position(s)**: The adoption-strategist's revision (Recommendation 1, Modified recommendation) positions the Claude Code skill prototype as shipping with a defined output contract (2-3 days of work) but not a full SDK type system. The adoption-strategist treats the skill as a config-generation-plus-output-formatting wrapper over existing SKILL.md execution, with the SDK types defined later, informed by usage data. The architect's revision (Recommendation 1, Modified recommendation) partially agrees with my position — Phase 0 defines both internal and external types — but time-boxes it to one week and treats the external SDK types as an "initial draft that may evolve after early usage data." The difference is whether the SDK types exist before or after the skill ships.
  - **Why I will not concede**: The adoption-strategist's output contract (recommendation, confidence metadata, debate transcript) is substantively an SDK type definition — it specifies the same fields I propose for `Result`. The disagreement is not whether types should be defined, but whether they should be called "output contract" (adoption-strategist) or "SDK types" (my position). My concern is that if these types are not explicitly framed as SDK types from the start, the skill implementation will make assumptions about serialization, field naming, and structure that diverge from what the SDK eventually needs. The adoption-strategist's own revision acknowledges this risk: "the consumer-advocate's warning about inheriting a 'flat-text output model' is valid" (New Recommendation: Design-output-format-for-dual-audiences). Defining SDK types is not a heavyweight process that blocks shipping — it is the same 2-3 days the adoption-strategist already allocates for the output contract, but with the explicit framing that these types are the SDK's `Result` contract, not just a skill output format. The architect's one-week time-box for Phase 0 is compatible with the adoption-strategist's timeline.
  - **Counter-argument to their position**: The adoption-strategist frames the skill prototype as preceding SDK design because speed-to-users is paramount. But their own modification requires defining an output contract with specific fields before the skill ships. The delta between "output contract with specific fields" and "SDK Result type with the same fields" is naming and framing, not engineering effort. The adoption-strategist's concern about SDK design blocking shipping is valid against a months-long SDK design process, but not against a one-week Phase 0 that produces draft types. The real risk is not that Phase 0 delays shipping — it is that shipping without Phase 0 produces an output format that the SDK must awkwardly accommodate later, which is exactly the divergence the adoption-strategist, consumer-advocate, and I all identified as a risk in our revisions.
  - **Proposed resolution path**: The adoption-strategist's "output contract" and my "SDK Result type" should be the same document, defined before the skill ships. Call it whatever the synthesis prefers — "output contract," "Result type," "output schema" — but frame it explicitly as the contract that CLI, MCP, SDK, and web app will all consume. The architect's one-week Phase 0 time-box is the right scope. The skill ships immediately after Phase 0 using these types. This costs zero additional time (the adoption-strategist already allocates 2-3 days for the output contract) while preventing the divergence all parties identified as a risk.

- **Dispute: MCP server prerequisites — quality model required before MCP ships**
  - **My claim**: The MCP server should ship after three prerequisites are met: (1) engine extraction committed, (2) SDK API designed (even as a draft), (3) "Just Ask" quality model defined. The devil's advocate's suggestion to ship `conversus_run` first and add `conversus_decide` only after quality criteria are met is the right incremental approach. (Revision, Recommendation 3, Modified recommendation.)
  - **Opposing position(s)**: The adoption-strategist's revision (Recommendation 4, Surviving; Recommendation 10, Modified recommendation) positions MCP development as running in parallel with skill validation, not sequentially gated behind quality model definition. The adoption-strategist argues that MCP and Claude Code skill users are the same population, so sequential gating creates unnecessary delay. The architect's revision (Recommendation 9, Modified recommendation) defines MV1 (feature validation via SKILL.md) and MV2 (engine validation via Python CLI) but does not gate MCP on quality model completion.
  - **Why I will not concede**: The MCP server exposes `conversus_decide` as a tool that AI coding assistants will invoke programmatically, often without the developer seeing the full output before it influences a code generation decision. This is a qualitatively different risk profile from the Claude Code skill, where the user reads the output and makes a conscious decision. If `conversus_decide` produces output indistinguishable from a single-model response (the devil's advocate's core concern from Recommendation 1), the MCP tool actively degrades the developer's workflow by adding latency and cost for no quality improvement. The quality model need not be exhaustive — the adoption-strategist's two-heuristic approach (genuine disagreement + agent attributions) is sufficient as a minimum — but some quality gate must exist before `conversus_decide` ships as an MCP tool. I accept `conversus_run` shipping before the quality model (it executes user-specified configurations, so quality is the user's responsibility), but `conversus_decide` (where the system makes quality-relevant decisions about agents, mode, and depth) requires a quality floor.
  - **Counter-argument to their position**: The adoption-strategist's argument that MCP and Claude Code skill users overlap is true for the population but not for the interaction pattern. The Claude Code skill is invoked intentionally and its output is read by a human. An MCP tool can be invoked by an AI agent as part of a larger workflow, where the output may be consumed programmatically without human review. Shipping `conversus_decide` as an MCP tool before the quality model is defined means a tool with no quality guarantees is available for programmatic consumption in automated workflows. The adoption-strategist's own new recommendation (Define-Just-Ask-quality-floor) acknowledges the need for a quality gate before shipping. The disagreement is whether the MCP server can ship before that gate is validated. I argue `conversus_decide` cannot; `conversus_run` can.
  - **Proposed resolution path**: Split the MCP tool set into two tiers. Tier 1 (ships with or before quality model): `conversus_run` — executes user-specified YAML configurations. No quality judgment by the system; the user controls agents, mode, and depth. Tier 2 (ships after quality model is validated): `conversus_decide` — the "Just Ask" MCP tool where the system makes quality-relevant decisions. This preserves the adoption-strategist's parallel development timeline for MCP while ensuring the highest-risk tool has quality backing. The guided workflow tools (`conversus_define`, `conversus_interests`, `conversus_mode`, `conversus_converge`) can ship with Tier 1 since they produce artifacts for human review, not automated consumption.

### Convergence

- **Converged: Engine extraction decomposition into independently testable sub-phases**
  - **Shared position**: Engine extraction must be decomposed into at least 5 sub-phases (config parser, template engine, async dispatch, dispute parsing, output manager), each with defined input/output contracts and independent testability. Treating engine extraction as a single build phase is a planning failure.
  - **Agreeing agents**: Architect (Recommendation 2, Surviving — zero challenges across all cross-reviews), devex-advocate (Revision, Recommendation 1 — acknowledged decomposition as complementary to SDK API design), consumer-advocate (Revision, Position Summary — agreed from the product perspective), adoption-strategist (Revision, Position Summary — endorsed from the adoption-timeline perspective), devil's advocate (Revision, Recommendation 5 — endorsed the decomposition).
  - **Strength**: Unanimous
  - **Path to convergence**: Agreed from Phase 1. The architect proposed the 5-sub-phase decomposition in their original review, and every cross-review independently confirmed it. This is the single most universally endorsed recommendation in the entire deliberation.

- **Converged: Deliberation quality criteria must be defined before or alongside output schema**
  - **Shared position**: Define minimum quality criteria for "Just Ask" output before shipping — at minimum, the synthesis must surface at least one substantive disagreement between agents, and the output must be structurally distinguishable from a single-model response. Quality criteria inform the output schema, not the other way around.
  - **Agreeing agents**: Devil's advocate (Recommendation 1, Surviving — highest-priority recommendation), devex-advocate (New Recommendation: "Define 'Just Ask' quality model before output schema"), consumer-advocate (New Recommendation: "Adopt deliberation quality criteria for 'Just Ask' mode"), adoption-strategist (New Recommendation: "Define-Just-Ask-quality-floor"), architect (Recommendation 8, Modified — "Quality gate" as priority 1 constraint for Just Ask output).
  - **Strength**: Unanimous
  - **Path to convergence**: The devil's advocate proposed this in Phase 1, and every other agent initially either overlooked it or deprioritized it. Through cross-review, every agent independently recognized the gap in their own position and adopted quality criteria as a prerequisite. This is the clearest example of the deliberation process producing genuine convergence — a position that started with one agent became unanimous through evidence and argument.

- **Converged: Vague question handling as a shared engine capability**
  - **Shared position**: The "Just Ask" pipeline must handle vague, ambiguous, or insufficient input gracefully. The engine should include a `QuestionClassifier` protocol or `NEEDS_CLARIFICATION` state that works across all distribution channels — interactive mode triggers conversational clarification (one question, not five), non-interactive mode returns a structured error with missing fields. The clarification step must be cost-controlled (cheap model, single lightweight call).
  - **Agreeing agents**: Consumer-advocate (Recommendation 2, Surviving — unanimous agreement across all cross-reviews), architect (New Recommendation: "Add-question-classifier-protocol"), devex-advocate (Revision, Recommendation 4 — accepted mode-dependent response design), devil's advocate (Revision, Recommendation 4 — accepted cost-control constraint).
  - **Strength**: Unanimous
  - **Path to convergence**: The consumer-advocate proposed this in Phase 1, and it received zero challenges across all cross-reviews. The architect elevated it to a protocol-level engine design concern. The devex-advocate and devil's advocate added design constraints (mode-dependent response, cost control) that refined rather than contested it. This is the strongest consumer-originated recommendation in the deliberation.

- **Converged: Two-layer model abstraction (ModelProvider + AgentRuntime/capability validation)**
  - **Shared position**: The model abstraction requires two layers: (a) a `ModelProvider` interface with signature `async def execute(messages, tools, output_schema, **kwargs) -> AgentOutput` — handling model routing and credentials, with LiteLLM as the default implementation; and (b) a capability validation layer — either an `AgentRuntime` that validates output structure after generation (my position) or a capability matrix that checks model qualification before dispatch (devil's advocate's position), or both (architect's position). The original `async def complete(messages, **kwargs) -> str` signature was wrong.
  - **Agreeing agents**: Devex-advocate (Recommendation 8, Modified — accepted the architect's correction on the method signature and proposed the two-layer model), architect (Recommendation 5, Modified — proposed the same two-layer structure with `ModelProvider` + capability gate), devil's advocate (Recommendation 2, Modified — converged on runtime validation over static catalog).
  - **Strength**: Majority (three agents; consumer-advocate and adoption-strategist did not take detailed positions on provider architecture)
  - **Path to convergence**: This emerged through cross-review. My original `-> str` interface was challenged by the architect as fundamentally misrepresenting what conversus agents need. The devil's advocate added the capability validation dimension. Through Phase 2-3, all three agents converged on the richer method signature and the two-layer separation. The architect's cross-review was the catalyst — it was the single most technically consequential correction in the deliberation.

- **Converged: Claude Code skill prototype ships first, Python extraction follows**
  - **Shared position**: Ship "Just Ask" as a Claude Code skill within the existing SKILL.md runtime for initial user validation, before beginning Python engine extraction. The skill is implemented as config-generation-plus-output-formatting (not new orchestration logic) to ensure portability. Python extraction is committed as the target architecture but informed by skill prototype usage data. The prototype has a defined sunset — it informs the extraction, it does not replace it.
  - **Agreeing agents**: Adoption-strategist (Recommendation 1, Modified — core recommendation), architect (Recommendation 7, Modified — SKILL.md as primary runtime for initial validation; Recommendation 9, Modified — MV1 feature validation then MV2 engine validation), devil's advocate (Recommendation 5, Modified — commit to Python extraction but allow time-boxed prototype), devex-advocate (Revision, Recommendation 1, Modified — accepted that Claude Code skill prototype can validate before SDK design finalizes).
  - **Strength**: Majority (four agents; consumer-advocate focused on the web channel rather than the skill prototype sequencing)
  - **Path to convergence**: The adoption-strategist proposed this in Phase 1 and it was challenged by the architect, devil's advocate, and myself on different grounds (SDK divergence, engine extraction commitment, output format portability). Through cross-review, all challengers accepted the sequencing principle while adding constraints: output contract before shipping (architect), Python extraction committed as target (devil's advocate), SDK types framed as the output contract (devex-advocate). The final converged position preserves speed-to-users while preventing the divergence risks the challengers identified.

### Final Position Statement

**Non-Negotiables** (3 items):

1. **The SDK public API types and engine internal interfaces must be designed in a shared Phase 0, not after implementation begins.** Without a shared type contract (`Result`, `Config`, `DeliberationState`, and the mapping between them), each distribution channel will implement its own version of config parsing, execution, and result handling — the three-divergent-implementations failure mode that every agent acknowledged as a real risk. This is a one-week investment that prevents months of integration pain. (Revision, Recommendation 1; cross-supported by architect Revision, Recommendation 1.)

2. **Numeric confidence scores must not ship until calibrated.** A `confidence: 0.72` field from an uncalibrated system is worse than no confidence field — it creates an illusion of precision that developers will build CI/CD logic on and consumers will trust without understanding. Quality indicators (structural facts about what the deliberation did) are honest, verifiable, and sufficient for deriving consumer-facing labels. (Revision, Recommendation 2; cross-supported by devil's advocate Revision, Recommendation 1 — quality model must precede output schema.)

3. **The MCP tool `conversus_decide` must not ship before a minimum quality floor is validated.** Unlike `conversus_run` (which executes user-specified configurations), `conversus_decide` makes system-level quality decisions about agents, mode, and deliberation depth. Shipping it without quality backing means an MCP tool with no quality guarantees is available for programmatic consumption in automated AI workflows. The quality floor can be the adoption-strategist's two-heuristic test (genuine disagreement + agent attributions), not an exhaustive quality model — but some floor must exist. (Revision, Recommendation 3; cross-supported by devil's advocate Revision, new recommendation "Gate 'Just Ask' prototype on minimum quality bar.")

**Flexibility** (3 items):

1. **MCP server build timing relative to skill validation.** I proposed MCP ships after SDK API + quality model. I am flexible on parallel development of the MCP server during skill validation (adoption-strategist's position), provided `conversus_decide` specifically does not ship before the quality floor is validated. `conversus_run` and the guided workflow tools can ship earlier. The specific step number is less important than the quality prerequisite for `conversus_decide`.

2. **Web app scope and gating mechanism.** I proposed gating the web app behind 200 active CLI/MCP/SDK users. I am flexible on the specific metric and on whether the initial consumer validation artifact is a minimal web form (adoption-strategist), a hosted share page (consumer-advocate), or a lightweight alternative like a Slack bot (architect). What must be preserved: the engine must not assume filesystem-only storage (forward compatibility), and the full web app (Next.js + PostgreSQL + auth) must not be in this spec's scope.

3. **Preset API tiering and launch scope.** I proposed a two-tier preset API with `presets.list()`, `.get()`, `.compose()` at launch and `.install()` deferred. I am flexible on whether the preset API ships with the initial SDK or is deferred to a second release, as long as the preset system is designed to be programmatically accessible from the start (not locked to SKILL.md filesystem conventions). What must be preserved: presets must be composable and discoverable through the SDK, not just through file system conventions.
