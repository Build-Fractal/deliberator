# Adoption Strategist Cross-Review of Architect's Review

---

### Dangerous Contradictions

- **Build order: infrastructure-first vs. validation-first**
  - **architect claims**: The most important recommendation is to "invert the build order so that spec 007's plugin interface and `DeliberationState` model are defined first, then extract the engine to target those interfaces" (Actionable Recommendations, item 1: Define-engine-interfaces-first). The architect further recommends a "Phase 0: Interface Definition" step before engine extraction, and advocates decomposing engine extraction into five sub-phases (item 2: Decompose-engine-extraction). The architect's entire build order begins with interface design and engine infrastructure.
  - **adoption-strategist claims**: "Ship 'Just Ask' as a Claude Code skill first" (Actionable Recommendations, item 1). The most important recommendation is to "ship 'Just Ask' mode as a Claude Code skill within the existing runtime in two weeks, validate it with 100 real decisions, and let usage data -- not architectural ambition -- drive the subsequent build order" (Executive Summary). My review explicitly calls out that "Python engine extraction is step 1" is an off-base assumption because the decision framework spec already enables a working guided workflow within the current runtime (Off-Base Assumptions, item 2).
  - **Why this is dangerous**: These two recommendations are mutually exclusive as step 1. The architect's Phase 0 (interface definition) and decomposed engine extraction would consume weeks or months of effort before any user-facing feature ships. My recommendation ships a user-facing feature in days by leveraging the existing runtime. If both are adopted without resolution, the team either splits effort between infrastructure and user validation (doing both poorly) or one silently wins and the other becomes stale spec text. The specific failure mode: the team begins defining `DeliberationState` dataclasses and async dispatch engines while zero users have validated that "Just Ask" mode produces decisions people trust. If the core value proposition is wrong, the infrastructure is wasted.
  - **Suggested resolution**: Sequence, not compromise. Ship "Just Ask" within the existing Claude Code runtime first (my recommendation). Use the validation data from real usage to inform the interface design (the architect's recommendation). The architect's Phase 0 interfaces will be better if they are designed after observing how users actually interact with "Just Ask" mode -- what state needs to persist, what output formats users need, what modes get used. The architect should yield on sequencing; I should yield on the principle that interface-first design is the right approach for the engine extraction once it begins. The resolution is: validate first, then design interfaces informed by real usage, then extract.

- **SKILL.md coexistence: thin adapter vs. frozen legacy**
  - **architect claims**: "Commit to a clear answer: the Python engine is the canonical implementation. SKILL.md becomes a thin adapter that invokes the Python engine via subprocess or MCP, OR SKILL.md is frozen as a legacy distribution format that receives no new features" (Actionable Recommendations, item 7: Resolve-SKILL.md-vs-engine-coexistence). The architect frames this as a maintenance cost problem: "Do not maintain two independent implementations of the same orchestration logic -- they will diverge."
  - **adoption-strategist claims**: My review positions the existing Claude Code skill as the primary channel for initial adoption: "The primary path for the first 100 users should be the channel with the lowest friction -- which is the existing Claude Code skill, where conversus already works" (Off-Base Assumptions, item 1). My recommendation to ship "Just Ask" within the current SKILL.md runtime (Actionable Recommendations, item 1) actively invests new features into the SKILL.md path.
  - **Why this is dangerous**: The architect wants to freeze SKILL.md or reduce it to a subprocess wrapper. I want to ship new features (Just Ask, guided workflow) into SKILL.md first. If both positions are adopted, we either freeze the very runtime I am recommending as the fastest path to users, or we invest in new SKILL.md features that the architect views as technical debt to be replaced. The failure mode: the team builds "Just Ask" into SKILL.md, gets 100 users, then faces a disruptive migration to the Python engine where those features must be reimplemented from scratch -- with the added pressure of not breaking the existing user base.
  - **Suggested resolution**: Accept my recommendation for SKILL.md as the initial shipping vehicle, but adopt the architect's principle that SKILL.md is not the long-term canonical implementation. Build "Just Ask" in SKILL.md with the explicit understanding that it is a prototype: validate the UX, the mode-selection heuristics, and the output format. Then, when the Python engine is built (targeting the architect's spec 007 interfaces), migrate the validated behavior into the engine. The SKILL.md version becomes a legacy path that is maintained for backward compatibility but receives no new features after the Python engine reaches parity. Both reviewers yield partially: I accept that SKILL.md is not the permanent home; the architect accepts that SKILL.md is the right first shipping vehicle.

- **Web app: defer to v2 vs. cut entirely**
  - **architect claims**: "Move the web app out of the v1 scope entirely" (Actionable Recommendations, item 4: Defer-web-app-to-v2). The architect frames this as scope management: the web app "adds 5+ new technology layers" and "creates scope pressure that will force shortcuts in the engine layer." The architect's recommendation is to ship "CLI + MCP server + Python SDK" as v1, with the web app as a separate proposal.
  - **adoption-strategist claims**: "Remove the web app from this proposal entirely" and further argues that "the fastest path to non-technical users is not a custom web app -- it is embedding conversus in tools non-technical users already use. A Slack bot, a ChatGPT plugin, or even a simple hosted API with a one-page form would reach non-technical users faster" (Actionable Recommendations, item 8; Off-Base Assumptions, item 3).
  - **Why this is dangerous**: While both reviews agree the web app should not be in v1, the framing creates different expectations for what comes after v1. The architect defers the web app to v2, implying it will be built eventually. I argue the web app may not be the right vehicle at all -- non-technical users should be reached through existing platforms (Slack, ChatGPT plugins). If the team internalizes "v2 is the web app," they may skip the cheaper experiments (Slack bot, hosted API) that would validate demand before committing to a Next.js + FastAPI + PostgreSQL stack. The failure mode is subtle: the team does not build the web app in v1 (good), but also does not explore the lightweight alternatives I propose, because "web app is planned for v2" becomes the default answer to "how do we reach non-technical users."
  - **Suggested resolution**: Reframe the web app not as "deferred" but as "one candidate among several for reaching non-technical users, to be validated by demand." The next step after CLI + MCP is not "build the web app" but "experiment with the cheapest path to non-technical users" -- which might be a Slack bot, a ChatGPT plugin, a simple hosted form, or indeed a web app. The architect should yield on the implicit assumption that a web app is eventually correct; I should acknowledge that if demand validation points to a web app, the architect's concerns about scope and technology layers are the right constraints for its design.

### Tensions

- **Interface design timing: upfront vs. usage-informed**
  - **architect's position**: The architect's most emphatic recommendation is defining engine interfaces before building (Actionable Recommendations, item 1). The architect argues that spec 007's `DeliberationState`, `AgentState`, `RoundState`, and lifecycle hooks should be defined as Python dataclasses/protocols first, because "building without them means a second rewrite when plugins ship." The architect explicitly warns that without upfront interface definition, "the engine will be built with ad-hoc internal state, requiring a disruptive refactor" (item 1, Risk if ignored).
  - **adoption-strategist's position**: My review frames build order as something that should be "driven by adoption milestones, not technical dependencies" (Executive Summary framing). My recommendation to define adoption gates before committing to build order (Actionable Recommendations, item 2) implies that the interface design should be informed by what users actually need, which cannot be known until users exist.
  - **Nature of tension**: The architect wants to design interfaces before building to avoid rewrites. I want to build before designing interfaces to avoid building the wrong thing. These are not contradictory -- it is possible to do both -- but they pull in different directions on the question of when and how much to invest in interface design. The architect's approach risks over-engineering interfaces for use cases that never materialize. My approach risks under-engineering interfaces that need to be rewritten once the engine is built. This is the classic "plan more" vs. "ship faster" tension.
  - **Coordination needed**: A time-boxed interface design phase after initial user validation but before engine extraction begins. The architect gets interface-first design; I get usage data informing those interfaces. Concretely: ship "Just Ask" in the existing runtime, run 50+ real deliberations, then use the patterns observed (which modes are popular, what output formats users want, how often multi-round is needed) to inform the spec 007 interface definitions. The interface design phase takes a week, not a month, because it is informed by real data.

- **Minimum viable product scope: engine MVE vs. feature MVP**
  - **architect's position**: The architect proposes a "Minimum Viable Extraction" (Actionable Recommendations, item 9): "Python CLI that reads `conversus.yml`, makes concurrent API calls to one provider (Anthropic), writes output files, and supports cooperative mode only." This MVE validates the engine extraction, not the user experience.
  - **adoption-strategist's position**: My implied MVP is the "Just Ask" mode within the existing Claude Code runtime -- a feature that validates the user experience and value proposition, not the technical extraction. My review argues that the engine extraction "is not a prerequisite for initial adoption" (Off-Base Assumptions, item 2).
  - **Nature of tension**: These are two different minimum viable products targeting two different hypotheses. The architect's MVE tests "can we extract the SKILL.md orchestration logic into standalone Python?" My MVP tests "do users trust multi-agent deliberation for real decisions?" Both hypotheses matter, but they cannot both be the first thing built. The architect's MVE produces a working Python CLI with no users; my MVP produces users on the existing runtime with no Python engine.
  - **Coordination needed**: Sequence them. My MVP (Just Ask in Claude Code) ships first because it answers the more existential question: is there demand? If the answer is no, the engine extraction is moot. If the answer is yes, the architect's MVE becomes the clear next step, and the engineer doing the extraction has real usage patterns to guide the implementation. The architect's MVE scope (cooperative-only, single-provider) is actually a good match for what early "Just Ask" usage will likely show -- most casual questions will run in cooperative mode.

- **LiteLLM complexity vs. distribution breadth**
  - **architect's position**: The architect's Off-Base Assumptions section flags LiteLLM as more complex than the proposal assumes: "conversus's agent model is unusual: agents are not simple prompt-response pairs" and "LiteLLM normalizes the chat completion API but does not normalize tool use, structured output, or long-context handling" (Off-Base Assumptions, item 3). The architect recommends a custom `ConversusAgent` abstraction on top of LiteLLM (Actionable Recommendations, item 5).
  - **adoption-strategist's position**: My review does not directly address LiteLLM complexity but argues for MCP as a distribution channel (Actionable Recommendations, item 4) and emphasizes that the primary path should be the existing Claude Code skill (Off-Base Assumptions, item 1). Implicitly, my position is that model agnosticism is a lower priority than getting users on the existing Anthropic-only runtime.
  - **Nature of tension**: The architect correctly identifies that LiteLLM integration is harder than the proposal suggests. My position implicitly deprioritizes it. The tension is: the architect wants to solve the LiteLLM problem properly (custom abstraction layer), which increases the scope of the engine extraction. I want to defer the multi-provider problem entirely until adoption validates demand. These positions do not conflict, but they create friction around how much engineering investment to allocate to model agnosticism early on.
  - **Coordination needed**: Agree that LiteLLM integration is phase 2 or later, not phase 1. The initial Python engine (architect's MVE) should target Anthropic only, as the architect already recommends. LiteLLM and the `ConversusAgent` abstraction are designed after the single-provider engine works. This aligns both positions: I get early shipping without the LiteLLM complexity; the architect gets a properly designed abstraction when it is built.

- **"Just Ask" output format: structured vs. accessible**
  - **architect's position**: "Just Ask" should produce "a subset of the standard conversus output: at minimum, a synthesis file following the same mode-specific template structure" so that outputs "can be fed back into the system as `prior:` context" and work with the dispute parsing subsystem (Actionable Recommendations, item 8: Specify-output-contract-for-Just-Ask).
  - **adoption-strategist's position**: "Just Ask" output should have "two layers: (1) a concise recommendation (2-3 sentences), and (2) a full 'debate transcript' showing the agent positions, cross-review attacks, and how the synthesis resolved disagreements" (Actionable Recommendations, item 3). My emphasis is on making the multi-agent process visible to differentiate from ChatGPT, not on machine-parseable structure.
  - **Nature of tension**: The architect wants structured output for system interoperability (feeding into `prior:`, plugin analysis). I want layered output for user experience and differentiation. These are not mutually exclusive -- the output can be both structured and layered -- but they optimize for different consumers. If the structured format is prioritized, the user-facing presentation may be constrained by template requirements. If the user-facing presentation is prioritized, the machine-parseable structure may be missing fields that plugins need.
  - **Coordination needed**: Design the output format to serve both needs explicitly. The underlying artifact should follow the structured template format the architect requires (synthesis file with mode-specific sections). The user-facing presentation layer should reformat this into the two-layer format I recommend (concise answer + expandable debate). The structure is the data model; the presentation is the rendering. Both reviewers get what they need if the output is structured data rendered in a user-friendly way.

- **Scenario replay: engine feature vs. adoption feature**
  - **architect's position**: The architect recommends adding `conversus_replay` as a seventh MCP tool, framing it as an adoption-friendly feature from spec 007 (Missed Opportunities, item 4; Actionable Recommendations, item 6). The architect's framing is architectural: replay depends on spec 007's scenario storage system.
  - **adoption-strategist's position**: My review emphasizes community presets as the growth flywheel (Alignment, item 3) and recommends seeding 20 presets before launching the preset system (Actionable Recommendations, item 5). I do not mention scenario replay. My focus is on reusable configurations (presets), not reusable executions (replays).
  - **Nature of tension**: Presets and replays serve related but different adoption needs. Presets help users start new deliberations quickly ("use the framework-selection preset"). Replays help users reuse specific past deliberations ("re-run last quarter's architecture review with updated data"). The architect treats replay as architecturally foundational (spec 007 integration); I treat presets as adoption-foundational (growth flywheel). If only presets are built, teams cannot easily re-run proven deliberation frameworks. If only replay is built, new users still face a cold start.
  - **Coordination needed**: Build presets first (lower technical dependency, immediate adoption value), then add replay as a power-user feature once the spec 007 engine is available. Presets are the on-ramp; replays are the retention mechanism. The architect's `conversus_replay` MCP tool is a good idea but depends on the spec 007 infrastructure that both reviews agree should come after initial adoption validation.

### Safe Agreements

- **The web app should not be in v1**
  - **Shared position**: The architect recommends deferring the web app to v2 or later, arguing it "adds 5+ new technology layers" and "creates scope pressure that will force shortcuts in the engine layer" (Actionable Recommendations, item 4). My review recommends removing it from the roadmap entirely, arguing "the web app is the highest-cost, highest-risk item in the proposal" and should be "justified by demonstrated demand, not assumed need" (Actionable Recommendations, item 8).
  - **Combined evidence**: The architect provides technical evidence: the web app requires Next.js, WebSocket, PostgreSQL, auth, and hosting -- a full product engineering effort orthogonal to the core engine. My review provides strategic evidence: the web app assumes non-technical users need a custom app when they may be better served by embedding conversus in tools they already use (Slack, ChatGPT plugins). Together, these arguments cover both the engineering cost and the market risk. The proposal's web app (proposal `L89-99`) is simultaneously the most expensive deliverable and the least validated in terms of user demand.
  - **Confidence level**: High. Both reviews independently arrive at this conclusion from different analytical frameworks (engineering feasibility vs. adoption strategy), which makes the agreement robust.

- **The proposal underestimates engine extraction complexity**
  - **Shared position**: The architect calls engine extraction a "module-scale piece of work" across six subsystems, arguing it "risks underestimating the effort by 3-5x" (Off-Base Assumptions, item 2). My review argues the same point from the adoption side: treating engine extraction as step 1 "delays all user-facing work by the duration of a significant rewrite" (Off-Base Assumptions, item 2).
  - **Combined evidence**: The architect provides structural evidence: SKILL.md contains 734 lines across six distinct subsystems (config parser, template engine, dispatch engine, dispute parsing, output manager, prompt construction), each requiring independent implementation and testing. My review provides strategic evidence: if extraction takes months instead of weeks, the entire adoption timeline slips, and no user validation happens during that period. The architect's decomposition (five sub-phases) and my adoption gates (validate before building) are complementary responses to the same underlying problem -- the proposal presents a months-long infrastructure project as a single build phase.
  - **Confidence level**: High. The architect's detailed technical decomposition and my adoption-timeline concern independently demonstrate that "Python engine extraction" as a single phase is not a viable unit of work planning.

- **"Just Ask" mode is the most important feature for adoption**
  - **Shared position**: The architect calls the three-tier model (Just Ask / Guided / Power) "correctly maps to three distinct user populations" (Alignment, item 1) and devotes significant attention to specifying the output contract for Just Ask (Actionable Recommendations, item 8). My review calls Just Ask "the single most important feature for adoption" (Alignment, item 2) and makes shipping it the top recommendation (Actionable Recommendations, item 1).
  - **Combined evidence**: The architect's evidence is architectural: Just Ask needs proper output structure to interoperate with the conversus ecosystem (prior context, dispute parsing, plugins). My evidence is strategic: Just Ask is the atomic unit of value that makes conversus accessible to non-power-users and differentiates it from single-model alternatives. Together, these confirm that Just Ask is both the right entry point for users and a technically feasible feature that can integrate with the broader system -- if its output format is properly designed.
  - **Confidence level**: High. Both reviews treat Just Ask as the feature that unlocks the widest user base, and both provide concrete recommendations for how to build it well (output structure from the architect, UX differentiation from the adoption strategist).

- **Parallel dispatch outside Claude Code is a hard engineering problem**
  - **Shared position**: The architect identifies that "parallel dispatch is built for Claude Code's Agent tool" and replicating it in standalone Python requires implementing "an async task manager that: (a) makes concurrent LLM API calls, (b) enforces context isolation between concurrent agents, (c) collects and validates outputs, (d) handles partial failures without corrupting other agents' results, and (e) enforces hard phase barriers" (Off-Base Assumptions, item 1). My review implicitly supports this by arguing that the existing runtime should be leveraged for initial adoption precisely because the engine extraction is non-trivial (Off-Base Assumptions, item 2; Actionable Recommendations, item 1).
  - **Combined evidence**: The architect provides the specific technical requirements for the dispatch engine. My review provides the strategic implication: because this is hard, it should not be the first thing built. Together, we establish that the proposal's framing of parallel dispatch as "already built" (`L111`) is misleading, and that the dispatch engine is a significant piece of infrastructure that should be built after -- not before -- user validation.
  - **Confidence level**: Medium. The architect's evidence is detailed and specific. My evidence is indirect (I argue to defer the problem, not that the problem is hard per se). But both reviews converge on the conclusion that the proposal underestimates this challenge, and both recommend sequencing it after other work.
