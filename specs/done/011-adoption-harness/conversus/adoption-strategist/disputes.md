# Adoption Strategist — Final Disputes and Convergence

---

### Remaining Disputes

- **Dispute: Build order — ship Just Ask before engine extraction, not after**
  - **My claim**: Ship "Just Ask" as a Claude Code skill within the existing SKILL.md runtime immediately, with output contract and quality floor defined beforehand (2-3 days each). Engine extraction to Python follows, informed by real usage data. MV1 (feature validation) precedes MV2 (engine validation). (Revision, Recommendation 1 and Recommendation 2.)
  - **Opposing position(s)**: The architect's revised position (Recommendation 1, modified) calls for a Phase 0 interface definition — both internal engine interfaces and external SDK types — time-boxed to one week, before any shipping. The devex-advocate's revised position (Recommendation 1, modified) requires resolving the engine extraction question first, then designing the SDK public API and engine interfaces together in Phase 0, with the Claude Code skill prototype informing API refinement afterward. Both positions place design work before any user-facing shipping.
  - **Why I will not concede**: The proposal's existential question is not "can we extract the engine?" — it is "do users trust multi-agent deliberation for real decisions?" (proposal, Open Question 7: "Does 'just ask' mode risk oversimplifying and producing shallow deliberations?"). Designing SDK types and engine interfaces before answering this question means designing in a vacuum. The architect acknowledges this in revision (Recommendation 9, modified): "the existential question (is there demand?) should be answered before the engineering question (can we extract?)." Yet the architect's Phase 0 still precedes any user validation. The devex-advocate's own revision concedes that the SDK API should be treated as a "draft sketch" refined after 50 validated uses — but then requires designing it before those uses can begin. My position resolves this contradiction: ship the skill first, define the output contract (not the full SDK API) as the minimal design prerequisite, and let the 50-use data inform the comprehensive Phase 0 design that follows. The output contract (structured fields for recommendation, confidence, debate transcript) is a strict subset of the full SDK API and takes days, not weeks.
  - **Counter-argument to their position**: The architect and devex-advocate treat Phase 0 interface design as a prerequisite for shipping anything. But the Just Ask skill, as I defined it in my revision, is pure config-generation-plus-output-formatting — it auto-generates a `conversus.yml`, delegates to `/conversus run`, and reformats the existing synthesis output. It adds zero new orchestration logic to SKILL.md. The architect's own revision (Recommendation 7, modified) endorses this exact approach: "New features (Just Ask) are built as config-generation layers on top of existing SKILL.md orchestration, not as new orchestration logic within SKILL.md." If Just Ask is config-generation-plus-formatting — and the architect agrees it should be — then the full Phase 0 interface definition is not a prerequisite for shipping it. The output contract is the only design prerequisite. Requiring the full SDK type system before shipping a thin SKILL.md wrapper conflates two different deliverables.
  - **Proposed resolution path**: The synthesizer should adopt a three-step sequence: (1) define the Just Ask output contract and quality floor (days of work), (2) ship the Just Ask Claude Code skill as config-generation-plus-formatting (days of work), (3) begin Phase 0 interface design informed by early usage data. Steps 1 and 2 can overlap with the architect's Phase 0 planning, but shipping must not be blocked on Phase 0 completion. The architect and devex-advocate get their interface design; users get a product to try; neither blocks the other.

- **Dispute: Minimal web form as part of consumer validation — in scope or deferred**
  - **My claim**: Build a minimal hosted web form — single-page, no auth, no history, no PostgreSQL — as part of the consumer validation gate, immediately after the Just Ask engine work validates with developers. This is days of work and produces real consumer data. Without it, validating only through developer channels creates a self-fulfilling prophecy where consumer demand appears absent because consumers were never given a channel to try. (Revision, Recommendation 8, modified.)
  - **Opposing position(s)**: The devil's advocate's revised position (Recommendation 7, modified) removes the web app from scope and does not include a minimal web form — instead defining a quantitative adoption gate (measurable demand from non-technical users via CLI/MCP channels) that triggers a dedicated web app spec. The devil's advocate's gate relies on demand signals from channels that non-technical users cannot access. The architect's revised position (Recommendation 4, modified) similarly removes the full web app and suggests evaluating "lightweight alternatives (Slack bot, simple hosted form) alongside the engine work" but does not commit to building any of them.
  - **Why I will not concede**: The devil's advocate's adoption gate — "measurable demand from non-technical users via CLI/MCP channels" — is structurally unsound. A retiree considering retirement planning will never install a CLI or configure an MCP server. Requiring demand signals from channels that exclude the target population by design means the gate will never be triggered. The consumer-advocate's revision (Recommendation 1, modified) makes this argument most clearly: "non-technical users must have a non-terminal path to conversus within the initial release cycle." The proposal itself (Vision section) declares conversus should be usable for "personal decisions (stock picking, career choices, vacation planning)" — these are consumer use cases that require a consumer-accessible channel to validate. The README describes conversus as a tool for "vetting ideas" generally, not exclusively for developers.
  - **Counter-argument to their position**: The devil's advocate frames the web form as scope creep. It is the opposite: it is the minimum viable validation artifact for the proposal's own stated vision. A single-page web form with a text input and an API call is not the Next.js + FastAPI + WebSocket + PostgreSQL stack the proposal describes — it is a landing page with a function call. The architect's suggestion to "evaluate lightweight alternatives" defers the consumer validation decision rather than making it. Evaluation takes time; building a minimal web form takes less time than evaluating whether to build it. The consumer-advocate and I converge on this point. The devil's advocate's engine design constraints (streaming events, no filesystem-only storage) are correct and complementary — they ensure the engine supports a future web app. But engine design constraints do not validate consumer demand. Only a consumer-accessible artifact does that.
  - **Proposed resolution path**: The synthesizer should include the minimal web form as a conditional deliverable: it ships after developer validation (Just Ask skill, 50+ runs) demonstrates that conversus produces output worth showing to anyone, but it ships before declaring "no consumer demand exists." The devil's advocate's engine design constraints (streaming events, structured output) are adopted as engine requirements regardless. The full web app remains out of scope, deferred to a separate spec triggered by consumer validation data from the minimal form.

- **Dispute: MCP development timing — parallel with skill validation or sequentially gated**
  - **My claim**: MCP server development should begin in parallel with Claude Code skill validation, not sequentially gated behind it, because MCP users and Claude Code skill users are the same developer population. Gating MCP behind skill validation creates unnecessary delay for the same audience. (Revision, Recommendation 4, surviving; Recommendation 10, modified.)
  - **Opposing position(s)**: The devex-advocate's revised position (Recommendation 3, modified) requires three prerequisites before MCP ships: (1) engine extraction committed, (2) SDK API designed, (3) Just Ask quality model defined. The devil's advocate's revised position (Recommendation 10, modified) proposes a two-level contract approach where full MCP tool contracts are specified only "when MCP implementation begins," implying sequential gating behind quality model and SDK design. Both positions make MCP dependent on completing the full Phase 0 + quality model work before development starts.
  - **Why I will not concede**: The devex-advocate's prerequisites are individually reasonable but collectively produce a months-long delay before the MCP server ships. The SDK API design, quality model definition, and engine extraction commitment are all Phase 0 deliverables. If MCP development cannot start until all three are complete, MCP ships months after the Claude Code skill — but both serve the same developers. A developer using Cursor is in the same population as a developer using Claude Code. Delaying MCP means delaying conversus's reach within a population it has already validated. The devex-advocate's own revision acknowledges that MCP is the "primary programmatic integration path for developer users" and that the Claude Code skill "does not compete with MCP, it informs it" (Recommendation 3, modified). If the skill informs MCP rather than competing with it, then learning from the skill should feed into MCP design, not block MCP development entirely.
  - **Counter-argument to their position**: The devex-advocate's concern about wrapping an unstable SDK is valid for the full MCP tool surface. But the devil's advocate's own two-level contract approach provides the answer: define directional MCP contracts now (rough input/output shapes, execution model), begin implementation of `conversus_run` (which wraps existing behavior with known contracts) in parallel with skill validation, and add `conversus_decide` only after the quality model is defined. This incremental approach — which the devil's advocate proposed — gives MCP development a head start without requiring the full SDK API to be stable. The devex-advocate's objection assumes MCP must ship all tools simultaneously; the devil's advocate's incremental approach shows it does not.
  - **Proposed resolution path**: Adopt the devil's advocate's two-level contract approach as the MCP development model. `conversus_run` (known behavior, stable contract) begins development in parallel with skill validation. `conversus_decide` (new behavior, quality-dependent) is added after the quality model is defined. Full MCP tool contracts are specified when each tool moves to implementation. This gives MCP a head start without the instability risk the devex-advocate fears.

### Convergence

- **Converged: Quality floor before shipping Just Ask**
  - **Shared position**: Before the Just Ask prototype ships (even as a Claude Code skill), validate that its output passes at minimum two binary tests: (1) the synthesis contains at least one substantive disagreement between agents, and (2) the output structurally differs from a single-model response (agent attributions, disagreement metadata). These checks are testable in a single afternoon against 10-20 sample questions. A mini-cross-review (2 agents + 1 combined cross-review prompt + 1 synthesis = 4 launches) should be the default Just Ask configuration to ensure genuine adversarial engagement.
  - **Agreeing agents**: All five agents converge on this position. Devil's advocate (Recommendation 1, surviving; new recommendation "Gate Just Ask prototype on minimum quality bar"). Adoption strategist (new recommendation "Define-Just-Ask-quality-floor"). Consumer advocate (new recommendation "Adopt deliberation quality criteria for Just Ask mode"). Devex-advocate (new recommendation "Define Just Ask quality model before output schema"). Architect (Recommendation 8, modified, quality gate as priority 1).
  - **Strength**: Unanimous
  - **Path to convergence**: The devil's advocate raised this concern in Phase 1. In Phase 2, the adoption strategist initially resisted quality criteria as a shipping gate, framing them as an "iteration target." The devil's advocate's cross-review argued that shipping without any quality bar risks output indistinguishable from ChatGPT, creating false-negative validation data. In Phase 3, every agent — including the adoption strategist — adopted some version of a pre-ship quality floor. The adoption strategist proposed the "two binary tests in one afternoon" formulation as a compromise between exhaustive quality modeling and no quality gate at all. All agents accepted this framing.

- **Converged: Engine extraction decomposition into 5 sub-phases**
  - **Shared position**: The engine extraction must be decomposed into independently testable sub-phases: config parser, template engine, async dispatch, dispute parsing, and output manager. Treating engine extraction as a single monolithic build phase is a planning failure that makes the extraction unestimable and untestable.
  - **Agreeing agents**: All five agents. Architect (Recommendation 2, surviving — zero challenges received). Devex-advocate (Safe Agreements in cross-review). Adoption strategist (Safe Agreements in cross-review). Consumer advocate (Safe Agreements in cross-review). Devil's advocate (Safe Agreements in cross-review).
  - **Strength**: Unanimous
  - **Path to convergence**: Agreed from Phase 1. The architect proposed this decomposition in the initial review and it received zero challenges across all four cross-reviews. Every agent independently confirmed the diagnosis. This is the strongest consensus finding in the entire deliberation.

- **Converged: MCP before CLI in build order**
  - **Shared position**: The MCP server should ship before the standalone CLI. MCP puts conversus in front of developers at the moment of decision-making, inside their editors, without context-switching. The CLI is a convenience wrapper that ships after MCP. The proposal's original build order (CLI at step 3, MCP at step 5) should be reversed.
  - **Agreeing agents**: Adoption strategist (Recommendation 4, surviving). Devex-advocate (Recommendation 3, modified — MCP ships after SDK but before web app). Devil's advocate (Recommendation 10, modified — withdrew MCP maturity concern). Consumer advocate (Recommendation 6, surviving — dual-primary paths with MCP as developer primary).
  - **Strength**: Majority (four agents; architect did not contest but focused on prerequisites)
  - **Path to convergence**: The adoption strategist and devex-advocate both proposed this reordering in Phase 1. No cross-review argued that CLI should come before MCP. The devil's advocate initially characterized MCP maturity as a medium-impact risk but withdrew this characterization in Phase 3 after the devex-advocate's evidence about MCP deployment across multiple IDEs (Claude Code, Cursor, Windsurf, Zed, VS Code). The remaining tension is about prerequisites (what must be done before MCP ships), not about ordering (MCP before or after CLI).

- **Converged: Full web app out of this spec's scope**
  - **Shared position**: The full-featured web app (Next.js + FastAPI + WebSocket + PostgreSQL + auth + history) is removed from this proposal's scope. It is either deferred to a separate spec (012 or later) or gated behind adoption metrics. The engine must be designed with web-app-compatible requirements from day one (streaming events, structured output, no filesystem-only storage assumption) to prevent CLI-shaped abstractions from calcifying.
  - **Agreeing agents**: All five agents. Architect (Recommendation 4, modified). Devil's advocate (Recommendation 7, modified). Adoption strategist (Recommendation 8, modified). Devex-advocate (new recommendation "Gate web app behind adoption metric"). Consumer advocate (Recommendation 1, modified — accepts full web app is too large for step 4-5).
  - **Strength**: Unanimous
  - **Path to convergence**: The consumer advocate initially proposed elevating the web app to step 4-5. Four cross-reviews challenged this, citing scope pressure, underspecified design surface, and unvalidated demand. In Phase 3, the consumer advocate conceded that the full web app is too large for this proposal but extracted a crucial constraint: engine design must account for web consumption from day one. All agents accepted this compromise — the full web app leaves scope, but the engine carries forward-compatible requirements.

- **Converged: Structured output schema with dual-audience rendering**
  - **Shared position**: The Just Ask output should be defined as a structured schema from day one, with fields for recommendation, confidence metadata (agent count, mode, disagreements surfaced, disagreements surviving), summary, arguments, dissent, and debate transcript. The schema is rendered differently per distribution channel: progressive disclosure for web, concise-plus-expandable for CLI, typed Result dataclass for SDK. Template-conformant markdown is the canonical artifact; structured JSON and human-readable prose are both first-class projections. Neither is derived from the other.
  - **Agreeing agents**: Adoption strategist (new recommendation "Design-output-format-for-dual-audiences"). Devex-advocate (Recommendation 2, modified). Architect (Recommendation 8, modified). Consumer advocate (Recommendation 4, modified). Devil's advocate converges on quality-first ordering (Recommendation 1) but accepts the schema as the container for quality indicators.
  - **Strength**: Unanimous
  - **Path to convergence**: In Phase 1, the adoption strategist focused exclusively on human-readable output, the devex-advocate focused on structured JSON, and the consumer advocate focused on progressive disclosure. Each cross-review exposed the other's blind spot. In Phase 3, all agents converged on the same architecture: one canonical output, multiple renderings. The architect provided the unifying frame (template-conformant markdown as canonical), and the devil's advocate added the constraint that quality indicators must be fields in the schema, not cosmetic additions.

### Final Position Statement

**Non-Negotiables** (3 items):

1. **Ship Just Ask as a Claude Code skill before completing engine extraction or full SDK design.** The proposal's existential question — does multi-agent deliberation produce decisions people trust? — must be answered with real user data before investing months in infrastructure. The output contract and quality floor are the only design prerequisites for shipping; the full Phase 0 interface design follows, informed by usage data. (Revision, Recommendation 1; README vision of conversus as a general-purpose decision tool; proposal Open Question 7.)

2. **The minimal web form must be built to validate consumer demand before declaring no consumer demand exists.** Validating only through developer channels (CLI, MCP, Claude Code) and concluding "no consumer demand" is a methodological error, not a market finding. The proposal's vision (personal decisions, career choices, vacation planning) requires a consumer-accessible channel to test. A single-page web form with a text input and an API call is the minimum viable consumer validation artifact. (Revision, Recommendation 8; proposal Vision section.)

3. **Adoption gates must use channel-appropriate populations.** Developer adoption is measured through developer channels (Claude Code skill usage, MCP installs, CLI downloads). Consumer adoption is measured through consumer channels (minimal web form task completion, return rate). Neither population's data can be used to evaluate the other's demand. This prevents the self-fulfilling prophecy where channel selection, not market reality, determines the product roadmap. (Revision, Recommendation 2.)

**Flexibility** (3 items):

1. **The exact timing of MCP development start relative to skill validation.** I prefer parallel development, but I can accept a short sequential gap (weeks, not months) if the devex-advocate's prerequisite of directional MCP contracts is completed first. What must be preserved: MCP must not be blocked on full SDK API stability or complete engine extraction. The devil's advocate's incremental approach (`conversus_run` first, `conversus_decide` after quality model) is an acceptable compromise.

2. **The number and composition of seed presets.** I proposed 20 presets (12-13 developer, 7-8 consumer). I am flexible on the exact count and allocation. What must be preserved: the seed library must include both developer and consumer presets to signal that conversus is a general-purpose decision tool, not exclusively a developer tool. A library of 15 presets with 10 developer and 5 consumer would be acceptable.

3. **The specific format of the confidence indicator.** I proposed combining quantitative metadata with qualitative labels ("Strong recommendation," "Moderate recommendation," "Close call"). I am flexible on whether the underlying representation is a float, an enum, or a composite object. What must be preserved: the output must include both a machine-readable confidence signal (for SDK/MCP consumers) and a human-readable confidence label (for non-technical users). The consumer advocate's float-with-documented-bucket-boundaries approach is acceptable.
