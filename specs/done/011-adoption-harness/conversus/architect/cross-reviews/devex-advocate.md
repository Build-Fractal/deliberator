# Architect Cross-Review of devex-advocate's Review

**Cross-reviewer:** architect
**Reviewing:** devex-advocate's Phase 1 review of `specs/011-adoption-harness/proposal.md`

---

### Dangerous Contradictions

- **Build order priority: MCP server vs engine interfaces**
  - **devex-advocate claims**: The MCP server should move to build step 3, immediately after the SDK, because it "reaches the largest developer audience" and is "a thin wrapper, not a large engineering effort" (Actionable Recommendations, item 3). The current build order delays "the highest-value developer integration" by placing it at step 5.
  - **architect claims**: A "Phase 0: Interface Definition" step must precede engine extraction, where `DeliberationState`, `AgentState`, `RoundState`, and the lifecycle hook enum from spec 007 are defined as Python dataclasses/protocols (Actionable Recommendations, item 1). The engine extraction itself must be decomposed into 5 sub-phases (Actionable Recommendations, item 2) and the async dispatch engine requires dedicated architecture work (Actionable Recommendations, item 3).
  - **Why this is dangerous**: devex-advocate's recommendation to move MCP to step 3 assumes the SDK is a settled, stable surface by step 2. But the architect review demonstrates that the engine extraction alone is a multi-module effort with at least 5 sub-phases, and that the interfaces it targets (from spec 007) must be defined before extraction begins. If MCP is built at step 3 against an SDK whose underlying engine is still being decomposed and whose interfaces are still shifting, the MCP tool signatures will either (a) expose unstable internals that break with every engine iteration, or (b) be designed as a superficial shell that cannot represent the actual engine state -- making the MCP server a second integration project when the engine stabilizes. Both outcomes are worse than building MCP slightly later against a proven SDK.
  - **Suggested resolution**: Agree on a "Phase 0.5" milestone: define the SDK's public API types (devex-advocate's recommendation 1) simultaneously with the engine interface definitions (architect's recommendation 1). The MCP server can then be built at step 3, but only after both the type contracts and the engine interfaces are locked. devex-advocate should yield on timing (MCP at step 3 is too early if the SDK is still in flux) while architect should yield on priority (MCP should be the first consumer of the stable SDK, not an afterthought at step 5).

- **SDK as foundation vs engine interfaces as foundation**
  - **devex-advocate claims**: "Define the Python SDK's public API surface (classes, methods, types, async support) before any implementation begins -- it is the contract that CLI, MCP server, and web app all depend on" (Executive Summary, most important recommendation). The SDK is "the foundational layer" and its public API should drive the architecture (Actionable Recommendations, item 1).
  - **architect claims**: The foundational layer is spec 007's `DeliberationState` model and plugin lifecycle hooks, which define the engine's internal architecture. The SDK wraps this; it does not define it. "The engine extraction then targets these interfaces. The plugin system becomes 'expose what already exists'" (Actionable Recommendations, item 1).
  - **Why this is dangerous**: These are competing answers to the question "what is the contract everything depends on?" If devex-advocate's SDK API (Problem -> Interests -> Config -> Result) drives the architecture, the engine's internal state model becomes an implementation detail that may not align with spec 007's `DeliberationState`. If architect's engine interfaces drive the architecture, the SDK's public API becomes a thin projection of internal state that may not match developer ergonomics (exposing `RoundState` and `HookPoint` to SDK users who just want `Deliberation.run()`). Building both independently produces two incompatible contract layers: an external SDK API and an internal engine API that fight each other at every boundary.
  - **Suggested resolution**: Define both contracts simultaneously in Phase 0, with explicit mapping between them. The engine interfaces (`DeliberationState`, `AgentState`, lifecycle hooks) are the internal contract. The SDK API (`Problem`, `Config`, `Deliberation`, `Result`) is the external contract. A thin adapter layer maps between them. devex-advocate should acknowledge that the SDK API cannot be designed without reference to the engine's state model; architect should acknowledge that the engine interfaces alone do not constitute a developer-facing API and that ergonomic SDK types are equally foundational.

- **LiteLLM sufficiency assessment**
  - **devex-advocate claims**: Commit to "a thin provider interface (`class ModelProvider: async def complete(messages, **kwargs) -> str`) with LiteLLM as the default implementation" (Actionable Recommendations, item 8). This resolves the open question decisively and provides model agnosticism immediately.
  - **architect claims**: LiteLLM "normalizes the chat completion API but does not normalize tool use, structured output, or long-context handling -- all of which conversus agents depend on" (Off-Base Assumptions, third item). A `ConversusAgent` abstraction is needed on top of LiteLLM to handle tool registration and output validation (Actionable Recommendations, item 5).
  - **Why this is dangerous**: devex-advocate's thin interface (`async def complete(messages, **kwargs) -> str`) hides the fact that conversus agents are not simple chat completions. If this interface ships as the SDK's model contract, developers building custom providers will implement simple message-in/string-out adapters that cannot support the structured output, file I/O, and template-format enforcement that conversus agents actually require. The interface will be correct for trivial cases and broken for real deliberations, and fixing it later is a breaking API change.
  - **Suggested resolution**: Architect's position is stronger here. The provider interface must account for structured output and tool-use semantics, not just chat completion. devex-advocate's recommendation should be modified: the thin interface is the right pattern, but the method signature needs to be `async def execute(messages, tools, output_schema, **kwargs) -> AgentOutput` rather than a bare string return. LiteLLM remains the default implementation, but the interface reflects what conversus agents actually need.

- No additional contradictions identified.

### Tensions

- **Developer adoption speed vs architectural correctness**
  - **devex-advocate's position**: Build order should be driven by "developer adoption milestones" rather than technical dependencies (Executive Summary). The MCP server is "the single highest-value integration for AI-native engineers" and should ship as early as possible (Actionable Recommendations, item 3).
  - **architect's position**: Build order should be driven by architectural dependencies. The engine extraction is a multi-module effort that must target spec 007's interfaces (Actionable Recommendations, items 1-3). Shipping early on unstable foundations creates maintenance debt.
  - **Nature of tension**: devex-advocate optimizes for time-to-first-user; architect optimizes for time-to-stable-foundation. These are not mutually exclusive goals, but they pull resource allocation in opposite directions. Prioritizing adoption speed risks shipping a fragile MCP server that creates a bad first impression. Prioritizing architectural correctness risks losing the adoption window while perfecting internals nobody sees.
  - **Coordination needed**: Define a "preview" tier for early distribution formats. The MCP server can ship at step 3 with an explicit "preview" label and a limited tool surface (e.g., only `conversus_decide` and `conversus_run`) while the full SDK stabilizes. This gives devex-advocate the early adoption signal while giving architect the freedom to evolve interfaces. The preview-to-stable transition must be planned, with breaking changes expected and communicated.

- **Scope of v1: web app inclusion**
  - **devex-advocate's position**: The build order correctly sequences "CLI before web app" (Alignment, item 5), and the web app is a valid distribution format for non-technical users. No recommendation to defer or cut it.
  - **architect's position**: The web app should be moved "out of the v1 scope entirely" because it "adds 5+ new technology layers" and creates "scope pressure that will force shortcuts in the engine layer" (Actionable Recommendations, item 4).
  - **Nature of tension**: devex-advocate implicitly accepts the web app as part of the adoption harness scope by not flagging it for deferral. Architect explicitly rejects it. This is not a direct contradiction -- devex-advocate did not advocate for the web app, they simply did not object -- but the silence creates a gap. If the synthesis follows devex-advocate's framing, the web app stays in scope. If it follows architect's, it is deferred.
  - **Coordination needed**: Both reviewers should state explicitly whether the web app belongs in v1. devex-advocate's review would be strengthened by either endorsing the deferral (since their review is entirely focused on developer-facing surfaces, not consumer-facing ones) or arguing why the web app serves developer adoption goals. The current ambiguity will let the web app remain in scope by default, which architect identifies as a significant risk.

- **Structured output: SDK concern vs architectural concern**
  - **devex-advocate's position**: "Just Ask" mode should return structured data (JSON with `recommendation`, `confidence`, `arguments_for`, etc.) as the primary output, with plain-English as a rendering of this structure (Actionable Recommendations, item 2). This is framed as a developer experience requirement.
  - **architect's position**: "Just Ask" output must follow "the same mode-specific template structure" so that its results can be fed back into the system as `prior:` context and parsed by the dispute parsing subsystem (Actionable Recommendations, item 8). This is framed as an architectural compatibility requirement.
  - **Nature of tension**: These positions are compatible in intent but different in design implications. devex-advocate wants a new structured format (JSON dataclass) optimized for external consumers. Architect wants the existing template-based format preserved for internal ecosystem compatibility. If the SDK returns a JSON `Result` dataclass while the engine produces template-structured markdown, there must be a reliable parser that converts one to the other -- and that parser must be maintained as templates evolve.
  - **Coordination needed**: Define the structured output as a layer on top of the template-structured markdown, not a replacement for it. The engine always produces template-structured markdown (architect's requirement). The SDK parses this into a typed `Result` dataclass (devex-advocate's requirement). The parser is a first-class component with tests, not an afterthought. Both reviewers should agree that the template-structured markdown is the canonical output and the JSON dataclass is a parsed projection of it.

- **CI/CD non-interactive mode: depth of design**
  - **devex-advocate's position**: A `--non-interactive` / `--ci` flag is needed for all CLI commands, with specific behaviors: accept defaults, fail with structured errors, output JSON (Actionable Recommendations, item 4). This is a P1 recommendation.
  - **architect's position**: The minimum viable extraction should be a CLI that "reads `conversus.yml`, makes concurrent API calls to one provider (Anthropic), writes output files" (Actionable Recommendations, item 9). The MVE is inherently non-interactive -- it reads a config file and produces output files without any prompts.
  - **Nature of tension**: devex-advocate's CI/CD design implies the CLI has interactive and non-interactive modes, with the flag toggling between them. Architect's MVE implies the CLI starts non-interactive (config-file-driven) and interactive features (guided wizard) are added later. If the MVE ships first, the `--ci` flag is unnecessary because there is no interactive mode to disable. If the guided workflow ships first, the flag becomes essential.
  - **Coordination needed**: Agree that the CLI's default mode is non-interactive (config-file-in, output-files-out). Interactive features (guided wizard from spec 003) are layered on top as a separate command or flag (`--interactive` / `--guided`). This inverts devex-advocate's framing: instead of "add a flag to disable interactivity," the CLI starts non-interactive and adds a flag to enable it. Both goals are met with less design overhead.

- **Preset system: programmatic API priority**
  - **devex-advocate's position**: The preset system needs a full programmatic API: `conversus.presets.list()`, `.get()`, `.compose()`, `.install()`, plus corresponding MCP tools and CLI commands (Actionable Recommendations, item 7). This is P2.
  - **architect's position**: The preset system is not mentioned in the architect review's recommendations. The architect focuses on template validation integration (Missed Opportunities, item 7) and stagnation detection portability (Missed Opportunities, item 6) as the extraction challenges.
  - **Nature of tension**: devex-advocate sees the preset system as a high-value developer surface worth wrapping in a programmatic API. Architect sees the preset system as one of many SKILL.md subsystems that must be correctly extracted to Python, but not as a priority API surface. If the extraction focuses on the preset API (devex-advocate's priority), other subsystems (dispute parsing, stagnation detection, output management) may receive less attention. If the extraction focuses on orchestration correctness (architect's priority), the preset API may be an internal-only concern with no public surface.
  - **Coordination needed**: The preset system should be extracted as a Python module with a clean internal API as part of the engine extraction (architect's scope), which devex-advocate's public SDK methods can then wrap. The internal API does not need to be designed for external ergonomics -- that is the SDK layer's job. Both concerns are addressed without competing for priority.

### Safe Agreements

- **Engine extraction is underscoped in the proposal**
  - **Shared position**: Both reviews identify the proposal's treatment of engine extraction as a single build phase (`L120`) as a significant underestimate. devex-advocate states the SKILL.md is "an agent orchestration specification that relies on the host runtime" and the extraction requires designing the Python API "that the Agent-tool runtime was implicitly providing" (Off-Base Assumptions, first item). Architect states the extraction "requires 5 sub-phases" across 6 distinct subsystems and "treating it as one phase risks underestimating the effort by 3-5x" (Off-Base Assumptions, second item; Actionable Recommendations, item 2).
  - **Combined evidence**: devex-advocate approaches this from the API design perspective -- what was implicit must become explicit. Architect approaches from the implementation perspective -- each SKILL.md subsystem (config parser, template engine, async dispatch, dispute parsing, output manager, prompt construction) is a module-scale piece of work. Together, they establish both the design burden (defining what the Agent tool was providing) and the implementation burden (rewriting 6 subsystems). The proposal's framing of extraction as a single step is contradicted from two independent angles.
  - **Confidence level**: High. This agreement should directly influence the synthesis: the proposal must decompose engine extraction into sub-phases with explicit milestones.

- **"Parallel dispatch already built" is misleading**
  - **Shared position**: Both reviews flag the proposal's claim that "parallel agent dispatch (already built)" (`L111`) misrepresents the current state. devex-advocate notes that the current distribution "requires an MCP-compatible agent runtime" and the lock-in is "to the Agent tool pattern, not to Claude Code specifically" (Off-Base Assumptions, first item). Architect states that parallel dispatch "is built for Claude Code's Agent tool" and replicating it in standalone Python requires implementing "an async task manager" with concurrent calls, context isolation, output collection, partial failure handling, and phase barriers (Off-Base Assumptions, first item).
  - **Combined evidence**: devex-advocate identifies the abstraction gap: the Agent tool pattern is the real dependency. Architect identifies the implementation gap: 5 specific capabilities must be built from scratch. Together, they show that the proposal both misidentifies the dependency (it is the Agent tool pattern, not Claude Code) and underestimates the replacement work (5 infrastructure capabilities, not a simple swap). The "already built" framing creates a false sense of readiness that could lead to underinvestment in the dispatch engine.
  - **Confidence level**: High. The synthesis should require an explicit async dispatch engine design section in the proposal, acknowledging that this is new infrastructure, not a port.

- **SKILL.md and Python engine coexistence must be resolved**
  - **Shared position**: Both reviews identify the dual-implementation risk. devex-advocate notes that the proposal correctly preserves the current SKILL.md (Alignment, item 3) but frames the extraction as replacing the implicit Agent-tool runtime contract with an explicit Python API (Off-Base Assumptions, first item). Architect explicitly recommends resolving coexistence: "the Python engine is the canonical implementation. SKILL.md becomes a thin adapter... OR SKILL.md is frozen as a legacy distribution format" and warns "do not maintain two independent implementations of the same orchestration logic -- they will diverge" (Actionable Recommendations, item 7).
  - **Combined evidence**: devex-advocate's framing that the extraction defines "the Python API that the Agent-tool runtime was implicitly providing" implies the Python engine is the new canonical form. Architect's explicit recommendation to freeze or adapt SKILL.md addresses the maintenance reality. Both reviews, from different angles, converge on: two independent implementations of the same orchestration logic will diverge, and the proposal must commit to which one is canonical. The spec 007 plugin system reinforces this -- it is designed for Python and cannot run in SKILL.md (`007-game-engine/spec.md, L131-158`).
  - **Confidence level**: High. The synthesis should require the proposal to declare the Python engine as canonical and define SKILL.md's future role (frozen legacy, thin adapter, or deprecated with migration path).

- **Model tiering is an architectural decision, not an optimization**
  - **Shared position**: Both reviews identify that the proposal's treatment of model tiering ("cheap model for cross-reviews, expensive for synthesis" at `L115`) understates its architectural significance. devex-advocate notes that the LiteLLM provider interface must support per-invocation model selection and recommends a thin provider interface as the default implementation (Actionable Recommendations, item 8). Architect notes that model tiering contradicts the current SKILL.md constraint ("All subagents use the orchestrator's model" at `SKILL.md, L716`) and must be "designed into the engine from the start, not bolted on later" (Actionable Recommendations, item 10).
  - **Combined evidence**: devex-advocate establishes the API design requirement: the provider interface must support multiple models. Architect establishes the breaking-change reality: model tiering overrides an existing constraint in SKILL.md. Together, they show that model tiering is not a performance optimization to add later -- it is a provider abstraction design decision that must be made during Phase 2 (LiteLLM integration) and that explicitly breaks backward compatibility with the single-model assumption.
  - **Confidence level**: Medium. The agreement is substantive but the practical impact depends on whether model tiering ships in v1 or is deferred. Both reviews agree it must be designed for, even if not implemented immediately.
