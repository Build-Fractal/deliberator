# Architect Cross-Review of Consumer Advocate's Review

**Reviewer**: architect
**Reviewing**: consumer-advocate's Phase 1 review
**Target**: Adoption Harness Proposal (011)

---

### Dangerous Contradictions

- **Web app priority vs. engine foundation**
  - **consumer-advocate claims**: "Move web app to step 4 or 5, immediately after 'Just Ask' engine work. Deliver 'Just Ask' and web app as a single milestone, not separate steps." (Actionable Recommendations, #1). The review frames the web app as the single most important deliverable and argues the current build order "buries the consumer-facing product at step 7 of 8" (Executive Summary).
  - **architect claims**: "Move the web app out of the v1 scope entirely... Replace with: 'v1 ships CLI + MCP server + Python SDK. Web app is a separate proposal.'" (Actionable Recommendations, #4). The architect review argues the web app "adds 5+ new technology layers (Next.js, WebSocket, PostgreSQL, auth, hosting)" and its inclusion "creates scope pressure that will force shortcuts in the engine layer."
  - **Why this is dangerous**: These are directly opposite prescriptions for the same build-order decision. If both are adopted, the project either attempts to rush the web app forward onto an immature engine (consumer-advocate's recommendation) or defers the web app entirely and loses the consumer audience (architect's recommendation). The consumer-advocate is correct that non-technical users will never touch a CLI. The architect is correct that a web app on a fragile engine will produce a bad consumer product. Adopting both positions without resolution produces either a half-built web app on an untested engine, or a technically sound engine that nobody outside developer circles can use.
  - **Suggested resolution**: The architect should yield on scope exclusion; the consumer-advocate should yield on timeline. Compromise: the web app enters v1 scope but is the final phase, not step 4-5. The engine extraction is decomposed into sub-phases (architect's recommendation #2) with explicit "web-app-ready" milestones -- specifically, the async dispatch engine and streaming output contract must be designed with web consumption in mind from phase 1, even if the web UI ships last. This ensures the engine is not CLI-shaped when the web app arrives, addressing the consumer-advocate's core concern that "Building 'Just Ask' as a headless engine and then bolting a web UI onto it will produce a developer tool with a web skin" (Off-Base Assumptions), while preserving the architect's insistence that engine quality cannot be sacrificed to scope pressure.

- **"Just Ask" output format: structured vs. progressive**
  - **consumer-advocate claims**: Results should use "progressive disclosure" with three layers: "(1) headline recommendation in one sentence, (2) summary paragraph with key trade-offs, (3) full agent arguments and dissent expandable on demand" (Actionable Recommendations, #4). The review explicitly critiques the decision framework's `summary/final.md` as a monolithic dump unsuitable for consumers (Missed Opportunities, "No progressive disclosure of results").
  - **architect claims**: "'Just Ask' should produce a subset of the standard conversus output: at minimum, a synthesis file following the same mode-specific template structure. This ensures 'Just Ask' results can be fed back into the system as `prior:` context... and that the dispute parsing subsystem works on Just Ask output." (Actionable Recommendations, #8). The architect requires structural compatibility with SKILL.md's `prior:` mechanism (`SKILL.md, L51-56`) and the dispute parsing subsystem (`SKILL.md, L670-697`).
  - **Why this is dangerous**: The consumer-advocate wants output shaped for human reading (layered, progressive, presentation-first). The architect wants output shaped for machine consumption (structured, parseable, ecosystem-compatible). If "Just Ask" output follows the consumer-advocate's progressive format, it will not have the mode-specific headings and structural markers that the dispute parsing subsystem requires. If it follows the architect's structured format, it will overwhelm non-technical users exactly as the consumer-advocate predicts. Implementing both without coordination produces either two output formats (doubling maintenance) or a single format that satisfies neither requirement.
  - **Suggested resolution**: Both positions can coexist through a separation of storage and presentation. The engine produces structured output compatible with the architect's ecosystem requirements (parseable by dispute parsing, usable as `prior:` context). The web app and CLI apply a presentation layer that transforms structured output into the consumer-advocate's three-tier progressive format. This is consistent with spec 007's principle that "templates become the presentation layer" while "the engine becomes the decision layer" (`007-game-engine/spec.md`, Section 5, Evolution Path table). The structured output is the canonical artifact; the progressive view is a rendering of it.

- **MCP server primacy**
  - **consumer-advocate claims**: "Replace 'Primary Integration Path' with 'Primary Developer Integration Path' for MCP. Add 'Primary Consumer Integration Path' heading for the Web App section. Both are primary, for different audiences." (Actionable Recommendations, #6). The review argues that labeling MCP as primary "signals that the web app is secondary" and shapes internal prioritization (Off-Base Assumptions, "MCP Server as 'Primary Integration Path'").
  - **architect claims**: The architect review endorses the MCP tool surface as "a well-chosen surface area" (Alignment, "MCP tool surface") and recommends deferring the web app entirely (Actionable Recommendations, #4). The architect's build order prioritizes CLI + MCP + SDK, with the web app outside v1 scope. This implicitly treats MCP as the primary path and the web app as a future concern.
  - **Why this is dangerous**: The consumer-advocate's "dual-primary" framing and the architect's "MCP-first, web-later" framing create contradictory prioritization signals. If the team adopts dual-primary labeling but the architect's build order, the label is dishonest -- the web app is labeled primary but resourced as secondary. If the team adopts dual-primary labeling and the consumer-advocate's build order, the MCP server and engine quality suffer from divided attention. The contradiction is not in the labeling itself but in what the label implies for resource allocation.
  - **Suggested resolution**: Adopt the consumer-advocate's dual-primary labeling in the spec (it correctly describes the product's audience segmentation), but adopt a sequenced build order where the engine is built to serve both paths from the start. The architect should acknowledge that "primary" refers to audience importance, not build order. The consumer-advocate should acknowledge that building the engine well is a prerequisite for both primary paths, and sequencing developer-facing distribution first does not make the web app less important -- it makes the web app's foundation more solid.

### Tensions

- **Scope minimalism vs. consumer completeness**
  - **consumer-advocate's position**: The review adds 10 actionable recommendations, including example-driven onboarding (#3), progressive result disclosure (#4), confidence indicators (#5), mobile-first design (#7), self-contained share pages (#8), consumer domain routing (#9), and result quality feedback (#10). Each is individually well-reasoned. Together, they expand the web app from a simple frontend into a full consumer product with onboarding, domain routing, feedback loops, and viral growth mechanics (Missed Opportunities and Actionable Recommendations, #1-#10).
  - **architect's position**: The architect review argues for a "Minimum Viable Extraction" (Actionable Recommendations, #9) and warns that the 8-phase plan without an MVP creates "phase 1 paralysis." The architect's entire framing is about reducing scope to what is buildable and testable: "which 2-3 things actually matter, and can we defer the rest without painting ourselves into a corner?"
  - **Nature of tension**: The consumer-advocate is defining what the product needs to be to succeed with consumers. The architect is defining what can be built without engineering collapse. Both are correct within their frames. The tension is that consumer product completeness requires features (onboarding, mobile, feedback, share pages) that each individually seem small but collectively represent a second product engineering effort on top of the engine extraction. The consumer-advocate's review adds scope; the architect's review subtracts scope. The proposal needs both perspectives but cannot satisfy both without explicit scoping decisions.
  - **Coordination needed**: A two-phase product strategy. Phase A (v1): engine + CLI + MCP + minimal web app with "Just Ask" and basic results. Phase B (v1.5 or v2): the consumer-advocate's full recommendation set (onboarding, mobile, progressive disclosure, share pages, feedback, domain routing). The consumer-advocate's recommendations become the v2 product requirements document. The architect's MVE becomes the v1 scope. Both are adopted, neither is discarded, and the sequencing prevents scope collapse.

- **Vague question handling vs. single-shot "Just Ask"**
  - **consumer-advocate's position**: "The system must ask one clarifying question (not five), offer to reframe the question, or explain what kinds of questions work best" (Actionable Recommendations, #2). The review emphasizes that consumers "ask bad questions constantly" and the system must handle this "gracefully or it will feel broken" (Missed Opportunities, "Vague question handling is unspecified").
  - **architect's position**: The architect review specifies that "Just Ask" output must be structured enough to feed back into the system as `prior:` context (Actionable Recommendations, #8) and does not address the multi-turn interaction pattern that clarifying questions imply. The architect's framing of "Just Ask" is as a pipeline: input question, configure, execute, produce output. The async dispatch engine design (Actionable Recommendations, #3) assumes a single-shot execution model.
  - **Nature of tension**: Clarifying questions turn "Just Ask" from a one-shot pipeline into a multi-turn conversation. This has architectural implications the architect does not address: the async dispatch engine needs to support an intermediate "awaiting user input" state between question classification and agent dispatch. The web app needs a conversational UI, not just a submit-and-wait pattern. The MCP server needs a tool that can return a clarifying question and accept a follow-up. These are not insurmountable, but they are not free, and they affect the engine design the architect is focused on.
  - **Coordination needed**: Define "Just Ask" as having two sub-modes: (a) sufficient-input mode (question is clear enough to proceed), and (b) clarification mode (question is vague, one round of clarification occurs before dispatch). The architect's engine design should account for a `NEEDS_CLARIFICATION` state in the execution flow, between config generation and agent dispatch. The consumer-advocate's clarification UX is a presentation concern on top of this state. Both reviews' concerns are addressed if the engine supports the state and the frontend surfaces it appropriately.

- **Model tiering vs. consumer cost transparency**
  - **consumer-advocate's position**: The review calls for a confidence indicator showing "Strong recommendation," "Moderate recommendation," or "Close call" (Actionable Recommendations, #5). This is a consumer-facing quality signal. The review does not address cost or model selection because consumers should not need to think about models.
  - **architect's position**: The architect review calls for explicit per-phase model tiering in `conversus.yml` (Actionable Recommendations, #10): `models: { default: claude-sonnet-4-6, synthesis: claude-opus-4, cross-review: gpt-4o-mini }`. This is a power-user configuration concern that enables cost optimization.
  - **Nature of tension**: For consumers, model tiering should be invisible -- the system picks the right model for each phase and the user sees a confidence indicator on the output. For power users, model tiering is an explicit configuration lever. These are not contradictory, but they require the engine to support model tiering as an internal capability (architect's concern) while the "Just Ask" mode auto-selects models based on question complexity (consumer-advocate's implicit concern). If model tiering is only exposed as explicit YAML config, consumers cannot benefit from it. If it is only automatic, power users lose control.
  - **Coordination needed**: Model tiering in the engine should support both explicit configuration (power tier) and automatic selection (just-ask tier). The "Just Ask" auto-configuration logic (which the architect suggests housing in the `PRE_EXECUTION` hook from spec 007) should include model tier selection alongside agent count, round count, and mode selection. The consumer-advocate's confidence indicator can be partially derived from deliberation dynamics (dispute convergence) and partially from model tier (higher-tier models producing higher baseline confidence).

- **Domain routing vs. game-theoretic classification**
  - **consumer-advocate's position**: Add a "secondary classification layer for consumer domains: personal finance, career, travel, shopping, health, entertainment" (Actionable Recommendations, #9). This domain routing adjusts agent personas, disclaimers, and output tone. The review argues that "Consumer users think in domains, not problem types" (Actionable Recommendations, #9).
  - **architect's position**: The architect review connects "Just Ask" classification to spec 007's feature extraction pipeline and structured extraction approach (`007-game-engine/spec.md, L392-406`), suggesting it could "be adapted for input classification rather than output analysis" (Missed Opportunities, "Feature extraction pipeline for 'Just Ask' mode"). The architect's classification is game-theoretic (selection, integration, scoping, stress-test) rather than domain-based.
  - **Nature of tension**: These are two orthogonal classification dimensions. Game-theoretic classification determines mode and deliberation structure. Domain classification determines agent personas, disclaimers, and output tone. Both are needed for a good consumer experience, but neither review connects them. The risk is that implementation treats them as competing approaches rather than complementary layers, or that domain classification is built as a separate system from the game-theoretic classification rather than composing with it.
  - **Coordination needed**: Define a two-stage classification pipeline: (1) game-theoretic classification selects mode and structure (architect's concern), (2) domain classification selects persona templates, disclaimers, and tone (consumer-advocate's concern). The domain layer is a modifier on top of the structural layer, not a replacement for it. This maps naturally to spec 007's `PRE_EXECUTION` hook: the config optimizer selects structural parameters, and a domain-routing module adjusts presentation parameters.

### Safe Agreements

- **"Just Ask" mode is the highest-impact feature for adoption**
  - **Shared position**: The consumer-advocate's Executive Summary calls "Just Ask" mode "the single most important feature for non-technical users." The architect's review identifies the "Just Ask" auto-configuration logic as important enough to warrant a dedicated output contract (Actionable Recommendations, #8) and connects it to spec 007's config optimizer (Missed Opportunities, "Config optimizer for 'Just Ask' defaults"). Both reviews treat "Just Ask" as the feature that transforms conversus from a power-user tool into a general-purpose product.
  - **Combined evidence**: The consumer-advocate provides user-facing evidence: non-technical users (retirees, students, parents) cannot write YAML or understand game theory modes (Alignment, "Three-tier user model"). The architect provides system-level evidence: the SKILL.md's config parsing (`SKILL.md, L28-78`) and mode selection are the primary barriers to adoption, and auto-configuration via the `PRE_EXECUTION` hook from spec 007 (`007-game-engine/spec.md, L206-211`) is the architectural path to eliminating them. Both perspectives converge on the same conclusion from different angles.
  - **Confidence level**: High. Both reviews independently arrive at "Just Ask" as the adoption-critical feature, and both identify specific mechanisms (auto-generated agents, mode selection, lightweight defaults) that make it feasible. This agreement should strongly influence build prioritization.

- **The proposal's build order is wrong**
  - **Shared position**: The consumer-advocate argues the build order "buries the consumer-facing product at step 7 of 8" (Executive Summary) and recommends reordering to elevate the web app. The architect argues the build order puts the plugin system last when its interfaces should be defined first (Actionable Recommendations, #1, "Define-engine-interfaces-first") and that engine extraction is undersized as a single phase (Actionable Recommendations, #2, "Decompose-engine-extraction"). Both reviews conclude that the proposal's linear 8-phase build order (`L119-127`) does not reflect the actual dependency structure of the work.
  - **Combined evidence**: The consumer-advocate identifies a prioritization problem (consumer features are last). The architect identifies a dependency problem (spec 007's interfaces are needed before engine extraction, not after it). Together, these reveal that the build order is neither priority-ordered nor dependency-ordered -- it is a rough narrative sequence that does not account for either user needs or technical dependencies. The architect's recommendation to add a "Phase 0: Interface Definition" and the consumer-advocate's recommendation to move the web app earlier are both corrections to the same underlying problem: the build order was written as a story, not as an engineering plan.
  - **Confidence level**: High. Both reviews identify concrete problems with the build order from their respective concerns, and neither review defends the current ordering. The final synthesis should treat build-order restructuring as a given, with the specific new ordering as the point of negotiation.

- **Parallel dispatch is harder than the proposal acknowledges**
  - **Shared position**: The consumer-advocate does not directly address parallel dispatch, but the review's insistence on real-time deliberation viewing (Alignment, "Web app as consumer product," citing `L93` "Live deliberation view: see agents arguing in real-time") implicitly requires a robust streaming dispatch system. The architect explicitly flags that "Parallel dispatch is built *for Claude Code's Agent tool*" and that replicating it in Python requires "a substantial piece of infrastructure that does not exist and must be built from scratch" (Off-Base Assumptions, "'Parallel agent dispatch (already built)'"). Both reviews imply that the proposal underestimates the engineering difficulty of making multi-agent execution work outside Claude Code.
  - **Combined evidence**: The architect provides the technical analysis: five non-negotiable rules (`SKILL.md, L286-298`) that the dispatch engine must enforce, including context isolation, parallel launch, and hard phase barriers. The consumer-advocate provides the product requirement: consumers expect to see agents deliberating in real-time, which requires the dispatch engine to emit streaming events, not just final outputs. Together, these establish that the dispatch engine must be both correct (architect) and observable (consumer-advocate) -- a harder engineering problem than either review alone identifies.
  - **Confidence level**: Medium. The agreement is indirect -- the consumer-advocate does not analyze dispatch complexity. But the consumer-advocate's product requirements (real-time view, streaming) add engineering requirements to the dispatch engine that reinforce the architect's warning about scope. The final synthesis should treat dispatch engine design as a P1 engineering task that must satisfy both correctness and observability requirements.
