# Cross-Review: architect reviewing devils-advocate

---

### Dangerous Contradictions

- **Engine extraction framing: blocking decision vs. blocking architecture**
  - **devils-advocate claims**: "This is not an open question — it is a blocking architectural decision that determines the shape of everything downstream. The proposal should either commit to Python extraction with a concrete migration plan... or commit to the adapter approach with a concrete interface definition. Present both as evaluated options with trade-offs, then decide." (Actionable Recommendations, #5)
  - **architect claims**: "Commit to a clear answer: the Python engine is the canonical implementation. SKILL.md becomes a thin adapter that invokes the Python engine via subprocess or MCP, OR SKILL.md is frozen as a legacy distribution format that receives no new features. Do not maintain two independent implementations of the same orchestration logic — they will diverge." (Actionable Recommendations, #7, Resolve-SKILL.md-vs-engine-coexistence)
  - **Why this is dangerous**: devils-advocate frames this as a decision that needs evaluation of both options before committing. architect has already committed: the Python engine must be canonical, and SKILL.md must either become a thin wrapper or be frozen. If a synthesis adopts devils-advocate's framing ("evaluate both, then decide"), it delays the decision that architect correctly identifies as foundational — the spec 007 plugin interface (`007-game-engine/spec.md, L131-157`) only works in Python, which means the adapter approach is a dead end for any feature that depends on plugins. But if the synthesis adopts architect's position without the evaluation devils-advocate demands, the team may commit to Python extraction without understanding the full migration cost (which architect's own recommendation #2, Decompose-engine-extraction, describes as 5 sub-phases of module-scale work). The danger is that one position rushes the commitment and the other delays it indefinitely.
  - **Suggested resolution**: Adopt architect's conclusion (Python is canonical) but require devils-advocate's rigor: the spec must include a concrete evaluation showing why the adapter approach fails for spec 007's plugin system. This makes the decision documented and defensible rather than assumed. architect should yield on the process (evaluate formally) while devils-advocate should yield on the outcome (the evaluation will confirm Python extraction is necessary).

- **"Just Ask" quality: structural redesign vs. quality metric**
  - **devils-advocate claims**: "Explicitly design the phase subset for 'just ask' mode. If cross-reviews are skipped, document what adversarial pressure mechanism replaces them. If cross-reviews are included, the 'fast and cheap' claim needs revision (2 agents with cross-reviews = 2 + 2 + 2 + 2 + 1 = 9 agent launches, not 'lightweight'). Consider a 'mini-cross-review' phase." (Actionable Recommendations, #3, Design the cross-review bypass for lightweight mode)
  - **architect claims**: "Define the output format explicitly. 'Just Ask' should produce a subset of the standard conversus output: at minimum, a synthesis file following the same mode-specific template structure. This ensures 'Just Ask' results can be fed back into the system as `prior:` context." (Actionable Recommendations, #8, Specify-output-contract-for-Just-Ask)
  - **Why this is dangerous**: These two recommendations pull in opposite directions on the same feature. devils-advocate wants to redesign the phase pipeline for "Just Ask" (possibly inventing a new "mini-cross-review" phase), while architect wants "Just Ask" to produce structurally compatible output that plugs into the existing ecosystem (`prior:` mechanism, dispute parsing subsystem). If the spec adopts the mini-cross-review innovation, the output format may diverge from the standard template structure that architect's recommendation depends on. But if the spec enforces strict template compatibility, the "mini-cross-review" may be impossible because the dispute parsing subsystem (`SKILL.md, L670-697`) expects specific headings produced by the full cross-review/revision cycle. The failure mode: "Just Ask" is either incompatible with the conversus ecosystem (devils-advocate's path) or too heavyweight to be "just ask" (architect's path).
  - **Suggested resolution**: Design "Just Ask" in two layers. The inner layer follows devils-advocate's recommendation: define the actual phase subset (which phases run, which are skipped, what replaces them). The outer layer follows architect's recommendation: whatever the inner layer produces, the final synthesis output must conform to the template structure so it can be used as `prior:` input. This means the synthesis template for "Just Ask" is the integration point — it can accept input from a reduced phase set but must produce structurally valid output. Both reviewers should converge on the synthesis template as the contract boundary.

- **Web app scope: separate spec vs. v2 deferral**
  - **devils-advocate claims**: "Remove the web app from this spec's build order. Create a separate spec (012 or later) for the web app after the core engine, CLI, and MCP server are stable." (Actionable Recommendations, #7, Separate the web app into its own spec)
  - **architect claims**: "Move the web app out of the v1 scope entirely... Replace with: 'v1 ships CLI + MCP server + Python SDK. Web app is a separate proposal.'" (Actionable Recommendations, #4, Defer-web-app-to-v2)
  - **Why this is dangerous**: Both agree the web app should leave this spec, but the mechanisms differ in a way that affects the proposal's architecture section. devils-advocate says "create a separate spec" — implying the web app architecture section (`L89-99`) should be extracted into its own document but remain part of the near-term plan. architect says "out of v1 scope entirely" — implying the architecture section should be removed and the web app should not constrain the engine design at all. If the synthesis adopts devils-advocate's framing, the engine may still be designed with web app requirements in mind (WebSocket streaming, PostgreSQL state persistence, session management), adding architectural constraints to the core engine that architect argues should not exist in v1. If the synthesis adopts architect's framing, a future web app spec may find the engine lacks the hooks it needs (e.g., no streaming event model, no persistent state layer).
  - **Suggested resolution**: This is a genuine tension more than a contradiction — see the Tensions section below for the more nuanced framing. The practical resolution is to adopt architect's position (remove from v1 scope) but add a single constraint to the engine design: "the dispatch engine must emit phase-lifecycle events that a future streaming consumer could subscribe to." This is the minimum hook that prevents painting the engine into a corner without importing the full web app complexity.

### Tensions

- **Model capability gates vs. model agnosticism**
  - **devils-advocate's position**: "Define a capability matrix: which modes require which model features (structured output, long context, instruction following fidelity). Add runtime validation that warns or blocks when the selected model is unlikely to produce valid deliberation output for the requested mode." (Actionable Recommendations, #2, Add model capability requirements per mode)
  - **architect's position**: "Evaluate whether LiteLLM's tool-use normalization is sufficient or whether a custom agent abstraction is needed on top of LiteLLM. Consider a thin `ConversusAgent` abstraction that uses LiteLLM for the API call but handles tool registration and output validation." (Actionable Recommendations, #5, Address-LiteLLM-tool-use-gap)
  - **Nature of tension**: devils-advocate wants to gate model selection before execution (capability matrix, minimum requirements). architect wants to abstract the model interface after execution starts (custom agent wrapper, output validation). These are not contradictory — they operate at different layers — but they pull the implementation in different directions. The capability matrix implies a registry of known model capabilities that must be maintained. The ConversusAgent abstraction implies runtime output validation that catches capability problems after they manifest. If both are implemented without coordination, the system has two separate quality gates that may disagree (the capability matrix allows a model that the runtime validation then rejects, or vice versa).
  - **Coordination needed**: Define a single quality enforcement point. Either the capability matrix gates models before invocation (devils-advocate's approach, requiring a maintained registry), or the ConversusAgent validates output after invocation (architect's approach, requiring retry/fallback logic). Doing both is defensible but the spec must define which is authoritative when they conflict.

- **Cost as an adoption concern vs. cost as an architecture concern**
  - **devils-advocate's position**: "Add a 'Cost Model' section. For each tier, estimate API cost ranges. For 'just ask' and the web app, define a cost estimation step before execution." (Actionable Recommendations, #4, Add cost estimation and budget controls)
  - **architect's position**: "Model tiering is an architectural decision, not an optimization. It requires the provider abstraction to support per-invocation model selection, which must be designed into the engine from the start." (Actionable Recommendations, #10, Align-model-tiering-with-provider-abstraction)
  - **Nature of tension**: devils-advocate treats cost as a user-facing concern (budget caps, cost estimation prompts, surprise bill prevention). architect treats cost as an engine-level concern (per-phase model selection in the dispatch loop). Both are valid, but they have different urgencies. architect's concern is foundational — if per-phase model selection is not designed in, it cannot be added later without refactoring the dispatch loop. devils-advocate's concern is user-facing — if cost estimation is not visible, adoption suffers. The tension is that architect's concern must be resolved in Phase 0/1 (engine interfaces), but devils-advocate's concern does not manifest until Phase 4+ ("Just Ask" mode) or Phase 7 (web app, which may be deferred).
  - **Coordination needed**: The engine interface definition (architect's Phase 0) should include a `model` field on the per-phase or per-agent dispatch config. The cost estimation layer (devils-advocate's recommendation) should be a separate concern that reads this config and the provider's pricing data to compute estimates. The two are complementary but must be sequenced: architect's per-invocation model selection enables devils-advocate's cost estimation, not the other way around.

- **Failure mode scope: multi-provider vs. single-provider**
  - **devils-advocate's position**: "Add a 'Failure Modes' section addressing: (a) what happens when one agent in a parallel batch fails (retry? abort phase? continue with N-1 agents?), (b) how to handle provider-specific rate limits... (c) how to validate that agent output conforms to template structure before proceeding..." (Actionable Recommendations, #6, Add failure mode analysis for multi-provider execution)
  - **architect's position**: "An MVE is: Python CLI that reads `conversus.yml`, makes concurrent API calls to one provider (Anthropic), writes output files, and supports cooperative mode only." (Actionable Recommendations, #9, Define-minimum-viable-extraction)
  - **Nature of tension**: devils-advocate wants comprehensive failure mode analysis for multi-provider execution now. architect wants to start with a single-provider MVE where failure modes are simpler. These are not contradictory — the MVE can ship without multi-provider failure handling — but the tension is about when the failure mode analysis happens. If it happens before the MVE (as devils-advocate implies by marking it P2), it delays shipping. If it happens after the MVE (as architect implies by starting single-provider), the multi-provider failure modes may reveal architectural problems that require reworking the dispatch engine.
  - **Coordination needed**: The dispatch engine design (architect's recommendation #3) should define the failure isolation contract (per-agent error isolation, phase barrier semantics) for the single-provider case. devils-advocate's multi-provider failure modes should be documented as known future requirements that the dispatch engine's error contract must be extensible enough to handle. The key design question to resolve now: does a single agent failure abort the phase or continue with N-1 agents? This applies to both single-provider and multi-provider scenarios.

- **MCP maturity risk: primary path vs. fallback strategy**
  - **devils-advocate's position**: "No fallback integration strategy is defined if MCP adoption stalls." (Missed Opportunities, MCP as 'primary integration path' without fallback)
  - **architect's position**: The architect review does not challenge MCP's role directly; it endorses the six MCP tools as "a well-chosen surface area" (Alignment section) and recommends adding a seventh (`conversus_replay`). The implicit position is that MCP is viable.
  - **Nature of tension**: devils-advocate sees MCP immaturity as a risk requiring a fallback plan. architect sees MCP as sufficiently mature to invest in (adding more tools to the surface area). If MCP stalls, architect's `conversus_replay` recommendation becomes wasted design work, and the system has no alternative integration path for Cursor/VS Code users. But if MCP succeeds, devils-advocate's fallback strategy is wasted planning.
  - **Coordination needed**: Define a decision point: "If MCP adoption in Cursor/VS Code has not materialized by [milestone], build native extensions as a fallback." This keeps the MCP-first strategy without leaving the system stranded if the bet fails. architect should acknowledge this risk explicitly rather than doubling down on the MCP surface area.

### Safe Agreements

- **Parallel dispatch is not "already built"**
  - **Shared position**: Both reviews identify the proposal's claim that "Parallel agent dispatch (already built)" (`L111`) is misleading. devils-advocate states: "Parallel dispatch is built for Claude Code's Agent tool... In a standalone Python runtime, 'parallel dispatch' means implementing an async task manager" (Off-Base Assumptions). architect states: "This is misleading. Parallel dispatch is built for Claude Code's Agent tool... This is a substantial piece of infrastructure that does not exist and must be built from scratch" (Off-Base Assumptions).
  - **Combined evidence**: devils-advocate identifies the specific requirements: concurrent API calls, context isolation, output collection, partial failure handling, hard phase barriers. architect identifies the same requirements and adds that the five non-negotiable multi-agent rules (`SKILL.md, L286-298`) are the contract the dispatch engine must satisfy. Together, the two reviews produce a comprehensive requirements list for the async dispatch engine that the proposal entirely fails to scope.
  - **Confidence level**: High. This is the strongest agreement between both reviews. The proposal's framing of parallel dispatch as "already built" is factually incorrect and creates a false sense of readiness that could lead to severe underestimation of the engine extraction effort.

- **Web app should not be in v1 / this spec**
  - **Shared position**: Both reviews agree that the web app adds disproportionate complexity and should be removed from the current scope. devils-advocate states: "Remove the web app from this spec's build order. Create a separate spec" (Actionable Recommendations, #7). architect states: "Move the web app out of the v1 scope entirely... The web app shares the Python engine with CLI/MCP but adds 5+ new technology layers" (Actionable Recommendations, #4).
  - **Combined evidence**: devils-advocate grounds the recommendation in scope risk: "the web app is the highest-complexity, lowest-certainty item in the proposal." architect grounds it in engineering dependency: the web app requires Next.js, WebSocket, PostgreSQL, auth, and hosting — none of which share any infrastructure with the core engine extraction. Both reviews note that the web app scope would create pressure that forces shortcuts in the engine layer. The converging evidence from two different analytical lenses (scope risk vs. engineering dependency) strengthens the recommendation.
  - **Confidence level**: High. Both reviews arrive at the same conclusion from different directions, and neither identifies any counterargument or dependency that would require the web app in v1.

- **Engine extraction is undersized as a single phase**
  - **Shared position**: Both reviews identify that "Python engine extraction (SKILL.md logic to Python package)" as a single build phase (`L120`) dramatically understates the scope. devils-advocate states: "The proposal should either commit to Python extraction with a concrete migration plan (including how SKILL.md's orchestration logic maps to Python constructs, how the Agent tool's parallel dispatch is replicated with asyncio, and how template resolution works without filesystem-relative paths)" (Actionable Recommendations, #5). architect states: "Break into 5 sub-phases: (a) config parser + validator, (b) template engine + linter integration, (c) async dispatch engine with phase barriers, (d) dispute parsing subsystem, (e) output manager with round-directory lifecycle" (Actionable Recommendations, #2).
  - **Combined evidence**: devils-advocate identifies the scope problem at the decision level (the extraction approach is not even decided). architect identifies it at the implementation level (the extraction requires 5 distinct modules). Together, the two perspectives reveal a compound underestimation: the proposal has not decided how to extract AND has not scoped the work even if it had decided. architect's specific decomposition into 5 sub-phases, each mapped to specific SKILL.md line ranges (`SKILL.md, L28-196`, `L243-271`, `L273-327`, `L670-697`, `L210-241`), provides the granularity that devils-advocate's recommendation lacks.
  - **Confidence level**: High. This agreement directly affects project planning. If the synthesis treats engine extraction as a single phase, the effort will be underestimated by 3-5x (architect's estimate), leading to schedule failure.

- **LiteLLM is not a simple swap**
  - **Shared position**: Both reviews challenge the proposal's framing of LiteLLM as a straightforward abstraction layer. devils-advocate states: "Model agnosticism is not 'use any model' — it is 'use any model that meets minimum capability thresholds for the requested mode'" (Off-Base Assumptions). architect states: "LiteLLM normalizes the chat completion API but does not normalize tool use, structured output, or long-context handling — all of which conversus agents depend on" (Off-Base Assumptions).
  - **Combined evidence**: devils-advocate's evidence is about deliberation quality (models that cannot follow structured templates will produce garbage). architect's evidence is about API capability (LiteLLM does not normalize the tool-use and structured-output APIs that conversus agents rely on). These are two distinct problems with the same root cause: treating model agnosticism as a routing problem rather than a capability problem. The combined picture is that LiteLLM solves the easy part (which API endpoint to call) but not the hard parts (can this model follow the template? can this model use tools? does this model produce structured output?).
  - **Confidence level**: High. Both reviews provide different but complementary evidence that LiteLLM alone is insufficient. The synthesis should require a `ConversusAgent` abstraction on top of LiteLLM that handles capability validation, tool-use normalization, and output structure enforcement.
