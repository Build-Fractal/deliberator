# Functional-Typing Review: Spec 005 — Generalized Template Schema, Variables, and Linter

**Reviewer**: functional-typing
**Spec**: `specs/005-generalized-templates/spec.md`
**Implementation files reviewed**: `linter/models.py`, `linter/validate.py`, `linter/test_validate.py`, `schema/variables.yml`, `schema/modes/*.yml`, `pyproject.toml`

---

### Executive Summary

Spec 005 introduces a machine-readable variable schema and a development-time linter to catch template defects before multi-agent runs. The implementation materially advances the project's compliance with Constitution Principle IX (Functional Programming and Clean Code) and its Explicit Typing mandate. The linter (`validate.py`) is structured as a pipeline of pure functions composed in `validate_template`, the Pydantic models (`models.py`) enforce typed parsing of all YAML data, and the test suite (`test_validate.py`) is data-driven and thorough.

However, several violations of the functional programming and explicit typing mandates remain. The most significant are: impure side effects embedded in functions that should be pure (schema-loading functions call `sys.exit` and `click.echo`), a 28-entry hardcoded `MODE_PRESENCE` lookup table that duplicates information derivable from the schema, path-list fields typed as raw `str` instead of structured types, and the absence of a `Result` type pattern that would eliminate early-exit side effects. The spec itself (Section 6, Implementation Notes) underspecifies the paradigm requirements — it says "Python or shell" without mandating the functional style that the constitution requires.

My most important recommendation: replace `sys.exit()` side effects in schema-loading functions with a `Result[T, str]` return type so that all validation logic remains pure and composable, and the CLI layer is the sole site of side effects.

---

### Alignment

- **[Pydantic models for all YAML data]** (`models.py`, L1-270): Every YAML structure — `VariablesSchema`, `ModeSchema`, `DisputeConfig`, `ArbitrationConfig`, `CrossRoundSynthesisConfig`, and all seven phase-specific `TemplateContext` subclasses — is loaded into a Pydantic `BaseModel` before use. Raw dicts from `yaml.safe_load` are immediately passed to `model_validate`. This directly satisfies Constitution Principle IX's Explicit Typing mandate: "ALL data structures MUST use Pydantic models for validation and type safety. Raw dicts from YAML/JSON parsing MUST be loaded into typed Pydantic models before use." [`constitution.md`, L175-177].

- **[Pure validation functions]** (`validate.py`, L82-305): The five `check_*` functions (`check_unknown_variables`, `check_missing_required_variables`, `check_mode_specific_variables`, `check_required_headings`, `check_structural_markers`) are pure functions. They take typed inputs and return `list[str]` error lists without side effects. The composition in `validate_template` (L299-305) concatenates results cleanly. This aligns with the FP HOWTO's modularity and composability principles [`python-functional-howto.md`, L208-241] and Constitution Principle IX's requirement that functions be "stateless, composable, and testable" [`constitution.md`, L149-151].

- **[Full type annotations on function signatures]** (`validate.py`, `models.py`, `test_validate.py`): Every function has explicit type annotations for parameters and return values. Local variables inside functions also carry inline type annotations (e.g., `errors: list[str] = []`, `candidate: Path = Path(...)`, `rel_path: str = ...`). This satisfies Constitution Principle IX: "ALL function signatures MUST have explicit type annotations for every parameter and return value. No exceptions." [`constitution.md`, L173-174].

- **[Pydantic field validators for domain constraints]** (`models.py`, L52-71, L115-122): `VariableDefinition.validate_type` and `VariableDefinition.validate_phases` use `@field_validator` to enforce that type and phase values are drawn from the `VALID_*` frozensets. `ModeSchema.validate_mode` does the same for mode names. This is correct use of Pydantic's validation layer to encode domain invariants at the model boundary.

- **[Data-driven parametrized tests]** (`test_validate.py`, L119-465): Test cases are generated by pure functions (`all_template_cases`, `required_variable_cases`, `structural_marker_cases`, etc.) and fed to `@pytest.mark.parametrize`. Content mutation is done by pure helper functions (`remove_variable`, `inject_typo`, `remove_heading`, `remove_marker`). This is a textbook functional testing pattern — no mutable test state, no fixtures that modify the filesystem (temp files are created and deleted within `validate_mutated_template`).

- **[Frozenset usage for immutable collections]** (`models.py`, L23-35; `validate.py`, L82-84): `VALID_VARIABLE_TYPES`, `VALID_PHASES`, and `VALID_MODES` are `frozenset[str]`, and `extract_variables` returns `frozenset[str]`. This prevents accidental mutation and signals immutability at the type level, consistent with FP principles of immutable data structures [`python-functional-howto.md`, L134-137; `constitution.md`, L162-164].

### Missed Opportunities

- **[Result type for error-or-value returns]**: `load_variables_schema` (`validate.py`, L48-56) and `load_mode_schema` (L59-67) call `sys.exit(2)` on file-not-found, making them impure. The FP HOWTO states that functions should "only take inputs and produce outputs, and don't have any internal state that affects the output produced for a given input" [`python-functional-howto.md`, L113-116]. Returning a `Result[VariablesSchema, str]` (or raising a domain exception that the CLI layer catches) would keep these functions pure. The `find_project_root` function (L35-45) has the same issue. Impact: **high**.

- **[Structured path-list types instead of raw `str`]**: In `models.py`, fields like `TARGET_FILES`, `CROSS_REVIEWS_OF_ME`, `MY_CROSS_REVIEWS`, `ALL_REVISION_PATHS`, `ALL_REVIEWS`, `ALL_CROSS_REVIEWS`, `ALL_REVISIONS`, `ALL_DISPUTES`, and `ROUND_SYNTHESES` are all typed as `str` with comments like `# newline-separated paths`. This violates the Explicit Typing mandate: raw strings encoding structured data (lists of paths) should be typed as `list[Path]` with a custom Pydantic validator that splits on newlines. Constitution Principle IX states: "ALL data structures MUST use Pydantic models for validation and type safety" [`constitution.md`, L175-176]. A raw string containing newline-delimited paths is not a typed data structure. Impact: **high**.

- **[Derive `MODE_PRESENCE` from schema instead of hardcoding]**: `validate.py` L108-144 contains a 28-entry hardcoded dict `MODE_PRESENCE` that records which (phase, mode) pairs expect the `MODE` variable. This data is partially derivable from `variables.yml`'s `condition` field and from scanning actual templates. Hardcoding it creates a maintenance burden and a drift risk — if a new mode is added, this table must be manually updated. A pure function `compute_mode_presence(schema: VariablesSchema, modes: list[str]) -> dict[tuple[str, str], bool]` would be more aligned with functional principles and single-source-of-truth. Impact: **medium**.

- **[Generator-based template discovery]**: `main()` in `validate.py` (L317-367) uses imperative loops to discover and validate templates. A generator-based approach — `yield from validate_all_templates(root, modes, schema)` — would separate discovery from validation from reporting, improving composability. The FP HOWTO specifically advocates generators for pipeline-style processing [`python-functional-howto.md`, L553-589]. Impact: **low**.

- **[`functools.reduce` or `itertools.chain` for error aggregation]**: `validate_template` (L299-305) concatenates five lists with `+`. While readable, using `itertools.chain.from_iterable` would avoid creating intermediate lists and is more idiomatically functional. The FP HOWTO documents `itertools` as the standard tool for combining iterator outputs [`python-functional-howto.md`, L22-27]. Impact: **low**.

- **[Literal types for constrained string fields]**: `ModeSchema.mode` is typed as `str` with a runtime validator. Using `Literal["cooperative", "red-blue", "winner-take-all", "prisoners-dilemma"]` would provide static type checking in addition to runtime validation. Similarly, `VariableDefinition.type` could use a `Literal` for the six valid types. This gives mypy-level enforcement, not just Pydantic runtime checks. Constitution Principle IX says to "Use `typing` module constructs (`Optional`, `Union`, `Literal`) for precise type narrowing" [`constitution.md`, L183-184]. Impact: **medium**.

- **[Immutable `TemplateContext` models]**: The `TemplateContext` base class and its subclasses use `model_config = {"extra": "forbid"}` but do not set `frozen=True`. Pydantic v2 supports `model_config = {"extra": "forbid", "frozen": True}` to make instances fully immutable. Constitution Principle IX states: "When classes ARE used (Pydantic models...), prefer immutable data structures and minimize internal state" [`constitution.md`, L162-164]. Impact: **medium**.

### Off-Base Assumptions

- **[Spec assumes "Python or shell" is equally acceptable]** (spec.md, L362): Section 6, Implementation Notes says "The linter should be a script (Python or shell)." The Constitution Principle IX mandates explicit typing, Pydantic models, and functional programming practices — none of which are achievable in shell. The spec should mandate Python and reference the constitution's paradigm requirements. This is not a minor stylistic preference; the constitution's Explicit Typing mandate is "non-negotiable" [`constitution.md`, L171].

- **[Spec data model shows `required` field only on some variables]** (spec.md, L96-290): The example `variables.yml` in the spec omits the `required` field from most variable definitions, implying it defaults to true. The implementation (`models.py`, L48) correctly defaults `required` to `True`, but the spec never documents this default. This creates ambiguity about whether omission means "required" or "unspecified." The spec should state the default explicitly.

### Actionable Recommendations

1. **Purify schema-loading functions** (Priority: P1)
   - **Current state**: `load_variables_schema` (`validate.py`, L48-56), `load_mode_schema` (L59-67), and `find_project_root` (L35-45) call `sys.exit()` and `click.echo()` directly, making them impure.
   - **Proposed change**: These functions should raise a typed exception (e.g., `class SchemaLoadError(Exception)`) or return a union type. The `main()` CLI function should be the sole site of `sys.exit()` and user-facing output. Example: `def load_variables_schema(root: Path) -> VariablesSchema` raises `SchemaLoadError` on failure; `main()` catches it and calls `sys.exit(2)`.
   - **Rationale**: Constitution Principle IX requires functions to be "stateless, composable, and testable" [`constitution.md`, L149-151]. A function that calls `sys.exit` cannot be composed or tested without monkeypatching. The FP HOWTO defines pure functions as those that "only take inputs and produce outputs" [`python-functional-howto.md`, L113-116].
   - **Risk if ignored**: These functions cannot be imported and used in other contexts (e.g., an orchestrator calling the linter as a library) without risking process termination. Testing requires `pytest.raises(SystemExit)` hacks.

2. **Replace raw `str` path-list fields with `list[Path]`** (Priority: P1)
   - **Current state**: `models.py` L143, L189-190, L207, L222-225, L242, L257 use `str` for newline-separated path lists with inline comments.
   - **Proposed change**: Define a custom type `PathList = Annotated[list[Path], BeforeValidator(lambda v: [Path(p) for p in v.split('\n') if p.strip()] if isinstance(v, str) else v)]` and use it for all path-list fields. At minimum, change these to `list[Path]` with a field validator.
   - **Rationale**: Constitution Principle IX Explicit Typing mandate: "ALL data structures MUST use Pydantic models for validation and type safety" [`constitution.md`, L175-176]. A `str` containing structured data is the opposite of a typed data structure.
   - **Risk if ignored**: Consumers of these context models must parse paths manually, duplicating logic and introducing potential inconsistencies. Type checkers cannot verify correct usage.

3. **Use `Literal` types for constrained string enumerations** (Priority: P2)
   - **Current state**: `ModeSchema.mode` is `str` with a runtime `@field_validator` (`models.py`, L108, L115-122). `VariableDefinition.type` is `str` with a validator (L45, L52-60).
   - **Proposed change**: `mode: Literal["cooperative", "red-blue", "winner-take-all", "prisoners-dilemma"]` and `type: Literal["string", "integer", "path", "path-list", "conditional-block", "extracted-content"]`. Remove the corresponding `@field_validator` methods (Pydantic validates `Literal` fields automatically).
   - **Rationale**: Constitution Principle IX: "Use `typing` module constructs (`Optional`, `Union`, `Literal`) for precise type narrowing" [`constitution.md`, L183-184]. `Literal` provides both static and runtime validation, reducing code.
   - **Risk if ignored**: Type narrowing is only runtime, not static. Mypy and Pyright cannot verify correct mode/type strings at development time.

4. **Make `TemplateContext` models frozen** (Priority: P2)
   - **Current state**: `TemplateContext` and subclasses use `model_config = {"extra": "forbid"}` (`models.py`, L140) but instances are mutable.
   - **Proposed change**: `model_config = {"extra": "forbid", "frozen": True}`.
   - **Rationale**: Constitution Principle IX: "prefer immutable data structures and minimize internal state" [`constitution.md`, L162-164]. Context objects should be constructed once and read during template substitution — never mutated.
   - **Risk if ignored**: Nothing prevents downstream code from mutating a context object after construction, violating the assumption that template substitution is deterministic (Constitution Principle VII).

5. **Derive `MODE_PRESENCE` from schema data** (Priority: P2)
   - **Current state**: `validate.py` L108-144 hardcodes a 28-entry dict mapping (phase, mode) to boolean.
   - **Proposed change**: Add a `mode_presence` field to `variables.yml`'s `MODE` entry (a mapping of phase -> list of modes where MODE is expected), or compute it from the `condition` field via a pure function. Replace the hardcoded dict with a call to this function.
   - **Rationale**: Constitution Principle VI (Scripts Over Markdown) applies to hardcoded tables too — if data is derivable from structured config, it should not be duplicated in code. Constitution Principle IX prefers composable functions over static data.
   - **Risk if ignored**: When a fifth mode is added, a developer must remember to update both the schema and this hardcoded table. Drift between them produces silent false negatives.

6. **Mandate Python in spec Implementation Notes** (Priority: P2)
   - **Current state**: Spec Section 6 (L362) says "The linter should be a script (Python or shell)."
   - **Proposed change**: "The linter MUST be a Python script following Constitution Principle IX (functional programming, explicit typing, Pydantic models)."
   - **Rationale**: Constitution Principle IX is non-negotiable [`constitution.md`, L171]. Shell cannot satisfy the Explicit Typing mandate. Leaving "or shell" in the spec creates ambiguity about paradigm requirements.
   - **Risk if ignored**: A future implementor could choose shell, producing an artifact that violates the constitution and lacks type safety.

7. **Add `__all__` exports to `models.py`** (Priority: P3)
   - **Current state**: `models.py` exports all classes implicitly. No `__all__` declaration.
   - **Proposed change**: Add `__all__: list[str] = ["VariableDefinition", "VariablesSchema", "ModeSchema", "DisputeConfig", ...]` at the top of the module.
   - **Rationale**: Explicit exports are a clean code practice — they document the public API surface and prevent accidental import of internal symbols. Constitution Principle IX: "Code should be self-documenting through clear naming and structure" [`constitution.md`, L165-166].
   - **Risk if ignored**: Minor — but as the module grows, implicit exports make it unclear which symbols are stable public API vs internal implementation details.

8. **Type the `PHASE_CONTEXT_MODELS` mapping as `Final`** (Priority: P3)
   - **Current state**: `PHASE_CONTEXT_MODELS` (`models.py`, L262-270) is a module-level `dict` that could theoretically be mutated at runtime.
   - **Proposed change**: `PHASE_CONTEXT_MODELS: Final[dict[str, type[TemplateContext]]] = { ... }` (import `Final` from `typing`).
   - **Rationale**: Constitution Principle IX: "No mutable global state" [`constitution.md`, L153-154]. Marking it `Final` signals immutability to both developers and type checkers.
   - **Risk if ignored**: Minimal — but inconsistent with the `frozenset` pattern used elsewhere in the module for other constants.

9. **Document the `required: True` default in the spec** (Priority: P3)
   - **Current state**: Spec Section 3 data model (L96-290) shows `required: true` on only two variables (`PRIOR_FILES_SECTION`, `REMAINING_DISPUTES`). The implementation defaults `required` to `True` (`models.py`, L48).
   - **Proposed change**: Add a note to the spec's data model section: "Variables default to `required: true` when the field is omitted. Set `required: false` explicitly for optional variables."
   - **Rationale**: Explicit is better than implicit (Constitution Principle X / Zen of Python Output [`constitution.md`, L186-189]). The spec should not rely on readers knowing the implementation default.
   - **Risk if ignored**: A reader of the spec may assume omitted `required` means false, creating incorrect schema entries.
