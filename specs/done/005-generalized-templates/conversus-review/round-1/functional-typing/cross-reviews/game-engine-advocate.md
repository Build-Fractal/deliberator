# Cross-Review of game-engine-advocate's Review

**Cross-reviewer**: functional-typing
**Reviewing**: game-engine-advocate's review of spec 005
**Date**: 2026-03-21

---

### Dangerous Contradictions

- **Literal types vs. registry extensibility**
  - **game-engine-advocate claims**: "`VALID_MODES` is a frozen set, not a registry" and recommends replacing it with "a function `get_valid_modes()` that scans `schema/modes/*.yml` file names" or accepting "any mode string in the Pydantic model" (Actionable Recommendations, item 3). The same argument is made for `VALID_PHASES` (item 8): derive from schema or make augmentable at import time.
  - **functional-typing claims**: `ModeSchema.mode` should use `Literal["cooperative", "red-blue", "winner-take-all", "prisoners-dilemma"]` and `VariableDefinition.type` should use `Literal[...]`, eliminating the `@field_validator` methods entirely (Actionable Recommendations, item 3). This provides static type checking via mypy/Pyright in addition to runtime validation, per Constitution Principle IX's mandate to "Use `typing` module constructs (`Optional`, `Union`, `Literal`) for precise type narrowing" (`constitution.md`, L183-184).
  - **Why this is dangerous**: These two recommendations are mutually exclusive at the implementation level. A `Literal` type is a compile-time fixed enumeration -- it cannot be extended by scanning a directory at runtime. If both recommendations are adopted, the implementor must choose one, and the unchosen reviewer's concern goes unaddressed. Adopting `Literal` closes extensibility; adopting dynamic scanning loses static type safety.
  - **Suggested resolution**: Use `Literal` for the core type system (static checking for the four known modes) but provide a parallel `validate_mode_exists(mode: str, schema_dir: Path) -> bool` function that the linter calls to accept plugin-contributed modes. The Pydantic model for schema validation uses a `str` field with a runtime validator that calls this function, while the value-level `TemplateContext` models can use `Literal` for the known modes and a `PluginTemplateContext` variant (as game-engine-advocate proposes) for plugin data. This separates the schema-loading path (open, dynamic) from the value-validation path (closed, typed).

- **`extra = "forbid"` as correctness guarantee vs. extensibility blocker**
  - **game-engine-advocate claims**: "`extra = "forbid"` blocks plugin injection" and proposes either `extra = "allow"` on a plugin-aware variant or a `plugin_data: dict[str, Any]` escape hatch (Actionable Recommendations, item 2; Missed Opportunities, second bullet).
  - **functional-typing claims**: `TemplateContext` models should add `frozen=True` to the existing `extra = "forbid"` config, making instances fully immutable (Actionable Recommendations, item 4). Constitution Principle IX requires "prefer immutable data structures and minimize internal state" (`constitution.md`, L162-164).
  - **Why this is dangerous**: game-engine-advocate wants to relax the model boundary to accept unknown fields; functional-typing wants to tighten it further with immutability. If both are adopted without coordination, we get a frozen model that forbids extras (functional-typing's direction) alongside a plugin variant that allows extras (game-engine-advocate's direction) -- two divergent model hierarchies with no clear guidance on which to use when. Worse, game-engine-advocate's `dict[str, Any]` escape hatch directly contradicts Constitution Principle IX's prohibition on `Any` "unless wrapping an untyped third-party API" (`constitution.md`, L183-184).
  - **Suggested resolution**: Adopt `frozen=True` for the core `TemplateContext` hierarchy (functional-typing's position). For plugin extensibility, create a separate `PluginContext(BaseModel)` that is composed alongside -- not inherited from -- `TemplateContext`. Plugins populate `PluginContext` with their own typed Pydantic models, not raw `dict[str, Any]`. The orchestrator passes both objects to template rendering. This satisfies immutability, type safety, and extensibility without any single model trying to serve both purposes.

- **`MODE_PRESENCE` resolution direction**
  - **game-engine-advocate claims**: `MODE_PRESENCE` should be "derivable from the schema rather than hardcoded" and proposes encoding it in mode schema files as `mode_uses_in_phase: {review: true, revision: false}` or computing it by scanning templates (Actionable Recommendations, item 6).
  - **functional-typing claims**: `MODE_PRESENCE` should be derived via "a pure function `compute_mode_presence(schema: VariablesSchema, modes: list[str]) -> dict[tuple[str, str], bool]`" using the `condition` field from `variables.yml` (Actionable Recommendations, item 5).
  - **Why this is dangerous**: Both agree the hardcoded table must go, but the proposed replacement sources differ. game-engine-advocate wants the data in mode schema YAML files or derived from template scanning. functional-typing wants it computed from the existing `condition` field in `variables.yml`. If both are partially implemented, we get three sources of truth: `variables.yml` conditions, mode schema `mode_uses_in_phase`, and the (hopefully deleted) hardcoded dict. Two derivation paths for the same data guarantees drift.
  - **Suggested resolution**: Use functional-typing's approach -- derive from `variables.yml`'s `condition` field via a pure function -- but formalize the `condition` field syntax so it is machine-parseable rather than free-text. This keeps the single source of truth in `variables.yml` (where the variable metadata already lives) and satisfies game-engine-advocate's concern about scalability to new modes without adding a second YAML location.

### Tensions

- **Scope of spec 005 review: intrinsic quality vs. forward compatibility**
  - game-engine-advocate's review is primarily oriented around spec 007 (game engine) compatibility. Seven of ten recommendations and six of nine missed opportunities explicitly reference spec 007's needs. functional-typing's review evaluates spec 005 against Constitution Principle IX and internal consistency, with no reference to spec 007. Both perspectives are valid, but they create a priority tension: game-engine-advocate's P1 items (plugin namespace, extensible context, mode registry) are speculative -- they address a spec that is not yet implemented. functional-typing's P1 items (purify schema-loading functions, replace raw `str` path-lists) address code quality defects that exist today. If implementation bandwidth is constrained, adopting game-engine-advocate's P1s first could mean shipping forward-looking extension points while leaving impure functions and untyped data in the codebase.

- **`float`/`number` type addition**
  - game-engine-advocate recommends adding `float` or `number` to `VALID_VARIABLE_TYPES` (Actionable Recommendations, item 4) for spec 007's feature extraction pipeline. functional-typing does not address this but does recommend using `Literal` for the type field (Actionable Recommendations, item 3). If `Literal` is adopted for `VariableDefinition.type` with the current six types, adding `float` later requires modifying the `Literal` union -- a source code change. This is not a contradiction (both reviewers could agree on adding `float` to the `Literal`), but it highlights how functional-typing's static typing approach makes game-engine-advocate's extensibility concerns more concrete: every new type requires a code change, not just a schema change.

- **`PHASE_CONTEXT_MODELS` as `Final` vs. as extensible registry**
  - functional-typing recommends marking `PHASE_CONTEXT_MODELS` as `Final[dict[str, type[TemplateContext]]]` (Actionable Recommendations, item 8) to prevent runtime mutation, per Constitution Principle IX's "No mutable global state" (`constitution.md`, L153-154). game-engine-advocate identifies the same registry as "the exact pattern spec 007 needs for registering plugin-contributed context models" and envisions plugins extending it at load time (Alignment, fifth bullet). `Final` prevents exactly the runtime extension game-engine-advocate envisions. This is a lower-severity version of the Literal/registry contradiction: one reviewer wants to lock the interface for safety, the other wants to keep it open for extensibility.

- **Schema versioning and reproducibility**
  - game-engine-advocate recommends adding `schema_version: "1.0"` to `variables.yml` and mode schema files (Actionable Recommendations, item 5), citing spec 007's scenario replay system and Constitution Principle VII (Reproducibility). functional-typing does not address versioning but does note the absence of a documented `required: True` default as an implicit-vs-explicit problem (Actionable Recommendations, item 9; Off-Base Assumptions, second bullet). Both concerns point toward schema documentation maturity, but they approach it from different angles -- game-engine-advocate wants machine-readable version tracking, functional-typing wants human-readable defaults documentation. These are complementary but compete for spec amendment bandwidth.

- **Generator-based template discovery vs. plugin-aware validation**
  - functional-typing recommends refactoring `main()` to use generators for template discovery (Missed Opportunities, fourth bullet), separating discovery from validation from reporting. game-engine-advocate envisions plugin-aware validation where "a plugin that introduces new template variables could provide its own validation function composed alongside the existing ones" (Alignment, fourth bullet). If both are pursued, the generator pipeline needs to be designed to accept plugin-contributed validation steps -- not just core check functions. This is tractable but requires coordination: the generator architecture must be designed with composition hooks, not just linear piping.

### Safe Agreements

- **`MODE_PRESENCE` must not be hardcoded**
  - Both reviews identify `validate.py` L108-144's 28-entry `MODE_PRESENCE` dict as a maintenance risk that should be derived from schema data. game-engine-advocate cites scalability to plugin-introduced modes (Missed Opportunities, ninth bullet; Actionable Recommendations, item 6). functional-typing cites functional programming principles and single-source-of-truth (Missed Opportunities, third bullet; Actionable Recommendations, item 5). The convergence here is strong: both reviewers agree on the problem, and the disagreement on derivation source (discussed under Dangerous Contradictions) is a design detail, not a philosophical divide. Implementing either approach eliminates the maintenance burden both reviewers identify.

- **Pure validation functions are a strength**
  - Both reviews explicitly praise the `check_*` function composition pattern in `validate.py` L151-305. game-engine-advocate calls the "composable validation architecture (pure functions that return error lists)" compatible with plugin-aware validation (Alignment, fourth bullet). functional-typing calls the same functions "pure functions" that "return `list[str]` error lists without side effects" and credits the composition in `validate_template` as aligned with the FP HOWTO's modularity principles (Alignment, second bullet). This shared positive assessment strengthens the case for preserving this architecture as the foundation for any extensibility work.

- **Pydantic model hierarchy is architecturally sound**
  - game-engine-advocate identifies the `TemplateContext` base class with per-phase subclasses as establishing "a typed contract" that spec 007's `DeliberationState` can consume (Alignment, third bullet). functional-typing identifies the same hierarchy as satisfying Constitution Principle IX's Explicit Typing mandate (Alignment, first bullet). Both reviewers endorse the structural decision, differing only on whether it should be extended (game-engine-advocate) or tightened (functional-typing). The base architecture is not in question.

- **Spec should mandate Python, not "Python or shell"**
  - functional-typing explicitly calls out spec.md L362's "Python or shell" phrasing as an off-base assumption, arguing that Constitution Principle IX's typing and Pydantic mandates are impossible in shell (Off-Base Assumptions, first bullet; Actionable Recommendations, item 6). game-engine-advocate does not address this directly but implicitly assumes Python throughout -- every recommendation references Pydantic models, `@field_validator`, and Python type constructs. The absence of any shell consideration in game-engine-advocate's review is itself an implicit agreement that Python is the only viable implementation language for this spec's requirements.
