### Dangerous Contradictions

- **[Priority and handling of the STATUS.md / Principle IV conflict]**
  - **scope-boundary claims**: The constitution Principle IV conflict is a "Missed Opportunity" (not a scope violation) and recommends a P2 fix -- either adding a note to the Known Antipatterns section acknowledging the tension, or adding a "When This Does NOT Apply" clarification in the antipattern entry. Scope-boundary frames this as something the spec "neither addresses nor acknowledges" but treats it as a follow-up item, not a blocking issue. (Missed Opportunities, bullet 1; Actionable Recommendations, item 2, Priority P2)
  - **integration claims**: The same conflict is flagged as a blocking integration failure (Executive Summary, paragraph 2) and the top recommendation at P1 priority. Integration proposes amending Principle IV itself -- removing or qualifying the STATUS.md mandate, with options including removing the bullet, replacing it with derivation guidance, or adding a supersession note. Integration cites the constitution's own governance clause (L196-199) to argue the MUST-level mandate will override the catalog guidance. (Actionable Recommendations, item 2, Priority P1)
  - **Why this is dangerous**: If scope-boundary's P2 framing prevails and the fix is deferred, agents encountering both the constitution and the catalog will follow the constitution's MUST-level mandate (per governance L196-199) and continue maintaining STATUS.md -- defeating the antipattern system's purpose. If integration's P1 framing prevails but scope-boundary's concern about modifying Principle IV without a spec is valid, the amendment itself becomes a scope violation. Both reviews agree the tension exists, but the priority disagreement determines whether this ships with contradictory agent instructions or gets resolved first.
  - **Suggested resolution**: Adopt integration's P1 priority (the contradiction is live and will produce conflicting agent behavior immediately), but use scope-boundary's more conservative intervention -- a qualifying note within Principle IV rather than removing it. This could read: "STATUS.md maintenance is subject to the antipattern catalog; see `redundant-cache` in `antipatterns/catalog.md`." This resolves the contradiction without requiring a full principle rewrite or a separate spec, and respects scope-boundary's concern about not over-modifying the constitution without spec authorization.

- **[Scope of constitution T006 -- legitimate or over-scope]**
  - **scope-boundary claims**: T006 (constitution Known Antipatterns update) "goes beyond the spec's stated scope" because spec.md L109 only mentions SKILL.md and templates as integration points. Scope-boundary recommends either adding spec traceability (acceptance scenario or assumptions note) or explicitly documenting it as a scope extension. (Missed Opportunities, bullet 3; Actionable Recommendations, item 3, Priority P2; Off-Base Assumptions, bullet 1)
  - **integration claims**: Integration does not flag T006 as an over-scope concern. The constitution update is listed under Alignment as a positive integration point: "The Known Antipatterns section correctly references `antipatterns/catalog.md` as the catalog location and `specs/010-antipattern-steering/contracts/catalog-format.md` as the governing contract" (Alignment, bullet 5). Integration treats the constitution cross-reference as part of the system's functional coherence.
  - **Why this is dangerous**: If scope-boundary's position is adopted and T006 is retroactively flagged as requiring spec-level justification, this sets a precedent where any cross-reference addition to shared documents (constitution, CLAUDE.md) requires explicit spec authorization -- even when the cross-reference is purely informational. If integration's position is adopted without acknowledging the scope gap, future reviews will not know whether constitution edits require spec authorization or not. The rule becomes ambiguous.
  - **Suggested resolution**: Accept T006 as legitimate (integration's position) but adopt scope-boundary's recommendation to add a brief note to the spec's Assumptions section acknowledging constitution.md as an integration point. This closes the traceability gap without undoing the work or creating a precedent that informational cross-references need full spec coverage.

### Tensions

- **[Contract "Exact wording" divergence -- severity and fix location]**
  - Scope-boundary does not flag the divergence between the contract's SKILL.md Integration Contract (catalog-format.md L91, "Exact wording") and the actual SKILL.md step 2 wording (which adds keyword retrieval guidance per T008). Integration flags this explicitly as a Missed Opportunity at medium impact (Missed Opportunities, bullet 2) and recommends updating the contract to match SKILL.md (Actionable Recommendations, item 3, Priority P2). Both reviews implicitly agree that the contract and SKILL.md must be synchronized, but scope-boundary's silence on this point means it could be overlooked in the resolution phase. The tension: scope-boundary's thoroughness on spec-level traceability (T006) contrasts with its absence of comment on a contract-level inconsistency that has the same character.

- **[Maintenance section ambiguity -- how much structure is enough]**
  - Integration flags two related issues: (1) the contract template does not include the Maintenance section that exists in the catalog (Actionable Recommendations, item 4, P2), and (2) the Maintenance heading uses H2 like entries, creating potential parsing confusion (Missed Opportunities, bullet 3; Actionable Recommendations, item 5, P2). Scope-boundary does not raise either concern. Given scope-boundary's focus on structural completeness (e.g., verifying no template changes, confirming append-only structure), the absence of comment on the Maintenance section's structural ambiguity is a gap. The tension: scope-boundary treats the Maintenance section as correctly implemented (Alignment, bullet 5: "The Maintenance section in catalog.md correctly documents...") while integration treats its structure as an integration risk.

- **[Broken path -- same diagnosis, different scope of fix]**
  - Both reviews identify the `specs/001-antipattern-steering/examples/redundant-cache/` broken path as a P1 issue. Scope-boundary identifies it in catalog.md L33, tasks.md T003 and T011 (Missed Opportunities, bullet 2; Actionable Recommendations, items 1 and 4). Integration identifies it across six files: catalog.md, tasks.md (twice), quickstart.md (twice), and plan.md (Missed Opportunities, bullet 1; Actionable Recommendations, item 1). The tension is in completeness of the fix -- scope-boundary's fix covers 3 locations while integration covers 6. If only scope-boundary's locations are patched, three broken references remain in quickstart.md and plan.md.

- **[Constitution version bump]**
  - Integration raises the need for a constitution version bump from 1.1.0 to 1.2.0 per the constitution's own versioning rules (Actionable Recommendations, item 8, P3). Scope-boundary does not mention versioning at all. Given that scope-boundary is explicitly concerned with constitution traceability (T006 spec coverage), the absence of a version-bump recommendation creates tension: scope-boundary wants formal justification for the constitution edit but does not flag that the edit itself triggers a version increment per the constitution's governance rules.

- **[T011 validation status]**
  - Integration explicitly recommends unchecking T011 (marking it incomplete) because the validation condition it specifies cannot be met with the broken path (Actionable Recommendations, item 6, P2). Scope-boundary identifies the same underlying problem (the broken path in T011's checkpoint text) but recommends fixing the path reference rather than unchecking the task (Actionable Recommendations, item 4). The tension: fixing the path in T011 and leaving it checked implies the validation passed against the corrected path, which is historically inaccurate. Unchecking it preserves the record that the validation was not actually performed against a valid path. Both approaches have merit -- scope-boundary's is forward-looking (fix and move on), integration's is audit-preserving (mark the gap).
