# User-Advocate Cross-Review of Code-Verifier -- Round 2

## Dangerous Contradictions

### 1. The three-way provider default mismatch deepens the problem but the proposed fix still does not solve it for new users

Code-verifier's Round 2 finding #5 identifies that `EngineConfig.provider` defaults to `"anthropic"` (config.py L77), the CLI defaults to `"mock"` (cli/__init__.py L101), and the SDK defaults to `"mock"` (sdk.py L155). Code-verifier's recommendation #4 proposes a documentation note in config-reference.md explaining the three-way mismatch. My review (Missed Opportunities #3) identified the `uv run` prefix inconsistency across the quickstart and CLI reference as another surface where defaults silently diverge from what the user expects.

The danger is that these are two facets of the same underlying problem -- the documentation presents multiple entry points (index page, quickstart, CLI reference, SDK page, config reference) and each one establishes different expectations about defaults. Code-verifier's solution documents the provider mismatch in one location (config-reference.md), but a user who starts from the quickstart, follows `--provider mock` successfully, and then writes a config file omitting `provider:` will get `anthropic` behavior with no warning. The config-reference.md note helps only if the user reads the config reference before writing their config -- which is exactly the kind of linear reading assumption that both reviews agree users do not follow. The Round 1 synthesis converged on a cli.md note (P2 item #10), which is better positioned, but even that assumes the user consults the CLI reference before writing a config file. I believe code-verifier's three-way mismatch finding is the strongest new evidence in Round 2 and deserves P1 treatment: a warning directly in the config-reference.md `provider:` field documentation, not just a cross-reference.

### 2. The `run` command epilog bug and the `--phase review` documentation gap compound into a broken self-help loop

Code-verifier's Round 2 finding #1 identifies that the `run` command's epilog at cli/__init__.py L95 shows `--phase synthesis`, which is not a valid Click choice. Finding #2 identifies that `--phase review` is a valid option but the docs never explain what a partial run produces. My review (Missed Opportunities #4) identified the quickstart's failure to show expected output as a separate problem.

These three findings are individually moderate but together they create a trap: a user who runs `conversus run --help` sees `--phase synthesis` as an example, tries it, gets a Click error, falls back to `--phase review` (which does work), gets partial output, and has no documentation to explain why the output is incomplete. Code-verifier correctly flags the epilog as a code bug (P1 recommendation #1), but the `--phase review` documentation gap (P2 recommendation #9) should be elevated. A user who encounters the epilog bug and then tries the only other `--phase` value needs to understand what they will get. Without that documentation, they may conclude the tool is broken rather than that they ran a partial phase. Code-verifier's priority split (epilog fix at P1, phase documentation at P2) under-weights the compounding effect.

### 3. The `cost_estimate` nullability gap and `construct_objective` failure modes share a pattern the synthesis has not named

Code-verifier's Round 2 finding #2 (Off-Base Assumptions) identifies that `Deliberation.cost_estimate` can return `None` but the docs show it as always returning a dict. Finding #1 (Off-Base Assumptions) identifies that `construct_objective()` can raise `ValueError` or `RuntimeError` but the docs show only the happy path. My review (Off-Base Assumptions #2) identified the SDK sync-first resolution as needing a copy-paste-test framing, which is fundamentally about the same principle: first examples must not silently fail.

The pattern is that the SDK documentation consistently presents nullable returns and exception-raising functions as if they always succeed. This is not a single-page problem -- it is a documentation style choice that will produce bugs at every integration boundary. Code-verifier correctly identifies both instances but recommends them at different priorities (P2 for cost_estimate, P3 for construct_objective). I would frame these as a single P2 recommendation: audit the SDK page for all return types that include `None` or functions that raise exceptions, and add a brief "Returns `None` when..." or "Raises `ValueError` when..." note to each. This prevents the whack-a-mole pattern where we fix two instances now and discover three more next round.

### 4. The `classify` export gap persists across both reviews but neither proposes a user-facing mitigation

Code-verifier's Round 2 finding #6 confirms that `classify` is defined in `engine/sdk.py` but not exported from `engine/__init__.py`. The SDK docs at sdk.md L134 show `from engine.sdk import classify`, which works but bypasses the public API boundary. My review did not identify this issue independently. The Round 1 synthesis's actionable item #16 recommends the code fix (add to `__init__.py` exports) and a docs note about dual namespaces.

The danger is timing: if the docs ship before the code fix, users will import from the undocumented internal path and their code will break if the internal module structure changes. Code-verifier treats this as a confirmed finding but does not flag the sequencing risk. The mitigation is straightforward: either the code fix ships with the docs, or the docs use the current working import path (`from engine.sdk import classify`) with a note that this will move to `from engine import classify` in a future release. Either approach is safe; shipping the docs with the future import path before the code change is not.

## Tensions

### 1. Code-level precision vs. user-facing impact weighting

Code-verifier's Round 2 review is the strongest source-verified review in this process. Every finding includes file paths, line numbers, and confirmed behavior. This precision is invaluable for implementation. However, the priority assignments reflect code-level severity rather than user-facing impact. The epilog bug (finding #1) is P1 because it is a code bug; the `--phase review` documentation gap (finding #2) is P2 because it is a docs gap. From a user's perspective, the documentation gap causes more confusion than the epilog bug -- the epilog bug produces a clear Click error ("invalid choice"), while the undocumented partial run produces ambiguous output that the user cannot interpret. My review consistently weights issues by "what happens to someone who encounters this" rather than "what category of artifact contains the error." Neither weighting is wrong, but the implementation plan should consider both when assigning priority.

### 2. Three-way default mismatch: document the complexity vs. simplify the defaults

Code-verifier's recommendation #4 proposes documenting the three-way provider default mismatch (config defaults to `anthropic`, CLI defaults to `mock`, SDK defaults to `mock`). This is the correct documentation fix. My review (Missed Opportunities #1, index page) identified a parallel problem: the index page says `pip install conversus` while the quickstart says `uv sync`, creating a different kind of default mismatch (install method). Both reviews agree that contradictory defaults across entry points are harmful. The tension is whether the response should be documentation (explain the complexity) or simplification (align the defaults). Code-verifier operates within the constraint that spec 031 is a docs spec and recommends documentation. I would note that the provider default mismatch is a strong candidate for a follow-up code change: if the CLI `run` command consulted `config.provider` as a fallback before defaulting to `mock`, the three-way mismatch would collapse to a two-way mismatch, and the documentation fix would become trivial. The Round 1 synthesis recommended filing a follow-up issue for this; code-verifier's Round 2 findings provide the specific evidence that follow-up issue needs.

### 3. New findings vs. carried-forward findings: how to prevent Round 3 scope creep

Code-verifier's Round 2 produces six new findings on top of four carried-forward items from Round 1. My Round 2 produces five new findings on top of the Round 1 base. The total recommendation count across both reviews is now substantial. The tension is between thoroughness (every real issue should be captured) and actionability (an implementation plan with 25+ items across three priority tiers risks nothing being done). Code-verifier's approach -- carrying forward Round 1 items verbatim and adding new items separately -- is clean and traceable. My concern is that Round 3 should focus on reconciling and prioritizing the existing findings rather than discovering more. Both reviews would benefit from a strict scope cap: Round 3 should produce a ranked implementation plan from the existing findings, not new source-code spelunking.

### 4. The `CallbackEmitter` documentation gap: implementation detail or developer-facing contract?

Code-verifier's Round 2 finding #4 identifies that `CallbackEmitter` takes a callable but the CLI instantiates it with a `RichProgressHandler` instance, meaning the handler must implement `__call__`. The architecture.md event system table describes `CallbackEmitter` at a high level without this detail. My review did not identify this issue. The tension is whether this is an implementation detail (the handler pattern is internal to the CLI) or a developer-facing contract (someone building a custom emitter needs to know the callable signature). Code-verifier presents it as documentation gap but does not assign it a priority, which suggests uncertainty about its audience. I lean toward P3: a developer building a custom emitter is an advanced user who will read the source, and the architecture page is not the right place for callable signatures. But code-verifier's instinct to flag it is correct -- it should land somewhere in the developer guide's event system section if one is created.

### 5. Index page discrepancies: code-verifier's silence vs. user-advocate's alarm

My Round 2 review's strongest new findings center on the index page: the "4 competition modes" claim, the `pip install conversus` vs. `uv sync` discrepancy, and the missing prerequisites. Code-verifier's Round 2 review does not mention the index page at all -- its new findings are all source-code-verified issues in CLI internals, SDK nullability, and export boundaries. This is not a contradiction (code-verifier's mandate is code verification, not front-door evaluation), but it means the index page issues have only one advocate in Round 2. The Round 1 synthesis captured the "4 modes" fix as P1 item #1, but the `pip install` discrepancy and missing prerequisites are new findings that need code-verifier's verification: does a `pip install conversus` PyPI package exist? If not, the index page contains a command that will fail on first contact, which is exactly the kind of code-docs mismatch that code-verifier is best positioned to confirm or refute.

## Safe Agreements

### 1. All Round 1 convergence items are correctly characterized and should proceed without further debate

Code-verifier's Round 2 "Convergence items I fully support" section re-confirms all seven Round 1 convergence items with updated source verification. My Round 2 "Alignment" section independently confirms the same seven items. Neither review reverses any Round 1 concession. The seven convergence items (decide 4-mode note, scaffolds YAML fix, plugins config key, API reference prose, determine_verdict split, provider precedence note, estimate_cost_usd documentation) represent the stable core of this review process and should be implemented as specified in the Round 1 synthesis.

### 2. The synthesizer's dispute resolutions are accepted by both reviews

Code-verifier explicitly accepts the synthesizer's resolutions on sync-first SDK Quick Start, implementation priority (parallel tracks), and quickstart micro-hints. My review independently supports the same three resolutions. The sync-first resolution (lead with `asyncio.run()` wrapper) is accepted by both reviews, with my review adding the "copy-paste test" framing as a strengthening rationale rather than a competing proposal. The parallel-tracks resolution for onboarding vs. extensibility priority is accepted without modification by both reviews. The micro-hint resolution is accepted by both reviews, with my review proposing a minor extension to cover the `uv` not-installed case. None of these acceptances are conditional or partial -- they represent genuine alignment.

### 3. Code-verifier's new source-level findings fill gaps that user-advocate's review cannot reach

Code-verifier's Round 2 findings on the epilog bug (finding #1), AgentCompleted optional field (finding #3), CallbackEmitter callable pattern (finding #4), and three-way provider defaults (finding #5) are all source-verified discoveries that my review methodology (reading docs as a new user) would never produce. I accept all four findings as accurate and valuable. In particular, the epilog bug is a clear P1 code fix that both reviews should endorse for Round 3. These findings demonstrate the complementary value of the two review perspectives: user-advocate identifies where users get confused, code-verifier identifies why the confusion exists at the source level.

### 4. The documentation style pattern of hiding failure modes is a shared concern

Code-verifier's Off-Base Assumptions #1 and #2 (construct_objective failure modes, cost_estimate nullability) and my Off-Base Assumptions #2 (copy-paste test for SDK examples) both point to the same documentation habit: presenting only the happy path. Code-verifier approaches this from type-safety (nullable returns should be documented as nullable), while I approach it from user experience (first examples should not silently fail). These are complementary framings of the same problem, and both reviews would benefit from the synthesis treating "happy-path-only SDK documentation" as a systemic issue rather than a collection of individual findings.
