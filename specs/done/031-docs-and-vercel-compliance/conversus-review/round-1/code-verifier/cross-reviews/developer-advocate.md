## Dangerous Contradictions

- **Hard blocks evaluation: two functions with different capabilities**
  - **developer-advocate claims**: "The `_check_hard_blocks` function (`base.py`, L302-352) only supports the three-part comparison form (`variable operator threshold`), not bare truthy checks. The bare truthy form is only supported in `_evaluate_single_hard_block` (`base.py`, L378-441), which is called by `_evaluate_hard_block_rules`. The `DomainPlugin.evaluate_hard_blocks()` method (`base.py`, L605-626) correctly delegates to `_evaluate_hard_block_rules`, so the documented behavior is correct for domains" (Off-Base Assumptions, item 2).
  - **code-verifier claims**: My review did not flag this as an issue at all. I verified the `DomainPlugin` scoring pipeline and `determine_verdict` signature but did not trace the internal hard block function dispatch to check whether the documented three rule forms (truthy, comparison, boolean equality) all work via the domain ABC's public API.
  - **Why this is dangerous**: developer-advocate correctly identified that two separate hard block evaluation functions exist with different capabilities, but then concluded the docs are "correct for domains." If anyone refactors to consolidate these functions, or if a developer calls `_check_hard_blocks` directly (it is module-level, not underscore-hidden by import), they will get silently different behavior -- bare truthy checks like `secrets_exposed` will be logged as "Invalid hard block condition" and skipped. My review's silence on this point means neither review produced a clear, actionable recommendation to either (a) consolidate the two functions, or (b) add a doc warning that the internal `_check_hard_blocks` function has a different capability set.
  - **Suggested resolution**: Merge both perspectives. The docs are technically correct for the public `DomainPlugin.evaluate_hard_blocks()` path as developer-advocate notes. Add a brief note to the architecture or API reference page that the internal `_check_hard_blocks` function (used by the standalone scoring pure functions) only supports the three-part comparison form, not bare truthy checks. This prevents accidental misuse if someone imports the helper directly.

- **`determine_verdict` documentation: misleading example vs. incomplete contract**
  - **developer-advocate claims**: "The building-domains guide (`building-domains.md`, L126-132) shows `determine_verdict` [...] but the base class's default `_determine_verdict` implementation (`base.py`, L355-375) [...] only checks hard blocks and per-dimension thresholds. The guide's example implements logic that is *not* the default -- it is the code-review domain's override" (Off-Base Assumptions, item 1). developer-advocate recommends separating into "Default behavior" vs. "Customizing verdict logic" (Recommendation 7).
  - **code-verifier claims**: "The docs (building-domains.md L126-132) show `determine_verdict(self, overall, hard_blocks, thresholds, dimensions, variables)` with 5 parameters. This matches the actual code [...] However, the inline code example [...] shows a simpler version that only checks `hard_blocks` and `overall < thresholds.get("minimum_overall", 0.7)`, never using the `dimensions` or `variables` params. The doc example works but is misleading about the method's full contract" (Off-Base Assumptions, item 3). code-verifier recommends updating the example to demonstrate at least one of the ignored parameters (Recommendation 8).
  - **Why this is dangerous**: Both reviews identify the same documentation defect but propose different fixes that could conflict. developer-advocate wants to split the section into two parts (default behavior explanation + override example), while code-verifier wants to update the single example to use more parameters. If both are implemented without coordination, the section could end up with a corrected "default behavior" explanation from developer-advocate's fix AND a revised example that still shows `minimum_overall` (which is not the default) from code-verifier's fix. The result would be more confusing than the current state.
  - **Suggested resolution**: Adopt developer-advocate's structural recommendation (split into "Default behavior" and "Customizing verdict logic") as the framework, then apply code-verifier's recommendation within the "Customizing verdict logic" subsection by ensuring the override example demonstrates the `dimensions` and `variables` parameters. This addresses both concerns: the default behavior is accurately described, and the override example shows the full contract.

- **Scaffolds endpoint: YAML vs. JSON file listing**
  - **developer-advocate claims**: No mention of the `/scaffolds` endpoint only listing `.json` files despite the documentation encouraging YAML scaffolds. The review notes that scaffold YAML format is "well-documented" (Alignment, item 4) and does not flag any discrepancy.
  - **code-verifier claims**: "The `/scaffolds` API endpoint at `conversus/domains/api.py` L208 only globs `*.json` files [...] The docs encourage YAML scaffolds but the API endpoint silently ignores them" (Recommendation 2, Priority P1).
  - **Why this is dangerous**: developer-advocate's review evaluated the scaffold documentation as a positive ("well-documented with a concrete example") and specifically praised the YAML format. This could lead a reviewer implementing developer-advocate's recommendations to leave the scaffold docs unchanged, reinforcing YAML as the primary format -- while the API endpoint (`api.py` L208: `domain.scaffold_dir.glob("*.json")`) silently ignores YAML files. A developer following the docs would create `startup-mvp.yml` as shown, mount the API router, and get an empty list from `/scaffolds`. This is a silent data loss scenario that developer-advocate's review does not surface.
  - **Suggested resolution**: Accept code-verifier's P1 recommendation. Either fix `api.py` L208 to glob for `("*.yml", "*.yaml", "*.json")` extensions, or update the building-domains doc to note that the API listing endpoint only discovers JSON scaffolds (while `load_scaffold()` and `score()` accept both formats). developer-advocate's positive assessment of the scaffold docs should be revised to note this gap.

### Tensions

- **API reference stubs: narrative docs vs. autodoc directives**
  - **developer-advocate's position**: "The API reference pages [...] contain only mkdocstrings directives. Without a running mkdocs build, these pages are unreadable. They provide no narrative context, no usage examples, and no explanation of the relationships between the listed members. A developer reading the docs on GitHub or in a static context gets nothing" (Missed Opportunities, item 5; Recommendation 4, Priority P2).
  - **code-verifier's position**: My review flagged the `api/domains/base.md` page for not listing `DomainStore`, `JSONLStore`, or `SQLiteStore` (Missed Opportunities, item 5; Recommendation 5, Priority P2), but did not challenge the autodoc-only format itself.
  - **Nature of tension**: developer-advocate wants narrative documentation added before each autodoc directive; code-verifier wants the autodoc coverage expanded to include missing classes. These pull in different directions on effort allocation: adding narrative text is a different kind of work than adding more autodoc members. If the narrative sections are added first, the additional autodoc members might not get mentioned in the narrative. If the autodoc members are added first, the pages are still unreadable without mkdocs.
  - **Coordination needed**: Both should be done together. The narrative section should be written knowing the full member list (including store classes), so it can explain the relationship between `DomainPlugin`, `DomainStore`, `JSONLStore`, and `SQLiteStore`. The implementation order should be: (1) add missing autodoc members (code-verifier's fix), then (2) add narrative sections that reference all members (developer-advocate's fix).

- **Plugin wiring vs. config reference completeness**

Must the plugin be installed as a package, or can it be a local file?" (Missed Opportunities, item 2; Recommendation 2, Priority P1). Also: "The config-reference page [...] has no section for the `plugins:` key" (Missed Opportunities, item 7; Recommendation 3, Priority P1).
  - **code-verifier's position**: My review did not flag the missing `plugins:` config key or the plugin discoverability gap. I verified the `load_plugins()` function behavior (L229-295) and the `importlib.import_module` path but focused on code accuracy rather than developer onboarding completeness.
  - **Nature of tension**: developer-advocate identified two related gaps (plugin wiring guide + config reference) and wants both as P1. My review's silence on these points does not contradict them, but it means the verification angle -- whether the proposed documentation for `plugins:` schema would match the actual `load_plugins()` behavior -- has not been confirmed. developer-advocate's proposed schema (`name`, `package`, `config`) matches the actual code at `base.py` L251-254, but the behavior when `config` is missing (defaults to `{}`) and when `package` is missing (logs warning, skips) should be documented as well.
  - **Coordination needed**: developer-advocate's P1 recommendations are well-founded. The config reference `plugins:` section should note the fallback behaviors that code verification confirms: missing `package` logs a warning and skips, missing `config` defaults to `{}`, and failed instantiation logs a warning and skips (no crash). This enriches the schema doc with the resilience guarantees that are actually implemented.

- **Provider precedence documentation**
  - **developer-advocate's position**: No mention of the provider precedence confusion between CLI `--provider mock` default and config file `provider: anthropic` default.
  - **code-verifier's position**: "Config `provider` default is 'anthropic', not 'mock'" (Off-Base Assumptions, item 2; Recommendation 3, Priority P2). The CLI flag at `engine/cli/__init__.py` L101 defaults to `mock`, while `engine/config.py` L77 defaults to `anthropic`, and the docs do not explain which wins.
  - **Nature of tension**: developer-advocate praised the cost estimation and provider documentation as aligned without noting this precedence confusion. code-verifier found that running `conversus run config.yml` without `--provider` uses `mock` (CLI default), not the config's `provider` field, because the CLI flag is passed separately to `run_engine()`. The concern is that developer-advocate's positive assessment of the CLI/SDK documentation could be taken as "no changes needed" when a real user confusion vector exists.
  - **Coordination needed**: developer-advocate's overall positive assessment of the provider documentation should be qualified with code-verifier's finding. A one-line addition to the `run` command docs -- "The `--provider` CLI flag overrides the `provider` field in the config file. When neither is explicitly specified, the CLI defaults to `mock`." -- resolves both perspectives.

- **End-to-end domain tutorial vs. code accuracy**
  - **developer-advocate's position**: "There is no example of: creating a `DomainContext`, calling `extract()` then `score()`, persisting with a store, or mounting the API router on a running FastAPI app [...] A developer cannot build and *run* a domain from the guide alone" (Missed Opportunities, item 1; Recommendation 1, Priority P1).
  - **code-verifier's position**: My review did not flag the absence of an end-to-end tutorial. I focused on verifying the accuracy of what is documented rather than evaluating completeness of the developer journey.
  - **Nature of tension**: developer-advocate is asking for new documentation content; code-verifier would need to verify that any new end-to-end example actually matches the code. The `score()` method signature at `base.py` L711-714 accepts `variables: dict[str, Any]` and `scaffold: str | Scaffold`, which means the tutorial must show the string-based scaffold name pattern (not a `Scaffold` object) to match the simplest usage. The `create_record()` method at L804-810 takes optional `equilibrium_score` and `convergence` params that should be mentioned. Any tutorial written without code verification could introduce new inaccuracies.
  - **Coordination needed**: developer-advocate should draft the end-to-end tutorial; code-verifier should review every code example in it against the actual source before it ships. The draft should use the string-based scaffold name pattern (`domain.score(variables, "default")`) and mention both optional `create_record()` parameters.

### Safe Agreements

- **Plugin ABC documentation is accurate and complete**
  - **Shared position**: Both reviews confirm the Plugin ABC documentation faithfully reflects the source code. developer-advocate: "The plugin guide successfully explains the Plugin ABC, the hook lifecycle, and the produces/consumes data flow pattern with enough detail that a developer could build a plugin from the guide alone" (Executive Summary). code-verifier: "The `Plugin` class attributes `name`, `hooks`, `produces`, `consumes`, the `execute()` signature, and `__init_subclass__` validation all match `conversus/plugins/base.py` L126-208" (Alignment, item 3); "The 4 hook points [...] match `HookPoint` enum" (Alignment, item 4).
  - **Combined evidence**: developer-advocate validated from a usability perspective (can a developer build a plugin from the guide alone?), while code-verifier validated from a correctness perspective (do the documented signatures, enums, and behaviors match the source?). Both lines of evidence converge: the plugin documentation is both usable and accurate.
  - **Confidence level**: high.

- **Error handling documentation is missing and needed**
  - **Shared position**: Both reviews agree that the documentation does not explain what happens when plugin `execute()` or domain `extract()` raises an exception. developer-advocate: "Neither the plugin guide nor the domain guide explains what happens when `execute()` or `extract()` raises an exception. The source code [...] shows that exceptions are caught, logged, and skipped -- but this is not documented" (Missed Opportunities, item 3; Recommendation 5, Priority P2). code-verifier: confirmed the exception handling behavior at `base.py` L519-525 (plugins) and L700-708 (domains) in the source verification, and noted the resilient skip-on-error behavior in the plugin loading path (L264-269).
  - **Combined evidence**: developer-advocate assessed the user impact (developers will raise exceptions expecting propagation, then see silent failures). code-verifier verified the actual exception handling code paths. Together, these confirm both the gap and its real-world impact. The skip-and-log behavior is a deliberate design choice (FR-008) that affects how developers should structure their code, and it is invisible in the current documentation.
  - **Confidence level**: high.

- **8 modes match VALID_MODES but `decide` restricts to 4**
  - **Shared position**: Both reviews agree that the 8 modes documented in `modes.md` and `config-reference.md` are accurate against `VALID_MODES` in `conversus/schemas/modes.py`. Both also note the `decide` command restricts `--mode` to 4 modes. developer-advocate: "The quickstart immediately uses `--provider mock`" and references mode documentation as accurate (Alignment, items 1-2). code-verifier: "The docs list exactly 8 modes [...] These match `VALID_MODES` in `conversus/schemas/modes.py` L9-18 exactly" (Alignment, item 1); "The actual Click definition at `engine/cli/__init__.py` L240-244 constrains `--mode` to exactly these same 4 modes" (Off-Base Assumptions, item 1; Recommendation 1, Priority P1).
  - **Combined evidence**: developer-advocate validated the mode documentation from a usability lens, while code-verifier traced the `decide` command's Click constraint to the exact source line. The 4-mode restriction is confirmed in code at L240-244 and is not mentioned in the docs. Both perspectives agree this creates user confusion -- the docs prominently feature all 8 modes, but ad-hoc `decide` silently rejects 4 of them.
  - **Confidence level**: high.
