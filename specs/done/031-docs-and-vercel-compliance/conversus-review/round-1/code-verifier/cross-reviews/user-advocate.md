## Dangerous Contradictions

- **CLI `decide` mode count: documentation clarity versus documentation accuracy**
  - **user-advocate claims**: The CLI docs (cli.md L57) list only 4 modes for `decide` and the index page saying "4 competition modes" is a factual inconsistency with modes.md's 8 modes that "will confuse users trying to understand the scope of the tool." Recommendation #3 (P1) proposes updating the index page to say "8 deliberation modes" and listing all 8. Recommendation #10 (P3) proposes updating the CLI `--mode` description to list all 8 mode names. (Off-Base Assumptions section; Recommendations #3, #10)
  - **code-verifier claims**: The `decide` command's Click definition at `engine/cli/__init__.py` L240-244 genuinely constrains `--mode` to exactly 4 modes via `click.Choice(["cooperative", "winner-take-all", "prisoners-dilemma", "red-blue"])`. The CLI docs are *correct* in listing only 4 for `decide`. The remaining 4 modes (negotiation, resource-allocation, fair-division, mechanism-design) require a config file via `conversus run`. (Off-Base Assumptions section; Recommendation #1)
  - **Why this is dangerous**: If user-advocate's recommendation #10 is adopted literally -- updating cli.md's `decide` command to say "See Deliberation Modes for all 8 options" and listing all 8 mode names as valid `--mode` values -- users will try `conversus decide "question" --mode negotiation` and get an unhelpful Click error ("Invalid value for '--mode'"). The docs would be actively misleading about what the CLI accepts. Meanwhile, if user-advocate's recommendation #3 is adopted (updating the index to say "8 modes") without also clarifying that `decide` only supports 4 of them, users will have a reasonable expectation that all 8 work everywhere. The two recommendations compound to create worse confusion than the current state.
  - **Suggested resolution**: Adopt my recommendation #1 and a modified version of user-advocate's recommendations. The cli.md `decide` section should keep listing 4 modes but add an explicit note: "The `decide` command supports 4 modes. The remaining 4 modes require a config file via `conversus run`. See [Deliberation Modes](modes.md) for all 8." The index page should say "8 deliberation modes" (user-advocate's #3) with the qualifier that ad-hoc `decide` supports a subset. Alternatively, update the Click definition to accept all 8 modes, which eliminates the discrepancy entirely.

- **Provider default: "mock" or "anthropic"?**
  - **user-advocate claims**: The auth resolution order and mock-first default are strengths of the documentation. The review praises the mock provider default (Alignment section: "The quickstart defaults to `--provider mock` on the very first command") and the auth resolution documentation (Alignment section: "The three-step credential resolution... is documented explicitly"). No issue is flagged with provider precedence between CLI and config. (Alignment section, items 1 and 4)
  - **code-verifier claims**: The CLI `--provider` defaults to `"mock"` (`engine/cli/__init__.py` L101-103), but `EngineConfig.provider` defaults to `"anthropic"` (`engine/config.py` L77), and `parse_config()` at L572 also defaults to `"anthropic"`. The documentation does not explain which wins when both are in play. A user who sets `provider: anthropic` in their config and runs `conversus run config.yml` without `--provider` may get mock responses because the CLI flag default takes precedence. (Off-Base Assumptions section, item 2; Recommendation #3)
  - **Why this is dangerous**: user-advocate's review validates the provider documentation as correct and clear, which would signal to implementers that no changes are needed. My review identifies a real precedence confusion that could cause silent provider substitution. If only user-advocate's feedback is acted on, this issue remains unfixed. A user who explicitly writes `provider: anthropic` in their config file and omits `--provider` from the command line would reasonably expect Anthropic to be used -- but the CLI's mock default overrides it.
  - **Suggested resolution**: Add the provider precedence clarification I recommended (Recommendation #3): "The `--provider` CLI flag overrides the `provider` field in the config file. When neither is specified, the CLI defaults to `mock`." This does not contradict anything in user-advocate's review; it supplements it.

- **SDK async-first versus sync-first example ordering**
  - **user-advocate claims**: Recommendation #4 (P2) proposes moving the sync `asyncio.run()` pattern to be the first "Quick start" example and demoting the async pattern to a secondary "Async usage" section, on the basis that "most first-time SDK users will be writing scripts, not async applications." (Missed Opportunities section, item 6; Recommendation #4)
  - **code-verifier claims**: The SDK's `Deliberation.run()` method is natively async (confirmed at `engine/sdk.py` L125-332). The `Result` model, event subscription, and all core APIs are designed async-first. My review does not recommend changing the example order because the SDK genuinely is async-first -- the sync wrapper is a convenience, not the primary interface. My review focuses instead on verifiable inaccuracies (import paths, missing exports, signature mismatches). (Alignment section, items on Result model fields and event types)
  - **Why this is dangerous**: If both positions are adopted, the documentation would simultaneously present sync as the primary pattern (user-advocate) while the API reference and architecture docs describe an async-first design (my review validates this as accurate). This creates a conceptual mismatch: the quickstart teaches sync, the architecture says async-first, and developers must reconcile the contradiction. A developer who learns the sync pattern first may structure their entire integration around `asyncio.run()` wrappers, missing the event subscription pattern (which requires an async context) entirely.
  - **Suggested resolution**: Keep `await` as the first example (it is the native interface) but prefix the Quick Start code block with a 2-line note: "The SDK is async-first. In a synchronous script, wrap with `asyncio.run()` -- see [Async patterns](#async-patterns) below." This respects the architectural truth (my position) while immediately addressing the new-user confusion (user-advocate's concern) without reordering.

## Tensions

- **Scope of "what docs should fix" versus "what code should fix"**
  - **user-advocate's position**: All 10 recommendations target documentation changes. The review explicitly avoids recommending code changes, treating the docs as the sole remediation surface. For example, the 4-vs-8 mode inconsistency is addressed by updating the index page text, not by expanding the Click constraint. (Recommendations #3, #10)
  - **code-verifier's position**: Several recommendations identify cases where the code is the root cause and should be fixed alongside or instead of the docs. Recommendation #1 offers an alternative: "update the Click definition to accept all 8 modes." Recommendation #2 proposes changing the `/scaffolds` endpoint glob from `*.json` to include YAML files. Recommendation #4 proposes adding `classify` to `engine/__init__.py` exports. (Recommendations #1, #2, #4)
  - **Nature of tension**: user-advocate's docs-only approach is safer and faster to ship but leaves code-level bugs (the scaffolds endpoint silently ignoring YAML files, the `classify` import inconsistency) in place. My code-fix approach is more thorough but has a larger blast radius. Neither is wrong; they optimize for different things.
  - **Coordination needed**: The final recommendation set should explicitly label each item as "docs change," "code change," or "both." Items where the docs accurately reflect buggy code (scaffolds endpoint, `classify` export) need code fixes regardless of documentation changes.

- **API reference stub treatment: prose summary versus mkdocstrings rendering**
  - **user-advocate's position**: Recommendation #6 (P2) says the API reference pages (construction.md, plugins/base.md, domains/base.md) are "effectively blank" when read as raw Markdown on GitHub, and proposes adding 3-5 sentences of prose above each `:::` directive. (Missed Opportunities, item 6; Recommendation #6)
  - **code-verifier's position**: My review notes that `docs/api/domains/base.md` L6 uses a bare `:::` directive without member filtering (unlike plugins/base.md and construction.md which enumerate members explicitly). I also flag that `DomainStore`, `JSONLStore`, and `SQLiteStore` are missing from the API reference entirely. (Missed Opportunities, item 5; Recommendation #5)
  - **Nature of tension**: user-advocate wants prose summaries added to existing stubs for GitHub readability. I want the stubs to be technically complete (correct member lists, missing modules added). These are complementary but pull priority in different directions -- cosmetic accessibility versus technical completeness. If only prose is added without fixing the member lists, the rendered MkDocs site will still have gaps (missing DomainStore protocol). If only the member lists are fixed without prose, the GitHub experience remains poor.
  - **Coordination needed**: Both changes should be applied together. Add prose introductions (user-advocate) AND fix member lists and add the missing store.md page (code-verifier). The domains/base.md page especially needs both: it currently has no member list at all, which means even in rendered MkDocs it will dump the entire module's private API.

- **Quickstart prerequisites: how much context is enough?**
  - **user-advocate's position**: Recommendation #1 (P1) proposes a full "Prerequisites" section before "Install" covering Python 3.12+, `uv` with install link and `pip` fallback, and API key requirements. Recommendation #5 (P2) adds a troubleshooting section for common failures. Combined, these would add significant length to the quickstart. (Recommendations #1, #5)
  - **code-verifier's position**: My review does not address quickstart prerequisites because they are outside my verification scope (no code claim to verify). However, the CLAUDE.md project instructions state: "Documentation is meant to be very simple and straightforward, we must avoid bloating it with unnecessary information. It must be pragmatic, to the point, succint and practical."
  - **Nature of tension**: user-advocate's recommendations would make the quickstart more accessible but longer. The project's explicit documentation philosophy ("succint and practical") pushes toward minimal documentation. A full prerequisites section with install links, pip fallbacks, and a troubleshooting section could double the quickstart's length.
  - **Coordination needed**: Implement prerequisites as a brief 2-3 line callout ("Requires Python 3.12+ and uv. Install uv: `curl -LsSf https://astral.sh/uv/install.sh | sh`. Alternative: `pip install conversus`.") rather than a full section. Keep troubleshooting in a separate page linked from the quickstart, not inline.

- **determine_verdict documentation: incomplete example versus incomplete signature**
  - **user-advocate's position**: Does not flag the `determine_verdict` example in building-domains.md. The developer guide is noted as having "no issues found from user perspective." (Referenced Documentation section)
  - **code-verifier's position**: The `determine_verdict` example at building-domains.md L126-132 shows an override that only uses `hard_blocks` and `overall`, ignoring `dimensions` and `variables` parameters. The actual signature at `conversus/domains/base.py` L628-634 takes 5 parameters. The example teaches an incomplete pattern. (Off-Base Assumptions, item 3; Recommendation #8)
  - **Nature of tension**: From a user-advocate perspective, the example "works" and gets the concept across. From a code-verifier perspective, it teaches developers to ignore two parameters they might need, and it misrepresents the override contract. The tension is between example simplicity and API fidelity.
  - **Coordination needed**: Update the example to acknowledge all 5 parameters in the signature while keeping the body simple. The body can still check only `hard_blocks` and `overall`, but a comment should note: "# `dimensions` and `variables` are available for domain-specific logic."
