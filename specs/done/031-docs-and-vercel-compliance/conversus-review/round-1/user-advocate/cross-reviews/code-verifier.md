# Cross-Review of code-verifier by user-advocate

### Dangerous Contradictions

- **`decide --mode` scope: documentation bug vs. design gap**
  - **code-verifier claims**: The CLI docs (cli.md L57) list only 4 modes for `decide`, which matches the actual Click definition at `engine/cli/__init__.py` L240-244. code-verifier frames this as a "documentation clarity issue rather than an error" (Off-Base Assumptions, bullet 1) and recommends either adding a note explaining the restriction or updating the code to accept all 8 modes (Recommendation #1).
  - **user-advocate claims**: My review (Recommendation #10) flags the same 4-vs-8 gap from the opposite direction -- that cli.md listing only 4 modes without linking to the full modes page silently hides the other 4 modes from users who land on the CLI page first. I recommended cross-linking to modes.md and listing all 8 mode names. Separately, my Off-Base Assumptions bullet 3 flagged the index.md "4 competition modes" claim as a factual inconsistency with the 8 modes documented elsewhere.
  - **Why this is dangerous**: code-verifier's recommendation says "add a note to cli.md explaining that `decide` supports a subset" or alternatively "update Click to accept all 8." My recommendation says "list all 8 mode names" in the cli.md `--mode` description. If both are implemented without coordination, the cli.md page could simultaneously say `decide` only supports 4 modes and also list all 8 mode names -- a direct self-contradiction on the same page. The underlying question is whether the 4-mode restriction is intentional design or an incomplete implementation, and the two reviews approach this from different assumptions.
  - **Suggested resolution**: First determine the design intent: if `decide` is meant to be a quick-start command that only supports the 4 "core" modes, then document the restriction clearly in cli.md (code-verifier's approach) and ensure the modes page and index page explain the two tiers. If the restriction is just an implementation gap, expand the Click definition to all 8 modes (code-verifier's alternative). Either way, fix the index.md "4 competition modes" claim, which both reviews agree is wrong.

- **Provider default: "mock" vs. "anthropic" -- who is confused?**
  - **code-verifier claims**: The CLI `--provider` defaults to `mock` (cli.md L27), while `EngineConfig.provider` defaults to `"anthropic"` (engine/config.py L77). code-verifier identifies this as a precedence issue where "running `conversus run config.yml` without `--provider` uses `mock` (CLI default), not the config's `provider` field, because the CLI flag overrides" (Off-Base Assumptions, bullet 2). The recommendation (#3) is to document the precedence.
  - **user-advocate claims**: My review did not flag the provider default inconsistency at all. I focused on the user-facing behavior (mock works without a key, anthropic needs one) and praised the auth resolution documentation (Alignment, bullet 4) without noticing the underlying config-vs-CLI default tension.
  - **Why this is dangerous**: code-verifier's finding reveals a real trap: a user writes `provider: anthropic` in their config, runs `conversus run conversus.yml` without `--provider`, and gets mock responses because the CLI default silently overrides. If code-verifier's recommendation is implemented (documenting precedence) but the user-facing flow is not updated to match user expectations, users will still get surprised. If the user-advocate perspective (that the mock default is fine for zero-friction onboarding) is left unchallenged, the precedence trap remains undocumented.
  - **Suggested resolution**: Adopt code-verifier's recommendation to document precedence explicitly. Additionally, consider whether the CLI should respect the config file's `provider` field when one is present -- i.e., the CLI default should only apply when neither CLI flag nor config field is set. This resolves both the code-verifier's accuracy concern and the user-advocate's expectation that what you write in the config is what you get.

- **API reference stubs: "correct mkdocstrings directives" vs. "empty pages for GitHub readers"**
  - **code-verifier claims**: The API reference pages (construction.md, plugins/base.md, domains/base.md) use mkdocstrings directives and code-verifier evaluates them as accurate references to the correct modules and members (Referenced Documentation section lists them without flagging them as incomplete). The missed opportunity for DomainStore (Missed Opportunities, bullet 5) focuses on missing content, not the rendering problem.
  - **user-advocate claims**: My review (Missed Opportunities, bullet 6; Recommendation #6) flags these same pages as "effectively blank" when read as raw Markdown on GitHub, which is "the most common discovery path for new open-source projects." I recommended adding 3-5 sentences of prose above each directive.
  - **Why this is dangerous**: code-verifier's review implicitly treats the mkdocstrings directives as adequate documentation because they will render correctly in a built MkDocs site. The user-advocate review says the raw-Markdown reading experience is the primary evaluation surface. If the documentation team accepts code-verifier's framing (the directives are correct, no structural change needed), the GitHub discovery experience remains empty. If they accept the user-advocate framing (add prose), the mkdocstrings output may become redundant with the manually-written summaries.
  - **Suggested resolution**: Add brief prose summaries above each `:::` directive as the user-advocate recommends. This is additive -- it does not break the mkdocstrings rendering and fixes the GitHub readability gap. code-verifier's recommendation to add DomainStore coverage should be incorporated in the same pass.

### Tensions

- **Accuracy-first vs. accessibility-first prioritization**
  - **code-verifier's position**: All 9 recommendations prioritize code-documentation parity. P1 items are the `decide` mode restriction and the scaffolds endpoint JSON-only glob -- both cases where the docs say one thing and the code does another (Recommendations #1, #2).
  - **user-advocate's position**: P1 items are the missing prerequisites section, the unexplained slash commands, and the "4 modes" factual error on the index page (Recommendations #1, #2, #3). These are user-facing barriers to entry.
  - **Nature of tension**: code-verifier's priorities protect users who are already past the onboarding stage and actively writing configs or building domains. user-advocate's priorities protect users who have not yet successfully completed their first deliberation. Both are valid, but a limited documentation sprint must choose which to tackle first.
  - **Coordination needed**: Assign the two P1 sets to different work streams: code-verifier's P1s are code changes or targeted doc edits (narrow scope), while user-advocate's P1s are new prose sections in quickstart.md and guided-workflow.md (broader scope). Both can proceed in parallel without conflict.

- **SDK async-first framing vs. sync-first onboarding**
  - **code-verifier's position**: The SDK docs are evaluated for signature accuracy and import correctness. code-verifier confirms that `Result` model fields match (Alignment, bullet 6), event types match (Alignment, bullet 7), and `classify` import path works (Missed Opportunities, bullet 1). The async-first presentation is not flagged as an issue.
  - **user-advocate's position**: The SDK quick start showing `await` as the first example is flagged as a medium-impact missed opportunity (Missed Opportunities, bullet 5) and a P2 recommendation (#4) because most Python developers will paste the first example into a script and get a `SyntaxError`.
  - **Nature of tension**: code-verifier evaluates documentation against source code correctness. The `await` example is technically correct -- `Deliberation.run()` is indeed async. user-advocate evaluates documentation against user success probability. The tension is whether "correct" or "most likely to succeed on first paste" should govern the ordering of examples.
  - **Coordination needed**: Both positions can coexist by keeping the async example as the "canonical" form (code-verifier's accuracy standard) while placing the `asyncio.run()` sync wrapper first with a brief note like "The SDK is async-native. For scripts, wrap with `asyncio.run()`." This satisfies accuracy (the async nature is stated) and usability (the first example works in a plain script).

- **Scope of "documentation" under review**
  - **code-verifier's position**: Reviews exclusively the target doc files listed in the spec, verifying claims against source code. References to index.md, guided-workflow.md, and mcp-setup.md are absent from the review since they are not in the target file list.
  - **user-advocate's position**: Reviews the full user journey, following links out of the target files into index.md, guided-workflow.md, and mcp-setup.md. Several high-impact findings (the "4 modes" claim on index.md, the slash command barrier in guided-workflow.md, the missing `uv` explanation) come from these adjacent files.
  - **Nature of tension**: code-verifier's strict scoping produces higher confidence on the files reviewed but misses cross-file inconsistencies that affect user experience. user-advocate's broader scoping catches journey-level problems but cannot verify code-level accuracy.
  - **Coordination needed**: The synthesis should incorporate the user-advocate's cross-file findings as additive items, not as corrections to code-verifier's review. code-verifier's scope was intentionally constrained to source-code verification; the broader user-journey issues are a different category that both reviewers would likely agree matters.

- **`determine_verdict` example: incomplete vs. sufficient-for-teaching**
  - **code-verifier's position**: The `determine_verdict` example in building-domains.md (L126-132) is flagged as incomplete because it ignores the `dimensions` and `variables` parameters from the real signature (Off-Base Assumptions, bullet 3; Recommendation #8, P3).
  - **user-advocate's position**: My review read the building-domains doc and found "no issues from user perspective" (Referenced Documentation). The simplified example teaches the override pattern without overwhelming a new domain author.
  - **Nature of tension**: code-verifier wants the example to demonstrate the full contract so developers do not write partial overrides. The user-advocate perspective is that a minimal example is less intimidating and teaches the core pattern first. Over-specifying the example risks making the "Building Domains" guide feel like API reference rather than a tutorial.
  - **Coordination needed**: Keep the current simplified example as the primary teaching tool, but add a second "advanced override" example below it (or a note saying "For full access to dimension scores and raw variables, see the `determine_verdict` signature in the API reference") that shows the `dimensions` and `variables` parameters in use. This satisfies both pedagogical clarity and contract completeness.

Both reviews agree this is well-documented and correct.
  - **Combined evidence**: code-verifier's source-level verification (formula matches code) combined with user-advocate's usability assessment (the worked example with "3 agents = 16 launches" makes it concrete) provides both accuracy and accessibility confirmation. code-verifier additionally identifies an undocumented `estimate_cost_usd()` function (Missed Opportunities, bullet 2) that could further strengthen this already-good section.
  - **Confidence level**: high.

- **Plugin ABC documentation is accurate and usable**

The complete logging plugin example at the end provides a copy-paste starting point that both perspectives value.
