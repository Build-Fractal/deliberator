# Devil's Advocate Revision: Monorepo vs Polyrepo Decision

## Revision Iteration 1

**Cross-reviews considered:**
- Pragmatist's cross-review of Devil's Advocate
- Devil's Advocate's cross-review of Pragmatist

### Recommendation Dispositions

**1. Isolate the Schema Problem (P1) — Surviving**
Both the Pragmatist's cross-review (Safe Agreements §1) and my cross-review of the Pragmatist (Safe Agreements §1) identify this as the strongest convergence point between both perspectives. The Pragmatist's cross-review explicitly states: "Any synthesis that doesn't start here is ignoring both perspectives." No challenge was raised to the substance of this recommendation — only the Pragmatist's cross-review notes a tension in confidence level (Tensions §5), where the Pragmatist treats the schema fix as near-certain while I treat it as a hypothesis. I maintain the hypothesis framing: the schema fix should be implemented immediately *and* its sufficiency should be validated over 4-6 weeks before declaring the monorepo question resolved. This is not softening — it is intellectual honesty about whether two incidents fully characterize the coordination pain.

**2. Require Asymmetric Risk Assessment (P1) — Modified**
The Pragmatist's cross-review (Dangerous Contradictions §2) argues this recommendation conflicts with the "just ship the fix" approach: if the surgical schema fix is low-cost and reversible, spending weeks on formal risk assessment before deploying it is analysis overkill. This is a valid hit. My original framing implied the risk assessment should precede *any* action, but the Pragmatist is right that the schema fix doesn't need probabilistic analysis — it's a 2-day CI job with obvious upside and trivial downside. **Modified position:** The asymmetric risk assessment applies specifically to the monorepo migration decision, not to the schema fix. If and when the team revisits the monorepo question (after the schema fix has been validated or found insufficient), the risk assessment becomes essential — because at that point, the team is considering a multi-month commitment with asymmetric failure modes. The assessment is gating the expensive decision, not the cheap one.

**3. Decompose Migration Cost Into Workstreams (P1) — Surviving**
The Pragmatist's cross-review (Tensions §1) notes that presenting this decomposition alongside a "defer" recommendation sends mixed signals — the team hears "don't do this yet" and "here's a detailed plan for doing it." My cross-review of the Pragmatist (Dangerous Contradictions §3) identified the same tension from the other side: the Pragmatist's "4-8 weeks" estimate and my "3-4 months" estimate produce incompatible risk assessments. The decomposition survives precisely because it resolves this conflict. The reason aggregated estimates diverge (the Pragmatist's 4-8 weeks vs. my 3-4 months) is that aggregated estimates hide workstreams. The decomposition is not a migration plan — it is a tool for honest estimation whenever the team evaluates the monorepo option. If the team defers as the Pragmatist recommends, this decomposition should be the framework they use when they revisit. If the monorepo question is live now, the decomposition prevents the "4-8 weeks" estimate from going unchallenged.

**4. Benchmark CI Duration Under Monorepo (P2) — Modified**
The Pragmatist's cross-review (Tensions §3) argues this is premature if the monorepo decision is deferred. My cross-review of the Pragmatist (Tensions §4) raised the same point from the resource angle: running both tooling benchmarks and CI benchmarks consumes 2-3 engineer-weeks during a growth phase. Both valid. **Modified position:** The CI benchmark should be sequenced *after* the schema fix validation period, and only triggered if the team is actively considering the monorepo path. It should not be a pre-commitment spike run in parallel with the schema fix. However, if the monorepo decision becomes live, this benchmark is non-negotiable — the Safe Agreements across both reviews (Pragmatist's Safe Agreements §4, my cross-review Safe Agreements) confirm that both perspectives independently concluded CI could degrade under a naive monorepo. You cannot make a CI-speed argument for the monorepo without measuring it.

**5. Evaluate the "Thin Shared Repo" Middle Path (P2) — Modified**
The Pragmatist's cross-review (Dangerous Contradictions §1) identifies a real scope conflict between my "thin shared repo" (proto schemas + shared libraries + integration tests) and the Pragmatist's narrower "shared-protos repo" (proto files + generated code packages only). The Pragmatist argues my maximalist version risks recreating coordination overhead in a fourth repo that nobody owns. My own cross-review of the Pragmatist (Dangerous Contradictions §2) acknowledged these are mutually exclusive designs. **Modified position:** The shared repo scope should start narrow — proto files and `buf` validation only, matching the Pragmatist's formulation. Shared libraries and integration tests should *not* be pulled into this repo initially. The scope can expand if and only if the team identifies a concrete problem that the narrow scope doesn't solve. I was wrong to bundle integration tests into the shared repo; integration tests belong in CI pipelines that pull from all repos, not in a repo that becomes a dependency of all services. The forcing function of cross-repo integration tests is that they run *across* repos — co-locating them defeats the purpose.

**6. Stress-Test the Scaling Argument (P2) — Surviving**
The Pragmatist's cross-review (Tensions §2) notes a confidence-level divergence: I treat the scaling argument as "actively misleading" while the Pragmatist treats it as "speculative, defer it." Both reviews agree on direction (monorepo scaling is not automatic), but the Pragmatist's softer framing is more appropriate for a recommendation. That said, the core challenge survives because neither cross-review disputes the substance. The question's implicit assumption that monorepos scale better at 25-30 engineers remains unchallenged by evidence in either review. No one argued that a 30-person startup without platform engineers will find a monorepo *easier* to manage than a polyrepo with proper cross-repo tooling. The stress test is necessary because the scaling argument is the monorepo's strongest remaining justification once the schema problem is solved independently — and it needs to survive scrutiny in both directions, not just the pro-monorepo direction.

**7. Define Rollback Criteria (P2) — Modified**
My cross-review of the Pragmatist (Dangerous Contradictions §4) identified a scope conflict: the Pragmatist defines rollback criteria for "any migration" with qualitative thresholds, while I define them specifically for the monorepo with quantitative thresholds. Both approaches have gaps — mine is too narrow (polyrepo-with-tooling also needs exit criteria), the Pragmatist's is too vague ("developer satisfaction drops below threshold" is unmeasurable). **Modified position:** Rollback criteria should be unified into a single framework that applies to whichever path is chosen. The framework should include both quantitative triggers (CI time thresholds, merge conflict frequency, tooling maintenance time as percentage of engineering capacity) and a qualitative escape valve (structured developer survey at defined intervals — not "satisfaction drops," but "survey at 4 weeks and 8 weeks with specific questions about workflow friction"). This addresses both the Pragmatist's valid point that any migration needs exit criteria and my valid point that the criteria must be measurable.

**8. Name the Opportunity Cost (P3) — Modified**
The Pragmatist's cross-review (Dangerous Contradictions §4) argues this recommendation is calibrated for the monorepo migration, not for the schema fix — and applying opportunity-cost analysis to a 2-day CI job is overkill that delays the obvious first move. Correct. **Modified position:** Opportunity cost analysis applies only to the monorepo migration decision, not to the schema fix or the shared-protos repo setup. If the team is considering a multi-month monorepo migration, they must name what ships later because of it. If they are implementing a 2-day schema CI gate, they do not need to run a prioritization exercise against the product roadmap. The recommendation's priority drops from P3 to P3-conditional: it activates only when the monorepo path is under serious consideration.

### New Recommendations

**N1. Mandate a Validation Window Before Revisiting Repo Structure (P1)**
*Source: Tension between Pragmatist's "defer 3-6 months" and my cross-review's warning about deferring into a data vacuum (Dangerous Contradictions §1).*

The Pragmatist recommends deferring the monorepo decision 3-6 months. My cross-review argues that deferral without structured instrumentation produces no new information — the team arrives at the 3-month mark with the same anecdotal evidence. These are both right. The fix: define a validation window (6-8 weeks after the schema CI gate is deployed) with explicit instrumentation. During this window, the team tracks: (a) schema-related incidents (should drop to zero), (b) cross-repo coordination time per cross-cutting change (measured in hours, not vibes), (c) developer-reported friction points via a structured bi-weekly survey. At the end of the window, the team has quantitative data to decide whether the monorepo question is still live. If schema incidents are zero and coordination overhead is tolerable, the monorepo is deprioritized with evidence. If coordination pain persists despite the schema fix, the monorepo discussion reopens with real data instead of two dramatic incidents.

**N2. Unify the Shared Repo Scope Decision Before Implementation (P1)**
*Source: Dangerous Contradictions §1 in Pragmatist's cross-review and §2 in my cross-review of Pragmatist.*

Both reviews propose a shared repository but with conflicting scope. Implementing either without resolving scope creates confusion. The team must make a single, explicit decision: the shared repo contains proto schema files and `buf` validation configuration, and nothing else at launch. Shared libraries stay in their current locations. Integration tests stay in CI pipelines that pull from multiple repos. Scope expansion requires a proposal reviewed by all three squads. This prevents the "mini-monorepo" failure mode the Pragmatist warned about and prevents my original over-broad scoping from creating a fourth repo with unclear ownership.

### Position Summary

The cross-review process sharpened one thing above all: the schema fix and the monorepo question are two separate decisions on two separate timelines, and my original review didn't draw that line cleanly enough. Three of my eight recommendations were implicitly scoped to "the overall decision" when they should have been scoped specifically to the monorepo migration — the asymmetric risk assessment, the opportunity cost naming, and the CI benchmark are all irrelevant to a 2-day schema CI gate and become essential only when a multi-month structural migration is on the table. The Pragmatist's cross-review correctly identified this calibration error. My modified positions now explicitly gate these recommendations behind the monorepo decision becoming live, rather than applying them to the entire problem space.

What survived without modification: the schema problem must be isolated first, migration costs must be decomposed into workstreams (because the 4-8 week vs. 3-4 month estimation gap is real and dangerous), and the scaling argument needs to be stress-tested in both directions. These recommendations were not effectively challenged by either cross-review — the Pragmatist's review offered complementary concerns (timing, sequencing) but did not dispute the substance. The strongest safe agreement across both reviews is that the monorepo tooling options are all problematic for this polyglot stack without a platform team, and a monorepo without proper tooling is the worst possible outcome.

My strongest remaining recommendation is the new one: mandate a structured validation window with explicit instrumentation before revisiting repo structure. The Pragmatist's "defer 3-6 months" and my "diagnose before committing" converge on the same insight — the team shouldn't make a structural decision under incident pressure — but diverge on what happens during the deferral period. Without instrumentation, deferral is just procrastination. With instrumentation, it's an experiment that produces the data the team actually needs to make this decision well. The schema CI gate is the intervention; the validation window is the measurement of whether the intervention was sufficient. If it was, the monorepo question dissolves. If it wasn't, the team knows exactly what coordination problems remain and can evaluate structural changes against specific, quantified pain — not two scary incidents and a vague sense that things should be better.
